# 15 · 标识符体系：ULID 与旧格式兼容

> **文档类型：设计类**（按 `docs/specs/AGENTS.md` 治理约定）——只因设计变更修改。
> 状态：v1 · 2026-11-02
> 归属：rust 内核域（crate 结构见 [05-crate-structure.md](05-crate-structure.md)，执行状态见 [ROADMAP.md](ROADMAP.md)）
> 上游决策：[00-overview.md §7 ADR-003](00-overview.md)（本文是实现该 ADR 的设计展开）

## 1. 问题

系统里所有“有身份的实体”——会话、agent、后台任务、回合、消息、审批请求、问答请求、定时任务、协作会话——都用 128 位标识符指称。这类标识符的生成与解析分散在多处，格式约定只存在于各处调用点的字符串拼接里。由此产生三类现实问题：

- **不可排序。** 随机标识符不携带时间信息，任何“按产生顺序”的需求都只能另存时间戳，而时间戳在多机/多进程场景下并不保证单调。
- **格式约定没有单一事实源。** 生成用什么格式、解析接受哪些拼写、前后缀清单有哪些，不同模块各自实现，新增一处前缀就可能漏掉一处的解析。
- **与协议面不一致。** 传输契约里已经有一类标识符按字典序可排序的格式约定（请求追踪 id），引擎侧却仍用随机格式，两套并存的差异需要长期解释。

## 2. 目标终态

| # | 终态 | 可验收的判定 |
|---|---|---|
| ID-1 | **新生成的实体标识符一律是 ULID**（128 位、48 位毫秒时间戳 + 80 位随机、Crockford Base32 26 字符） | 新建会话、新建任务、新建审批请求的标识符载荷都是 26 字符合法 ULID |
| ID-2 | **旧格式（UUID）继续可读**：解析与反序列化同时接受 ULID 与 UUID，存量会话、任务、事件日志不需要迁移即可继续打开、继续回放 | 用旧版产生的会话目录与事件日志启动，会话可列出、可继续对话 |
| ID-3 | **规范形态逐字保真**：以规范形态读入的标识符再写出时字符串完全一致；非规范形态规范化后幂等 | 旧事件日志里的规范形态标识符读入后再序列化，逐字符相同；非规范形态两次往返后稳定 |
| ID-4 | **标识符发源地唯一**：新生成与解析只有一处实现，任何模块不得自行拼接或自行解析标识符 | 工作区内无 `uuid` 生产依赖；无独立的标识符解析实现 |
| ID-5 | **“无身份”语义显式化**：表示“主 agent / 未知来源”的哨兵值有唯一规范形态，旧数据里该哨兵的任何历史拼写都归一到它 | 旧日志中哨兵的任一历史拼写反序列化后与规范哨兵相等 |
| ID-6 | **wire 形状不变**：标识符在 JSON 里仍是字符串，字段名、nesting 与现值完全相同 | 同一事件的新旧序列化结果，除标识符取值本身外字段完全一致 |

## 3. 概念

### 3.1 标识符的两个组成部分

每个实体标识符 = **前缀** + **载荷**。

- **载荷**：128 位值的文本形态。新生成时是 ULID（26 字符）；存量数据里是 UUID（36 字符带连字符，或 32 字符无连字符）。
- **前缀**：标明实体类别，用 `-` 或 `_` 与载荷连接。前缀是**给人看的**，不参与解析幂等性判断。

| 前缀 | 实体 | 出现面 |
|---|---|---|
| `session-` / `session_` | 会话（`_` 为旧版目录名拼写，只读兼容） | 会话目录名、wire 事件、REST 路径 |
| `agent-` | agent（主 agent 用哨兵，不带后缀注册） | 事件、子 agent 目录 |
| `task-` | 后台任务 | 任务事件、任务工具入参/出参 |
| `turn-` | 回合 | 事件、分叉锚点 |
| `msg-` | 消息 | 事件 |
| `run-` | 定时任务的一次执行 | 定时任务事件 |
| `cron-` | 定时任务定义 | 定时任务存储 |
| `draft-` | 定时任务候选草案（待用户确认） | web 侧草案 |
| `goal-` | 目标 | 目标事件 |
| `plan-` | 计划 | 计划事件 |
| `act-` | 技能激活 | 技能激活事件 |
| `term_` | 终端会话（下划线连接） | 终端池 |
| `f_` | 附件/文件索引项（下划线连接） | 文件存储 |

不在表内的字符串（如回合内步骤序号、`step-1` 这类既有测试数据）不是实体标识符，不参与本文的生成与解析约定。

跨域术语的规范定义（实体标识符、哨兵值、请求追踪 id）登记在 [../glossary.md](../glossary.md) X 节；本节只是域内视图。

### 3.2 哨兵值

“没有身份”不是“一个随机的身份”。主 agent 没有自己注册的 id，未知来源的审批请求也没有。这类情况用**全零载荷**表示，它必须是一个可比较的常量，而不是每次生成的随机值。历史数据里全零载荷存在多种拼写（带连字符、不带连字符），它们必须归一到同一个值，否则“是不是主 agent”的判断会对旧数据失效。

### 3.3 时间顺序保证的边界

ULID 的字典序仅在**毫秒时间戳不同**时保证与产生顺序一致；同一毫秒内的顺序由 80 位随机部分决定，是随机的。因此：

- 任何**业务顺序**需求（会话列表、任务列表、消息顺序）必须以显式顺序字段（发布序号、`created_at`）为准，**不得**用标识符字典序替代。
- 标识符字典序只作为**同类同时刻的展示兜底**使用，不做正确性承诺。

## 4. 架构

### 4.1 标识符发源地：`mirri-id`

新增叶子 crate `mirri-id`，位于依赖图底层：不依赖任何其他 `mirri-*` crate。

```
mirri-proto ──┐
mirri-os ─────┤
mirri-id ─────┼──→ mirri-core ──→ mirri-transport ──→ mirri-server / mirri-embedded / mirri-remote
              │                                                                   ↑
              └──→ mirri-persistence · mirri-collaboration · mirri-plugin-host ───┘
```

为什么必须是独立 crate 而不是放进 `mirri-core`：`mirri-collaboration`、`mirri-persistence`、`mirri-plugin-host` 都需要生成标识符，但它们位于 `mirri-core` **下方**（`mirri-core` 依赖它们）。把标识符放进 core 会造成反向依赖。当前仓库没有其他合适的公共层（`mirri-os` 是执行环境抽象、`mirri-proto` 是 wire 类型）。（各 crate 的职责与依赖规则见 [05-crate-structure.md](05-crate-structure.md) §2–§3。）

### 4.2 类型

`mirri-id` 对外只提供一个值类型 `Id`：

| 项 | 约定 |
|---|---|
| 内部表示 | 128 位整数（`u128`），是唯一参与相等、哈希、比较的部分 |
| 原文 | 不保存。序列化时由 128 位按**读入时的形态类别**输出（见 4.4） |
| 相等 / 哈希 | 只比较 128 位值，与文本拼写无关（带/不带连字符的同一 UUID 相等） |
| 哨兵 | 常量 `Id::NIL`（全零），`Id::is_nil()` |
| 有序 | 实现 `Ord`，按 128 位值比较（ULID 即字典序，符合 3.3 的兜底用途） |
| 形态类别 | `Id::shape()` 返回 `Ulid` / `Uuid` / `Nil`，供序列化侧还原文本形态 |

**不变量 I1（规范形态逐字保真，非规范形态规范化且幂等）**：

- 两个**规范形态**：26 字符大写 Crockford Base32（ULID）、36 字符小写带连字符（UUID）。标识符以这两种形态读入时，重新写出必须逐字符相同。
- 非规范形态（32 字符无连字符 UUID、全小写的 26 字符 Base32、任何大写 UUID）读入后**规范化**为对应规范形态写出；规范化是幂等的——第二遍 round-trip 起逐字稳定。全零载荷不属于本条，由 I2 独占处理。
- 非规范形态必须能被读入，因为存量数据里存在（无连字符拼写曾用于错误追踪 id 与协作成员 id），这是“可读”的要求，不是“保真”的要求。

**不变量 I2（哨兵优先）**：载荷为全零时，**无论文本是 26 字符还是 32/36 字符**，一律归为 `Id::NIL`（形态类别 `Nil`），写出为 36 字符全零 UUID。哨兵判定先于形态判定。这是 I1 的唯一例外，且是刻意的：哨兵的意义是“同一个无身份常量”，不是“某段文本”。

### 4.3 生成

- 生成入口唯一：`Id::new()` / `Id::new_prefixed(prefix)`。
- 使用 `ulid` crate 的生成能力；**不启用**其 `uuid` feature（否则会把 `uuid` 依赖带回来）。
- 同一毫秒内不保证单调递增（3.3）；不做进程内的单调生成器——系统里没有依赖该性质的需求，引入它会把生成器变成需要跨线程共享的状态。

### 4.4 解析

解析入口唯一：`Id::parse_raw(s) -> Result<Id, IdParseError>`，按固定顺序尝试：

1. 先判哨兵：文本解码后载荷为全零 → `Id::NIL`（不变量 I2），不论文本是 26 字符还是 32/36 字符；
2. 26 字符、Crockford Base32 合法 → ULID，形态类别 `Ulid`（大写输出、小写输入也接受）；
3. 36 字符带连字符（8-4-4-4-12），或 32 字符无连字符，且全部是十六进制 → UUID，形态类别 `Uuid`；
4. 其余 → 解析失败。带花括号或 `urn:uuid:` 前缀的旧拼写**不接受**（存量数据不产生它们）。

带前缀的解析入口：`Id::parse_with_prefix(s)` 先按已知前缀（3.1 表）剥离，再走 `parse_raw`；也接受不带前缀的裸载荷。**不做**“任意前缀剥离”——盲拆会把 `session-` 之外的字符串拆坏。

### 4.5 序列化

- `Serialize`：按 4.2 的形态类别输出规范文本（不变量 I1 / I2）。
- `Deserialize`：接受 4.4 的两类形态；无法解析时报错（**不静默归零**）。

### 4.6 强类型分层

标识符在两个层次上被使用，二者不合并：

- `Id`：128 位载荷，用于**强类型传递**（审批门禁、问答门禁、事件字段、协作会话映射）。相等、哈希、比较都只看载荷。
- 作用域 id（`SessionId` / `AgentId` / `WorkspaceId`）：带前缀的完整字符串，用于**对外指称**（会话目录名、RPC 参数、事件载荷）。它们的载荷就是 `Id` 的文本形态，由 `Id::prefixed(prefix)` 构造。

### 4.7 依赖收口

- `uuid` 不在工作区依赖表中出现。
- `ulid` 只由 `mirri-id` 直接依赖；其他 crate 通过 `mirri-id` 使用，不直接 `use ulid`。
- `mirri-proto` 不依赖 `mirri-id`：wire 契约里的标识符始终是字符串，协议层不消费 `Id` 类型。

## 5. 兼容边界

### 5.1 解析入口唯一

任何“从字符串或 JSON 里取出标识符”的行为都必须经过 4.4 的唯一入口。判定是否满足，以工作区内是否还存在独立的标识符解析实现为准（检查手段见计划）。

### 5.2 两个消费面的对称性

嵌入服务端与独立服务端是同一份 RPC 方法表的两个宿主。**两个服务端的每一次标识符解析都必须使用同一入口**——任何一侧遗漏，表现为该宿主下该能力完全失效（审批/问答响应全部报参数非法，或 agent 归属被静默判成主 agent 而丢失成员归属）。

### 5.3 面向模型的入参声明

工具入参 schema 不对标识符声明固定格式（不写 `format: uuid` 之类），只要求“原样使用服务器给出的值，不要改写”。声明固定格式会让模型持续生成旧格式，形成长期的不一致源头。

### 5.4 存量数据

- 不做数据迁移（ADR-003 决策）。
- 会话目录名就是标识符原文（前缀 + 载荷），旧目录 `session-<uuid>` / `session_<uuid>` 原样保留、原样可读。
- 事件日志与 `wire.jsonl` 里的旧值由 4.4 / 4.5 覆盖。

## 6. 风险与取舍

| 风险 | 应对 |
|---|---|
| 新旧混合期，同一时刻的标识符字典序不可比（ULID 大写开头、UUID 小写） | 会话/任务的展示顺序以 `created_at` 为主键、标识符为次键；不承诺跨格式的字典序语义（3.3） |
| 某一侧解析点遗漏 → 静默降级（归属丢失），不报错 | 解析入口唯一（5.1）+ 双宿主对称性测试 |
| 非规范形态读入后被规范化，旧日志文本不再逐字一致 | 不变量 I1 只承诺规范形态的保真与非规范形态的幂等；wire 消费方对标识符只透传、不比较文本 |
| 哨兵的历史拼写不统一导致归属判定失效 | 不变量 I2（哨兵优先于形态判定）+ 旧格式回归测试 |
| ULID 同毫秒无序被误用为业务顺序 | 3.3 明确禁止；代码评审以“是否用标识符排序做业务序”为检查项 |

被否决的备选：

- **各模块各自生成与解析**：兼容逻辑会被复制到多处，将来下线旧格式需要逐处排查。
- **把强类型一律改成 `ulid::Ulid`**：`Ulid` 表达不了存量 UUID 值，旧事件反序列化直接失败，与 ID-2 冲突。
- **用 `String` + 常量哨兵替代强类型 `Id`**：兼容性天然成立、改动面更小，但失去“解析入口唯一”的类型强制，ID-4 只能靠人守。
- **把形态类别扩展到覆盖每一种非规范拼写（真逐字保真）**：状态机膨胀，收益只在于诊断类字段，不成立。
