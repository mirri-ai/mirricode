## 0. 角色定义

| 角色 | 场景 | 核心诉求 |
|---|---|---|
| **带图提问用户**（截图贴进对话的人） | 贴一张界面截图/照片让助手分析 | 图能被真正"看到"并进入回答；发出去的东西不丢 |
| **纯文本主模型用户**（主力模型不支持看图的人） | 贴了图但当前模型看不了 | 不报错、不中断；助手自己想办法（找看得懂的帮手或明说看不了），并给出下一步建议 |
| **终端粘贴用户**（CLI/TUI 用户） | 在终端里粘贴截图、@ 引用图片文件 | 粘贴即附带；模型看不了时当场被告知，而不是事后失败 |
| **带视频/音频的用户** | 附件里混有视频或音频 | 与图片一致的可达性语义；不会因为主模型只缺一种模态而整条消息失败 |
| **聚焦若干代码的用户**（E9） | 让助手重写某个组件、读懂某个模块 | 敲 `@` 立刻找到目标文件或文件夹；助手明确知道引用了什么，不必再解释 |

## 1. Epic E1：附件接入（P0）

> 解决"用户的图怎么进来"。原则：每个消费端（web/终端）都要有不绕过持久化的正规入口。

### US1.1 Web 附件上传（P0）

作为带图提问用户，我想在网页输入框通过文件选择、拖拽、粘贴三种方式附带媒体文件，以便不打断打字节奏地提交带媒体的问题。

验收：
- Given 我在 web 输入框，When 我通过文件选择器（可多选）、把文件拖入输入框、或粘贴剪贴板中的内容（粘贴入口接受任意文件类型，非仅媒体），Then 每个文件先独立上传到服务端并拿到文件凭证，再随消息一起提交
- Given 任一附件仍在上传中，When 我点发送，Then 发送被阻止（防止带着半截附件提交出坏消息）
- Given 某个附件上传失败，When 我查看输入框，Then 该附件带失败标识且可移除后重新附加；发送时失败附件不进入消息
- Given 我撤回/编辑一条带附件的历史消息，When 消息回到输入框，Then 附件条回填且原文件凭证直接复用（免重新上传）
- Given 附件按会话隔离管理，When 我切换会话，Then 各会话的附件互不串扰
- Given 我提交含图片的消息，When 服务端接收，Then 图片以文件凭证引用（而非把原始字节内联进消息），消息内容为「文字 + 图片引用」的混排
- Given 我提交的消息引用了失效或类型不匹配的文件凭证，When 服务端接收，Then 快速失败并给出明确错误（不进入对话）
- Given 我提交的消息引用了已过期的文件凭证（文件上传时带有效期），When 服务端接收，Then 提交失败并提示凭证已过期
- Given 我附带的是视频或普通文件（非图片），When 提交，Then 同样走上传凭证链路；普通文件以"附件已保存，可用读文件工具打开"的方式进入对话

### US1.2 终端粘贴图片（P0）

作为终端粘贴用户，我想直接把剪贴板里的截图粘贴进输入框，以便零操作成本地带图提问。

验收：
- Given 我的剪贴板里有一张截图（跨平台：macOS/Linux/WSL 各自的剪贴板通道），When 我在输入框按粘贴，Then 图片被收进本次输入（插入可读的图片占位标记，如 `[image #1 (宽×高)]`），原文数据同时留档
- Given 粘贴的图片体积较大，When 收进输入，Then 先压缩到模型友好的尺寸再进消息，同时保留未压缩原件的留档
- Given 我的剪贴板里没有媒体只有文字，When 我粘贴，Then 正常粘贴文字，不弹多余提示
- Given 我提交时输入框里还有图片占位标记，When 发送，Then 占位标记展开成真正的图片内容进入消息（普通消息、斜杠命令与技能参数中的媒体占位同样展开）

### US1.3 终端文件引用（P0）

作为终端粘贴用户，我想用 @ 补全引用工作区里的图片/视频文件，以便让助手读取磁盘上的媒体。

验收：
- Given 我输入 @ 并选择一个图片文件，When 提交，Then 引用以文件路径（纯文本）进入消息，由助手决定用读媒体工具读取
- Given 我引用了一个图片文件但当前模型没有图片输入能力，When 提交，Then 见 US4.3（读媒体工具按能力门控）

## 2. Epic E2：原始文件保留（P0）

> 解决"发出去的图丢了怎么办"。原则：用户交出的媒体，原始字节必须在引擎侧留档，且留档位置作为可交给帮手的恢复句柄随内容流传。

### US2.1 原件留档（P0）

作为带图提问用户，我想让我提交的每张图片的原始字节都被留档，以便任何后续处理都能拿回原图。

验收：
- Given 我通过**上传凭证或内联数据**入口提交了一张图片（无论经压缩与否），When 消息进入引擎，Then 原始字节被持久化到**全局内容寻址附件存储**（跨会话共享去重、fork 不复制本体、删除会话不级联清理，存储归属见持久化域 ADR-007/SDR-003；TS 现状为会话目录内存储，属其已登记的待迁移项），且留档路径作为该图片内容的隐藏属性随消息保存；纯**网络地址**入口的图片现状为透传不留档（该场景下发生能力缺口时，占位文本只有省略声明，见 US4.1 最后一条）
- Given 历史进入摘要流程且媒体部件需要被文本化，When 摘要请求被服务商以超限/格式原因拒绝而触发降级，Then 媒体部件在摘要输入中以占位替代；留档路径经由占位或压缩说明等相邻文本得以保留，可被后续提取（版本口径：v1 为光占位词（如 `[image]`）、路径仅经相邻文本间接保留；v2 摘要请求先命中请求层媒体降级链——占位按架构 §5.2 体积超限成因构造、路径可得时携带——压缩服务的溢出收缩阶梯在其耗尽后接管，证据见 context §4/§6）
- Given 我提交的是普通文件附件（非媒体），When 消息进入引擎，Then 文件被物化到全局内容寻址附件存储（存储归属同上，持久化域 ADR-007；TS 现状为会话附件目录，待迁移），消息中以"附件已保存到某路径，用读文件工具打开"的文本呈现

### US2.2 恢复句柄可信（P0）

验收：
- Given 引擎要给助手提供留档路径作为恢复句柄，When 判定该属性是否为可打开的文件路径，Then 只有真实文件系统路径被采信；协议式标识（如内部引用协议头）不得被误当作可读文件路径交给帮手

## 3. Epic E3：模型输入能力识别（P0）

> 解决"系统怎么知道当前模型看得懂图"。原则：能力以显式定义为准——声明支持即视为支持；无声明也无推断信号的模态一律按不支持处理，"未知"态已废除（SDR-006）；支持与不支持两种状态行为不同且都必须定义。本域「模型输入能力」即术语 MI1「模型模态能力」。

### US3.1 能力的两态语义（P0）

作为纯文本主模型用户，我想让系统准确区分"已知当前模型不支持图片"和"不知道当前模型支不支持图片"两种情况，以便两种情况下我都不遭遇莫名其妙的失败。

验收：
- Given 系统对当前模型的输入能力**明确已知**（无论来自配置声明还是内置目录推断），When 消息含该模型不支持模态的内容，Then 按 E4 的适配规则处理（绝不原样发给模型）
- Given 系统对当前模型的输入能力**无任何信号**（模型未被任何来源收录、用户也未声明任何媒体能力），When 消息含媒体内容，Then 一律按不支持处理：媒体部件投影为占位文本并注入能力缺口提示，不再原样发出交由服务商裁决
- Given 用户在配置中为某个模型显式声明了能力词表（如声明支持图片），When 能力判定，Then 声明为王：声明中未列出的媒体模态一律按不支持处理（即使内置推断认为支持）；仅当声明为空时，才以模型名推断兜底

### US3.2 能力信息对用户可见（P1）

验收：
- Given 我在模型列表/选择界面，When 查看一个模型，Then 我能看到它支持哪些输入模态（以模态能力徽标呈现）
- Given 我在配置模型时，When 填写能力，Then 我能从预置选项（支持图片/视频/音频输入等）中声明，而非自由文本；完整预置集以编辑表单为准，新增入口仅提供其子集（现状，见 context §2.3），子集未覆盖的模态可先保存、再经编辑表单补全——任一入口提交的声明均被系统采信

## 4. Epic E4：能力缺口适配（P0）

> 解决"当前模型看不了图时，请求怎么发"。原则：绝不把已知不支持的内容原样发给模型；替换物必须保留可恢复性；会话内的原始记录永不损毁。

### US4.1 请求前剥离与占位替换（P0）

作为纯文本主模型用户，我想让助手在当前模型不支持图片时仍然正常回答（而不是报错卡死），以便对话继续并走向能看图的路径。

验收：
- Given 当前模型已知不支持图片输入，When 任何一次模型请求被组装（含重试、降级等全部请求形态），Then 消息中的图片内容一律不进入请求，被替换为一段占位文本；替换只发生在"本次请求的投影"上，会话内保存的原始消息（含图片本体）原样保留
- Given 一条消息里同时有文字和图片，When 替换发生，Then 文字部分原样保留，仅图片被替换；同一消息里的视频/音频按各自模态独立判定
- Given 被替换的图片有留档路径（E2），When 占位文本生成，Then 占位文本至少包含：① 省略声明（当前模型不支持该模态）② 原件留档路径 ③ 具体的恢复指引（见 E5）
- Given 被替换的媒体没有留档路径（如纯网络地址且未留档），When 占位文本生成，Then 只有简短省略声明，不编造路径

### US4.2 全模态对称（P0）

验收：
- Given 当前模型已知不支持视频（或音频）输入，When 请求组装，Then 视频（音频）内容按与图片完全相同的规则剥离与占位替换，三种模态的适配行为对称

### US4.3 媒体工具按能力门控（P0）

作为纯文本主模型用户，我想让"看不了图的模型拿不到读图工具"，以便它不被诱导去调一个注定失败的工具。

验收：
- Given 当前模型既不支持图片也不支持视频输入，When 工具集组装，Then 读媒体工具不出现在工具列表中
- Given 当前模型支持图片或视频任一模态，When 工具集组装，Then 读媒体工具出现，且其说明按实际支持的模态裁剪
- Given 当前模型不支持图片输入但用户/助手仍尝试读图（如历史会话切换模型后），When 读媒体工具被调用，Then 返回明确的错误指引：提示派发一个模型支持图片输入的子代理来读，而不是静默失败
- Given 我用普通读文件工具读一个图片文件，When 调用，Then 被明确拒绝并指引改用读媒体工具

### US4.4 终端提交前门控（P0，终端消费端）

作为终端粘贴用户，我想在发送前就被告知当前模型看不了图，以便当场换模型或撤图，而不是发出去才失败。

验收：
- Given 终端输入里带图片附件且当前模型已知不支持图片输入，When 我提交，Then 提交被阻止并提示"当前模型不支持图片输入"；视频同理
- Given 当前模型的能力信息缺失（终端拿不到该模型的能力数据），When 我带图提交，Then 放行提交（交给引擎侧适配兜底），不误拦

### US4.5 视频投递通道的服务商差异（P0）

作为带视频/音频的用户，我想在当前模型"声明支持视频"但实际收不到视频内容时得到明确的可达性说明，以便知道这单视频到底能不能被看、而不是被静默糊弄。

验收：
- Given 当前模型支持视频输入且其服务商具备视频投递通道（上传或内联任一），When 对话中的视频需要投递，Then 视频按"上传通道 → 内联"的顺序择一投递，模型可真正观看
- Given 当前模型支持视频输入但其服务商**没有**视频投递通道（既不能接收上传也不支持内联），When 对话中存在视频内容，Then 视频以留档路径的文本引用进入对话（模型无法直接观看），且需要真正读取视频内容时读媒体工具明确报错说明该服务商不支持视频投递——不静默丢失、不假装已投递

## 5. Epic E5：委托多模态子代理（P0）

> 解决"看不了图的模型怎么把活儿交出去"。原则：委托是给主模型提供顺畅的委托通道与充分信息，由主模型自主执行，而非系统强制改道。

### US5.1 占位文本内的恢复指引（P0）

作为纯文本主模型用户，我想让占位文本直接告诉助手三条出路，以便它自己选一条把用户的图处理掉。

验收：
- Given 占位文本生成（US4.1），When 助手读到它，Then 它能看到按优先级排列的三条恢复路径：
  1. 检查是否存在专用的多模态子代理（如媒体阅读类型），有则直接派发（其默认模型已支持该模态，无需额外指定），并指示它读留档文件；
  2. 不存在专用子代理时，派发一个通用子代理并显式指定一个支持该模态的模型（指引其查阅代理工具说明里的可用模型清单及各模型能力），并指示它读留档文件；
  3. 全库找不到任何支持该模态的模型时，如实告知用户无法处理该媒体，建议换用支持该模态的模型，或请用户用文字转述内容。
- Given 三条指引生成，When 任意一条被助手执行，Then 指引中的路径（原件留档路径）与工具名（读媒体工具）必须真实可用，不允许指向不存在的入口

### US5.2 能力缺口提示注入（P0）

作为纯文本主模型用户，我想让助手在本回合开始时就收到"你看不了图，但可以这样做"的明确提醒，以便它第一时间选择委托而不是装作没看见图。

验收：
- Given 一个新回合开始，当前模型已知不支持某模态，且用户消息中确实含该模态的内容（含被客户端替换成的"图片已省略/已留档"文本通知），When 回合上下文组装，Then 注入一条系统提醒：说明当前模型不支持该模态、用户消息中含该模态内容、并给出具体委派建议
- Given 建议中要点名子代理，When 系统扫描可用子代理档案，Then 只点名**默认模型确实支持缺口模态**的子代理；没有任何子代理符合时给出通用建议（指定支持该模态的模型派发）
- Given 全库没有任何模型支持缺口模态（委托注定无解），When 提示注入判定，Then 不注入"去派子代理"的建议（不说做不到的空话）
- Given 提示注入发生，When 用户消息文本中能提取出留档路径标记（压缩说明、附件通知等），Then 提醒中直接列出这些路径，并指示让子代理读这些文件
- Given 没有能力缺口或用户消息不含缺口模态，When 回合上下文组装，Then 不注入该提示（零噪音）

### US5.3 委托通道：子代理指定模型（P0）

作为纯文本主模型用户，我想让派发子代理时可以显式指定一个看得懂图的模型，以便帮手真正具备看图能力。

验收：
- Given 助手派发子代理，When 它显式指定了模型参数，Then 子代理使用该模型执行（该模型必须是配置中存在的模型；非法指定被校验拒绝）
- Given 助手未指定模型，When 子代理启动，Then 按模型裁定链（术语 M5 的子代理链）裁定：子代理类型默认模型 → 派发者当前模型
- Given 助手在挑选模型，When 它阅读代理工具说明，Then 它能看到可用模型清单（收录带用途描述的模型）中每个模型的模态能力标注（如"支持 vision"）与每个子代理档案的默认模型及其能力，足以自行选出看得懂图的组合

## 6. Epic E6：上游拒绝后的媒体恢复（P1）

> 解决"发出去还是被拒了怎么办"。原则：能自动救的自动救，救不了的要留下可恢复的线索。

### US6.1 请求体积超限降级（P1）

验收：
- Given 服务商报请求体积超限，When 引擎处理，Then 先按"媒体降级"投影重试（较早消息里的媒体被替换为占位，保留路径与"可重读"提示）
- Given 降级重试仍超限，When 引擎处理，Then 再按"媒体剥离"投影重试（仅剥离被拒请求中的媒体，按剥离快照精确执行）；被拒请求中的媒体在本回合后续重放中保持剥离状态，不反复踩坑

### US6.2 图片格式被拒恢复（P1）

验收：
- Given 服务商明确拒绝某个图片的格式/编码，When 引擎处理，Then 该图片被剥离并替换为带路径与转换指引的占位文本后自动重试；格式类拒绝的识别范围不覆盖"模型不支持图片输入"这类能力型错误（能力型错误不允许走到上游，见 E4）
- Given 入口处收到不支持的图片格式（如 HEIC/AVIF），When 消息进入引擎，Then 该图片被替换为格式说明文本并留档原件，不进入后续请求

## 7. Epic E7：非功能需求（P0/P1）

### US7.1 不作恶于会话记录（P0）

验收：
- Given 任何模态适配/降级/剥离发生，When 事后查看会话历史与人类视图，Then 用户当时提交的媒体原样可见（适配只影响发给模型的请求投影），媒体本体不被删除

### US7.2 观测与旁路序列化（P1）

验收：
- Given 我事后翻看观测日志，When 日志中本应出现图片数据的位置，Then 只见体量标记（如字节数），不会看到大段图片编码数据
- Given 会话标题派生/最近输入摘要，When 文本化用户消息，Then 图片以占位词（如 `[image]`）呈现

### US7.3 路径安全（P0）

验收：
- Given 媒体留档路径被用作恢复句柄或被读媒体工具打开，When 路径解析，Then 与读文件工具一致的路径越界校验生效

### US7.4 性能与资源（P1）

验收：
- Given 模型支持全部在场模态，When 请求投影执行，Then 适配逻辑不带来可感知的开销（无适配时直通）
- Given 多张图片同时提交，When 处理，Then 逐张独立处理（压缩、留档、判定），单张失败不影响其余

### US7.5 媒体上下文生命周期可见性（P1）

验收：
- Given 我事后翻看请求记录（会话 wire 日志的 `llm.request` 记录），When 本回合请求含媒体内容，Then 能看到该请求携带的媒体数量与总字节；引擎日志同步输出一行结构化摘要，以便判断媒体对本次请求的实际压力
- Given 媒体未进入某次请求（压缩退场 / 体积超限 / 能力缺口 / 格式被拒），When 我查看该请求的记录，Then 能分辨媒体缺席及其原因；替换类事件在引擎日志中按签名去重，不逐轮刷屏

## 8. Epic E8：媒体在场经济性（P1 · 目标需求，超出 TS 现状）

> 解决"图片进来之后，如何不长期压迫对话的思考空间"。原则（SDR-003 修订）：媒体的持续在场是**随压缩衰减、缓存友好、有界、可恢复**的状态——两次压缩之间媒体在场且历史不因媒体改写（前缀缓存友好）；退场发生在摘要压缩边界（压缩本就整体重写历史，退场搭车零边际代价）；单图体积由入口压缩限定、请求总量由 413 兜底约束；退场文本化永远携带可重读的留档路径。对话历史里用户看到的媒体永不因退场而消失。
> 口径说明：本 Epic 经用户裁决新增（SDR-002），后经前缀缓存经济性分析收敛为"压缩即退场"（SDR-003，否决滚动退场与主动预算驱逐）；记录**目标需求**而非现状——TS 引擎现状为媒体驻留至压缩（媒体已按固定 2000 token 估值计入压缩触发，见 context 文档），设计方向见架构文档 §5.5 与 ADR-005。

### US8.1 媒体成本计入记忆压力（P1）

作为多图对话用户，我想让媒体对上下文的占用被真实计入对话的"记忆压力"，以便附图之后对话的记忆力不明显劣于纯文字对话。

验收：
- Given 我连续附带多张媒体，When 引擎评估是否需要摘要压缩，Then 媒体计入压力评估（现状：每媒体部件按固定 2000 token 估值计入，见 context 文档），媒体密集的对话更早进入压缩，而不是把压力转嫁给文字记忆
- Given 摘要压缩执行且被摘要的头部含媒体，When 压缩完成，Then 媒体以文本形态存在且**携带留档路径**（见 US8.2），后续仍可按路径重读
- 按模型视觉定价的精细化估值（替代固定 2000）为可选增强，非本 Epic 落地前提（SDR-003）

### US8.2 媒体退场：压缩时机与路径跟走（P1）

作为多图对话用户，我想让较老的媒体在摘要压缩时一并文本化退场，以便长对话不被旧图持续拖慢、拖贵，且压缩后助手仍能找回原图。

验收：
- Given 摘要压缩执行，When 被摘要的头部含媒体部件，Then 媒体退场为文本标记且**携带原件留档路径**（模型可见，并声明"既有结论是解释而非证据，核对请重读路径"）；最近尾部媒体原样保留
- Given 两次压缩之间，When 媒体持续在场，Then 在场状态不引入任何逐轮改写历史的机制（前缀缓存友好；SDR-003 否决了滚动退场与主动预算驱逐）
- Given 服务商以请求体积超限拒绝（413），When 引擎兜底，Then 现有 413 降级链（媒体降级 → 媒体剥离）保留为字节维度的唯一防线——token 维度的压缩触发挡不住请求体字节超限
- Given 媒体退场，When 用户查看对话历史，Then 用户看到的媒体原样保留（退场只影响发给模型的请求内容）

## 9. Epic E9：工作区文件与文件夹引用（P0）

> 解决"我要让助手聚焦这几份代码"的问题。原则（SDR-007）：`@` 产生的是**结构化引用**而非文本巧合——用户看得见引用了什么，引擎保证引用内容真的进入本轮上下文；引用的检索范围严格限定在工作区内，与既有权限边界一致。
> 消费端范围：web 与桌面端（同一套界面，桌面端是 web 界面的外壳）；终端沿用其既有的 `@` 文件补全（US1.3），交互契约见终端界面域（[tui/interaction-requirements.md](tui/interaction-requirements.md) §1.3）。
> 交互契约（触发、候选菜单、键盘、视觉与状态规格）见 [file-reference-uiux.md](file-reference-uiux.md)；技术机制见 [multimodal-input-architecture.md](multimodal-input-architecture.md) §11。

### US9.1 触发与候选（P0）

作为聚焦若干代码的用户，我想在输入框敲 `@` 就得到候选，以便不用回忆并手敲完整路径。

验收：
- Given 我在输入框里 `@` 之后输入若干字符，When 候选菜单呈现，Then 我能在可感知的瞬间看到候选（首屏出现时延见 US9.9），且输入不被阻塞
- Given 候选菜单已打开，When 我继续输入或改字，Then 候选随输入更新；我快速连续输入时，看到的是与当前输入一致的结果，不会出现旧输入的结果覆盖新输入
- Given 候选里同时有文件与文件夹，When 我查看候选行，Then 能一眼区分两者（图标与结尾斜杠），文件夹也能作为候选出现
- Given 我输入形如 `src/comp` 的路径分段，When 候选更新，Then 只在 `src` 文件夹下检索，而不是全工作区模糊匹配
- Given 候选结果中有与实际输入匹配的字符，When 我查看候选行，Then 匹配的字符被高亮，我能看懂这条为什么排在前面
- Given 没有任何匹配，When 菜单仍在打开状态，Then 我看到明确的"没有匹配"提示，而不是一个空白浮层
- Given 我所在会话尚未创建（草稿态），When 我敲 `@`，Then 候选正常出现（引用能力不依赖会话已存在）

### US9.2 文件夹的两个动作（P0）

作为要找某个文件夹里的文件的用户，我想在候选里直接"进入"这个文件夹继续搜，也让"引用整个文件夹"与"进文件夹找文件"是两个不会互相妨碍的动作。

验收：
- Given 候选中我选中了一个文件夹，When 我按 Tab（或点候选行尾的箭头），Then 我进入该文件夹继续检索，菜单保持打开，输入框里的路径片段被改写成该文件夹前缀
- Given 候选中我选中了一个文件夹，When 我按 Enter（或点候选行主体），Then 该文件夹作为一项引用插入，菜单关闭
- Given 我是通过"进入文件夹"到达当前层级的，When 我查看菜单顶部，Then 能看到回到上级的路径面包屑
- Given 我按 Esc 关闭菜单，When 再次把光标移回同一处 `@` 片段，Then 菜单**不会**自己重新弹出（我明确关闭过它）；只有我继续输入才重新唤起

### US9.3 插入为可辨识的引用（P0）

作为聚焦若干代码的用户，我想让引用在输入框里以可辨识、可操作的形式存在，以便随时看清我引用了什么、并能方便地撤掉。

验收：
- Given 我从候选里选中一个文件，When 它插入输入框，Then 它以"文件名 + 所在文件夹（灰字）"的引用形态呈现，与普通文本明显不同
- Given 光标紧邻某个引用，When 我按退格，Then 整个引用被一次删除，而不是逐字符删除
- Given 输入框里有若干引用，When 我单击引用的文件名，Then 我能直接查看该文件内容
- Given 我不小心插入错了引用，When 我删除它，Then 它不会再影响发送后的上下文
- Given 我先引用文件 A、再引用文件夹 A 或另一层级路径，When 候选插入，Then 不会产生指向同一目标的重复引用

### US9.4 引用的注入形态（P0）

作为聚焦若干代码的用户，我想让引用的内容真的被助手看到，从而不必在提问里再复述一遍文件内容。

验收：
- Given 我引用了一个工作中的文本文件并发送，When 助手收到我这一轮消息，Then 它能读到该文件的内容，且知道这段内容来自哪个路径
- Given 我引用了一个很大的文件，When 内容被送入，Then 只有约定范围内的内容被送入，并且助手被告知内容被截取（我这边也能看到"已截取"的提示）；截断的具体数值与归属见架构文档 §11.4
- Given 我引用了一个文件夹并发送，When 助手收到我这一轮消息，Then 它拿到的是该文件夹下的路径清单（遵守忽略规则、有数量上限），而不是整目录内容；助手需要时可自行读取其中具体文件
- Given 同一个文件在同一轮被引用多次，When 内容送入，Then 只送入一次
- Given 我在输入框里手打了形如 `@some/path` 的文本但没有从候选里选中它，When 发送，Then 它被当作普通文本，不触发任何内容送入（避免随手写的文本被误当作引用）
- Given 引用发生在一次发送中，When 后续轮次对话继续，Then 该引用不重复送入，避免上下文无限增长（我需要时再引用一次）
- Given 引用来自工作区之外的路径，When 我尝试检索或引用，Then 检索结果中不出现它，且我得到明确的"超出工作区范围"说明

### US9.5 引用失效与内容变化（P0）

作为聚焦若干代码的用户，我想在发送前就知道引用还成不成立，以便不会发出一个"看起来引用了、其实什么都没带到"的请求。

验收：
- Given 我引用的文件在我发送前被删除或移走，When 我点发送，Then 我被提示"有 N 个引用已失效"，并可以选择"移除失效引用后发送"或取消发送
- Given 我引用的文件在我发送前被修改，When 我查看该引用，Then 能看出"内容已更新"，且送入的是发送时刻的内容
- Given 我引用的文件在我发送前变成了文件夹（或相反），When 我点发送，Then 按失效处理并在提示中说明类型已变化，不静默按旧类型送入
- Given 我引用的目标因权限变化无法读取，When 我点发送，Then 按失效处理（US9.8）

### US9.6 检索范围与忽略规则（P0）

作为聚焦若干代码的用户，我想让候选只包含真正相关的文件，而不是被依赖目录和构建产物淹没。

验收：
- Given 我的工作区遵守版本控制的忽略规则（如依赖目录、构建产物、虚拟环境），When 我检索，Then 这些被忽略的路径**默认**不出现在候选里
- Given 我需要引用一个被忽略的文件，When 我输入的当前路径段以 `.` 开头（如 `@.env` 或 `@src/.h`），Then 隐藏/被忽略的条目可按需出现在候选里（明确可预期的逃逸方式）
- Given 我已在会话中附带多个目录（多根工作区），When 我检索，Then 候选覆盖所有已附带目录，且每一行都能看出它在哪个根下；超出引擎常驻上限的根不因此不可用——按需重建并告知（数值上限归架构文档）
- Given 我正在引用工作区之外的绝对路径，When 我输入它，Then 我不会"搜到一个实际打不开的结果"——要么给出明确的越界说明，要么不出现在候选里

### US9.7 文件变化被反映（P0）

作为在编辑器与对话之间来回切换的用户，我想让我在编辑器里新建、重命名、删除文件的动作立刻反映到 `@` 候选里。

验收：
- Given 我在编辑器里新建了一个文件，When 我回到输入框敲 `@` 并输入该文件名，Then 能搜到它，无需刷新页面或重启会话
- Given 我删除或重命名了一个文件，When 我再次检索，Then 已删除/旧名不再出现在候选里，指向它的旧引用在发送时按 US9.5 报失效
- Given 其他程序（版本控制切换分支、外部编辑器）在工作区内大量增删文件，When 变化事件到达后的下一次检索，Then 候选反映已到达的变更；在此期间我可以正常使用（不卡顿、不报错）
- Given 我的工作区非常大，When 我敲 `@`，Then 我不需要等待整体扫描完成才能开始输入；扫描尚未完成时我能看到结果并被告知"结果可能不全"

### US9.8 失败与降级（P0/P1）

作为聚焦若干代码的用户，我想在引用能力出问题时得到明确的告知与可预期的兜底，以便不会在不知情的情况下发出残缺的请求。

验收：
- Given 候选检索暂时不可用，When 我敲 `@`，Then 我得到明确的不可用说明（而不是一个静默变慢的菜单）；引用能力恢复后我无需任何操作即可继续使用
- Given 我引用的文件没有读权限或读取失败，When 发送，Then 该引用按"失效"处理并走 US9.5 的阻止与选择流程；我选择移除后发送时，其余引用照常注入
- Given 检索正在建立索引，When 我查看菜单，Then 我看到来自已扫到部分的真实结果与"正在建立索引，结果可能不全"的固定说明（而不是空白或报错）；单次查询未返回时才显示骨架行（P1）
- Given 我的工作区规模超过索引的容量上限，When 我查看菜单，Then 我被告知"结果可能不全"（截断不静默发生）

### US9.9 性能（P0）

作为大仓库工作区的用户，我想让 `@` 检索在任何规模下都跟手，以便不会因为补全卡顿而打断思路。

验收：
- Given 一个约 5 万个文件的工作区且索引已就绪，When 我敲 `@` 并输入字符，Then 首个候选在 100 毫秒内出现（指标口径见架构文档 §11）
- Given 同一工作区，When 我持续修改检索词，Then 输入不被可感知地阻塞（无肉眼可见的卡顿或跳字，可测口径：输入响应无超过 50 毫秒的阻塞）
- Given 引擎刚启动（索引尚未建立），When 我敲 `@`，Then 引擎侧主动重建索引期间的资源占用不阻塞对话的其它操作（P1）

### US9.10 引用的可辨识与可观测（P1）

作为聚焦若干代码的用户，我想在事后仍能看出每轮引用了什么、注入了什么形态的内容，以便排查"助手为什么没看到那个文件"。

验收：
- Given 我事后回看我发出的消息，When 该消息含文件引用，Then 我能从消息里看出"这一轮引用了哪些文件/文件夹"（与普通文本中的 `@xxx` 可区分）
- Given 我排查"助手为什么没看到那个文件"，When 我查看该轮请求记录，Then 能看到本轮注入的引用清单及其注入形态（全文 / 截取 / 清单）与体积

## 11. 未来增强提案（超出 TS 现状，非已支持能力）

> 以下为设计提案，**不声称 TS 当前已支持**；采纳与否由用户裁决，裁决后转入正式需求并登记 SDR。
> 已裁决项不在此列：媒体在场经济性（原"旧媒体驱逐策略"讨论提案）已于 2026-09-16 经用户裁决升格为正式需求 Epic E8，见 SDR-002。

- **P-1 引擎自动模态路由**：当前委托是"提示主模型去做"（E5），依赖主模型读懂指引并正确派发。提案：引擎检测到缺口模态且有唯一可行视觉模型时，自动派发多模态子代理并把结果缝合回主对话。代价：主模型对"谁在回答"失去感知、结果归属与审批链变复杂；与"委托是模型自主权"的现有设计哲学冲突（ADR-001）。建议谨慎，优先保持提示式委托，只优化提示质量。
- **P-2 Web 发送前能力预检**：当前 web 不做发送前预检（§9）。提案：web 在当前模型已知无图片输入能力时，在附件入口处给出"当前模型无法直接查看图片，将尝试由子代理处理"的预期管理提示（不阻止发送，保留引擎侧兜底）。纯前端增强，不改变引擎行为。
- **P-3 内置多模态子代理档案**：当前无内置的"媒体阅读"子代理（仅占位文案示例与用户自建通道）。提案：出厂内置一个默认模型为多模态模型的子代理档案，令 US5.1 第 1 条指引在开箱状态即可命中。代价：需要默认多模态模型的配置假设。
- **P-4 能力学习（推断误报残留的增强）**：SDR-006 后不再有"未知透传"，残留通路仅剩**推断误报**——名字带 marker 但实际不支持的模型把媒体原样发出，被"仅支持文本输入"类上游错误拒绝；这类错误不属于自动剥离的识别范围、会直接上抛。提案：把"模型仅支持文本输入"类错误纳入可识别的错误族，首次遭遇后记忆该模型能力并按 E4 适配重试。可缩小与未对齐引擎在能力型上游错误上的体验差距。
- **P-5 音频输入消费端入口补全**：引擎侧（部件、占位、投影）音频与图片对称；消费端现状无音频媒体入口（web 音频按普通文件附件处理、终端无音频粘贴）。若产品确认音频为需求，需补消费端验收。
- **P-6 网络地址图片的留档拉取**：当前纯网络地址入口的图片透传不留档（US2.1），该场景发生能力缺口时无恢复句柄。提案：入口层对网络地址图片做后台拉取留档（或至少在剥离时给出可传递的原始地址），使委托路径也能覆盖该场景。
- **P-7 无描述模型的能力可见性**：当前代理工具说明中的可用模型清单只收录带用途描述的模型——若库里唯一的多模态模型没有描述，US5.1 第 2 条指引在助手视角下无候选可选。提案：对具备独特模态能力的模型放宽清单收录门槛（或自动补占位描述）。
- **P-8 服务商文件引用通道（file-id，低优先级）**：服务商支持时（DeepSeek Files API 形态），图片首次请求上传换文件 id，此后请求只携带 id——历史永不变（前缀缓存永续命中）+ 字节不跨网（413 消失），退场问题对该类服务商直接消解。经用户裁决列为低优先级 backlog：服务商专属能力（非通用解），优先级不高（SDR-003）。
- **P-9 终端对齐结构化文件引用（P1，待裁决）**：终端现状以 `@path` 纯文本引用、由助手自行读取（US1.3），与 web/桌面 的结构化引用（US9.4）语义不一致——同一句 `@a.ts` 在两个消费端的注入结果不同。提案：终端也走结构化引用，`@path` 在提交时被包装为引用对象，注入形态由引擎统一决定。代价：终端输入框无芯片基础设施，需要外部标记方案；跨端会话里同一消息的呈现语义需统一。
## 附录 A：域内术语

| 术语 | 定义（域内视图） |
|---|---|
| 媒体（media） | 图片、视频、音频三类内容的统称；进入消息后以带隐藏留档属性的内容部件表示 |
| 留档（persisted original） | 用户提交媒体的原始字节在全局内容寻址附件存储（持久化域 ADR-007；TS 现状为会话目录内，待迁移）的持久化副本；其路径是能力缺口恢复与子代理读图的句柄 |
| 占位文本（media placeholder） | 媒体因故不能进入请求时替换它的说明文字；四种成因（SDR-003）：能力缺口（带路径与恢复指引）、压缩退场（带路径与"既有结论是解释而非证据"认知声明）、体积超限（带路径与重读提示）、格式被拒（带路径与转换指引） |
| 能力缺口（capability gap） | 当前模型已知不支持某输入模态，而对话内容中确实存在该模态内容的状态 |
| 提示式委托（prompt-level delegation） | 通过占位文本与回合提示向主模型描述出路、由主模型自主派发子代理的委托形态；与"引擎自动改道"相对 |
| 可用模型清单（available models list） | 代理工具说明中向助手展示的候选模型清单，以"带用途描述"为收录门槛；委托时的模型能力标注以此清单为作用面 |
| 媒体在场（media residency） | 媒体内容在传递给模型的请求中的持续参与状态；域原则（SDR-003）：随压缩衰减、缓存友好、有界、可恢复（规范定义见跨域术语表 MI2） |
| 退场（offload） | 媒体在摘要压缩时被文本化替换、退出后续请求的动作；退场文本携带留档路径，不改变会话历史中的媒体本体，留档保持可重读 |
| 文件引用（file reference，E9） | 用户从 `@` 候选中选定的、指向工作区内某个文件或文件夹的一等输入元素；以可辨识形态存在于输入框、随消息保存、由引擎送入内容（规范定义见跨域术语表 MI3） |
| 列表清单注入（listing injection，E9） | 引用文件夹时的注入形态：只送入该文件夹下的路径清单（遵守忽略规则、有条数上限），不送入文件内容；助手需要时自行读取具体文件 |
| 引用失效（stale reference，E9） | 引用目标在发送前因删除、移动、类型变化或不可读取而不再成立的状态；发送前必须提示并允许用户移除失效项，不得静默送入残缺内容 |
| 文件夹双动作（folder drill / pick，E9） | 选中文件夹时的两种正交动作：进入（把检索范围收进该文件夹、菜单保持打开）与引用（把该文件夹作为引用插入、菜单关闭） |

## 附录 B：需求决策记录（SDR）

### SDR-001 留档范围与摘要标记的口径修订（2026-09-16）

- **背景与动机**：初版把"网络地址图片"并入无条件留档范围、并声称摘要中的媒体占位标记携带路径；两处均与事实不符，且与 US4.1"无留档路径时占位只有省略声明"的验收自相矛盾（R1 审查 B1/B2）。
- **决策**：① 无条件留档仅覆盖上传凭证与内联数据入口；纯网络地址入口透传不留档，该场景的能力缺口占位走无路径短文案，补救登记为提案 P-6。② 媒体部件在摘要输入中以 `[image]` 等占位词替代（现状仅在摘要请求被服务商拒绝后的降级重试中触发），留档路径经由压缩说明等相邻文本保留并可被提取。同批增补：US4.5 视频投递通道服务商差异；US5.1/US5.3 的可用模型清单明确以"带用途描述"为收录门槛（提案 P-7）。
- **被拒方案**：网络地址入口立即拉取留档（失败面与成本大，且需求未裁决，登记为提案而非现状）；摘要占位标记内嵌路径（属设计增强，未采纳为现状基线）。
- **影响范围**：US2.1、US4.1、US4.5、US5.1、US5.3、§10（P-6/P-7）。

### SDR-002 媒体在场经济性升格为正式需求（2026-09-16）

- **背景与动机**：用户评审指出：图片等多模态输入在多轮对话中无限期全额驻留于每次请求，对上下文造成持续压迫——提前触发摘要压缩（挤占文字记忆）、请求随媒体量线性变慢变贵，且伤害间接隐蔽（用户归因不到媒体头上）。外部产品实践（deepseek-harness）佐证：无状态对话协议下"每轮全量重放历史"不可避免，但重发单位可为"引用 + 预算内投影"，配确定性驱逐与视觉成本计价即可受控。
- **决策**：新增 Epic E8（媒体在场经济性，P1，以目标需求口径记录）与 US7.5（媒体上下文生命周期可见性）；产品原则定为**"媒体在场是有预算、随对话衰减、确定性、可恢复的状态"**。讨论中的"旧媒体驱逐策略"提案据此直接升格为正式需求（未经历未决提案阶段），设计方向见架构文档 ADR-005。
- **被拒方案**：维持现状（无限期全额驻留，仅靠上游拒绝后的反应式降级兜底——伤害隐蔽且不可预期）；"媒体只发一次、永不重发"（剥夺近期媒体在场的真实价值，助手无法回看，违背"带不带图都能聊"）。
- **影响范围**：新增 Epic E8（US8.1–8.2）、US7.5；架构文档 §5.5 + ADR-005；ROADMAP §1/§2；术语表 MI2（媒体在场）。

### SDR-003 媒体退场收敛为压缩时机，否决滚动退场与预算驱逐（2026-09-16）

- **背景与动机**：SDR-002 后的设计推演发现两个否定性事实：① **前缀缓存经济性**——逐轮滚动退场（在场窗口）与主动预算驱逐每轮在历史中部制造内容变化，触发"从变更点到结尾"的缓存失效（≈窗口回合量的全价重写），而保留老图的缓存读成本仅每图每轮 0.1× 视觉 token 当量——滚动退场省字节、亏 token，净负收益（工程先例：工具调用域 F-15 已确立"provider 提示词缓存不失效"原则）；② **维度错位**——压缩触发是 token 维度（媒体按固定 2000 估值计入），请求体超限（413）是字节维度，token 压缩永远挡不住字节超限，反应式 413 链不可删。同批核实现状缺口：v1 压缩文本化标记（`[image]`）不携带留档路径，v2 fullCompaction 无媒体专项处理——压缩后恢复句柄断裂（证据见 context 文档 §6）。
- **决策**：E8 机制收敛为"**压缩即退场**"：退场时机 = 摘要压缩边界（缓存必灭时刻，边际代价零）；413 反应式降级链保留为字节维度防线；**压缩文本化必须携带留档路径**（E8 核心增量，路径跨压缩存活并携带"既有结论是解释而非证据"的认知声明）。同批裁决：① 证据分层 L1（占位/标记的认知声明）与 L2（读图工具说明要求对含文字图片逐字引用决定性内容，登记工具调用域）为必做，L3（退休转录，专门提取调用）可选默认关；② E8 退场状态与能力缺口状态同构复用（占位构造器/恢复句柄/重读通道共享，仅转换时机与指引分叉不同）；③ file-id 文件引用降级为低优先级提案 P-8（DeepSeek Files API 专属）；④ US7.5 观测落点定为 `llm.request` wire 记录追加媒体字段 + 引擎日志结构化行（替换事件按签名去重），不进 `usage.record` Op（累积型 token 模型）与遥测；⑤ US8.1 口径修正：现状媒体已按固定 2000 token 计入压缩触发，按模型视觉定价细化为可选增强。
- **被拒方案**：逐轮滚动退场（在场窗口 K 回合——缓存失效净亏损）；主动预算驱逐管线步骤（mediaBudgetOffload——同样的中部改写问题且系统性触发）；"只发一次、永不重发"（剥夺近期媒体在场价值，助手无法回看）；压缩文本化不带路径（恢复句柄断裂，用户须重发图）。
- **影响范围**：US8.1、US8.2、US7.5、§10（P-8）；架构 §5.5 + ADR-005（重写）；ROADMAP §1/§2；context §6（补现状证据）；工具调用域（L2 约定跨域登记，其 ROADMAP F-16）；术语表 MI2 语义修订。
- **登记同步（2026-09-16 审查修复批）**：压缩域联动（文本化带路径）补登记至其 ROADMAP 开放项 25；附录 A「占位文本」四成因口径与本域 US7.5/架构 §5.2/§5.5.4 的"体积超限"术语统一于本批补同步。

### SDR-004 留档存储归属对齐持久化域：全局内容寻址，fork 不复制（2026-09-16）

- **背景与动机**：用户裁决诉求：fork 会话不应复制媒体本体——按会话存档媒体会使 fork 存储随分叉次数翻倍。该诉求已由持久化域 **ADR-007/SDR-003** 裁决为全局方案（附件本体上移至数据根下的全局内容寻址存储 `<sha256>`，跨会话共享去重、fork 停止复制、删除不级联本体、引用感知延迟回收）；但本域基线文本仍写"该会话的媒体留档区 / 会话附件目录"（按 TS 现状记录），与已裁决目标冲突，构成跨域不一致。
- **决策**：本域跟进对齐——US2.1（两条验收）、附录 A「留档」术语的存储归属统一改为**全局内容寻址附件存储**（存储细节与回收语义归持久化域，本域只约定留档语义与路径句柄）；TS 会话目录内存储明确标注为待迁移现状。兼容性确认：全局 blobs 的 sha256 路径仍是合法文件系统路径，US2.2 路径采信、US7.3 路径安全、ADR-004 无条件留档语义全部原样成立，变的只是"存到哪"。存量迁移缺口同步登记：TS `<会话目录>/media-originals/`（提示摄入的媒体原件留档，本域 E2/ADR-004 恢复句柄的来源）须显式纳入持久化域 ADR-007 的上移合并清单（该域 ROADMAP 开放项 11 已补充）。
- **被拒方案**：维持"会话媒体留档区"表述（与持久化域已裁决目标冲突，误导 Rust 对齐实现按会话存档）；fork 时复制媒体本体（持久化域 ADR-007 已明确否决——存储随分叉翻倍）。
- **影响范围**：US2.1、附录 A；架构 §1/§3.3/ADR-004；ROADMAP §2；持久化域 ROADMAP 开放项 11（迁移范围补充）。

### SDR-005 媒体压缩预算体系披露与范围边界归属口径（2026-09-16）

- **背景与动机**：范围边界原文对"读时压缩"的参数归属未做声明，读者无法判断入口 / 读时 / 上下文估值三层数值各自的事实源；读时参数若由本域叙述，会与工具调用域 ReadMediaFile 规格形成双源漂移。经用户裁决做披露性补全（架构 §3.4）。
- **决策**：① 范围边界修订：媒体压缩预算体系（入口 / 读时 / 上下文估值三层与行为契约）见架构文档 §3.4——读时压缩的参数规格归属工具调用域（本域只引用、不复制数值），入口压缩与上下文估值的现状数值以 context 文档证据为准。② 架构新增 §3.4：三层预算表（各管一段、互不越权）与行为契约三条（模型默认看到压缩视图、原件是保真升级源；恢复路径预算闭环；压缩与留档正交）。
- **被拒方案**：本域复制读时参数数值（双源漂移）；维持原范围边界（数值归属不可判读，读者无法定位事实源）。
- **影响范围**：范围边界（文档头）；US1.2；架构 §3.4（新增，配套 ADR-006）；ROADMAP §1。

### SDR-006 ADR-003 修订落地：废除"未知"第三态，能力以显式定义为准（2026-09-18）

- **背景与动机**：原语义把"任何来源都未收录、用户也未声明"的模型列为"完全未知"，媒体原样发出由服务商裁决。两个否定性事实：① 三态语义使用户无法表达"明确没有此能力"——配置声明只有正向勾选，未勾选与未触碰无法区分，从 provider 模型列表自动同步生成的条目在同步修复前既不能算支持也不算反对；② 实践证伪（session-8999，2026-09-18）：未定义模型把图片原样发给服务商被拒后落入格式类降级链，得到的是"转换格式"指引而非委托指引，白白重试多轮。委托链路（留档句柄 + 子代理读图）修复后，"按不支持处理"已可恢复，剥夺成本与放行失败成本的天平反转。
- **决策**：模型能力以显式定义为准——设置中声明了能力词表即权威（未列出的媒体模态 = 不支持）；声明为空时以模型名推断兜底；两者皆无信号则一律按不支持处理（媒体部件投影为占位文本并注入能力缺口提示），不再放行给服务商裁决。废除"未知"第三态。从 provider 模型列表自动同步生成的条目一旦同步修复将携带非空声明，天然落入"声明为王"分支，无需为同步数据单独建模"无信息"态。
- **被拒方案**：维持"未知放行"（session-8999 证伪——徒劳重试 + 误导性恢复指引）；未知时主动探测（额外请求成本与误判面，维持原否决）；三态持久化（"未触碰 ≠ 明确关闭"复杂化设置模型——以修复 models.dev 数据源取代语义复杂化）。
- **影响范围**：US3.1（验收第二、三条按新语义重写）、US4.1、US5.2（触发条件从"已知不支持"放宽为"按不支持收敛"）；提案 P-4 降级为推断误报残留的增强；架构 ADR-003 修订（2026-09-18）；数据前提——models.dev 目录自动填充的正确性由 rust core + web 的同步缺陷修复另案处理，不在本域跟踪。

### SDR-007 新增 E9（工作区文件与文件夹引用），`@` 定为结构化引用（2026-10-26）

- **背景与动机**：web/桌面 的 `@` 目前只做文本补全——选中后把路径作为普通文本插入、连 `@` 标记本身一并吃掉，引擎侧不解析也不注入，助手是否真的读了这个文件完全不可知；与终端（US1.3 的 `@path` 语义）也不一致。用户的真实诉求是"让助手聚焦这几份代码/这个文件夹"，这是一个**输入可达性**问题，与"把媒体交给助手"同属本域，故扩本域而非新建域。
- **决策**：① 新增 Epic E9（P0），定义为工作区内文件与文件夹的一等引用；② `@` 的产出是**结构化引用**而非文本——引用在输入框内可辨识、可整体删除、可预览，引擎保证其内容按 US9.4 的形态送入本轮上下文；③ 文件夹引用只做**列表清单注入**，不整段注入内容；④ 选中文件夹时提供"进入"（Tab / 行尾箭头，菜单保持打开）与"引用"（Enter / 行主体，菜单关闭）两个正交动作；⑤ 检索范围严格限定在工作区内（含已附带的多个目录根），遵守忽略规则，隐藏/被忽略条目通过输入以 `.` 开头的片段按需放出；⑥ 引擎侧维护可随时丢弃的路径索引并反映文件增删，不依赖任何持久化索引；⑦ 用户手打但未从候选选中的 `@xxx` 不产生引用。
- **被拒方案**：维持纯文本补全（无法回答"助手到底读没读"，也无法演进到"哪些引用真正进了上下文"的可见性）；`@` 注入目录内容而非清单（大目录会挤占上下文，阈值需反复调）；文件夹只作检索范围不产生引用（用户选完文件夹看到"什么都没发生"）；全盘检索或允许绝对路径跳出工作区（与权限边界不一致，会出现"引用成功但助手读不到"的错觉）；把该能力并入对话渲染域或新建独立域（前者只管呈现不管采集，后者会与 US1.3 形成两套"引用"术语）。与外部参考实现的差异及理由见架构 [multimodal-input-architecture.md](multimodal-input-architecture.md) §11.2。
- **影响范围**：范围边界、角色定义、新增 §9（US9.1–9.10）；§10 消费端差异登记新增两行；§11 新增提案 P-9；附录 A 新增四项术语；交互契约 [file-reference-uiux.md](file-reference-uiux.md)（新增）；架构 §11 + ADR-007（新增）；术语表 MI3（文件引用）；ROADMAP 新增 E9 执行项。
