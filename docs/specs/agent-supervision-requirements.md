# 多 Agent 督导域 — 需求文档（User Stories）

> 状态：v1 基线 · 2026-09-14 · 待用户评审
> 本文是督导域需求侧的唯一事实源（内部规格文档，不进文档站构建，中文单语）。
> 产品愿景：**让用户把活委托出去之后依然心里有底**——主会话区永远干净、聚焦对话本身；想看过程时有层级分明的观测面，一层比一层深；想管的时候随时能管（停止、暂停、纠偏）；界面上的每一个信号（按钮、状态、进度）都与真实执行一致，没有假承诺。
> 配套文档：技术形状与呈现架构见 [agent-supervision-architecture.md](agent-supervision-architecture.md)；现状盘点（含代码事实与本域来源会话的实证）见 [agent-supervision-context.md](agent-supervision-context.md)。
> 术语规范：委托、督导等跨域词的唯一定义见 [glossary.md](glossary.md)（SV1–SV2）；本文件只使用规范叫法。
> 验收标准统一 Given-When-Then；优先级 P0 > P1 > P2。
> 范围边界：本域只覆盖**用户对被委托/自主运行的 agent 的观察、控制、干预的界面与信息架构**。派发与子代理生命周期语义归 [subagent-requirements.md](subagent-requirements.md)；团队协作模型（任务板、角色通信、仲裁）归 [collaboration-requirements.md](collaboration-requirements.md)；转录渲染通用协议与快照协议归 conversation-rendering 域；跨 agent 回放调试归可视化调试工具（vis）。

## 0. 角色定义（Personas）

| 角色 | 场景 | 核心诉求 |
|---|---|---|
| **督导者**（发起委托、观察进展的用户） | 在网页/桌面上看着委托出去的活推进 | 对话区不被过程细节淹没；我想看的时候一键直达、一层层看；我不关心的时候它就安安静静一行 |
| **团队发起人**（协作模式下发起团队的用户） | 看着一群 agent 自主推进 | 一屏看懂谁在干什么、卡没卡；我能随时介入纠偏，介入不破坏协作 |
| **界面消费端**（web / 桌面 / 终端的呈现层） | 渲染委托卡片、详情面板、任务坞 | 同一状态源；单个与批量委托同一套呈现规则，不各写一套 |

## 1. 根需求：理想形态（终态定义）

本域一切设计服从五条根需求。它们是验收任何督导界面变更的最高准则：

**R-1 对话区纯净。** 主会话消息区是"对话"的地方，不是"监控台"。委托（无论单个还是批量）在对话区中的呈现永远是最小化的：一行卡片承载"委托了什么、进展如何"；执行过程细节（工具调用记录、流式输出、中间推理）**永不**进入对话区。

**R-2 渐进披露三层。** 督导信息按"摘要 → 聚焦 → 深挖"三层组织，逐层加深、逐层按需：
- **摘要层（对话区内）**：一行卡片，默认收起；
- **聚焦层（右侧详情面板）**：选中一个被委托 agent 后的完整工作过程；
- **深挖层（聚焦层内部）**：该 agent 执行历史的展开形态（调用叙事、推理链）。

**R-3 统一委托心智。** 单个委托（Agent 工具派发）与批量委托（AgentSwarm 模板派发）在用户界面上是**同一种东西**——区别只在数量。数量是数据属性，不是交互范式属性：不因数量不同而出现两套卡片形态、两套展开行为、两套详情入口。

**R-4 诚实呈现。** 界面上的每一个进度与状态信号都必须能从真实执行推导。不合成百分比、不虚构预计完成时间——发现信号造假一次，信任即归零。允许的信号形态：完成计数（N/M）、阶段分布、当前活动摘要、最近事件。

**R-5 三轴完备。** 督导能力沿三轴定义完备：**可观测**（实时看得到、事后回看得回）、**可控**（停止/暂停/审批处处可达且真生效）、**可干预**（能向指定 agent 定向下达指令）。三轴与呈现三层正交：任何一层都不因某轴能力缺失而呈现假入口。

## 2. Epic S1：委托卡片的对话区呈现（摘要层）

> 解决"对话区里委托长什么样"。对应根需求 R-1、R-3、R-4。

### US1.1 统一委托卡片（P0）

作为督导者，我想让单个委托和批量委托在对话区里呈现为同一种卡片，以便我不用学两套界面规则。

验收：
- Given 任一委托（单个或批量）出现在对话流中，Then 它呈现为一张可收起的卡片：图标 · 描述 · 进度信息 · 状态 · 耗时 · 详情入口，全部在头部一行内
- Given 批量委托运行中，When 我不进行任何操作，Then 卡片保持收起（批次头 + 成员行均为收起态），对话区不会因它而展开任何过程细节
- Given 批量委托已启动若干成员，Then 卡片按实际启动的成员数显示成员行：每行含成员标识、状态标记与最新活动的单行摘要；未启动的成员不占行（SDR-007）
- Given 我手动展开卡片，Then 展开内容只含轻量信息（任务描述、型号、成员名单与各自状态），不含工具调用记录、流式输出或成员执行细节
- Given 我点击某个成员行，Then 进入该成员的详情视图（右侧督导面板聚焦该成员）
- Given 委托已结束（无论成功/失败/中断），When 我重新打开会话回看，Then 卡片形态与实时结束时一致——实时观感与回看观感不因界面刷新而改变
- Given 单个委托与批量委托并排出现在同一会话，Then 两者的卡片结构、展开行为、详情入口完全同构，仅聚合信息（如完成计数）与成员行数因数量不同而出现或省略

### US1.2 一行进度摘要（P0）

作为督导者，我想从收起的卡片上直接读出"进行到哪了"，以便不点开任何东西就掌握态势。

验收：
- Given 委托运行中，Then 卡片头部行内实时显示：运行状态标记、已完成成员数 / 总成员数（单成员委托省略计数）；各成员行的单行摘要共同给出"谁在干什么"的态势
- Given 批量委托的部分成员完成、部分仍在运行，Then 完成计数与各阶段（排队/进行中/等待用户/挂起/完成/失败/中止）的分布从计数信息中可读，成员行的状态标记逐成员一致；成员被用户/批次取消呈现"已中止"，与"失败"分档呈现，不混同（SDR-008）
- Given 批量委托中任一成员在等待我的决策（审批/作答），Then 卡片聚合状态呈现"需要你处理"档（区别于运行中/成功/异常），点击可达该等待项（US5.4）
- Given 所有成员已结束，Then 状态标记如实反映聚合结果（全部成功为成功；任一失败/中断为异常）

### US1.3 详情入口（P0）

作为督导者，我想从委托卡片一键进入该委托的过程详情，以便按需查看执行过程。

验收：
- Given 委托卡片所在处存在可查看的过程数据（实时或已持久化），Then 卡片行提供"打开详情"入口，点击后在右侧详情面板聚焦该委托
- Given 不存在可查看的过程数据（例如委托已结束且过程未被保留），Then 该入口**不出现**——不允许出现"点了没反应"或"点开是空的"的入口
- Given 详情面板已聚焦该委托，When 再次点击入口，Then 面板关闭（入口同时承担开/关两个方向）

### US1.4 异常可见（P0）

作为督导者，我想委托出现异常时在对话区就能察觉，以便不必逐个点开排查。

验收：
- Given 委托任一成员失败或被中断，Then 该委托卡片以醒目但克制的方式标记异常（如边框变色 + 异常徽章），且不遮挡对话区其余内容
- Given 系统开启了"减少动效"偏好，Then 异常标记采用静态视觉方案，不使用动画

### US1.5 呈现诚实（P0）

作为督导者，我想委托卡片上不出现无法从真实执行推导的信号，以便我建立的每一分预期都是真的。

验收：
- Given 任意委托状态，Then 卡片不呈现完成百分比、预计剩余时间或任何合成推算信号
- Given 卡片呈现的计数、阶段、活动摘要，Then 每一项都能与底层真实事件一一对应（成员完成一个，计数加一个）

## 3. Epic S2：过程详情面板（聚焦层）

> 解决"过程细节在哪里看、怎么看"。对应根需求 R-1、R-2、R-5（观测轴）。

### US2.1 过程细节的唯一表面（P0）

作为督导者，我想让右侧详情面板成为委托过程细节的唯一展示位置，以便信息有唯一的家、界面有唯一的规则。

验收：
- Given 任何委托成员的工具调用记录、流式输出、中间推理，Then 它们只在详情面板中呈现，对话区与卡片展开态均不出现
- Given 我从任一入口（卡片详情入口、任务坞成员行、卡片展开态的成员名）发起查看，Then 都进入同一个详情面板，看到同一份内容

### US2.2 单成员聚焦视图（P0）

作为督导者，我选中一个成员后想看到它的完整工作档案，以便判断它干得怎么样。

验收：
- Given 详情面板聚焦一个成员，Then 面板呈现：成员身份（类型/角色名、所用型号）、收到的任务原文、实时输出的文本、按时间排列的工具调用过程、最终结果（已结束时）
- Given 该成员仍在运行，Then 其实时输出与调用过程持续流入面板；面板跟随最新内容滚动，但当用户向上翻阅时停止跟随，回到接近底部后恢复跟随

### US2.3 多成员选择（P0）

作为督导者，批量委托打开详情面板时我想先看成员概览再选人，以便快速定位到关心的成员。

验收：
- Given 批量委托的详情面板，Then 面板顶部呈现成员选择区：每个成员一行（状态点 · 名字 · 型号 · 当前活动单行摘要 · 阶段），点击选中
- Given 我选中某成员，Then 面板主体切换为该成员的聚焦视图（US2.2 的同一形态）
- Given 某成员出现异常，Then 其选择区行内有明确视觉标记，无需点开即可察觉
- Given 单个委托打开详情面板，Then 不出现成员选择区，直接呈现该成员聚焦视图（数量为 1 时省略选择结构）

### US2.4 成员稳定色（P1）

作为督导者，我想同一成员在卡片、选择区、各视图中的颜色标识一致，以便跨位置的视觉追踪。

验收：
- Given 一个委托批次内的成员，Then 每个成员获得批次内稳定且互不混淆的颜色标识，用于状态点与选择区行
- Given 同一成员出现在聚合视图（卡片分布条）与选择区，Then 其颜色一致

### US2.5 事件四分类（P1）

作为督导者，我想成员过程里的四类事件（推理、工具调用、状态变化、错误）有可辨识的视觉区分，以便扫读时快速定位关键信息。

验收：
- Given 成员过程事件流，Then 推理（思考）、工具调用、状态变化、错误四类事件各有独立视觉样式（图标/色彩/排版至少一项区分），且图例可发现
- Given 错误事件，Then 其呈现包含错误原因，样式为四类中最醒目

### US2.6 修改类调用的差异入口（P1）

作为督导者，我想从成员的文件修改类调用直接跳到改动对比，以便不离开面板就能审查它改了什么。

验收：
- Given 成员过程含文件修改类工具调用，Then 该调用条目提供"查看改动"入口，点击后在差异查看面呈现该次改动的对比
- Given 调用为读取类或其它非修改类，Then 不出现该入口

### US2.7 长输出的性能（P1）

作为督导者，我想成员输出很长时面板依然流畅，以便长时间运行的大量委托不拖垮界面。

验收：
- Given 单成员过程事件超过界面呈现的舒适量级，Then 面板采用按需渲染（虚拟滚动等手段）保持流畅，滚动行为与常规列表无差别
- Given 多个成员同时运行且各自持续产出，Then 面板与对话区的界面响应不随累计事件量显著退化

### US2.8 详情面板的位置语义（P1）

作为督导者，我想详情面板与其它详情（文件预览、思考过程等）共享右侧区域的占用规则，以便右侧不会被多个面板撕碎。

验收：
- Given 详情面板打开时其它详情被请求打开，Then 同一时刻只呈现一个详情（后开的替换先开的），互斥规则与既有右侧详情一致
- Given 我关闭详情面板，Then 回到我发起查看前的界面状态

## 4. Epic S3：深挖叙事（聚焦层内部）

> 解决"看的过程是否可读"。执行历史以"叙事"而非"日志转储"呈现。

### US3.1 调用叙事（P0）

作为督导者，我想成员的工具调用按发生顺序组成可读的叙事（调用了什么 → 参数摘要 → 结果），以便像读工作日志一样理解过程。

验收：
- Given 成员的工具调用序列，Then 按发生时间排列，每次调用呈现：调用名、参数的人读摘要、结果摘要（或进行中标记）
- Given 单次调用的输出超过折叠阈值，Then 默认呈现头尾若干行 + 折叠提示（"还有 N 行"），点击展开全量
- Given 相邻调用之间存在流式文本或推理，Then 它们按真实发生位置穿插在叙事中，不与调用混排

### US3.2 推理过程可展开（P1）

作为督导者，我想成员的推理（思考）内容默认折叠为一行摘要、按需展开，以便想深究时看得到、不深究时不占空间。

验收：
- Given 成员过程含推理内容，Then 默认呈现为折叠形态（首行摘要或"推理过程"标记）
- Given 我展开推理，Then 完整推理文本按时间顺序呈现，且与工具调用的穿插关系保持真实顺序

## 5. Epic S4：观测的完整性（含回看）

> 解决"看完之后还看不看得到"。对应根需求 R-5（观测轴）的回看半轴。

### US4.1 刷新不致盲（P0）

作为督导者，我想刷新页面或重开会话后，委托的名册与过程依然可查，以便回看历史会话时与实时观感一致。

验收：
- Given 一个含批量委托的历史会话被重新打开，Then 委托卡片呈现（描述、最终状态、成员结果聚合），可展开成员名单与各自终态
- Given 该会话的成员过程数据已随会话持久化，Then 详情入口可用且面板内容完整（名册、成员终态、过程叙事、结果）
- Given 成员过程数据未持久化（能力边界），Then 详情入口按 US1.3 规则隐藏，不出现空壳面板
- Given 实时与回看呈现同一委托，Then 卡片与面板的结构一致（内容可因数据边界不同，结构不允许不同）

### US4.2 回放与深度观测（P2）

作为督导者/开发者，我想跨 agent 的关系与时间线的深度观测在调试工具中获得，以便产品界面保持简洁。

验收（裁决性 US——产出是定位而非功能）：
- Given 需要拓扑关系图、时间线泳道、跨 agent 消息追踪等深度观测，Then 其归属为可视化调试工具（vis），不进入产品对话界面
- Given 产品界面需要关系信息，Then 只以轻量摘要形态呈现（如卡片上的成员名单），不引入图/泳道类重型可视化

### US4.3 用量归因（P1）

作为督导者，我想每个成员的用量与成本可归因查询，以便评估委托的开销。

验收（指针性 US——数值口径与能力归 subagent 域）：
- Given 详情面板聚焦某成员，Then 该成员的用量信息（输入/输出等口径）可查，口径与既有会话用量统计一致
- 给 subagent 域的指针：成员级用量事件与聚合能力由该域承接，本域只约定呈现位置与一致性

## 6. Epic S5：可控（停止 / 暂停 / 审批）

> 解决"想管的时候管得住"。对应根需求 R-5（可控轴）。停止与审批的执行语义归 subagent 域；本域约定它们的界面可达性。

### US5.1 停止处处可达（P0）

作为督导者，我想对运行中的委托在各个呈现层都能找到停止入口，以便不必回到特定位置才能止损。

验收：
- Given 委托卡片（收起态）、详情面板（成员视图与选择区）、任务坞成员行，Then 任一处都提供该成员/委托的停止入口，且入口只在成员可停止时出现
- Given 我从任一处发起停止，Then 停止真实生效（语义与验收归 subagent 域的停止条目），所有呈现层的该成员状态同步收敛，无残留"运行中"
- Given 成员已结束，Then 停止入口消失（或收敛为不可用且不误导的形态），不出现可点击但无效的信号

### US5.2 暂停与恢复（P1）

作为督导者，我想暂停某个成员（保留其已有进展、停止继续执行），稍后恢复，以便临时控制成本或节奏。

验收（依赖引擎能力，能力落地前本 US 处于等待态——见提案登记）：
- Given 成员运行中，When 我暂停，Then 该成员停止推进但进展与上下文保留、状态明确呈现"已暂停"，卡片聚合计数如实反映
- Given 成员已暂停，When 我恢复，Then 该成员从中断处继续推进，过程叙事无缝续接
- Given 能力未落地时，Then 界面不呈现暂停入口（R-5：不呈现假入口）

### US5.3 审批标明发起者（P0）

作为督导者，多个 agent 并发运行时，我想每张审批请求卡明确显示是哪个成员在请求什么，以便决策有上下文。

验收：
- Given 并发多成员运行时任一成员触发审批，Then 审批卡呈现该成员的身份（名字/角色），与对话区、面板中的标识一致
- Given 单代理会话（无成员并发），Then 审批卡呈现与现状一致（不因本需求增加噪音）

### US5.4 成员等待用户的状态与直达（P0）

作为督导者，批量委托中任一成员需要我决策（审批/作答）时，我想在委托卡片与成员视图立即看到"等待中"状态并直达决策入口，以便我的等待不变成整个委托的隐性阻塞。

验收：
- Given 批量委托运行中任一成员发起审批请求，Then 该成员行与成员聚焦视图呈现"等待审批中"状态标记，委托卡片聚合状态呈现"需要你处理"
- Given 我点击该状态标记，Then 直达（或内联呈现）对应的审批卡；决策后成员状态自动回到"进行中"并继续推进，过程叙事续接
- Given 成员等待的是问询而非审批，Then 呈现"等待作答中"，行为与审批同构
- Given 全部等待已处理或无等待成员，Then 聚合状态回到常规运行态（或终态）
- Given 我刷新页面或断线重连，Then 未决的等待状态与审批卡一同恢复，"待我处理"的事项不因界面刷新丢失
- Given 我长时间不决策，Then 成员不因等待我的时间而被判超时失败；真实的执行超时仍如实呈现（等待豁免的预算规则见 subagent 域 ADR-011）

## 7. Epic S6：可干预（定向指令）

> 解决"能不能直接对某个 agent 说话"。对应根需求 R-5（干预轴）。

### US6.1 定向指令（P2）

作为督导者/团队发起人，我想向指定的成员直接下达指令（纠偏、补充要求、改变方向），以便不经主代理转述、不中断协作地介入。

验收（依赖引擎能力，能力落地前处于等待态——见提案登记）：
- Given 成员运行中，When 我在详情面板向它发送指令，Then 指令进入该成员的下一轮上下文，效果可见于其后续行为；面板中我的指令以可辨识的形态出现在该成员的过程叙事中
- Given 指令需要权限配合（如涉及工具操作），Then 按既有审批规则执行，干预不是权限豁免通道
- Given 能力未落地时，Then 面板不呈现指令输入（R-5）

### US6.2 干预入口的位置语义（P0）

作为界面消费端，详情面板需要在结构上预留干预操作的落位，以便引擎侧干预能力落地时无需重构界面。

验收（裁决性 US）：
- Given 详情面板的成员视图，Then 其结构包含操作区（停止等即时控制）与指令输入区的固定落位；能力未就绪的落位不渲染占位控件
- Given 干预能力落地，Then 其入口出现在预留落位，不挤占叙事区、不需要面板结构变更

## 8. Epic S7：协作模式下的升格

> 解决"团队自主推进时督导界面长什么样"。依赖 collaboration 域 E1–E3（团队骨架）落地；本域只定义观测/控制/干预的界面形态，团队语义归 collaboration 域。

### US7.1 Agent 总览（P1）

作为团队发起人，我想一屏看到团队全景（谁在干什么、任务板快照、最近关键事件），以便掌握整体进展。

验收：
- Given 团队运行中，Then 存在一个总览面：成员卡墙（每张卡 = 身份/角色 + 状态 + 当前活动一行 + 该成员的详情入口）+ 最近关键事件流（任务状态变更、认领/交接、成员起止，摘要级）
- Given 我点击成员卡，Then 进入该成员的详情面板（US2.2 的同一形态——单个成员视图与团队成员视图是同一组件）
- Given 任务坞在非协作会话中的既有职能（后台任务列表），Then 在协作会话中升格为总览的成员卡墙入口，两者是同一表面在不同模式下的形态，不是两个并列功能

### US7.2 总览的诚实与克制（P1）

作为团队发起人，我想总览只呈现可从真实执行推导的信息，以便掌握的是事实而非合成数字。

验收：
- Given 团队总览，Then 不呈现全局完成百分比、预计完成时间；呈现成员状态分布、任务板事实快照、最近事件
- Given 总览信息密度超过单屏，Then 通过筛选（按成员/按事件类型）而非聚合造假解决

### US7.3 干预常驻（P1）

作为团队发起人，协作运行中我想干预入口始终可达，以便介入不需要导航成本。

验收：
- Given 团队运行中，Then 总览中每个成员卡与详情面板均可发起该成员的干预（定向指令，依赖 US6.1）与控制（停止/暂停）
- Given 我向团队广播指令（而非定向），Then 属 collaboration 域 US4.3 的既有裁决，本域只保证其入口与定向干预在同一操作区，心智一致

## 9. 非功能需求（NFR）

| # | 需求 | 指标/约束 |
|---|---|---|
| N1 | 单一状态源 | 委托/成员的状态只有一个权威判定源；卡片、面板、任务坞/总览读同一状态，不出现互相矛盾 |
| N2 | 呈现-执行一致 | 界面上任何可交互信号（入口、按钮、状态）背后能力完备；"存在但无效"是缺陷不是降级（R-5 的验收化） |
| N3 | 呈现性能 | 多成员并发 × 长过程下，对话区与面板的交互响应不随累计事件量线性退化；超量内容按需渲染 |
| N4 | 可访问性 | 异常动效、状态色均遵循系统"减少动效"偏好与既有色彩对比标准；全部操作键盘可达 |
| N5 | 端点对等原则 | 本域以 web 为主定义面；终端端的对等呈现由呈现层各自承接（对齐 subagent 域 US12.5 的既有原则），不因端点不同产生语义分叉 |
| N6 | 观测即事件 | 本域全部呈现消费事件/事实数据，不解析自然语言文本获取结构（凡需要结构处，作为契约需求输入引擎侧，见架构文档 §4） |

## 10. Out of Scope

- 派发入口与派发参数语义（subagent 域 E1）
- 子代理生命周期、超时、并发节奏（subagent 域 E5/E6）
- 团队组建、任务板、角色通信、仲裁（collaboration 域 E1–E4）
- 转录渲染通用规则、快照协议六要素（conversation-rendering 域）
- 跨 agent 回放的深度观测工具形态（可视化调试工具 vis）
- 多人类用户协同督导（本域督导者为单人）

## 附录：需求决策记录（SDR）

### SDR-001 单个与批量委托统一为一种心智（2026-09-14）

1. **背景与动机**：界面现状中单个委托与批量委托各自演化出两套卡片形态、两套展开行为（单个：收起 + 面板详情；批量：运行时自动展开 + 行内成员手风琴），用户需学两套规则，且两套中各含对方缺失的优点（见 [agent-supervision-context.md](agent-supervision-context.md) §2 对照表）。两者在用户心智中是同一行为（"把活委托出去"）的数量变体。
2. **决策**：单一委托心智——统一卡片组件、统一展开行为、统一详情入口；聚合信息（计数、分布）按数量参数化呈现，数量为 1 时省略聚合结构（US1.1）。单成员的批量委托不再需要特判降级。
3. **被否决的备选方案**：a) 保留两套组件、互抄优点——重复实现且不一致会再次发生；b) 增加用户偏好开关切换两种形态——默认形态已满足"点开即看"，开关的边际价值低于维护成本。
4. **影响范围**：US1.1、US2.3、全部呈现层组件；conversation-rendering 域的工具卡片呈现条目。

### SDR-002 对话区零过程细节原则（2026-09-14）

1. **背景与动机**：批量委托运行时在对话消息区自动展开成员过程（工具调用记录、流式输出），把"对话的地方"变成"监控台"；并非所有用户都关心子代理活动，过程细节的强加呈现构成污染（本域起源的真实用户反馈，实证见 context §1）。
2. **决策**：委托过程细节**永不**进入对话区；对话区内委托只保留一行收起卡片（可展开轻量摘要）；过程细节的唯一表面是详情面板（US1.1/US2.1）。刷新/重开后的观感与实时观感必须一致（US1.1 第 4 条）。
3. **被否决的备选方案**：a) 保留自动展开 + 提供收起偏好——默认体验即污染，偏好救不了第一印象；b) 过程细节独立弹窗——丢失对话流中的位置锚点，且右侧面板基建已存在。
4. **影响范围**：US1.1、US1.2、US2.1；subagent 域 US7.2（界面呈现）中涉及蜂群卡片行为的条目以其为上位约束。

### SDR-003 诚实呈现：拒绝合成百分比与预计时间（2026-09-14）

1. **背景与动机**：委托工作负载的完成度与耗时无法从真实执行可靠推导；合成的"67% / 预计 2 分钟"类信号一旦被证伪，用户对全部进度信号的信任归零——可视化首要价值是建立信任而非制造掌控感。
2. **决策**：本域全部界面只呈现可推导信号：完成计数（N/M）、阶段分布、当前活动摘要、最近事件（US1.5、US7.2）；NFR N2 将"信号与真实效果一致"定为验收级约束。
3. **被否决的备选方案**：以估算值标注"仅供参考"——置信度无法表达，误导面大于信息面。
4. **影响范围**：US1.2、US1.5、US7.2；N2。

### SDR-004 全景总览分期：小规模由卡片+任务坞承担，协作模式才升格（2026-09-14）

1. **背景与动机**：外部调研（多 Agent 产品横向对比，见 context §6）提出的"任务全景仪表盘"层在当前产品形态（会话式编码助手、一次性 2–5 成员委托）中没有承载位置——不存在常驻 mission 屏幕；且总览层的价值随并发 agent 数与自主性增长而增长。
2. **决策**：总览面（成员卡墙 + 活动流）**只在协作模式（团队自主推进）下存在**（US7.1），由既有任务坞升格而来——两者是同一表面的模式化形态；非协作会话的态势感知由委托卡片行的聚合摘要承担。升格不需要重写：卡片/成员视图/面板均为总览的直接组件。
3. **被否决的备选方案**：a) 现在即建常驻总览屏——解决不存在的问题，且与"对话区纯净"的产品心智冲突；b) 总览做成独立浮窗——碎片化右侧区域。
4. **影响范围**：US7.1、US7.2；conversation-rendering 域（任务坞的升格路径）。

### SDR-005 拓扑图与时间线泳道归调试工具，不进产品界面（2026-09-14）

1. **背景与动机**：跨 agent 关系图与时间线泳道是观测工具形态，服务于"几十个 agent 协作时谁连着谁"的排查场景；产品界面引入图类重型可视化违背渐进披露与克制原则，而可视化调试工具本就以会话回放为职——引擎侧每 agent 独立日志（事件溯源已是事实）正是其数据源。
2. **决策**：深度观测（拓扑、泳道、跨 agent 消息追踪）归可视化调试工具（vis）；产品界面最多呈现轻量关系摘要（US4.2）。
3. **被否决的备选方案**：产品内嵌可折叠拓扑视图——维护两套回放能力，产品侧收益不成比例。
4. **影响范围**：US4.2；可视化调试工具的演进方向。

### SDR-006 干预与暂停为引擎前置项，界面只做槽位预留（2026-09-14）

1. **背景与动机**：定向指令（对运行中成员下达 steering）与暂停/恢复需要引擎侧新语义（当前仅具备事后续作与终止），界面先行会呈现假入口，违反 N2。
2. **决策**：US5.2/US6.1 定义终态验收但显式依赖引擎提案裁决（登记于跨域提案登记簿）；界面侧只交付 US6.2（结构预留，不渲染占位控件）；能力落地前不呈现相关入口。
3. **被否决的备选方案**：界面先行实现输入框、后端返回"不支持"——正是 N2 禁止的"存在但无效"缺陷。
4. **影响范围**：US5.2、US6.1、US6.2；subagent 域（提案的语义裁决归属）。

### SDR-007 主会话区委托块按实际启动成员数显示收起成员行（2026-09-15）

1. **背景与动机**：SDR-002 落地后，整批委托在对话区收敛为一张一行卡片——批次内"哪个成员在干什么"在对话区完全不可见，须点开右侧面板才能分辨；真实使用（tx1 会话）显示用户需要一眼扫到每个成员的存在与状态，但不需要过程细节。同时该会话暴露了成员工具事件泄漏进主转录的缺陷（见 context §8），修复时需一并明确"成员在对话区的合法形态"。
2. **决策**：委托卡片的收起形态从"整批一行"修订为"批次头行 + 每个实际启动成员一行"：批次头承载描述、完成计数、聚合状态；每个成员行承载成员标识、状态标记与最新活动的单行摘要（收起、不含工具调用记录与流式输出）；点击成员行进入该成员的详情视图（右侧督导面板聚焦视图）。成员行数量以实际启动的成员为准（未启动/排队中的成员不占行）。SDR-001/SDR-002 的其余原则不变：单个委托（N=1）的成员行即卡片主体，无批次头聚合结构；过程细节仍永不进对话区。本决策修订 SDR-002 中"只保留一行收起卡片"的字面粒度。
3. **被否决的备选方案**：a) 维持整批一行（现状）——批次内成员态势在对话区不可见，与"一眼掌握谁在干活"的诉求冲突；b) 恢复运行时自动展开成员过程——回到 SDR-002 已否决的监控台污染。
4. **影响范围**：US1.1、US1.2 的收起形态描述；web 委托卡片渲染与既有 browser e2e 断言更新；context §8 泄漏缺陷的修复以本决策为"成员行"的合法形态边界。

### SDR-008 成员等待用户是必须可见的成员状态（2026-09-16）

1. **背景与动机**：成员执行中请求审批时，界面上该成员仍显示"进行中"，无任何"正在等你"的信号；若等待期间成员因其他信号（如超时）落败，用户看到的是"失败"而非"我有一件事没处理"——阻塞归因错误。真实使用（2026-09-16，rust 核心 + web 的蜂群会话）暴露三类信号失真：等待审批不可见、等待时间计入成员时长预算导致超时误杀、状态通道断开使审批卡随断连消失（实证见 [agent-supervision-context.md](agent-supervision-context.md) §9）。根需求 R-4/N2 要求界面信号与真实执行一致——"等待用户"是成员的真实状态，必须可见；"用户取消"与"执行失败"也必须分档可见。
2. **决策**：① 成员等待用户（审批/作答）时呈现专属状态（"等待审批中/等待作答中"），可直达决策入口（US5.4）；② 委托卡片聚合状态增加"需要你处理"档（attention），与运行中/成功/异常并列，不计入异常；③ 用户取消与失败分档呈现（"已中止"）；④ 成员状态以引擎挂起事件为唯一事实源（架构 ADR-008），迁移期允许呈现层以待决审批关联做**显式标注待删**的过渡推导；⑤ 刷新/重连后等待状态与审批卡一同恢复；⑥ 等待用户的时间不计入成员时长预算（引擎侧承接：subagent 域 ADR-011）。
3. **被否决的备选方案**：a) 等待折入"进行中"——阻塞归因错误，用户不知委托卡在自己的决策上；b) 只在审批卡显示、成员行不显示——成员状态与审批队列两处口径不一致；c) 提高成员超时上限缓解——治标，超时误杀仅阈值变化，且把"等用户"与"跑太久"混为一谈。
4. **影响范围**：US1.2、US1.4（聚合状态档位）、新增 US5.4、US4.1（等待状态恢复）；架构 §2.1/§4.6/ADR-008；subagent 域 ADR-011（引擎侧承接）；glossary A14。
