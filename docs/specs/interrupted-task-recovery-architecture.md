# 中断任务恢复（interrupted-task-recovery）架构文档

> 本文档描述中断任务恢复域的实现机制、接口形状与数据流；动机保持抽象（不含代码事实），现状依据见 [interrupted-task-recovery-context.md](interrupted-task-recovery-context.md)。需求见 [interrupted-task-recovery-requirements.md](interrupted-task-recovery-requirements.md)（下称「需求文档」，裁决编号 D-M* 沿用其 §8）。
> 运行目标为 Rust core + web（desktop 外壳行为一致；desktop-lite 复用同一引擎）。

## 0. 架构总览

```
├─ 呈现层 ─────────────────────────────────────────────────────┐
│ web 恢复通知卡片（逐任务按钮组 + 批量按钮；非模态）             │
│ web 会话树行徽标「运行中断」+ 悬停/菜单就地操作 + 工作区计数   │
├─ 服务层（embedded server 内，进程内 RPC）──────────────────────┤
│ RecoveryService（中断清单 · 状态视图 · 续跑发起 · 忽略收尾）    │
├─ 生命周期层（mirri-server 关闭链路挂钩）───────────────────────┤
│ LifecycleSentinel：启动标记 → 优雅退出记录（含在跑清单）        │
│ 启动时判定：读上次记录 → 异常则反推 → 产出中断清单 → 清记录    │
├─ 存储层 ───────────────────────────────────────────────────────┤
│ <mirri-home>/lifecycle/<instance-id>/    哨兵记录（原子写）     │
│ 会话 wire.jsonl（只读消费：未收尾回合判定沿用既有事实）          │
└───────────────────────────────────────────────────────────────┘
```

**分层动机**（抽象问题）：中断的「判定」是服务进程生命周期的副产物、「识别」是对持久事实的一次只读推导、「呈现与操作」是 web 的消费面——三者若各自为政，会再现「读面不知道磁盘知道的事」的漂移（这正是本域要修的缺口）。因此判定收敛到生命周期哨兵、识别与操作收敛为进程内单一服务，呈现面只做消费。

## 1. 生命周期哨兵（LifecycleSentinel）

### 1.1 记录文件

位置：`<mirri-home>/lifecycle/<instance-id>/`，其中 `<instance-id>` 唯一标识一个服务实例（推荐形态：监听端口 + 启动时刻的组合，如 `55827-1770000000`——端口天然区分主桌面版与轻量版的不同守护进程；同一端口被前实例崩溃遗留时由启动时刻消歧）。两个文件：

```jsonc
// launch.json —— 服务启动时写（A.1）
{ "instance": "55827-1770000000", "started_at": 1770000000000,
  "port": 55827, "pid": 4242 }          // 端口 + pid 供他实例做存活门（§1.2）

// graceful.json —— 优雅退出时写（A.2），含在跑清单
{
  "instance": "55827-1770000000",
  "exited_at": 1770003600000,
  "running_sessions": [
    { "session_id": "sess_a", "interrupted_at": 1770003598000,
      "workspace": "ws-key-a", "title": "实现用户登录接口" }
  ]
}
```

- 写入协议：复用既有原子写基建（0600 临时文件 + rename）；两文件体量恒小（在跑会话数）。
- **多实例**：目录按实例隔离（A.5）——主桌面版（55827）与轻量版（55828）各持各的记录；一实例崩溃不污染另一实例的判定面。

### 1.2 启动时判定（一次性流程）

服务进入可服务状态后、接受首个业务 RPC 前，执行**一次性启动检查**（失败按 F.4 容错，不阻断启动）：

```text
扫描 lifecycle/ 下全部实例目录：
  对每个"非自身"的实例目录：
    先过存活门（A.5）：
      目录端口 == 自身端口 → 结构性已死（端口唯一占用者已换人，
        现任就是自己），免探测直接进入判定
      否则按 launch.json 携带的端口做本地连接探测，
      pid 探活作裁决辅助（可选）：
        端口通且 pid 仍活 → 该实例在正常运行：
          目录既不判定也不删除，跳过
          （这是 A.5 的硬性执行点——否则轻量版启动会把正在运行的
          主桌面版误判为异常退出，V10）
        端口通但 pid 已死（端口被无关进程复用）
          → 判死进入判定，判定后清理目录（防永滞留）
        端口不通 → 进入判定：
          有 launch.json 且无 graceful.json
            → 该实例异常退出（A.3）
            → 磁盘反推该实例的中断清单（§1.3）
          有 graceful.json
            → 该实例优雅退出
            → 中断清单 = graceful.json 的 running_sessions（直读，D-M2）
  合并产出全局中断清单（含来源实例标识），回填前重查幂等（§2.1）
  消费并删除已判定的旧记录目录（A.6 只认最近一个生命周期）
写自身 launch.json（含端口与 pid，供他实例做存活门）
```

- **同端口前实例遗留**：同端口目录免存活探测（见伪代码特例）——旧实例必然已死（端口唯一占用者已换人，现任是自己）；无 graceful.json 即视为前实例异常退出，进入反推；这正是「冷启动即发现上次崩溃」的路径（单实例主路径）。
- **双实例同时启动的竞态**：两实例几乎同时跑启动检查时，回填以「读-判-写」幂等保护——向某会话写入收口前重查该回合是否已有 `interrupted` 收口记录（wire 日志追加型，见 ADR-002/ADR-008）；lifecycle 目录的消费删除以目录 rename（原子移走）为占位，保证单胜者。
- **损坏容错**（F.4）：launch.json 或 graceful.json 解析失败 → 该实例按「无法判定」处理（不产出中断、不报错、日志留痕），记录目录照常删除。
- **判定产物**：中断清单载入 RecoveryService 的进程内状态，同时为每个被中断会话回填「运行中断」结局（§3.2）。

### 1.3 异常退出的磁盘反推（A.4）

反推以「最近一个生命周期的痕迹」为界，逐会话判定：

```text
对每个工作区 × 每个会话的 wire.jsonl（已压缩形态 .gz 的会话：解压读，不还原落盘）：
  从尾部向前扫描，遇到首个 turn.ended（或 turn.cancel）为止：
    若先遇到 turn.prompt（即存在未收尾回合）→ 候选中断会话
  候选会话的该 turn.prompt 记录时间戳 > 该实例 launch.json 的 started_at
    → 属于上一个生命周期（而非更早遗留）→ 判入中断清单
    否则 → 更早遗留，跳过（不翻旧账）
  会话已归档 → 跳过（D.4）
  该未收尾回合处于等待用户决策（有未决的提问/审批记录）
    → 跳过（D-M6）
  fork 出的子会话：中断判定只看「被 fork 的源会话」的收口责任方
    （fork 会话各有独立日志，若子会话自身有未收尾回合且时间窗命中，
    同样判入——不因 fork 关系豁免或扩大）
```

- **interrupted_at 的取值**：优雅路径 = 退出记录写入时刻（或记录内条目时刻）；异常路径 = 该未收尾 `turn.prompt` 的落盘时间戳（最后一次活动可见事实）——72h 保留期统一从中断时刻（两路径各自的上述取值）起算。
- **排队回合的口径**：`turn.prompt` 落盘即视为「在跑」——排队中尚未启动的回合在日志上与运行中的不可区分，且都承载了用户发起意图，计入清单；宁多（一个刚排队即退出的会话被推荐恢复）不漏。
- 尾部扫描的成本天然有界（多数会话末尾几条即见 `turn.ended`）；判定谓词复用既有「最后一个 `turn.prompt` 后无 `turn.ended`」语义（现成只读探测在 serve 路径存在，embedded 路径新增同语义复用，见 context §1.3）。
- **宁少勿误**（F.1）：退出前极短窗口内刚收尾的回合以 `turn.ended` 的时间戳为准判已收尾；刚发起未落盘的 `turn.prompt`（极端崩溃丢尾）宁可漏报。
- 反推只读 wire 日志，不写任何会话数据。

## 2. 「运行中断」结局的回填与呈现数据源

### 2.1 结局成因扩展（D-M3）

回合结局成因在 `turn.ended` 的 reason 载荷层新增 `interrupted` 值；读侧枚举（四值 `Completed/Cancelled/Failed/Stalled` 保持不动）之上，本域新增**呈现层成因视图**：

- 会话被判定中断时，RecoveryService 为该会话的未收尾回合补写一条 `turn.ended { reason: "interrupted", error: { cause: "service_exit" | "graceful_exit" } }` 收口记录（E.2 的「定局收口」，在**识别完成时**一次性写入，而非续跑时才写——保证打开会话的任何读面都看不到悬空回合）；
- **turnId 推导**：被中断回合的 `turnId` 从该未收尾 `turn.prompt` 之后的记录序列推导（该回合内工具调用/事件携带的回合号的最大值 +1 为下界，探测不到则以「同会话 `turn.ended` 序列的最大回合号 +1」兜底）——写入的合成收口必须携带合法回合号；重放路径遇到「先于其 turn.prompt 的 turn.ended」时按乱序容错跳过（合成收口只作呈现定局，不驱动重放语义）；
- **拦截点清单**（防止 `interrupted` 被既有折叠误归为 `failed`/「已中断」徽标）：① 列表读面的 `last_turn_reason` 投影在既有字符串归并**之前**特判 `interrupted`，原样透传新值；② web `SessionRow` 新增 `interrupted` 徽标分支（§4）；③ 会话 resume 重放期间的活动视图折叠同样在归并前特判（识别已先于任何 resume 完成，重放只会「读到」而非「重演」这条收口）；
- **已处理与过期的读时推导**（ADR-008）：wire 日志是追加型事实日志，收口记录不改写、不删除。「已处理」与「过期」在读面推导——`interrupted` 收口之后若存在更新的 `turn.prompt`（续跑或用户新消息）即视为已处理；过期 = 收口时间戳与 72h 边界的比较（§3 惰性判定）。零额外存储，与追加型日志完全相容；
- 列表读面（`session.list` 行结构的 `last_turn_reason`）在活动视图无数据时（重启后）以持久化的 `interrupted` 收口为准点亮——这使徽标数据天然跨重启（B.2）；
- zh 界面词「运行中断」与既有「已中断（用户取消/失败）」「已停滞」分立，徽标视觉同家族。

### 2.2 状态来源合并

会话行的中断态 = **持久事实**（wire 日志里的 `interrupted` 收口 + 未被后续 `turn.prompt` 处理 + 保留期内）**OR 进程内恢复清单**（本生命周期刚判定、收口写盘竞态窗口期的兜底）。两源合并由列表读面完成——即便识别与写盘之间有毫秒级窗口，进程内清单先行可见，无闪烁。

## 3. 服务层（RecoveryService，进程内 RPC）

`mirri-embedded` 内新模块，与既有 session handlers 平级。RPC 面（klient contract，注册进 mirri-proto 既有注册表）：

```text
recovery.list() -> { interruptions: [{
    session_id, workspace_id, workspace_name, title,
    interrupted_at, cause: service_exit | graceful_exit,
    pending_background_hint?           // E.3：中断时在等后台任务
  }],
  expires_at                            // 保留期边界（72h） }

recovery.resume(session_id) -> { turn_id }   // 单个续跑（C.3/D.2/E.1）
recovery.resume_all([session_ids]) -> { accepted, queued }   // 批量（C.4/C.5）
recovery.dismiss(session_id) -> noResult     // 单个忽略（C.3）
recovery.dismiss_all() -> noResult           // 全部忽略（C.4）
```

- **通知拉取**：web 启动完成会话列表装载后调用 `recovery.list()`（C.1 的时机锚点）；非空则渲染通知卡片。**不引入全局推送通道**（context §5：现无服务器级广播，拉取与「会话列表就绪」的既有时序对齐即可）。
- **保留期到期**：`recovery.list()` 返回时对过期项惰性过滤（读时推导：收口时间戳 vs 72h 边界，ADR-008——不写盘清除）；不设后台定时器（72 小时粒度无需精确定时，F.3 低开销）。
- **跨重启重现**（C.8）：前端每次新启动拉取 `recovery.list()`，未处理项非空即呈现通知——无需额外机制，拉取模型天然满足。
- **幂等**：`resume` 对同一会话重复调用时，若续跑回合已在跑则返回既有 turn（单活动回合排队规则兜底）；`dismiss` 对已消散项为 no-op。

### 3.1 续跑的实现（Epic E）

`recovery.resume(session_id)` 的语义分解：

```text
1. 会话若未驻留 → 走既有 session.resume 重放驻留（复用，不新建驻留机制）
2. 构造续跑请求：用户消息类准入（既有 turn.prompt 通道），
   系统注入中断恢复语境（cause + interrupted_at + 「从中断处继续」指令），
   并携带后台任务提示（若该回合区间内存在未消费的后台任务发起记录
   ——从 wire 日志推导，与判定路径无关，两路径同样适用 → E.3 提示；
   死活裁决交既有孤儿清扫，不重复），
   由 web 在续跑确认时以可见提示呈现，模型侧同时收到待检查清单
3. 清除该会话的中断状态（徽标灭；收口随续跑 turn.prompt 的存在
   被读时推导为已处理，ADR-008——不写盘改写）
```

- **不新增 wire op**：续跑请求就是一次带特殊来源语境的 `turn.prompt`（D-M4 通知/树两通道调用同一 RPC；准入、排队、单活动回合规则全部沿用回合调度域，不发明旁路）。
- **并发上限（C.5）**：`resume_all` 的调度策略——至多 3 个并发在跑，其余按清单顺序排队，前一个收尾后自动启动下一个；每个续跑独立 turn，进度各自可见。

### 3.2 忽略的收尾（E.5）

`dismiss` = 清除恢复推荐身份：中断状态灭（徽标灭；收口记录保持原样，由 ADR-008 的读时推导不再呈现）；会话本体与历史不动。已忽略的会话再次中断（新生命周期）重新进入清单。

## 4. web 呈现层

- **恢复通知卡片**：新组件，挂在冷启动空白草稿页之上（非模态，可关闭）；数据源 `recovery.list()`；逐任务行（工作区名 + 标题 + 相对时间 + `[继续][忽略]`）+ 底部 `[全部继续（N）] [全部忽略]`；行内标题点击跳转深链会话（复用既有 `/sessions/<id>` 路由）。C.6 的「关闭≠忽略」：卡片关闭只收 UI，不调用任何 recovery RPC。
- **会话树徽标**：`SessionRow.vue` 既有徽标机制（用户取消/失败、停滞同族）新增 `interrupted` 分支——数据源为列表行 `last_turn_reason === 'interrupted'`（§2.2 合并后，归并前特判透传，见 §2.1 拦截点）；悬停出现「继续」快捷入口，徽标点击弹小菜单（继续/忽略/打开）；工作区分组标题渲染中断计数（D.3）。
- **i18n**：zh `运行中断`、`恢复中断的任务`、`全部继续（{n}）` 等；en `Interrupted` / `Resume interrupted tasks` / `Resume all (n)`。与既有徽标文案族保持同构。
- **措辞**（C.7）：cause 为 `graceful_exit` → 「上次退出时有 N 个任务仍在进行中」；`service_exit` → 「上次应用异常退出，N 个任务被中断」。

## 5. 生命周期挂钩点（优雅退出记录的写入位置）

优雅退出记录的写入挂在**服务关闭链路**（`request_shutdown` → drain 之间）：收到优雅关闭信号时，先快照在跑会话清单（来源：进程内在途回合注册 + 活动视图），写 `graceful.json`，再继续既有 drain 流程。两条优雅通道（Ctrl+C / HTTP shutdown）天然汇聚到同一关闭状态机（context §3）；**SIGTERM handler 本域顺带补齐**（桌面壳关闭/系统关机发给服务的常是 SIGTERM，现状缺失——补齐它不是新机制，是让「优雅」覆盖真实退出路径）。

- 在跑清单的快照口径：以「有未收尾回合且不处于等待用户决策」的会话为准（与 §1.3 反推口径一致，D-M6）。
- 极端时序（drain 中回合恰好收尾）：以 `graceful.json` 记录时刻为准；退出记录里在跑、实际已收尾的会话，下次启动由 §2.1 的收口写盘自然修正（读到 `turn.ended` 已在，跳过回填）。

## 7. ADR 记录

- **ADR-001（2026-10-28）**：生命周期哨兵采用「启动标记 + 优雅退出记录」双文件，实例按端口+启动时刻隔离目录；启动检查对非自身实例先过**存活门**（评审修订：launch.json 携带 port/pid，探测存活，存活实例不判定不删除）。背景：退出方式判定需要跨进程死亡存活的证据；既有桌面壳的 pid 状态文件不覆盖 serve 形态且非引擎侧。决策：`lifecycle/<instance-id>/{launch.json, graceful.json}`，原子写，启动检查后消费删除（目录 rename 原子占位防双实例竞态）。被否决备选：a) 单文件脏位（否——异常退出后无法携带在跑清单，优雅路径的信息浪费）；b) 周期性心跳快照（否——D-M1 裁决，持续写盘与两个事件的骨架冗余）；c) 写进 SQLite 索引库（否——生命周期证据应在引擎侧独立小文件，不与读模型耦合）；d) 无存活门（否——跨端口存活实例会被误判异常，违反 A.5/V10）。影响范围：§1.1/§1.2、需求 A.1/A.2/A.5、V10。
- **ADR-002（2026-10-28）**：中断识别产物回写 wire 日志（`interrupted` 收口记录），而非仅进程内视图。背景：徽标跨重启（B.2）若靠纯内存态则下次重启又要重判；而 wire 日志本就是回合事实的既有归宿。决策：识别完成即为未收尾回合补写 `turn.ended {reason: interrupted}` 收口（turnId 按 §2.1 推导）；徽标数据源 = 持久收口 OR 进程内清单的合并（§2.2）。被否决备选：a) 纯进程内恢复清单（否——重启即丢，每代重启重复判定且 72h 保留期无法跨重启维持）；b) state.json 加中断字段（否——回合结局的事实源在 wire 日志，两处写会漂移）。影响范围：§2.1/§2.2、需求 B.2/E.2、V8。
- **ADR-003（2026-10-28）**：续跑 = 带语境的 `turn.prompt`，不新增 wire op / 不新增准入类别。背景：回合调度域有「单一插座」纪律（N4 准入封闭）；续跑本质是一次用户消息类的新回合请求。决策：`recovery.resume` 在服务端构造特殊来源语境的 turn.prompt（含 cause、时间、继续指令、后台任务提示），复用全部既有排队与单活动回合规则。被否决备选：a) 新 `turn.resume` op（否——调度侧要开新准入路径，违反 N4；且历史重放要教新词表）；b) 由 web 直接发用户消息文本（否——语境拼装散落前端，措辞漂移不可控）。影响范围：§3.1、需求 E.1/E.3、V8/V9。
- **ADR-004（2026-10-28）**：通知用拉取模型（recovery.list），不建全局推送通道。背景：现无服务器级广播通道；冷启动的「会话列表就绪」已是 web 既有锚点。决策：web 在列表装载后拉取一次，非空渲染通知卡片；运行期徽标数据走既有列表刷新；跨重启重现（C.8）由每次前端启动的拉取天然满足。被否决备选：新建全局 WS 广播（否——为一次性通知引入常驻通道，成本错配）。影响范围：§3/§4、需求 C.1/C.8、V17。
- **ADR-005（2026-10-28）**：补齐 SIGTERM 优雅关闭信号处理。背景：优雅退出记录的前提是「收到关闭信号」；现状仅 Ctrl+C 与 HTTP shutdown，而桌面壳/系统发给服务的常是 SIGTERM。决策：在服务关闭状态机前挂 SIGTERM handler（与 ctrl_c 同汇入 request_shutdown）。被否决备选：只靠桌面壳主动调 HTTP shutdown（否——系统关机/容器停止直接 SIGTERM，届时记录缺失会把优雅退出误判为异常，误报比漏报伤信任）。影响范围：§5、需求 A.2、V1。
- **ADR-006（2026-10-28）**：保留期到期用惰性判定，不设定时器。背景：72 小时粒度的消散不需要精确定时；后台定时器是常驻成本。决策：`recovery.list()` 与列表读面在读取时按时间边界过滤过期项（读时推导，不落盘清除）。被否决备选：后台过期扫描线程（否——F.3 低开销裁决，收益为零）。影响范围：§3、需求 B.3、V5。
- **ADR-007（2026-10-28）**：合成收口的 turnId 由记录序列推导，重放按乱序容错。背景：wire 契约的 `turn.ended` 必须携带回合号，但 `turn.prompt` 载荷不含回合号，既有只读探测只返回时间戳。决策：从该未收尾 `turn.prompt` 之后的记录序列推最大回合号（下界 +1 兜底）；重放遇到先于其 turn.prompt 的 turn.ended 时跳过（合成收口只作呈现定局）。被否决备选：改 wire 契约让 turn.prompt 携带回合号（否——触碰既有词表，波及面与收益不成比例）。影响范围：§2.1、需求 E.2。
- **ADR-008（2026-10-28）**：中断状态的「已处理 / 过期」读时推导，不改写追加型日志。背景：wire 日志是追加型事实日志，收口记录写入后不可改写删除；dismiss/续跑/72h 到期都要求状态流转。决策：读面推导——`interrupted` 收口之后存在更新的 `turn.prompt` 即已处理；过期 = 收口时间戳与 72h 边界比较；dismiss 只改进程内推荐身份（徽标与通知读面），不动日志。双实例竞态由回填前「读-判-写」重查 + lifecycle 目录 rename 占位兜底（§1.2）。被否决备选：a) 旁挂状态文件记录处理进度（否——第二事实源，与日志漂移面扩大）；b) 压缩/归档时物理清除收口（否——修改既有压缩语义，越域）。影响范围：§2.1/§2.2/§3/§3.1/§3.2、需求 B.3/C.6/E.5/E.6、V5/V15。

## 8. 实施批裁决补录（ADR-009，2026-10-28）

- **ADR-009（2026-10-28）**：实施探查后对 ADR-007 的 turnId 推导与 §2.1 拦截点做三处收敛。背景：落地前的代码级核查发现三处 spec 假设与机制事实不符：a) 悬空回合内部不存在任何携带 turnId 的记录（`turn.prompt`/`turn.steer` 及回合内事件均不带回合号），「从 turn.prompt 之后的记录序列推最大回合号」不可实现；b) 既有回合号工具的兜底口径正是「prompt 序数」（对无 ended 的 prompt 计数）；c) `foreign_stop_reason_wire` 对未识别 reason 一律退化为 `completed`，构成 §2.1 拦截点清单之外的第四个漏点。决策：① 合成收口的 turnId 取该悬空 `turn.prompt` 的**序数**（该 prompt 是该会话日志中第几个 prompt，从 1 起），与既有回合号分配器的 replay 地板口径对齐；② 拦截点清单补第四处：增量吸收路径的 foreign journal 折叠在 `interrupted` 值上须原样透传，不得退化为 `completed`；③ 后台任务提示（E.3）的推导口径为「悬空回合约内存在 `task.started` 且无对应 `task.terminated` 的记录」——弱于「正在等待」但可从磁盘事实可靠推出。被否决备选：为 turnId 推导扩展 wire 词表（否——波及面大；探查确认序数口径已有先例）。影响范围：§2.1（turnId 推导改序数口径、拦截点补第四处）、§1.3/§3.1 步骤 2（后台提示推导口径）。

- **ADR-010（2026-10-28）**：web 侧徽标数据源为「recovery 清单优先、事件值兜底」的读面合并。背景：批次 1 落地后发现 web 的事件归约器对 `sessionWorkChanged` 采取「缺省 lastTurnReason 即权威清除」语义（合法既有行为），引擎覆写值经事件通道会被擦掉；同时 `session.list` 行的 `interrupted`（批次 1 覆写点）只在该行刷新时到达。决策：web 的 `SessionWorkFacts.lastTurnReason` 在计算时先查恢复清单（未结算未过期 → `interrupted`），事件/列表携带值为兜底；resume/dismiss 动作成功后对恢复清单引用做乐观移除（不依赖下一次事件）。被否决备选：改事件归约器的清除语义（否——那是既有权威语义，为一个值反转全局行为，回归面大）。影响范围：§4 web 呈现层（批次 2）。
