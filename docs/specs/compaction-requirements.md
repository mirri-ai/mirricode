# 上下文压缩 — 需求文档

> 状态：v1 基线 · 2026-09-09 · 含 SDR-001~012（001~005 已裁决；006~012 为 2026-09-11 审计偏差登记，待用户裁决；见文末决策记录）· 待用户评审 ·
> 本文是上下文压缩域需求侧的唯一事实源（内部规格文档，不进文档站构建，中文单语）。
> 基线说明：本文以 TS 引擎已落地能力为 Rust 对齐基线记录，同时按既定方向纳入超出 TS 现状的增强设计（保留尾、修剪优先、必须变小守护等），增强处均显式标注；基线是 Rust 要达到的底线，不是 Rust 的上限。
> 产品愿景：**长对话不失忆、不爆窗、不烧冤枉钱**——桌面快满才动手、能免费解决就不动刀、动了刀最新的对话原样还在、失败永远可退回原状。
> 配套文档：技术形状与机制见 [compaction-architecture.md](compaction-architecture.md)；现状盘点见 [compaction-context.md](compaction-context.md)；执行状态见 [compaction-ROADMAP.md](compaction-ROADMAP.md)。
> 术语规范：压缩（C1）、保留尾（C2）、压缩摘要（C3）、投影修剪（C4）的唯一定义见 [glossary.md](glossary.md)。
> 范围边界：本域覆盖**模型可见历史的压缩与恢复**——触发、保留策略、摘要生成、失败恢复、压缩记录与视图投影、配置与观测，适用于会话内**全部身份记录流**（主代理、子代理、顺带问分支各自独立触发与落位）。对话记录的存储布局、wire 日志格式与版本链、会话恢复的整体流程属会话持久化域（[session-persistence-requirements.md](session-persistence-requirements.md)）；压缩相关的呈现验收（转录分隔条、压缩面板）见本域 US5.3/US7.1，转录呈现的框架性交互（滚动、加载等）不在本域；token 估算的精度本身不另立域，作为本域非功能属性记录。

## 0. 角色定义

| 角色 | 场景 | 核心诉求 |
|---|---|---|
| **长任务用户**（跑几小时调查/重构的人） | 对话越滚越长，模型开始"忘事" | 压缩后最新的对话原样还在；旧事有可信的摘要可依 |
| **成本敏感用户**（盯着账单的人） | 每轮重发全部历史，越聊越贵 | 不到真满不折腾；摘要调用能享缓存折扣；做了就必须真省空间 |
| **边界情况用户**（赶上压缩出错的人） | 压缩中途失败/崩溃/服务商报超限 | 失败永远退回原状；重启不留半套状态；报错说人话 |

## 1. Epic E1：触发与时机（P0）

> 解决"什么时候压、压的时候挡不挡路"。原则：不到真满不动手，动手时用户无感或有明确提示。

### US1.1 自动压力触发（P0）

作为长任务用户，我想在上下文接近模型上限时自动压缩，以便不用盯着用量也能一直聊下去。

验收：
- Given 上下文占用达到模型窗口的触发阈值（默认 85%，可配 0.5–0.99），When 系统在任一次模型请求前的检查点判定，Then 自动开始压缩（该次请求停等压缩完成后才发出）
- Given 占用未达阈值但"当前占用 + 预留空间（默认 50,000 token，可配）"将超过窗口，When 准备下一步请求，Then 同样触发压缩（预留口径保证给模型回复留出空间）
- Given 上下文占用的真实计量包含缓存命中的部分（缓存只省钱不省桌面），When 判定阈值，Then 按真实占用量计算，不因命中缓存而少算
- Given 模型窗口大小未知（未配置也未被观测过），When 准备下一步请求，Then 不按阈值触发（只在服务商明确报超限时走溢出恢复），且不误报

### US1.2 同步阻塞语义（P0）

作为长任务用户，我想让触发时正在准备的那一步请求等压缩完成后再发出，以便不把注定超限的请求发出去白花钱。

验收：
- Given 自动压缩在模型请求之间的检查点触发，When 压缩进行中，Then 当前这一步请求停等，压缩完成（或失败退回）后才发出
- Given 压缩阻塞中用户取消（中止当前回合），Then 压缩随之取消，不留半套状态
- Given 手动压缩在会话空闲时触发，When 压缩运行期间用户发来新消息，Then 消息被接受并排队，压缩结束后自动开始下一轮（不硬闯、不丢输入）

### US1.3 溢出恢复（P0）

作为边界情况用户，我想让服务商报"超出上下文窗口"时系统自动压缩并重试，以便长对话不必手动收拾。

验收：
- Given 服务商明确报上下文超限，When 系统收到该错误，Then 先闭合失败的那一步账目，再触发压缩，然后自动重试（新开一步，不是原地重发）
- Given 溢出发生，When 系统观测到真实窗口比标称的小，Then 记住观测值并在后续触发判定中采用更小的有效窗口
- Given 压缩后重试仍超限，When 连续溢出恢复超过上限（默认 3 次），Then 停止重试并给出明确错误（说明压缩未能把上下文压回窗口内），不无限循环
- Given 用户把溢出恢复重试上限配为 0（新增配置键，见架构 §8），When 服务商报超限，Then 只关闭"超限后自动恢复"，其他自动压缩行为不受影响

### US1.4 手动触发（P0）

作为长任务用户，我想随时主动压缩并附上我的重点提示，以便在我觉得合适的时间点整理上下文。

验收：
- Given 会话空闲，When 我执行压缩命令（可附一段自定义说明），Then 无论占用是否达阈值都开始压缩，且我的说明会并入摘要指令（引导摘要侧重）
- Given 一个回合正在执行中，When 我执行压缩命令，Then 被拒绝并提示"等当前回合结束后再试"，不排队、不打断
- Given 压缩已在进行，When 我再次执行压缩命令，Then 被拒绝并提示忙
- Given 压缩完成，When 我查看结果，Then 我能看到压缩前后的用量对比

### US1.5 单飞互斥（P0）

验收：
- Given 任意来源（自动/溢出/手动）的压缩正在进行，When 任何来源再次触发，Then 一律被拒绝，同一时刻最多只有一个压缩在跑

### US1.6 压缩期间输入不丢（P0）

验收：
- Given 自动压缩运行中用户发来新消息，When 压缩结束，Then 新消息按原顺序进入下一轮
- Given 手动压缩运行中用户发来新消息，When 压缩结束，Then 新消息自动开始下一轮
- Given 压缩运行中用户执行其他命令，When 命令与压缩冲突，Then 得到明确提示（如"压缩结束后再执行"），不静默吞掉

### US1.7 无新内容不重复压缩（P1）

验收：
- Given 压缩刚完成且之后没有产生新内容，When 再次到达触发判定点，Then 跳过压缩（不摘要套摘要）

### US1.8 修剪优先，免费手段先上（P1，超出 TS 现状的增强）

作为成本敏感用户，我想让系统先用不花钱的手段腾空间，以便能不调摘要就不调。

> 与常驻的"单条工具输出预算"划界：工具输出在**追加时**就有单条上限（超长输出当场替换为预览 + 取回指引，与空间压力无关，是常驻防线）；本条的投影修剪是**压缩流程内**的第二层手段，两者独立生效、互不替代。

验收：
- Given 自动压缩条件成立，When 判定流程启动，Then 先把"较早的、超长的工具输出"在模型视图中替换为占位说明（原文仍在日志里，需要时可取回），然后重新称重
- Given 修剪后占用已降到阈值以下，When 重新称重，Then 跳过摘要调用，压缩到此为止
- Given 历史不缺空间，When 正常运行，Then 压缩流程自身不引入任何新的修剪（投影修剪只在压缩条件已成立时才发生；常驻的单条输出预算不在此列）

## 2. Epic E2：压缩范围与保留尾（P0，SDR-001 核心变更）

> 解决"压哪段、留什么"。原则：**只压缩旧历史，最近的完整对话原样保留**——模型对最近发生了什么保持逐字记忆，不因压缩而丢失最新交互。

### US2.1 完整最近对话保留（P0，增强——TS 现状只保留用户消息）

作为长任务用户，我想让压缩后最近的完整对话（我的消息、模型回复、工具调用与结果）原样保留，以便模型对刚发生的事有逐字记忆，而不是只剩一段转述。

验收：
- Given 压缩发生，When 落位完成，Then 保留尾（最近一段完整对话，含用户消息、助手回复、工具调用与结果）逐字节原样进入后续每一次请求
- Given 保留尾内的一次工具调用与它的结果，When 压缩落位，Then 二者成对完整保留，永不拆散
- Given 保留尾中的一条用户消息带附件，When 压缩落位，Then 附件原样保留（预算内的保留尾不做任何截断）

### US2.2 只压缩旧历史（P0，增强）

验收：
- Given 压缩发生，When 摘要生成，Then 摘要只覆盖保留尾之前的旧历史；保留尾不进摘要输入、不参与摘要（它不是手术对象）
- Given 压缩完成，When 组装下一次请求，Then 依次为：规则说明、工具清单、摘要（替换旧段原位）、保留尾、新内容

### US2.3 保留预算与切线规则（P0，增强）

验收：
- Given 压缩发生，When 计算保留尾，Then 按预算从最新内容往回收，预算口径为"当前模型窗口容量 × 保留比例（默认 16%）"，也可配置为绝对 token 值（两种方式互斥）
- Given 保留预算配置值不低于触发阈值对应量，When 加载配置，Then 拒绝启动并给出可读错误（保留的不能比要压的还多）
- Given 初始切线落在"工具调用 + 结果"这类不可拆分配对中间，When 修正切线，Then 只向更老方向退，直到合法边界（预算是"最少保留"，保留尾只会变大不会变小）
- Given 从头数到底预算仍未凑够（整段历史都在保留预算内），When 判定，Then 什么都不压
- Given 退到最老也找不到合法边界，When 判定，Then 放弃压缩，什么也不写

### US2.4 必须变小守护（P0，增强）

作为成本敏感用户，我想让"压完反而更大"的压缩被拒绝，以便不做亏本买卖。

验收：
- Given 摘要生成完毕，When 落位前校验，若"摘要 + 保留尾"不比压缩前的完整历史严格更省，Then 整次压缩作废、上下文保持原状、不落任何压缩生效记录
- Given 守护拒绝发生，When 用户或系统查看，Then 该次尝试作为失败记录在案（可观测），不是静默吞掉

### US2.5 最旧任务声明的保真（P1，现状保留不回退）

验收：
- Given 最初的用户请求已不在保留尾内，When 压缩落位，Then 最初请求的精华（最旧用户输入的头部预算，默认 2,000 token）仍以原文形式保留（摘要可能转述失真，原文保底）
- Given 头部保留与保留尾之间存在被省略的中间用户输入，When 落位，Then 插入一段明确的省略说明（大致规模 + 指引到摘要），模型不误以为中间没有内容

### US2.6 找不到安全切割点（P1，SDR-003 补充）

验收：
- Given 整段历史是不可分割的单个超大单元（如一次超大的工具调用），When 修剪后仍无安全切点，Then 压缩直接放弃且不写任何记录，系统继续以原状运行（宁可暂时超预算，不产出残缺序列）
- Given 手动发起压缩而会话没有可压缩的内容（整段历史都在保留预算内、或历史为空、或为不可分割的单个单元），When 请求处理，Then 以"未开始"的提示性结果返回（info 级提示，非错误），客户端据此展示"当前会话没有需要压缩的内容"一类的提示
- Given 压缩因无可压内容被跳过，When 查看会话，Then 会话状态与历史不受任何影响、不落任何压缩生效记录，后续再次手动压缩仍按新状态正常判定

### US2.7 压缩后的重注入（P1）

作为长任务用户，我想让压缩后仍知道"我正在做什么"——生效的目标、可加载的工具清单、活跃的后台任务提醒不因压缩而丢失。

验收：
- Given 压缩成功落位，When 组装下一次请求，Then 生效目标、可加载工具清单、活跃后台任务提醒等会话级注入物被重新注入（从各自的唯一事实源取当前值，不依赖压缩前留在历史里的旧注入）
- Given 重注入的内容，When 与保留尾并置，Then 不与保留尾内的同类信息冲突（重注入位置与保留尾的相对顺序有确定规则，见架构 §6）

## 3. Epic E3：摘要生成（P0）

### US3.1 摘要输入构成（P1，增强——现状为全部历史）

验收：
- Given 摘要调用发起，When 组装输入，Then 依次为：规则说明（与上一轮真实请求逐字相同）、工具清单（与上一轮真实请求逐字相同）、待压缩的旧段（仅此一段）、一条固定措辞的总结指令
- Given 保留尾，When 组装摘要输入，Then 保留尾不在输入里（少递少付钱，且开头部天然命中缓存折扣）
- Given 动态工具的协议公告类消息，When 组装摘要输入，Then 被排除（防工具协议文本被抄进摘要）

### US3.2 摘要指令风格（P0，SDR-002）

验收：
- Given 摘要调用发起，When 使用固定指令，Then 指令要求模型以第一人称写"交接笔记"——最新请求的真实意图、在生效的约束、已做工作（精确的命令/路径/结果）、未知项、前向计划
- Given 保留尾存在，When 指令表述，Then 明确告知"最近的对话已原样保留、无需转述"，指令只要求覆盖旧段
- Given 用户在手动压缩时附了自定义说明，When 渲染指令，Then 说明作为可选项并入固定指令

### US3.3 摘要附带任务清单（P1）

验收：
- Given 压缩完成时存在进行中的任务清单，When 生成摘要消息，Then 清单的当前状态自动附在摘要之后（从唯一事实源取，不要求模型转述）

### US3.4 失败重试阶梯（P0）

验收：
- Given 摘要请求因含媒体被拒（请求体过大或媒体格式被服务商拒绝），When 重试，Then 先把输入中的媒体替换为文字占位重试一次（真实历史不受影响）
- Given 摘要请求本身溢出，When 重试，Then 按递减预算从尾部收缩保留（默认 0.7 → 0.5 → 0.35），最多 3 次
- Given 摘要响应被截断或为空，When 重试，Then 逐次丢最旧一条消息重试，最多 5 次
- Given 其他可重试错误，When 重试，Then 指数退避，总预算 5 次
- Given 每一次收缩/裁剪，When 记录，Then 被裁掉的消息数如实上报（压缩记录与用量统计中可见，不静默消失）
- Given 重试耗尽仍失败，When 收尾，Then 保留压缩前的完整对话继续运行（宁可暂时超预算），并向用户呈现明确的失败提示

### US3.5 防泄漏与输出通道（P1）

验收：
- Given 摘要模型的原始返回可能含推理过程或工具调用，When 提取摘要，Then 只有纯文本进入压缩摘要；其余通道一律剥掉（原始全文只存在日志里备查）

### US3.6 压缩前后钩子（P2）

验收：
- Given 外部钩子配置了压缩前钩子，When 压缩开始，Then 钩子被触发且可注入附加上下文（并入摘要输入）
- Given 压缩完成或取消，When 收尾，Then 压缩后钩子收到通知

## 4. Epic E4：失败与恢复（P0）

### US4.1 失败保原状（P0）

验收：
- Given 摘要失败/截断/超时，When 收尾，Then 上下文保持压缩前的完整状态继续运行（若修剪已生效则从修剪后状态继续），记录一条警告，不留半套状态
- Given 鉴权类错误（需登录/密钥失效），When 收尾，Then 原样上抛给用户处理，不被包装成模糊的"压缩失败"

### US4.2 摘要期间对话变化（P0）

验收：
- Given 摘要生成期间对话前缀被改变（如撤销），When 摘要返回，Then 本次压缩取消（宁可不压，不压错）
- Given 摘要生成期间仅追加了真实用户输入或钩子附加上下文，When 摘要返回，Then 压缩继续（追加内容会被重新纳入保留范围，不丢）
- Given 摘要生成期间追加了其他内容（助手消息、工具结果、后台通知），When 摘要返回，Then 本次压缩取消（这些内容既不在摘要里也没被保留，不能带着丢失风险落位）

### US4.3 崩溃恢复（P0）

验收：
- Given 压缩进行中进程崩溃，When 重启恢复会话，Then 未闭合的压缩被识别并归位为"无压缩进行"（孤儿标记不算数），会话照常可用
- Given 恢复后的模型视图，When 与崩溃前 live 视图对照，Then 压缩后状态逐条一致（保留的内容不因恢复而丢失）

### US4.4 撤销与压缩边界（P1）

验收：
- Given 用户撤销对话回退，When 回退路径上遇到压缩摘要，Then 撤销在压缩边界停止（不穿越压缩"考古"）

## 5. Epic E5：记录与视图（P0）

> 原则：**日志是唯一真相，模型视图只是投影**。原始记录物理永不删除。

### US5.1 日志唯一真相（P0）

验收：
- Given 任意次压缩，When 写入记录，Then 只追加、不修改、不删除任何已有记录；被压缩的原文完整留在日志里
- Given 一次完整压缩，When 查看记录，Then 包含：开始（含触发来源与自定义说明）、摘要全文与替换范围、落位结果（含保留/省略/裁剪的计量）、结束——四个环节全部在案，崩溃可判读

### US5.2 模型视图是投影（P0）

验收：
- Given 会话日志，When 重放计算模型可见内容，Then 结果是纯函数（同一日志永远算出同一视图），不存在需要另行同步的第二份状态

### US5.3 人类视图全量（P0）

作为长任务用户，我想让压缩不清空我在界面上看到的对话，以便随时往回翻原始内容。

验收：
- Given 压缩完成，When 我查看会话转录，Then 压缩前的全部对话仍然完整可见；压缩以一条整理记录（分隔条）的形式插入
- Given 压缩分隔条，When 我在终端查看，Then 可展开查看摘要全文、压缩前后用量与我的自定义说明；When 我在网页查看，Then 分隔条标注触发来源（自动/手动）与前后用量，并可打开详情面板查看摘要全文
- Given 压缩后的会话经快照恢复，When 我查看转录，Then 分隔条仍然可见并展示摘要全文（计量等元数据不保证完整）

### US5.4 恢复保真（P0）

验收：
- Given 压缩后的会话被重启/恢复，When 模型视图重建，Then 与压缩刚落位时的 live 视图逐条一致——保留的内容、省略说明、摘要位置全部还原，不因恢复而降级

### US5.5 压缩可取消（P1）

验收：
- Given 压缩进行中，When 用户取消，Then 压缩终止、上下文保持原状、记录中留下取消标记

### US5.6 复制会话（fork）保真（P1）

验收：
- Given 一个发生过压缩的会话被复制（fork），When 新会话重放，Then 其模型视图与源会话压缩后的视图逐条一致（压缩记录随对话记录一同复制，复制边界记录不干扰压缩折叠）
- Given 复制出的会话，When 我查看其转录，Then 源会话的压缩分隔条与摘要同样可见

## 6. Epic E6：配置（P1）

### US6.1 触发阈值与预留空间（P1）

验收：
- Given 我在配置中设置触发阈值（0.5–0.99）与预留空间，When 会话运行，Then 压缩按我的值触发
- Given 我未做任何配置，When 会话运行，Then 使用默认（阈值 85%、预留 50,000 token）

### US6.2 保留尾预算（P1，增强）

验收：
- Given 我配置保留比例（默认 0.16）或保留绝对值（二选一），When 压缩发生，Then 保留尾按我的预算划线
- Given 两种保留配置同时设置，When 加载配置，Then 拒绝启动并指出冲突
- Given 不同模型，When 各自运行，Then 按各自窗口容量计算保留尾（比例制天然随窗口缩放）

### US6.3 配置必须真实接线（P1）

验收：
- Given 一个压缩相关配置键被文档声明，When 用户设置它，Then 它必须驱动引擎行为；不允许"声明了但不生效"的键出现在交付面

## 7. Epic E7：呈现与观测（P1）

### US7.1 过程可见（P1）

验收：
- Given 压缩开始/阻塞/完成/取消，When 任一界面（终端/网页）在用，Then 对应状态可见（终端压缩面板可取消；网页活动流出现压缩条目）
- Given 压缩阻塞了一个回合，When 用户查看，Then 能看出"正在压缩所以这一步慢"

### US7.2 用量观测（P1）

验收：
- Given 压缩完成，When 查看遥测，Then 可见：压缩前后 token、耗时、被压缩条数、被裁剪条数、重试次数、触发来源
- Given 压缩失败，When 查看遥测，Then 可见失败类型与发生阶段

## 8. 非功能需求（NFR）

| # | 需求 | 说明 |
|---|---|---|
| NFR1 | **头部结构性豁免** | 规则说明与工具清单是每个请求都重复的大块头，压缩永不触碰它们——失效范围被硬性限定在历史段内 |
| NFR2 | **计量口径为真实占用** | 缓存命中的内容照样占桌面，判定阈值按含缓存的总量计 |
| NFR3 | **折扣友好** | 摘要调用沿原对话"续读"（开头部与上轮请求逐字相同），绝大部分输入按缓存折扣计费；压缩后的失效范围从历史起点缩小到摘要位置 |
| NFR4 | **估算口径已知偏差** | token 计量为启发式（ASCII 约 4 字符折 1 token、非 ASCII 1 字符折 1），对中文与结构化数据偏低——偏差作为已知约束记录，不掩盖 |
| NFR5 | **内存上限防失控** | 会话历史在内存中维护条数/延迟上限，超限拒绝而非无界增长 |
| NFR6 | **检查点语义** | 压缩的判定与执行只发生在模型请求之间的检查点；正在执行的回合遇到压缩只停等下一步请求，绝不中止回合（回合 = 一次用户消息到该轮交互结束；一步 = 一次模型请求） |

## 9. 未来增强提案（超出三引擎现状，未立项实现）

> 以下为显式提案，不声明任何当前能力。

- **P-E1 可回溯压缩**：当前"摘要替换旧段"的方案存在累积缺陷——第二轮压缩会把第一轮的摘要也重写，折扣每次从历史起点全部丢失，且旧摘要逐层"摘要的摘要"细节流失。提案方向：把摘要拆成"每段旧历史一张、永不重写、永远享受折扣的目录卡片" + "一张每次整理只重写现状的可变卡片"；同时给模型配"读历史"（分页读回被压缩原文）与"搜历史"（在被压缩原文中字面搜索）两个翻旧账工具，读回内容作为普通工具结果落在请求末尾、不碰前缀。原始字节本来就在日志里，不需要新存储。**已立项（提案，2026-09-10，SDR-005）**——需求内容迁移至新域，见 [history-readback-ROADMAP.md](history-readback-ROADMAP.md)（术语 H1–H4 见 [glossary.md](glossary.md)）。
- **P-E2 多段摘要并发**：一次整理的多段摘要可共享开头、各算各的、结尾统一落地；以及"边积累边起草"的后台式压缩。

## 10. 决策记录（SDR）

### SDR-001：压缩范围采用"保留尾"设计——只压缩旧历史，最近完整对话原样保留

- **编号与日期**：SDR-001 · 2026-09-09
- **背景与动机**：现有实现的压缩是"整段历史折叠"——除按 token 预算保留的部分**用户消息**外，全部助手回复、工具调用与结果被折叠进摘要，原文不再进入后续请求（三引擎现状证据见 context §1.2/§2）。后果：压缩刚发生时，模型对自己最近一轮的回答与工具输出**失去逐字记忆**，只剩自己写的转述；转述质量无硬保证，最新交互内容的保真完全寄望于摘要自觉。长任务场景下这是高频痛点（用户在最近几轮刚建立的工作状态被抹平）。
- **决策**：压缩范围改为保留尾设计——按预算（窗口比例默认 16% 或绝对值，互斥可配）从最新往回收**完整对话**（用户消息、助手回复、工具调用与结果成对），原样保留；摘要只替换保留尾之前的旧段。切线遵守配对完整性且只向更老方向退（预算是最少保留）。现有"用户消息独立 20k 预算"机制由保留尾吸收取代，但"最旧用户输入头部 2k 精华保留"保留（US2.5，防原始任务声明只剩转述）。
- **被否决的备选**：
  1. *维持现状（仅保留用户消息）*——改动最小，但不解决核心痛点：最新交互（助手回复、工具结果）仍全部丢失逐字保真。
  2. *按条数保留最近 N 条消息*——一"条"可能是一句话也可能是几万字工具输出，大小不可控；token 预算直接对应下一请求占用量，与称重同尺。
  3. *保留尾设计搭配固定八栏结构化摘要模板*——保留尾、切线规则、免费修剪、变小守护采纳；摘要指令风格另行裁决（见 SDR-002）。
- **影响范围**：US2.1–2.3、US2.5、US3.1、US3.2、NFR3；架构侧触发与落位形态整体重构（见架构 ADR-001）。
- **裁决人**：用户（2026-09-09 会话中明示方向："保留最近的一部分会话，而只压缩旧的"）。

### SDR-002：摘要指令保留"第一人称交接笔记"风格

- **编号与日期**：SDR-002 · 2026-09-09
- **背景与动机**：摘要指令存在两种流派——第一人称交接笔记（模型以"继续自己的思路"的口吻写给未来的自己，形状自然），与固定八栏结构化模板（事实形状、防泄漏能力强，但机械）。保留尾落地后，摘要只需覆盖旧段，"最近对话已消失、必须自我转述"的前提不复存在，两种风格的差距缩小。
- **决策**：保留第一人称交接笔记风格，但指令表述随 SDR-001 改写——明确"最近对话已原样保留、无需转述"，笔记只覆盖旧段；大输入的截断风险提示保留。
- **被否决的备选**：固定八栏结构化模板（主要请求/概念/文件/错误/待办/当前/下一步/背景）——结构化利于审计，但与第一人称笔记的"思维连续性"优势冲突；可在落地后按摘要质量遥测再评估。
- **影响范围**：US3.2；摘要指令模板与摘要前缀文案同步改写。

### SDR-003：手动压缩"无可压内容"时以提示性跳过返回，不上报错误

- **编号与日期**：SDR-003 · 2026-09-10
- **背景与动机**：保留尾设计（SDR-001）引入了"无可压内容"的判定（整段历史都在保留预算内、历史为空、或无可分割的合法切点）——该判定落地后真实可达，而 US2.6 原文只定义了"放弃压缩、继续原状"，未定义**手动压缩入口**在调用层的表现。Rust 初版实现让该情形以错误冒泡，用户在界面上看到"操作失败"级提示——对"会话本来就不需要压缩"这一正常状态，错误语义过重。
- **决策**：手动压缩无可压内容时跳过并返回"未开始"的提示性结果（info 级），不作为错误上报；自动路径维持静默跳过。引擎以"未开始"布尔结果为信号，由客户端渲染"当前会话没有需要压缩的内容"类提示文案。
- **被否决的备选**：① 维持错误冒泡——错误语义过重，把正常状态伪装成故障；② 返回成功但无任何信号——用户无法区分"开始了"与"跳过了"，压缩面板空等。
- **影响范围**：US2.6（新增两条验收）；Rust 手动压缩 RPC 的"无可压内容"分支（错误类型与返回值）；TS 侧对齐随 M3（TS 现状无保留尾、手动压缩总能执行，不触发该条件）。
- **裁决人**：用户（2026-09-10："可以出 info 级别的提示信息，跳过吧"）。

### SDR-004：M4 摘要盲区治理采用「出处链 + 显式标注」

- **编号与日期**：SDR-004 · 2026-09-10
- **背景与动机**：重试阶梯（L2 溢出收缩/L3 截断空丢最旧）丢弃的内容对模型彻底丢失，droppedCount 仅在记录里可见；盲区不可见、不可引用。
- **决策**：M4 摘要盲区治理采用「出处链 + 显式标注」——`apply` 记录携带被替换条目编号清单，摘要内可引用编号；被丢弃段在记录中显式标注"不可覆盖"边界。完整分析见 compaction-context.md §5。
- **被否决的备选**：丢弃内容纳入保留尾（保真彻底但保留尾膨胀、压缩触发更频繁、与省窗口目标冲突）；推迟到 P-E1（近期盲区无改善且 P-E1 立项时间未定）。
- **影响范围**：`apply` 记录可选字段扩展（出处链编号清单，按"可选追加不递增版本"纪律，持久化域 ADR-008）；摘要指令的编号引用表述；M4 实现另立计划。
- **裁决人**：用户（2026-09-10）。

### SDR-005：P-E1 可回溯压缩立项归属——需求迁移至 history-readback 域

- **编号与日期**：SDR-005 · 2026-09-10
- **背景与动机**：§9 P-E1 提案（可回溯压缩：目录卡片 + 现状卡 + 读历史/搜历史工具）自 v1 基线起以"未立项"状态挂账；ADR-007 编号地基落地后，2026-09-10 终审将其立项，需求/架构/context 四件套建于新域 history-readback（glossary 术语 H1–H4），本域 §9 条目的"未立项"表述与实际状态脱节。
- **决策**：P-E1 立项归属 history-readback 域；§9 P-E1 条目更新为已立项指针（[history-readback-ROADMAP.md](history-readback-ROADMAP.md)）。本决策仅记录立项归属与文档指针更新，**非本域需求内容变更**——US/NFR 基线不动；压缩域对 P-E1 的关联条款（头部精华过渡设计重审、盲区治理方案 A 的"读回工具归 P-E1"）经本域 ROADMAP 开放项 2/6 指向新域，新域开放项 1 承接重审义务（已互指）。
- **被否决的备选**：① 留在本域立项——读回/检索工具面与压缩机制的边界清晰、独立演进更稳，且本域批次状态表以压缩里程碑为主干，混入跨域工具面稀释管理粒度；② 维持"未立项"挂账——编号地基已落地，翻旧账工具的承接方悬空会阻塞盲区治理复评与头部精华重审义务的落实。
- **影响范围**：§9 P-E1 条目（状态指针）；本域 ROADMAP 开放项 2/6（既有指向，无文本变更）；无 US/NFR 条目变更。
- **裁决人**：用户（2026-09-10 终审立项裁决；本 SDR 由收口批次记录指针更新）。

### SDR-006：摘要调用输入缺「规则说明 + 工具清单」前缀——NFR3 折扣声明无实现支撑（待裁决）

- **编号与日期**：SDR-006 · 2026-09-11
- **背景与动机**：US3.1 第一条验收与架构 §5.1 规定摘要调用的输入构成为「规则说明（与上一轮真实请求逐字相同）+ 工具清单（与上一轮真实请求逐字相同）+ 待压缩旧段 + 固定指令」，NFR3（折扣友好）以此为前提声明「摘要调用沿原对话续读（开头部与上轮请求逐字相同），绝大部分输入按缓存折扣计费」。2026-09-11 测试修复批审计发现：引擎现状的摘要 LLM 调用只组装「投影后的旧段 + 指令」，既不携带规则说明前缀，工具清单也显式置空（`rust/crates/mirri-core/src/compaction/round.rs:315-334`，`tools: Vec::new()`）。摘要请求与上一轮真实请求**没有逐字共享的前缀**——NFR3 的折扣声明目前无实现支撑，摘要调用的输入按无缓存折扣的全价支付。
- **选项与权衡**：
  1. *改需求措辞*——NFR3 与 US3.1 第一条如实化：摘要调用为独立计费的全新请求，折扣友好声明删除或降级为未来增强。优点：零实现成本、文档与实现一致；缺点：成本敏感用户的「摘要调用享缓存折扣」预期落空（§0 角色表对成本敏感用户的承诺项），且摘要请求与后续请求的上下文形态脱钩。
  2. *排实现批次*——摘要调用按架构 §5.1 组装前缀（规则说明与工具清单逐字复用上轮真实请求），使输入开头天然命中前缀缓存折扣。优点：兑现 NFR3 与角色承诺，长会话压缩的摘要调用省真实成本；缺点：需将上轮请求的系统提示与工具表 threading 进压缩路径（跨模块接线），且「工具清单在场但指令禁用工具」的请求形状需与摘要指令协调。
- **影响范围**：US3.1 第一条验收、NFR3；架构 §5.1（输入构成）。
- **裁决人**：待用户裁决。

### SDR-007：压缩摘要的任务清单自动附着未接线（待裁决）

- **编号与日期**：SDR-007 · 2026-09-11
- **背景与动机**：US3.3 与架构 §5.2 要求：压缩完成时存在进行中的任务清单，清单当前状态自动附在摘要之后（从唯一事实源取，不要求模型转述）。2026-09-11 审计发现：后处理入口的签名支持该能力（`post_process_summary(summary, todos)`），但压缩路径的调用点写死 `None`（`rust/crates/mirri-core/src/compaction/round.rs:434`，代码注释自认「TODOs are not currently available in the compaction path」）——任务清单事实源在压缩执行点不可达，清单从不附着。落位后的摘要不含任务状态，模型对未完成项的记忆只剩摘要正文的自觉转述（无硬保证）。
- **选项与权衡**：
  1. *排实现*——把任务清单事实源接入压缩执行路径（服务句柄注入或回调），`post_process_summary` 换真值。优点：兑现「从唯一事实源取、不要求模型转述」的设计，长任务压缩后未完成项有可靠记忆；缺点：压缩在引擎核心层执行、任务清单服务在更外层，需新增注入面/依赖接线。
  2. *需求降级为可选*——US3.3 标注为暂缓/可选或移入未来增强。优点：零成本，且摘要指令已要求模型覆盖「前向计划」，实际损失有限；缺点：模型转述的任务状态无保真保证，与「不要求模型转述」的初衷背离。
- **影响范围**：US3.3；架构 §5.2（摘要消息落位附着）。
- **裁决人**：待用户裁决。

### SDR-008：保留预算 ≥ 触发量的启动拒绝未实现——用户可配出「永不压缩」组合且无报错（待裁决）

- **编号与日期**：SDR-008 · 2026-09-11
- **背景与动机**：US2.3 第二条验收要求：保留预算配置值不低于触发阈值对应量时，加载配置应拒绝启动并给出可读错误（保留的不能比要压的还多）。2026-09-11 审计发现：配置加载校验只覆盖保留尾两键的互斥与比例范围（`rust/crates/mirri-core/src/config/mod.rs:237-305`；`from_toml` 的硬校验入口 `:459-470`），不存在「保留预算 vs 触发阈值」的跨键校验。用户配置如「触发 0.5 + 保留比例 0.6」被静默接受；运行后果是切线判定永远落在保留预算内 → 每次触发都走「无可压内容」跳过（US2.6 路径），压缩功能整体失效，无任何报错或提示告知用户该配置使压缩永不发生。
- **选项与权衡**：
  1. *排实现（validate 跨键校验）*——加载期比较两键（同为比例制可直接比；绝对 token 制需窗口容量，窗口未知时降级为运行期首判提示）。优点：早失败、可读错误，符合「配置必须真实接线」（US6.3）的精神；缺点：绝对值制下模型窗口未知（未配置且未观测）使加载期无法定论，需要「加载期硬校验（同制）+ 运行期软提示（异制/窗口未知）」两层设计，实现面比单点校验宽。
  2. *需求放宽为文档提示*——US2.3 第二条降级为「配置文档写明约束 + 运行期可见保留/触发关系」。优点：零实现；缺点：静默失效仍然发生，「声明了但实际使功能失效」的配置组合留在交付面。
- **影响范围**：US2.3 第二条验收；US6.2（配置校验面）；架构 §8。
- **裁决人**：待用户裁决。

### SDR-009：摘要指令缺「最近对话已原样保留」条款——且该缺口被 verbatim 冻结测试固化（待裁决）

- **编号与日期**：SDR-009 · 2026-09-11
- **背景与动机**：US3.2 第二条验收与架构 §5.2 规定：保留尾存在时，摘要指令须明确告知模型「最近的对话已原样保留、无需转述」，指令只要求覆盖旧段（SDR-002 既定方向的一部分——指令表述随保留尾语义适配）。2026-09-11 审计发现：指令模板（`rust/crates/mirri-core/src/compaction/round.rs:520-567` `build_compaction_instruction`）不含该条款——通篇按「整段对话都要总结」的表述（"Summarize the conversation so far"），未告知模型最近对话已在保留尾中原样保留。且 2026-09-10 加固批对该指令全文做了字节级 verbatim 冻结测试，**直接补上条款会使现有测试红**：该偏差已被测试基线固化，修复必须连冻结文本一起在同一变更内修订。
- **选项与权衡**：
  1. *排实现（修订冻结文本并同步测试）*——指令模板补「最近对话已原样保留、无需转述」条款，同一变更内更新 verbatim 冻结测试的期望文本。优点：兑现 SDR-002 的指令语义，模型不再浪费篇幅转述仍在眼前的最近对话；缺点：冻结基线变更需显式评审（冻结的意义就是防无意识漂移），指令变更影响所有摘要输出形态。
  2. *改需求删该条款*——删除 US3.2 第二条验收并同步架构 §5.2。优点：零实现；缺点：模型可能把保留尾内容也转述进摘要（浪费 token 且转述失真风险），与 SDR-002 已裁决的方向冲突（推翻需明示）。
- **影响范围**：US3.2 第二条验收；SDR-002（指令表述的既定方向）；架构 §5.2；2026-09-10 加固批的 verbatim 冻结测试。
- **裁决人**：待用户裁决。

### SDR-011：摘要期间历史分歧的取消分支未接入 begin→block 落位面——中途追加的助手内容被静默压缩（待裁决，P0）

- **编号与日期**：SDR-011 · 2026-09-11
- **背景与动机**：US4.2 第三条验收与架构 §5.4 要求：摘要生成期间追加了助手消息/工具结果/后台通知（既不在摘要快照里、也不该被落位跳过）时，本次压缩必须取消。2026-09-11 审计发现：§5.4 的前缀竞态检查只存在于 `compaction_round`（`rust/crates/mirri-core/src/compaction/round.rs:166-170`），而该函数**生产路径零调用方（死代码，仅测试消费）**；生产实际走的 `FullCompaction::begin → block` 落位路径（`rust/crates/mirri-core/src/compaction/mod.rs:753-830`）对返回的摘要直接按 live 历史重切线落位，**无任何竞态检查**——摘要调用期间追加的助手消息被划入被替换的旧段、随摘要落位一起从模型视图消失（`applied:true`），内容既不在摘要里（快照早于它）也不在保留尾里，且连丢弃计数都不体现（静默丢失）。修复形状：把 begin 时刻的历史快照 threading 过 `ActiveCompaction`，`block` 落位前按 §5.4 语义校验（前缀不变 + 追加仅限真实用户输入/钩子附加上下文）。`#[ignore]`d 验收夹具已就绪：`rust/crates/mirri-core/tests/compaction_tests.rs:3214` `should_cancel_the_round_when_history_diverges_during_the_summarizer_call`，`-- --ignored` 红于缺口。

- **影响范围**：US4.2 第三条验收；架构 §5.4；`FullCompaction::begin/block` 与 `compaction_round`（死代码处置）。

### SDR-012：turn-active 手动压缩拒绝不可达 + dispatch 锁序反转（ABBA 可永久卡死会话）（待裁决，P0）

- **编号与日期**：SDR-012 · 2026-09-11
- **背景与动机**：US1.4 第二条验收要求：回合执行中执行压缩命令应被拒绝并提示「等当前回合结束后再试」，不排队、不打断。2026-09-11 审计（Task 6，经代码追溯与实测证实）发现两个缺口：① **拒绝不可达**——手动压缩 dispatch 先取 memory 锁再取 flow 锁（`rust/crates/mirri-embedded/src/embedded_server/compaction_handlers.rs:107-116`：`memory.lock()` → `flow_arc.lock()`），而正在执行的回合持有 flow 锁并在回合内追加 memory；RPC 线程持 memory 锁阻塞等 flow 锁，`request_manual_compaction` 的 turn-active 拒绝分支（`rust/crates/mirri-core/src/turn_flow/mod.rs:605-617`）要拿到 flow 锁才可达——实际表现是 RPC 阻塞至回合结束（事实上的「排队」），而非即时拒绝。② **锁序反转 ABBA**——引擎文档规定的锁序为 flow → compaction → steer → memory（`rust/crates/mirri-core/src/turn_flow/mod.rs:127-139`），该 handler 以 memory → flow 倒序持双锁，与回合路径（flow → memory）构成 ABBA：回合要追加 memory（等锁）、RPC 持 memory 等 flow——会话可永久卡死；`ENGINE_TURN_TIMEOUT` 无法救援（超时 timer 与被阻塞的同步锁在同一线程上，同样拿不到锁）。双修形状：busy 预检（`rust/crates/mirri-embedded/src/embedded_server/message_handlers.rs:862` 已有 `flow_handle.try_lock()` 先例）+ 锁序对齐。`#[ignore]`d 验收夹具已就绪：`rust/crates/mirri-embedded/src/embedded_server/tests.rs:8673` `should_refuse_manual_compaction_when_a_turn_is_active`，`-- --ignored` 红于缺口。
- **选项与权衡**：
  1. *排实现（双修：busy 预检 + 锁序）*——预检返回即时拒绝 + 按文档序取锁（锁序修正是正确性问题，独立于需求裁决成立）。优点：兑现 US1.4 即时拒绝、消除 ABBA（可用性 P0）；夹具现成。缺点：预检通过到真实 begin 之间存在竞态窗口（回合恰好启动），需以「预检 + 单飞互斥（US1.5）」组合闭合，接线细节在实现批设计。
  2. *改需求（US1.4 第二条改为排队语义）*——接受「回合中手动压缩阻塞至回合结束后执行」的现状。优点：零实现；缺点：RPC 长阻塞（回合可达分钟级）对客户端是挂起体验，且**锁序反转必须单独修复**——ABBA 死锁不随需求裁决消失，该选项只覆盖缺口①，缺口②仍需排期。
- **影响范围**：US1.4 第二条验收、US1.5（单飞与预检的组合）；引擎锁序不变量（`rust/crates/mirri-core/src/turn_flow/mod.rs:127-139` 的 Lock Ordering 文档注释——架构文档本身无锁序条款，是否将其提升为架构 §2.3 是修复批的待决问题）；embedded 手动压缩 RPC。
- **裁决人**：待用户裁决（P0——ABBA 为正确性缺陷，任一选项下都需修复锁序）。
