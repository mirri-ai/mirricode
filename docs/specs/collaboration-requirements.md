# 多 Agent 团队协作生态 — 需求文档（User Stories）

> 状态：v2（v1 基线 + 2026-09-08 角色域评审裁决并入，见文末 SDR-001–002；待用户评审） ·
> 本文是协作域需求侧的唯一事实源（内部规格文档，不进文档站构建，中文单语）。
> 产品愿景：**让多 agent 像人类团队那样，按各自职责相互协作推进任务**——超越现有"主 agent 拆活派发"的主从模型。
> 配套文档：[collaboration-architecture.md](collaboration-architecture.md)（架构机制与团队模型骨架）· [collaboration-context.md](collaboration-context.md)（现状参考）。（勘误 2026-09-12，B0：原文「collaboration-architecture.md（待需求确认后撰写）」已过时——该文档已于 2026-09-12 新建。）
> 验收标准统一 Given-When-Then；优先级 P0 > P1 > P2。

## 0. 角色定义（Personas）

| 角色 | 场景 | 核心诉求 |
|---|---|---|
| **团队发起人**（发起协作任务的用户） | 给一个目标，让团队推进 | 我不用微观管理；团队自己分工、推进、汇报 |
| **团队观察者**（盯着团队干活的用户） | desktop/web 上看团队工作 | 谁在干什么一目了然；我能随时介入纠偏 |
| **角色定义者**（编写 agent 角色的用户/社区） | 定义团队里的角色 | 声明职责与产出契约，而不是只配工具白名单 |
| **lead agent**（团队中的协调角色） | 协调分工与流转 | 我能看到全局任务板，能分派、能求助、能升级 |
| **成员 agent**（团队中的执行角色） | 执行自己职责内的任务 | 我知道自己的职责边界；需要别的角色时能直接问、直接交接 |

## 1. Epic E1：团队组建（Team Formation）

> 解决"团队从哪来"。从主从模型的一人全包，走向角色分工。

### US1.1 角色的职责声明（P0）

作为角色定义者，我想在 agent profile 中声明职责（负责什么、产出什么、何时被需要），以便团队成员按职责边界工作而不是共享全部上下文。

验收：
- Given 一个角色的行为提示词正文声明了职责与产出契约（该角色完成任务时必须产出什么），When 该角色作为团队成员执行，Then 其系统提示包含职责声明，且任务完成的判定包含产出契约（正文承载，不设独立字段，SDR-001）
- Given 角色未声明职责内容，When 组建团队，Then 该角色仍可加入（向后兼容，视为"通用执行者"）
- Given 角色声明的职责与既有 `tools` 白名单并存，Then 两者独立生效（职责引导行为，白名单约束能力面）

### US1.2 显式组建团队（P0）

作为团队发起人，我想用一份团队定义（成员角色列表 + 协作规则）围绕一个目标启动团队，以便结构化地开始协作。

验收：
- Given 团队定义含 2 个以上角色（含一个 lead 角色与至少一个执行角色）与一个目标，When 发起团队，Then 团队进入运行态：各角色按职责就位，目标进入共享任务板
- Given 团队定义只含 1 个角色，When 发起，Then 被拒绝并提示（单角色不属于团队协作，走既有单 agent 会话）
- Given 团队运行中重复以相同团队定义发起，Then 复用既有团队（幂等）而非创建平行团队

### US1.3 团队模板（P1）

作为团队发起人，我想使用预设团队模板（如 feature-team = lead + coder + reviewer + tester），以便不必每次手写角色组合。

验收：
- Given 选择模板，When 组建，Then 展开为对应角色集（模板引用的角色 profile 必须存在，缺失则报错指名）
- Given 用户在模板基础上增删角色，When 组建，Then 生效的是修改后的组合
- Given 模板由仓库 `.mirri-code/` 或用户目录提供，Then 团队模板可团队共享（project 层）或个人复用（user 层）——分层复用既有配置发现机制

### US1.4 按目标自动组建（P2）

作为团队发起人，我只给一个目标，让引擎建议团队构成（角色组合），以便零配置获得合理分工。

验收：
- Given 一个目标描述，When 请求自动组建建议，Then 返回建议的角色组合与职责草案，用户确认后进入 US1.2 流程（建议不直接执行）

## 2. Epic E2：共享任务板（Task Board）

> 解决"活怎么分、怎么流转"。任务从 agent 私有后台任务升级为团队共享的一等工作单元。

### US2.1 团队共享任务板（P0）

作为团队发起人/lead agent，我想在团队内创建任务并让全体成员可见，以便工作是结构化流转而不是埋在对话里。

验收：
- Given 团队运行中，When 创建任务（标题、描述、目标验收标准、建议角色），Then 任务进入团队任务板，全体成员 agent 可查询
- Given 任务处于 `todo` 状态，When 查询任务板，Then 每个任务含状态（todo/claimed/in_progress/in_review/done/blocked）、认领者、依赖
- Given 团队结束，Then 任务板随团队归档可查（依赖 E6）

### US2.2 任务分派与认领（P0）

作为 lead agent/成员 agent，我想分派任务给特定角色，或按职责自主认领未分派任务，以便分工有明确归属。

验收：
- Given lead 将任务分派给角色 R，When 分派，Then 任务归属 R（状态 claimed），R 的下一轮上下文包含该任务
- Given 任务未分派且其建议角色与成员 A 的职责匹配，When A 认领，Then 认领成功且其他成员可见归属变更
- Given 任务已被角色 R 认领，When 其他角色尝试认领，Then 被拒绝（归属互斥），需经 lead 转派

### US2.3 任务依赖与阻塞（P1）

作为 lead agent，我想声明任务间的依赖（B 依赖 A），以便工作按正确顺序推进而非全部并行。

验收：
- Given 任务 B 声明依赖任务 A，When A 未完成，Then B 处于 blocked 状态且不可认领
- Given A 完成，Then B 自动解除阻塞并通知（对应角色收到可认领信号）

### US2.4 交付物归集（P1）

作为团队发起人，我想每个任务的产出物（diff/文档/结论）挂在任务上，以便最终成果可追溯、可归集。

验收：
- Given 任务完成，When 成员提交产出，Then 产出物关联到任务记录（可含多个工件）
- Given 团队目标达成，When 请求成果汇总，Then 按任务维度聚合全部产出物与验收结论

## 3. Epic E3：角色间通信与交接（Communication & Handoff）

> 解决"agent 之间怎么直接对话/交接"。替代"一切经父 agent 转述"。

### US3.1 角色间结构化消息（P0）

作为成员 agent，我想向另一个角色发结构化消息（提问/回答/状态同步/协助请求），以便直接协作而不经 lead 转述。

验收：
- Given 成员 A 向成员 B 发送 question 消息，Then B 的下一轮上下文包含该消息（含 A 的身份与任务上下文），B 的回答以 answer 消息回到 A
- Given 消息类型超出预定义集（question/answer/status/assistance），Then 以前向兼容方式投递（未知类型不崩、可扩展）——对齐 mirri-collaboration 既有 8 种 AgentMessage 枚举的演进
- Given 消息含敏感操作请求，Then 受 permission 层策略约束（协作工具不是权限豁免区）

### US3.2 带上下文的交接（P0）

作为成员 agent，我想把任务连同我的发现（结论/约束/未竟事项）交接给另一角色，以便接手者不必从零开始。

验收：
- Given A 将 in_progress 任务交接给 B，When 交接，Then 任务归属变为 B，交接包含 A 的进展摘要与关键上下文（A 显式给出的部分）
- Given 交接发生，Then 任务历史记录保留 A 的贡献（可追溯），团队视图显示交接事件

### US3.3 升级（Escalation）（P1）

作为成员 agent，当我遇到超出职责/无法解决的阻塞时，我想升级给 lead 或用户，以便阻塞不无限悬置。

验收：
- Given A 发起升级（含原因与已尝试），Then lead 收到升级通知并可在下一轮处理；标记为"需用户裁决"的升级进入用户介入队列（US4.3）
- Given 同一任务连续升级超过团队规则上限，Then 自动升级给用户（防 agent 间死循环）

## 4. Epic E4：冲突与仲裁（Arbitration）

### US4.1 冲突检测与呈现（P1）

作为团队观察者，当两个角色对同一问题给出矛盾结论/方案时，我想看到冲突被识别出来，以便不静默择一。

验收：
- Given 成员 A 与 B 对同一任务/技术决策产出矛盾结论，When 冲突发生，Then 团队视图呈现冲突（双方观点、涉及任务），不静默丢弃任何一方

### US4.2 仲裁策略（P1）

作为团队发起人，我想为团队配置仲裁规则（人裁 / lead 裁 / 多数决），以便冲突有确定性出口。

验收：
- Given 仲裁策略为 lead，When 冲突发生，Then lead 在下一轮裁决并记录裁决理由
- Given 仲裁策略为 human，When 冲突发生，Then 进入用户介入队列（US4.3），团队在该决策上等待
- Given 仲裁策略为 majority，Then 按团队规则定义的仲裁者集合表决（对齐既有 ConflictResolution 枚举的落地）

### US4.3 用户介入（Intervene）（P1）

作为团队发起人，我想随时介入团队（纠正方向、改任务、给裁决、终止），以便人始终是最终控制点。

验收：
- Given 团队运行中，When 用户发出介入指令，Then 指令进入相应角色的上下文（或团队广播），效果可见于下一轮行为
- Given 用户终止团队，Then 全体成员停止，任务板定格归档（E6）
- Given 用户挂起团队，Then 状态冻结可恢复（与 session pause/resume 语义对齐）

## 5. Epic E5：团队观测（Observability）

> 没有观测的 multi-agent 是黑盒，用户不会信任。观测与骨架同优先级。

### US5.1 团队实时视图（P0）

作为团队观察者，我想看到团队的实时状态（谁在干什么、任务板快照、正在发生的交接），以便掌握进度。

验收：
- Given 团队运行中，When 订阅团队事件流，Then 收到：任务状态变更、认领/交接、消息往来（摘要级）、成员 started/completed/failed 事件
- Given 观察团队视图（UI/wire），Then 呈现成员列表（角色+状态）、任务板全量、最近关键事件
- Given 成员失败，Then 失败事件含原因，任务回到可认领状态（不静默消失）

### US5.2 消息流可查（P1）

作为团队观察者，我想回看 agent 之间的完整消息历史，以便审计团队是怎么得出结论的。

验收：
- Given 团队历史消息，When 请求消息历史（过滤：按成员/按任务/按类型），Then 返回完整时序消息（依赖 E6 持久化；团队运行期内存可查）

### US5.3 成果报告（P1）

作为团队发起人，团队目标达成后，我想得到一份结构化的成果汇总，以便验收与归档。

验收：
- Given 团队完成（目标达成或用户终止），When 请求成果报告，Then 汇总：目标、任务板终态、各任务产出物、关键决策与裁决记录（依赖 US2.4）

## 6. Epic E6：团队生命周期与持久化（Lifecycle & Persistence）

### US6.1 团队持久化与恢复（P2）

作为团队发起人，我想团队跨会话存在（进程重启/隔天继续），以便长期任务不因会话中断而丢失。

验收：
- Given 团队运行中进程退出，When 重新打开并恢复团队，Then 任务板、成员、消息历史、任务产出全部恢复，团队可继续推进
- Given 团队长期空闲（超过阈值），Then 挂起而非静默消耗资源

### US6.2 解散与归档（P2）

作为团队发起人，我想团队结束后归档（成果保留、资源释放），以便团队有完整生命周期。

验收：
- Given 团队解散，Then 成员 session 按规则收敛（随团队结束/保留可查），任务板与成果冻结归档
- Given 归档团队，When 事后查询，Then 完整历史可读（团队/任务/消息/成果）

## 7. Epic E7：与既有模型的统一（Model Unification）

> 避免三套并行机制（subagent / swarm / team）造成概念税。

### US7.1 subagent 的定位（P1，架构裁决）

作为集成者/用户，我需要明确的模型统一：subagent（Agent 工具派发）与团队模型的关系是"同一机制的两种用法"还是"分层并存"，以便心智模型与文档一致。

验收（裁决性 US——产出是决策而非功能）：
- 团队模型落地时，给出明确裁决文档：subagent 是团队模型的单角色退化形态（长期统一），或 subagent 保留为轻量路径、team 为结构化路径（长期并存）——两条路线的行为边界、迁移影响、文档措辞一次说清
- 无论裁决为何，既有 Agent/AgentSwarm 工具行为在裁决落地前不破坏

### US7.2 swarm 模式的归宿（P2，架构裁决）

验收（裁决性 US）：
- 给出 swarm（纯状态标记+提醒）与团队模型的关系裁决：作为团队模式的前向兼容别名保留，或退役——退役走 changeset major 流程

## 8. 非功能需求（NFR）

| # | 需求 | 指标/约束 |
|---|---|---|
| N1 | 并发上界 | 团队成员并发受可配置上界约束（默认对齐现有 Agent 工具并发 5 的量级），超出排队 |
| N2 | 成本可观测 | 团队维度的 token/成本聚合可查（复用 agent.getUsage 语义），任务维度可归因 |
| N3 | 权限一致 | 协作工具（消息/任务操作/交接）全部过 permission 面；团队模式不是权限豁免区（现状差距见 [collaboration-context.md](collaboration-context.md) §4.7） |
| N4 | 可中断性 | 用户介入指令的生效延迟 ≤ 一个成员轮次；终止在秒级收敛 |
| N5 | 事件完整 | 团队/任务/消息三类事件进事件流（durable，可 cursor 重放），与既有 subagent.* 事件风格对齐 |
| N6 | 单向依赖 | 协作域依赖 agent 域（角色即 agent profile，协作域不为其发明字段——职责等以提示词正文承载，SDR-001），反向禁止 |
| N7 | 前向兼容 | AgentMessage 未知类型不崩（既有协议设计已如此）；团队 wire 契约进 klient + mirri-proto 注册表（契约事实源链） |

## 9. Out of Scope

- 多人类用户协作（本 spec 只涉及 agent 团队与单人发起人）
- 跨进程/多机团队（单进程内起步；跨进程留架构位）
- 完全自主的常驻自组织团队（无人值守自进化——长期方向，本期不做）
- 第三方角色/模板市场（生态化——依赖 E1.3 模板先行）
- agent 自主修改团队结构（增删角色/改规则——所有结构变更经发起人或 lead）

## 附录：需求决策记录（SDR）

### SDR-001 职责与产出契约以提示词正文承载（2026-09-08）

1. **背景与动机**：本文原设想 agent profile 增加 `responsibility` / `deliverable` 两个独立字段；角色域评审裁决（[agent-profile-consumption-requirements.md](agent-profile-consumption-requirements.md) SDR-009）：两者的最终消费者均为 LLM（lead 选人、完成判定），自由正文对其无理解损失，独立字段与正文提示词语义重叠、且需数据模型到页面的完整扩展链路。
2. **决策**：US1.1 的职责与产出契约声明并入 agent profile 的行为提示词正文，不设独立字段；团队组建与完成判定从正文读取；「按职责筛选团队就绪」的结构化能力放弃（配置面文档 US-D2 改按被团队模板引用筛选）。
3. **被否决的备选方案**：a) 独立字段（本 US 原方案）；b) 约定标题的结构化正文——隐式契约脆弱。详见使用域 SDR-009。
4. **影响范围**：US1.1、N6；使用域文档 §7/US-U4.2；配置面文档 US-D1/US-D2。

### SDR-002 lead 与主 agent 为同一机制（2026-09-08）

1. **背景与动机**：lead 若在主 agent 机制之外另建一套，用户需学两套概念且行为易漂移（选择、切换、快照、权限各一套规则）；角色域评审裁决（使用域 SDR-010）。
2. **决策**：lead 即「团队会话的主 agent」——复用主 agent 的装配与切换、快照语义、权限面、按角色归因，不建第二套；任务板分派等团队需求作为主 agent 机制之上的协作能力。
3. **被否决的备选方案**：两套独立机制——概念税与行为漂移风险高。
4. **影响范围**：US1.2、E7 的模型统一边界（subagent 与团队模型的关系仍随 E7.1 裁决）；使用域 SDR-010、配置面文档 Q3。

### SDR-003 协作工具在成熟前默认隐藏，经界面模式显式 opt-in 暴露（2026-09-12）

1. **背景与动机**：rust 侧 7 个 `Collaboration*` builtin 工具此前无条件进 LLM 工具表——但协作机制尚不成熟（无真实 agent 执行接线，见 context §4），暴露半成品工具面会污染模型的工具视野、诱发无效调用；且常驻工具表条目还占提示词预算与缓存稳定性。
2. **决策**：协作工具**注册但默认对 LLM 隐藏**，宿主经显式 RPC（`collaboration.enter` / `collaboration.exit`）进入/退出协作模式时整组暴露/收回；web 界面在 Mode 选择区（plan / goal / swarm 并列处）提供 Collaboration 开关作为用户入口。模式为会话级、不持久化——重启后回到隐藏态，需再次显式开启。
3. **被否决的备选方案**：a) 常驻暴露（污染工具面，半成品被误用）；b) 连注册都不做、经实验旗标整体编译开关（失去运行期切换能力，且 wire 面无法契约登记）；c) 逐工具单独开关（用户无逐工具心智，组是协作语义的最小单位）。
4. **影响范围**：E5.1（团队实时视图的入口前提）；rust 侧实现 `03c3ecb1`（门控 + RPC + 契约可发现性）、`08bbd989`（web Mode 开关）；工具排序为配套的非功能约束（缓存稳定性）；协作域成熟后（真实执行接线、E1-E3 骨架落地）可重新裁决是否转默认暴露。

## 12. Epic E8：单用户蜂群协作（TS 支持基线）

> **本节性质**：记录引擎与消费端当前支持的蜂群协作能力，作为 Rust Core 的**对齐基线**（基线是 Rust 需匹配的下限，不是上限）。既有 E1–E7 为多 agent 团队模型设计目标，属超出 TS 现状的设计增强（定性见 SDR-004）。
> **场景**：单用户 + 主代理 + 一批并行子代理；不涉及多人类用户协作（对齐 §9 Out of Scope）。
> **边界**：单个子代理的派发、后台化、续作、止损、生命周期与批量执行的并发节奏/限流/结果呈现归**子代理派发域**（[subagent-requirements.md](subagent-requirements.md) E1–E12）；本节只覆盖**蜂群模式语义**（进入/退出/触发/指引/独占）与**模式级入口/可见性**。
> **端点范围**：条目按"网页端与终端端的并集"表述；两端行为差异（如偏好记忆仅网页端）在 [collaboration-context.md](collaboration-context.md) §6 逐项记录。

### US8.1 蜂群模式的开启与关闭（P0）

作为团队发起人，我想在会话中显式开启/关闭蜂群模式，让主代理以"先探索拆解、再并行派发"的方式工作，以便一批相关子任务并行推进。

验收：
- Given 蜂群模式未开启，When 用户开启（网页模式菜单的 Swarm 开关 / 终端 `/swarm` 或 `/swarm on`），Then 模式生效，主代理收到蜂群工作法指引（先探索拆解、再批量派发、任务尽量细分、避免成员间重复与冲突）
- Given 蜂群模式已开启，When 用户再次执行开启，Then 不重复生效、不重复注入指引（幂等）
- Given 蜂群模式开启中，When 用户关闭（开关或 `/swarm off`），Then 模式退出；若进入指引尚未被消化，Then 收回该进入指引而非叠加一条退出指引，否则给出退出指引
- Given 用户手动开启蜂群模式，When 当前回合结束，Then 模式保持开启（手动进入不自动退出）
- Given 蜂群模式因单任务命令或批量派发而进入，When 该回合结束，Then 模式自动退出
- Given 蜂群模式因批量派发而进入，When 进入，Then 不注入工作法指引（批量派发自身的参数语义已足够）；工作法指引仅随其它进入方式注入

### US8.2 单任务蜂群命令（P0）

作为团队发起人，我想用一条命令"以蜂群方式执行这个任务"，以便一次输入即获得并行拆解与执行。

验收：
- Given 无回合进行中，When 用户输入 `/swarm <任务描述>`，Then 自动开启蜂群模式并立即提交该任务
- Given 单任务蜂群的回合结束、模式自动退出，Then 界面给出"蜂群已结束"的明确标记
- Given 回合进行中，When 用户输入 `/swarm`，Then 命令不可用并提示需先中断当前回合（不产生半生效状态）
- Given 无活动会话，When 用户输入 `/swarm`，Then 提示无活动会话，不生效

端点注记：单任务蜂群（进入即提交、回合结束自动退出、"已结束"标记）目前仅终端端具备；网页端的 `/swarm <任务>` 走"开启（手动）+ 提交"，回合结束不自动退出、无"已结束"标记（差异详录见 context §6、ROADMAP O10）。

### US8.3 手动审批下的蜂群启动确认（P0）

作为团队发起人，当权限模式为手动审批时，我想在启动蜂群前得到明确提示与选择，以便知情决定是否切换到更自动的权限模式。

验收：
- Given 权限模式为手动审批，When 用户在网页的**模式菜单**开启蜂群模式，Then 弹出确认（说明将并行运行多个子代理）；用户取消则不开启
- Given 权限模式为手动审批，When 用户在终端开启蜂群模式（含裸命令、显式开启与单任务蜂群），Then 呈现三选项——切换为自动并启动（工具自动批准、提问跳过）/ 切换为免确认并启动（工具与计划变更自动批准、仍可能提问）/ 保持手动启动（蜂群工作中可能停下等待用户）——取消则命令文本回到输入框、不丢失
- Given 权限模式非手动，When 开启蜂群模式，Then 不出现确认、直接生效
- Given 蜂群模式设置失败（如引擎侧出错），Then 用户收到含原因的明确失败提示

端点注记：网页端斜杠命令的 `on` 与 `<任务>` 变体不出现确认框（裸 `/swarm` 与模式菜单同路径、均有确认）；终端端所有开启路径均经确认。模式设置失败时，网页端呈现通用操作失败告警，终端端失败提示含原因。

### US8.4 蜂群模式的界面可见性（P0）

作为团队观察者，我想随时看出会话是否处于蜂群模式，以便掌握状态。

验收：
- Given 蜂群模式开启，Then 网页输入区模式标签显示 Swarm、终端底部状态栏显示蜂群徽标、网页状态面板显示"蜂群模式：开"（关闭态对称显示"关"）
- Given 终端中用户经命令开启或关闭蜂群模式，Then 会话转录中出现对应的进入/退出标记；单任务蜂群结束时出现"蜂群已结束"标记（批量派发自动进入/退出的蜂群无转录标记）
- Given 用户重新打开会话（含重启后），When 读取会话状态，Then 蜂群模式开闭如实回读
- Given 移动端界面，Then 设置面板提供与桌面同等的蜂群模式开关
- Given 蜂群模式状态变化，Then 界面各处（标签/徽标/面板）读同一状态源，不出现互相矛盾的显示

### US8.5 蜂群模式跨重启保持（P1）

作为团队发起人，我希望蜂群模式的开闭状态在会话重启后如实恢复，以便重启不丢模式上下文。

验收：
- Given 会话在蜂群模式下被持久化，When 会话重载，Then 模式恢复为开启，且不向主代理重复注入蜂群指引、不重复发布模式变化通知（恢复是无声的）
- Given 会话持久化时不在蜂群模式，When 重载，Then 恢复为关闭

### US8.6 蜂群批次的独占性（P1）

作为团队观察者，我想蜂群批量派发独占一次工具调用批次，以便一次编排决策原子化、结果可归因。

验收：
- Given 主代理一次发起批量派发，When 同批混有其它工具调用，Then 整批被否决并给出明确指引（批量派发需独占批次）
- Given 同一批次包含多个批量派发调用，Then 整批被否决并提示
- Given 批次中只有一次批量派发调用，Then 正常放行
- Given 主代理在批次中发起多个单一派发（非批量），Then 不受独占限制（单一派发可混批）

### US8.7 模式偏好的按会话独立记忆（P2）

作为团队发起人，我想蜂群模式偏好按会话独立记忆（网页端），以便不同会话各自维持模式。

验收：
- Given 会话 A 开启蜂群、会话 B 未开启，Then 两会话互不影响；会话被删除后其偏好一并清理
- Given 无活动会话时开启蜂群（网页端），When 用户建立首个会话，Then 偏好转移到该会话生效（新会话即处于蜂群模式）
- Given 主会话处于蜂群模式，When 用户在网页侧聊（顺带问）提交问题，Then 侧聊以蜂群模式运行（模式随提交携带）

### E8 非功能需求追加（并入 §8 表）

| # | 需求 | 指标/约束 |
|---|---|---|
| N8 | 模式状态可恢复 | 蜂群模式开闭状态随会话持久化，重启后如实恢复，不依赖进程内存 |
| N9 | 指引生命周期一致 | 进入/退出指引的呈现与收回在实时查看与历史回看两个视角一致（回看不重现"当时不存在"的指引） |
| N10 | 模式非权限豁免 | 蜂群模式不改变权限语义：成员权限与工具约束随派发者（继承语义见子代理派发域）；蜂群不是绕过审批的通道 |
| N11 | 单一状态源 | 蜂群模式状态只有一个权威判定源；界面标签、状态面板、命令回读读同一状态 |

## 13. 未来增强提案（超出 TS 现状）

> 以下为基线化侦察中识别的改进方向，**均为提案，不描述现状**，免于现状对齐检查；与既有 E1–E7 的关系已标注。

- **P-1 蜂群结果的结构化回流**：现状批量派发的完成结果以文本块回流，消费端靠解析文本渲染进度卡片。提案：结果经结构化事件通道回流，减少文本解析的脆弱性。（可并入 E5 团队观测设计）
- **P-2 成员阶段汇报**：现状成员只有终态摘要回流派发者，进行中的发现对派发者不可见。提案：轻量阶段汇报（心跳/里程碑）机制，作为 E3 通信设计的子集（避免与全量消息通道重复建设）。
- **P-3 终端协作模式入口**：协作模式的用户入口目前仅网页端，终端无入口。提案：终端提供对称入口（命令或开关），与 SDR-003 的显式 opt-in 原则一致。
- **P-4 模式字段端到端一致性**：单次请求携带的模式字段与独立的模式切换调用并存时，两者应有一致性规则（以谁为准、冲突如何呈现），避免"请求说开、状态说关"。

### SDR-004 TS 支持基线补录与既有 Epic 定性（2026-09-12）

1. **背景与动机**：本文原有 E1–E7 描述多 agent 团队协作模型，属超出 TS 引擎现状的设计目标（TS 现状为单用户主从派发 + 蜂群模式，无角色间通信/共享任务板/仲裁，见 [collaboration-context.md](collaboration-context.md) §5–§7）；同时 TS 已支持的蜂群模式能力此前只在现状盘点中出现，未落为可验收需求条目，Rust 团队缺少对齐基线。
2. **决策**：a) 新增 Epic E8（US8.1–8.7、NFR N8–N11）记录蜂群协作能力为 Rust 对齐基线；b) E1–E7 维持原文，定性为"超出 TS 现状的设计增强"，不削弱、不向下对齐；c) 边界裁定：单子代理派发生命周期与批量执行的并发/限流/结果呈现归子代理派发域，本域覆盖蜂群模式语义与模式级入口/可见性；d) 新增 §13 未来增强提案，与现状描述严格分离。
3. **被否决的备选方案**：a) 将 E1–E7 改写为现状口径——违反设计文档终态原则且削弱既有设计；b) 另建独立基线文档——破坏"协作域需求侧唯一事实源"；c) 在 E1–E7 内逐条插注现状——构成对既有内容的改写。
4. **影响范围**：新增 §12/§13；[collaboration-context.md](collaboration-context.md) §5–§8 增量；[collaboration-architecture.md](collaboration-architecture.md)、[collaboration-ROADMAP.md](collaboration-ROADMAP.md) 新建。
