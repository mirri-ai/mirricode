# 非功能性 — 需求文档

> 状态：v1 基线 · 2026-09-12 · 待用户评审 ·
> 本文是非功能性域（non-functional）需求侧的唯一事实源（内部规格文档，不进文档站构建，中文单语）。
> 基线性质说明：本文以 TS 引擎（v2 为主）能力为 **Rust 对齐基线**记录——基线是 Rust 要达到的底线，不是 Rust 的上限；超出 TS 现状的改进以明确标注的提案形式记录（§9）。现状证据（file:line）见 [non-functional-context.md](non-functional-context.md)。
> 产品愿景：**快得起来、扛得下去、看得见底、关得干净**——打开就能用、长跑不失控、出事能诊断、不想被采集就真的不被采集。
> 配套文档：机制与技术形状见 [non-functional-architecture.md](non-functional-architecture.md)；现状盘点见 [non-functional-context.md](non-functional-context.md)；执行状态与开放项见 [non-functional-ROADMAP.md](non-functional-ROADMAP.md)。
> 范围边界：本域覆盖**全局/跨域的非功能基线**——启动与就绪体验、运行期响应与资源占用有界性、并发模型与吞吐特征、超时与重试的全局契约、日志与诊断体系、遥测与可观测性（事件采集/上报/退出选择）、崩溃与错误上报、退出与清理。**不属本域**（归各业务域，本文只做全局索引引用，不重复定义）：压缩的触发与计量（[compaction-requirements.md](compaction-requirements.md) §8 NFR）；对话呈现的投影保真与断线一致性（[conversation-rendering-requirements.md](conversation-rendering-requirements.md) §6 NFR）；会话记录的落盘与版本链（session-persistence 域）；单工具的执行语义与超时参数（tool-calling 域）；子代理/后台任务的生命周期语义（subagent/background-tasks 域）；MCP 连接与超时配置的语义（mcp 域）；审批流的拦截语义（approval 域）。各域内的超时/重试/并发数值统一收录于本文 §5「全局等待与上限索引」，作为跨域可查的唯一汇总表。

## 0. 角色定义

| 角色 | 场景 | 核心诉求 |
|---|---|---|
| **日常使用者**（打开终端敲一句话的人） | 等待启动、盯着流式输出 | 秒级进入可交互；流式输出不卡顿；崩溃不丢已做的工作 |
| **长任务用户**（跑几小时调查/重构的人） | 会话越滚越长、机器越跑越热 | 内存与界面占用有界；日志与临时文件不悄悄塞满磁盘 |
| **隐私敏感用户 / 合规管理者** | 关心数据外发的人 | 明确知道采集什么、何时上报；一键关闭后真的不再发送 |
| **弱环境用户**（弱网、低配机、容器、后台标签页） | 网络不稳、磁盘紧张 | 断网不报错刷屏、恢复后补齐；后台冻结不丢内容；重连自动补偿 |
| **排障者**（用户本人或支持工程师） | 出了问题要找原因 | 日志分级可查、有轮转不丢关键现场；崩溃自动留痕；启动失败直接指出日志位置 |

## 1. Epic E1：启动与就绪体验（P0）

> 解决"打开到能用有多快、等多久"。原则：用户能交互的时刻尽早到来；一切非必要工作放到后台或推迟到需要时。

### US1.1 首帧不等待非必要工作（P0）

作为日常使用者，我想启动后立刻看到可交互的界面，不被无关工作拖住。

验收：
- Given 用户启动交互界面，When 初始化启动，Then 界面首帧在必要工作（配置读取、界面搭建、会话建立）完成后立即呈现
- Given 启动过程中存在非必要工作（品牌横幅、输入历史、可选模型列表刷新、自动补全辅助程序、旧版本缓存清理、更新检查），When 启动进行，Then 这些工作均在后台进行，不阻塞首帧呈现与后续交互；任何一个失败或缓慢都不影响首帧与后续交互
- Given 更新检查需要联网，When 网络不可用，Then 更新检查静默跳过，不阻塞启动、不弹出错误

### US1.2 外部依赖就绪不挡首问（P0）

作为日常使用者，我不想因为外部服务（如外部工具服务器）连不上而打不开界面。

验收：
- Given 配置了多个外部工具服务器，When 会话创建，Then 这些服务器的连接在后台并行进行，界面可用与首个问题发出都不等待连接完成
- Given 用户发出第一个问题，When 尚有外部服务器未就绪，Then 仅在真正要用到该服务器的能力时才等待它（且按 mcp 域的超时契约限时）
- Given 用户显式要求保守启动（回滚开关打开），When 会话创建，Then 恢复为等待全部外部服务器就绪后再继续的旧行为

### US1.3 启动性能可观测（P0）

作为排障者/产品方，我想知道启动各阶段花了多久，以便定位"变慢了"的问题。

验收：
- Given 一次交互式启动完成，When 启动流程结束，Then 产生一条启动性能事件，包含总时长、配置读取耗时、初始化耗时、外部服务器就绪耗时四项分解
- Given 无界面的一次性执行模式（如脚本调用），When 执行结束，Then 产生一条含总时长的退出事件
- Given 启动过程失败，When 向用户报告错误，Then 错误信息中包含日志文件的所在位置，用户无需猜

### US1.4 原生资产与外部程序的取得策略（P0）

作为弱环境用户/普通安装者，我不想因为原生组件缺失而无法使用。

验收：
- Given 以单文件可执行形式分发，When 首次运行，Then 内嵌的原生组件（如界面驱动、终端模拟等）按需解出到本地缓存目录（校验完整性后才启用），且启动时在后台清理旧版本缓存
- Given 缓存解出或原生组件加载失败，When 程序继续运行，Then 回退到常规安装路径下的组件解析，不崩溃
- Given 系统缺少外部搜索程序，When 用户使用文件搜索类工具，Then 自动下载受信任版本（同一时刻只下载一份，不重复下载；下载自身有时限），用户等待下载完成后继续；无法下载时给出明确失败原因与一句话安装指引
- Given 引擎内部的文件搜索在搜索程序不可用时，When 执行搜索，Then 直接使用内置搜索实现完成，不因缺失而失败（并记录降级情况）
- Given 可选的原生加速组件（如高性能引擎、终端会话组件）安装失败，When 程序安装，Then 安装不失败（列为可选依赖），运行时缺失则相应功能明确报"未实现"而非静默异常

### US1.5 各运行模式启动一致（P0）

作为日常使用者，无论用哪种模式（交互界面/一次性执行/本地服务/升级），我都不希望启动行为不一致或退出时挂住。

验收：
- Given 任一模式启动失败，When 错误处理，Then 退出码正确设置（非零）、错误信息可读
- Given 任一模式退出，When 走退出路径，Then 退出流程整体有时间上限（见 US7.3），超时强制结束，绝不无限悬挂

### US1.6 桌面壳两阶段就绪（P0，[desktop-source]）

作为桌面应用用户，我想打开应用尽快见到主界面，而不是等后台全部预热完。

验收：
- Given 桌面应用启动，When 本地服务端口已可响应基本健康检查，Then 立即加载主界面（不等后台预热完成）
- Given 主界面已显示而后台仍在预热，When 预热完成，Then 界面无需任何动作即自然可用
- Given 已有一个服务实例在运行，When 再次启动桌面应用，Then 直接复用该实例，不重复拉起

## 2. Epic E2：运行期响应与资源有界（P0）

> 解决"长跑不失速、资源不失控"。原则：界面呈现节奏受控；占用随使用时长有界；诚实披露无界点。

### US2.1 流式呈现节奏受控（P0）

作为日常使用者，我想流式输出连续流畅，且界面更新频率不失控。

验收：
- Given 终端界面收到高频流式分片，When 渲染，Then 每帧合并渲染且有最低帧间隔（约每秒 60 帧上限），只重绘变化区域，不整屏闪烁
- Given 网页界面收到高频流式分片，When 渲染，Then 同类高频事件按帧合并批量应用，单批有数量与体积上限，超大内容拆分后分批应用
- Given 单条消息内容极大（超长文本或超大代码块），When 渲染，Then 自动降级渲染方式（如放弃语法高亮保底纯文本），不因渲染卡死界面
- Given 重型渲染任务（公式排版、图表绘制），When 处理，Then 在后台工作线程执行，不阻塞主线程交互

### US2.2 长会话资源有界（P0）

作为长任务用户，我想跑几小时的会话后内存和界面依然跟手。

验收：
- Given 终端界面会话持续变长，When 转录窗口超出保留上限（默认保留最近 15 个回合、超出上限再过一段余量才裁剪，避免频繁抖动），Then 更早的回合整块从界面释放，较早的步骤合并为摘要，界面节点数保持有界；最近若干回合（默认 3 个）仍可展开查看
- Given 网页界面打开超长会话，When 滚动查看更早消息，Then 更早内容按页加载（打开首屏只取最近一段），不因历史长拖慢打开；已加载内容的渲染占用控制见 §9 提案 P8
- Given 一条工具结果超长（默认超过 5 万字符），When 落入记录，Then 全文落盘、界面与模型视图只保留预览（默认 2 千字符），需要时显式取回

### US2.3 进程资源自监控（P1）

作为产品方/排障者，我想了解真实用户环境的资源画像。

验收：
- Given 遥测开启，When 启动后约 1.5 秒的预热采样与之后每 5 分钟的周期采样，Then 上报进程内存（常驻/堆/堆外）、CPU 累计与占比、机器内存与负载等系统指标事件
- Given 遥测关闭，When 运行，Then 不采样、不产生任何指标事件（见 US6.4）

### US2.4 磁盘占用有界（P0）

作为弱环境用户，我不想日志和临时文件悄悄塞满磁盘。

验收：
- Given 日志持续写入，When 单个日志文件超过大小上限（全局默认 6MB、会话默认 5MB），Then 轮转到新文件，且保留个数有上限（全局默认 5 个、会话默认 3 个），超龄删除
- Given 日志写入缓冲积压超过上限（默认 1000 条），When 继续产生日志，Then 丢弃最旧条目并记录丢弃计数，绝不因日志拖垮主流程
- Given 遥测暂存文件（上报失败时落盘的待发事件），When 超过 7 天，Then 自动清理，不无限堆积
- Given 单文件可执行的原生缓存存在多个历史版本，When 启动，Then 后台自动删除非当前版本的缓存目录

## 3. Epic E3：并发模型与吞吐（P0）

> 解决"哪些事串行、哪些事并行、并行到什么程度"。

### US3.1 单会话回合串行、回合内工具并行（P0）

作为日常使用者，我想在一个会话里的提问按先后顺序处理，但同一回合里的多个工具调用不要排队傻等。

验收：
- Given 同一会话内先后提交两个提问，When 处理，Then 严格按先来先服务排队，一次只有一个回合在执行（用户中途插入的引导消息按会话管理域语义处理，不在此重复定义）
- Given 一个回合内模型一次要求执行多个工具调用，When 调度，Then 声明会访问冲突资源（如同一文件、同一终端）的调用按声明串行，互不冲突的调用立即并行执行
- Given 工具调用之间无冲突声明，When 全部就绪，Then 不设数值并发上限（并行度由资源声明决定），完成顺序即呈现顺序（先完成先呈现，不按发起顺序硬排）
- Given 一个回合的模型调用次数超过每回合步数上限（如配置），When 达到上限，Then 回合按上限收尾（未配置上限时不因步数终止）

### US3.2 子代理批次启动节奏（P0）

作为长任务用户，我想批量启动子代理时既快又不被服务方限流封禁。

验收：
- Given 一批子代理任务需要启动，When 批次开始，Then 先快速启动初始一小批（默认 5 个），随后以固定间隔（默认每 0.7 秒 1 个）放行其余任务
- Given 服务方返回限流信号，When 批次仍在启动，Then 自动收缩并发容量，被限流的任务指数退避后重新排队，静默一段时间（默认 3 分钟）后每周期恢复 1 份容量
- Given 用户设置了批次硬上限，When 批次运行，Then 任何时刻并发不超过该上限；未设置时不设数值上限（默认无硬上限）
- Given 单个任务声明了超时，When 超过时限，Then 该任务按超时中止并回报明确原因

### US3.3 服务端多会话与推送背压（P0，[web-source]）

作为同时开多个会话的网页用户，我想消息推送不丢帧、不卡服务。

验收：
- Given 一个本地服务进程承载多个会话，When 各会话并发活动，Then 由同一进程统一调度承载（不每会话一个进程）；端口被占用时自动顺延尝试（而非直接失败）
- Given 客户端消费速度暂时跟不上服务端产出，When 推送事件，Then 服务端有界缓冲排队（默认 1000 帧）、按批合并发送（默认每 16 毫秒一批、单批 64 帧）；缓冲超过高水位（默认 1MB）时暂缓发送，水位回落后自动追赶
- Given 同机已有服务实例在运行，When 再次启动，Then 通过实例注册表（含定期心跳，默认 15 秒）发现并共存，不互相冲突

### US3.4 用户取消即时生效（P0）

作为日常使用者，我想按 ESC/Ctrl+C 后一切正在进行的工作立刻停下来。

验收：
- Given 一个回合正在执行（含模型流式输出与工具执行中），When 用户取消，Then 取消沿整条调用链传播：模型请求中止、工具执行收到取消信号、外部服务调用中止
- Given 工具正在执行且收到取消信号，When 工具未及时响应，Then 给予短暂宽限（默认 2 秒）后强制以"已取消"收尾，不让单个失控工具卡死整个回合
- Given 回合被用户手动中断，When 向模型记录本次结果，Then 明确标注"用户手动中断"，提示模型勿自动重试同一动作
- Given 一批子代理正在运行，When 用户取消，Then 整批按"已中止"收尾，各任务不再产生后续动作

## 4. Epic E4：超时与重试的全局契约（P0）

> 解决"等多久、失败了怎么办"。原则：临时故障自动恢复不打扰用户；每类外部等待都有明确上限；最终失败一次说清。

### US4.1 临时故障自动重试（P0）

作为弱环境用户，我不想因为服务方一次抖动就看到报错。

验收：
- Given 模型服务返回临时性错误（限流、服务端 5xx 类、超时类、请求体过大可降级），When 回合尚未耗尽重试预算，Then 按退避策略自动重试：默认最多 10 次尝试、首次等待 0.5 秒起指数翻倍、单次等待封顶 32 秒、带随机抖动；服务方给了明确的"稍后再试"时间时以它为准
- Given 错误属于不可重试类（如配额耗尽、鉴权失效），When 收到错误，Then 立即失败并给出人话解释，不做无意义重试
- Given 一次模型请求因附带内容过大被拒绝，When 重试，Then 自动按降级链重试（先降媒体质量、再去除媒体），尽量保住请求成功
- Given 鉴权凭证过期，When 请求被拒，Then 自动刷新凭证并恰好重放一次原请求
- Given 重试期间用户界面，When 多次重试进行中，Then 界面不闪烁错误（重试是后台行为），最终失败时一次性呈现完整原因

### US4.2 每类外部等待有上限（P0）

作为日常使用者/排障者，我想任何对外等待最终都会自己结束。

验收：
- Given 任一外部交互（外部服务器启动、子代理任务、前台命令、外部钩子脚本、网页请求、握手、心跳、磁盘落盘锁等），When 发起，Then 都有一个明确的超时上限或取消途径；全量清单与默认值见 §5 索引表，超时后的行为（取消/降级/失败）在表中逐项定义
- Given 模型请求本身，When 服务方长时间不响应，Then 不设请求级强制超时（当前设计以"用户可随时取消 + 出错自动重试"为准绳）；此为已知且显式记录的设计取舍（见 §9 提案 P6）

### US4.3 断线自动重连（P0，[web-source]）

作为弱网用户，我想网络抖一下应用自己恢复。

验收：
- Given 网页与服务端的连接意外断开，When 客户端感知，Then 指数退避自动重连（1 秒起翻倍、封顶 30 秒、带随机抖动），重连成功后重新订阅并按快照补偿对齐（补偿语义归对话渲染域）
- Given 连接长时间无任何数据，When 超过心跳宽限（默认心跳 15 秒的 3 倍），Then 主动断开并进入重连流程，不悬挂在半开连接上
- Given 连接握手发起，When 10 秒内未完成，Then 视为失败进入重连
- Given 网页常规请求，When 30 秒未响应，Then 超时失败并明确报网络错误（常规请求不自动重试）
- Given 连接疑似失效（长时间无数据但尚未超过心跳宽限），When 用户切回/聚焦页面，Then 主动验证连接状态，确认失效即强制重连，不等待心跳超时

## 5. 全局等待与上限索引（P0）

## 6. Epic E5：日志与诊断（P0）

> 解决"出事之后查得到"。

### US5.1 分级日志与双路落盘（P0）

作为排障者，我想日志按严重程度分级，且全局问题与单会话问题能分开查。

验收：
- Given 日志系统运行，When 产生日志，Then 按 debug/info/warn/error 分级，级别可通过环境变量调整（默认 info；关闭级别可完全不写）
- Given 全局日志与各会话日志，When 写入，Then 分两路落盘：全局日志一份（全局位置）、每个会话各自一份（会话目录内），互不混写
- Given 交互界面模式与服务模式（本地服务），When 分别运行，Then 服务模式另有结构化访问日志（按请求结果码而非 HTTP 状态记录），且可在启动时选择安静级别
- Given 用户查看会话导出，When 导出内容含诊断信息，Then 导出中包含全局日志路径的指引（导出语义归持久化域，此处只约束路径可发现性）

### US5.2 日志写入可靠且有界（P0）

作为排障者，我想崩溃前的日志尽力保全；作为弱环境用户，我想日志永远不拖垮主流程。

验收：
- Given 正常运行中的日志写入，When 写入，Then 异步串行化追加、批量落盘（每次追加后强制刷到磁盘），写失败时向标准错误流提示但**节流**（默认 30 秒最多一次），绝不刷屏
- Given 崩溃或紧急退出，When 走紧急路径，Then 已缓冲的日志同步保全落盘（尽力而为），随后才退出
- Given 日志轮转（见 US2.4 上限），When 轮转发生，Then 内容按时间有序，不因轮转丢当前会话现场

### US5.3 日志路径可发现（P0）

作为日常使用者，我遇到启动失败时不想猜日志在哪。

验收：
- Given 启动失败，When 向用户报告错误，Then 错误信息中直接包含全局日志文件路径（"查看日志：<路径>"）
- Given 用户想主动找日志，When 查看配置文档，Then 日志位置有明确文档说明

## 7. Epic E6：遥测与隐私（P0）

> 解决"采集什么、何时发、怎么关"。原则：遥测零伤害——永远不能让产品变慢、变坏、变失败。

### US6.1 默认开启、三面可关（P0）

作为隐私敏感用户，我想明确知道采集开关在哪里、关了之后是否真的不发了。

验收：
- Given 全新安装首次启动，When 遥测初始化，Then 默认开启（首次启动时记录一次"首启"事件），采集内容仅限事件名与数值/枚举属性（见 US6.2），**不采集对话内容、代码内容、文件路径等业务数据**
- Given 用户想关闭遥测，When 查找开关，Then 至少三个面可关：①环境变量（优先级最高，覆盖一切）；②配置文件中的布尔开关；③网页设置页的开关（带"重启生效"提示）
- Given 用户已通过任一面关闭，When 程序运行，Then 不采集、不缓冲、不发送（见 US6.4）；再次打开后恢复采集

### US6.2 匿名身份（P0）

作为隐私敏感用户，我不想被遥测关联到个人身份。

验收：
- Given 遥测身份，When 建立，Then 只有两个匿名标识：设备标识（首次启动生成、本地持久保存、文件权限仅限本人）与会话标识（每次会话新生成）；不采集姓名、邮箱、IP 等个人身份信息
- Given 遥测事件的属性值，When 上报，Then 仅接受数值/字符串/布尔等基础类型（非基础类型丢弃），且每事件有全局唯一编号
- Given 上报请求，When 发送，Then 携带环境上下文（应用名/版本/运行时/平台/架构/系统版本/是否 CI/语言/终端/界面模式/模型名），用于问题归因

### US6.3 上报不阻塞产品（P0）

作为日常使用者，我不想因为遥测服务器不可用而感到任何异常。

验收：
- Given 事件产生，When 缓冲，Then 批量冲刷（默认攒 50 条或每 30 秒，先到先发），冲刷与发送均不阻塞任何用户操作
- Given 上报请求失败（含限流/服务端错误），When 重试，Then 按 1s/4s/16s 退避重试，仍失败则把整批事件落盘暂存，后续启动时在 7 天内自动重发；遥测失败**绝不**影响产品功能、绝不弹出错误
- Given 程序退出，When 收尾，Then 限时（默认 3 秒）冲刷，超时则落盘暂存后结束，不悬挂退出
- Given 上报请求发出，When 单次请求，Then 有请求超时（默认 10 秒），不长期占用
- Given 事件在缓冲中，When 遥测尚未初始化完成，Then 事件先入内存队列（上限 1000 条，溢出丢最旧），初始化完成后一并送出，不丢失启动早期事件

### US6.4 关闭即真关闭（P0）

作为隐私敏感用户/合规管理者，我想确认关闭后没有残留发送。

验收：
- Given 用户关闭遥测（任一面），When 关闭生效，Then 内存缓冲清空、周期冲刷停止、资源采样停止、不再发送任何请求
- Given 关闭后用户重新打开，When 开启，Then 采集恢复（不追溯补采关闭期间的事件——仅暂存重发机制针对的是"开启状态下发送失败"的事件）

### US6.5 采集内容诚实可查（P1）

作为合规管理者，我想有一份采集事件清单可供审计。

验收：
- Given 遥测开启，When 采集事件，Then 事件属于已登记的事件族（交互事件、回合事件、工具事件、会话生命周期事件、错误事件、崩溃事件、系统指标事件等），每事件有类型登记与属性说明；事件族清单与用途说明以文档形式可查（现状证据见 context §7）
- Given 某端（如浏览器端）不采集遥测，When 用户使用该端，Then 该端只有本地调试日志，不外发任何事件

## 8. Epic E7：崩溃与退出（P0）

### US7.1 崩溃留痕（P0）

作为排障者，我想任何崩溃都有记录，且崩溃本身不被上报过程掩盖。

验收：
- Given 进程发生未捕获异常或未处理的异步拒绝，When 崩溃处理介入，Then 上报崩溃事件（含错误类型、发生阶段、来源），**同步**冲刷后放行原始崩溃语义（该退几分退几分）；上报过程自身出错绝不掩盖原始异常
- Given 崩溃发生时进程处于不同生命周期阶段（启动中/运行中/退出中），When 上报，Then 事件标注所处阶段
- Given 异步拒绝属于正常的取消类信号（如请求中止），When 处理，Then 不计为崩溃
- Given 交互界面模式下进程内已有兜底异常处理，When 仍未捕获的异常发生，Then 走紧急退出：同步保全诊断日志、恢复终端状态（显示光标、退出修饰键模式），再退出

### US7.2 信号差异化处理（P0）

作为日常使用者/脚本编写者，我想 Ctrl+C、终止信号、挂断信号各有正确行为。

验收：
- Given 交互界面中按下 Ctrl+C，When 处理，Then 按键盘输入处理（非信号）：第一次取消进行中的工作，清空输入框；连按两次才退出
- Given 收到终止信号（SIGTERM），When 处理，Then 走优雅退出路径（完整清理后以约定退出码退出）
- Given 收到挂断信号（SIGHUP，如终端被关闭），When 处理，Then 走紧急退出（不做可能失败的用户交互式清理），避免写入已死的终端
- Given 一次性执行模式（脚本调用）收到任一终止信号，When 处理，Then 先执行清理（含遥测限时冲刷）再以对应约定的退出码退出（中断 130 / 终止 143 / 挂断 129，按系统惯例 128+信号编号）
- Given 本地服务模式收到终止信号，When 处理，Then 优雅关停服务（含尽力冲刷）

### US7.3 退出不悬挂（P0）

作为日常使用者/脚本编写者，我想退出命令永远真的退出。

验收：
- Given 正常退出（界面内触发退出或一次性执行完成），When 走退出路径，Then 依次完成：退出事件记录、遥测限时冲刷（3 秒）、会话关闭（引擎已持续落盘，退出无需专门"保存会话"）、终端状态恢复、按退出码结束
- Given 一次性执行模式输出量很大，When 进程退出，Then 先排空标准输出（上限 10 秒），排空后自然退出；若仍未退出，2 秒后强制结束
- Given 清理路径本身卡住（外部服务不响应等），When 超过整体清理时限（8 秒），Then 放弃剩余清理直接退出

## 9. 未来增强提案（超出 TS 现状，未立项实现）

> 以下为**提案**：TS 引擎今日**不支持**（或不完整）的能力，落地与否另行裁决，不构成对当前引擎的基线记录。与相邻域提案不重复（如网页端虚拟滚动已由对话渲染域提案 P1 覆盖，此处不再提）。

- **P1 交互界面内的遥测开关**：今日关闭遥测需改配置文件/设环境变量/去网页设置页，交互界面（TUI）内无开关命令。提案：提供界面内开关与状态查看。
- **P2 统一关闭环境变量名**：今日存在两个并存的关闭变量名（交互/一次性模式一套、本地服务模式另一套），拼写不一致。提案：统一为单一规范名并保留旧名兼容期。
- **P3 首帧事件与更细启动分解**：今日启动性能事件含四项分解，但无"首帧呈现"独立埋点，界面卡顿归因仍靠推断。提案：增加首帧事件与分阶段埋点。
- **P4 采集内容披露页**：今日事件族有类型登记但无面向用户的"我们采集了什么"披露界面。提案：设置页展示采集清单与样例数据。
- **P5 日志脱敏与采样**：今日日志内容不做敏感信息扫描或脱敏（日志可能包含用户操作细节）。提案：可选的敏感模式（如关闭 debug、对参数做脱敏）。
- **P6 模型请求可选超时上限**：今日模型请求无请求级强制超时，依赖"用户取消 + 自动重试"。提案：可配置的请求级超时上限作为逃生门（默认仍可不设）。
- **P7 流式缓冲背压上限**：今日模型流式分片的内部缓冲无容量上限（靠消费端反压）。提案：有界缓冲 + 溢出策略。
- **P8 已加载网页会话的渲染窗口化**：已由对话渲染域提案 P1（长会话界面窗口化）覆盖，本域仅登记依赖关系，不重复提案。
- **P9 内存上限与自我保护**：今日无进程内存上限或接近上限时的自我保护动作。提案：可配的内存水位告警与主动收缩（如触发压缩、释放缓存）。
- **P10 日志体系统一**：今日存在两代日志栈（旧引擎与新引擎各一套，环境变量前缀不同），双栈并存增加排障成本。提案：Rust 侧统一为一套日志体系与单一前缀。
- **P11 搜索程序下载期间的内置回退**：今日使用文件搜索类工具时若外部搜索程序缺失，下载需等待完成（有下载时限）后才能继续，下载等待期间不切换到内置实现（引擎内部的文件搜索则始终有内置回退）。提案：下载在后台进行、期间先用内置实现响应。

## 10. 决策记录（SDR）

### SDR-001：非功能性域建域与边界裁决

- **编号与日期**：SDR-001 · 2026-09-12
- **背景与动机**：各业务域文档内散落着非功能细节（压缩域的计量口径、渲染域的流式延迟、工具域的执行超时），但没有一份全局视图回答"启动多快、并发模型是什么、全局等什么、日志和遥测怎么运转"这类跨域问题；Rust 团队需要一份全局基线而非逐域拼图。
- **决策**：新建 non-functional 域四件套；本域只收**全局/跨域**基线（启动、资源、并发、超时重试全局契约、日志、遥测、崩溃上报、退出清理），各域内部非功能细节归各域，本文以 §5 索引表做唯一汇总、以链接引用不重复；TS 无现状支撑的维度按"未来增强提案"记录、不作为事实。
- **被否决的备选方案**：①把非功能需求并入每个业务域文档（否决：跨域视图缺失、数值口径漂移无汇总）；②单文件"全局 NFR 附录"（否决：违反治理四件套结构，且无法区分现状事实与终态需求）。
- **影响范围**：本文全部章节；相邻域文档无需回改（本文只引用）。
