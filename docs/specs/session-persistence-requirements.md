# 会话持久化与索引 — 需求文档

## 0. 角色定义

| 角色 | 场景 | 核心诉求 |
|---|---|---|
| **回访用户**（重开历史会话的人） | 关掉应用后重新打开、翻出旧会话继续聊 | 历史一条不少；打开够快；上次聊到哪就接着哪 |
| **跨端用户**（在多个入口使用同一工作区的人） | 在 IDE 里聊到一半，切到桌面版/网页版继续；在任意入口翻全部历史 | 任意入口产生的会话在其余入口可见可续；不因入口不同而"丢会话" |
| **浏览用户**（在列表里找会话的人） | 会话积累到几百上千条后翻列表、搜历史 | 列表不因数量增长而变慢；归档过的不再碍眼 |
| **双引擎用户**（TypeScript 与 Rust 两代内核共用一份数据的人） | 升级引擎、新旧版本交替使用 | 换引擎历史不丢；旧数据自动升级可读；不要求手工迁移 |
| **并发用户**（桌面端 + 终端 + 服务器同时使用的人） | 多个程序同时读写同一份会话数据 | 互不阻塞报错、永不互相损坏 |
| **排查者**（人工检查数据文件的人） | 数据异常时打开数据目录定位问题 | 目录结构按工作区分明可猜；单条会话独立成目录可直接拷走 |

## 1. Epic N1：崩溃与断电安全（P0）

> 解决"半路断掉不丢不烂"。任何时刻断电或强杀，重开后数据要么完整、要么按既定规则降级，绝不因半份文件卡死整个产品。

### US1.1 元数据写入原子性（P0）

作为回访用户，我想让会话的名称、标签、归档状态等元数据在任意时刻断电后仍然完整，以便不会出现"改名改了一半"的烂数据。

验收：
- Given 会话元数据正在写入，When 进程在写入中途被强杀，Then 重开后该会话元数据要么是写入前的完整旧值、要么是写入后的完整新值，**不存在**半新半旧的中间态
- Given 断电残留了临时文件，When 重开后浏览，Then 临时文件不影响任何会话的正常读取（不可见的垃圾，不是可见的损坏）

### US1.2 损坏数据不阻断启动（P0）

作为回访用户，我想让个别损坏的会话数据不阻塞整个产品启动和其他会话的使用，以便单点损坏不做全局灾难。

验收：
- Given 某个会话的元数据文件损坏，When 打开应用并列出会话，Then 其他会话正常列出；损坏会话不出现在列表中（宁缺毋滥），且有可查的告警记录
- Given 某个会话的元数据文件损坏，When 直接恢复该会话，Then 恢复不被损坏卡死：按无名称的缺省会话处理并继续，产品不崩
- Given 损坏的只是某个会话，When 进行其他会话操作，Then 一切正常

### US1.3 创建失败不留半成品（P0）

作为任意用户，我想让新建或复制会话中途失败时自动清理回滚，以便列表和磁盘上不出现"残缺会话"。

验收：
- Given 新建会话在写入中途失败，When 查看列表与数据目录，Then 无半成品会话目录残留、列表无残缺条目
- Given 复制会话（见会话管理域 E5）在拷贝源数据中途失败，Then 同样回滚干净（已创建的目标目录被清理，源会话不受影响）

## 2. Epic N2：恢复速度（P0）

> 解决"重开要等"。关掉的会话是"收起来"而不是"销毁"——重开是常态操作，必须快。

### US2.1 会话重开时长稳定（P0）

作为回访用户，我想让重开一个聊了很久的会话也保持秒级等待，以便长会话不值得被抛弃重开。

验收：
- Given 一个已结束的长会话（对话轮次很多），When 重开，Then 只需处理自上次收起以来的增量内容，而不是从头重算整个历史
- Given 重开时增量记录已收纳完整，Then 用户看到的对话历史与收起前一字不差（收起 = 冻结检查点）
- Given 收起时检查点没能保存成功，When 重开，Then 自动回退为从头处理并仍然完整恢复（慢一点，但绝不缺内容）
- Given 无检查点的长会话（走了从头处理分支），When 重开，Then 从头处理本身也有时长与内存上限——完成时间与内存占用不随历史长度超线性增长、不随子代理数量线性膨胀（SDR-005）
- Given 一个含大量子代理的长会话（子代理记录总量远大于主对话记录），When 重开，Then 就绪只等待主对话记录的处理；子代理记录不读入内存，其上下文在被继续使用（续作/查看）时按需重建且记忆完整——重开瞬间不因任何一个子代理而多等（SDR-005 / 架构 ADR-006 懒重放）

## 3. Epic N3：浏览性能（P0）

> 解决"会话多了翻不动"。列表与计数是界面的热路径（搜索的**检索需求**——搜什么、结果排序、归档可见性——不属本域，见 §12 非目标；本域只承诺搜索读取的数据路径享受同样的性能与自愈保证），数据量增长不能转化为等待。

### US3.1 会话列表速度与数量解耦（P0）

作为浏览用户，我想让会话列表的打开速度不随历史会话总数明显变慢，以便敢于长期积累历史。

验收：
- Given 已积累大量历史会话，When 打开会话列表，Then 每行信息从一份"已经备好的清单"读取，而不是逐个打开每条会话的文件现场拼装
- Given 清单中没有某条会话（冷启动），When 列表需要它，Then 当场从文件补齐一次并收入清单（下次不再现场拼装），列表结果与现场拼装完全一致
- Given 会话元数据发生变更（改名、归档、收起），When 再次浏览列表，Then 清单已同步更新，读到的就是新值

## 4. Epic N4：多进程并发（P1）

> 解决"几个程序一份数据"。桌面端、终端、开发服务器共用同一份个人数据目录是真实场景。

### US4.1 并发共存不阻塞不损坏（P1）

作为并发用户，我想让多个程序同时使用同一份会话数据，以便不需要"先关掉一个再开另一个"。

验收：
- Given 一个程序正在写会话数据，When 另一个程序同时读取，Then 读取不被阻塞，且读到的是某个一致的完整版本（可能是稍旧，但绝不半新）
- Given 两个程序几乎同时写，Then 后到者在短暂等待后完成，而不是直接报错
- Given 多程序并发长期运行，When 事后校验数据，Then 无任何损坏

## 5. Epic N5：跨引擎兼容（P0）

> 解决"换引擎不丢历史"。两代内核在过渡期共用磁盘数据，用户感知不到"迁移"这件事。

### US5.1 新引擎读旧数据（P0）

作为双引擎用户，我想让新版内核直接读出旧版内核写下的全部历史会话，以便升级无需任何手工操作。

验收：
- Given 旧版内核写下的历史会话数据，When 用新版内核打开，Then 全部历史会话可见、可恢复、可继续
- Given 旧版记录格式与新版有差异，When 新版读取，Then 按既定规则自动转换，转换对用户不可见
- Given 新版在恢复会话时完成了自动转换，When 之后再次读取，Then 使用转换后的新格式（一次成本，不反复付）

### US5.2 超前版本容忍（P1）

作为双引擎用户，我想让旧版内核遇到新版内核写下的数据时不损坏它，以便新旧版本可以回退交替使用。

验收：
- Given 数据由更新版本的内核写下，When 旧版内核读取，Then 尽力原样理解并恢复，**不删除、不改写**它不认识的部分
- Given 旧版读取后继续使用该会话，Then 不认识的部分对旧版功能无破坏性影响

### US5.3 布局组织的一致性（P0）

作为双引擎用户 + 排查者，我想让两代内核把会话按同样的目录结构组织，以便数据目录只有一种读法、备份和排查不用区分引擎。

验收：
- Given 任一内核新建会话，When 查看数据目录，Then 会话按其所属工作区归入同名目录（见 [glossary.md](glossary.md) S3 工作区桶）
- Given 历史上遗留了未按工作区归置的旧会话，When 新版内核启动，Then 自动将其归置到所属工作区目录下（归置不改变会话内容；归属不明的归入当前工作区并补记归属）
- Given 归置目标位置已有同名会话，When 归置，Then 跳过该会话并记录告警（**绝不覆盖**既有数据）
- Given 归置过程被中断，When 下次启动再次归置，Then 从中断处继续（可重复执行，结果一致）

## 6. Epic N6：归档的可逆性（P0）

> 解决"收起来 ≠ 删掉"。归档是收纳：离开默认视野、随时取回；归档的承诺必须与真实存储一致。

### US6.1 归档离开默认视野（P0）

作为浏览用户，我想归档一个会话后它就从日常列表消失，以便列表只剩"我还在用的"。

验收：
- Given 任意会话（正在进行的或已结束的），When 我执行归档，Then 操作成功，且该会话此后不出现在默认列表中
- Given 归档刚完成时界面对该会话仍有在途的内容拉取，When 拉取的回答是「会话不存在」（无论来自哪条通道、哪种编码形态），Then 界面安静移除该会话并落到下一个会话——不弹出「无法加载」类错误提示（识别以语义为准，见会话管理域 SDR-015）
- Given 一个已经结束、当前并未打开的会话，When 我在列表里对它执行归档，Then **同样成功**（不因"它没开着"而报错或提示失败——对已收起的会话归档是合法操作）
- Given 归档完成后的列表刷新，Then 归档会话不可见，其他会话的顺序与内容不受影响
- **执行位置**：默认列表排除归档会话在**数据读取层**执行——界面隐藏不是合格实现；绕过界面直接查询列表同样看不到归档会话（除非显式要求包含）

### US6.2 归档可恢复（P0）

作为回访用户，我想从归档中取回任意会话继续使用，以便"收起来"不等于"找不回"。

验收：
- Given 一个已归档的会话，When 我执行恢复，Then 会话回到可用状态且此后重新出现在默认列表中
- Given 归档前会话有历史对话，When 恢复并打开，Then 历史完整保留
- Given 恢复完成，When 再归档，Then 可再次收纳（归档↔恢复可无限次往返，结果一致）

### US6.3 归档状态跨重开保持（P0）

作为浏览用户，我想让归档状态在应用重启后依然生效，以便不需要每次重新归档。

验收：
- Given 会话已归档，When 应用重启后查看默认列表，Then 该会话依然不在其中
- Given 显式要求查看归档会话，When 查询，Then 归档会话可被列出且带归档标记

## 7. Epic N7：索引的可信性（P0）

> 解决"清单 ≠ 数据"。为速度准备的"备好清单"（见 [glossary.md](glossary.md) S4 会话索引）只是缓存——它坏了、旧了、被删了，都不能骗用户。

### US7.1 索引可丢弃（P0）

作为并发用户/排查者，我想让性能清单可以随时整体删除而不损失任何数据，以便它永远只是"缓存"而不是"第二份事实"。

验收：
- Given 索引文件被整体删除，When 重启应用，Then 全部历史会话照常可见可恢复（首次浏览稍慢），无任何数据丢失
- Given 索引丢失后的首次浏览，Then 每条会话信息从磁盘原始数据补齐并重建清单

### US7.2 索引与磁盘不一致时以磁盘为准（P0）

作为任意用户，我想让清单与真实数据出现不一致时自动以真实数据为准并自愈，以便清单永远不会"骗"我。

验收：
- Given 索引中某条会话的信息落后于磁盘真实状态，When 浏览，Then 显示磁盘真实值，且索引被自动修正
- Given 磁盘上某会话已被删除（例如人工清理），When 浏览，Then 该会话不再出现，索引中的残留记录被自动清除
- Given 索引写失败，When 执行会话操作，Then 操作本身照常成功（索引只是尽力而为，绝不让缓存故障升级为用户可见的失败）

## 8. Epic N8：删除的完备性（P1）

> 解决"删就删干净"。删除是唯一不可逆操作，必须一次做全。

### US8.1 删除即彻底（P1）

作为浏览用户，我想删除一个会话时它的全部数据一并清除，以便没有"删了还剩尾巴"的困惑。

验收：
- Given 删除一个会话，Then 其全部存储一并清除：对话记录（含各身份记录流）、元数据、检查点、索引条目，以及**会话附加物**——用户在该会话设置的定时任务、挂在该会话的后台任务输出（见 SDR-001）；**附件本体除外**——它是全局共享资产，删除会话只消除引用，本体交由引用感知回收裁决（SDR-003 / ADR-007）
- Given 删除后再浏览/搜索/查询，Then 该会话任何形态都不再出现（定时任务不再触发）
- Given 删除一个不存在的会话，Then 静默成功（删除是幂等的，不报"未找到"错误）

## 9. Epic N9：标识与目录安全（P1）

> 解决"看不见的入口不能成为暗门"。会话标识直达文件系统，必须是受控面。

### US9.1 会话标识合法性强制（P0）

作为任意用户，我想让会话标识在进入存储层之前被强制校验，以便外部输入不可能构造出越出会话数据根的路径。

验收：
- **执行位置**：校验发生在会话目录路径计算之前（存储层入口），界面层过滤不是合格实现——绕过界面直接调用创建/派生接口，携带含路径分隔符、`..` 等成分的标识同样被拒绝并报错
- Given 引擎自己生成的会话标识，Then 天然合法（生成器只产安全字符集）
- Given 校验拒绝，Then 拒绝不产生任何磁盘副作用（无目录创建）

### US9.2 数据目录权限收紧（P2）

作为排查者，我想让会话数据目录的权限收紧为仅本人可读写，以便多用户机器上会话内容不暴露。

验收：
- Given 会话数据目录被创建，Then 其权限为仅属主可读写（平台不支持时降级并记录，不阻断功能）

## 10. Epic N10：会话标题的自动派生与用户命名（P0）

> 解决"列表里新会话有意义的名字从哪来"。这是两代 TS 引擎均已落地、此前需求文档未披露的基线能力（2026-09-12 补录，现状事实见 context §2/§3-7）；Rust 内核已对齐实现。

### US10.1 首条消息自动命名（P0）

作为发起会话的用户，我想让一个还没命名的会话在我发出第一条消息后自动获得一个可辨识的标题，以便在会话列表里一眼找到它，而不是面对一排"新会话"。

验收：
- **触发条件**：仅当会话当前标题仍是"未命名态"（空、空白、或引擎的缺省占位名）**且**未被用户命名过（用户命名标记为假）时才自动命名；两个条件任一不满足，发送消息不改动标题
- Given 用户在未命名会话中发出第一条文本消息，Then 标题被替换为该消息文本派生的标题，并广播元数据更新事件（含新标题、用户命名标记、最近输入）
- Given 消息文本中含图片/音频/视频附件，Then 附件以占位词（如 `[image]`）参与标题；仅附件无文本时若派生结果为空则不命名
- **派生规则**：控制字符与连续空白折叠为单空格；疑似密钥的内容（私钥块、Bearer 凭据、键值对形态的密钥、`sk-` 前缀长随机串、超长 base64 形态 token）替换为脱敏占位；裁剪至固定长度上限（当前 200 字符）；派生结果为空则不命名
- Given 消息文本本身就是一段密钥，Then 自动命名后标题中不含密钥明文（脱敏占位可见），不泄漏到列表与索引

### US10.2 用户命名后不再被自动覆盖（P0）

作为给会话改过名的用户，我想让我的命名在后续任何消息发送后都保持不变，以便命名权在我手里、引擎不"帮倒忙"。

验收：
- Given 用户已显式命名（改名接口）该会话，Then 之后任何消息发送都不再自动改名（用户命名标记为真，持久化于元数据）
- Given 用户命名时只清空标题（不提供新标题），Then 旧标题保留、标记保留（改名接口只在提供了非空标题时改写标题与标记）
- Given 元数据经断电/重启恢复，Then 标题与用户命名标记成对恢复——被命名过的会话恢复后仍是"已命名"态

### US10.3 自动命名不侵入用户数据（P1）

作为用户，我想让自动命名只改元数据、不改对话历史，以便标题生成永远不会破坏消息本体。

验收：
- Given 自动命名发生，Then 只有元数据文件与元数据更新事件受影响；对话记录与重放语义不变（标题是元数据投影，不是消息）
- Given 客户端在本地也做标题推导（离线显示），Then 本地推导不得写入用户命名标记（否则会抑制引擎的自动命名——本地推导只读展示）

## 11. Epic N11：跨入口会话可见性（P0，SDR-009）

> 解决"入口不同 ≠ 会话失踪"。IDE 集成入口（ACP）产生的会话沉淀到个人数据目录，桌面版/网页版都能看到、能继续。

### US11.1 桌面/网页列表可见 IDE 会话（P0）

作为跨端用户，我想在 IDE 入口产生的会话出现在桌面版/网页版的会话列表里，以便"在 IDE 里聊到一半，切到桌面版继续"不需要任何搬运操作。

验收：
- 假如我在 IDE 入口的某工作区产生了会话（有过对话），当我在桌面版/网页版打开同一工作区的会话列表，那么该会话可见，且归属正确的工作区（不是孤立出现，也不是混入别的工作区）
- 假如该会话此后在 IDE 里继续推进，当我用桌面版/网页版再次查看列表，那么"最近活跃"如实体现在 IDE 侧的最后写入时刻
- 假如多个 IDE 入口会话共存，当我浏览桌面版/网页版列表，那么各会话独立成条、互不串内容（同一工作区并发入口的数据一致性由会话一致性域管辖，本条只承诺可见）

### US11.2 IDE 会话跨端可续作（P0）

作为跨端用户，我想把 IDE 入口里聊到一半的会话在桌面版/网页版里原样继续，以便深度编码在 IDE、审查整理在桌面，动线自由切换。

验收：
- 假如是一个 IDE 入口产生的会话，当我在桌面版/网页版打开（恢复），那么历史完整——主对话与各身份记录流一并恢复，"上次聊到哪就接着哪"与同入口续作无差别
- 假如桌面版/网页版续作后产生了新内容，当我之后再次从 IDE 入口续作同一会话，那么同样完整恢复续作（可见性对称，不挑方向）

### US11.3 数据归一沉淀（P0）

作为跨端用户，我想让 IDE 入口的会话与桌面版/网页版的会话沉淀在同一个地方、按同样的结构组织，以便备份、清理和排查不需要区分"会话是哪个入口开的"。

验收：
- 假如个人数据目录可正常解析，当任一入口新建会话，那么会话落在统一的存储根、按其所属工作区归入同一目录结构（一种读法，无需按入口区分）
- 假如任一入口产生了会话，当我浏览/搜索/归档/删除，那么与其他入口产生的会话享受同一套列表、索引与生命周期语义（含"从未对话不落盘"——SDR-004 对 IDE 入口同样成立）

### US11.4 IDE 宿主列表保持以项目为中心（P1）

作为 IDE 入口的用户，我想让 IDE 内的会话列表仍以当前项目为中心，以便多项目混用时 IDE 的列表不被无关工作区干扰。

验收：
- 假如 IDE 入口以某项目目录启动，当我用 IDE 查看其会话列表，那么仍以该项目工作区为中心（其余注册工作区不进入默认可见列表）
- **执行位置**：列表钉扎在数据读取侧执行（IDE 宿主查询列表即得钉扎结果），不是界面层的展示过滤

## 12. 非目标（明确不做）

- **不做**云端同步/多机共享——本域只管本机磁盘数据的持久化
- **不做**会话内容级加密——密钥管理属安全域
- **不做**搜索的检索需求定义——搜什么、结果怎么排、归档会话是否出现在搜索结果，属"会话列表查询契约"的扩展（挂会话管理域 ROADMAP 开放项，待评审；当前行为：搜索包含归档会话）
- **不做**列表交互功能（置顶、拖拽排序、复制与派生）的需求定义——属"会话管理"域（其 E5 已立项），本域只保证为其提供可承载的存储契约
- **不做**多个入口同时打开同一会话的并发协调（运行状态互见、并发写拦截、实时跟随）——属"会话一致性"域；本域 N11 只承诺存储与列表层面的可见可续
- **不做**IDE 内会话列表的呈现与交互——IDE 宿主列表以项目为中心（US11.4 只钉住数据读取侧的可见范围）；IDE 界面自身如何组织列表由 IDE 客户端决定

## 13. 决策记录（SDR）

### SDR-009 IDE 入口会话沉淀个人数据目录：写共享、读钉扎（Epic N11，2026-10-28）

- **背景与动机**：IDE 集成入口（ACP 宿主）独立启动、随 IDE 会话生灭，其产生的会话曾落在了工作区本地的存储形态里——对用户的体感是"在 IDE 里聊了一半，桌面版/网页版翻不到这条会话"，近似数据丢失。用户对产品的感知是"一个产品、多个入口"，而不是"几个进程、几份数据"；"在 IDE 里聊到一半、切桌面版继续"是真实高频动线。此前这一跨端语义从未被任何裁决显式覆盖，属语义空洞，本次裁决补齐。IDE 宿主自身的列表以项目为中心是有意设计（工作区管理域 US5.3 宿主钉扎——多项目混用时 IDE 列表不被无关工作区污染），该钉扎只涉**读面可见范围**，与**会话存储归属**正交，本裁决不动它。
- **决策**：IDE 入口（ACP 宿主）产生的会话**沉淀到个人数据目录**（与桌面版/网页版同一存储根、同一目录组织、同一索引），桌面版/网页版对它可见可续，且对称（桌面/网页产生、IDE 续作同样成立）。归纳为**写共享、读钉扎**：写入侧各入口同根同构（US11.3）；IDE 宿主自己的列表读取侧保持以宿主根为中心的钉扎（US11.4，即既有宿主钉扎语义不变）。用户裁决记录：2026-10-28 会话裁决"统一可见"（分析见本条背景）。
- **否决的替代**：维持现状 + 文档化（成本最低，但"翻不到会话"的体感问题原封不动，且工作区本地会话成为不可归档、不可续作的存储死角）；IDE 入口默认连接常驻服务进程（语义最彻底，但要求 IDE 场景必须先有一个常驻服务在跑，破坏 ACP 作为独立子进程的即开即用性，对不装桌面版的纯 IDE 用户是倒退）。
- **影响面**：新增 Epic N11（US11.1–11.4）；架构 ADR-019（IDE 宿主注入个人数据目录的技术形状）；非目标新增两条（并发协调归会话一致性域、IDE 列表呈现归 IDE 客户端）；存量工作区本地的 ACP 会话目前**无晋升入个人数据目录的既有路径**（既有迁移命令只覆盖 legacy 目录形态），需为其新增显式迁移路径（是否纳入实现批随 ROADMAP 排期裁决）；角色表新增"跨端用户"。

- **修订记录**（2026-10-28，R1）：本 SDR 与架构 ADR-019 否决项中"远程模式非默认"的裁决，经设计文档 [rust-core-design/14-acp-desktop-runtime-sharing.md](../rust-core-design/14-acp-desktop-runtime-sharing.md) 在探测 + 回退新前提下重开（详见 ADR-019 修订记录）。**US11.4 执行位置增补**：远程模式下（IDE 入口复用桌面版引擎时），列表钉扎由 ACP 宿主的读取过滤承载（数据读取后、呈现给 IDE 前过滤）——仍属"数据读取侧执行"，非界面层展示过滤。

### SDR-008 界面对「会话不存在」的识别以语义为准（跨域承载，2026-10-25）

- **背景与动机**：会话被归档（本域 N6）或删除（本域 N8）后，引擎对后续读面请求如实回答「不存在」。界面若只认得一种通道形态下的「不存在」编码，同一语义在其他通道形态下会被误判为故障——用户在归档刚完成时收到「无法加载当前会话」的吓人提示，而正确行为是安静移除并切换。语义裁决与完整记录见会话管理域 SDR-015（本域按其影响面登记）。
- **决策**：本域 US6.1 增补一条验收：归档刚完成时界面在途的内容拉取收到「会话不存在」回答，界面安静移除该会话并落到下一个会话，不弹「无法加载」类错误提示（识别按语义而非单一编码形态）。
- **否决的替代**：引擎侧为快照读取增设专用错误码（迁就界面识别缺口、徒增契约面积）——详见会话管理域 SDR-015 的否决记录。
- **影响面**：US6.1（验收增补）；删除场景（US8.1）的界面侧消费同享该识别路径。

### SDR-005 从头处理的有界性与子代理记录不预载（US2.1 扩展，2026-10-15）

- **背景与动机**：用户报告重开大/多子代理会话需秒级以上等待，且恢复瞬间进程内存出现数十 GB 量级的瞬时尖峰（实测证据与根因分析见调查报告 `docs/specs/reports/rust-v3-session-cold-open-perf-20261015.md`，现状代码事实见 context §9）。两个事实超出 US2.1 原有验收的覆盖：① 检查点缺失走"从头处理"降级分支时，从头处理本身没有时长/内存上限——处理成本随历史长度超线性增长；② 恢复把**全部**子代理记录读入内存重建上下文，而重开后被继续使用的子代理占比极低——主对话记录已含委派内容与子代理最终结果，主对话上下文自洽。
- **决策**：① 从头处理分支的时长与内存占用必须有界——随历史长度线性、随子代理数量不膨胀（实现形状见架构 ADR-017）；② 子代理记录遵循架构 ADR-006 已裁决的懒重放——会话就绪只等待主对话记录，子代理上下文在续作/查看时按需重建，重建结果记忆完整（区别于被否决的"永不重建"）；③ 主对话处理结果在一次重开内不重复计算（多次消费同一记录流的场景共享一次处理）。量化验收锚点：修复后对实测基准会话（数千条操作、数十个子代理）的冷重开在亚秒级完成、恢复期间进程峰值内存不超过数百 MB 量级（实测口径见本域 ROADMAP 开放项 14）。
- **否决的替代**：子代理上下文永不重建、仅登记名单（被唤醒的子代理失去记忆，产出不可信——静默错误比慢更糟）；重开时后台并行预热全部子代理上下文（内存峰值随子代理数量同步膨胀，违背②的资源有界初衷）；仅靠提高检查点写入频率（不解决检查点缺失的降级分支，且子代理记录不在检查点覆盖内）。
- **影响面**：US2.1（验收扩展）；架构 ADR-006（恢复时序的执行遵从）、ADR-017（新增）；非功能域 E2（长会话资源有界的存储侧支撑）；子代理域 §3.2.1（恢复时序措辞对齐，非语义变更）。

### SDR-001 定时任务与后台任务是会话资产

- **背景与动机**：一个会话夹带的数据不止对话本身——用户设置的定时任务、挂在会话上的后台任务都有独立持久化。参照引擎对二者的处理自相矛盾：删除会话不带走定时任务、复制会话却复制它——同一资产在两个操作里归属不一致。
- **决策**：定时任务与后台任务输出是**会话资产**——删除会话时级联清除（定时任务不再触发）；归属由会话目录边界承载（任务输出与会话级定时记录都落在会话目录内）。~~复制会话时随包带走~~（**复制条款已被 SDR-002 取代**——fork 不携带定时任务，语义裁决归会话管理域 SDR-007）。
- **否决的替代**：定时任务归工作区层（删除不级联——与"删就删干净"冲突，且留下孤儿定时器继续触发的惊讶行为）；~~复制时丢弃定时任务（用户设置的提醒静默消失，不可预期）~~（此反对理由随 SDR-002 失效——产品裁决为"运行中状态不带过 fork"，提醒是否重建由用户在新会话自行决定，非静默丢失语义）。
- **影响面**：US8.1（删除级联——不变）；会话管理域 E5（复制语义——见其 SDR-007）；跨引擎差距见 context（参照引擎的矛盾形态）。

### SDR-002 fork 不携带定时任务（复制条款修订）

- **背景与动机**：SDR-001 的"复制随包"条款使 fork 后源会话与分叉会话各持一份相同的定时任务，两边开着时同一条提醒各触发一次（双跑），且执行时刻快照语义会把分叉点之后创建的提醒带进新方向。会话管理域对此做了产品裁决（其 SDR-007：复制"已完成"、重置"运行中"），本域跟进修订对应条款。
- **决策**：复制会话**不携带**任何定时任务与后台任务；删除会话的级联清除不变（SDR-001 剩余部分）。定时任务的归属载体不变——仍是会话资产，删除即级联。
- **否决的替代**：维持随包（双跑 + 分叉方向污染，即被取代的现状）；复制后源会话任务暂停（悄悄改动源会话，且引入会话暂停态概念）。
- **影响面**：SDR-001（复制条款取代）；会话管理域 US5.1/US5.4（引用本修订）；引擎对齐工作见该域 ROADMAP。

### SDR-003 附件本体不参与删除级联（全局共享资产）

- **背景与动机**：三套实现（TS v1/v2、Rust）现状把附件本体存在会话域内（agent/会话目录下的 blobs），fork 被迫复制本体、删除会话可能误伤分叉会话仍在引用的附件（事实见 context §7）。架构裁决（ADR-007）将其上移为全局内容寻址存储，本域跟进修订删除语义。
- **决策**：附件本体是**全局共享资产**——删除会话只消除该会话记录中的引用，**不**连带清理本体；无引用的孤儿附件由延迟且引用感知的回收机制清除（回收前保留缓冲，含 30 天老化窗口的溢出文件）。"删除即彻底"面向用户可见形态成立：删除后该会话任何形态不再出现（US8.1 不变），共享本体是否可回收由全局引用裁决。
- **否决的替代**：删除时即时引用计数（恢复/分叉等异步引用者无法在删除时刻枚举，误删风险高）；附件本体随会话级联删除（分叉会话引用悬空，"分叉会话里的图挂了"）。
- **影响面**：US8.1（级联范围排除附件本体）；ADR-007；会话管理域 US5.1（附件共享条款）。

### SDR-004 从未对话的会话不落盘（惰性物理创建 + lastPrompt 语义）
- **背景与动机**：参照引擎在会话创建时立即物化会话目录并写入索引（`sessionLifecycleService.ts:203-234`）——用户只是开了个新对话还没说话，磁盘上就多出一个空会话目录与索引行；列表侧因此需要"排除空会话"过滤来自我修复。与其事后过滤，不如一开始就不产生。
- **决策**：① 从未对话的会话**不产生物理会话目录与索引行**（仅存在于进程内存），**首条用户消息发出时**才物化；② "空会话"判定（`lastPrompt`）= **最近一条用户输入，无论成败**——"从未对话"才是空，"对话失败"不是空（失败会话对用户有回顾价值）。存量与跨引擎数据中的空会话仍按此判定过滤，过滤能力保留。
- **影响面**：US1.3（物化时机后移，"创建失败不留半成品"语义不变）；工作区管理域 exclude_empty 过滤——原生新会话不再产生空目录，过滤保留服务存量/TS 兼容桶（其 plans/08 W5 随本裁决落地，跨域登记已互引）。
