# 事件投递 — 需求文档

> 状态：v1.0 · 2026-10-23 · 新建域，首版裁决见决策记录 SDR-001/002/003（「使用」口径的裁决主属会话管理域 SDR-014，本域引用）
> 本文是事件投递域（event-delivery）需求侧的唯一事实源（内部规格文档，不进文档站构建，中文单语）。
> 配套文档：技术形状见 [event-delivery-architecture.md](event-delivery-architecture.md)；现状盘点见 [event-delivery-context.md](event-delivery-context.md)；执行状态见 [event-delivery-ROADMAP.md](event-delivery-ROADMAP.md)。
> 范围边界：本域覆盖**引擎事件到达界面后的投递分级、界面状态更新与渲染效率**；会话列表的组织交互（置顶/拖拽排序、「使用」口径的裁决）属会话管理域（[session-management-requirements.md](session-management-requirements.md)）——本域引用其裁决，不重复裁决；对话内容的流式呈现语义属对话渲染域（[conversation-rendering-requirements.md](conversation-rendering-requirements.md)）。

## 0. 角色定义

| 角色 | 场景 | 核心诉求 |
|---|---|---|
| **多任务操作者**（同时开多个主任务的用户） | 同时跑多个任务、各任务可能带子代理 | 我在看的那个流畅；其他跑着的别拖累它；需要我时一定叫得到我 |
| **旁观者**（盯着列表看全局的用户） | 一眼扫过会话列表 | 行的位置稳定别乱跳；跑着/结束了/等我一眼可辨 |
| **轻量设备用户**（笔记本/低配机用户） | 长会话、多会话并行 | 界面不卡、风扇不狂转（渲染工作量有界） |

## 1. Epic E1：事件按需分级投递（P0）

> 解决"喂给界面的信息量应该由界面此刻在做什么决定，而不是由连接方式决定"。

### US1.1 正在看的会话给全量（P0）

作为多任务操作者，我想当前打开的会话给完整实时流（打字机、工具调用进展、子代理动态），以便我盯着看的任务体验无损。

验收：
- Given 我打开会话 A（正在运行），When 其回合进行中，Then 文本/思考流式、工具调用生命周期、子代理进展实时呈现，与单会话独占时体验一致
- Given 我从会话 A 切到会话 B，When A 仍在运行，Then A 的实时流停止投递、B 开始全量投递；切回 A 时从切换点无缝续接（已完成内容已按对话渲染域的快照+重放契约恢复，不缺不重）

### US1.2 没在看的会话只给状态摘要（P0）

作为多任务操作者，我想没打开的运行中会话只推送状态变化（开始跑/跑完了/失败了/在等我），以便几十个会话并行也不产生流式开销。

验收：
- Given 我没打开会话 C（正在运行，含多个子代理），When C 的回合流式输出进行中，Then 我这边**不收到** C 的文本增量、思考增量、工具进度帧；只收到状态迁移通知
- Given C 的回合结束，When 结束帧到达，Then C 的列表行状态更新为对应结局
- Given 我打开 C，When 订阅建立，Then C 从服务端权威快照重建完整视图（含切换期间完成的对话，恢复语义对齐对话渲染域 US3.1，不缺不重）

### US1.3 需要我决策的事一定叫得到我（P0）

作为多任务操作者，我想任何会话出现待审批/待回答时，无论我当前在看哪个会话、甚至刚刷新过页面，都能及时收到明确提示，以便多任务不会被默默卡死。

验收：
- Given 任意会话（打开或没打开）挂起审批或提问，When 挂起发生，Then 我的界面收到主动通知（不依赖我恰好订阅/恰好刷新该会话），且列表行呈现"等我"状态
- Given 我正在看会话 A，When 会话 B 挂起审批，Then B 的到达提示只伴随状态变化（B 的内容流级事件本就不投递给我，提示到达不带来额外渲染负担——SDR-001 的推论）
- Given 我刷新页面，When 有会话仍在等我决策，Then 刷新后提示与"等我"状态如实恢复（对齐会话管理域 US4.4 的刷新保真）
- Given 挂起解除（我或另一端处理了），When 解除发生，Then 提示与状态同步熄灭
- Given 我收到"会话 B 等我审批"的提示，When 我点击该提示（或"等我"徽章所在行），Then 界面打开会话 B 并定位到待审批视图

### US1.4 新会话/新工作区全局可感知（P1）

作为旁观者，我想任何地方新建/删除会话或工作区时我的列表立即反映，以便列表永远与事实一致。

验收：
- Given 任意来源（另一个客户端、定时任务、后台）新建会话，When 创建完成，Then 我的列表出现该会话（按会话管理域 SDR-002 插入普通区顶部）
- Given 会话被删除/归档，When 操作完成，Then 我的列表同步移除/隐藏

## 2. Epic E2：列表行的稳定呈现（P0）

> 解决"位置和状态是两件事"——状态可以高频变，位置不能跟着变。「使用」的口径裁决（什么事件改变位置）主属会话管理域 SDR-014，本域消费该口径并约束其执行面的呈现细节。

### US2.1 行位置只随使用事件变化（P0）

作为旁观者，我想会话行的位置只在明确的排序事件时变化，以便我凭记忆的位置点中它。

验收：
- Given 会话 A 排在列表第 N 位且正在运行，When A 持续输出内容（回合内任何事件），Then A 的位置保持第 N 位不动
- Given 会话 A 在运行，When 其标题被系统自动更新（如自动命名），Then A 的位置不动（维护性更新不算使用，会话管理域 SDR-004）
- Given 会话 A 的回合结束，When 结束帧到达，Then A 的位置不动（回合结束不是"使用"，SDR-014）
- Given 我主动打开会话 A 或在其中发送消息，When 交互完成，Then A 按"最近使用"规则升到普通区顶部（用户交互才算使用，口径 = 会话管理域 SDR-014 的两项清单）
- Given 新会话创建，When 首次出现在列表，Then 插入普通区顶部（会话管理域 SDR-002）

### US2.2 运行状态用徽章而非位置表达（P0）

作为旁观者，我想每行的"运行中/已完成/失败/等我"用行内标记表达且实时准确，以便扫一眼即知全局。

验收：
- Given 多个会话并行运行，When 状态迁移发生，Then 对应行的徽章即时更新（转圈/结束/失败/等我），行位置不动
- Given 我刷新页面，When 之前的运行状态恢复，Then 徽章如实恢复（口径 = 主对话回合未收尾，对齐会话管理域 US4.4）
- Given 徽章状态迁移，When 同帧内有多个会话同时迁移，Then 各行独立更新，互不干扰

### US2.3 状态更新的开销与列表规模无关（P1）

作为轻量设备用户，我想列表有几百个会话时，一次状态迁移只影响那一行的呈现，以便列表不成为性能瓶颈。

验收：
- Given 列表有 N 个会话、M 个在运行，When 一个运行中会话产生回合内事件（状态不变），Then 列表侧不产生任何列表行的重新渲染（内部度量：状态不变的事件触发的列表行渲染次数 = 0——该内度量为验收代理，消费者判据是长列表滚动与悬停无可感知卡顿）

## 3. Epic E3：渲染开销有界（P0）

> 解决"看了的会话也不该无限烧 CPU"。

### US3.1 后台会话的事件不打扰前台会话（P0）

作为多任务操作者，我想正在看的会话的渲染节奏只由它自己的内容驱动，以便其他会话的活动不影响我看到的流畅度。

验收：
- Given 我在看会话 A，会话 B/C/D 在后台运行，When B/C/D 产生大量事件，Then A 的对话面板重渲染次数不增加（B/C/D 的状态事件只更新列表行徽章，不触发对话面板的重算）
- Given B/C/D 各自有子代理在流式输出，When 这些输出持续到达，Then A 的面板无可感知卡顿（验收协议：在"4 个后台会话各带 2 个流式子代理"的固定场景下做交互测试——在 A 中连续滚动与点按 20 次，全部交互响应无掉帧感知；该协议作为回归脚本固化）

### US3.2 高频流的渲染合并有底线保证（P0）

作为多任务操作者，我想同一时刻不管多少路流在动，界面的每秒渲染工作量有上限，以便风扇不狂转、不卡顿。

验收：
- Given 我打开的会话有 6 个子代理同时流式输出，When 输出持续，Then 界面渲染以帧为单位合并（每帧最多一次渲染提交），单帧工作量与流的路数无关（每帧提交次数 ≤ 显示器刷新率）
- Given 每秒到达数 KB 文本增量，When 渲染发生，Then 文本拼接与展示按帧批量进行，不逐 token 触发渲染
- Given 会话流式输出进行中，When 会话产生用量/水位更新帧，Then 该帧不触发独立的渲染提交（搭渲染帧的便车或跳过无可视变化的提交）

### US3.3 长会话与长输出的渲染成本有界（P1）

作为轻量设备用户，我想几千条消息的会话和几千行输出的任务不再让滚动和流式变卡，以便长任务全程可用。

验收：
- Given 会话已有大量历史消息，When 新增量到达，Then 增量渲染成本只与视口内可见内容相关（历史部分不重复解析/高亮）
- Given 子代理任务输出累积到数千行，When 输出继续增长，Then 渲染成本有界（超出可视部分不逐行渲染）

## 4. Epic E4：多端与断线的状态一致（P0）

### US4.1 刷新/换端后状态无谎言（P0）

对齐会话管理域 US4.4 的六条验收（刷新保真、换端一致、进程边界如实），本域不新增口径，只约束执行面：分级投递的引入不得回退其中任何一条。

### US4.2 断线重连不缺不重（P0）

对齐对话渲染域 US4.1 的验收，本域约束：状态摘要类通知在断线重连后靠既有的持久事件重放或快照重建补齐（语义对齐对话渲染域 ADR-002/003），不引入新的轮询机制。

## 5. 非目标（明确不做）

- **不做**会话列表的置顶/固化排序协议（属会话管理域 E1/E2，其排期见该域 ROADMAP）——本域只约束"现有 recency 排序的触发时机"的执行面
- **不做**对话渲染域的转录保真类需求（内容正确性属对话渲染域；本域只管到达效率）
- **不做**TUI 侧的等价改造（TUI 单会话视图天然不受影响；多会话 TUI 面另行裁决）
- **不做**服务端事件的压缩/差分编码（传输量当前不是瓶颈，先解决投递分级）
- **不定义**子代理过程事件的语义结构（关联提案 P-027，另行裁决）

## 6. 决策记录（SDR）

### SDR-001 事件按消费状态分三级：互动关键级全局必达、状态摘要级全局轻量、内容流级仅当前会话

- **编号与日期**：SDR-001 · 2026-10-23
- **背景与动机**：多主任务并行时，界面对不同会话的信息需求完全不同——正在看的要全量、没看的只要状态、等我决策的要必达。现状把"是否订阅"与"给什么"绑死在一个开关上，导致要么全量喂（卡）、要么收不到（漏），等待用户决策的提示反而可能因订阅驱逐而丢失（优先级倒挂）。证据快照见 context §1-§3。
- **决策**：事件按**消费者需求**而非连接形态分三级——(a) **互动关键级**（审批/提问挂起与解除、回合失败、后台任务终止）：全局必达，任何连接、任何时刻（含刷新后）都能收到；(b) **状态摘要级**（运行状态四元组迁移、会话/工作区增删、元数据变化）：全局轻量投递，每会话仅状态迁移帧；(c) **内容流级**（文本/思考增量、工具进度、子代理输出、用量水位）：仅投递给当前打开的会话，其余消费者不接收。
- **否决的替代**：(a) 维持"订阅即全量"+调大订阅上限——只调系数不解决结构错配，后台会话的流式开销仍随并行数线性增长；(b) 纯前端丢弃（服务端照发、客户端按 active 过滤）——网络与解析成本仍在，移动端/低端设备无解，且丢帧后回看需全量补拉；(c) 全部改轮询——倒退回拉模型，实时性（US2.2 徽章即时）无法满足。
- **影响面**：US1.1–US1.4、US3.1；架构文档 §2；与对话渲染域 ADR-002/003 的衔接点（快照+重放契约不变，分级只影响实时面）。

### SDR-002 列表位置与运行状态解耦：位置只随使用事件变化，状态用徽章表达（「使用」口径引用会话管理域 SDR-014）

- **编号与日期**：SDR-002 · 2026-10-23
- **背景与动机**：现状"最近使用"排序以会话更新时间为键，而会话每产出一条内容就刷新该时间——并行运行时行反复跳顶，用户"想点的那行跑了"。会话管理域 SDR-004 曾将"回复产出"计入使用，该子句正是跳顶的口径来源；2026-10-23 该域以 SDR-014 将使用清单收窄（排除回合内内容产出），本 SDR 消费该口径并裁决本域侧的呈现方式。
- **决策**：列表位置只随三种事件变化：新会话插入顶部（会话管理域 SDR-002）、用户交互触发的 recency 提升（口径 = 会话管理域 SDR-014 的两项清单：用户发送消息、用户主动打开）、用户显式拖拽（会话管理域 SDR-001）。运行中/等待干预/已结束的状态一律用行内徽章表达，徽章更新不移动行。位置与状态的解耦是本域的执行责任：状态通道（徽章）与排序通道（位置）在前端是两条独立派生链。
- **否决的替代**：(a) 运行中的会话冻结位置（跑完再跳）——"跑完跳顶"仍是用户没预期的移动，且与"会话结束不是使用"的口径矛盾；(b) 排序加滞回带（变化小于阈值不动）——治标，长任务跨越阈值时仍跳；(c) 完全静态排序（只有手动拖拽）——违背"最近使用"的产品愿景（会话管理域 §0 浏览用户角色）。
- **影响面**：US2.1–US2.3；会话管理域 SDR-014（口径来源，同批登记）；glossary G8（同批新增）；会话管理域 US4.4（徽章口径引用不变）。

### SDR-003 渲染提交按帧合并且失效面按会话隔离：任何会话的事件只弄脏它自己的消费面

- **编号与日期**：SDR-003 · 2026-10-23
- **背景与动机**：现状每个到达事件都整体刷新界面的全部状态容器，任何会话的一个增量都会触发当前打开会话的完整重算与重渲染（乘法效应）——多主任务时渲染进程 CPU 饱和、UI 卡顿。证据快照见 context §2.3-§2.4。
- **决策**：两条硬约束——(a) **每帧一次提交**：同一渲染帧内到达的所有事件合并为一次状态更新与一次渲染提交，无状态变化（如纯用量数值变化且无可视呈现）不产生提交；(b) **失效面隔离**：一个会话的事件只使其自身的消费面失效（该会话的对话面板状态、其列表行徽章），不得使其他会话的消费面失效。
- **否决的替代**：(a) 只调批处理白名单（把更多事件类型加进合并器）——合并不解决"写回即整体失效"的结构问题；(b) 把状态容器按会话拆成相互独立的响应式根——改动面与风险巨大，且徽章等跨会话消费面需要跨根订阅，复杂度不成比例；(c) 虚拟化优先——虚拟化解决的是渲染量，本痛点是重算量，先修失效面。
- **影响面**：US3.1–US3.3；架构文档 §3；对话渲染域 §2.5 消费端管线（实现落点，语义不变）。

## 7. 术语表（域内视图）

| 规范名 | 域内语境 |
|---|---|
| 互动关键级 | 不依赖订阅的全局必达事件类（SDR-001a）：挂起审批/提问、回合失败、后台任务终止 |
| 状态摘要级 | 全局轻量事件类（SDR-001b）：运行状态（G7）迁移、会话/工作区增删、元数据变化 |
| 内容流级 | 仅当前会话投递的事件类（SDR-001c）：文本/思考增量、工具进度、子代理输出、用量水位 |
| 运行状态 | 会话管理域 G7 的四元组口径，本域只消费不重定义 |
| 使用 | 会话管理域 SDR-014 / glossary G8 的两项清单（用户发送消息、用户主动打开会话），位置提升的唯一口径 |
| 渲染提交 | 一次"状态已定 → 界面更新"的原子呈现动作（一帧内合并为一次，SDR-003a） |
| 失效面 | 一个状态变化所触发的重算范围（按会话隔离，SDR-003b） |
