# 上下文注入域 · 需求规格（context-injection）

> 本文档为上下文注入域建立**需求基线**，作为 Rust Core 的对齐下限——基线是 Rust 必须达到的下限，不是 Rust 能力的天花板。文中「未来增强提案」小节收录超出基线的改进构想，明确与基线能力区分。

## 0. 领域边界

**管什么（in-scope）**——一切"引擎生成的、追加进对话上下文的补充内容"的**通道、格式与生命周期**：

- 系统提醒统一通道：信封标记、消息角色、落点、追加语义；
- 每回合条件注入框架：注入提供者的注册契约、触发时机、注入位置记账与对账；
- 事件型系统提醒：打断提醒、侧问子代理、项目说明生成完成、目标事件提醒、工具增删公告、插件会话启动、蜂群模式进出、图片压缩说明等**通道行为**（何时注入、以何种形态、如何去重）；
- 嵌入式提醒：拼接在工具结果尾部或工具侧信道内的提示；
- 事件驱动的引擎消息：定时任务触发、后台任务完成通知、停止钩子续跑、钩子附加上下文、`!` 直跑命令输出等以普通消息形态进入对话的引擎内容；
- 注入内容的生命周期：上下文压缩时退场与重注、撤销时的处理、会话恢复时的重放与补发、崩溃安全；
- 注入内容的来源标识体系，以及频率控制/幂等的通用要求。

**不管什么（out-of-scope）**——各注入变体**内容本身的产品语义**归其所属领域：

- 目标提醒的内容与预算引导 → 目标域（goal）；
- 权限模式提醒、审批拦截文案 → 权限与审批域（approval）；
- 插件会话启动块、技能激活的内容语义 → 技能域（skills）；
- 能力缺口提醒（多模态派发建议） → 多模态输入域（multimodal-input）；
- 后台任务通知与定时注入的内容语义、压缩后任务清单 → 后台任务域（subagent）；
- 待办列表提醒的内容、工具去重提醒的阈值语义 → 工具调用域（tool-calling）；
- 蜂群模式的工作法内容 → 协作域（collaboration）；
- 回合准入/合并/唤醒源接入契约 → 回合调度域（turn-scheduling）；
- **静态系统提示的组装**（基础提示、项目说明、目录树等一次性拼装）→ 画像域（agent-profile）与 `rust-core-design/10-agent-context-assembly.md`；
- 上下文压缩本体 → 压缩域（compaction），本域只定义"注入物在压缩时如何退场与重注"。

## 1. 人物角色（Personas）

- **模型消费者**：对话的另一端——所有注入内容的最终读者，需要在合适时机收到准确的引擎状态与指令，且能分辨"用户原话"与"引擎补充"。
- **终端用户**：偶尔在界面回看对话记录的人——需要不被注入内容误导（不误以为是自己说过的话），且注入行为不破坏撤销、续聊等操作。
- **宿主/引擎工程师（Rust Core 团队）**：需要一套完整、无歧义的注入通道规格，作为 Rust 实现的对齐基线。

## 2. 领域总述

引擎在纯用户输入与模型输出之外，需要一条**受控的旁路**向模型传达运行时状态与权威指令：回合被中断了、目标被取消了、工具集变了、后台任务完成了、项目说明重新生成了……这些内容统称**注入物**。它们必须在正确时机、以可辨识的形态、可预测地去留进出对话。本域定义这条旁路的全部通道契约：统一信封、条件注入框架、事件提醒、嵌入式提醒、事件驱动消息，以及注入物相对压缩/撤销/恢复的完整生命周期。

## US1 系统提醒统一通道（信封契约）

引擎需要一条统一的"权威旁注"通道，让模型把引擎补充内容与用户原话区分开，且不污染既有消息。

**AC1（信封与落点）**
- Given 引擎决定注入一条系统提醒，
  When 该提醒落地，
  Then 它作为**一条新增的独立消息**追加在当前对话末尾，文本包裹在统一的权威指令标记（`<system-reminder>` 信封）中，消息角色按"用户侧补充消息"投递；既不修改任何既有消息，也不在用户输入框回显。

**AC2（模型侧认知）**
- Given 系统提醒可能出现在对话任意位置，
  When 模型阅读系统提示时，
  Then 系统提示中包含对该信封的说明——信封内是**必须遵守的权威系统指令**，而非用户话语。

**AC3（工具交换期间的安全落点）**
- Given 对话尾部存在尚未闭合的工具调用与工具结果配对，
  When 一条注入物在此期间产生，
  Then 它被**暂存缓冲**，待工具交换闭合后按原顺序落地，绝不插进工具调用与结果中间破坏配对。

**AC4（不冒充用户）**
- Given 注入物以用户侧消息角色进入对话，
  When 终端用户在界面回看会话时，
  Then 注入内容或被静默折叠、或以专属形态呈现（定时卡片、压缩分隔条、直跑命令视图等，均携带来源标识），**绝不以用户气泡形态出现**，界面不暴露原始信封与标记文本（具体呈现形态归对话渲染域）。

## US2 每回合条件注入框架（注入提供者）

需要一类"每个模型交互步开始前都有机会注入"的框架，让各领域以可插拔方式声明自己的注入条件，而不各自发明注入路径。

**AC1（注册与触发）**
- Given 任一领域通过统一框架注册了注入提供者（以**注入变体名**标识），
  When 每个模型交互步即将开始（含上下文压缩完成后），
  Then 框架调用该提供者；提供者返回内容则按系统提醒信封落地，返回"无"则本步不注入。

**AC2（回合边界感知）**
- Given 提供者只希望在"新回合的第一步"注入（如目标常驻提醒），
  When 一个新回合开始，
  Then 框架向提供者告知"这是新回合"；该标记被消费一次后复位，且随会话状态持久化——恢复会话后不重复消费也不遗漏。

**AC3（注入位置记忆）**
- Given 提供者需要知道自己历史上的注入落点（如"本会话从未注入过"或"距上次注入已过多久"），
  When 撤销、压缩或其他历史裁剪发生，或会话整体恢复时，
  Then 框架自动跟踪并更正对提供者可见的落点记录——被裁掉的位置移除、保留下来的位置校正，提供者据此做出的去重判断在恢复后依然正确。

**AC4（压缩后重注）**
- Given 注入物会在上下文压缩时退场（见 US6），
  When 压缩完成，
  Then 框架以"新回合"名义重新给所有提供者注入机会，使必要的状态提醒（如活动目标、计划模式）在压缩后的对话里依然在场。

## US3 事件型系统提醒

引擎在明确的业务事件发生时，通过系统提醒通道向模型即时传达状态变化。本域只定义其**通道行为**（触发时机、形态、去重），内容语义归各所属领域。

**AC1（用户取消回合后的完整性提醒）**
- Given 一个回合被用户中断后模型再次获得交互机会，
  When 中断提醒尚未送达，
  Then 模型被告知"上一回合的部分输出可能不完整"；
  Given 同一回合的提醒已随会话记录持久化但进程在送达前崩溃，
  When 会话恢复，
  Then 待送达的提醒被**补发**，不丢失、不重复。

**AC2（侧问子代理的通道声明）**
- Given 用户发起"顺带一问"式轻量子代理，
  When 子代理启动，
  Then 其上下文首先收到一条系统提醒，声明该实例的轻量定位与工具约束。

**AC3（项目说明生成完成）**
- Given 项目说明文件刚被代理重新生成，
  When 生成完成，
  Then 主代理收到系统提醒，携带最新的项目说明全文以立即生效。

**AC4（目标事件提醒）**
- Given 活动目标被用户取消、或目标硬预算触顶进入停止流程、或会话分叉后目标归属被清除，
  When 相应事件发生，
  Then 模型收到对应的一次性系统提醒，告知目标状态变化及应采取的行为（忽略/收尾）。

**AC5（工具集变化公告）**
- Given 可选加载的工具集发生变化（新增或移除），
  When 每个新回合的首步（或压缩完成后），
  Then 模型收到折叠的增删公告；仅当集合真变化时公告，公告引导模型用按需加载机制获取新工具；被加载的工具定义本身经协议专用通道进入上下文（不占用对话正文、不冒充用户）。

**AC6（插件会话启动声明与中和）**
- Given 插件声明了会话启动技能，
  When 会话启动后插件技能目录首次可用、或目录发生变更，
  Then 注入对应的会话启动声明块；
  Given 历史上存在过启动声明但当前已无活跃插件，
  When 目录变更发生，
  Then 注入一条**中和性声明**，避免残留的旧指令误导模型。

**AC7（蜂群模式进出提醒）**
- Given 蜂群模式由用户主动开启或关闭，
  When 进入或退出发生，
  Then 注入对应的工作法说明；退出时若进入说明恰好是对话最后一条消息，则**移除它**而非再追加一条，避免无意义的头尾残留；
  Given 蜂群模式由模型自身通过工具开启，
  Then 不注入说明（模型已知自己在做什么）；该"进入则可能弹出"的行为在会话恢复重放后保持一致。

**AC8（图片压缩说明）**
- Given 用户消息中的图片为适配模型限制被压缩、原始图被剥离，
  When 用户消息进入对话，
  Then 压缩说明作为系统提醒落地，说明原始图内容去向；该说明**归属于所属用户消息**——撤销该消息时说明一并移除。

## US4 嵌入式提醒（工具结果内）

部分提示更适合就近出现在工具结果里，而不是独立消息。

**AC1（工具重复调用递进提醒）**
- Given 模型对同一工具以相同参数连续重复调用，
  When 重复次数达到递进阈值（3/5/8 级），
  Then 对应等级的提醒**追加在工具结果尾部**（仍用权威指令信封包裹），要求模型改变行为；达到强制停止阈值（12 次）时引擎直接结束回合。

**AC2（工具侧信道）**
- Given 工具执行产生面向模型的补充说明（错误或空输出的状态前缀、读取文件的收尾提示等），
  When 结果返回模型，
  Then 状态前缀以工具侧的补充标记（`<system>` 信封）呈现在工具结果内，收尾提示以纯文本附加在结果尾部；两者用户界面均不展示。

## US5 事件驱动的引擎消息

引擎事件需要以**普通消息**（不包系统提醒信封）进入对话，其进入方式由回合调度域的唤醒源契约统一定义；本域只约束其消息形态契约。

**AC1（消息角色与来源）**
- Given 定时任务触发、后台任务完成、停止钩子要求续跑、钩子附加上下文、钩子对用户输入的阻断结论、`!` 直跑命令、技能激活、插件命令、子代理启动、目标自动续航等任一事件，
  When 其内容进入对话，
  Then 以普通消息落地（以用户侧消息角色为主）、携带各自的来源标识；`!` 直跑命令以专用命令信封呈现（界面还原为命令视图）；用户输入被钩子阻断时的结论以**助手侧消息**呈现（本域唯一的角色例外）；除技能激活等需以用户口吻呈现的场景外，不在正文冒充用户。

**AC2（投递语义）**
- Given 上述事件发生时主回合可能正在执行，
  When 事件消息等待投递，
  Then 按回合调度域的准入规则折入在途回合或开启新回合；同一事件重复触发不产生重复投递，恢复会话后不重放已送达的内容。

## US6 注入内容的生命周期

**AC1（压缩退场与重注）**
- Given 对话被压缩，
  When 保留窗口划定，
  Then 注入物（系统提醒、事件消息等一切非真实用户输入）**随压缩退场**，保留窗口只保留真实用户输入的头尾部分与摘要；中间段被省略时，模型收到一条省略说明提醒（告知被省略的范围，内容语义归压缩域）；必要的状态由 US2 AC4 的重注机制与各领域自愈逻辑恢复。

**AC2（撤销处理）**
- Given 用户执行撤销，
  When 回退遍历历史，
  Then 注入物**不阻塞撤销**：随所属范围跳过或连带移除；归属特定用户消息的注入（如图片压缩说明）随该消息一并撤销。

**AC3（持久化与重放）**
- Given 注入物已进入对话，
  When 会话落盘并恢复，
  Then 每条注入物按其来源标识完整重放——恢复后的模型所见与崩溃前一致；带"待送达"语义的提醒（中断提醒、分叉目标清除）由持久化的待办标记保证补发。

## US7 频率控制与重复抑制

**AC1（一次性注入）**
- Given 属于"整个会话只需一次"的注入（如插件会话启动声明），
  When 历史中已存在同变体注入，
  Then 不再重复注入；即使被压缩折叠掉，也按各领域的重注策略处理而非盲目重复。

**AC2（节流注入）**
- Given 属于"按频率刷新"的注入（待办列表未更新提醒、计划模式阶段性重申等），
  When 距上次注入未达门槛，
  Then 不注入；达到门槛后以约定的强度阶梯注入。

**AC3（状态门控）**
- Given 注入依赖外部条件（活动目标存在、待办工具已启用、模型能力缺口存在等），
  When 条件不满足，
  Then 不注入；条件消失后已注入的历史不追溯删除（由压缩自然清理）。

## US8 来源可辨识

**AC1（来源标识体系）**
- Given 任何注入物进入对话，
  Then 它携带**封闭集合**内的来源标识（用户/技能激活/插件命令/注入+变体/直跑命令/压缩摘要/系统触发/后台任务/定时任务/定时补发/钩子结果/钩子附加上下文/重试），供界面、协议与重放消费。

**AC2（协议暴露）**
- Given 宿主应用需要区分展示，
  When 注入物投影到对外协议，
  Then 来源标识随消息元数据暴露。

## 9. 非功能性需求

- **低开销**：条件注入框架在每个模型交互步前运行，提供者必须轻量，不得阻塞主循环发起请求的关键路径（注入完成后请求才发出）。
- **崩溃安全**：所有"已决定注入但可能未送达"的路径有持久化保障，恢复后补发；已送达的不重放。
- **重放等价**：会话恢复后的上下文与在线语义一致（注入位置、去重状态、待发提醒均对账）。
- **可预测性**：注入行为完全由可枚举的触发条件决定，无随机或不可观测的注入。

## 10. 未来增强提案（超出 TS 现状）

以下构想**不是 TS 已支持的能力**，是本域调查中提出的改进方向，供 Rust Core 评估采纳：

- **P1 注入面板（用户可见的注入治理）**：向用户提供"当前活跃注入"视图（哪些提醒在轮询、各自的频率与上次注入时间），并允许按提醒类别关闭（如关闭待办提醒）。TS 现状无任何用户级开关。
- **P2 注入背压上限**：工具交换未闭合时的暂存缓冲目前（TS）无上限；Rust 已实现超限丢弃并告警。建议基线采纳"有上限 + 显式告警"语义，并考虑超限时优先保送高优先级提醒。
- **P3 注入审计可观测性**：统一记录每次注入的变体、触发原因、落点与字节数，供调试"模型为何行为异常"类问题。
- **P4 信封教学集中化**：`<system-reminder>` 与 `<system>` 双信封的语义说明分散在系统提示与各工具实现里，建议收敛为单一权威说明并测试覆盖。
