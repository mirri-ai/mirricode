# 对话渲染 — 需求文档

> 状态：v1 基线 · 2026-09-12 · 待用户评审 ·
> 本文是对话渲染域（conversation-rendering）需求侧的唯一事实源（内部规格文档，不进文档站构建，中文单语）。
> **基线性质说明**：本文以现有引擎（TS v2 一代）的能力为**底线而非上限**记录需求——参照实现的清单与差距见 [conversation-rendering-context.md](conversation-rendering-context.md)，修复排期见 [conversation-rendering-ROADMAP.md](conversation-rendering-ROADMAP.md)；超出参照现状的改进以明确标注的提案形式记录（§7）。
> 产品愿景：**记录落定什么，界面就呈现什么——一次不丢、一字不重、随时接上**。对话视图是会话记录（S5 会话日志）的忠实实时投影：已落定的内容如实呈现，流式中的内容连续可见，中途重开接得上，断线重连补得齐；呈现不了的部分说清楚，绝不装作都在。
> 配套文档：技术形状与投影机制见 [conversation-rendering-architecture.md](conversation-rendering-architecture.md)；现状盘点见 [conversation-rendering-context.md](conversation-rendering-context.md)；执行状态与开放项见 [conversation-rendering-ROADMAP.md](conversation-rendering-ROADMAP.md)。
> 术语规范：会话快照（R1）、在途回合（R2）、易失事件（R3）、事件游标（R4）、会话日志（S5）、转录（S6）、回合（S7）的唯一定义见 [glossary.md](glossary.md)；本文件只使用这些规范叫法。
> 范围边界：本域覆盖**会话日志到对话视图（S6 转录）的投影契约**——实时事件面（流式呈现）、打开与历史读面（快照、分页）、在途回合续看、断线重连一致性、转录保真的呈现面（压缩分隔条、撤销刷新、注入过滤、附件、错误/中止呈现）。**不属本域**：记录的存储布局与版本链（会话持久化域）；侧边栏会话列表的组织交互（会话管理域）；压缩机制本身（上下文压缩域）；模型侧读回（历史读回域）；审批的流程语义（approval 域，待立项）——但审批请求在对话中的**呈现**归本域；子代理的生命周期语义（子代理域）——但其事件在对话中的呈现与归因归本域；各端的具体视觉设计（TUI/web 的实现细节）。

## 0. 角色定义

| 角色 | 场景 | 核心诉求 |
|---|---|---|
| **流式观看者**（盯着回复生成的人） | 看文本逐字出现、工具逐个执行 | 流式连续不卡顿；工具做了什么、结果如何一目了然 |
| **中途回访者**（回复进行到一半时切走又切回的人） | 换设备/重开页面，回复还在生成中 | 已输出的部分都在，流从断点续上，不从头来 |
| **翻旧账用户**（往上翻很早以前对话的人） | 长会话往上滚动 | 旧内容按需加载、阅读位置不跳、加载失败有重试 |
| **弱网用户**（网络不稳/后台标签页的人） | 断线、后台冻结、半开连接 | 补齐而非报错；不静默落后；不重复 |
| **双端用户**（终端与网页换着用的人） | 同一会话两种界面打开 | 两端看到的对话一致——投影跟着数据走 |

## 1. Epic E1：打开即完整（快照与历史读面）（P0）

> 解决"打开会话的第一眼"。打开是常驻高频操作：首屏必须是一份同一时刻的完整切片，而不是边收边拼的半成品。

### US1.1 打开会话立见完整切片（P0）

作为回访用户，我想点开任一会话就立刻看到一份完整的最近对话，以便不需要等待"边加载边跳变"。

验收：
- Given 用户点开任一会话（空闲的或回复进行中的），When 首屏呈现，Then 展示的是**同一时刻**的对话切片——不出现"先给一半、又插一段"的半新半旧拼接（原子性）
- Given 该会话还有更早的对话超出切片容量，When 首屏呈现，Then 明确告知"还有更早"（可继续向上翻），不假装已经到底
- Given 快照携带"切片时刻"的水位（R4 事件游标对应的进度），When 之后的对话发生，Then 从水位之后接续（详见 E4），快照内容与后续内容不重不漏
- Given 快照请求发生时本地已有用户刚发出的消息，When 快照安装，Then 用户自己的消息不被快照顶掉（本地已见内容优先于快照回填）
- Given 用户重新打开已加载过更早历史的会话，When 新快照安装，Then 已加载的更早历史页保留不被清空（不闪烁、不要求重新翻页）
- Given 快照请求失败（网络/服务端异常），When 呈现，Then 有明确的失败提示与重试途径（提示用户重进或刷新），已加载内容不被清空破坏；打开已不存在的会话得到明确的"会话不存在"呈现，不进入空白等待
- Given 会话打开尚在进行或会话没有任何对话，When 首屏呈现，Then 有轻量的加载占位与空会话态（不误报错误，也不无限转圈）

### US1.2 消息有可指认的身份与时间（P0）

作为翻旧账用户与界面本身，我想每条消息都有稳定的身份与发生时间，以便翻页有锚点、重复到达可识别、展示有次序。

验收：
- Given 任一条消息，Then 对话视图与读取接口用**同一个身份**指认它：向上翻页以它为锚、同一内容的临时副本与正式副本据它识别为一条
- Given 同一份数据状态（未发生撤销等改变历史的操作），When 再次读取，Then 消息身份不变（身份在数据状态内稳定，不随重启漂移）
- Given 用户对会话执行了改变历史的操作（如撤销），When 身份随之更新，Then 读取方被告知需要重新对表（见 US4.1），不会拿旧锚点无限打转
- Given 任一条消息，Then 携带反映其先后次序的发生时间（供排序与展示），不是空缺值；同一读取面（快照、历史分页）的消息行形状一致（同一接口的两种入口不各说各话）

### US1.3 向上翻旧账（历史分页）（P0）

作为翻旧账用户，我想滚动到顶部时自动加载更早的对话，以便长会话不必一次全量载入。

验收：
- Given 用户滚动到已加载对话顶部附近，When 还有更早消息，Then 自动加载更早一页；加载完成后阅读位置**不跳动**（滚动锚定，用户正在看的那条不动）
- Given 加载失败，When 失败呈现，Then 有可感知的失败提示与**手动重试**入口（顶部常驻的"加载更早"入口可再点）；自动重试有节制（不无限循环轰炸）
- Given 翻页锚点所指的消息已不存在（如撤销后），When 再请求更早，Then 加载**终止且不重复插入**——界面识别"新页内容其实比已加载的更新或重叠"并停止，不出现"翻页变回锅"的重复加载循环（服务端读面今日对失效锚点返回最新一页的现状记为已知契约缺陷，见 context §2.1；需求钉死的是客户端不得把回锅内容二次插入）
- Given 分页参数（方向、每页上限），When 提交，Then 超上限被拒绝或截断到上限，同一服务的各读出入口上限一致

### US1.4 系统注入不冒充用户（P0）

作为任意用户，我想让对话视图里的"用户消息"都是真的用户输入，以便转录不被系统内部动作污染。

验收：
- Given 记录中存在用户角色但非用户来源的消息（压缩整理、上下文注入、重试、定时触发等），When 转录呈现，Then 它们不冒充用户气泡——要么作为回合边界静默、要么以专属形态呈现（如压缩分隔条），身份来源可辨
- Given 消息行携带来源标注，When 界面过滤，Then 据此判定呈现方式，不需要界面自己按内容猜

## 2. Epic E2：流式呈现契约（实时事件面）（P0）

> 解决"回复生成中看到什么"。流式期间的一切临时呈现，最终都要与落定后的记录对得上。

### US2.1 流式文本与思考（P0）

作为流式观看者，我想看文本与思考过程逐块呈现，以便等待有反馈、结果不突兀。

验收：
- Given 回复正在生成，When 新的文本/思考分片到达，Then 界面及时**增量**呈现（呈现连续不卡顿；界面被冻结的后台页面恢复后不丢期间内容）
- Given 思考内容为空或仅空白（如加密推理签名），When 呈现，Then 不渲染空块（不出现空白折叠框）
- Given 流式中途切换（文本结束开始工具调用、思考结束开始文本），Then 呈现顺序与真实发生顺序一致（文本块在前、工具卡片在后不颠倒）
- Given 同一回合内的各类事件先后发生（回合边界、步进、工具状态、流式内容），When 呈现，Then 先后顺序与到达顺序一致——任何提速的合并处理都不改变先后（控制类事件永不被其后的内容超越）
- Given 某一步失败后自动重试，When 重试的回复继续流出，Then 失败尝试已流出的部分被**同一位回复**替换收编（不与新尝试的内容并排双份）

### US2.2 工具调用全生命周期可见（P0）

作为流式观看者，我想每次工具调用从发起到结果全程可见，以便知道对方在做什么、做成了没有。

验收：
- Given 模型发起一次工具调用，When 调用开始，Then 卡片立即呈现：工具名、**完整参数**、本次调用的唯一标识；调用需要审批时，卡片呈现待审批状态与审批入口（审批流程语义属 approval 域）。参数流式生成期间的**增量参数预览**（边生成边看到参数长出来）终端界面已支持、网页界面尚未支持（提案 P6）
- Given 工具执行中持续产出（命令输出、进度），When 更新到达，Then 卡片内持续可见最新产出（终端界面按上限保留尾部滚动窗、超长截断保尾；网页界面的进度呈现上限为提案 P1 的一部分）
- Given 工具完成（无论成功或失败），When 结果到达，Then 卡片呈现**结果内容**与成败状态（失败以醒目的错误形态可辨——错误色/失败图标）；**迟到订阅者**（错过开场的重开者）也能凭结果携带的归位信息把结果放到正确的工具上
- Given 结果内容超长，When 呈现，Then 有单条展示上限（保尾部）与展开途径，超长不撑爆界面（终端界面已支持；网页界面的通用工具卡上限为提案 P1 的一部分）
- Given 同一回合内多次工具调用，Then 顺序稳定、可连续聚合呈现（连续同类调用可折叠为一组）

### US2.3 回合边界与结局（P0）

作为任意用户，我想每个回合的开始与结局都清楚，以便知道"这轮完了没、成了没"。

验收：
- Given 用户发出输入，When 回合开始，Then 该输入立即在对话中可见（含输入来源：用户发言、斜杠命令、技能触发等）
- Given 回合结束，When 无论结局为何——完成、被用户取消、失败、被安全策略拦截、达到步数上限，Then 界面如实呈现该结局；失败带原因；进行中的流式呈现收尾定格（取消的回合保留已生成的部分，不凭空消失也不假装修完）
- Given 回复因长度上限被截断，When 呈现，Then 截断被明确告知（不是静默的"就这样了"）——终端界面已支持；网页界面的截断与拦截告知为提案 P6
- Given 回合中途用户插话（追问引导），When 插话发生，Then 插话呈现于当前回合内、不打断流（插话的记录语义属会话管理域）
- Given 回合中途用户插话，When 插话呈现，Then 以**完整用户气泡**形态呈现于当前回合内部——插话文字与附件全部可见、带发生时间，气泡带"插话"角标（区别于回合开启消息）；它前后的模型输出属于同一个回合（序号连续、无回合分隔）
- Given 回合中途用户插话，When 会话重开或刷新后呈现，Then 插话的折叠呈现与进行中一致（进行中与历史回放同律）
- Given 回合中途用户插话，When 判定呈现方式，Then 依据记录携带的来源标注（插话专属标识），不依赖界面按位置猜
- Given 一条用户消息在回合结束后才被消化（如回合中止后的残留插话被下一回合首步消费），When 呈现，Then 作为普通回合开启消息呈现（无插话角标、正常回合边界）

### US2.4 每步用量可感知（P1）

作为成本敏感用户，我想随时知道这轮花了多少、会话累计多少，以便心里有账。

验收：
- Given 回合内每一步（单次模型请求）完成，Then 该步的用量与关键时延（首字延迟等）随事件可取、随记录可查
- Given 会话任意时刻，Then 会话累计用量（含缓存读写分桶、**分模型可查**）与当前上下文水位可查、界面上有常驻的轻量呈现位置

### US2.5 状态聚合视图（P1）

作为任意用户，我想随时在界面上看到"对方当前在干什么"（流式中/工具执行中/等待审批/重试中），以便长任务等待期间有明确的活动反馈。

验收：
- Given 会话处于任一活动阶段（流式中/工具执行中/等待审批/重试中），When 用户查看界面，Then 有一个现成的活动状态呈现（来自一份可丢弃重建的聚合状态），不需各界面从原始事件流自己拼装
- Given 聚合视图损坏或丢失，When 重建，Then 从持久事实重建可用（它只是缓存，不是第二份真相）

## 3. Epic E3：在途回合续看（中途回访）（P0）

> 解决"回复进行到一半时重开"。易失的流式内容（R3）不落记录，重开必须由快照把"进行到哪了"补齐。

### US3.1 重开进行中的会话（P0）

作为中途回访者，我想在回复生成中重开会话时看到已生成的部分并接上后续，以便换设备/刷新不损失进行中的回答。

验收：
- Given 回复正在流式输出，When 用户重开该会话，Then 快照携带**在途回合**（R2）：已生成的文本与思考的当前内容、正在执行的各工具（调用标识、名称、参数、最近进度）、当前回话标识——界面据此直接呈现"半成品"回复与运行中的工具卡
- Given 会话有活跃的子代理/群集任务，When 重开，Then 其卡片与进行状态从快照的子代理名册完整重建（派发工具的结果尚未落地前，子代理卡不悬空、不消失）
- Given 界面从快照播种了在途回合，When 后续流式分片继续到达，Then 从当前内容**无缝续上**（不从头重放、不闪断、不出现半成品与续流的双份）
- Given 会话空闲（没有进行中的回复），When 快照，Then 在途回合明确为"无"（不出现幽灵进行中状态，也不出现"加载中"的悬空呈现）
- Given 流式分片与已播种内容有重叠窗口，When 续流，Then 重合部分不重复渲染（续流以当前累计位置对齐）

### US3.2 待人工交互可见（P0）

作为中途回访者，我想重开时看到会话正在等待的审批与提问，以便马上处理、不卡住会话。

验收：
- Given 会话正等待审批或提问，When 重开，Then 待交互项完整可见（是什么操作/问题、选项），且可在此界面直接答复
- Given 待交互项已被另一端处理，When 界面收到解决事件，Then 待交互项消失且对话中留下处理结果（批准/拒绝可见）

## 4. Epic E4：断线与重连（一致性）（P0）

> 解决"断线/重连/多端之间的不丢不重"。

### US4.1 断线重连不丢不重（P0）

作为弱网用户，我想断线重连后对话自动补齐，以便不需要手动刷新。

验收：
- Given 连接断开，When 重连成功，Then 从上次收到的水位（R4）续订，补齐期间错过的持久事件；重连有退避重试，不疯狂轰炸
- Given 错过的事件超出服务端补齐能力（缓冲溢出）或会话被重建（水位作废），When 重连，Then 服务端**明确要求重新对表**（要求界面重新快照），界面照做后内容与真实一致——不静默丢、不假装齐
- Given 半开连接（界面冻结的后台标签页），When 页面回到前台，Then 检测连接健康并按需修复，恢复后内容与真实一致（不静默落后于真实进度）
- Given 用户在断线期间本地发出的消息，When 重连补齐，Then 与服务端确认的同一消息识别为一条（不双份）
- Given 用户同时打开的会话数超出界面的订阅容量，When 切换到新会话，Then 被挤出容量的会话停止实时更新；重开被挤出的会话时以快照**完整对表**（不以可能已落后的水位续订）
- Given 同一会话在两个界面（终端与网页）同时打开，When 一端发生对话，Then 另一端最终呈现同样的内容（双端一致性：呈现跟随数据，不随设备分叉）

### US4.2 流式副本与正式记录不重复（P0）

作为任意用户，我想流式看到的回复与最终落定的回复是同一条，以便不出现"一段话出现两遍"。

验收：
- Given 回复先以流式呈现、随后正式记录到达（快照重载、订阅回放等场景），When 两者先后可见，Then 识别为同一条内容（正式副本接管；流式期间积累的临时痕迹——如工具进度行——合并进正式副本不丢失）
- Given 识别依据（回合归属标识）缺失，When 兜底，Then 以内容与边界（相邻用户消息）为界去重，同轮之内不双渲染

## 5. Epic E5：转录保真（呈现面）（P0）

> 解决"转录（S6）是全量投影"的呈现兑现。

### US5.1 压缩不删转录（P0）

作为长任务用户，我想压缩发生后旧对话仍然全部可见，以便人能翻旧账（模型侧翻旧账是历史读回域的事）。

验收：
- Given 会话经历过压缩，When 浏览转录，Then 被压缩的原始对话**全部**可见（转录不因压缩删减），压缩处以整理记录（分隔条）呈现——带前后用量对比、可展开摘要
- Given 压缩正在进行，When 呈现，Then 过程可见（进行中/完成/取消各有形态）；压缩被拦截（blocked）的呈现与"被重试彻底丢弃的条目数"的披露为提案 P7（当前两端均不呈现）
- Given 撤销的回退点遇压缩边界，When 呈现，Then 边界反馈可见（撤销语义属会话管理域）

### US5.2 撤销后视图刷新（P0）

作为会话用户，我想撤销成功后视图立即变为撤销后的状态，以便所见与真实历史一致。

验收：
- Given 用户执行撤销并成功，When 视图刷新，Then 被撤销的轮次不再呈现，新对话接在撤销点之后——撤销后重新打开会话同样停留在撤销后状态（不复活）

### US5.3 附件呈现（P1）

作为任意用户，我想对话中的图片与文件附件始终以可用形态呈现，以便重开后不悬空。

验收：
- Given 用户输入携带附件（图片/文件），When 呈现，Then 附件以缩略/标签形态伴随消息（重开后同样恢复呈现，不因引用过期而悬空）
- Given 回复产出媒体内容，When 呈现（含重开），Then 媒体以可用的形态呈现（重开恢复路径的媒体呈现见 §7 提案 P5）

### US5.4 身份归因（P0）

作为双端用户/任意用户，我想对话中的多身份活动（子代理、后台任务）事件携带身份，以便呈现不张冠李戴。

验收：
- Given 会话内子代理/后台任务的事件到达界面，When 呈现，Then 事件携带其身份归因（谁发的），不误归到主对话；主对话与子身份的活动各自呈现、互不混淆
- Given 失败与成功两类终态事件，When 对照，Then 携带的归因信息**对称**（不能失败知道是谁、成功不知道是谁）

| # | 需求 | 说明 |
|---|---|---|
| NFR-1 | 流式呈现延迟 | 分片到达后界面及时连续呈现（单次用户可感知的停顿不跨越多个分片批）；界面被冻结（后台标签）时以定时兜底承接，恢复前台不丢内容 |

## 7. 未来增强提案（超出参照现状，非基线承诺）

> 以下为**提案**：参照实现（TS v2 一代）今日**不支持**（或部分端支持）的能力，落地与否另行裁决，不构成对当前引擎的基线记录。

- **P1 长会话界面窗口化与通用输出上限（web）**：网页端今日对全部已加载对话整段渲染、通用工具卡的输出无上限滚动（现状证据见 context §4.2）；超长会话（数百轮+富内容）的界面资源压力是已知体感风险。提案：列表虚拟化 + 通用工具卡输出上限保尾（终端端已具备）。
- **P2 易失流的断点续传**：参照实现今日流式分片不落记录、重开靠快照在途回合整体补偿（架构 ADR-003）；进程在流中途崩溃时已流出的部分不保证留存（仅中断时尽力落盘已积累内容）。提案：更细粒度的流内容落盘或崩溃后流恢复。
- **P3 引擎铸造的持久消息身份**：参照实现读面今日的消息身份是从记录位置**推导**的（随撤销等历史改变而变，靠"重新对表"兜住）。提案：记录落定时铸造一次、永不漂移的消息身份，免除推导身份的对表成本。
- **P4 网页端命令行事件流呈现**：网页端今日不呈现 `!` 命令的 shell 事件流（终端端已内联呈现、网页端有独立终端面板但不消费该事件流）。提案：网页对话区呈现命令执行事件流。
- **P5 恢复回放中的媒体呈现**：终端恢复回放今日丢弃媒体内容分片（只呈现文本与思考）。提案：恢复路径保留媒体呈现。
- **P6 网页端的截断/拦截告知与流式参数预览**：终端已支持 max_tokens 截断告知、安全拦截提示与工具参数流式预览；网页端今日均不呈现/不消费（现状证据见 context §2.3）。提案：网页端补齐。
- **P7 压缩拦截与丢弃披露**：压缩被拦截（blocked）事件今日两端均不呈现；压缩记录携带的"被重试彻底丢弃条目数"今日两端均不渲染（现状证据见 context §2.3）。提案：两端补齐。

## 9. 决策记录（SDR）

### SDR-001 插话呈现细化：回合内完整气泡 + 专属来源标识（2026-10-13）

1. **背景与动机**：回合中途用户插话在网页界面被渲染为回合边界——运行中的回合被切成两片，与 US2.3 "不打断流"的既有承诺不符。根因是插话消息落进记录时与回合开启消息携带完全相同的来源标注（均为"用户"），界面只能按"用户消息即回合边界"的通则切割（现状证据见 [conversation-rendering-context.md](conversation-rendering-context.md)）。
2. **决策**：细化 US2.3 的插话验收——插话以完整用户气泡（含附件与时间、"插话"角标）呈现于当前回合内部，不切断回合；进行中与历史回放同律；判定依据是记录携带的插话专属来源标识（引擎在插话折入运行中回合时打标；插话在无运行中回合时自行开起新回合的路径保持"用户"标识，正常回合边界）。技术形状见架构 ADR-010。
3. **被否决的备选方案**：a) 插话折叠为小号内联条（类似后台任务通知）——插话是真实用户输入，长插话与带附件插话在内联条中可读性不可接受；b) 界面按位置结构推断（插话消息夹在同一回合的模型输出之间即折叠）——回合刚结束的时序竞态与缺回合归属消息的场景下误判不可控，与"来源标注可辨识、界面不猜"（US1.4）的既有原则冲突；c) 进行中完整气泡、历史回放折叠为内联条——同一消息刷新前后形态不一致，违反"两条路径收敛到同一结果"的域原则。
4. **影响范围**：US2.3（验收细化）；架构 ADR-010；[turn-scheduling-architecture.md](turn-scheduling-architecture.md) §5 插话来源标识与 ADR-003；ROADMAP 新批次 CR13。
