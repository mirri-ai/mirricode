# 历史读回 — 需求文档

> 状态：v1 提案基线（P-E1 立项）· 2026-09-10 · 待用户评审 ·
> 本文是历史读回域（history-readback）需求侧的唯一事实源（内部规格文档，不进文档站构建，中文单语）。
> **提案性质说明**：本域是**设计提案（未来增强）**，不是既有能力的基线记录——三引擎今日均无任何读回、卡片、历史检索能力（现状证据见 [history-readback-context.md](history-readback-context.md) §1.1）；Rust 已落地本域赖以工作的编号地基（压缩域 ADR-007，作为前提引用，不是本域设计）。本域按 rust-first 方向设计，**不声明任何当前支持**，不做 TS 基线对齐记录。
> 产品愿景：**压掉的旧账，翻得回来**——模型忘掉的旧内容，能按编号查（读回）、能翻目录（目录卡片）、能看全貌（现状卡）、能按话题搜（搜历史）；翻不回来的部分说清楚，绝不装作都在。
> 配套文档：技术形状与机制见 [history-readback-architecture.md](history-readback-architecture.md)；现状盘点见 [history-readback-context.md](history-readback-context.md)；执行状态与开放项见 [history-readback-ROADMAP.md](history-readback-ROADMAP.md)。
> 术语规范：读回、目录卡片、现状卡、按编号寻址的唯一定义见 [glossary.md](glossary.md)（H1–H4）；本文件只使用这些规范叫法。
> 范围边界：本域覆盖**模型对被压缩旧历史的按需取回与导航**——读回工具、目录卡片、现状卡、历史检索。压缩本身（触发、摘要生成、落位、失败恢复）与编号的产生/标注属上下文压缩域（[compaction-requirements.md](compaction-requirements.md)），本域只消费其产物；会话记录的存储布局属会话持久化域；界面上的卡片与读回呈现归下游呈现层（见架构 §6），不在本域验收。

## 0. 角色定义

| 角色 | 场景 | 核心诉求 |
|---|---|---|
| **长任务用户**（跑几小时、经历多次压缩的人） | 追问几小时前的旧细节，模型只剩转述、答非所问 | 模型能自己翻旧账，不用我复述、它不瞎编 |
| **成本敏感用户** | 旧原文若整体塞回上下文会把窗口撑爆、账单暴涨 | 翻账按需、量可控——翻一次付一次，不常驻烧钱 |
| **边界情况用户**（经历过压缩重试丢弃的会话） | 有一段内容连摘要都没覆盖 | 哪些永远找不回来说清楚，别让我以为都在 |

## 背景与存在前提（既有事实，非本域设计）

1. **模型丢的，记录里有**：会话记录完整且只增不改——被压缩"丢弃"的对话，在用户侧转录里一直可见；模型侧看不到只是因为它被摘要替换出了模型可见历史。因此本域全部能力**不需要任何新存储**，只是把记录里已有的东西按需喂回模型。这是本域的存在前提。
2. **旧账有页码**：每条进入模型可见历史的对话都有一个会话内累计、压缩与撤销都不回收的**条目编号**；每次压缩留档被覆盖段的编号区间与"经重试彻底丢弃、不可找回"的编号清单，摘要里也告知了模型这套编号约定（压缩域 ADR-007，已落地——现状证据见 [history-readback-context.md](history-readback-context.md) §1.2）。本域的一切定位、导航、检索都以编号为坐标。
3. **今日的失忆是结构性的**：多次压缩后旧摘要被再压缩（转述的转述）、最早请求只剩截断的头部精华、被重试丢弃的内容对模型彻底不可达——这是压缩域已声明的已知取舍（其 §9 P-E1 提案），本域是它的立项承接。

## 1. Epic E1：读回原文（P0）

> 解决"模型忘了的东西怎么按页码翻回来"。原则：按编号取原文、当轮即取即用、翻不动的不装。

### US-R1 按编号区间读回原文（P0）

> 依赖：编号地基（压缩域 ADR-007，已落地）；数据源为完整会话记录（前提 1）。

作为长任务用户，我想让模型在忘了旧细节时自己把旧原文翻回来看，以便我不用复述、它不靠转述瞎编。

验收：
- Given 一段对话已被压缩摘要取代（模型可见历史里只剩摘要与编号区间），When 模型在执行任务中请求"第 #60 至 #70 条"的原文，Then 拿到该区间内每条的原文（谁说的、编号、内容），这些内容作为本轮任务中的普通查询结果回到模型手上
- Given 读回发生在回合进行中，When 结果落位，Then 它出现在本轮对话的**末尾**，此前的对话逐字不动——翻旧账不给进行中的对话引入任何扰动
- Given 请求的区间里有一部分编号属于"已彻底丢弃、不可找回"的清单，When 读回，Then 可找回的部分如实给出，不可找回的编号被明确列出并说明"这部分永久丢失"——不编造、不含糊带过
- Given 请求的编号超出本会话累计的范围（还没发生过这么多条），When 读回，Then 得到明确的"编号不存在"提示与当前有效范围，不返回空内容让模型猜
- Given 请求的区间过大，When 读回，Then 按分页返回（单次读回量有上限、可继续翻页），并告知还有多少未读——读回是翻账，不是把整个历史搬回来

## 2. Epic E2：压缩后导航卡片（P1）

> 解决"模型知不知道有什么可翻、该翻哪页"。原则：卡是路标不是账本——只导航，不承载转述。

### US-R2 目录卡片（P1）

> 依赖：US-R1（卡片的编号区间以读回为兑现出口）；编号地基（压缩域 ADR-007）。

作为长任务用户，我想让模型手边有"被覆盖内容目录"，以便它想翻旧账时知道该翻哪页，而不是连有什么都不知道。

验收：
- Given 一次压缩落位，When 生成目录卡片，Then 卡片列出：本次被覆盖段落的编号区间、段内条目的简短摘要行（每行带编号，能据此直接发起读回）
- Given 后续再次压缩，When 落位，Then 只**新增**一张目录卡片描述新被覆盖的段落；既有目录卡片的内容**原样保留、不改写**（旧账的目录不随新整理而重写）
- Given 模型拿到目录卡片，When 它需要某段旧内容，Then 能按卡片上的编号区间与摘要行发起读回（US-R1），卡片摘要行与读回所得原文对得上
- Given 卡片的生成时机（每次压缩后自动生成 vs 用户或模型需要时再生成），When 裁决，Then 触发策略为待裁决项（ROADMAP 开放项 5）；无论哪种策略，已生成的卡片必须与当次压缩的覆盖范围一致，不出现描述已不存在范围的过期卡片

### US-R3 现状卡（P1）

> 依赖：同 US-R2（与目录卡片同源派生）。

作为长任务用户，我想让模型随时知道"当前窗口外还压着什么、各段是什么"，以便它对旧账全貌有数、翻起来有的放矢。

验收：
- Given 会话经历过压缩，When 每次整理落位，Then 现状卡被**重写**为最新全貌：当前窗口外共压着几段、各段的编号区间、每段一句话概要（这段在做什么）、合计规模；会话内**始终最多一张**现状卡
- Given 会话从未发生压缩，When 运行，Then 没有现状卡（不出现"目录为空"的占位物）
- Given 多次压缩叠加，When 查看现状卡，Then 各段区间互不重叠、按时间有序，能对上"哪段是什么时候被压掉的"
- Given 现状卡与目录卡片描述同一段落，When 对照，Then 两者一致（同一事实源，不各说各话）：现状卡是"全貌一张图"，目录卡片是"逐段明细页"

## 3. Epic E3：历史检索（P1）

> 解决"不知道页码时怎么找"。原则：搜到的是路标（编号 + 摘要行），读回才是正文。

### US-R4 搜历史（P1）

> 依赖：US-R1（搜索结果以读回兑现）；数据源为完整会话记录（前提 1）；搜索范围与检索性能为待裁决项（开放项 2/3）。

作为长任务用户，我想让模型在完整历史里按关键词检索（包括被压缩覆盖的部分），以便它按话题找旧事，而不是靠编号瞎猜区间。

验收：
- Given 关键词出现在已被压缩覆盖的原文中，When 模型搜索，Then 返回匹配条目的编号与摘要行，能据此直接发起读回
- Given 关键词无任何匹配，When 搜索，Then 明确告知无结果（不返回空、不装作搜过）
- Given 搜索结果过多，When 返回，Then 结果有上限、可分页，并按与查询的相关度排序呈现
- Given 搜索范围（仅本会话 vs 跨会话），When 裁决前，Then 不实现跨会话（范围为待裁决项，开放项 2）；若裁决为包含跨会话，则每条结果必须标注来自哪个会话
- Given 搜索进行中，When 用户继续对话，Then 搜索不得阻塞正常对话（慢可以是慢，不能卡死会话——性能路径见开放项 3）

## 4. 权限与诚实边界（横切验收）

- Given 读回/搜索能力被纳入模型的工具清单，When 模型调用，Then 必须先经过与其他工具一致的调用校验环节；具体策略（自动放行 vs 需用户确认）为待裁决项（开放项 4），但无论哪种：被禁用时拦截并说明理由，重新放行后立即可用（拦截与放行对称），不存在绕过校验环节的旁路
- Given 工具被禁用，When 模型尝试调用，Then 得到明确的拒绝结果（不是静默无结果，也不是"点了报错"的坏入口）
- Given 读回/搜索执行，When 取数，Then 只读取既有会话记录本身——不发起任何新的模型调用、不读取会话记录以外的数据（本地文件、网络等）
- Given 卡片描述与实际压缩范围、读回内容与编号所指，When 任一对照，Then 逐一相符（模型看到的每个编号都能在记录里归位到唯一一条原文）

## 5. 非功能需求（NFR）

| # | 需求 | 说明 |
|---|---|---|
| NFR-R1 | 读回不搅动既有对话 | 读回内容落在当轮对话末尾、此前内容逐字不动——翻旧账对进行中的对话零扰动（与缓存计费的关系见架构文档） |
| NFR-R2 | 读回延迟 | 体验目标"即翻即得"（不劣于一次普通文件读取的体感）；具体延迟预算为待裁决项，不做超出体验目标的承诺 |
| NFR-R3 | 大日志检索性能 | 长会话（大体量记录）下的检索路径（顺序扫描 vs 检索索引、索引形态与数据量阈值）为**待裁决项**（开放项 3）——本域不预设承诺，只钉死体感底线：搜索不得阻塞正常对话 |
| NFR-R4 | 读回的量上限 | 单次读回有上限、可分页——读回是"翻账"不是"把整个历史搬回来"；上限默认值随实现批定 |
| NFR-R5 | 能力诚实 | 读回/搜索/卡片要么完整可用、要么不存在——不交付"能调但报错"的入口；不可找回的条目必须如实标注（不可找回 ≠ 静默跳过） |

## 6. 依赖与前提清单（背景事实）

| 依赖 | 提供方 | 状态口径 |
|---|---|---|
| 条目编号 + 替换区间 + 丢弃清单标注 | 上下文压缩域（ADR-007） | 已落地（Rust）；本域只消费、不重定义 |
| 完整且只增不改的会话记录 | 会话持久化域（wire 日志） | 已落地（三引擎共有） |
| 工具调用校验管线（强制点） | 工具调用域 | 已落地；本域工具接入同一管线 |
| TS 引擎 | — | 无编号地基、无读回能力（rust-first 提案不要求对齐；现状见 context §1.3） |
