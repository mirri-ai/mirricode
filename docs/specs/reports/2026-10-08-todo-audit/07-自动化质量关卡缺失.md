# 07 · Rust 侧的质量关卡没有上自动化流水线

## 背景

Rust 核心有一套很严格的质量关卡，每次提交前必须在本地跑四件套：

1. 全量测试（数万条，当前基线约 4800+ 通过）；
2. 代码风格与常见问题扫描（零告警才算过）；
3. 「内核不做输入输出」的自检脚本——这是产品架构的一条铁律（内核层必须与操作系统解耦，才能支持多种运行环境），脚本自动扫描代码里违规的直接系统调用；
4. 版本一致性检查。

团队内部的执行台账里明确记着：**「质量门禁（本地，CI 暂缺）」**——关卡只有自觉，没有强制。

## 现状（2026-10-08 核验）

检查了自动化流水线的全部配置文件，Rust 相关的检查只有两项：一个「两侧引擎对同一批测试样本给出相同结果」的定向测试，和一个版本号一致性检查。**四件套中的主力——全量测试、问题扫描、内核纯净度自检——都没有进流水线。**

这意味着：如果有人（或某个自动化代理）提交代码时没在本地跑关卡，问题会一路带到主干，直到下一个人本地跑全量时才炸出来。

## 问题与影响

- 随着参与开发的自动化代理和并行批次越来越多，「忘了跑关卡」的概率在上升，而这恰恰是关卡要防的事情。
- 数万条测试在本地全量跑一遍耗时可观，开发者会倾向于「只跑我改动的部分」——全量守卫事实上靠自觉维持。
- 主干一旦被污染，回溯排查的成本远高于流水线先跑一遍的成本。

## 期待的最终形态

- 每次提交 / 每个合并请求自动触发四件套（全量测试可以允许拆分或分级——比如快速关卡拦明显问题，全量夜间跑）。
- 关卡不过，合并被自动拒绝，无需人工把关。
- 本地与流水线跑的是同一套命令，避免「本地过、线上不过」的双标准。

## 大致要做的事

1. 在现有流水线里新增一个 Rust 质量任务：跑问题扫描（较快，适合每次提交）+ 内核纯净度自检（同样快）。
2. 全量测试因耗时长，两个方案任选其一：
   - 方案 A（推荐）：作为合并的必过关卡，接受流水线耗时增加；
   - 方案 B：每日定时跑全量，提交时只跑快速关卡，失败时自动在对应任务上标注。
3. 缓存策略：流水线已有 Rust 构建缓存，测试任务复用它即可。
4. 跑通一次真实验证后，在内部执行台账里把「CI 暂缺」的注记改掉。

## 规模与风险

小。基础设施（流水线、缓存、Rust 环境）全部现成，纯粹是「把已有命令搬进流水线」的配置工作。风险点是全量测试的耗时与稳定性（历史上有个别依赖真实终端的测试偶发不稳定），按方案 A/B 的取舍处理即可。
