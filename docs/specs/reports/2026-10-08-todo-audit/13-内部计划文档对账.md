# 13 · 内部计划文档的「对账」卫生问题

## 背景

团队用带勾选框的计划文档管理每一批开发工作，约定「完成后勾选、以状态台账为唯一真源」。但实际执行中，负责实施的代理完成任务后**不负责勾选**，由主持者事后统一勾——这个补勾的动作经常没有发生。审计发现了成片的「实际已完成但文档显示未开始」的漂移。

## 现状（2026-10-08 核验）

实测抽查的漂移案例：

| 计划文档 | 勾选状态 | 实际状态 |
|---|---|---|
| 目标模式停止冻结计划（10 号） | 0 / 32 勾选 | 提交记录显示 2026-09-17 已全部落地 |
| 蜂群成员等待状态计划 | 1 / 33 勾选 | 领域台账显示该阶段 2026-09-16 已完成 |
| 模型裁定链计划（11 号）等 | 0 勾选 | 台账记录 21 个提交已落地 |
| 多个旧版程序级计划 | 0 / 10、0 / 8、0 / 39 勾选 | 或已落地、或已被后续方案取代（需逐个甄别） |

对照之下，**状态台账（ROADMAP）是准确且勤更新的**——问题只出在计划文档这一层。

## 问题与影响

- 对**人类接手者**：打开一份计划文件看到满页空勾选框，第一反应是「这事还没做」——要么重复劳动，要么错误汇报进度。
- 对**自动化代理**（风险更大）：代理会严格按文档字面执行。给它一份显示未完成的计划，它可能把已落地的功能重做一遍、甚至覆盖掉后来演进的实现。仓库的协作约定里明确要求代理「以文档+代码双核对」，但不是每个代理都会做。
- 审计本身也被拖累：甄别「真未做」和「做了没勾」花费了本报告相当一部分核验时间。

## 期待的最终形态

- 计划文档的勾选状态与实际进度一致——要么补勾到位，要么对已完成的计划在文件头加一行醒目的「本计划已于 X 年 X 月 X 日全部完成，勾选状态不再维护，以状态台账为准」。
- 长期机制：把「完成即销账」纳入每个批次的收尾清单（完成一个任务勾一个，而不是攒到最后），或者在流程上规定计划文件只保留引用、进度一律看台账。

## 大致要做的事

1. 盘点 `plan/` 与 `docs/specs/*/plans/` 下所有带勾选框的计划文档，逐份与状态台账、提交记录对照，分三类：已完成（补勾或加完成声明）、已废弃（标注取代关系）、真未完成（保持原样）。
2. 已完成的文件在**开头第一段**加完成声明与日期——这是成本最低、防误读效果最好的做法（代理和人都先读开头）。
3. 顺手在协作约定的文档里补一句：「计划文件的勾选状态不可信时以状态台账为准」的提醒已有，补充「接手任何计划前先核对台账」的强制步骤。

## 规模与风险

小，但琐碎——约十几份文档、上百个勾选框需要人工核对（可以用「台账说完成 + 提交记录存在」为依据批量处理，不必逐任务回溯细节）。无代码风险。建议一次性清完，之后维持「批完成即销账」的习惯即可。
