# 08 · 工具插件（MCP）体验层的剩余工作

## 背景

MCP 是让 AI 助手连接外部工具（数据库、浏览器、设计软件等）的开放协议。产品的 MCP 支持分四个阶段推进：配置管理、连接池管理、热更新已完成；**第四阶段「体验层」做了一半**——安全授权登录机制已落地（服务器要求登录时，AI 会引导用户完成整套授权），但剩下几项体验优化还没开工。

这些不是功能缺失（当前一切可用），而是「用起来更省资源、更顺手」的打磨项。状态记录在 MCP 领域的执行台账里，审计时核对了台账与代码，台账描述属实。

## 现状（2026-10-08）

四个未开工的缺口：

1. ~~**懒启动**~~：**已裁决不做（2026-10-12，SDR-008/ADR-013）**。核验发现两个前提不成立——连接本来就不阻塞启动（服务启动后在后台连接，用户创建会话/打开工作区零等待），且服务器连上时有实时状态通知。更重要的是：中途连上会改变对话的工具清单（发给模型的内容前缀的一部分），破坏供应商的提示缓存命中率；而现状「启动后即全部连上、首轮对话前基本就绪」恰好保证了前缀稳定。
2. ~~**工具清单缓存**~~：**同上裁决不做**。清单只在连接建立时清点一次，连接保持期间天然驻留在内存里——连接本身就是缓存，不存在重复清点成本；服务器静默更新的场景已有「手动重连强制刷新」逃生门。
3. ~~**无会话场景下的授权入口**~~：**已裁决搁置（2026-10-12，SDR-008 补遗）**。会话内授权流程完整可用，设置页主动发起属便利项；触发条件与 web 事件消费的既有决策同构——真实需求出现再立项。
4. ~~**令牌存储位置不统一**~~：**已裁决不做（2026-10-12，SDR-008 补遗）**。不单独迁移，随旧引擎退役自然消失。

另外有一项**有意搁置**的决策（不是欠账，说明如下）：引擎已经能推送「工具服务器状态变化」的实时事件，但网页端选择继续用「打开页面时拉取一次」的方式获取状态。台账里记录了明确的触发条件——当「用户在设置页外改了配置需要即时反映」这类真实需求出现时再接线。这是经过权衡的产品决策，不应重新立项。

## 问题与影响

- ~~懒启动缺失意味着启动慢、白占资源~~：**证伪**——启动已零等待（后台连接不阻塞任何操作），原问题描述基于对现状的误判。
- ~~无缓存意味着重复的握手开销~~：**证伪**——清单只清点一次，连接期间驻留内存。
- ~~令牌位置不统一只影响过渡期用户~~：已裁决不做（随旧引擎退役一并消失）。

## 期待的最终形态

- 工具服务器**启动后即后台全连**（现状即终态，不阻塞任何请求；连接状态经事件实时通知）。
- 授权在会话内由 AI 引导完成（现状即终态；无会话主动发起入口按裁决搁置）。
- 令牌存储随旧引擎退役自然收敛（不单独迁移）。
