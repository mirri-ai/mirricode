## 1. 做对了的事（值得固化为习惯）

### 1.1 指纹先于代码

第一天先跑 vmmap/leaks 得到"海量小对象、零泄漏、6.4G dirty 空洞"的指纹，直接划掉了"泄漏"这个最大类别。三阶段调查每一步都先量化后行动，**读代码永远是最后一步**。

### 1.2 报告先行

用户要求"整理一个不懂项目的人能看的分析文档"——写外部视角文档强迫暴露了假设的不严密处；该文档发给外部帮手后，其建议虽大部分被证伪，但 MallocStackLogging/footprint-日志对齐两个方法被采纳，后者直接产出了"打字期间也涨"的关键发现。

### 1.3 数字对账作为防幻觉门

两次关键转折都靠算术：
- 排除 summary 主因：15 次 × 16MB = 240MB ≠ 26GB，差两个数量级 → 继续找；
- 确认 task.list 主因：2.6MB × 1Hz × 30min ≈ 4.7GB 响应 + 3-5× 中间态 ≈ 7-16G 峰值，且 nettop 24GiB 出站对账吻合 → 收网。

### 1.4 handoff 作为交付物

最后接手 S5 的会话在零上下文下不但执行了方案，还**发现并修复了原方案遗漏的 getTask 1+N 放大**。原因：handoff 文档把实锤证据与推测方案分开写，接手者有能力挑战方案而非机械执行。调查的产出包括"让执行者能超越自己的知识结构"。

## 2. 做错了/浪费的事（同样值钱）

### 2.1 坏对照组污染分析（最大单次浪费）

一度用旧二进制（01:08 构建，修复之前）"复现"了 26G 并抓了多轮栈样本，深挖后才发现对照组本身就错。**教训：对照组先验证自变量成立**（mtime 对 commit、特征串在不在）。

### 2.2 在隔离环境过度加码

第二阶段后期反复增加模拟复杂度（并发、完整调用序列、release 二进制）都复现不出，直到用户一句话点醒（"开发者控制台看到 task.list 超多次"）。回头看，"探针消费速度足够快，真实 Renderer 不行"这个事实出现后就应该更早转向真实环境观测，而不是继续在隔离侧堆场景。

### 2.3 早期漏看客户端轮询

第二阶段的排除清单里"订阅风暴"被排除过（当时高频 subscribe 是调查探针自身），这导致"客户端周期性行为"这个类别被过早淡化，S5 因此多绕了一天。教训：**排除一个类别时要记下"排除的是这个实例还是这个类别"**。

### 2.4 微基准的安慰剂

F1 的 2000 倍提速基准完全真实，但它测的是时间不是内存，导致第一轮修复后存在"问题应该解决了"的错觉。**每个维度的验收标准要对应那个维度**（后来才补上"峰值 < 1G"这类数值标准）。

## 3. 架构层沉淀（review 检查项）

1. **列表 API 必须是摘要视图**——本次三个放大器（summary 全量 replay、task.list 全量 output、message.list 全量拷贝）是同一反模式的三次实例。任何新 list RPC 出现"返回实体完整序列化"就该拦下。
2. **轮询最小化 + 事件流正道**：周期调用只拉活跃子集，状态迁移靠事件，详情靠单实体端点。
3. **队列双上限**：帧数上限不等于字节上限；resync 类重推需要冷却（信号照发、重推停止）以断反馈振荡。
4. **单遍纪律**：一次读盘派生所有缓存（含"空"结果），消费侧 take-once。
5. **"性能通过 ≠ 内存通过"**：基准测试只测它测的维度。
