# 会话一致性 — 需求文档

> 状态：v1.1 · 2026-10-13 · 评审修订（跟随延迟锚定 5 秒、合并表述与三路合并对齐） ·
> 本文是会话一致性域需求侧的唯一事实源（内部规格文档，不进文档站构建，中文单语）。
> 产品愿景：**多入口共享一份会话数据时，看到的永远是一致的、正在发生的**——两个入口同时打开同一份会话数据，历史互不损坏、进度互相可见、想插话时能被温和而明确地拦住。
> 配套文档：技术形状见 [session-consistency-architecture.md](session-consistency-architecture.md)；现状证据（双服务并存下的缺陷清单）见 [session-consistency-context.md](session-consistency-context.md)；执行状态与批次见 [session-consistency-ROADMAP.md](session-consistency-ROADMAP.md)。
> 术语规范：另一入口（SC1）、并发修改冲突（SC2）、本地已知版本（SC3）、回合（S7）的定义见 [glossary.md](glossary.md)；本文件只使用这些规范叫法。
> 范围边界：本域覆盖**同一台机器上、共享同一份个人数据目录的多个服务入口之间**的会话数据一致性与并发行为。明确不覆盖：终端旧引擎（TUI，待重构）、TypeScript 旧核心（已冻结）、跨机器多用户场景。本域的需求以 Rust 核心（v3）的 web 与 desktop 两个入口为验收对象。

## 0. 角色定义

| 角色 | 场景 | 核心诉求 |
|---|---|---|
| **双开用户**（同时开着网页版和桌面版的同一个人） | 白天挂着桌面版，临时又开了网页版，两边看同一批会话 | 两边看到的会话列表、历史、进度是一致的；谁在跑什么一目了然 |
| **插话用户**（在另一入口正在活动时想发消息的人） | 看到 A 入口的会话在跑任务，自己也想问一句 | 被拦截时消息不丢、原因说得清、刷新后能立刻重试 |
| **旁观用户**（只看不动手的人） | 一边跑任务，另一边只浏览 | 浏览不被打扰、能实时看到对方回合的进展 |

## 1. Epic C1：跨入口可见性（P0）

> 解决"两边信息不对称"。会话数据由磁盘上同一份文件承载，任何入口的变更与活动状态，其余入口都能在秒级看到。

### US C1.1 会话列表反映另一入口的变更（P0）

作为双开用户，我想在一侧改名、归档、新建会话后，另一侧的列表不用手动刷新就对齐，以便两边的清单永远是同一份事实。

验收：
- Given 入口 A 对某会话完成改名或归档，When 入口 B 刷新或查看会话列表，Then B 看到的名称与归档状态与 A 一致
- Given 入口 A 新建了会话，When 入口 B 查看会话列表，Then 新会话可见，且"最近更新"时间反映 A 侧的写入时刻
- Given 两边都没有变更，Then 列表零额外刷新动作（无变化时不做任何事）

### US C1.2 双开会话的实时跟随（P0）

作为旁观用户，我想在一侧正在跑的回合，在另一侧打开同一会话时能看到接近实时的进展，以便决定要不要等它跑完再插话。

验收：
- Given 入口 A 的会话正在跑一个回合，When 入口 B 打开同一会话，Then B 看到完整历史以及 A 正在产生的新内容
- Given B 已打开该会话并停在前台，When A 的回合继续产生新内容，Then B 在 5 秒内逐段看到新内容出现（跟随延迟上限 5 秒，不缺段、不乱序、不重复）
- Given B 把该会话切到后台，Then 跟随暂停（不再产生同步开销），切回前台后从暂停点继续补齐、内容完整

### US C1.3 活动状态徽标（P1）

作为双开用户，我想在会话列表和会话页看到"另一入口正在此会话活动"的标识，以便不去无谓地插话。

验收：
- Given 入口 A 正在某会话产生新内容，When 入口 B 查看该会话（列表或详情），Then B 侧展示活动标识（如"另一入口正在活动"徽标）
- Given A 的活动停止（回合结束），When B 在数秒后查看，Then 徽标消失
- 徽标只反映"数据正在变化"这一事实，不声称知道对面是谁、在干什么

## 2. Epic C2：并发修改冲突的检测与拦截（P0）

> 解决"两边同时动手"。拦截只发生在**提交动作**上；浏览永不拦截。

### US C2.1 提交前冲突拦截，消息不丢失（P0）

作为插话用户，我想在另一入口刚改了这个会话时提交消息会被拦下，且我的消息原样回到输入框，以便确认刷新后的内容再决定重发。

验收：
- Given 入口 B 提交消息时检测到该会话存在 B 未同步的变更（来自另一入口），When 提交动作发生，Then 本次提交被拒绝执行、**消息内容原样回填输入框**、界面提示"该会话可能正在被另一入口使用或已被修改，已为你刷新"
- Given 拦截发生，Then 磁盘上不残留本次提交的任何半成品（既没有消息记录、也没有回合开始记录）
- Given 拦截后 B 完成刷新，When 用户再次点击发送，Then 按正常提交处理（此时若对面又有新变更，则再次拦截，规则对称）
- Given B 提交时无未同步变更，Then 提交正常执行，无感知
- 提示文案对成因保持中性（"可能正在被使用或已被修改"），不区分"对面在跑"与"对面刚写过"

### US C2.2 回合进行中的冲突中止（P0）

作为双开用户，我想在本入口回合跑到一半、发现另一入口开始写同一会话时，系统立即中止本回合，以便两个代理不会同时在我的文件和终端里动手。

验收：
- Given 入口 B 的回合已在进行中，When 检测到另一入口对同一会话写入新内容，Then 本回合立即中止：停止后续工具操作、在会话中留下一条可读的中止记录、通知用户
- Given 中止发生，Then 已完成部分的记录完整保留（历史不回滚），用户刷新后可见全貌
- Given 本入口回合进行中且对面无写入，Then 回合不受任何影响照常执行
- 中止检测的检查粒度覆盖回合内的每个执行间隙，检测本身的耗时对用户不可感知

### US C2.3 冲突的可解释性（P1）

作为双开用户，我想知道每次拦截/中止时对面发生了什么，以便判断是等一等还是直接重发。

验收：
- Given 拦截或中止发生，When 用户查看提示详情，Then 至少能看到"检测到另一入口的新内容"这一事实与刷新后的会话现状
- 提示中不出现内部实现词汇（进程名、文件名、技术机制名）

## 3. Epic C3：元数据与索引一致性（P0）

> 解决"后写者覆盖"与"清单互相打架"。会话元数据（标题、归档、自定义字段）与列表索引在双入口并发下不互相丢更新。

### US C3.1 元数据并发合并（P0）

作为双开用户，我想两侧同时改同一会话的不同元数据时两边都保留，以便不会出现"我在桌面改的名字被网页侧一笔抹掉"。

验收：
- Given 入口 A 改了标题、入口 B 在几乎同时归档了同一会话，When 两边都完成后查看，Then 标题是 A 的新标题**且**归档状态是 B 的设置——两者都生效
- Given 同一字段被两边先后修改，Then 后写入者生效（按三路合并规则），不整份覆盖
- Given 单侧修改无并发，Then 行为与现状完全一致（无感知）

### US C3.2 会话列表跨入口不丢行（P0）

作为双开用户，我想两个入口同时维护各自的会话清单缓存时，列表永不丢会话、永不出现"两边看到的集合不一样"。

验收：
- Given 入口 A 与 B 同时启动并对齐清单，When 任意一侧新建、删除、归档会话，Then 稳定后两边列表集合一致，与磁盘真实状态一致
- Given 两边同时做清单维护动作（同时刷新、同时归档），Then 维护过程互相排队完成，结果不互相覆盖、不互相删行
- 清单永远是磁盘真实状态的缓存：任何时刻丢弃清单缓存重建，结果与磁盘一致

## 4. Epic C4：性能与开销预算（P1）

> 同步机制自身的成本必须有界，且不随会话体量增长。

### US C4.1 跟随开销与历史体量无关（P1）

作为双开用户，我想长会话（几十上百 MB 历史）的双开跟随开销与短会话无异，以便长会话不因此变慢。

验收：
- Given 一个历史很长的会话，When 另一入口跟随其新内容，Then 每次同步只处理自上次同步点以来的新增内容，不重读、不重算历史
- Given 某次同步时读到尚未写完整的最后一段，Then 该段留到下次同步补齐，不报错、不丢段

### US C4.2 同步开销只花在前台（P1）

作为双开用户，我想没在看会话时系统不为它花任何同步成本，以便后台挂几十个会话不影响整机。

验收：
- Given 会话在入口 B 不在前台（未打开/切走），Then 不为其产生周期性同步开销
- Given 会话回到前台，Then 同步立即恢复并从暂停点补齐
