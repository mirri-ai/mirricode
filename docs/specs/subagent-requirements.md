## 0. 角色定义

| 角色 | 场景 | 核心诉求 |
|---|---|---|
| **派发者**（执行派发的主代理） | 把一个子任务交给子代理做 | 派出去能拿回结果；结果状态不能骗我；活没干完我能接着让它干 |
| **执行者**（被派发的子代理） | 干活、被打断、被恢复 | 被打断就是被打断；被要求继续时记得我之前干到哪 |
| **用户**（观察/介入的人） | 在终端/网页上看着子代理干活 | 谁在干、卡在哪、为什么失败一目了然；我要停能真停 |
| **配置者**（设置默认行为的用户/团队） | 调整时长上限、并发上限 | 默认值合理，关键项可配，配置立刻生效 |
| **集成方**（订阅生命周期回调/事件流的程序方） | 基于子代理生命周期做自动化 | 开始/结束一对一配对，没有悬挂的开始 |

## 1. Epic E1：派发与角色、型号选择

> 解决"派给谁、用什么型号干"。派发是入口，选择必须可预期、可纠错。

### US1.1 按子角色派发（P0）

作为派发者，我想指定用哪个子代理类型来干这个活（不指定时有一个合理默认），以便按任务难度选对执行者。

验收：
- Given 未指定子代理类型，When 派发，Then 使用内置默认类型，且结果中说明实际使用的类型
- Given 指定了可用的子代理类型，When 派发，Then 按该类型装配执行者
- Given 派发者所在角色的可派发范围已声明（名单），When 指定名单外的类型，Then 派发被拒绝，并说明可用范围（不是静默换成默认）
- Given 指定了不存在的类型，When 派发，Then 派发被拒绝并给出可用的类型清单

### US1.2 指定型号与纠错（P0）

作为派发者，我想为某个子代理临时指定型号（不指定则沿用默认规则），以便任务难度匹配型号投入。

验收：
- Given 指定了合法型号，When 派发，Then 子代理按该型号执行，结果中报告实际型号
- Given 不指定型号，When 派发，Then 按"指派型号 → 该类型的默认型号 → 沿用派发者型号"的既定规则确定，并在结果中报告
- Given 指定了非法/不存在的型号，When 派发，Then 派发被拒绝并列出可选型号，而不是悄悄退回默认（不静默降级）

### US1.3 派发前置信息（P1）

作为派发者，我想在派发入口看到可用的子代理类型与可选的型号清单及其适用场景，以便选择时不用碰运气。

验收：
- Given 派发入口的说明面展示类型清单，When 查看，Then 每个类型含名称、一句话用途、适用时机、默认型号与型号能力提示
- Given 型号清单有内容说明，When 查看，Then 每个型号含别名、用途一句话、上下文规模与能力提示；无用途说明的型号不展示（避免误导）

## 2. Epic E2：前台执行与结果

> 解决"派出去后怎么拿回结果"。前台是默认路径：派发者原地等待，结果必须说真话。

### US2.1 阻塞等待与结果结构（P0）

作为派发者，我想在前台等待子代理干完并拿到结构化结果，以便判断下一步。

验收：
- Given 前台派发，When 子代理完成，Then 返回结果含：子代理标识、实际类型、实际型号、终态（完成/失败/中断/超时/停止）、内容摘要
- Given 结果文本为空，Then 明确标注"无产出"而非返回空白（可辨识的占位说明）

> 注（2026-09-12）：结果摘要的**可用性**保障（不达标自动续问提炼、截断定局失败）由 SDR-004 增补。

### US2.2 状态真实性（P0）

作为派发者/用户，子代理的终态必须与真实结局一致，任何中断都不能伪装成成功。

验收：
- Given 子代理被用户中断或停止，When 返回结果，Then 终态为"已中断/已停止"并附原因，**不得**显示为"已完成"
- Given 子代理超时，When 返回结果，Then 终态为"已超时"并说明时长上限与处置结果（见 E5）
- Given 子代理执行中报错，When 返回结果，Then 终态为"失败"并附失败原因
- Given 子代理正常完成，When 返回结果，Then 终态为"已完成"

### US2.3 续作入口提示（P0）

作为派发者，当子代理失败/中断/超时/或者我认为活还没干完，我想知道拿什么标识可以接着让它干，以便不会因为找不到入口而重开一份。

验收：
- Given 任一非完成终态返回，When 查看结果，Then 附"续作指引"：指明用哪个子代理标识继续（并注明不能与类型选择同时使用）
- Given 结果展示续作指引，Then 指引指向的续作能力真实可用（见 E4）——指引与实现不一致即为缺陷

### US2.4 运行中的可见性（用户）（P1）

作为用户，我想在前台派发运行期间看到子代理在干什么，以便判断是否值得干预。

验收：
- Given 前台子代理运行中，When 查看界面，Then 看到：身份与类型、当前状态、工具调用与进展、用量指标（可展开）
- Given 子代理运行中输出中间文本或思考过程，When 查看，Then 界面按类别区分呈现并实时追加

## 3. Epic E3：后台执行

> 解决"不占着派发者等"。后台化让派发者继续干别的，但返回的控制权必须配套真实可靠的后台管理能力。

### US3.1 后台派发与立即返回（P0）

作为派发者，我想把子代理放后台跑并立刻拿回控制权，以便不阻塞当前工作。

验收：
- Given 选择后台运行，When 派发，Then 接口立即返回：后台任务号、子代理标识、实际类型与型号、当前状态"运行中（后台）"
- Given 后台返回的结果，Then 附续作指引与取结果指引（怎么查、怎么停、什么时候会收到通知）
- Given 后台运行可用性受当前会话能力约束（查看/停止后台任务的入口不可用），When 请求后台运行，Then 请求被拒绝并说明前提缺失（入口与能力不一致即为缺陷）

### US3.2 后台任务上限（P0）

作为配置者/I（用户），后台任务不能无界堆积：超限时新后台派发被拒绝，前台不受影响。

验收：
- Given 当前后台运行数已达配置上限，When 再次请求后台派发，Then 拒绝并说明原因（提示现有任务可停或转前台）
- Given 后台未达上限，When 请求后台派发，Then 正常接受
- Given 上限未配置，Then 使用内置默认上限

### US3.3 后台结果获取与停止（P0）

作为派发者/用户，我想在后台任务进行中查进度、结束后取结果、必要时停掉它，并且"停止"必须真实停止。

验收：
- Given 后台任务运行中，When 查询，Then 返回当前状态与已产出内容（含截断标记，内容超限时保留最近部分并注明）
- Given 后台任务已结束，When 查询，Then 返回终态与完整可读结果
- Given 请求停止一个运行中的后台子代理，When 停止，Then 该子代理**真正停止**（不再产生执行与用量），状态置为"已停止"且不再被后续事件改写
- Given 停止请求到达前任务恰好自然结束，Then 以先定局者为准，状态不被覆盖
- Given 重复停止已结束的任务，Then 返回其当前终态并注明"已处于终态"，不重复停止

### US3.4 完成自动通知（P1）

作为派发者，我想后台子代理定局时收到通知而不是轮询，以便不空耗注意力。

验收：
- Given 后台子代理完成/失败/被停止/被丢失（会话重启后失去归属），When 定局，Then 自动产生一条通知，含任务号、子代理标识与终态/原因
- Given 会话重启且存在重启前未定局的后台任务，When 恢复，Then 该任务按"已丢失"通知并可续作（对话保留）

## 4. Epic E4：续作（resume）

> 解决"活没干完怎么办"。续作是失败恢复的第一入口：带着记忆继续，远比丢弃记忆重新派发便宜、完整；其契约必须严格、可信。

### US4.1 只认派发者（P0）

作为派发者，我只能续作我自己派出去的子代理——别人派的活不能被我半路接管。

验收：
- Given 续作目标不在我的派发范围（他人派发/不是子代理），When 请求续作，Then 被拒绝并说明原因
- Given 续作目标是本会话内我曾经派发的子代理，When 请求续作，Then 允许

### US4.2 运行态约束（P0）

作为派发者，同一时间一个子代理只能有一个执行流。

验收：
- Given 子代理正在运行，When 请求续作，Then 被拒绝（说明正在运行，不能并发双跑）
- Given 子代理空闲（完成/失败/中断/超时/后台已终态），When 请求续作，Then 成功：沿用其既有对话与记忆继续执行新指令
- Given 续作成功，Then 返回与首次派发同结构的结果（含新一次的终态与用量）

### US4.3 续作复用既有记忆与成本（P0）

作为派发者，我想续作时让子代理带着之前的全部记忆继续干活，以便已完成的工作不重来、成本远低于重新派发一个从头开始的新子代理。

验收：
- Given 子代理此前已产生结论并完成若干动作，When 续作，Then 新执行以既有全部对话为起点，子代理可直接引用其先前结论与进度（无需重述）
- Given 中断前已完成的动作，When 续作，Then 不重复执行——续作只继续未竟工作，已入记忆的动作再次执行即为缺陷
- Given 续作后的首次请求，Then 输入上下文包含既有全部对话，复用部分按既有上下文缓存计费，不产生重建完整上下文的输入成本（缓存是否命中以用量数据如实反映为准，系统不承诺命中）
- Given 同一任务分别走"续作"与"重新派发"，Then 续作复用既有上下文，不产生重新构建完整上下文的输入成本（缓存命中的额外节省以用量数据如实反映）

### US4.4 中断点未竟动作的衔接（P1）

作为派发者，子代理在某个动作进行中被中断时，我想续作后它知道那个动作的结果可能没保住，以便不被半成品欺骗。

验收：
- Given 中断发生在动作执行过程中且其结果未进入记忆，When 续作，Then 子代理被提示重做该动作，且不会把未竟动作当作已完成（此为提示级衔接——是否重做由子代理依记忆判断，非强制不变量）
- Given 未竟动作带外部副作用（如写文件、发起请求），When 重做，Then 以记忆为凭：有结果则引用、无结果则重做，重做事实如实可见

### US4.5 失败恢复闭环（P0）

作为派发者，任何"活没干完"的终态都必须有真实的续作出口——提示存在的地方，能力必须存在。

验收：
- Given 子代理失败/中断/超时/后台丢失，When 按结果中的续作指引发起续作，Then 续作成功，不可出现"指引存在但续作报错"
- Given 进程重启后恢复会话，When 续作重启前派发的子代理，Then 成功（其对话跨重启保留）

### US4.6 续作与类型选择互斥（P1）

作为派发者，续作不需要重新选类型——子代理保持自己的类型。

验收：
- Given 请求续作，When 同时指定了子代理类型，Then 请求被拒绝（提示续作按既存类型，不能同时指定）
- Given 续作请求未带型号参数，Then 沿用该子代理此前使用的型号（不跟随派发者当前型号变化）

### US4.7 续作与重新派发的边界（P2）

作为派发者，当既有记忆不可信或延续价值低时，我想明确选择"重新派发"而不是续作，以便不被陈旧上下文误导。

验收：
- Given 既有子代理记忆存在，When 分别选择续作与重新派发，Then 两种路径可区分：续作沿用记忆；重新派发从零开始、记忆互不污染
- Given 选择重新派发，Then 新身份的记忆与用量归因独立于旧身份

## 5. Epic E5：时长上限与中断

> 解决"子代理失控怎么办"。时长上限是预算闸门，中断是人的最后手段；两者都必须真实生效。

### US5.1 时长上限与配置（P0）

作为配置者，我想给子代理运行时长设上限（全局默认 + 环境覆盖），以便控制失控成本。

验收：
- Given 未配置时长上限，Then 使用内置默认（约 2 小时）
- Given 配置了时长上限，Then 对每次派发生效；环境覆盖优先于配置文件，且环境覆盖不写回配置文件
- Given 更换时长上限配置，Then 新派发立即按新值生效（存量运行中的任务不受影响，或按既定策略处置——见裁决点 Q1）

### US5.2 超时处置（P0）

作为派发者/用户，子代理超过时长上限时，处置结果必须真实、可说明、可续作。

验收：
- Given 前台子代理超过时长上限，When 定局，Then 按既定处置（停止或转后台，见裁决点 Q1）执行，返回终态"已超时"、说明时长与处置结果，并附续作指引
- Given 批量派发中单个子代理超过时长上限，When 定局，Then 仅该成员按超时处置，其余成员不受影响

### US5.3 用户中断即时生效（P0）

作为用户，我想中断一个正在运行的前台子代理，并且中断立刻、真实地生效。

验收：
- Given 用户发出中断，When 中断前台子代理，Then 子代理停止执行（不产生后续调用与用量），派发者收到"已中断"，与启动前的状态事件闭合
- Given 中断事件发生时子代理恰好在写文件等收尾，Then 以中断为终态（已完成动作不回溯），不再启动新动作

### US5.4 停止=真实停止（P0）

作为用户/派发者，界面或工具上一切"停止"语义都对应真实停止，杜绝假停止。

验收：
- Given 任何入口（后台任务停止、批量中止、会话关闭）请求停止子代理，When 停止，Then 执行流被真实终止，且该终态不被后续完成事件改写

## 6. Epic E6：批量派发

> 解决"一堆相似的小活怎么高效派"。批量派发是并发调度的主战场：节奏、自愈、诚实的结果呈现。

### US6.1 模板批量派发（P0）

作为派发者，我想用一个模板 + 一批条目批量派发同类型子代理，以便一行一次派一堆。

验收：
- Given 模板含条目占位符且条目数 ≥ 2，When 批量派发，Then 每个条目展开为一个子代理，各自独立执行（同类型、可用同一型号选择规则）
- Given 条目与续作名单同时提供，When 批量派发，Then 续作名单的成员先启动，再启动新条目
- Given 条目展开后出现两份相同任务内容，When 批量派发，Then 请求被拒绝并指明重复（批量派发要求成员可区分）
- Given 条目为 1 条且无续作名单，When 批量派发，Then 被拒绝（提示单条走单个派发）
- Given 条目或续作成员合计超过上限（缺省 3，可经 `[subagent] maxSwarmItems` 或 `MIRRI_AGENT_SWARM_MAX_ITEMS`/`MIRRICODE_AGENT_SWARM_MAX_ITEMS` 覆盖，`0` = 不限——见 SDR-012），When 批量派发，Then 被拒绝

> 注（2026-09-12）：本条"续作名单"的语义已由 SDR-004 扩展为"成员标识 → 逐成员续作指令"的映射（每成员可携带专属指令）。

### US6.2 并发节奏（P0）

作为配置者/派发者，批量派发要避免"一窝蜂"：启动有节奏，并发有上界。

验收：
- Given 批量派发开始，When 观察启动，Then 首批少量成员立即启动，随后放缓节奏逐个启动（不全部同时开跑）
- Given 并发上界已配置（环境变量），When 批量派发，Then 运行中成员数不超过该上界；未配置时使用内置默认
- Given 运行中成员完成，When 调度，Then 释放的槽位按节奏补充新成员

### US6.3 限流自动恢复（P0）

作为派发者，批量执行遇到服务限流时，系统应自动恢复而不是让任务成片失败。

验收：
- Given 某成员因限流失败，When 批量执行，Then 该成员自动排队等待重试（指数递增的等待时长），并尽可能复用其已完成的进展（不从头重跑）
- Given 限流持续，When 批量执行，Then 系统自我降速（降低并发容量逐步试探），并在恢复期逐步回升
- Given 重试超过合理次数仍失败，When 定局，Then 该成员如实记为失败并说明原因
- Given 限流重试期间，Then 界面呈现"排队重试中"的可辨识状态（事件同步可见）

### US6.4 批量结果诚实呈现（P0）

作为派发者，批量结果要让我一眼分清：谁成了、谁败了、谁被打断、谁根本没启动。

验收：
- Given 批量定局，When 查看结果，Then 逐成员呈现：成员内容、子代理标识、终态（完成/失败/中断/超时/停止），且**中断与失败分开统计**
- Given 批量被取消/中止，When 查看结果，Then 未启动成员与已启动成员分别标识（"未启动"可辨识），并附统一的中止原因
- Given 批量中有失败成员，When 查看结果，Then 附续作指引（指明可续作的成员标识，且续作真实可用——见 E4）
- Given 批量结果，Then 每个成员带可辨识信息（如"第几条"），界面/任务列表能区分不同成员

### US6.5 单成员失败不拖垮整体（P1）

作为派发者，一个成员炸了不应让整批失败。

验收：
- Given 批量中若干成员失败，When 其余成员正常，Then 其余成员继续执行并如实汇总；全员都失败时才整体判失败
- Given 批量中单个成员派发本身报错（如非法模型），When 处理，Then 报错并停止该批（防止批量放量前先清理输入问题），已启动成员按既定中止语义处置

## 7. Epic E7：观测与状态事件

> 没有可信观测的派发是黑盒。每一个"开始"都必须有闭合的"结束"。

### US7.1 状态事件全集与闭合（P0）

作为用户/派发者，子代理从创建到定局的每个阶段都应通过状态事件可见，且事件必须闭合（有开始必有终态）。

验收：
- Given 任何子代理被派发，When 走过生命周期，Then 事件序列含：已创建、已启动、（后台排队重试时）已排队、（终态）已完成/已失败/已中断/已超时/已停止，且每个"已启动"必有且仅有一个终态事件（重启调谐的"已丢失"经任务通知面出终态，见 US3.4/N4）
- Given 创建后未能启动（如被中止），When 定局，Then 仍产生明确的终态事件（"未启动即中止"可辨识），不留悬挂
- Given 续作路径，When 执行，Then 产生与首次派发相同的事件闭合（已启动 → 终态），不出现"只发开始不发结束"

### US7.2 界面呈现（P0）

作为用户，我想在终端/网页上看到子代理与批量执行的实时面貌，以便决定介入。

验收：
- Given 单个子代理运行中，When 查看界面，Then 呈现：身份与类型、后台/前台标记、父子归属（哪个工具调用派出来的）、状态
- Given 批量派发运行中，When 查看界面，Then 呈现成员网格：每个成员的状态（运行中/排队重试/完成/失败/中断）、序号，失败与取消有可辨识标记
- Given 子代理的工具调用与输出，When 查看界面，Then 在派发它的工具卡片下可展开：子工具调用、实时输出、用量指标
- Given 子代理失败或中断，When 查看界面，Then 网格/卡片呈现对应标记与原因，状态与真实执行一致

### US7.3 用量与成本归因（P1）

作为用户，我想知道子代理花了多少 token，以便成本可归属。

验收：
- Given 子代理完成/定局，When 查看，Then 其 token 用量（输入/输出/缓存）展示在派发处，且归因到该子代理的会话记录；批量成员按成员分别归因
- Given 子代理会话记录（其独立的完整对话与事件记录，见 A8），When 按身份回放或导出，Then 能完整查看该子代理自派发起的对话、工具调用与事件，不受主会话记录干扰（主会话回放视图仅呈现派发面镜像与摘要）

### US7.4 生命周期回调一致性（P1）

作为集成方（订阅了子代理生命周期回调的程序方），子代理的开始/结束回调必须逐次配对，包括续作与异常退出。

验收：
- Given 任意子代理生命周期（含续作、以及派发后派发者提前放弃等待的情形），When 结束或异常退出，Then 派发者侧的开始回调必有对应结束回调，不产生悬挂的开始

## 8. Epic E8：边界与一致性

> 解决"子代理与主世界的一致性"。子代理不是法外之地，也不是二等公民。

### US8.1 权限与能力一致（P0）

作为用户，子代理执行的权限约束应与派发它的主代理一致，不能因派发而变松或变紧。

验收：
- Given 派发者在某种权限模式下，When 派发，Then 子代理沿用该模式的生效规则（例外：任何差异必须有明确配置与此处说明）
- Given 后台运行能力的前置依赖缺失（见 US3.1），When 请求后台派发，Then 拒绝——界面展示的选项与底层真实能力始终一致

### US8.2 层级边界（P1）

作为集成者，子代理能否再派发子代理（多层派发）需要明确的边界。

验收（裁决性 US——产出是边界决策）：
- Given 本版本裁决为单层，When 用户配置使子代理拿到派发入口，Then 行为与文档一致：不静默失效、不崩溃（见裁决点 Q2）
- Given 未来裁决为多层，Then 按裁决放开并保持事件/续作/权限语义逐层成立

### US8.3 跨重启恢复（P1）

作为用户，会话重启后子代理身份与续作能力应保留。

验收：
- Given 会话重启，When 恢复，Then 重启前派发的子代理身份可查、可续作（对话保留）；重启前未定局的后台任务按"丢失"通知与处置

### US8.4 会话关闭收敛（P2）

作为用户/集成者，会话关闭时子代理与后台任务应有明确的收敛行为，不发生孤儿执行。

验收：
- Given 会话关闭，When 收敛，Then 全部/按配置的进行中任务被真实停止并落终态（"已停止"），重启后不出现悬挂"运行中"

## 9. 非功能需求（NFR）

| # | 需求 | 指标/约束 |
|---|---|---|
| N1 | 并发上界 | 同时运行子代理数（含批量）受配置上界约束；默认对齐现行量级（约 5），超出排队/限流 |
| N2 | 成本可观测 | 子代理 token 用量可查并可归因（成员级）；批量按成员聚合 |
| N3 | 信号真实 | 一切用户可见信号（状态、文案、图标、事件）与真实执行一致；"停止/中断/超时"三类语义必须真生效 |
| N4 | 事件闭合 | 每个"已启动"必有且仅有一个终态事件（重启调谐的"已丢失"属任务通知面语义，不占状态事件闭合承诺）；续作路径同律；事件面与既有子代理事件风格对齐 |
| N5 | 时长闸门 | 时长上限默认约 2 小时，配置/环境可覆盖；超时处置确定、可说明、可续作 |
| N6 | 限流自愈 | 批量遇供应商限流自动降速重试（指数退避），不静默吞失败、不放弃已进展 |
| N7 | 并发安全与终态唯一 | 同一子代理不允许并发双执行流；"停止"终态不被后续事件改写 |
| N8 | 单向依赖 | 本域依赖角色域（子代理由角色装配）；被协作域依赖，反向禁止 |

## 10. Out of Scope

- 多代理团队协作（共享任务板、角色间通信、仲裁、成果归集）——[collaboration-requirements.md](collaboration-requirements.md)
- 子代理的持久化会话形态（子代理不是独立会话，身份随主会话，见架构文档）
- 跨进程/多主机派发（单主机单进程内；架构留位）
- 派发目标的智能推荐（自动判断该不该派、派给谁）

## 附录：需求决策记录（SDR）

> 后续需求变更以 SDR 追加于本节（编号 SDR-0xx，含背景与动机、决策、被否决备选、影响范围），历史只追加不重写；被取代条目标记 superseded 并指向新记录。

### SDR-001 续作显式承载上下文复用与中断衔接（2026-09-09）

1. **背景与动机**：v1 基线续作需求只覆盖所有权、运行态、恢复闭环与类型互斥，未显式回答"续作为什么值得用"与"中断点未竟动作怎么办"——需求评审中提出两个产品角度（复用已完成上下文的经济性、中途中断后带记忆继续的衔接）。
2. **决策**：E4 增补 US4.3（续作复用既有记忆与成本，P0）、US4.4（中断点未竟动作的衔接，P1）、US4.7（续作与重新派发的边界，P2），原 US4.3/US4.4 顺延为 US4.5/US4.6；确立"续作"与"重新派发"为互相对照的规范叫法；执行流终态枚举跨文档统一为六元（完成/失败/中断/超时/停止/丢失，其中丢失属任务通知面语义）。
3. **被否决的备选方案**：a) 上下文复用语义并入 US4.2 不单列——成本与连续性是可独立验收的产品面，并入会稀释可测性；b) 中断衔接写成强制不变量——重做与否取决于子代理对记忆的自主判断，只能承诺为提示级衔接。
4. **影响范围**：E4 全体成员编号；US2.1/2.2/6.4/7.1 与 N4 的终态枚举；架构 §3.2/5.2 续作契约；glossary A6 警示句。

### SDR-002 子代理会话记录：独立记录流与回放可查（2026-09-09）

1. **背景与动机**：需求中"该子代理的会话记录"（US7.3）一词未定义；记录形态（存什么、在哪、如何回放/恢复）在需求层悬空。参照基线中每子代理有自己的记录流；设计裁定（ADR-002）子代理记录独立于主会话记录。
2. **决策**：确立"子代理会话记录"为正式需求词（glossary A8）：每个子代理独立的完整对话与事件记录；随需求补充按身份回放/导出的可验收项（US7.3 第二条）；主会话回放视图仅呈现派发面镜像与摘要。
3. **被否决的备选方案**：a) 子代理记录并入主会话记录（混流）——主会话日志污染、按身份回放/恢复困难；b) 不回放只保留用量归因——观测完整性（需求 E7）不完整。
4. **影响范围**：US7.3、US8.3；架构 §2.1/3.2.1；glossary A8。

### SDR-003 域范围扩展：任务管理面、定时任务与后台提问入域（2026-09-12）

1. **背景与动机**：v1 基线聚焦"子代理派发"，但后台任务管理面（任务清单/输出/停止三类操作，承载子代理、后台进程、后台提问三类任务）、任务终态通知的对话投递闭环、定时任务（按计划自动向会话注入提示）与子代理共用同一套生命周期、观测与恢复设施；这些在基线文档中缺位会导致 Rust 核心复刻时任务面残缺。会话内待办清单（TodoList）与目标（goal）工具是纯会话内计划/自治控制辅助，与后台执行生命周期零耦合（现状依据见 [subagent-context.md](subagent-context.md) §6.9），不属本域。
2. **决策**：本域范围扩展为"后台任务与子代理"全生命周期，即：既有"主代理派发与子代理生命周期"（E1–E8，维持 v1 基线不动）之上，纳入后台任务的统一管理面与终态通知闭环（E9/E10）与定时任务（E11）及消费端呈现增补（E12）；"后台提问"作为任务类型并入 E9/E10（提问的"问"界面交互归审批域，按生命周期归属切分）；待办清单与目标工具出域。跨域新术语（定时任务、后台提问、任务通知）的 glossary 注册见 ROADMAP 开放项 O5。
3. **被否决的备选方案**：a) 任务管理面独立成域——与子代理的后台派发共用状态机/持久化/通知面，拆域会重复且产生边界缝隙；b) 定时任务独立成域——其投递、持久化、会话生命周期与任务面同构，并入更完整；c) 把后台提问归审批域——提问的"问"属审批交互，但"后台化后的任务生命周期"属本域，按生命周期归属裁决。
4. **影响范围**：新 E9/E10/E11/E12；NFR 增补 N9–N15；裁决点 Q5–Q8；架构 ADR-003~007；context §6；文件头范围边界维持 v1 原文（按"增量不改写既有内容"约定，扩展后的范围以本 SDR 为准）。

### SDR-004 结果摘要可用性与批量续作名单映射（2026-09-12）

1. **背景与动机**：子代理的产出以"最后一条助手文本"作为返回结果；空摘要或过短摘要使派发者拿到不可用的结果（US2.1 只承诺了空产出有占位标注，未承诺摘要的可用性保障）。批量场景下续作成员各自处境不同，US6.1 的"续作名单"语义无法表达逐成员的差异交代（现状依据见 [subagent-context.md](subagent-context.md) §6.4/§6.5）。
2. **决策**：a) **摘要可用性**：子代理回合结束后，若最终助手文本不满足其角色声明的摘要质量线（最小长度），系统自动以续问方式追加回合直至达标或达重试上限（对派发者透明，表现为结果可用）；回合因输出长度上限被截断的，按失败定局并明示原因（不得把半截文本当成功结果）。b) **批量续作名单映射**：批量派发的续作参数为"成员标识 → 逐成员续作指令"的映射，每成员可携带专属指令；续作成员先于新条目成员启动（修订 US6.1 中"续作名单"的语义为映射）。
3. **被否决的备选方案**：a) 空摘要原样返回并仅标注占位——派发者无法行动；b) 截断静默成功——掩盖执行不完整；c) 续作名单只带统一指令——逐成员差异无处表达。
4. **影响范围**：US2.1（摘要可用性语义）、US6.1（续作名单语义扩展）；架构 ADR-007；context G29/G30。

### SDR-005 定时任务的时区语义与防扎堆/过期口径（2026-09-12）

1. **背景与动机**：裁决点 Q5 悬空：本地时区符合用户直觉（"每天上午 9 点"即用户所在地的 9 点），但跨时区场景（会话迁移、远程环境）存在语义漂移；同时基线盘点发现目标侧现行实现与参照基线在时区、防扎堆偏移、错过触发合并、过期自动删除四项语义上存在系统性差异（详证见 [subagent-context.md](subagent-context.md) G26），须统一口径。秒级表达式与命名别名（提案 P5 / 全局提案 P-024）涉及调度精度与解析复杂度，收益未证。
2. **决策**：a) **默认本地时区**，创建时支持**可选的显式时区指定**（不指定即本地时区）——跨时区场景可显式锚定，消除漂移；b) 防扎堆偏移、错过触发合并（合并计数）、7 天过期自动删除三项语义**对齐参照基线**（US11.5 / US11.2 / US11.3，维持既有终态表述）；c) **秒级表达式不采纳**（全局提案 P-024 已裁决推迟，理由见本域 ROADMAP 范围标注）。
3. **被否决的备选方案**：a) 固定时区为世界时——用户的"上午 9 点"会随夏令时与迁移漂移，属惊讶行为；b) 强制显式指定时区——抬高创建门槛，多数场景本地时区即正确答案；c) 采纳秒级表达式——提醒/看护类场景分钟级已足够，秒级徒增解析与调度复杂度。
4. **影响范围**：US11.1（已同步增补显式时区指定的验收条目与生效时区呈现口径）；裁决点 Q5 关闭；提案 P2 并入本决策、P5 推迟；架构 ADR-005 中"时区与语法扩展见裁决点 Q5"的缺省表述以本 SDR 为准（显式时区字段的架构承接随本程序 B5 批次以新 ADR 落档）；术语表 A9 的时区表述维持"本地时区"缺省口径不变。

**实施追记（2026-09-13，B5 批次落地时）**：

1. **时区依赖选型（zero-IO 合规）**：任务日历求值采用 `chrono-tz = 0.10`（workspace 级新增）——tzdb **编译期内嵌**，运行时解析为纯计算零 IO；宿主本地时区探测采用 `iana-time-zone = 0.1` 转为 mirri-core 直接依赖（原为 chrono 的传递依赖，未向锁文件引入新外部 crate）——其读取系统时区配置发生在依赖 crate 内，与既有 `dirs`/`chrono::Local` 同等待遇。否决备选：`tz-rs`（运行时读 `/usr/share/zoneinfo`，真 IO，违背 zero-IO 裁决方向 Z1）；仅 `chrono::FixedOffset`（±HH:MM）无法表达 DST 边界，语义不完整。
2. **DST 边界微语义（对齐 JS `Date`，作为已裁决口径）**：本地墙钟候选映射为绝对时刻时——夏令时**空隙**（spring-forward，如 02:30 不存在）按空隙前一分钟生效的 offset 解释（即 `new Date("…02:30")` 归一化到 03:30 时刻）；**重叠**（fall-back，同一本地时刻出现两次）取**较早**实例（先生效的 offset）。两条规则由 `compute_next_fire` 的 `to_instant` 统一实现，测试锁定（cron.rs DST 四则）。
3. **旧记录语义漂移（已接受）**：B5 之前 Rust 记录按 UTC 求值且无 `timezone` 键；升级后统一按**宿主本地**解释（与 TS 记录同待遇），旧 UTC 任务的触发含义随升级漂移——DEC-3 已裁决接受，用户逃生门为显式 `timezone: "UTC"`。恢复路径遇无法解析的 timezone 名（脏数据）回退本地并告警，单条记录永不使 resume 失败。

### SDR-006 会话复制（fork）不携带定时任务（2026-09-12）

1. **背景与动机**：US11.4 原表述为"源会话的全部定时任务被克隆一份到新会话"，与跨域既有裁决冲突——会话管理域 SDR-007 与会话持久化域 SDR-002 均裁决 fork 一律不携带运行中资产；且克隆会导致同一提醒在新旧两个会话**双触发**（两份任务各自按计划注入提示），用户在同一工作区内被重复打扰、用量翻倍。术语表 A9 此前已按"不携带"侧登记冲突警示。
2. **决策**：fork 一律**不携带**定时任务——新会话需要定时任务须重新创建（创建入口与既有语义一致）。本条与 TS 参照行为（克隆）相悖，作为**有意的设计增强**披露：跨域一致性与避免双触发优先于继承便利。
3. **被否决的备选方案**：a) 维持克隆——与跨域裁决矛盾且双触发不可接受；b) 克隆但置为停用态待用户确认——引入"停用任务"这一新状态面，超出本域状态词汇，成本不成比例；c) fork 时逐任务询问用户——fork 是轻量动作，弹问破坏其流畅性。
4. **影响范围**：US11.4（fork 条目已同步修订为终态）；术语表 A9（fork 边界口径更新为已裁决）；架构 ADR-005 中"会话复制时整体克隆"表述作废（见该 ADR 内批注）；本域 ROADMAP 开放项 O7 解除。

### SDR-007 会话关闭的孤儿任务以 persisted-killed 实现，不新增 `lost` wire 状态（2026-10，B1）

1. **背景与动机**：TS 的 `lost` 终态服务于一个进程生命周期竞态——close 时进程将死、异步 settle 与重启调谐竞争同一任务。Rust 引擎的 close 路径**同步**落盘：`stop_all_with_grace` 在 close 内完成信号发射、宽限等待与终态写入，重启加载直接读到已落盘的 `stopped`，不存在二次调谐窗口。
2. **决策**：Rust 以「close → 同步落盘 Stopped（wire `killed`）」实现 TS `lost` 的语义等价物；**不新增** `lost` wire 状态。新增状态会触发三端事件同步（`BackgroundTaskInfo` schema + web 投影 + SDK/ACP 翻译），在竞态动因不存在的前提下成本不成比例。
3. **被否决的备选方案**：a) 照抄 `lost` 字面量——见上成本论证；b) close 异步 settle + 重启调谐复刻 TS 竞态——主动引入自己已消除的竞态，无收益。
4. **影响范围**：矩阵 G31（context §3/§6.8/§6.10）；wire 词汇表不扩容；keepAliveOnExit（SDR 无关，G33）下仍 running 的任务在下次重载时调谐为 Stopped（该路径即 TS lost 的重启等价物，已有行为锁定）。

### SDR-008 双层宽限：管理器宽限与进程层升级分离（2026-10，B1）

1. **背景与动机**：优雅停止（D-63）天然出现两层时间窗——管理器层的"等自然定局"（`killGracePeriodMs`，缺省 5s，管对象是**任务终态**）与进程层的 SIGTERM→5s→SIGKILL 升级（mirri-os `ChildProcess::kill` 既有实现，管对象是**OS 进程**）。两层各自独立可配/可演化，不应互相代理。
2. **决策**：`stop_with_grace`/`stop_all_with_grace` 只负责管理器层宽限（可配）；进程层升级复用 mirri-os 既有实现，其内部 5s 保持硬编码不在本域配置面暴露（两层语义不同：前者等"任务定局"，后者等"进程退出"）。
3. **被否决的备选方案**：a) 把进程层 5s 也并入 `killGracePeriodMs`——语义混淆（一个旋钮两个所有权层）；b) 重造进程升级机制——mirri-os 已有且经过测试，纯重复。
4. **影响范围**：矩阵 G32（context §6.10）；`[task] killGracePeriodMs` 文档口径为"宽限窗口（自然定局等待）"。

### SDR-009 print 模式的超时缺省为内存覆写，不落盘（2026-10，B1）

1. **背景与动机**：TS printDefaults：print 运行时**未显式配置**的子代理/bash 超时视为不设限（长工作不被意外腰斩）。Rust CLI 的 print 装配不加载磁盘 config.toml，天然只有内存配置。
2. **决策**：`run_print` 在内存 `ServerConfig` 上置 `subagent.timeoutMs = 0`、`task.bashTaskTimeoutS = 0`（均=不限）后**再应用 env**（显式 env 配置可覆盖缺省）；任何写盘路径（`save_to`/`save_raw_to`）都不经由该内存实例，缺省值不可能落盘。
3. **被否决的备选方案**：a) 引入独立的 print 专用配置节——print 只是需要两个缺省值，一个节是过度设计；b) 每次调用点判空——三处消费方（swarm/agent/bash）各判一次，口径易漂移。
4. **影响范围**：矩阵 G28（context §6.10）；`mirri print` 行为文档（print 缺省不设限）。

### SDR-010 容量口径、拒绝顺序与问题任务停止语义——评审裁决补录（2026-10，B1 评审轮）

1. **背景与动机**：B1 双评审（code + design）对四个实现口径提出升级裁决项：a) 容量拒绝发生在 `host.spawn` 之后（拒掉的派发已铸造 `subagent.spawned` 事件与 children 残留）；b) 容量口径只覆盖 Agent 工具的 `register_background`，后台 bash 与后台提问绕过上限，而 TS `assertCanRegister`/`activeTaskCount` 统计**所有** detached 条目（taskService.ts:934-943）；c) 问题任务（后台提问）挂着它无法观察的 cancel 信号，stop 路径白烧整个 kill-grace 窗口；d) print steer 模式的时长上限是软上限（每次 `waitForBackgroundTasksOnPrint` 重新武装一个全新 ceiling）。
2. **决策**：a) Agent 工具在 spawn **之前**做容量预检（`can_register_background` 查询，TS 拒绝顺序对齐）；残余竞态（预检与注册之间被并发注册关闭窗口）在 `register_background` Err 处做清理（取消子令牌 + `forget_child` 移除 children 条目），已铸造的事件无法撤回——这正是预检存在的原因。b) 后台 bash 经 `spawn_background_with_signal`、后台提问经 `spawn_background_detached`（均走 `register_background`）计入容量——与 TS 的 detached-only 口径一致。c) 问题任务**不挂信号**（`spawn_background_detached`）：无信号 → `stop_with_grace` 走即时升级捷径，TaskStop/会话关闭不再等待；这是提问无法被取消的既有事实（reverse RPC 无取消通道）的诚实映射。d) steer 软上限维持现状并在代码注释与 print_mode 模块文档中显式记录（每次 continue 的等待重新武装 ceiling；上限约束决策节奏而非进程总寿命；TS 同为近似语义）——不加锚定剩余时限的 wire 参数（会扩 wire 面）。
3. **被否决的备选方案**：a) 只修注释不动顺序——违背「先拒绝后铸造」原则；b) 容量只记 Agent（维持 plan 原范围）——评审核实 TS 口径后判定为文档夸大 parity，修正成本小；c) 问题任务保留信号只修注释——5s 关闭延迟是真实代价，无对应收益；d) 给 `waitForBackgroundTasksOnPrint` 加剩余时限参数——B1 冻结 wire 面。
4. **影响范围**：矩阵 G10（context §6.10）；`TaskManager` 新增 `can_register_background` / `spawn_background_with_signal` / `spawn_background_detached`；`SubagentHost` 新增带缺省实现的 `forget_child`；`background_ids` 在首个终态转移时随信号条目一并修剪（集合不再无界增长）；`register_background` 的检查与插入在同一临界区内（TOCTOU 关闭）。

### SDR-B2-01 通知投递账本采用上下文扫描式，不移植 checkpoint 化 wire Model（2026-11，B2）

1. **背景与动机**：TS 用 checkpoint 化 wire Model（`TaskNotificationDeliveryModel`，taskService.ts:124-135）+ building/scheduled/delivered 三重内存键集 + context 直扫兜底（`hasDeliveredNotification`）登记"已投递键"。Rust 侧移植该机制需要新增 wire 模型注册、checkpoint 帧与四重去重门的全部代码；而 Rust 的恢复本就走磁盘 JSON + wire 回放重建 context，context 天然就是可扫的单一事实源。
2. **决策**：投递账本为**扫描式**——`delivered = context history 中 BackgroundTask origin 的键集 ∪ steer buffer 中已 park 的键集`（`mirri-core/src/task_notification.rs` 的 `delivered_keys`/`parked_keys`/`due_notifications`）。幂等去重 = 扫描不命中才投；**undo 对账免代码**：undo 删消息 → 扫描自动失配 → 驱动器重新投递（等价 TS `reconcileAfterUndo`，B2 T8 以测试锁语义，零对账实现）；恢复 = 回放后的 context 扫描（T7 静默补投同源），零新 wire op。投递确认门：闲路径先解析 agent/LLM，失败则**什么都不记**，欠账保留至下一 tick 重试。
3. **被否决的备选方案**：a) 移植 checkpoint 化 wire Model——为 Rust 已有的"context 即回放事实源"再叠一层影子账本，四重去重门（building/scheduled/delivered/context 直扫）收敛为两重（delivered/parked 扫描），代码与 wire 面双增；b) 驱动器内存 Map 记账——与恢复/undo 的对账代码全部回来，违背本裁决动机。代价声明：每次裁决扫描 O(history)——与 TS `hasDeliveredNotification` 的 context 直扫同阶，可接受。
4. **影响范围**：矩阵 G22/G25/G27（context §6.8）；`PromptOrigin::BackgroundTask` 结构化（taskId/status/notificationId 三元组，camelCase wire 形状与 TS TaskOrigin 互认）；steer flush 的 `ContextAppendMessage` 耐久化记录**收窄至 background_task origin**（user steer 的既有不记录重放契约不动——推广为通用修复另行立项）；通知 XML（`<notification …>`）逐字移植 TS notificationXml.ts（body/children 一并文本转义，较 TS 多转义 body——文档安全于逐字，测试锁定）。

### SDR-B6-01 cron 手动触发（run-now）不动日程，且不为手动触发加事件标记（2026-11，B6）

1. **背景与动机**：B6 管理面（D-29/P-020）引入 `cron.trigger`（「立即运行一次」）。TS/TUI 无任何 cron 管理面或手动触发能力（P-020 是 RustFirst 全新能力），语义无 TS 基准，须裁决。两问：a) run-now 是否算作日程的一次触发（消耗/提前）？b) 事件面是否区分「手动触发」？
2. **决策**：a) **run-now 不动日程（D-2）**——`CronManager::trigger` 纯增量：零 wire op、游标不推进、不重排、不消耗 one-shot，自然触发照常发生。理由：①管理面语义直观（「现在跑一次看看」而非「把这次日程提前」）；②零持久化副作用——日程状态只由 `check_due` 单一演进源驱动；③one-shot 手动跑一次后仍按计划自然触发，不会「跑一次就消失」。事件发布在任务表锁内（与 `check_due` 同址），`coalesced_count=1`/`stale=false`；注入经 `tokio::spawn` fire-and-forget（RPC 立即 ack，与 driver 投递姿态一致；busy-time 并发投递语义属 B2 域）。b) **无 `manual` 事件标记（D-3）**——复用现行 `cron.fired` 事件与 `cron_job` origin，避免 event_projection + web projector + SDK translate + ACP 四端同步；web 管理面板自身以 RPC ack 给反馈。若产品后续要求对话区区分「手动触发」，再立 SDR 扩 origin（记 ROADMAP）。
3. **被否决的备选方案**：a) run-now 等价一次自然触发（推进游标/消耗 one-shot）——「现在跑一次」会静默改日程，且 one-shot 场景「跑一次就消失」反直觉；b) `cron.fired` 加 `manual: true` 键——四端投影同步成本换一个当前无消费者的标记。
4. **影响范围**：矩阵 G26（管理面收敛）；`CronManager::trigger`（mirri-core）+ `cron.trigger` RPC 五环 + cross_backend cron 域首例；`cron.delete` RPC 同批（薄封装 `CronManager::remove`，复用 B5 的 durable wire op，无新裁决）；web 呈现链零改动（D-3 的直接收益）。**可观测推论**：`cron.list` 行的 `lastFiredAt` 不反映手动触发——`last_fired` 是游标状态（喂 resume base `max(last_fired, created_at)` 与节奏相位），只由 `check_due` 推进；手动触发的确认信号是 `cron.fired` 事件与注入的 turn 本身，不是 lastFiredAt 列。

### SDR-B3-01 重试形态、容量种子与 env 命名——swarm 调度器参数语义（2026-11，B3）

1. **背景与动机**：B3（D-42/43）引入起步斜坡与 429 requeue，三处语义需裁决：重试的 turn 形态、限流模式的容量种子、env 并发上界的命名与非法值行为。
2. **决策**：a) **重试形态** = `ResumeRequest.retry` + `TurnFlow::retry_one_turn`——重跑失败 turn、**不追加新 user 消息**（对位 TS `promptService.retry()`，runAgentTurn.ts:52-60）；同 run 面（SubagentStarted hook、stop guard、settle、live events），无新 `subagent.spawned`。b) **容量种子近似**：TS 的 onReady 精确信号（`startedSuccessCount`）无 Rust 对应物——种子取「已完成 + 在跑（未失败）的已 launch 成员数」（`max(1, …)`），够保守且无需新信号面。c) **env 命名**：主名 `MIRRI_AGENT_SWARM_MAX_CONCURRENCY`（B11 规范名口径），兼容 TS 拼写 `MIRRICODE_AGENT_SWARM_MAX_CONCURRENCY`；**非法值 fail-soft**（`tracing::warn` + 忽略）——TS 在 session 装配期 throw 会炸整个会话，不采纳。d) 超时文案沿用 B1 的 `"Subagent timed out after {}s."`（不逐字 TS `"Subagent timed out."`，B1 已裁决）。
3. **被否决的备选方案**：a) 重试 = 带 prompt 的普通 resume——会追加一条空 user 消息污染子代理记忆，且 TS 明确是 retry 语义；b) 容量种子取已 launch 总数——高估（失败成员不该占容量）；c) env 非法值对齐 TS throw——引擎装配健壮性优先（fail-soft 已是本仓库 env 族惯例）。
4. **影响范围**：矩阵 G3/G4；`subagent/swarm_batch.rs`（调度器 + `parse_swarm_max_concurrency`）、`turn_flow/mod.rs`（`run_one_turn_inner(prompt: Option<_>)`）、`subagent/host.rs`（resume 的 retry 分支）；embedded 无装配缝——集成测试接受 ~3s 真实退避（`SwarmBatchOptions::retry_base_ms` 为 core 侧测试缝）。

### SDR-B3-02 成员 future 被外层 drop 时的兜底终态事件（2026-11，B3）

1. **背景与动机**：G19 后半——TS 批调度器的事件循环总能 drain（future 不被 drop），Rust 的工具 future 可被外层 drop（父 turn abort、并发 buffer 取消）——排队/在跑成员曾在 UI 悬挂无终态。
2. **决策**：`RunningGuard` 扩展——携带 session bus + `settled` 原子标志；每个终局分支（完成/失败/取消/LLM 构建失败/会话丢失）`mark_settled()`；Drop 时若未 settled 则补发 `SessionEvent::SubagentFailed{error: "cancelled"}`（settle running 标志照旧）。覆盖 drop-before-first-poll（并发 buffer 中被取消的排队成员正是此形态）；同时惠及前台 Agent 工具的取消路径。
3. **被否决的备选方案**：a) 在调度器取消分支逐成员发终态——只覆盖调度器路径，前台 Agent 的 drop 无兜底，且 drop-before-first-poll 的成员根本不在 `active` 集合里；b) 每 spawn 即注册 TaskManager 走通知——直接违反 B2 前置约束 1（swarm 成员不注册 TaskManager，per-member 通知是 TS 没有的行为）。
4. **影响范围**：矩阵 G19 后半；`subagent/host.rs`（guard 扩展 + 终局标记）；事件词汇零新增（复用 `subagent.failed`）。

### SDR-B3-03 swarm 工具结果恒 success、body 不转义——TS v2 呈现对齐（2026-11，B3）

1. **背景与动机**：旧 Rust 结果 XML 与 TS v2（agentSwarmTool.ts:307-352）四处不合：body 转义（web `parseSwarmResult` 按 "producer writes body unescaped" 契约消费，转义会显示实体字面量）、summary 零项不省略、`is_error` 在全失败时置真、resume_hint 文案与位置不同。
2. **决策**：`format_swarm_results` 逐字对齐 TS `renderSwarmResults`——`<summary>` 只列非零项；`<resume_hint>` 固定文案（"Call AgentSwarm with resume_agent_ids using the agent_id values in this result to continue unfinished work."）紧随 summary、条件 = 存在非 completed 且存在任一 agent_id；`mode` 仅 resume 行、`state` 仅非 completed 行（属性经 `xml_escape`，**body 原样**）；工具结果**恒 success**（`is_error` 仅用于入参校验错误——TS v2 的 isError 从不因成员失败而置）。
3. **被否决的备选方案**：a) 保留 `is_error = 全失败`——主代理会把整批失败当作工具调用错误重试整个 swarm，而非经 `resume_agent_ids` 选择性续作；b) body 转义——直接违反 web 解析契约（转义实体会渲染为字面量）。
4. **影响范围**：矩阵 G5；`tools/agent_swarm_tool.rs::format_swarm_results`；web 零改动验证（parseSwarmResult/swarmCardRows/SwarmTool 五相位消费面全部就绪，T11 只读核验 + 三件套绿）。

### SDR-011 等待与自治目标模式协同：A+B 组合裁决（2026-09-13）

1. **背景与动机**：非目标模式下「后台派发 + 完成通知」闭环成立（回合结束即空闲，通知自起新回合消化）；但目标模式存在结构缺陷——回合一结束即被续航提示强制开新回合，目标模式下**不存在「空闲」**：派发者判定后台结果为达成目标所必需时，唯一手段是对非阻塞快照的反复确认，直至任务定局，token 空耗（结构根因与三引擎现状见 [subagent-context.md](subagent-context.md) §6.13；提案 P6/P7 据此提出）。
2. **决策**：采纳 **A+B 组合**（用户裁决 2026-09-13）：
   a) **方向 A（主）——等待挂起**：续航提示携带进行中任务清单（P7 转正为 US13.2）；续航回合无实际工作（无工具调用）视为等待信号，目标循环**挂起**不发新续航提示；后台任务定局通知开启唤醒回合（目标上下文由既有常驻提醒在场）；看门狗兜底强制续航；用户插话随时唤醒；挂起期不计回合预算（US13.3）。
   b) **方向 B（辅）——阻塞等待入口**（P6 转正为 US13.1）：显式等待带时长上限，到期诚实返回部分输出并劝退；普通查询的未就绪返回附动态劝阻提示；批量等待由并行多次等待表达。
   c) **归属切分**：等待入口、任务清单供给、通知唤醒属本域；目标循环的挂起态/看门狗/预算计费属目标（goal）域——该域暂无规格落点，登记 ROADMAP 开放项（O11），本域以 US13.3 记录用户可见的协同契约。
3. **被否决的备选方案**：a) 仅方向 B——不治根（回合外无空闲的结构缺陷仍在，长等待需反复续期）；b) 仅缓解件（动态劝阻文案/查询频控）——降低而非归高空耗，且依赖模型自律；c) 任务在跑即自动挂起（无等待信号判定）——误伤「后台派发后并行做独立工作」的正向用法，退化为串行；d) 自由 sleep 类等待工具——与任务无绑定、鼓励空转，被 P6 的任务绑定形态取代。
4. **影响范围**：新增 Epic E13（§19，US13.1–13.3）与 N16；§17 P6/P7 标注已采纳（提案正文按惯例保留不改写）；架构 ADR-008；ROADMAP O9 关闭、新增 O11；glossary 同批注册 A12（阻塞等待入口）/A13（等待挂起）。

### SDR-B4-01 子代理 host 去 block_on：驱动形态、锁迁移与 drop 语义变更（2026-09-13，B4）

1. **背景与动机**：Rust HEAD 的子代理 host 以 `block_on` 驱动子代理 turn——嵌套派发（D-46/G7）落地后，父 turn 持锁内 `block_on` 子 turn 的重入形态直接死锁；且 `block_on` 在异步运行时内是反模式（阻塞执行器线程）。须裁决：驱动形态、两把锁（`TurnFlow` 互斥、`ToolManager` 互斥）的迁移、子代理 future 被 drop 的语义、以及 TS `promptPrefix` 的移植面。
2. **决策**：a) **纯 async 驱动**——host 方法全部 `async`，工具 future 由调用方（工具执行器）自然 await；panic 隔离用 `catch_unwind` 包裹（与主 agent 面同形）。b) **锁迁移**：`TurnFlow` 互斥从 std 改 tokio Mutex（turn 期跨 await 持锁合法）；`ToolManager` 迁 parking_lot（`send_guard` feature——读 guard 跨 await 仍 `Send`）——与主 agent 侧同形，非 B4 特有形状。c) **drop 语义变更（M1，重要）**：子代理 future 被 drop 即在最近 await 点取消，无 graceful cancel——比 TS（任务系统显式停止）更"裸"；缓解 = resume 路径复用 `TurnFlow` 既有恢复测试锁定（实测干净恢复，未需要 turn-state reset；若后续暴露脏状态再补 reset 面记 ROADMAP）。d) **`promptPrefix` 只做静态字符串**——TS 的动态函数式注入不做（Rust profile 面没有函数注入点，序列化边界即静态）。e) **用户工具继承必须在 turn 开始前完成**——T5 的继承读 `ToolManager` 读 guard 跨整个 turn 生命周期，turn 中途改写工具面不可行（与主 agent 同约束）。f) TurnFlow turn 期事件经路由 recorder 落子代理 journal（归属表见 SDR-B4-02）。
3. **被否决的备选方案**：a) host actor 化（消息循环串行化）——改动面大且嵌套 turn 内仍需 async 递归，收益只是锁的形态；b) 保留 `block_on` + 深度护栏顶住——治标：深度上限会退化为死锁防护参数而非资源护栏，且每个嵌套层仍占一个阻塞线程；c) 独立 runtime（`spawn_blocking` 内自建）——跨 runtime 的 handle 持有与 waker 语义复杂，嵌套 host 仍需传递 executor 上下文。
4. **影响范围**：矩阵 G8/G9（context §2.1 B4 落地注记 + §3 矩阵行）；`subagent/host.rs`（async 化 + catch_unwind）、`turn_flow/mod.rs`（tokio Mutex）、`ToolManager` 锁迁移跨 crates（含 workspace 加 `parking_lot` send_guard 依赖）；drop 取消语义由 resume/回归测试锁定；主 turn 的 `run_engine_turn` **仍 block_on**（顶层 await 边界、无父级等待者，非死锁面——记档见 SDR-B4-04）。

### SDR-B4-02 子代理 journal 的 op 归属：穷举 match 与域划分（2026-09-13，B4）

1. **背景与动机**：D-55/G30——子代理 turn 的 wire 记录此前全部落主 journal，恢复回放时子代理的 context/turn 记录与主会话状态混杂，无法单独重建子代理记忆。须裁决：哪些 op 归子代理 journal（`agents/<agent_id>/wire.jsonl`）、哪些归主 journal（`wire.jsonl`），以及路由机制本身。
2. **决策**：a) **路由 = `WireOp` 枚举穷举 `match`，无通配臂**——每个变体一个显式臂；新增 `WireOp` 变体时路由处编译失败，强制归属裁决（T8 新增 `SubagentRegistered` 时当场验证该机制）。b) **禁字符串前缀匹配**——`context_size.measured` 不是 `context.*`：前缀匹配会误路由（测试锁定该反例）。c) **`WireOp::Unknown` → 主 journal 保底**——未识别记录永不丢弃（主 journal 是重启回放的单一事实源）。d) **归属表**——子代理域：`metadata`、`context.*` 全域（append_message/append_loop_event/clear/apply_compaction/undo）、`context_size.measured`、turn 五 op（prompt/steer/steer_flushed/cancel/ended）、`usage.record`、`llm.request`、`llm.tools_snapshot`、`request.header.changed`、`interruptionReminder.recorded`；主域：`forked`、`goal.*`、`plan_mode.*`、`plan.revision`、`permission.*`、`profile.bind`、`config.update`、`tools.*`（五 op）、`mcp.tools_discovered`、`full_compaction.*`、`skill.activate`、`task.started/terminated`、`swarm_mode.*`、`cron.*`、`interaction.*`、`collaboration.*`、`subagent.registered`。e) 两侧都是 `SessionWireLog` 句柄、共享 Detached → Deferred → Writer 状态机（SDR-004）——子代理在会话物化前 spawn 则缓冲，物化路径统一 flush。
3. **偏差记录（对 TS 基线）**：a) `tools.*` 归主域——ToolManager 虽为 per-agent，但 reducer 把这些 op 折进会话级状态（`reducer.rs` 的 ToolsState），会话级 manager 是事实源；b) 子代理 agent 级 recorder 直接传主 `SessionWireLog`（agent 级 op 已由路由分流，此处为等价纯透传；泛化为 `Arc<dyn WireOpRecorder>` 管线留后续批次）；c) TS `mirrorAgentRun` 的派发面镜像未做（Rust 无对应镜像消费者）。
4. **影响范围**：矩阵 G30；`session/journal_route.rs`（新文件——穷举 match + 归属表 + 双向全量锁定测试）、T7 per-child 落盘、T8 重启回放（`restore_subagents` 逐 child 折叠 journal 重建记忆）。**评审轮补记（S1/S2）**：子代理 journal 的物化**恒走 append 语义**（`JsonlAppendLog::open_for_append`——恢复会话收养既有 journal 绝不截断，与主 journal 的 resume 规则同形；收养时不再铸造第二条 `metadata` 信封）；resume 派发与 `summaryPolicy` 续问 turn 均落完整 dispatch 括号（`turn.prompt` + `context.append_message`，retry 形态保持无 prompt 语义）——否则重启折叠出的记忆缺每条续作指令。回归：重启 → resume → 二次重启折叠双轮断言。

### SDR-B4-03 嵌套深度护栏：默认 5、0 不限、超限 RequestInvalid（2026-09-13，B4）

1. **背景与动机**：D-46/G7——嵌套子代理落地后须裁决深度上界的缺省值、语义与拒绝面。TS 基线：工具描述声明"actual maximum nesting is 5"且 `maxNestingDepth` 参数 `0 = 不限`；Rust 侧无既有护栏。
2. **决策**：a) **默认上限 5**（对齐 TS 工具描述的运行时事实）；b) **0 = 不限**（对齐 TS `maxNestingDepth` 参数语义）；c) 计数口径：根 agent `nesting_depth = 1`，每层嵌套派发 +1，超限在 spawn 处拒绝；d) 拒绝面 = 工具结果 `RequestInvalid` 错误（不 panic、不静默）——子代理收到可读的拒绝理由；e) 传参链：`SessionScopeConfig` 携带上限（`with_nesting_limits`）→ host 逐层下传，子代理 AgentScope 继承父配置再由其 host 继续下传；embedded 两个装配站点已接 `with_nesting_limits(1, …)`（顶层会话从 1 起算）。f) **配置面（评审轮 SF-4 补）**：`[subagent] maxNestingDepth` TOML 键（camelCase/snake_case 双拼写）经 `resolve_subagent_max_nesting_depth` → `session_scope_config_from` 装配进会话——拒绝文案指名的旋钮是真实可达的，`0 = 不限` 在生产配置面同样可达（缺省 5）。
3. **被否决的备选方案**：a) 默认 0 不限——递归派发在 API 成本与延迟上无天然刹车，5 层已覆盖「子代理拆活再拆活」的合理纵深；b) 深度护栏兼任死锁防护（配 `block_on` 旧形态）——已在 SDR-B4-01 否决（护栏应只管资源，不管正确性）；c) 超限静默降级为单层执行——违反「任何界面承诺与真实执行一致」的域愿景。
4. **影响范围**：矩阵 G7/G21（context §3 矩阵行 + §2.6 B4 勘误块）；`scope/config.rs`（`with_nesting_limits`）、`subagent/host.rs`（深度检查 + `RequestInvalid`）、embedded 装配站点两处；嵌套限流 requeue 回归（B3 面，T9）。**已知限制（评审轮 SF-5 记档，ROADMAP 开放项）**：跨重启恢复的子代理当前**不带嵌套派发面**（`restore_subagents` 重建的 AgentScope 无 `subagent_host`，其 ToolManager 不注册 Agent/AgentSwarm 工具）——恢复子代理的续作（resume）可用，但不能再派发孙代理；`subagent.registered` 也不携带 `nesting_depth`，重启后逐层重建嵌套 host 需按 `parentAgentId` 链推算深度。修复留后续批次（embedded resume 装配处重建 per-child host）。

### SDR-B4-04 自驱动 executor 桥接点记档与主 turn block_on 保留（2026-09-13，B4）

1. **背景与动机**：SDR-B4-01 重构后，存在**主 turn 之外**驱动 executor 的路径（loop_engine 自愈重试、TaskOutput/TaskList 工具查询），它们的记档与 journal 归属需要显式留痕；同时主 turn 的 `run_engine_turn` 仍 `block_on`，须记档为何不迁。
2. **决策**：a) **主 turn `run_engine_turn` 保留 block_on**——主 turn 是顶层 await 边界，无父级等待者（不构成 SDR-B4-01 的重入死锁面），不在本批重构范围；迁 async 属全局引擎面工作，触发时另行立项。b) **三处自驱动桥接点记档**：`loop_engine/retry.rs:981`、`tools/task_output.rs:242`、`tools/task_list.rs:132`——它们在主 turn 之外以纯 async 驱动 executor，行为受 SDR-B4-01 的 drop 语义约束（被 drop 即在 await 点取消）。c) **B2 通知 driver 的收件人语义（评审轮 SF-3/N4/S3 修订 + 复审二轮 F1/F2/Q-1/Q-2 收口）**：通知的收件人是任务的**派发者**——`TaskKind::Agent` 的 agent_id 仍是**主体**（subject，恢复/续作身份到处一致），经会话的**活跃身份注册表**（`SessionScope::record_op` 对 `subagent.registered` 的实时 fold + resume 时的 seed）解析 `parentAgentId` 得到派发者；父即主代理（或不可解析/不存活）→ 投递主代理（扁平派发的既有行为）。一个 tick 只服务一个收件人：按任务表顺序解析候选收件人，**首个确有欠账的**收件人锚定本轮（已满足的跳过，多代理欠账跨 tick 收敛），due 集按收件人过滤。子代理收件人的 busy 排除是**原子 claim**（`SubagentHost::claim_child_notification_turn`：与 spawn/resume 在同一 children-map 锁下取-判-置 per-child `running` 标志，guard 持有至本 tick 的通知 turn 结束）——点时探测（is_child_running）在探测与 turn 之间有 TOCTOU 窗口，claim 关闭之；主代理收件人的 busy 信号仍是共享 flow-map mutex 的 `try_lock`。busy 收件人 park 后**继续锚定循环**（一个 busy 代理不阻塞本轮其余收件人，停靠欠账走自己的 buffer 到后续空闲 tick）；park 对 steer buffer get-or-create（子代理收件人的首个 busy tick 此前无 driver 侧 entry，no-op 停靠变真实停靠）；通知 turn 的身份（hook env `MIRRI_AGENT_ID`、live 事件、失败事件）盖章为**收件人**而非主代理。d) **保留偏差（含复审二轮 F-1 后果记档）**：driver 的 dispatch 级记录（通知 turn 的 `turn.prompt` 等）仍写主 journal（子代理自身 turn 的 op 已由 SDR-B4-02 路由归子 journal）——随 SDR-B4-02 的 `Arc<dyn WireOpRecorder>` 泛化一并统一。**功能后果（记 ROADMAP O13）**：子代理收件人的通知 turn 记录与 busy-park 的 `turn.steer` 写主 journal，而送达/停靠账本（delivered/parked 扫描）读**收件人**自己的记忆与 buffer——跨重启时：(a) 重启前已投递给派发者的通知会**重复投递**（子代理记忆只从其子 journal 重建，账本缺键）；(b) 投递消息的 `context.append_message` 无条件 fold 进**主代理**回放上下文（SF-3 要消除的错址污染在重启后重现）；(c) 崩溃时停靠的 `turn.steer` 重放只进主 buffer，驱动器又投给派发者——**双收**；(d) `restore_task_notifications` 按主代理账本算 due，把未投递的子代理址通知写进主上下文。定性：**非本批修复引入**（pre-B4 主体寻址同样错位），修复面是 addressee-aware 的 restore 对账 + 记录路由的多表面改动，留 O13，B12 rust+web 实跑覆盖验证。
3. **被否决的备选方案**：a) 本批一并迁 `run_engine_turn`——范围蔓延：主 turn 驱动面牵动 print 模式/会话关闭的等待语义，与 B4 无关；b) dispatch 层记录按目标分流——需要 dispatch 层感知子代理身份，与 SDR-B4-02「路由在 recorder 层」的机制重复。
4. **影响范围**：矩阵 G9（context §2.1 B4 落地注记）；rust+web 实跑（R1–R3：两层真 provider、磁盘核验、跨重启 resume）留 B12；本 SDR 是记档性裁决，无独立代码面。

### SDR-012 批量派发条目上限：缺省 3、可配置、偏离 TS 硬编码 128（2026-11）

1. **背景与动机**：TS 基线 `agent-swarm/agentSwarmTool.ts` 的 `MAX_AGENT_SWARM_SUBAGENTS=128` 是硬编码常量（schema 描述与运行时双重限制），Rust 引擎此前忠实镜像 128。2026-11 产品要求下修缺省：单次 swarm 的 API 成本与延迟应有天然刹车（对位 SDR-B4-03 否决「默认 0 不限」的同型推理——128 层级缺省已近似无界），且上限须成为真实可达的旋钮而非常量。
2. **决策**：a) **缺省上限 3**（`DEFAULT_MAX_SWARM_ITEMS`，`subagent/host.rs`）——Rust 引擎对 TS 硬编码 128 的**刻意产品偏差**（TS 代码 `packages/agent-core` 本批只读不改，此记录即偏差登记：跨引擎默认值 TS 128 / Rust 3）；b) **配置面**：`[subagent] maxSwarmItems`（camelCase/snake_case 双拼写，`Option<u32>`）经 `resolve_subagent_max_swarm_items` → `session_scope_config_from` → `TaskLifecycleSettings` → `AgentScopeConfig` 装配进会话（对位 SDR-B4-03 f 的 `maxNestingDepth` 装配链）；c) **env 覆盖**：主名 `MIRRI_AGENT_SWARM_MAX_ITEMS` + TS 拼写别名 `MIRRICODE_AGENT_SWARM_MAX_ITEMS`（命名对位 SDR-B3-01 的并发 env），**调用期解析**——工具在 `resolve_execution` 与 `parameters` 时读 env，env 变更无需重装配，schema 的 items 描述（`Max {N}`）同步携带真实上限；优先级 **env > config 文件 > 缺省 3**；非法值 **fail-soft**（warn + 忽略、回落下一级——沿用 SDR-B3-01 否决 TS throw 的引擎健壮性裁决）；d) **`0` = 不限**（镜像同节 `maxNestingDepth` 语义）；拒绝文案形状不变（`Too many items: N (max M)`）；「至少 2 条」规则不受上限影响。
3. **被否决的备选方案**：a) 保留 128 与 TS 严格对齐——成本/延迟无刹车的批评同样适用于条目上限，产品已裁决下修；b) env 非法值整批拒绝（TS 式 throw）——SDR-B3-01 已裁决 fail-soft 优先；c) 装配期一次性解析 env——env 变更后 schema 声明与运行时上限会漂移，调用期解析（与并发 env 同法）关闭该窗口；d) `0` 视为非法值——与同节 `maxNestingDepth` 的 `0 = 不限` 语义冲突。
4. **影响范围**：US6.1 验收（上限从常量 128 改为缺省 3 + 双旋钮）；`tools/agent_swarm_tool.rs`（移除硬编码 128、调用期解析、动态 schema 描述——缓存按上限值去重，`Box::leak` 每个不同上限一份）、`config/mod.rs`（`SubagentConfig.max_swarm_items` + resolver）、`scope/config.rs` / `session/manager/mod.rs` / `scope/session_scope.rs`（装配链）、`tools/mod.rs` 与 embedded `session_handlers.rs`（工具构造第三参）；TS `packages/agent-core` 零改动。

## 12. Epic E9：后台任务管理面（统一任务面板）

> 解决"派出去的后台工作如何被看见、被取回、被叫停"。任务面板承载三类后台工作：子代理、后台进程（命令）、后台提问（等用户回答的问题），一套状态、一套操作、一套终态语义。

### US9.1 任务清单（P0）

作为派发者/用户，我想查看当前会话的后台任务清单，以便掌握"谁在跑、跑了多久、是否已定局"。

验收：
- Given 存在后台任务，When 查询清单，Then 每个任务呈现：任务号、描述、类型（子代理/进程/提问）、当前状态、启动时间、（已定局时）结束时间与停止原因
- Given 查询清单，Then 默认只列出仍在进行的任务；明确要求时也列出已定局的历史任务
- Given 清单中存在因异常重启而失去归属的任务，When 查看，Then 该任务按"已丢失"呈现，且说明其不可再控制、应按已终止对待
- Given 后台任务数量多，When 查询，Then 清单条数有默认上限（可调），避免清单本身淹没上下文

### US9.2 输出获取（P0）

作为派发者，我想读取任一后台任务的输出，以便不等待就能了解进展。

验收：
- Given 任务运行中或已定局，When 读取输出，Then 返回尾部预览（超出预览长度时保留最近部分并明确标注截断）
- Given 任务输出已完整留存，When 读取，Then 同时给出全量输出的存放位置，并可按页翻阅完整输出（预览只是快照，不是全部）
- Given 任务尚未定局，When 读取，Then 明确标注"尚未就绪"而非伪装成完成；读取本身不阻塞、不等待
- Given 任务不存在，When 读取，Then 报错"任务不存在"（不静默返回空）

### US9.3 停止（P0）

作为用户/派发者，停止一个后台任务必须真实、可预期、不重复打扰。

验收：
- Given 请求停止一个进行中的任务，When 停止，Then 任务真实终止并定局为"已停止"，且**不再为此任务补发完成通知**——停止操作的直接结果就是唯一应答（不出现"先看到停止结果、又收到一条完成通知"的重复打扰）
- Given 请求停止一个已定局的任务，When 处理，Then 返回其当前终态与既有原因，不做任何改写（幂等）
- Given 停止请求发出，When 执行，Then 先给任务一个短暂的收尾窗口（宽限期），窗口内自然定局则以自然结果为准；窗口过后才强制终止——收尾与强杀的边界可预期

### US9.4 三类任务一视同仁（P1）

作为用户，后台子代理、后台命令、后台提问共用同一套任务面板与终态语义。

验收：
- Given 任意类型的后台任务，When 在任务面板查询/读取输出/停止，Then 操作语义一致（同一套状态词、同一套停止/超时/丢失语义）
- Given 后台提问任务，When 用户作答，Then 任务定局为"已完成"且答案作为通知送达派发者（提问的界面交互本身归审批域，见 SDR-003 的范围裁决）

### US9.5 无界面模式的后台收敛（P1）

作为用户，在无界面的单次运行模式（管道/脚本调用）下，后台任务的收尾策略可预期且可配置。

验收：
- Given 无界面模式配置为"完成即退"，When 主回合结束，Then 立即结束、不等后台任务
- Given 配置为"等待收敛"，When 主回合结束仍有后台任务在跑，Then 等待其全部定局（有时长上限）后结束，期间不为这些任务补发通知
- Given 配置为"接力驱动"（默认），When 主回合结束仍有后台任务在跑，Then 保持存活，任务完成的通知驱动新的主回合，直至清零或达到时长/回合数上限
- Given 无界面模式且用户未显式配置任务时长上限，Then 后台工作默认不受交互场景的时长限制约束（避免长任务被误杀）

## 13. Epic E10：任务通知与对话闭环

> 解决"后台定局如何让派发者知道"。通知不是界面弹窗，而是**作为一条后续消息送达派发者**——不轮询、不空等、跨重启不丢不重。

### US10.1 通知即消息（P0）

作为派发者，后台任务定局时我想以"收到一条消息"的方式获知，而不是轮询。

验收：
- Given 后台任务定局（完成/失败/超时/被停止/丢失），When 定局发生，Then 一条含任务号、类型、终态与原因的通知消息被自动送达派发者；派发者无需轮询、无需等待
- Given 派发者正处于工作回合中，When 通知到达，Then 通知并入当前回合继续处理（不打断、不排队到失去时效）
- Given 派发者空闲，When 通知到达，Then 自动开启新的处理回合消化该通知
- Given 工具入口承诺"完成会自动通知"，When 使用，Then 该承诺真实成立（入口文案与通知能力一致即为验收，反之即缺陷）

### US10.2 通知内容可行动（P1）

作为派发者，失败类通知要让我直接知道下一步怎么补救。

验收：
- Given 子代理类任务以非完成态定局，When 查看通知，Then 附带可行动的恢复指引：用哪个标识续作、该标识与任务号的区别（防混淆警示）、可否保持后台
- Given 任务有输出，When 查看通知，Then 附带输出的获取方式（全量输出文件位置，或尾部预览及其截断说明）
- Given 通知中的恢复指引，Then 指向的续作能力真实可用（与 US2.3 同律）

### US10.3 恢复与不重不漏（P0）

作为用户，会话重开后任务通知不丢失、不重复。

验收：
- Given 会话重启前有任务已定局但通知未送达，When 会话恢复，Then 该通知被静默补录进上下文（不额外触发新回合、不重复打扰）
- Given 同一任务的同一终态，Then 通知至多送达一次（重开、撤销重做等操作不产生重复通知）
- Given 用户撤销了对话中的某些回合，When 通知投递状态与之对账，Then 已撤销的通知不再投、未投的不漏投
- Given 因异常重启失去归属的任务，When 恢复，Then 按"已丢失"通知并可续作（与 US3.4 一致）

### US10.4 压缩后不失忆（P1）

作为派发者，对话被压缩后我仍记得有后台任务在跑。

验收：
- Given 对话发生了压缩、且仍有后台任务进行中，When 压缩后的首个回合，Then 一段提醒被注入：既有后台任务仍在跑、不要重复派发、如何查看/停止、完成会自动通知
- Given 该提醒，Then 附带当时的任务清单快照，供直接引用

## 14. Epic E11：定时任务（按计划自动注入提示）

> 解决"到点让模型替我记得做事"。定时任务 = 一条计划 + 一段提示词：到点把提示词作为消息注入当前会话，驱动模型执行。提醒、周期检查、看护类工作流是其主场。

### US11.1 创建与校验（P0）

作为用户/派发者，我想创建一个定时任务（计划表达式 + 提示词），并得到人能读懂的确认。

验收：
- Given 合法的计划表达式与提示词，When 创建，Then 成功并返回：任务标识、规范化的表达式、**人话版计划说明**（如"每天上午 9 点"）、是否循环、下次触发时间（按生效时区呈现；未显式指定时区即本地时区）
- Given 创建时显式指定了时区，When 创建，Then 触发时刻按该时区推算并生效，返回说明中注明实际生效时区；未指定时区，Then 默认本地时区（见 SDR-005）
- Given 表达式非法或计划在可预见的未来（5 年）内不会触发，When 创建，Then 拒绝并说明原因
- Given 循环任务按计划推算的下一次触发距今超过单次上限（约 350 天），When 创建一次性任务，Then 拒绝并提示改用更近的未来日期或通配符
- Given 提示词超出大小上限（约 8KB），When 创建，Then 拒绝并说明实际大小
- Given 当前会话的活跃定时任务已达上限（50 个），When 再创建，Then 拒绝并说明上限
- Given 创建一次性（非循环）任务，Then 计划含义为"下一个匹配时刻触发一次"；创建循环任务，Then 按计划周期反复触发
- Given 定时功能被整体关闭，When 创建，Then 拒绝并说明定时功能不可用

### US11.2 触发与投递（P0）

作为用户，到点的任务把提示词注入会话，且注入方式可辨识、可追溯。

验收：
- Given 定时任务到点，且会话正忙（模型回合进行中），When 触发时刻到达，Then 该触发被挂起等待，直至会话空闲才注入（不插入到进行中的回合里）
- Given 任务触发并注入，When 查看，Then 注入的消息带明确的来源标识（任务标识、计划、是否循环、合并计数、过期标记）与原始提示词逐字全文——模型能区分"这是定时触发"并知道该做什么
- Given 会话休眠/长回合期间错过了多次触发时机，When 恢复，Then 错过的触发合并为一次注入，并标注合并次数；提示模型"错过的检查按最新状态处理"
- Given 循环任务触发后，Then 下次触发时间按计划推进；一次性任务触发后自动删除

### US11.3 生命周期与过期（P0）

作为用户，定时任务不会无限堆积，也不会悄无声息地失效。

验收：
- Given 循环任务存活超过 7 天，When 再次触发，Then 该次注入明确标注"过期"（提示模型如需继续应重新创建），且该次触发后任务自动删除
- Given 一次性任务已触发（已自动删除），When 尝试删除它，Then 报"任务不存在"（删除不幂等——防止把删除当成确认手段而误删别的任务）
- Given 需要修改一个定时任务，When 操作，Then 通过删除旧任务 + 创建新任务完成（不存在原地修改语义，文档须明示）
- Given 任务标识格式非法，When 删除，Then 拒绝并说明合法格式

### US11.4 持久化与会话边界（P0）

作为用户，重开会话后我的定时任务还在；但换新会话不会带过来。

验收：
- Given 会话被重开（恢复），When 恢复完成，Then 该会话的定时任务连同触发游标恢复，错过的触发按 US11.2 合并处理
- Given 全新会话，When 创建，Then 新会话不继承旧会话的定时任务（任务归属其创建时的会话）
- Given 会话被复制（fork），When 复制完成，Then 源会话的定时任务**不被携带**到新会话——fork 一律不携带运行中资产，新会话需要定时任务须重新创建（见 SDR-006；与 TS 参照行为相悖，属有意的设计增强）
- Given 任务持久化，Then 不依赖"下次触发的绝对时刻"这类会随停机失效的数据——恢复时从触发游标重新推算（停机不产生幽灵触发）

### US11.5 触发时刻的错峰（P1）

作为系统/用户，大量任务的触发时刻不应在同一瞬间扎堆。

验收：
- Given 循环任务，When 计算触发时刻，Then 实际触发在计划时刻基础上**向后**小幅偏移（不超过计划周期的一小部分且有硬上限），偏移量对同一任务稳定可复现
- Given 一次性任务，When 计划时刻恰逢整点/半点这类扎堆时刻，Then 实际触发**向前**小幅提前（有硬上限，且不早于任务创建时刻）；非扎堆时刻原样触发

### US11.6 查询与删除（P0）

作为用户/派发者，我能随时列出、删除定时任务，并清楚每个任务的状态。

验收：
- Given 存在定时任务，When 列出，Then 每个任务呈现：标识、计划表达式、人话版计划、提示词（超长截断并标注）、下次触发时间、是否循环、存活天数、是否过期
- Given 无定时任务，When 列出，Then 明确说明"无定时任务"
- Given 删除一个存在的任务，When 删除，Then 成功并回报被删任务标识

## 15. Epic E12：界面呈现增补（任务面板、转后台入口与定时消息）

> E7 已定义子代理/swarm 的基础界面承诺；本 Epic 补齐任务管理面与定时任务在终端/网页上的消费端呈现（与 E9/E10/E11 配套）。消息呈现的字形/布局细节归对话渲染域，本 Epic 只约定"呈现什么、何时呈现、操作是否真实"。

### US12.1 后台任务面板（P0）

作为用户，我想随时打开一个后台任务面板，查看、读取、停止任务，操作真实生效。

验收：
- Given 用户打开任务面板（终端命令入口），Then 面板列出后台任务并**自动持续刷新**（无需手动刷新也有近实时状态，手动刷新仍可强制）
- Given 面板中的任务列表，Then 每行呈现任务号（按类型可区分）、状态徽章（运行中/已完成/失败/已超时/被停止/丢失）、描述；顶部汇总各状态计数
- Given 面板提供"全部/进行中"过滤切换，When 切换，Then 列表按选择过滤；面板打开时默认列出全部（含已定局），并优先选中进行中的任务
- Given 用户在面板中选择任务并确认停止，Then 任务真实停止（与 US9.3 同律）；停止需二次确认，且确认有时限（超时自动取消）
- Given 选择已定局的任务请求停止，Then 提示"已定局，无可停止"（不误导为操作成功）
- Given 用户在面板中打开任务输出，Then 进入输出全屏查看：跟随输出增长（停底时）、可翻页回滚、无输出时明确说明
- Given 面板只呈现后台任务；前台任务在主对话流内呈现（转后台后才进入面板）

### US12.2 前台任务转后台的用户入口（P0）

作为用户，前台跑着的任务（命令或子代理）我可以一键转为后台继续，且不丢失。

验收：
- Given 前台任务运行中，When 用户按下约定的"转后台"快捷键，Then 当前前台任务转为后台继续运行（不被终止），用户立即得到反馈（转了几个、去哪查看）
- Given 无前台任务在跑，When 按下快捷键，Then 明确提示"没有正在运行的前台任务"（按键不做无关动作）
- Given 前台任务刚好结束，When 按下快捷键，Then 提示"任务已结束"
- Given 前台任务运行中，Then 其界面上展示转后台的入口提示（命令类任务运行一段时间后才出现提示以免干扰；子代理类立即出现）
- Given 前台任务被转为后台，Then 原界面卡片呈现"已转后台"标记（即使该次调用的结果返回，也不伪转为"已完成"）

### US12.3 后台状态播报与常驻徽章（P1）

作为用户，后台任务的开始与定局在对话流可见，进行中数量常驻可见。

验收：
- Given 后台任务开始/定局，Then 对话流出现一条状态播报（含任务描述与结局：完成/失败/超时/停止/丢失，进程类附退出码或原因，丢失附"会话重启前未完成"说明）
- Given 后台任务在跑，Then 界面常驻徽章分别显示"命令任务数"与"子代理任务数"两类计数
- Given 会话回放（重开查看历史），Then 后台任务的播报与定局对等呈现（不因重开而丢失或错标）

### US12.4 定时触发的呈现（P1）

作为用户，定时任务触发注入的消息要能一眼认出"这是计划触发"，且带足上下文。

验收：
- Given 定时任务触发并注入，Then 消息以可辨识的专属样式呈现（区别于用户手打消息）：标题表明"计划提醒已触发"（错过的触发合并时为"错过的计划提醒"）、计划表达式、任务标识、是否一次性、合并次数、过期标记（过期用警示色）
- Given 该消息正文，Then 展示注入的提示词全文
- Given 会话回放与导出，Then 定时触发消息对等呈现（识别来源信封，不显示原始标记符）

### US12.5 网页端对等呈现（P1）

作为用户，网页端的任务查看、停止与子代理实时详情与终端能力对等（**范围声明**：网页端不承诺"前台任务转后台"的快捷入口——终端的转后台交互不在网页端验收范围，是否补齐另立项，见提案 P1/P4 一并裁决）。

验收：
- Given 网页会话中有后台任务，Then 对话区提供任务入口（按"命令任务/子代理任务"分组的计数入口），点击进入任务列表
- Given 任务列表，Then 每行呈现状态、名称、类型、计时；进行中的任务可停止（真实停止）；命令类任务可展开查看命令与输出（可复制）
- Given 子代理类任务（含前台），Then 提供实时详情视图：流式文本与按调用分组的工具执行记录；工具卡片提供跳转入口
- Given 网页打开的是桌面壳（桌面应用），Then 任务/子代理/定时消息呈现与网页一致（同一界面）
- Given 定时触发在网页端，Then 以用户气泡样式呈现（语义上是用户预先排定的消息），携带计划人话说明、合并次数、过期标记与任务标识

## 17. 未来增强提案（超出 TS 现状，明确标注为提案）

> 以下为设计余量方向的**建议**，非 TS 引擎现有能力，Rust 核心不承担对齐义务；采纳与否需单独立项裁决。各条的现状依据统一见 [subagent-context.md](subagent-context.md) §6.1/§6.2/§6.6/§6.13，此处只陈述目标侧建议。
>
> 裁决进度注（2026-09-12，B0）：P2 已由 SDR-005 采纳并入；P1/P4 已纳入本程序（落地批次见 [subagent-ROADMAP.md](subagent-ROADMAP.md) §4/§5）；P3（全局 P-022）与 P5（全局 P-024）已裁决推迟（同上）。

- **P1 定时任务的用户自助管理面**：为用户提供直接的定时任务管理入口（如终端命令/网页界面：列表、删除、手动触发一次），与"用户只能请模型代为排定/变更"的现状互补。
- **P2 定时任务的时区显式化**：支持显式时区参数并保留本地时区缺省，消除跨时区协作（会话迁移、远程环境）下的语义漂移。
- **P3 通知的分级与免打扰**：为低价值通知（如心跳类任务的例行完成）提供聚合/降噪选项，避免合成消息打扰主线。
- **P4 任务面板的跨会话视图**：提供"全部后台任务"聚合视图（按工作区），便于多会话并行时的总览；同 P1 一并考虑网页端的前台转后台入口。
- **P5 cron 表达式支持秒级与命名别名**：如需秒级调度或 `Mon`/`Jan` 类别名，须评估调度精度与解析复杂度。
- **P6 后台任务的阻塞等待入口**（2026-09-13 增补）：当派发者判定"下一步依赖后台任务结果、且当前确无其他可做的有效工作"时，提供**原地等待**能力——等待一个或一批后台任务定局后再返回，替代当前唯一手段"反复调用非阻塞快照查询直到定局"（自治目标模式（goal）下该模式会退化为连续轮询确认，token 空耗；现状盘点见 [subagent-context.md](subagent-context.md) §6.13）。验收要点（提案级）：a) 等待带时长上限，到期任务仍未定局时**诚实返回部分输出与"仍在运行"标注**，不伪装为失败或完成；b) 到期结果的下一步指引引导"结束回合等通知或换不依赖该结果的切片工作"，不再连续等待；非阻塞快照的未就绪返回同样附一行"完成将自动送达、勿重复查询"的动态提示（现状为裸"未就绪"无任何提示）；c) 等待期间用户中断可即时打断等待；d) 等待定局的结果与自动通知不重复投递（等待的返回即应答）；e) 等待入口的文案与"优先不等待"的既定契约一致（默认仍是非阻塞快照，等待是显式选择且带"劝退"说明）；f) 批量等待时先定局者的结果即时并入返回，未定局者按 a)/b) 处理（部分定局可辨识，不伪装为全员完成）。**现状标注**：TS v2 无阻塞等待入口；v1/Rust 的等待参数分别处于休眠 legacy 与未迁移状态，三者均不构成 TS v2 现行能力，本条为提案。**裁决（2026-09-13）**：已由 SDR-011 采纳（A+B 组合之「辅」），转正为 E13/US13.1；提案正文按惯例保留不改写，终态以 E13 为准。
- **P7 自治目标模式（goal）与后台任务的协调**（2026-09-13 增补）：目标模式下驱动继续回合的"续航提示"应感知进行中的后台任务，让派发者在续航回合有依据地选择**不依赖待定结果的切片工作**或正常结束回合等通知，而不是因"缺结果的下一步无法推进、又无人告知结果会自己来"而陷入轮询（结构根因见 [subagent-context.md](subagent-context.md) §6.13；与 US10.4 压缩后重注入同一设计家族——把"有任务在跑、通知会来"这个事实在需要的时机重申给模型）。验收要点（提案级）：a) 仅当存在进行中的后台任务时，续航提示携带任务清单；b) 清单含数量/类型/描述，为注入时刻的快照；c) 清单附带"完成会自动以消息送达、勿轮询查询"的指引；d) 任务清零后续航提示不再携带清单；e) 与 P6 的文案口径一致（等待是显式选择，默认引导为不等待）。**裁决（2026-09-13）**：已由 SDR-011 采纳（A+B 组合之「主」的输入面），转正为 E13/US13.2，挂起语义另立 US13.3；提案正文按惯例保留不改写，终态以 E13 为准。

## 19. Epic E13：等待与自治目标模式的协同（2026-09-13 增补）

> 解决「自治目标模式下，等待后台结果退化为连续轮询确认」的空耗问题（裁决依据 SDR-011，A+B 组合）。非目标模式不受影响——回合结束后台通知的闭环原样成立；本 Epic 只补齐目标模式下的「合法等待」语义。归属切分：等待入口、任务清单供给、通知唤醒属本域；目标循环的挂起态/看门狗/预算计费属目标（goal）域（该域规格落点见 ROADMAP O11），本 Epic 记录其对用户可见的协同契约。

### US13.1 后台任务的阻塞等待入口（P0）

作为派发者，当我明确需要原地等待一个后台任务的结果时，我想显式选择「等待它定局」，以便用一次等待替代反复查询确认。

验收：
- Given 派发者对运行中的后台任务显式选择等待，When 等待开始，Then 持续到该任务定局或达到声明的时长上限为止，等待期间不再产生新的查询开销
- Given 等待到期任务仍未定局，When 返回，Then 诚实返回当时的部分输出与「仍在运行」标注（不伪装为失败、不伪装为完成），并附下一步指引：结束回合等通知、或转做不依赖该结果的切片工作，且明确劝阻再次原地等待
- Given 普通查询（不带等待）返回「未就绪」，When 查看，Then 附一行「完成将自动送达、勿重复查询」的动态提示（不返回无任何提示的裸「未就绪」）
- Given 等待期间用户发出中断，When 中断到达，Then 等待即时被打断并进入正常中断语义
- Given 等待以任务定局结束，When 返回，Then 等待的返回即该任务的应答，不再补发一份完成通知（不重复打扰）
- Given 多个后台任务被并行等待，When 部分先定局，Then 各自定局各自返回（先完成者先拿到结果）；到期仍未定局者按上述到期语义处理
- Given 等待入口的说明面，Then 保持「优先不等待」的既定契约：默认仍是即时快照，等待是显式选择且说明面劝退不当使用

### US13.2 自治目标模式续航提示的任务感知（P0）

作为派发者，在目标模式的续航回合里我想知道有哪些后台任务还在跑、它们的结果会自己来，以便有依据地选择不依赖待定结果的切片工作，而不是陷入查询循环。

验收：
- Given 目标进行中且存在未定局的后台任务，When 续航提示注入，Then 携带任务清单（数量/类型/描述，注入时刻快照）与「完成会自动以消息送达、勿轮询查询」的指引
- Given 无进行中的后台任务，When 续航提示注入，Then 不携带清单（与现状一致，不加噪音）
- Given 清单中的任务在注入后定局，When 查看后续，Then 清单以注入时刻为准不回写（快照语义，定局走通知）
- Given 提示中的指引，Then 与等待入口（US13.1）的文案口径一致：等待是显式选择，默认引导为不等待

### US13.3 等待挂起与通知唤醒（P0，目标域协同契约）

作为派发者，在目标模式下当前确实没有可做的事、只剩等待后台结果时，我想让目标循环停下来等结果自己来，而不是被反复要求「继续朝目标工作」。

验收：
- Given 目标进行中、存在未定局的后台任务，且续航回合结束时派发者未执行任何实际工作（无工具调用），When 判定，Then 视为「正在等待」信号：目标循环挂起，不再发起新的续航提示
- Given 挂起期间任一后台任务定局，When 通知到达，Then 以该通知开启新回合消化结果（目标上下文随回合常驻提醒一并在场；一次唤醒一个回合，不双开）
- Given 挂起持续且无任何事件（任务未定局、通知被抑制或异常丢失），When 超过兜底时限，Then 强制续航一次（等待不能变成永久沉睡）
- Given 挂起期间用户插话，When 消息到达，Then 照常开启回答回合（用户优先于挂起）
- Given 目标处于挂起，Then 挂起期不计入回合数预算（消耗的是时间，不是回合）

## 20. Epic E14：重启后的孤儿后台进程治理（2026-10-14 增补）

> 解决「服务退出后，后台进程仍活着且无人认领」的失控问题。场景：agent 后台启动的长时命令（如全量测试）在服务重启/崩溃后继续占用机器资源——占用可长达数小时到数十小时，无任何面板可见、无任何入口可停。归属切分：本 Epic 管**进程形态**后台任务的跨服务代际回收；子代理执行流与后台提问不持有独立 OS 进程，天然随服务消亡，不在本 Epic 范围。

### US14.1 任务档案携带进程身份（P0）

作为用户，当一个后台命令被后台启动时，它的进程身份就随任务档案一并留存，以便将来任何一方（服务重启后的新实例、诊断工具）都能准确回答「这个任务对应的进程还在不在、是不是它」。

验收：
- Given 以后台方式启动一个命令，When 任务档案落盘，Then 档案包含该进程的身份指纹（进程号、进程组号、该进程的启动时刻）与命令文本（旁证展示信息，不参与身份判定——见 A15）
- Given 两份任务档案，When 比对，Then 各自的身份指纹互不混淆（身份指纹的含义见 A15——「进程号 + 进程启动时刻」共同构成身份，进程号单独不构成身份）
- Given 一个在前台跑过、后被转后台的任务，When 它落盘，Then 档案同样携带身份指纹（前台/后台只是等待方式不同，进程身份的留存规则一致）
- Given 一份不含身份指纹的旧任务档案（指纹机制引入前落盘的记录），When 普查，Then 按「无法判定」处理：仅出现在普查报告里，不参与任何处置（保守降级，不误伤）

### US14.2 服务启动时的孤儿普查（P0）

作为用户，服务每次启动时自动盘点「上一代服务遗留、可能还活着」的后台进程，让我不必自己去猜机器为什么卡。

验收：
- Given 服务启动且上一代服务留有「档案未定局」的进程类后台任务，When 启动完成，Then 自动执行一次孤儿普查并把结果归档（每个候选：任务号、描述、命令、已存活时长、普查判定）
- Given 普查发现某任务对应的进程（组长）已不存在，When 判定，Then 该任务档案收敛为「已丢失」（与 US9.1 的「已丢失」呈现一致）；若其进程组内仍有存活后代，则单独登记为「组内残留」进入报告（见 US14.3 第二条），不被静默遗忘
- Given 普查发现某进程号当前被**别的程序**占用（进程号被复用），When 判定，Then 绝不把它当作我们的孤儿（按身份指纹校验，见 A15），档案按「进程已不存在」收敛
- Given 普查发现某任务确为存活的孤儿（身份指纹匹配），When 默认模式，Then **只报告、不动手**：结果留存可查，不杀进程、不改任务状态
- Given 服务启动时上一代服务正常退出、且无声明「退出保留」的任务，When 普查，Then 无候选、零开销

### US14.3 孤儿的处置策略与安全边界（P0）

作为用户，孤儿进程的处置必须「默认不动手、动手必精准、动过手必有痕」。

验收：
- Given 孤儿普查发现存活孤儿，When 用户（或配置）选择终止，Then 只向身份指纹确认过的那个进程所在的进程组发信号，不主动向指纹确认范围之外的任何进程发信号（后代进程自行脱离进程组的情形超出信号可达范围，属事实边界非承诺违约）
- Given 某孤儿任务的进程组组长已死、但组内仍有后代进程存活（普查登记的「组内残留」），When 处置，Then 默认模式仅报告；仅当用户明确选择终止该组时才对其动手（该组是任务启动时创建的独立组——这是安全边界的事实基础；终止执行前重验组内成员仍属该组，组号被系统复用给他人的情形除外并如实报告）
- Given 处置已执行，When 落档，Then 被处置任务的档案收敛为「已丢失」并注明「启动普查处置」与处置时刻，此档案不再参与后续普查
- Given 任一普查/处置动作，When 事后查看，Then 有完整记录可回溯（何时普查、发现什么、判了什么、做了什么）
- Given 配置面，Then 处置策略仅两档：「仅报告」（默认）与「报告并终止」；不存在「静默终止」档（动手必先可见）

### US14.4 无时限后台任务的硬上限兜底（P1）

作为配置者，即使任务声明「不限时」（长任务合法），也有一个可配置的总寿命上限兜底，防单个后台任务无限占用。

验收：
- Given 未配置总寿命上限，Then 使用内置缺省（4 小时）；配置为 0 表示不设限
- Given 后台任务（含声明「不限时」者）超过总寿命上限，When 定局，Then 按「已超时」处置：终止并附续作指引（与 E5 超时语义一致，同一套状态词）；总寿命的计数起点 = 任务创建时刻，全程连续累计（不因转后台、等待外部输入而重置或暂停）
- Given 总寿命上限触发，When 查看，Then 说明真实原因（达到总寿命上限），不伪装为自然完成
- Given 用户明确知道某任务需要更长，When 发起时，Then 可显式豁免该单次任务的总寿命上限；同一任务的豁免至多一次，不可追加续期（要延长就重新发起，豁免不是第二条默认路径）
- Given 任务声明「退出保留」，When 总寿命上限判定，Then 该任务**默认豁免**总寿命上限（「退出保留」本身是用户显式要它活着的表态，与寿命兜底的动因冲突）；其资源可见性仍由 US14.6 覆盖，普查处置入口（US14.3）仍可终止它

### US14.5 活跃后台任务的关闭决策点（P1）

作为用户，关闭一个仍有活跃后台任务的会话（或退出服务）时，我应该被告知并有权选择，而不是任务被无声处置。

验收：
- Given 会话关闭/服务退出时存在活跃的后台进程任务，且任务未声明「退出保留」，When 关闭，Then 先发出明确告知（哪些任务、跑了多久），再按既定策略执行（默认：全部真实停止）
- Given 任务声明了「退出保留」（既有配置，含义不变），When 关闭，Then 该任务不受停止影响，其档案保持未定局，成为下一代普查的候选（进入 US14.2 流程）
- Given 关闭时存在交互界面（终端 / 网页 / 桌面任一），When 关闭触发告知，Then 界面呈现选择：「全部停止」或「保留到后台」（选择不改变上两条的默认值，只改变这一次的行为）；呈现与选择由各端的会话关闭确认承载（消费端契约按 E12 先例：本域定契约，呈现归各端）
- Given 无界面模式（服务进程退出、无任何客户端在场），When 关闭，Then 不等用户：直接按既定策略执行（默认全部真实停止），告知内容落入日志与下次普查报告（决策点是有界面时的增强，不是关闭的前置条件）

### US14.6 孤儿与超长任务的资源可见性（P1）

作为用户，机器变卡时我能查到「是不是遗留的后台任务在吃资源」。

验收：
- Given 孤儿普查完成，When 用户查看任务历史，Then 上一代遗留的候选与判定结果可见（含存活状态、已存活时长）
- Given 普查后孤儿仍存活，When 用户查看，Then 该任务明确标注「上一代遗留、不受当前服务管控」与其命令、描述，用户能看到但当前服务不提供对它的常规操作（操作走 US14.3 的处置入口）


### SDR-013 后台进程的跨服务代际治理：进程身份指纹、启动普查与「仅报告」缺省（2026-10-14；评审二轮修订）

1. **背景与动机**：进程形态的后台任务（后台命令）在服务退出后成为无主进程——无面板可见、无入口可停，可继续占用机器资源数十小时（多见于 agent 后台发起的全量测试/构建类长命令）。既有收敛路径只覆盖「服务正常关闭」：会话 close 同步收敛全部任务（SDR-007），但「退出保留」（keepAliveOnExit，G33 既有配置）的任务与崩溃路径都产生「档案未定局、进程无主」的孤儿态，无人对账。进程号会被操作系统复用，孤儿判定不能只看进程号。
2. **决策**：a) **进程身份指纹**：进程类后台任务档案落地「进程号 + 进程组号 + 进程启动时刻」（术语 A15）——启动时刻使身份在进程号复用下仍然唯一可判；命令文本仅作旁证展示，不参与判定。b) **启动普查**：服务每次启动执行一次孤儿普查，对上一代遗留的「档案未定局」进程类任务按指纹校验，判定三分支——①指纹匹配 → 存活孤儿（登记报告）；②进程号不存在/被复用 → 档案收敛「已丢失」；③组长已死但进程组内仍有存活后代 → 档案收敛「已丢失」的同时登记「组内残留」单独报告（该形态正是事故形态之一，不得静默归档）。普查与既有的「会话加载时把运行中任务调谐为已停止」机制的时序关系由 ADR-012 裁决（普查先行、加载尊重普查结论）。c) **处置缺省「仅报告」**：普查只报告不动手；动手档位（报告并终止）必须显式配置，终止只向指纹确认的进程组发信号，执行前重验。d) **总寿命上限兜底**：全局可配的进程类后台任务总寿命上限（缺省 4 小时，0 = 不设限，计数起点 = 任务创建时刻、全程连续累计；单次任务可显式豁免，同一任务至多一次）；「退出保留」任务默认豁免（用户已显式表态要它活）——超时语义复用 E5「已超时」，不发明新状态。
3. **被否决的备选方案**：a) 纯进程号判定——复用误伤；b) 普查即自动终止——与「动手必有痕」域原则冲突，组长死亡态在无确认下不可控；c) 新增 wire 状态（如 orphaned）——SDR-007 同型论证，「已丢失」+原因注记已可表达；d) 仅靠总寿命上限——「退出保留」与崩溃路径下上限无执行者（服务不在场），普查是唯一入口；e) 命令文本参与判定——同命令巧合进程与真孤儿不可区分；f) 「退出保留」任务也套总寿命上限——与该配置「用户显式要它活」的语义直接冲突。
4. **影响范围**：新增 Epic E14（US14.1–14.6）；E5 超时语义扩展至总寿命上限触发（同词表）；US9.1「已丢失」呈现新增来源（启动普查处置）；glossary A15 同批登记；配置面新增孤儿处置策略与总寿命上限两旋钮；会话加载调谐机制与普查的时序耦合裁决见 ADR-012（评审二轮补）；「退出保留」（keepAliveOnExit，G33）任务的档案成为普查候选（Q8 的 b 路线如未来裁决通过，同走此衔接，本次不预裁 Q8）。
