# Skills 技能系统域 — 内置技能逐技能需求规格（设计文档）

> 状态：v1 · 2026-10-10 ·
> **定位**：本文件是 skills 域的补充需求规格文档——逐技能给出全部 **6 个内置技能（8 个注册条目）**的**用户可见行为契约**（触发与门控、功能闭环、安全范式、依赖面、验收标准），作为 **Rust 内核对齐的权威规格源**。这是 Rust 需要对齐的**底线**，不是天花板；Rust 可以做得更好。
> 与域内其他文档的关系：技能系统通用机制（发现/优先级/激活管线/门控/呈现）见 [skills-requirements.md](skills-requirements.md)（本文只做逐技能细化，不重复通用条目——通用条目以 requirements 为准）；实现机制见 [skills-architecture.md](skills-architecture.md)；代码定位（文件:行号、注册包装、v1/v2 文案差异）见 [skills-context.md](skills-context.md) §10，本文不重复。
> **约定**：① 各技能的 `description` 原文是**模型可见接口的一部分**（模型据此判断何时自动调用），本文照录英文原文——Rust 侧应逐字对齐或刻意改进（改进须披露）；② 验收标准统一 Given-When-Then；优先级 P0 > P1 > P2；③ 叙述用中文，产品名/工具名/命令名保留英文；④ 本文所有行为均为**终态需求**，不含执行状态。
> 优先级口径：`write-goal` 与 `update-config` 标 P0（模型可自动调用的两个，多端复用面最广）；`mcp-config`、`custom-theme`、`import-from-cc-codex` 标 P1（用户显式调用的配置/迁移工作流）；`sub-skill` 家族标 P2（技能库整理元工作流，依赖已有一定规模的用户技能库）。

## 0. 通用约定（全部内置技能共享）

### 0.1 注册条目与调用门控

| # | 技能名 | 一句话 | 模型可自动调用 | 优先级 |
|---|---|---|---|---|
| 1 | `write-goal` | 帮用户把模糊意图打磨成有完成契约的 `/goal` 目标 | ✅ | P0 |
| 2 | `update-config` | 查看 / 修改产品自身配置（引擎配置与终端界面配置两个文件） | ✅ | P0 |
| 3 | `mcp-config` | 配置 MCP 服务器与处理 MCP OAuth 登录 | ❌（仅用户显式调用） | P1 |
| 4 | `custom-theme` | 创建 / 编辑终端自定义配色主题 | ❌（仅用户显式调用） | P1 |
| 5 | `import-from-cc-codex` | 从 Claude Code / Codex 迁移指令、技能与 MCP 声明 | ❌（仅用户显式调用） | P1 |
| 6 | `sub-skill`（父） | 发现并把技能库重组成层级化子技能包 | ❌（仅用户显式调用） | P2 |
| 7 | `sub-skill.review` | 只读分析技能集并提议分组（子技能） | ❌（仅用户显式调用） | P2 |
| 8 | `sub-skill.consolidate` | 执行已批准的分组，移动技能并做时间戳备份（子技能） | ❌（仅用户显式调用） | P2 |

- 全部内置技能随产品分发（不落用户目录、不依赖磁盘发现），来源层级为**内置（最低优先级）**，用户/项目层的同名技能可覆盖内置版本（覆盖语义见 requirements US2.1/US2.3，本文不重复）。
- 内置技能正文以英文撰写（模型接口语言）；其中 `write-goal` 内建了「以用户语言产出草稿」的输出行为（见 §1），其余技能的对话语言遵循产品通用行为。
- 各技能正文遵循技能格式契约（头部配置区 + 正文），并适用通用激活管线：用户斜杠激活的排队语义、激活卡片呈现、撤销锚点、遥测（requirements US3/US8，不重复）。

### 0.2 命令入口与多端呈现（P0）

- Given 终端输入框，Then 六个技能以**裸名**斜杠命令可用：`/write-goal`、`/update-config`、`/mcp-config`、`/custom-theme`、`/import-from-cc-codex`、`/sub-skill`（不带 `skill:` 前缀）；子技能同样以裸名列出（`/sub-skill.review`、`/sub-skill.consolidate`），只是不进**模型可见清单**（US1.2 口径：不在模型列表中；斜杠命令用裸名）。
- Given 网页端对话输入框，Then 内置技能同样出现在斜杠菜单中（裸名条目），选中后命令留在输入框供追加参数；网页端无会话时以技能命令发出首条消息，先创建会话再执行激活（requirements US3.3 的多端语义对内置技能同样成立）。
- Given 模型可见技能清单，Then 内置技能归入「Built-in」分组呈现（requirements US4.1）。
- **与客户端命令的分工（不是重复）**：终端的 `/goal`、`/config`、`/theme`、`/mcp`、`/editor` 等是**客户端即时动作**（面板/选择器）；内置技能是**模型行为指引**（一次对话内完成的分析与文件工作）。两者并存且各自保持入口；技能正文负责在合适的时机把用户指向客户端命令（如 `/theme`、`/reload`），反之客户端帮助文案应能发现对应技能。

### 0.3 写文件安全范式（分档，P0）

会写用户文件/资产的内置技能按**三档安全范式**约束，作为逐技能验收的公共底座——其中**完整六条**由 `update-config` 与 `custom-theme` 共用；`import-from-cc-codex` 与 `sub-skill.consolidate` 采用各自的子集/变体（在各自技能节显式定义）：

- **数据根解析先行**：Given 任何触及产品数据目录的操作，Then 先解析真实数据根（环境变量 `MIRRICODE_HOME` 优先，为空回退 `~/.mirri-code`），绝不假设默认路径。
- **先读后写**：Given 任何修改目标，Then 先读取目标文件；目标不存在（或为空）不算错误（后续创建最小骨架）；目标存在但**解析失败**（损坏的 TOML/JSON）→ 原样报告错误并**停止**——绝不就地覆盖一个损坏的文件（可能摧毁用户既有配置）。
- **候选副本，不就地编辑**：Given 修改既有文件，Then 先逐字复制出候选副本，只对候选做最小编辑（只改目标键/条目，保留全部既有内容、注释与格式），校验通过后再覆盖。
- **时间戳备份，全部保留**：Given 覆盖既有文件，Then 覆盖前创建带时间戳的备份（命名形如 `原名.YYYYMMDD-HHMMSS.bak`，取备份时刻）；**每次都新备份、永不覆盖既有备份、全部保留**（不是单一 `.bak`）；目标本不存在时跳过备份。
- **校验通过才覆盖**：Given 有产品自带的校验手段（如配置诊断命令），Then 候选必须先通过校验、失败则修候选再验、循环至通过后才覆盖。
- **权威参照优先**：Given 有官方文档作为字段权威，Then 编辑前先取官方参照；取不到时明确告知用户并请求确认或粘贴，**绝不凭猜测编辑**。

**范式适用范围**：六条完整成立的技能是 `update-config` 与 `custom-theme`（后者以读回校验替代诊断命令；官方令牌文档仍是首选参照，取不到时回退内置令牌参照表而非停止）。`import-from-cc-codex` 走**保守迁移范式**（§5.1：预览确认前零写入、既有条目绝不覆盖、绝不整体替换、MCP 不落盘）；`sub-skill.consolidate` 走**迁移执行范式**（§6.2：计划确认 + 逐目录时间戳备份，但不承诺候选副本与校验循环）。

## 1. `write-goal`（P0 · 模型可调用）

> description 契约原文：
> Help the user craft a well-specified `/goal` objective for goal mode — turn a rough intention into a completion contract with a clear finish line, proof, boundaries, and stop rule. Use when the user asks for help writing, refining, or improving a goal.

**定位**：目标模式（goal 域）的「起草助手」。用户想用 `/goal` 但只有模糊意图时，本技能把意图打磨成一份**完成契约**——说清什么必须为真、如何证明、边界在哪、何时停下报告。撰写目标文本与启动目标是两个分离的步骤：先共同敲定措辞，用户批准后才经创建目标工具启动（启动时仍有最终确认，用户保留最后一票）。

### 1.1 介入纪律（P0）

- Given 用户没有要求写目标（普通「修复这个测试」类请求），Then 不主动把请求包装成目标、不擅自启动；若任务看起来适合目标模式，至多提一次该选项，等用户选择。
- Given 目标撰写过程中出现**选项式**决策（写什么范围、选哪种措辞、要不要加预算与多大、以什么权限模式启动），Then 一律经结构化提问工具（带选项与推荐项的选择题）呈现——**不得**写成一段散文罗列选项让用户自由回复，也不得把三个问题揉成一堵文字墙；相关选择可在同一次提问中打包。
- Given 结构化提问工具确实不可用（自动权限模式或不支持的宿主），Then 退化为一条带清晰标号选项的短消息并等待回复。
- Given 开放式输入（如「什么能证明这算完成？」），Then 纯文本提问是正当的——本条铁律只约束**选项之间**的选择。
- Given 用户书写语言，Then 目标草稿与讨论用同一语言；项目配置或已保存记忆声明了偏好语言时优先遵循。

### 1.2 好目标的契约形状（P0）

- Given 一份非平凡的目标草稿，Then 它定义**证明而非努力**，并覆盖以下要素中任务所需的部分：
  1. **终态**——必须为真的条件，落点具体（通过某套件、清零某队列、某文件已存在）；
  2. **证明**——可观察的证据，优先是可运行、事后可检查的（命令退出码、测试计数、零命中检索、指标阈值）；
  3. **边界**——可以碰与不可以碰的范围（目录/模块、禁区动作）；
  4. **迭代方式**——可迭代时说明怎么迭代（每次改动后重跑检查、按队列逐项推进）；
  5. **停止规则**——「完成不可达时停下报告而非硬凹」的条款（外部服务不可用→记录并继续；扩范围前先停下问），诚实条款与预算分离。
- Given 任务呈队列形状（失败测试、开放 issue、待迁移文件），Then 优先建议队列化——给代理一份工作清单、给用户一个可数的完成定义。
- Given 任务已有可复用验证手段（测试、CI、类型检查、lint、评测、零命中搜索），Then 草稿锚定它们；任务没有任何完成证明手段时，帮用户补一个，或重新考虑目标模式是否合适。
- Given 草稿质量自查，Then 不含「持续改进 X」式努力描述，而含可检验的「done when 检查 X 通过」式表述；短任务可以只是一句清晰的话，结构随工作规模与跑偏代价增长——更长的运行不是更好的运行。

### 1.3 预算的选择性启用（P1）

- Given 用户没有要求预算，Then 不默认设置预算、**绝不把回合上限写进目标文本**——契约良好的目标靠证明通过或撞上阻塞自然停止。
- Given 预算确实有益（通常是开放式/探索性、可能长时间无人值守的目标），When 建议，Then 以用户实际感知的量（代币成本）为框架、数值由用户选择、并对明显过大的值（如几轮可完成的目标配一千回合）提示一次更小的选择，尊重用户最终决定。

### 1.4 工作流与启动（P0）

- Given 协作流程，Then 按五步走：①理解意图（缺终态或缺检查是第一个要一起解决的缺口，开放问题一旦收敛为具体选项即转结构化提问）→ ②起草（用户语言、可读性优先）→ ③完整展示草稿并解释取舍（选了什么做终点、什么做证明、围了什么、何时停、哪里还软）→ ④一起修订（备选措辞/范围以结构化提问呈现；多轮直至满意；用户要更宽松就指出一次权衡后照写）→ ⑤启动。
- Given 措辞已获用户同意，Then 调用创建目标工具启动（有完成判据则一并传入）——不得只打印文本让用户自己粘贴，也不得在用户批准前启动；启动动作本身仍有最终确认。
- Given 起草被用户否定/放宽，When 已指出模糊或风险一次，Then 写用户要的版本——不再反复重申、不擅自「改进」。

**依赖面**：结构化提问工具（AskUserQuestion）、创建目标工具（CreateGoal，goal 域）；`/goal` 命令族与目标模式续航语义归 goal 域。

## 2. `update-config`（P0 · 模型可调用）

> description 契约原文：
> `Inspect or edit mirri-code's own config — config.toml (model, provider, permission, hooks) and tui.toml (theme, editor, notifications, auto-update). Use when the user asks what a setting does or wants to change one.`

**定位**：产品自身配置的解释者与安全修改者。两个 TOML 配置文件（snake_case 键）的所有权不同，先判定用户指哪个再动手：**引擎/运行时配置**（模型、provider、权限、hooks、循环控制等）与**终端界面偏好**（主题、编辑器、通知、自动更新——这些通常也能用交互命令 `/config`、`/theme`、`/editor` 更改，交互命令更容易，应优先把用户指向它们）。

### 2.1 解读类请求（只读，P0）

- Given 用户问「有哪些配置 / 这个设置是干什么的 / 怎么用」，Then 以官方文档 + 当前目标文件为据作答：列出相关节与键、各自作用、**当前值与默认值对照**、合法值域、属于哪个文件的哪个节；以紧凑的分组列表或表格呈现；**全程只读，不写任何文件**。

### 2.2 修改类请求（复制 → 编辑 → 校验 → 备份 → 覆盖，P0）

- Given 修改请求，Then 按序执行：
  1. **澄清意图**：哪个键、什么值、哪个文件；模糊时一句话询问（离散选择可用结构化提问，自由输入用普通提问）；
  2. **读取目标**（含解析失败即停止，见 §0.3）；
  3. **复制候选**：逐字复制目标为同目录 `-new` 后缀副本；目标不存在时才用最小骨架新建候选；
  4. **编辑候选**：只改/只加目标键，既有节、条目、注释与格式原样保留；改动对照官方文档检查（键名/节/值类型/合法值、snake_case）；
  5. **校验候选**（见下条校验规则），失败则继续编辑候选再校验，循环至全过；
  6. **备份并覆盖**：先建时间戳备份（§0.3），再以候选覆盖目标；覆盖后重载报错时，用户可从最近的时间戳备份恢复；
  7. 告知生效方式（见 2.3）。
- Given 候选校验，Then 用产品的配置诊断命令（不启动界面、不改文件，产品自身解析器 + 模式校验，是权威检查），按所改文件选子命令并显式传候选路径；退出码 0 = 通过，非 0 = 指定文件缺失或配置非法 → 原样展示输出、修候选、重跑至 0。诊断命令另有**无路径形态**（检查当前生效的两个配置文件，缺失的显示为跳过），用于整体体检而非候选校验。另做两项诊断命令覆盖不到的检查：①对照官方文档交叉核对（「模式合法但不是用户要的」，如拼错的模型别名）；②**完整性**——原文件的每个既有条目仍在候选里（候选是整体替换，丢一行即一次删除）。
- Given 目标文件不在两文件之列（其他作用域/文件形态），Then 以官方文档为准决定位置与写法，不凭猜测扩展。
- Given 官方文档在线参照，Then 任何触碰配置前先取官方配置文档作为字段（键名、类型、合法值、所属节）的唯一权威参照；取不到时明确告知无法到达在线文档，请用户粘贴相关节或确认是否凭已知继续——**绝无权威参照不盲改**。

### 2.3 生效告知（P1）

- Given 覆盖完成，Then 生效方式按文件区分：改了引擎配置 → 终端 `/reload`（重载会话并应用，同时也会重载界面配置）；只改界面配置 → `/reload-tui`（更轻）；两者都改 → 一次 `/reload` 覆盖。
- Given 提醒边界，Then 告知 `/reload` 仅空闲时可用（流式中需先 Esc / Ctrl-C 停止）；校验已过所以重载应干净落地，若仍报错按报错修复或从最近备份恢复；不想立即重载时，**下一个新会话**自动生效。

**依赖面**：官方配置文档站、配置诊断命令（`mirri doctor` 的 config/tui 子命令）、`/reload` 与 `/reload-tui` 命令、配置文件语义归 model-settings 域。

## 3. `mcp-config`（P1 · 仅用户显式调用）

> description 契约原文：
> `Configure MCP servers and handle MCP OAuth login.`

**定位**：MCP 服务器配置的交互式入口：要么替一个正在等待 OAuth 的服务器完成登录，要么编辑登记 MCP 服务器的 JSON 配置。工作小而局部——当回合自己完成，不派子代理、不建计划待办。**两条流先判定再动手**：工具面存在某服务器的认证工具（`mcp__<server>__authenticate`）且用户说登录/鉴权、调用 `/mcp-config login <server>` 或引用「待认证」状态 → **登录流**；增删改查配置条目 → **配置编辑流**；裸 `/mcp-config` 且工具面无任何认证工具 → 配置编辑流（若有待登录，认证工具会在工具面上）。

### 3.1 登录流（P0）

- Given 走登录流，Then 调用用户所指服务器的认证工具——该工具自身的描述负责 OAuth 体验（打印授权 URL、等待回调、成功后重连）；其输出（含授权 URL）**逐字呈现，URL 不做任何编辑**（其中的状态与 PKCE 参数改了就废）。
- Given 用户指名的服务器没有认证工具，Then 一句话说明并**停止**——不落入配置编辑（用户要登录的是一个当前没在等登录的服务器，悄悄改配置是错误的修法）。
- Given 存在多个认证工具且用户未指名，Then 询问指哪一个。

### 3.2 配置编辑流（P0）

- Given 纯粹「看看配置了什么」，Then 读全部三个配置文件，呈现**带来源路径上下文的合并视图**（足以让用户检查或从真正声明它的文件里移除某服务器）后停止——无范围提问、无写入。
- Given 修改请求，Then 三步：
  1. **选范围**：能从用户措辞推断就推断（全局/所有项目 → 用户全局；仓库根/共享/跨代理/Claude 兼容 → 项目根；当前目录/本产品专属 → 项目本地）；真无法推断时用**一次**结构化提问（默认用户全局）；用户关闭该提问即**停止**——不能安全地猜用户想把改动放哪。其余问题一律普通文本（结构化提问不适合自由输入）。
  2. **读取并宣布**：读目标文件（缺失/为空不算错，后续创建空壳）；解析失败原样报错并停止（§0.3）。然后向用户展示目标路径、现有内容、即将写入或删除的条目——这是**透明而非确认门**（编辑/写入的权限提示才是真正的门，此消息是权限提示出现时用户的上下文；yolo/auto 模式没有提示是那些模式的明示契约）。
  3. **写入并告知重载**：保留无关条目与外层包装；MCP 服务器在会话启动时加载，告知用户新开会话（如 `/new`）或重启产品后生效。
- Given 三层配置文件，Then 依次为：**用户全局**（数据根下 `mcp.json`，处处生效）、**项目根**（`.mcp.json`，从当前目录向上找最近 git 仓库根；用于 Claude 兼容、仓库共享、跨代理的服务器）、**项目本地**（当前目录下本产品专属的 `mcp.json`）；键冲突时按此顺序**后者覆盖前者**。项目根与项目本地的 stdio 条目会在会话启动时执行命令，应提示一次**只放信任的仓库**。
- Given 条目形态，Then 最小 stdio 条目需要 `command`（可选 `args`、`env`、`cwd`）；最小 http 条目需要 `url`，静态令牌鉴权的服务器加 `bearerTokenEnvVar`（OAuth 服务器不写令牌字段——登录流负责）；传输形态由 `command` 与 `url` 推断，无须声明；项目根 `.mcp.json` 的 stdio 条目默认从项目根运行，相对 `cwd` 按该文件所在目录解析。
- Given 条目中的字符串值，Then 支持 `${VAR}` 与 `${env:VAR}` 环境变量引用（配置加载时从进程环境解析；未定义展开为空串——展开后为空的必填字段（如空 `url`）校验失败；对象键与数值字段永不展开）；设置界面对此类文本编辑**字面量**，只读预览展示解析后的值。
- Given 用户想改**所有**服务器的超时，Then 指向全局默认（引擎配置的 mcp 节两个键或对应环境变量），不逐服务器写超时字段；每服务器字段覆盖全局；每个超时必须是 1 至 2147483647 毫秒的整数。
- Given 密钥类值，Then 不以明文落盘为原则：http 服务器用环境引用字段、stdio 的 `env` 等字符串用环境变量引用；必须写明文时先警告用户。

**依赖面**：MCP 认证工具与 `needs-auth` 状态、mcp.json 语义与模式归 mcp 域。

## 4. `custom-theme`（P1 · 仅用户显式调用）

> description 契约原文：
> `Create or edit a mirri-code custom color theme — a JSON file under the resolved MIRRICODE_HOME data directory that recolors the TUI. Use when the user wants their own theme, asks for a specific palette or mood, or wants to tweak an existing custom theme's colors.`

**定位**：终端自定义配色的设计、写入与应用助手。一个主题是一个 JSON 文件；产品自带 `dark`、`light`、`auto`，用户添加的任何文件（文件名不与这三个保留名冲突时——保留名的自定义文件不会与内置主题并排出现）出现在主题选择器中。

### 4.1 介入纪律（P0）

- Given 任何创建动作，Then 前置条件是用户已明确四件事：**明还是暗**、**风格或情绪**、**有无必须遵守的具体颜色**、**文件名**；缺任一先问（离散选择——明暗、几个风格备选——优先结构化提问；自动模式下退化为标号选项的纯文本并等待）；没弄清明暗与大致风格之前不动笔选色。
- Given 调整既有自定义主题，Then 先读该主题文件——没读过的主题绝不覆盖（§0.3）。

### 4.2 主题契约（P0）

- Given 主题文件位置，Then 在数据根的 `themes/` 子目录下，**文件名即主题名**（`ember.json` 在 `/theme` 选择器中显示为 `Custom: ember`）；目录不存在则创建。
- Given 文件形态，Then 含 `name`（必填）、`displayName`（可选）、`base`（可选，`"dark"` 缺省或 `"light"`）、`colors`（每个值为 6 位十六进制 `#RRGGBB`）；**部分主题合法**——未给出的令牌回落到 base 调色板，可以只重配几个令牌。
- Given 选色约束，Then 只用官方令牌集（未知键加载时被静默忽略）；每个值是完整 6 位十六进制（不是 3 位、不是命名色）；对照度有可用性要求（`text`/`textDim` 不贴背景、`success`/`warning`/`error` 互相可区分、`primary` 是最常见色须可读且与 `text` 区分、`roleUser` 是唯一有独立色相的角色色）。无效十六进制值加载时被静默跳过（回落 base）——发现即修，保证主题按预期渲染。
- Given 官方令牌文档，Then 选色前先取官方主题文档作为令牌与语义的权威清单；取不到时回退技能内置的令牌参照表（同一令牌集的镜像）并告知用户正在用内置清单而非在线文档。
- 令牌语义（每个令牌控制什么）以官方文档为准；技能内置参照表覆盖 19 个令牌：`primary`（最常用色：链接、内联代码、几乎所有对话框的选中项、聚焦编辑器边框、计划/运行徽章、转圈）、`accent`（次高亮：审批前缀、设备码框、图片占位、注册表导入、插话/队列面板）、`text`（正文）、`textStrong`（强调/粗体文本）、`textDim`（次级弱化文本，使用最广的暗色：思考中、提示、描述、已完成待办、引用、状态栏）、`textMuted`（最弱文本：计数、滚动信息、链接 URL、代码块边框）、`border` / `borderFocus`（面板与编辑器边框 / 焦点边框〔当前仅审批面板〕）、`success` / `warning` / `error`（成功/警示/错误态）、`diffAdded` / `diffRemoved` / `diffAddedStrong` / `diffRemovedStrong` / `diffGutter` / `diffMeta`（差异六件套：增行/删行/行内增词/行内删词/行号槽/分块头）、`roleUser`（用户消息圆点与文本、技能激活名）、`shellMode`（shell 模式提示符、编辑器边框与命令回显）。

### 4.3 写入与应用（P0）

- Given 写入流程，Then 遵循写文件安全范式（§0.3）：候选 `.json.new` → 校验（读回确认 JSON 良构、每个颜色值是完整 6 位十六进制）→ 时间戳备份 → 移入。
- Given 应用方式，Then 两条：`/theme` 选择器**每次打开都重扫主题目录**——新文件无须重启即可见，指引用户 `/theme` 选 `Custom: <名>`；或在界面配置里设 `theme = "<名>"`。
- Given 编辑**正在使用中**的主题，Then 变更不自动重载——指引 `/reload-tui`（或切走再切回）；在选择器里重选**同一个**主题是无操作（「主题未变」）。

**依赖面**：终端 `/theme` 与 `/reload-tui` 命令、主题文件加载器；本技能面向终端配色（web 端主题面不在其范围，见 §8 提案）。

## 5. `import-from-cc-codex`（P1 · 仅用户显式调用）

> description 契约原文：
> `Import Claude Code and Codex instructions, skills, and MCP settings into Mirri Code.`

**定位**：把用户本地的 Claude Code / Codex 资产**有选择地**迁入本产品。刻意保守：只迁 `.claude` / `.codex` 面上的**指令、技能、MCP 服务器声明**三类，任何写入前都有用户预览。

### 5.1 不可协商的边界（P0）

- **不迁** `.agents` 内容（本产品原生支持 `.agents` 技能与 AGENTS 文件）。
- **不迁** Claude 自定义命令（`.claude/commands/**`，超出本导入器范围）。
- **不迁**凭据、OAuth 令牌、会话、历史、日志、hooks、插件、插件缓存、output styles、自定义代理/子代理。
- **不运行、不安装**源目录里的任何东西。
- 用户选定要迁的内容、审阅过最终预览并**明确确认应用**之前，**不写任何东西**。
- 只写本产品目标路径：用户全局（数据根）、项目指令/技能（项目根的 `.mirri-code/`，项目根 = 最近的含 `.git` 父目录，无 `.git` 用当前目录）、项目本地 MCP（**当前工作目录**下的 `.mirri-code/mcp.json`——本产品读的是当前目录的专属 MCP 文件，不是子目录下的各项目根版本）。
- **保留既有文件**：绝不整文件替换既有的 AGENTS.md / mcp.json / 技能。

### 5.2 会话流程（P0）

1. **先问迁什么**：读源文件之前，先问用户要迁哪些类别——指令（AGENTS.md / CLAUDE.md）、技能、MCP 设置、全部（多选，结构化提问；不可用时纯文本提问并等待）。调用参数里已给了偏好则作为默认/推荐项呈现，**仍要确认类别**。用户关闭或拒绝即停止。
2. **只扫所选类别**：用户级源（`~/.claude/`、`~/.codex/` 下的指令、技能目录；Claude 用户级 MCP 只在选了 MCP 时读 `~/.claude.json`，不为纯指令/技能导入去读它；Codex 用户级 MCP 读 `~/.codex/config.toml`）与项目级源（项目根下 `.claude/`、`.codex/` 的同类路径）。**不扫**项目根 `AGENTS.md`、项目根 `CLAUDE.md`、`.agents/**`、项目根 `.mcp.json`（本产品原生已读）。
3. **构建导入计划**（三分节，含精确来源与目标路径，见 5.3）。
4. **展示最终预览并停**：按目标文件/目录分组呈现——将追加的指令块、将复制的技能包/文件、留给手工 `/mcp-config` 后续的 MCP 条目、已存在/跳过项、警告与阻塞项。然后请求明确确认（应用 / 取消）；**有阻塞项时不提供应用选项**，先解释必须先修什么。
5. **确认后才应用**（见 5.4）。

### 5.3 计划规则（P0）

- **指令**：用户级源 → 数据根的 `AGENTS.md`；项目级源 → 项目根 `.mirri-code/AGENTS.md`。以带标记的块**追加**（标记含来源绝对路径，成对包裹来源内容；Codex 用对应的 Codex 标记）；目标里已存在的同源标记块不重复追加；源文件为空记跳过；目标存在但无法按 UTF-8 文本读取 → 写前停止并报告阻塞。
- **技能**：用户级源 → 数据根 `skills/`；项目级源 → 项目根 `.mirri-code/skills/`。识别两种形态（目录包 `<名>/SKILL.md` 与平铺 `<名>.md`），整包复制并保留包内辅助文件；不复制隐藏目录、`node_modules`、缓存、插件托管目录。计划前先读目录包的 `SKILL.md` 确认头部有非空的 `name` 与 `description`（目录技能的必填项）；目标顶层条目已存在即**跳过不覆盖**；两个来源会写同一目标时按「项目 Claude > 项目 Codex > 用户 Claude > 用户 Codex」保留首个、报告后者跳过。源技能使用了生态特有字段或语法（`allowed-tools`、`disallowed-tools`、`context: fork`、`agent`、`hooks`、`paths`、动态 shell 注入、`agents/openai.yaml`）时**警告**本产品可能不按原意解释，但保留文件不重写（除非用户明确要求）。
- **MCP**：**不直接写 MCP 配置**。收集候选并尽可能归一化为本产品 MCP 形态后放入预览：Claude 用户级（读 `~/.claude.json` 顶层 `mcpServers`，保留 stdio 的 `command` 与 http 的 `url` 条目，保留合法的伴随字段，丢弃不支持/畸形条目并报告原因）；Codex（读所选 `config.toml` 的 `[mcp_servers.<名>]` 表，字段映射：`command`/`args`/`env`/`cwd`/`url`/`enabled` 同名直映，`bearer_token_env_var`→`bearerTokenEnvVar`，`enabled_tools`→`enabledTools`，`disabled_tools`→`disabledTools`，秒→毫秒两例（启动/工具超时），`http_headers`→`headers`；丢弃 Codex 专属字段并报告，尤其 `required`、审批模式族、`env_vars`、`env_http_headers`、`experimental_environment`）。范围映射：用户级源 → 用户全局目标；项目级源 → 项目本地目标（当前目录不是项目根时在预览中特别指出，让用户明白何时会加载）。stdio 条目会话启动即执行命令——警告只迁信任的服务器；条目疑似含明文密钥（`env`、`headers`、令牌类字段）时警告并建议环境引用。

### 5.4 应用与后续（P0）

- Given 用户确认应用，Then：目标目录尽可能以私有权限创建；追加指令块不重复既有同源块；复制技能不覆盖既有目标条目；**不写任何 MCP 条目**——展示可复制的手工后续（应运行的 `/mcp-config` 命令、目标范围与路径、归一化后的 JSON 条目、名称冲突时保留既有条目、保留无关条目的提醒），并明确 **MCP 导入保持待办**直至用户手工执行；精确报告改了什么、跳过什么；告知新会话（如 `/new`）或重启后新导入的技能、指令与 MCP 服务器才生效。
- Given 调用参数已给类别偏好，Then 作为默认/推荐项仍走确认；Given 所选类别什么都没找到，Then 明说、不当错误处理。
- **输出风格**：简短精确；预览与摘要用绝对路径；小表格或短列表优先于长散文。

**依赖面**：`/mcp-config` 技能（本技能**不得**经模型工具调用它——它是用户专用技能）；技能格式契约（US1.x）。

## 6. `sub-skill` 家族（P2 · 仅用户显式调用）

> 父技能 description 契约原文：
> `Discover and reorganize the skill inventory into hierarchical sub-skill bundles. Use when the user asks to review, group, or consolidate skills into a parent bundle.`
> `sub-skill.review`：
> `Analyze the available skill set and recommend candidate groups that could be consolidated into sub-skill bundles. Read-only — proposes a plan, does not move files.`
> `sub-skill.consolidate`：
> `Apply an approved sub-skill grouping by moving user-specified skills into a parent bundle, with timestamped backups of every modified directory.`

**定位**：技能库整理的元工作流。父技能是容器与调度说明：常规流程是先 `sub-skill.review`（只读提案），用户批准计划后再 `sub-skill.consolidate`（执行）；**未经用户明确放行绝不执行 consolidate**。子技能以「父名.子名」注册：不单列于**模型可见清单**（US1.2），但斜杠命令以裸名列出（`/sub-skill.review`、`/sub-skill.consolidate`，与 US1.2/US3.1 的口径一致——不在模型列表中；斜杠命令用裸名）。

### 6.1 `sub-skill.review`（只读提案，P2）

- Given 审查请求，Then 按序：①列全量清单（名称、描述、来源层级）；②按功能域归类；③检测耦合（常一起用、`whenToUse` 相近的技能）；④标记粒度问题（过细——一个命令行旗标一个技能；过泛——落不进任何单一域）；⑤为每个候选组提议父技能名与一行描述、应迁入的子技能、必须随迁的载荷目录（文档/参考/示例/资产/模板，保证目录布局对齐）、父技能是否需要子技能开关（有子要发现就需要）；⑥输出分组摘要报告（带理由）后**停止**——不改任何文件（那是 consolidate 的事）。
- Given 好分组的判据，Then 逐条满足：组内技能**共享功能语境**（同一功能域）；父技能为组提供**可组合的自然入口**（顶层句柄）；**嵌套偏浅**（两层为宜，避免三层及以上）；**向后兼容**（既有技能名保持可发现）；粒度适中（不过细——一个命令行旗标一个技能；不过泛——落不进任何单一域）。

### 6.2 `sub-skill.consolidate`（执行，P2）

- Given 执行请求（通常来自已批准的 review 提案），Then 按序：
  1. **确认计划**：复述哪些技能将移到哪，**做任何文件改动前**请用户确认；
  2. **逐目录备份**：每个将被修改的技能目录（含父目标）先做时间戳备份（整个目录），全部保留、不覆盖既有备份（§0.3）；
  3. **创建/更新父包**：父不存在则创建（头部配置区带子技能开关）；已存在则确保开关在位；
  4. **移动子技能**：每个子技能**整个目录**迁入父包下；
  5. **载荷目录对齐**：文档、参考、示例、资产等载荷目录随子技能对齐新目录布局；
  6. **验证结果**：呈现新的目录结构，确认每个被移动技能的 `SKILL.md` 仍带有效的 `name` 与 `description`，载荷目录对齐、内部相对链接不断；
  7. **报告变更**：迁移了什么、新的结构、随迁的文档目录，以及**各备份的位置**。

## 7. 非功能需求

| # | 需求 | 验收要点 |
|---|---|---|
| NF1 | **随产品分发**：内置技能不落任何用户目录、不依赖磁盘发现；用户/项目层同名技能可覆盖（US2.3） | 全新安装（空用户目录）下 6 技能全部可用 |
| NF2 | **正文即接口**：技能正文是模型可见接口的一部分——正文措辞的变更视为接口变更，Rust 对齐或刻意改进（改进须披露），不得静默偏离 | 逐字对照或披露改进清单 |
| NF3 | **上下文成本**：内置技能走「清单常驻、全文按需」的两级结构（US4/US5），不因内置身份常驻全文 | 技能清单条目按描述截断注入；全文仅激活时注入 |
| NF4 | **写操作安全范式分档**：§0.3 六条为 `update-config` 与 `custom-theme` 的完整底座；`import-from-cc-codex`（预览确认、绝不覆盖既有、不写 MCP）与 `sub-skill.consolidate`（计划确认、逐目录时间戳备份）各按其技能节内定义验收 | 按技能对照其所属范式逐项可验 |
| NF5 | **权威参照的可回退性**：依赖在线官方文档的技能（update-config、custom-theme）在文档不可达时有明确的告知与回退路径（请用户粘贴确认 / 内置参照表 + 告知），不盲改 | 断网场景逐条成立 |
| NF6 | **多端透传**：内置技能清单经程序接口透传（会话级/工作区级两口径），网页端斜杠菜单与终端一致可用 | TUI 与 web 对同一会话列出相同内置技能集 |

## 8. 未来增强提案（超出参照现状）

> 以下均为〔提案〕——尚不存在参照实现的建议，实现与否由 Rust 侧独立裁决；**不得作为现状承诺引用**。

1. **技能正文本地化**：内置技能正文为英文（模型接口语言）；`write-goal` 已内建「以用户语言产出草稿」的输出行为，但正文本身未本地化。若 Rust 侧做正文 i18n，须保持语义逐条等价并披露。
2. **web 端主题技能的对应物**：`custom-theme` 面向终端配色；web 端有自己的主题面。建议 Rust 侧为 web 定义对应内置技能（或在本规格标注终端专用），避免 web 用户经模型改到不生效的终端主题。
3. **命令/技能双入口的互相指路**：`/goal` 命令与 `write-goal` 技能、`/config` 与 `update-config`、`/theme` 与 `custom-theme`、`/mcp` 与 `mcp-config` 是成对的客户端动作与模型指引。建议 Rust 侧保持双入口，并在客户端命令帮助与技能正文中互相指路（参照现状：技能正文已指路命令，命令帮助未指路技能——该对照不构成现状承诺）。
4. **MCP 登录流的 web 对应物**：`mcp-config` 的登录流依赖 MCP 认证工具；web 端已有自己的授权页。建议明确两端入口分工并在规格中登记，防止同一 OAuth 流两端各做一套。
5. **内置技能的版本披露**：技能无版本概念；若 Rust 侧正文有语义变更，建议在更新说明中按技能披露（复用插件更新徽章机制的思路，见 requirements §11 提案 7）。
