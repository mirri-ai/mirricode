# 会话归档存储管理 — 需求文档

> 状态：v2 基线 · 2026-10-23 · 待用户评审 ·
> 本文是会话归档存储管理域需求侧的唯一事实源（内部规格文档，不进文档站构建，中文单语）。
> 产品愿景：**归档不该默默吃掉硬盘**——后台自动把旧的归档会话压缩瘦身（无损、可逆、无感），删除永远由用户在专属管理页亲手决断；用户在管理页能看到每条归档"占多少、压了多少、放了多久"，清不清、清哪个，一目了然。
> 配套文档：技术形状与机制见 [session-retention-architecture.md](session-retention-architecture.md)；现状盘点见 [session-retention-context.md](session-retention-context.md)；执行状态见 [session-retention-ROADMAP.md](session-retention-ROADMAP.md)。
> 术语规范：SR1 自动压缩、SR2 归档时点、SR3 压缩态、SR4 档位清理、SR5 附件回收，及沿用的 S2 归档会话、S5 会话日志、S4 会话索引、S1 会话恢复，唯一定义见 [glossary.md](glossary.md)；压缩时点（SR2 的对称术语，`compressedAt`）的定义随 SR3 一并登记于 glossary；本文件只使用这些规范叫法。
> 范围边界：本域覆盖**归档会话的自动压缩、压缩态的只读消费与恢复、用户手动删除（单条与批量）、附件存储联动回收，及其配置项与管理页交互**。归档动作本身、会话列表交互（置顶、排序）、检查点（快照）机制属"会话持久化"域（[session-persistence-requirements.md](session-persistence-requirements.md)），本域只消费其存储契约；删除的**存储语义**（目录 + 索引行 + 附件回收收敛）经持久化域登记（其 ADR-018）对所有删除入口生效，但**删除的交互入口**（列表按钮、工作区清空）归其所属域。上下文压缩（对话摘要）与磁盘压缩（文件体积缩减）同名不同物，本域只涉及后者——磁盘压缩（SR3）。

## 0. 角色定义

| 角色 | 场景 | 核心诉求 |
|---|---|---|
| **长期用户**（产品用了几个月、积累了上百条会话的人） | 发现磁盘空间告警、目录大小失控 | 不用懂内部机制，旧归档自动瘦身；重要的东西只有自己点头才会被删 |
| **翻旧账用户**（偶尔要找回几个月前归档会话的人） | 归档很久之后想取回、查看、导出 | 被自动压缩过的会话仍可完整查看、导出；取回后还能继续干活 |
| **决断用户**（要释放磁盘、准备动手清理的人） | 打开归档管理页，判断删什么 | 每条归档占多少空间、压缩省了多少、放了多少天，清清楚楚；批量清理一键完成且明示后果 |
| **旁观用户**（没有开启本功能的用户） | 默认安装、从未碰过设置 | 行为与现在完全一致，零变化、零感知
| **双进程用户**（桌面端与终端同时使用的人） | 压缩发生时另一进程正在干活 | 后台压缩绝不干扰正在使用的会话，绝不损坏共享数据 |

## 1. Epic RT1：不越权的默认（P0）

> 解决"信任前提"。自动压缩是对磁盘的处置，必须由用户显式授予；自动删除不存在（本域铁律）。

### US1.1 默认零行为（P0）

作为旁观用户，我想让产品在不开启本功能时对磁盘数据的行为与没有本功能时完全一致，以便升级不带来任何意外。

验收：
- Given 用户未开启自动压缩，When 产品运行任意时长，Then 没有任何**自动**的压缩、移动或删除发生在会话数据上（管理页中我亲手点击的"立即压缩/删除"等显式操作除外）；磁盘占用只增不减（与现状一致）
- Given 用户未开启自动压缩，When 查看任何历史归档会话，Then 读取、恢复、导出行为与本功能不存在时完全一致

### US1.2 显式开启与可预期配置（P0）

作为长期用户，我想用两个直白的设置控制压缩行为，以便不用理解内部机制就能预知产品会做什么。

验收：
- Given 我开启了自动压缩，When 设置"归档压缩天数"为 N（N ≥ 1），Then 一条归档会话在归档满 N 天后才被压缩，绝不在归档满 N 天之前被压缩
- Given 我开启了自动压缩，When 设置"检查间隔"为 H 小时（H ≥ 1），Then 压缩检查每 H 小时发生一次
- Given 任一天数/间隔设置值不合法（非正整数、无法解析），When 产品读取配置，Then 该项回退默认值、其余项照常生效；功能总开关解析失败时视为关闭——两种失败都只留一条日志，不崩溃（见 US5.1 的拆分定义）
- Given 我关闭了自动压缩，When 此前已被压缩的会话存在，Then 这些压缩会话保持压缩现状（不会被解压、不会被删除）；关闭即停止一切自动判定
- Given 配置项缺失任何子项，When 产品读取，Then 缺失项用默认值补齐，其余项照常生效

### US1.3 恢复归档即终止处理（P0）

作为翻旧账用户，我想让恢复归档一条会话后它脱离压缩流程，以便救回来的会话不会在背后被处理掉。

验收：
- Given 一条会话已归档且压缩倒计时进行中，When 我恢复归档它（清归档标记），Then 该会话立即脱离本次及后续一切压缩判定，按普通活跃会话对待
- Given 一条已压缩的会话，When 我恢复归档它，Then 它先被完整还原为压缩前的形态，再作为普通会话出现；还原后继续使用、发消息、导出，行为与从未被压缩完全一致（SR3 压缩态的还原，见 [glossary.md](glossary.md)）
- Given 一条会话被恢复归档后再次归档，When 压缩检查发生，Then 重新从新的归档时点起算压缩天数

## 2. Epic RT2：自动压缩与压缩态（P0）

> 解决"占空间的主矛盾"。压缩是后台家务：无损、可逆、无感；删除永远不自动（SR1 铁律）。

### US2.1 到期归档自动压缩（P0）

作为长期用户，我想让到期的归档会话被自动压缩，以便硬盘先降下来，同时数据一条不少。

验收：
- Given 一条归档会话已到"归档压缩天数"，When 压缩检查发生，Then 它的对话记录被压缩存储，磁盘占用降到压缩前的一小部分（量级见架构文档承诺）；会话本体（名称、标签、时间）完整保留
- Given 压缩过程在中途被中断（断电、强杀），When 事后查看该会话，Then 要么是压缩前的完整原样、要么是压缩后的完整压缩态，不存在半损状态
- Given 一条会话正在被另一个进程使用（恢复、导出、发消息中），When 压缩检查扫描到它，Then 本轮跳过它，绝不与正在进行的读写赛跑
- Given 我未开启自动压缩，When 在管理页使用"立即压缩"操作，Then 手动压缩不受总开关限制，正常执行（US1.1 的"零行为"指**自动**路径零动作，管理页的显式操作是用户亲手指令，不属自动路径）
- Given 会话历史列表与归档视图，When 浏览已被压缩的会话，Then 它正常可见并带有"已压缩"标识，用户能区分它与普通会话（标识在网页端与终端端的呈现属本域交付，见 Epic RT3 / SDR-007）

### US2.2 压缩会话的只读透明（P0）

作为翻旧账用户，我想让被压缩的会话在查看、导出、搜索上与未压缩无异，以便压缩对我透明。

验收：
- Given 一条已压缩的会话，When 我查看对话内容，Then 完整历史正常呈现，与压缩前一字不差
- Given 一条已压缩的会话，When 我导出它，Then 导出产物与未压缩会话的导出产物内容一致
- Given 搜索功能，When 检索结果命中已压缩的会话，Then 命中与摘要呈现正常，与未压缩会话无差别
- Given 一条已压缩的会话，When 我恢复归档它并继续发消息干活，Then 它先自动还原为压缩前形态再继续工作；后续一切行为（写入、检查点、再归档）与从未被压缩的会话完全一致

### US2.3 压缩会话不可复制（P0）

作为用户，我想让"复制会话"入口对压缩会话明确不可用，以便我理解压缩态的边界：要复制，先恢复归档。

验收：
- Given 一条已压缩的会话，When 我尝试复制它（任何入口），Then 复制被拒绝并明确提示"压缩会话需先恢复归档后才能复制"，绝不产生残缺产物
- Given 我先恢复归档一条压缩会话，When 还原完成后对它复制，Then 复制正常，产物与复制普通会话无异

### US2.4 附件回收仅随删除联动（P1）

作为长期用户，我想让图片等附件占用的空间随会话删除一并回收，以便"删了会话硬盘却没降"这种事不发生。

验收：
- Given 一条会话被删除（任何删除入口），When 它引用过的附件不再被任何其他存活会话引用，Then 这些附件的存储被一并释放（允许实现侧的延迟，但最终释放且不残留引用）
- Given 一条会话被删除，When 它引用过的附件仍被其他存活会话（含普通会话）引用，Then 这些附件完整保留，其他会话不受影响
- Given 附件回收发生，When 任何存活会话查看其图片，Then 图片正常显示（回收只针对"无人引用"的附件）
- Given 附件回收在中途被中断，When 事后查看，Then 不存在"附件被删但引用它的会话还在"的状态——要么附件还在、要么引用它的会话已全部删除

### US2.5 存量归档的保守起点（P1）

作为长期用户，我想让功能上线后第一次检查对历史上早已归档的会话从当前时刻起算，以便升级不会"一键压缩"我多年的旧归档。

验收：
- Given 历史上已归档但无法确定归档时点的会话，When 第一次压缩检查遇到它，Then 以本次检查时刻作为其归档时点起算，完整走过"归档压缩天数"后才会被压缩
- Given 存量会话被补上归档时点，When 后续检查发生，Then 与新归档的会话同一套规则判定，无特殊通道

## 3. Epic RT3：归档管理页（P0）

> 解决"决断时刻"的体验。删除永远手动，且发生在信息完备的管理页里。设置页交互规格以网页端为准绳（桌面端同构复用）。

### US3.1 管理页入口与两个视图（P0）

作为决断用户，我想在设置里打开"归档会话"管理页，分"归档"与"已压缩"两个视图浏览，以便分别处理未压缩与已压缩的存量。

验收：
- Given 我打开归档管理页，When 页面加载，Then 呈现"归档"与"已压缩"两个视图（tab 或等价切换），默认落在"归档"视图
- Given 列表首次加载中 / 加载失败，When 页面渲染，Then 有明确的加载状态与失败重试入口，不呈现空白或半截列表
- Given "归档"视图，When 列表渲染，Then 每条显示：标题、所属工作区、归档时间、磁盘占用；行内操作有：恢复归档、立即压缩（跳过天数等待、即时执行的手动压缩，不受自动压缩总开关限制）、删除
- Given "已压缩"视图，When 列表渲染，Then 每条显示：标题、所属工作区、归档时间、压缩时间、**已压缩天数**、当前占用、**压缩节省量**（压缩前占用 − 当前占用）；行内操作有：恢复归档（先还原为压缩前形态，再清归档标记，会话离开本管理页、回到普通会话列表）、删除

### US3.2 列表排序与状态（P0）

作为决断用户，我想按占用和天数排序归档与已压缩会话，以便快速找到"最值得删"的对象。

验收：
- Given "已压缩"视图，When 我首次进入，Then 列表默认按磁盘占用从大到小排列
- Given "归档"视图，When 我首次进入，Then 列表默认按归档时间从近到远排列
- Given 任一视图，When 我点击可排序列头，Then 按该列升序/降序切换；可排序列为封闭集合——"已压缩"视图：占用、已压缩天数、归档时间；"归档"视图：占用、归档时间
- Given 管理页已打开，When 会话数据被其他入口（另一进程压缩/删除/恢复归档、本进程操作）改变，Then 列表在合理的时间窗口内反映变化（拉取刷新或推送更新，实现侧择一），不长期呈现已失效的条目
- Given 任一视图为空，When 页面渲染，Then 显示空态文案（如"没有归档会话"），不显示空白框架

### US3.3 单条删除（P0）

作为决断用户，我想在任一视图删除单条会话，以便精确处置。

验收：
- Given 我在某视图点击某条会话的"删除"，When 确认对话框弹出，Then 明示：将删除哪条会话、预计释放多少空间（口径：立即释放的会话本体 + 随后联动回收的附件，附件部分最迟数小时内完成）、**此操作不可恢复**；只有我确认后才执行，取消则不发生任何变化
- Given 我确认删除，When 删除完成，Then 该条从列表消失、附件按 US2.4 联动回收、列表数据刷新
- Given 删除中途失败，When 结果反馈，Then 明确告知失败与原因，会话数据不被半删（要么原样、要么删净；残留的中间态在下一次删除尝试时收敛）

### US3.4 批量清理按钮（P0）

作为决断用户，我想用时间档位按钮一键清理压缩已久的会话，以便大批量释放空间不用逐条点。

验收：
- Given "已压缩"视图，When 页面渲染，Then 提供多个时间档位的批量清理按钮："清理压缩超过 30 天""清理压缩超过 90 天""清理压缩超过 180 天""清理压缩超过 365 天"（档位为产品默认集合，文案中的天数即档位定义）
- Given 我点击某个档位按钮，When 确认对话框弹出，Then 明示：将删除 N 条会话、预计释放约 X MB（口径同 US3.3）、此操作不可恢复；只有我确认后才执行
- Given 我确认批量清理，When 执行完成，Then 范围内会话全部删除（附件按 US2.4 联动回收），范围外一条不动；列表与统计刷新
- Given 批量清理正在执行，When 我重复点击任意档位按钮或操作列表，Then 操作被防重入（不产生第二次删除），并有执行中的进度反馈
- Given 档位范围内没有任何会话，When 我点击按钮，Then 明确提示"没有符合条件的会话"，不弹确认框、不执行任何删除
- Given 批量执行中部分会话删除失败，When 结果反馈，Then 逐条或汇总告知成败明细，失败条目保留在列表中

### US3.5 自动压缩状态告知（P1）

作为长期用户，我想在管理页看到自动压缩是否在生效，以便确认配置真的在起作用。

验收：
- Given 我开启了自动压缩，When 打开归档管理页，Then 页面以一句话级别的提示呈现当前策略（如"归档满 N 天后自动压缩"）；该提示不构成列表数据的一部分
- Given 压缩/删除动作发生，When 我事后翻查，Then 有可查的日志记录（哪条会话、做了什么、何时）

## 4. Epic RT4：无感与不扰民（P1）

> 解决"后台家务不该被感知为事故"。

### US4.1 启动零负担（P1）

作为任意用户，我想让压缩工作完全不拖慢产品启动，以便开产品永远是快的那件事。

验收：
- Given 产品启动，When 启动宽限期内（时长为固定常量，由架构文档定义），Then 不发生任何压缩活动
- Given 压缩检查正在进行，When 我同时使用产品（开会话、发消息、切界面），Then 压缩不阻塞任何用户操作

### US4.2 跳过不是终局（P1）

作为任意用户，我想让被跳过的会话在下一轮被重新正常处理，以便瞬时冲突不留永久遗憾。

验收：
- Given 压缩检查跳过了某个会话（例如它正被另一进程使用），When 下一轮检查，Then 它被重新正常判定，跳过不是终局

## 5. Epic RT5：并发安全（P0）

> 解决"多进程一份数据"。压缩与另一进程的读取、恢复、写入、归档并发时，永不损坏、永不赛跑。删除的手动入口天然低频，同样受此保护。

### US5.1 压缩与并发互斥（P0）

作为双进程用户，我想让压缩与另一个进程对同一会话的操作互相安全，以便后台压缩永远不会毁掉我正在干的事。

验收：
- Given 桌面进程正在恢复归档一条会话，When 终端进程的压缩检查同时扫描到它，Then 压缩本轮跳过该会话；两操作最终都成功，会话数据无损
- Given 压缩正在压缩一条会话，When 另一进程恰好同时要恢复归档它，Then 恢复方要么看到压缩前的完整形态、要么等到压缩完成后按压缩态正常恢复归档（还原），不存在读到半成品
- Given 一条会话刚被另一进程归档（毫秒级之前），When 压缩检查同时扫到它，Then 它以新归档时点完整走完压缩天数，不会被"抢跑"压缩
- Given 多个进程同时开启自动压缩，When 检查同时发生，Then 同一会话最多被处理一次，不出现双重压缩导致的错误
- Given 另一进程正在恢复归档某会话，When 我在管理页删除它，Then 要么删除被拒并提示会话正被使用、要么等恢复归档完成后由我再次确认执行；不存在删除与还原并发产生的半删半还原状态
- Given 删除与压缩同时对同一会话生效，When 两者竞争，Then 最多一个动作生效（先到者），后到者得到明确结果（成功方为压缩时删除按压缩态执行、成功方为删除时压缩空跑无害），数据无第三态

## 6. Epic RT6：配置入口（P1）

> 解决"在哪开、怎么改"。配置文件是唯一持久入口；管理页（RT3）展示策略但不修改策略。

### US6.1 配置即契约（P1）

作为长期用户，我想在产品的个人配置文件中开启和调整压缩行为，以便偏好可持久、可版本化、可手工迁移到别的机器。

验收：
- Given 我在个人配置文件中写下压缩设置（开关与两个数字：归档压缩天数、检查间隔），When 产品启动并读取配置，Then 压缩行为按设置生效
- Given 配置子项不合法，When 产品读取，Then 按逐项回退处理：天数/间隔不合法 → 该项用默认值、其余照常生效；开关解析失败 → 视为关闭；两种失败都只留日志、不崩溃（与 US1.2 第三条同一契约的验收视角）
- Given 我修改配置后保存，When 下一轮检查发生，Then 按新配置判定

## 7. 非目标

- **不存在任何形式的自动删除**：无论压缩多久、占用多大，删除只发生在用户显式操作（管理页单删或档位批量删）。这是本域铁律（SR1）。
- **不压缩未归档的会话**：无论多旧、多大，只要未归档（或被恢复归档过），永不进入自动压缩——用户没收纳的东西不碰。
- **不做按总量的自动清理**："超过 N GB 自动删"类容量策略不在范围内。
- **不清理附件存储中与删除会话无关的孤儿**：SR5 附件回收只随删除联动，不做独立的附件全量垃圾回收。
- **压缩会话的复制入口一律不可用**：提示"需先恢复归档"（US2.3）；不在复制路径上做透明解压。
- **不动旧一代（TS）会话存储根**：压缩只作用于当前引擎的会话数据根；旧存储根的处置由迁移机制（会话持久化域）先行决定。
- **档位按钮集合不配置化**：30/90/180/365 天为产品默认档位，不提供自定义档位配置（保持交互简单；自定义需求出现时另行立项）。

## 8. 决策记录

### SDR-001 自动压缩（策略两级制的修订）

- **日期**：2026-10-23
- **背景**：归档会话的磁盘占用持续增长且无回收机制。v1 基线曾裁决"先压缩后自动删除"两级策略；评审后用户裁决修订。
- **决策**：**自动压缩 + 手动删除**——归档满"归档压缩天数"后台自动压缩（无损、可逆、无感）；删除永不自动，唯一入口是归档管理页（单条删除与时间档位批量清理，见 SDR-002）。原 `delete_after_days`（压缩后自动删除天数）配置删除。
- **否决的备选**：
  - 压缩后自动删除（v1 方案）：不可逆处置自动化的信任风险；用户失去对删除的最终决定权。
  - 全手动（压缩也手动）：控制感最强，但从不进设置页的用户硬盘继续增长，核心痛点无解。
  - 只压缩永不删：可逆性最好，但"决断用户"的空间归零诉求无法满足，且无信息完备的决断入口。
- **影响范围**：US1.2、US2.1、US3.3、US3.4、US6.1；术语 SR1、SR4。

### SDR-002 归档管理页与档位批量清理

- **日期**：2026-10-23
- **背景**：删除手动化后，用户需要一个信息完备的决断场所：看不到占用与天数，就无法判断删什么。
- **决策**：新增"归档会话"管理页（设置内），"归档"与"已压缩"两视图；压缩视图默认按占用降序、可切换排序，列含"已压缩天数"与"压缩节省量"；批量清理按钮采用固定时间档位集合（30/90/180/365 天），执行前确认框明示条数、释放量与不可恢复性。设置页交互规格以网页端为准绳，桌面端同构复用（与仓库既有页面规格惯例一致）。
- **否决的备选**：
  - 按总量/按条数批量（"清理最大的 10 条"）：看似直接，但"大小"不是用户判断删除的天然维度（价值才是），时间档位与用户的"放着很久没用了"心智一致。
  - 自定义档位输入：交互与校验成本高，固定档位覆盖主流场景。
  - 不设批量入口、只逐条删：大批量释放场景体验不可用。
- **影响范围**：US3.1–US3.5。

### SDR-003 压缩会话不可复制

- **日期**：2026-10-23
- **背景**：压缩态是只读的中间态。v1 曾按"透明 fork"设计；用户裁决修订：压缩会话在会话树中不提供复制现实——要复制先恢复归档。
- **决策**：压缩会话的所有复制入口明确不可用并提示"需先恢复归档"；恢复归档（还原）后复制行为与普通会话无异（US2.3）。
- **否决的备选**：
  - 透明复制（v1 方案）：能力保全最全，但复制路径需透明解压读源日志，且"会话树中压缩态可复制"的产品语义混乱；用户裁决弃。
  - 复制时静默解压再复制：行为与"透明复制"相同但更隐晦，且改变源会话形态，副作用不可接受。
- **影响范围**：US2.3；术语 SR3。

### SDR-004 附件存储联动回收

- **日期**：2026-10-23
- **背景**：会话删除只删会话目录时，图片等附件的实际字节在全局共享的附件存储中，不随之释放——用户感知"删了没降"。附件是内容寻址、跨会话共享的。
- **决策**：**附件回收是删除执行体的内建行为，所有删除入口统一收敛**——本域两个入口（管理页单删、档位批删）与其他既有删除入口（会话列表删除、工作区清空）删除会话时，一律按同一规则联动回收：只回收"删除后不再被任何存活会话引用"的附件；仍在引用则完整保留（US2.4）。存储语义的跨域登记见会话持久化域（其 ADR-018）。不引入独立的附件全量 GC（非目标）。
- **否决的备选**：
  - 只覆盖本域入口：其他入口删除后"删了没降"原样复现，产品承诺被入口绕过。
  - 不动附件存储：实现最小，但图片重度用户的硬盘回收目标基本落空。
  - 独立的定时附件 GC：不绑定删除时机，扫描全量引用关系，开销与风险都更大。
- **影响范围**：US2.4；架构 §2.2 删除执行体。

### SDR-005 压缩时机：启动延时 + 周期检查

- **日期**：2026-10-23
- **背景**：产品形态含短生命周期（终端）与长生命周期（桌面/网页服务）两种进程。仅启动时检查对长进程无效；仅定时器无启动首查。
- **决策**：进程就绪并延时若干分钟后做首次检查，此后按"检查间隔"周期执行（US4.1）。延时目的是保护启动体验。
- **否决的备选**：
  - 仅启动时检查：对常驻进程（桌面）基本无效。
  - 磁盘占用超阈值时触发：不可预期的突发磁盘 IO，且容量语义超出范围。
- **影响范围**：US4.1、US1.2。

### SDR-006 压缩态能力边界与恢复语义

- **日期**：2026-10-23
- **背景**：压缩若破坏会话可用性，用户会视自动压缩为"变相删除"，信任崩塌。同时复制是唯一被显式排除的能力（SDR-003）。
- **决策**：压缩对用户透明——查看、导出、搜索等只读能力原样保全（US2.2）；恢复归档时先完整还原为压缩前形态，此后继续使用的行为与从未被压缩完全一致（US1.3、US2.2）；复制被明确排除（US2.3）。
- **否决的备选**：
  - 压缩后拒绝恢复归档并提示手动还原：违背透明性要求。
  - 恢复后保持压缩态、仅读取时解压：写路径长期双形态，一致性风险高。
- **影响范围**：US1.3、US2.2、US2.3。

### SDR-007 域拆分与交付范围（含界面）

- **日期**：2026-10-23
- **背景**：v1 曾裁决"第一期只做核心，UI 后置"；评审指出 P0 验收（列表"已压缩"标识）与无 UI 交付直接矛盾，用户裁决扩大范围。
- **决策**：本域第一批交付 = rust 核心能力（配置、自动压缩、压缩态读路径、恢复还原、删除与附件回收）**加** 用户界面——**网页端与桌面端**交付完整管理页（两视图、排序、批量档位、确认交互）与"已压缩"标识；**终端端交付"已压缩"标识与最小操作能力**（列表标识 + 逐条恢复归档/删除入口，等价能力以终端形态呈现，不要求复刻管理页全量交互——档位批删属网页/桌面端能力，终端用户需要批删时经网页端操作，此边界为接受的产品取舍）。
- **否决的备选**：
  - 仅核心后置 UI（v1 方案）：P0 验收无法在批次内闭环，且手动删除的产品形态必须有管理页才成立——删除入口与管理页是一体的。
  - 终端端完整复刻管理页：终端交互形态下批删/排序的体验成本高，与终端用户的低频清理诉求不匹配。
  - 三端各自独立规格：本域统一以网页端为准绳、桌面端同构复用，避免两套交互规格漂移。
- **影响范围**：US2.1 第 4 条、Epic RT3 全部、Epic RT6；ROADMAP 批次划分。

### SDR-008 存量归档保守起点

- **日期**：2026-10-23
- **背景**：存量归档会话只有"是否归档"布尔标记，无归档时点。升级后首查若用近似时间（如最后活动时间）起算，可能立即压缩大量老归档。
- **决策**：存量无法确定归档时点的会话，首次被压缩检查遇到时以**检查时刻**补写归档时点，完整走完压缩天数窗口（US2.5）。
- **否决的备选**：
  - 用最后活动时间近似：活动与归档决策语义不同，可能导致升级即压缩大量归档，违背保守起点。
  - 视为"远早于任何窗口"、首查即压缩：回收最快，但与"升级不带来意外"（US1.1 的精神）冲突。
- **影响范围**：US2.5。
