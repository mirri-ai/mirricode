## 明细

### P-001 添加对话框的 git 仓库标识

- **背景**：添加工作区的文件夹选择器界面已预留仓库徽章位（`apps/mirri-web/src/components/dialogs/AddWorkspaceDialog.vue:424-427`），但 v2 后端浏览接口的条目形状只有 `name/path/is_dir`（`packages/agent-core-v2/src/app/hostFolderBrowser/hostFolderBrowser.ts:22-26`）——前端徽章恒空（休眠）。
- **提案**：浏览接口补充"是否 git 仓库"（及可选分支）字段，对话框在文件夹行上展示标识——用户选择文件夹时即可辨识仓库。
- **关联**：workspace-management 需求 US1.1 的体验增强。

### P-002 最近根快捷选择

- **背景**：后端"主目录"接口已返回系统主目录与前 8 个注册工作区根（`hostFolderBrowserService.ts:70-75`，`RECENT_ROOTS_LIMIT = 8`），网页端也已存储（`rawState.recentRoots`），但对话框未渲染；`workspace.recentLabel` i18n 键为无消费的残留。
- **提案**：添加对话框渲染"最近使用过的项目"快捷区，一键选中注册过的根目录。
- **关联**：US1.1 的体验增强；与 P-001 同属激活既有预埋能力。

### P-003 工作区磁盘占用展示

- **背景**：workspace-management SDR-001（删除三选一、鼓励清理）的裁决动机是"存量会话占满磁盘的真实风险"；用户在确认删除时没有清理收益的量化依据。
- **提案**：删除确认框展示该工作区会话数据的磁盘占用（或会话数 × 平均体积等可感知度量），帮助判断物理删除的收益。
- **关联**：SDR-001 / 需求 US3.2 的体验增强；依赖会话数据体积的读取能力（需评估成本）。

### P-004 对话框内新建文件夹

- **背景**：后端已有"新建目录"能力（`packages/kap-server/src/routes/workspaceFs.ts:197-222`，非递归，存在/不存在/无权限错误均有明确映射——路由注释自述"the folder picker's 'new folder' backend"），网页端零调用。
- **提案**：添加工作区的文件夹选择器提供"新建文件夹"入口，选中后直接作为新工作区根。
- **关联**：US1.1 的能力补齐；后端就绪，前端纯新增。

### P-005 跨客户端信任同步

- **背景**：现网信任变化的生效边界是**同进程热重载**（`packages/agent-core-v2/src/workspace/workspaceTrust/workspaceTrustService.ts:12-14` 文档自述：另一进程翻转同一记录需重启才感知）；跨客户端（多开网页、多引擎）无任何同步信号。
- **提案**：信任/撤销变化发射跨客户端事件（对齐 workspace 生命周期事件的形态），多端信任状态即时一致；撤销即刻可见（不出现"这边已撤销、那边还在跑"的错位）。
- **关联**：workspace-management 需求 US4.1 的边界声明、US4.2；与 ROADMAP 开放项 #6（workspace 生命周期事件的 rust 发射面）属同一事件族——#6 已裁决并入 plans/08 W2（2026-09-11），本提案（信任事件）仍待裁决，裁决时可参照同一发射面形态。

### P-006 OS 级沙箱（分级信任与网络开关）

- **来源**：execution-environment 域内提案 P1（[execution-environment-requirements.md](execution-environment-requirements.md) §9）。
- **背景**：TS 现状执行沙箱面只有"路径约束"一层——命令执行不受约束（该域 US6.3 诚实边界已如实声明，不夸大为沙箱）。
- **提案**：引入真正的 OS 级隔离（容器、受限执行、网络隔离等平台机制），按工作区信任等级分级授予能力（文件系统范围、网络开关、进程数上限）；未信任工作区默认进入受限档。
- **关联**：与 workspace-management 域的工作区信任（W4）分级模型联动；涉及安全模型，需专项裁决。

### P-007 终端完整产品面（输入/尺寸/订阅打通与持久化）

- **来源**：execution-environment 域内提案 P5（同上 §9；现状缺口见该域 context §3.3-4 与开放项 O1）。
- **背景**：TS v2 的终端服务层与 PTY 层完备（创建/回放/退出），但输入、调整尺寸与附加订阅的传输通道尚未接线——服务层 API 有契约、产品面无入口。
- **提案**：Rust 内核交付完整的终端交互面（输入、调整尺寸、附加订阅一条通道打通），并考虑跨进程的终端持久化（重开引擎续看）。
- **关联**：与 conversation-rendering 域的易失事件（R3）与事件游标（R4）的续流/补齐语义联动设计（终端输出回放、断线重连与附加订阅复用同一套"缓冲 + 水位"思想）。

### P-009 模型请求可选超时上限（逃生门）

- **来源**：non-functional 域内提案 P6（同上 §9；ROADMAP 开放项 O3）。
- **背景**：TS 现状模型请求无请求级强制超时——这是显式记录的设计取舍（长思考模型合法响应时间跨度大，静态超时会误杀；恢复由"用户可随时取消 + 步级自动重试"承担）。
- **提案**：提供可配置的请求级超时上限作为逃生门（默认仍可不设）。
- **关联**：与该域"每类外部等待有上限"的全局契约互补——模型请求是当前唯一无上限的对外等待。

### P-018 技能占位符与环境变量命名统一

### P-020 定时任务的用户自助管理面

- **背景**：TS 现状用户只能请模型代为排定/变更定时任务（经模型可见的工具），无直接管理入口。
- **提案**：提供用户直接的定时任务管理入口（终端命令/网页界面：列表、删除、手动触发一次）。

### P-021 定时任务显式时区

- **背景**：TS 现状定时任务按本地时区解释计划表达式，跨时区协作（会话迁移、远程环境）下有语义漂移。

- **关联**：与执行环境域的远程执行环境（跨机器场景）联动。

### P-022 任务通知分级与降噪

- **提案**：为低价值通知提供聚合/降噪选项（分级与免打扰）。
- **关联**：subagent 域 E10（任务通知与对话闭环）的增强。

### P-023 跨会话任务总览与 web 端转后台入口

- **背景**：TS 现状任务面板以会话为单位；多会话并行时无"全部后台任务"总览；且网页端不承诺前台任务转后台的快捷入口（US12.5 范围声明）。
- **提案**：提供按工作区聚合的跨会话后台任务视图，并一并考虑网页端的前台转后台入口。
- **关联**：subagent 域 US9/US12.5；web 端能力对齐。

### P-024 cron 表达式秒级与命名别名

- **来源**：background-tasks 域内提案 P5（同上 §17）。
- **背景**：TS 现状计划表达式为标准 5 字段、纯数字语法。
- **提案**：如需秒级调度或 `Mon`/`Jan` 类命名别名，须评估调度精度与解析复杂度。
- **关联**：subagent 域 E11 创建校验与表达式语义。

### P-025 成员级暂停与恢复

- **来源**：督导域（agent-supervision v1 基线，2026-09-14；域内视图 [agent-supervision-requirements.md](agent-supervision-requirements.md) US5.2 / SDR-006）。
- **背景**：引擎现状只有终止（TaskStop）与事后续作（resume）两类控制；用户临时控制成本/节奏（"先停一下但别丢进展"）没有对应能力。外部多 Agent 产品调研（Devin/Manus/Swarm-IDE 等）将可中断性列为多 Agent UX 的核心原则。
- **提案**：子代理域裁决成员级暂停/恢复语义——暂停信号（成员停止推进、进展与上下文保留、状态如实呈现"已暂停"）与恢复信号（从中断处续接、过程叙事无缝）；与超时/停止的边界一次说清。
- **关联**：subagent 域 E5（止损）的扩展；督导域 Phase 2 前置项。

### P-026 运行中定向指令（in-flight steering）

- **来源**：督导域（同上；域内视图 US6.1 / SDR-006）。
- **背景**：引擎现状对子代理只有事后续作（resume 携带新提示），运行中无法定向纠偏；调研产品（Swarm-IDE）将"人类可像聊天一样介入任意层级"列为协作核心心智。
- **提案**：子代理域裁决运行中定向指令语义——注入通道（下一轮上下文）、与事后续作的关系、权限配合（干预不是审批豁免）、生效时机（≤ 一个成员轮次，对齐 collaboration 域 N4 量级）。
- **关联**：subagent 域 E4（续作）的运行中姊妹篇；collaboration 域 US4.3（用户介入）；督导域 Phase 2/3 前置项。

### P-027 结构化成员过程事件通道

- **来源**：督导域（同上；域内视图架构 §4.1）+ collaboration 域内提案 P-1/P-2（[collaboration-requirements.md](collaboration-requirements.md) §13，结构化回流与成员阶段汇报——两者与本提案是同一通道的三个消费面）。
- **背景**：现状成员过程信号为合成文本行（"Calling X: …"），web 端再按前缀启发式解析重建结构（双向有损）；蜂群完成结果也以文本块回流靠解析渲染（collaboration P-1 指认）。
- **提案**：统一的结构化成员过程事件通道——事件模型含四分类（thought/tool_call/tool_result/status/error）、成员标识、时序；实时（WS）与回看（journal 读面）同构；未知类型前向兼容。三个消费面：督导面板叙事、agent 总览事件流、调试工具回放。
- **关联**：rust-core-design 域（协议落位与契约校验）；conversation-rendering 域（转录侧已有 MAIN_AGENT_TRANSCRIPT_FRAMES 过滤，不受影响）；督导域 Phase 2 核心项。

### P-028 恢复会话时未消费任务结果的主动提示

- **背景**：回合因系统性终止（如僵死看门狗误杀，回合调度域 ADR-004）而非用户意图死亡时，其正在等待的后台任务往往仍在运行并最终完成——任务结果完整落盘但再无消费方；用户重新打开会话后不会收到任何"有已完成结果待消费"的提示，只能靠回忆自己翻任务列表（两起 2026-10-15 事故中，一次测试结果 4071 通过、一次任务超时被杀，均无人接手）。恢复时的任务通知重放机制（按 addressee 补投）覆盖的是"恢复时已在等待中的通知"，不覆盖"恢复之后才完成"的任务。
- **提案**：会话恢复时点起，对"回合死亡时仍在运行、其后才完成、且结果无消费方"的后台任务，在会话内主动提示（如一条系统消息列出任务与结果摘要，用户可选择让代理继续消费）；提示一次性、不重复打扰。
- **关联**：回合调度域 SDR-003 原则四（事故后恢复顺滑）/ ADR-004 / O8；任务通知业务语义在后台任务域（ADR-003/005/008），恢复流程落点会话管理域——裁决时需定归属域。

### P-029 僵死看门狗三代架构：推模型心跳改拉模式探活

- **背景**：ADR-004 重设计（2026-10-15）后的 48 小时内，看门狗又连续误杀三起健康回合（等模型首响应、等转后台进程、等子代理）——每次都落在"喂线缺失"的新等待点上。推模型的等待点集合是开放的：每个新等待类别都是新的误杀源，补丁清单不收敛（证据快照见回合调度域 context §3.5）。
- **提案**：看门狗判据从"全局静默 + 各等待点自觉喂信号"改为"回合等待状态机（WaitKind）+ 向被等待对象的 owner 拉取活体事实"（HTTP 连接/进程生命周期/子代理宿主/用户决策门——探活信息已在运行时中）；看门狗降级为 30–60 分钟长窗口死锁兜底，触发先 dump 诊断再取消。设计全文见 [turn-scheduling-watchdog-pull-model-proposal.md](turn-scheduling-watchdog-pull-model-proposal.md)。
- **关联**：回合调度域 ADR-004/ADR-005（二代形态）、US5.5/SDR-003（本提案是其结构性达成）；子代理运行态事实属代理监督域、任务心跳语义属后台任务域——裁决时需跨域对齐。
