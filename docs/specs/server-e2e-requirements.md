# server-e2e 场景测试域 — 需求定义

> **文档类型**：需求（Design/Spec）。本文只描述需求与验收标准；技术形态见 [server-e2e-architecture.md](server-e2e-architecture.md)；现状快照见 [server-e2e-context.md](server-e2e-context.md)。

## 1. 背景与问题

产品已完成"唯一 rust 内核"的收敛：用户的一切交互——桌面应用、浏览器界面、命令行——最终都由同一个 rust 引擎进程驱动。现有自动化测试大量覆盖了引擎的内部逻辑（单元测试）和接口层（进程内黑盒），但它们共享同一个特性：**测试和被测系统跑在同一个进程、同一个内存世界**。

这留下一个空白：**没有任何测试站在"第一次使用产品的用户"的位置，从零开始走完整条使用旅程**——安装后第一次启动、第一次配模型、第一次提问、第一次交出真实任务、关掉产品第二天回来继续。这条路径上的任何断裂（启动自举失败、配置不生效、会话丢失）都是现有测试看不到的。

同时，仓库现有的旧版场景测试（为已退役的 TypeScript 引擎编写）已经失效：它说的是旧引擎的对话协议，无法连接当前产品。它需要一个根本性的重做，而不是修补。

## 2. 目标

建立一套**用户旅程场景测试**：以真实用户的使用顺序为骨架，从安装启动到持续使用，在完整真实的产品进程上验证"每一步用户得到了产品承诺的东西"。

**非目标**（明确排除）：

- 不测模型的智能——模型由"可编程的模型替身"扮演（见 §4），被测的是产品的兑现能力
- 不重复引擎内部逻辑的测试（工具执行细节、回合状态机、权限规则明细）
- 不测界面像素（浏览器渲染、组件样式）
- 不追求测试数量——每个用例必须对应旅程中用户真实会走的一段

## 3. 用户旅程（需求骨架）

用户从零到持续使用的完整路径，分七个阶段：

| 阶段 | 用户在做的事 |
|---|---|
| ① 安装拿到产品 | 第一次启动，产品应该自己站起来 |
| ② 首次配置 | 配置模型服务；没配置时得到引导而非卡死 |
| ③ 第一次对话 | 产品自己读项目、危险操作先问、能随时停止 |
| ④ 交出真实任务 | 计划→修改文件→跑测试→汇报的完整闭环；子代理并行 |
| ⑤ 回访连续性 | 昨天的会话还在、能接着聊；刷新页面不丢内容 |
| ⑥ 老用户迁移 | 旧版本会话搬家到新版本 |
| ⑦ 多端同开 | 两个页面同时看同一个会话，内容同步 |

## 4. 模型替身（测试策略需求）

用户的旅程需要一个"会回答的模型"。测试使用**可编程的模型替身**：

- 它是一个真实的网络服务，使用与真实模型服务相同的通信协议（用户配置 provider 时填的地址就是它）
- 它的"智能"是测试预先编排的剧本：这一轮发起文件读取、这一轮流式回复三段文字、这一轮请求写文件……让每个旅程场景确定性地走到目标分支（审批卡、中断、子代理）
- 因此：**网络是真的、协议是真的、产品引擎是真的，只有 AI 的大脑是剧本**——产品对模型服务的一切消费行为（请求构造、流式解析、错误处理）都在被测范围内

## 5. 需求（R 系列）

### R1 — 全新环境自举
在没有任何历史数据的全新环境里，用户第一次启动产品：产品完成自身就绪，不要求用户先做任何准备；产品数据目录被自动创建。没有任何因"配置缺失"导致的崩溃。

### R2 — 无模型时的引导性反馈
用户未配置任何模型就发送第一条消息：产品返回**可自助解决的引导信息**（用户照着提示能自己配好），而不是转圈、崩溃或不可理解的错误。会话本身不因此损坏——配好模型后同一会话可继续使用。

### R3 — 配置即时生效
用户在设置中配置了模型服务（provider、密钥、默认模型）后，**无需重启产品**：回到对话框发消息立即得到回复。模型回复的文本完整出现在用户的会话中。

### R4 — 只读探索零打扰
用户让产品了解一个陌生项目：产品自动调用只读能力（读文件、搜索）收集信息后回答，全程**零确认弹窗**（产品文档《Interaction and input》对只读操作的承诺）。回复内容基于项目真实内容（替身读到工具结果并引用真实文件名）。

### R5 — 危险操作先经用户批准
产品要修改文件前，用户先看到"它要做什么"；用户**批准前文件未被改动**；批准后改动真实落盘。用户的**拒绝同样生效**：文件保持原样，产品收到拒绝原因并继续对话。

### R6 — 流式输出与中断
回答流式呈现；用户中途停止：输出立刻停下，已收到的部分保留在会话里，之后还能继续发新消息。

### R7 — 真实任务闭环
用户交出一个开发任务（加函数并跑测试）：产品完成 计划→修改文件→执行命令→汇报 的完整闭环，且：
- 文件真的被改了、命令真的执行了（产物落盘可查）
- 最终汇报引用真实的执行结果
- 全过程在会话历史中可回溯

### R8 — 子代理协作
主代理派子代理执行子任务：子代理的生命周期（创建→流式进度→完成）以任务卡片形式呈现——无头场景下的验收观察面是产品对外发出的子代理进度事件序列（界面的卡片正是由它驱动的）；主代理拿到子代理结果后给出最终答复。

### R9 — 会话回访
用户关闭产品（非正常退出）后再次打开：过往会话出现在列表中（标题与会话元数据中记录的创建时间一致）；打开后历史完整（含工具记录）；接着聊时**上文真实传给了模型**（替身能读到历史）。

### R10 — 页面刷新不丢内容
对话中途刷新页面：刷新前后内容一致、无重复、无丢失；进行中的事件流接续。

### R11 — 旧版会话迁移
老用户从旧版本升级：执行迁移命令后，旧会话出现在新版本中且内容完整可回访。

### R12 — 多端同步
两个页面同时打开同一会话：一处发消息，两处看到一致的事件流，互不干扰。

## 6. 验收标准

1. 十二个旅程需求（R1-R12）各有至少一个自动化场景用例覆盖，且全部通过
2. 用例的验收标准全部以用户可感知结果表达（回复内容、文件落盘、回访完整性），不含协议帧格式断言
3. 测试运行在真实产品进程上（非进程内嵌入），模型由可编程替身扮演
4. 旧版场景测试的十二个场景全部得到处置：并入旅程或明确删除并记录理由
5. 场景套件可重复执行（每次运行产生确定的结果，不依赖真实模型的随机性）

## 7. 决策记录

### SDR-001：以用户旅程为骨架重做，而非修补旧场景（2026-10-28，影响：本域全部用例的组织方式）
旧场景测试以接口覆盖为目标枚举功能点；重做后以用户使用顺序为骨架。理由：接口契约覆盖已由引擎侧进程内黑盒测试承担，旅程连续性是空白；且旧场景的对话协议已随 TypeScript 引擎退役失效。

### SDR-002：模型用可编程替身，不用真实模型服务（2026-10-28，影响：全部用例的执行形态）
确定性（每个用例稳定走到目标分支）与可离线运行的要求决定了替身方案；替身走真实网络与协议，保留对产品 provider 适配层的覆盖。
