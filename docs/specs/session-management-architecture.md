# 会话管理 — 架构设计（面向 Rust 核心）

> 状态：v1.1 基线 · 2026-10-09 · 待需求评审后校准 · fork 机制节与 ADR-007/008 随 SDR-010/011 增补 · 运行状态机制节与 ADR-009 随 SDR-013 增补（2026-10-13）·
> 本文是会话管理域设计侧的唯一事实源（内部规格文档，不进文档站构建，中文单语）。
> 需求契约：见 [session-management-requirements.md](session-management-requirements.md)（验收依据，含 SDR-001~012）；现状证据见 [session-management-context.md](session-management-context.md)。
> 依赖域：会话持久化域（[session-persistence-architecture.md](session-persistence-architecture.md)）——本域的一切持久化都架构在其存储与索引底座上。
> 术语规范：G1 置顶、G5 撤销、S1–S4 见 [glossary.md](glossary.md)。

## 1. 目标与设计原则

1. **顺序是数据**：置顶与排序持久化为服务端数据（US4.1），界面对顺序零私有状态。
2. **真相在磁盘、加速在索引**：延续持久化域"磁盘是唯一事实源"原则（US7.1）——排序真相存于磁盘文档，S4 会话索引只做缓存（ADR-001）。
3. **呈现顺序单一出处**：列表返回顺序即呈现顺序，引擎按"置顶区 → 固化序 / 最近使用"统一给出（US4.3），终端等无拖拽界面零成本对齐。
4. **契约先行**：wire 方法与参数形状一次定稿、跨引擎登记（SDR-003）；实现可以分批，契约不分叉。

## 2. 排序模型

### 2.1 会话的分层视图

```
工作区分组（S3 桶）
├── 置顶区   pinned = true，组内按 order 排列（固化；无固化时按置顶时间倒序——后置顶在上）
└── 普通区   pinned = false
    ├── 已固化：按 order 排列
    └── 未固化：按最近使用倒序（updated_at DESC）
```

- **置顶标记**：每会话一个布尔状态，独立于排序（US1.1/US1.2）。
- **固化（snapshot）**：普通区或置顶区各自持有一份有序 id 清单；未固化的分组按最近使用动态排（US2.2）。
- **新条目插入**：新会话、新恢复会话（S1）、取消置顶的会话、新出现的工作区一律插入普通区顶部——已固化清单则前插到清单头（SDR-002）。
- **归档压过置顶**：默认列表排除归档会话在读取层执行（持久化域 US6.1 的执行位置），置顶标记只对可见会话生效（US1.1 第三条）。

### 2.2 工作区的分层视图

- 已固化：按 order 清单排列；未固化：按最近使用倒序；新工作区（首次注册）插入顶部。
- 分组折叠状态是纯界面状态，不持久化到域数据（US3.2）。

## 3. 数据契约

### 3.1 磁盘真相（两份新文档 + 一个新字段）

| 数据 | 位置 | 说明 |
|---|---|---|
| 置顶标记 | 会话元数据文档新增 `pinned` 布尔字段 | 逐会话事实；跨引擎共享文档的并集扩展（持久化域 §4.1 同构） |
| 会话排序真相 | 每个工作区桶根下一份顺序文档（`order.json`）：`{ pinned: [id…], normal: [id…] }` | 两清单各自可缺（未固化）；缺失 id 按 §2.1 动态规则排 |
| 工作区排序真相 | 数据根下一份 `workspace-order.json`：`{ ordered: [wd_id…] }` | 独立于 `workspaces.json`（后者是跨引擎共享的身份文件，不承载排序——见 ADR-001） |

- 顺序文档经 AtomicDocument 原子写（持久化域 §8 原语）；条目校验：清单内 id 必须属于本工作区桶（跨桶 id 拒绝，US2.3）。
- 容忍：清单中出现已删除的 id 时静默忽略（读取时过滤）；文档损坏按"未固化"处理。

### 3.2 索引缓存（S4）

- `sessions` 表新增 `pinned` 列（INTEGER 0/1）；`workspaces` 表的 `sort_order` 列改为承载固化序号（清单位置）——两者都是**从顺序文档回填的缓存**，对账时以文档为准。
- 列表查询按 §2.1 的分层顺序组装：索引提供每行的 pinned/归属/时间，顺序文档提供固化清单，合成最终序。

### 3.3 wire 契约（mirri-proto 登记）

| 方法 | 参数 | 返回 | 语义 |
|---|---|---|---|
| `session.pin` | `sessionId` | `null`（noResult，与 `session.archive` 同形） | 置顶；重复置顶幂等 |
| `session.unpin` | `sessionId` | `null` | 取消置顶；会话插入普通区顶部 |
| `session.reorder` | `sessionId?`、`orderedIds: [...]`、`section: "pinned" \| "normal"` | `null` | 固化指定分组的整组顺序（客户端发送拖动后的完整清单，SDR-001 的全量快照协议） |
| `workspace.reorder` | `orderedIds: [...]` | `null` | 固化工作区顺序 |
| `session.list`（扩展） | 现有参数不变 | 行新增 `pinned: boolean`；**返回顺序即呈现顺序**（§2.1） | US4.3 |
| `workspace.list`（扩展） | 现有参数不变 | 返回顺序即呈现顺序 | US3.1 |

- `section` 缺省 `normal`；`orderedIds` 含不属于该工作区桶的 id → 整个请求拒绝（不部分生效）。
- 全量快照协议使协议无合并冲突面（最后写者胜），与"拖动即固化"的用户语义一一对应。

### 3.4 会话生命周期对排序的钩子

| 事件 | 排序效果 |
|---|---|
| 创建 / 恢复（S1） | 插入普通区顶部（固化清单则前插清单头） |
| 归档（S2） | 从任何固化清单中移除该 id（归档不可见，US1.1 第三条） |
| 恢复归档 | 视同新条目插入普通区顶部 |
| 删除 | 从固化清单移除 id；清理顺序文档中的残留 |
| 取消置顶 | 从置顶清单移除，插入普通区顶部（US1.2） |

## 4. 界面接线（网页首个消费方）

- 置顶区渲染：会话行新增置顶标记与置顶/取消置顶动作；列表数据源顺序即引擎返回顺序（零客户端排序）。
- 拖拽：采用原生 HTML5 拖放实现（现状无任何拖拽库依赖——见 context §1.1；不为此引入新依赖，ADR-004）。
- 拖放提交：松手即调用 `session.reorder` / `workspace.reorder`（乐观更新 + 失败回滚刷新）；拖入置顶区 = `session.pin` + 置顶区固化一步完成（US2.3 第三条）。
- 折叠状态保持为界面本地状态（US3.2）。

## 5. 跨引擎一致性

- 契约登记后 TS 侧跟进时：`pinned` 字段进元数据并集（持久化域 §4.1 的字段并集机制），顺序文档为 Rust 新增文件（TS 未识别前原样保留）。
- **已知风险（入 context/ROADMAP）**：TS 元数据写回是否透传未知字段（`pinned`）未验证——TS 对齐批次的首要验证项。

## 6. 会话复制机制（E5 fork）

### 6.1 复制管道的五个阶段

fork 的执行单元是"截至分叉点的会话现场"，管道顺序固定：

1. **锚点解析**：不指定分叉点 = 取最近一个已收尾的回合终点；指定则校验该锚点存在且已收尾（进行中/不存在 → 明确报错，不静默降级到末尾）。
2. **成员级历史截取**：对源会话的**每个成员**（SDR-011），读取其会话日志并截取到锚点所属回合的收尾记录为止（含该回合的全部记录）；截断边界落在回合边界上（回合原子性）。截取出的记录流 + 头部元数据记录 + `forked` 边界记录构成新会话该成员的日志初始内容。压缩摘要记录按其落位顺序保留在截断边界之内——模型可见历史由折叠器从记录流自然重建，无需另行快照。
3. **元数据铸造**：新会话身份（引擎铸造，外部指定的 id 一律拒绝）、血缘（forkedFrom）、默认命名「Fork of 原会话标题」（SDR-012，源标题不可得时退化）、自定义元数据合并（剔除目标/进度类键）。
4. **运行中资产重置**：定时任务不带（SDR-007）；目标恢复为未启动；挂起交互不转移——全部在复制管道内完成，不依赖新会话首次启动时的清理。
5. **原子落位**：复制全部成功后才可见（列表、事件）；任何阶段失败 → 清理已写的目标目录与内存态，源会话零修改（失败回滚）。

### 6.2 分叉点参数（US5.4）

- 语义参数为"回合标识"：消费方从对话呈现层获得每轮已收尾回合的标识，随分叉请求传入；引擎以"该回合收尾记录"为截断锚点。
- 不提供按消息粒度的锚点——回合是权限/用量/审批的最小一致单元（SDR-006 裁决）。
- 跨引擎契约随 E5 契约登记批次进 wire 注册表（ROADMAP 开放项 7）。
- **消费端接线**（US5.4 界面条款）：网页端入口挂在对话呈现的回合边界上（呈现层的回合对象即锚点候选，仅已收尾者渲染入口——进行中回合无入口，可用性诚实）；终端端为命令 + 可搜索选择器（每项含该轮用户输入预览，交互模式与撤销选择器同构）；确认后入口防重触发。锚点候选由呈现层从既有回合数据派生，引擎不感知界面形态。

### 6.3 分叉的缓存计费边界（US5.5 / ADR-007）

- 模型请求配线携带一个"对话归属标识"（服务方各异：有的作为前缀路由键、有的作为归属元数据——形状由画像与提示词域（agent-profile）的请求配线定义）。
- **规则**：该标识 = 会话自身的 id——分叉出的新会话用自己的新身份，不沿袭源会话（SDR-010 修订裁决；与参照引擎现状一致，无对齐变更）。多分叉场景下各会话独立积累缓存，互不竞争同一归属。
- 分叉会话的首次请求前缀与源会话在分叉点后的下一请求前缀一致（§6.1 第 2 步的截取保证）——前缀稳定是命中已读计费优惠的主因子；归属标识独立后，服务方按前缀匹配决定首次命中与否（不做保证），首次未命中被接受为分叉的成本结构，其后请求按新身份稳定积累。
- 引擎侧不引入任何服务方特定的缓存预写/管理逻辑：命中是服务方行为，引擎的义务止于**请求前缀的确定性**（分叉截取管道的输出逐字节稳定）。

### 6.4 createChild 的复用关系

`session.createChild` 走同一条 fork 管道（§6.1 全阶段），仅元数据铸造阶段额外写入父会话标识与子会话类别标记（SDR-005：溯源不等于所有权）。

## 7. 对话撤销机制（Epic U）

### 7.1 落盘义务（ADR-006）

撤销改变模型可见历史，而会话日志（S5，持久化域）是对话历史的唯一真相——**每一次生产路径的撤销都必须作为一条撤销 wire 记录写入会话日志**，与内存变更同批提交。撤销 wire 记录在重放折叠器（reducer fold）中的解释语义是**按消息条数截断**（记录的 `count` = 从尾部移除的消息条数）：任何撤销写入方（含 Rust 内核的 live 撤销，即 U1 实现批次的接口义务）写入的 `count` 必须采用该口径——撤销量（轮数，粒度按开放项裁决）→消息条数的换算发生在写入侧，折叠器的解释语义不因写入方而变。US-U2（撤销经收起/重开保持）即由"记录 + 折叠"闭环保证。

### 7.2 与压缩域的联动

- **编号区间括号校正（压缩域 ADR-007）**：wire 记录形态的撤销产生条目编号消耗间隙，压缩落位记录的区间括号据此校正重放编号。该校正存在压缩域文档化的残差：撤销切点落入头部精华区或保留尾区之内时该区段欠校正；任意切点保真需逐撤销记录——该延后项载于压缩域 context §1.2 与折叠器侧文档注释（后者援引 ADR-007 的校正），并非 ADR-007 正文承诺，本域亦不承诺。详见压缩域架构 ADR-007 与其 context §1.2。
- **边界即停（C3）**：撤销锚点回溯在压缩落位摘要处停止，不穿越压缩考古（SDR-009 承接的压缩域裁决）。

### 7.3 护栏与可用性

- 撤销仅在会话空闲时接受：回复进行中、压缩进行中一律拒绝并如实反馈（拒绝与放行以同一忙碌判定为准，对称定义）。
- 请求超过可撤销深度时拒绝，并携带当前可撤销轮数与原因（到压缩边界 / 无可撤销内容）——用户可感知信号与真实可撤销范围一致。
- 撤销锚点谓词与"真实用户输入"口径一致（用户消息、用户触发的命令），用于识别回退落点；回退单元为**整轮**（US-U1 基线，回合 S7 原子性）——一个回合及其后的全部内容构成一个回退单元。更细的撤销粒度（输入级）是否提供属 ROADMAP 开放项 9，裁决前不实现。

### 7.4 契约

撤销沿用已登记的 `session.undo`（`sessionId` / `agentId?` / `count?`，缺省 1）——RPC 契约面无新增方法；撤销的持久化载体是既有的 `context.undo` wire 记录族（非新记录类型），落盘义务与 count 口径见 §7.1 / ADR-006。

## 8. 会话运行状态机制（US4.4 / SDR-013）

### 8.1 状态口径：四元组与主对话回合判定

会话运行状态是一个**四元组**（与参照引擎 TS v2 的 work facts 同口径）：`busy`（任一成员回合在途或后台工作存活——聚合忙碌）、`mainTurnActive`（主对话成员的回合未收尾——列表"运行中"标记与停止按钮的判定输入）、`pendingInteraction`（none / approval / question——挂起交互类型）、`lastTurnReason`（completed / cancelled / failed——最近回合结局）。**侧边栏"运行中"标记的口径 = `mainTurnActive`**：后台任务与子代理回合点亮 `busy` 但不点亮标记——刷新前后口径一致是 US4.4 的验收前提。

### 8.2 读面重建：进程内权威，不猜进程外的状态

刷新/换端后的状态由服务端给出，数据源是**进程内的在途回合注册表**（引擎内存中"该会话哪个成员的哪个回合正在跑"的登记）——同进程刷新/换端直接命中，含主对话回合判定（回合归属成员 = 主对话成员即 `mainTurnActive=true`）。**注册表未覆盖的会话一律按"未运行"呈现**——不做跨进程/重启场景的日志探测兜底：每个服务进程只如实报告自己承载的回合；未配对的回合开始记录会存活于会话日志，但"该记录是否还活着"只有其承载进程知道，其他进程（含重启后的同进程）无从判定，任何推断都会在进程死亡后变成假阳性（违背 US4.4 第四条）。索引行（静态行）的四元组一律为中性值（未运行/无挂起）。

**已知边界（被接受的近似）**：多进程共用同一数据根的部署形态下，另一个进程承载的运行中会话在当前进程的列表中显示为未运行——与参照引擎（TS v2）行为一致（每个服务进程只报告自己）；会话历史本身跨进程完整可见，仅运行态标记的可见性限于承载进程。

### 8.3 事件面：会话级状态通知

状态四元组的每次真实迁移（聚合器自带去重——状态未变的重复输入不产生事件）广播一条**会话级通知事件**（`event.session.work_changed`，负载即四元组，snake_case 与参照引擎 wire 一致），全局扇出到每个连接（不要求订阅该会话——列表行的状态更新不依赖逐会话订阅；协议总览的全局扇出例外条款见协议 §2.3）。事件为 **durable**：落会话事件日志、携带 seq、可被 cursor 重放（与参照引擎一致——刷新丢连接期间的迁移靠重放补齐，而非靠重拉列表）。回合结束的迁移必须排在对应 `turn.ended` 事件之后（消费方依赖"回合结束在前、状态熄灭在后"的顺序关闭运行中呈现）。

### 8.4 契约

| 面 | 扩展 |
|---|---|
| `session.list` 行 | 新增 `mainTurnActive` / `busy`（已有，语义校正为四元组口径）/ `pendingInteraction` / `lastTurnReason`（视图字段 camelCase，与既有 SessionView 一致） |
| `session.snapshot` 会话视图 | 同上四元组（快照是刷新/重连的重建种子，US4.4 第一条的主通道） |
| `event.session.work_changed` | 新登记事件：durable、全局扇出、负载 `{sessionId, busy, main_turn_active, pending_interaction, last_turn_reason}`（snake_case，与参照引擎 wire 拼写一致） |

跨引擎一致性：契约登记后 TS 侧（存活期内）按既有实现直接对齐（v2 的列表行与事件即目标形态，无需变更）。

## 9. 决策记录（ADR）

### ADR-001 排序真相存于磁盘顺序文档，索引只做缓存

- **背景与动机**：手动排序是用户数据而非派生数据——S4 会话索引被整体删除时任何用户数据不得丢失（持久化域 US7.1），因此固化顺序不能只存在于索引中；持久化域 ADR-002 曾预留 `workspaces.sort_order` 索引列，本设计将其定位收窄为"缓存"。
- **决策**：固化顺序真相 = 桶内 `order.json` + 数据根 `workspace-order.json`（§3.1）；索引列由文档回填，对账以文档为准。
- **否决的替代**：顺序只存索引（违反索引可丢弃原则）；顺序存进 `workspaces.json`（跨引擎共享的身份文件，每次拖拽全量重写且 TS 写回可能丢未知字段）；每会话存序号（跨会话的全局顺序拆进逐会话文件，固化一次要写 N 个文件）。
- **影响面**：§3.1、§3.2；持久化域 ADR-002 的列定位收窄（该域架构文档由本 ADR 引用而不改写）。

### ADR-002 置顶标记存于会话元数据文档

- **背景与动机**：置顶是逐会话的持久事实，须随会话目录整体拷贝/备份而不丢。
- **决策**：`state.json` 新增 `pinned` 布尔字段（跨引擎并集扩展，默认 false）；索引 `pinned` 列为缓存。
- **否决的替代**：只存索引（同 ADR-001 的否决理由）；存进顺序文档（置顶是会话属性而非列表属性，会话级文件更内聚）。
- **影响面**：§3.1、§3.2、§3.4。

### ADR-003 固化采用全量快照协议

- **背景与动机**："拖动即固化整组"（SDR-001）需要与用户心智一一对应的协议形态。
- **决策**：`session.reorder` / `workspace.reorder` 接收拖动后的完整 id 清单（§3.3）；最后写者胜，无合并冲突面。
- **否决的替代**：增量移动协议（`move(id, before, after)`——需处理并发移动的相对语义，复杂度不成比例）。
- **影响面**：§3.3。

### ADR-004 网页拖拽用原生实现，不引入拖拽库

- **背景与动机**：侧边栏拖拽是垂直列表内的简单重排；当前网页依赖树中没有任何拖拽库（context §1.1）。
- **决策**：HTML5 原生拖放（draggable + dropzone），必要时局部 pointer 事件补齐；不新增依赖。
- **否决的替代**：引入通用拖拽库（为单一列表重排场景引入整树依赖，不成比例）。
- **影响面**：§4。

### ADR-005 呈现顺序由引擎统一给出

- **背景与动机**：顺序是数据（US4.1），若各端自行拼装排序则"一份顺序"退化为"每端一套拼装逻辑"。
- **决策**：`session.list` / `workspace.list` 的返回顺序即呈现顺序（§2.1 分层序）；无拖拽能力的终端界面零成本获得正确顺序（US4.3）。
- **否决的替代**：引擎返回无序集合 + 各端按 pinned/order 字段自行排（逻辑重复，行为漂移面大）。
- **影响面**：§2、§3.3；网页接线（§4）零客户端排序。

### ADR-006 撤销必须落盘，count 语义与折叠器的按消息截断一致

- **背景与动机**：撤销直接改变模型可见历史，而会话日志（S5）是历史的唯一真相——若 live 撤销只改内存不写日志，收起重开后重放会回到撤销前的内容：用户看到"撤销了"、重开后"撤销消失"（US-U2 要消除的信号失真；现状差异见 context §1.6）。折叠器对撤销记录的解释语义是"从尾部截断 `count` 条消息"，与撤销侧的轮/锚点计数不是同一个数——写入方与折叠器口径不一致时，重放截断位置错位。
- **决策**：撤销落盘为 U1 实现批次的**接口义务**：live 撤销在内存变更的同批写一条 `context.undo` wire 记录，记录的 `count` 采用与折叠器按消息条数截断一致的口径（= 被移除的尾部消息条数）；撤销量（轮数，粒度按开放项裁决）→消息条数的换算由写入方完成，折叠器的解释语义保持不因写入方而变（§7.1）。
- **否决的替代**：(a) 撤销不落盘——重开复活被撤内容，违反 US-U2 与信号真实性（即要消除的现状缺口）；(b) 记录锚点数、折叠器按锚点重算——改变折叠语义会牵动既有 TS 写入日志的重放（两代写入方共享同一折叠器，语义单侧变更造成跨引擎重放不一致）；(c) 撤销时快照整个历史——代价重，且与"日志唯一真相"原则冲突。
- **影响面**：US-U2；§7.1、§7.4；压缩域 ADR-007 的编号区间括号校正（仅对 wire 记录形态的撤销可校正）；U1 实现批次的接口验收。

### ADR-007 分叉的归属标识随新会话身份，引擎义务止于前缀确定性

- **编号与日期**：ADR-007 · 2026-10-09（同日修订，随 SDR-010 修订）
- **背景与动机**：服务方对已读前缀的计费优惠依赖请求前缀的字节一致性（引擎的截取管道已保证，§6.1）与归属标识。首个方案曾裁决分叉沿袭根会话身份以保证首请求命中；修订时权衡：前缀稳定已是命中主因子，身份继承的边际收益不抵多分叉共享同一缓存归属的竞争（各分叉的后续演进互相挤占），复杂度不成比例。
- **决策**：归属标识 = 会话自身 id（分叉出的新会话用新身份——与参照引擎现状一致，无对齐变更）；分叉首请求的命中不做保证（可能的未命中是分叉的成本结构），其后请求按新身份稳定积累。引擎对服务方缓存不负任何管理职责——义务止于**分叉后请求前缀的确定性**（截取管道的输出逐字节稳定）。
- **否决的替代**：(a) 分叉沿袭根会话身份（同日修订否决的原方案）——单分叉首命中更确定，但多分叉共享归属互相竞争，且把计费连续性耦合进会话身份体系；(b) 引擎侧预写缓存/预热 API——服务方特定逻辑，超出引擎边界（两版一致否决）。
- **影响面**：§6.3；US5.5；参照引擎（TS v2/v1）现有行为即目标行为，无对齐变更；glossary G6（形态同步改写）。

### ADR-008 复制管道以"按记录截取重写"取代"目录整拷"

- **编号与日期**：ADR-008 · 2026-10-09
- **背景与动机**：分叉点参数（US5.4）与成员级全量复制（SDR-011）共同要求"截至锚点的选择性复制"——现行的目录复制路线（现状证据见 context §1.4）无法表达截断，也无法在拷贝中重置运行中资产；它只能在拷完后清理，留下"半成品窗口"与死数据。
- **决策**：复制管道 = 按成员读取源日志 → 截取到锚点 → 加 `forked` 边界记录 → 重写为目标日志（§6.1 第 2 步）；会话级共享文件（附件等）走共享引用不复制（SDR-007 共享条款，持久化域 ADR-007 底座）。
- **否决的替代**：(a) 目录整拷 + 事后截断——两步非原子，中途失败留下撕裂状态，且无法表达"哪些文件属于锚点之后"；(b) 引用计数共享日志段——读取侧需理解分段，折叠器复杂度上升，收益（省盘）与分叉频度不成比例。
- **影响面**：§6.1；TS v2 对齐批次的重构方向（现状证据 context §1.4）；与持久化域 ADR-007（附件共享存储）的实现耦合。

### ADR-009 运行状态双侧同补：列表读面 + 状态事件，重建只认进程内权威，不落持久化标记

- **编号与日期**：ADR-009 · 2026-10-13
- **背景与动机**：刷新后列表的"运行中"标记需要服务端重建，而重建有读面（列表/快照带状态字段）与事件面（状态迁移通知）两侧——只补一侧会留下"首屏恢复但后续无感"或"实时有感但刷新即失"的半吊子状态。运行态天然是进程内易变状态（进程死亡即死），任何持久化标记都会在死亡后变成谎言；同理，任何跨进程的运行态推断（如会话日志的未收尾回合探测）都无从判定"承载该回合的进程是否还活着"。
- **决策**：读面 + 事件面同批补齐（§8.2/§8.3）；状态重建只认**进程内在途回合注册表**，未覆盖即"未运行"——不做日志探测兜底（与参照引擎行为一致：每个服务进程只报告自己承载的回合）；**不做**运行状态的独立持久化（无索引列、无标记文件）——进程重启后按"未运行"呈现。多进程共用数据根的部署下，他进程承载的运行中会话在当前进程显示未运行（已知边界，历史完整可见，仅运行态标记限于承载进程）。
- **否决的替代**：(a) 只补读面——状态变化无通知，列表行退化为轮询模型（SDR-013 否决项 a 的架构视角）；(b) 状态持久化到索引——死亡后脏标记 + 失效清理义务（SDR-013 否决项 c）；(c) 事件用 volatile——丢连接期间的迁移无法靠 cursor 重放补齐，重连后必须强制全量刷新列表，而 durable 事件让重放路径天然覆盖（参照引擎同为 durable）；(d) 会话日志未收尾回合探测——重启后未配对的开始记录仍在日志里，探测会把死亡进程的残留回合报成"运行中"（US4.4 第四条的假阳性），且无进程存活判定可用；"自然消散"在日志不可变的模型下不成立。
- **影响面**：§8；US4.4；SDR-013；协议事件目录（`event.session.work_changed` 登记 + §2.3 全局扇出例外条款，rust-core-design 01 的协议修订）。
