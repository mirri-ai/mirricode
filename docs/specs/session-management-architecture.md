## 1. 目标与设计原则

1. **顺序是数据**：置顶与排序持久化为服务端数据（US4.1），界面对顺序零私有状态。
2. **顺序是行、固化在文档**：会话元数据（含置顶三列）的事实源是数据库行（ADR-006 单表示，SDR-016）；用户固化过的组内顺序存于顺序文档（order.json），未固化时按动态规则排。
3. **呈现顺序单一出处**：列表返回顺序即呈现顺序，引擎按"置顶区 → 固化序 / 最近使用"统一给出（US4.3），终端等无拖拽界面零成本对齐。
4. **契约先行**：wire 方法与参数形状一次定稿、跨引擎登记（SDR-003）；实现可以分批，契约不分叉。

## 2. 排序模型

### 2.1 会话的分层视图

> ADR-012（SDR-020）：置顶区是**一个**跨工作区的全局分区，位于工作区分组之上。ADR-013（SDR-021）：置顶会话**同时**保留在其所属工作区分组内（组头、按置顶时刻倒序），全局分区与组内两处并存。固化顺序（order 清单）的作用域仍是工作区分组，这是两件事。

```
侧栏
├── 置顶区（全局一个，跨工作区聚合 pinned = true）
│     无固化时按 pinned_at DESC（后置顶在上）；固化后按该全局分区的 order 清单
└── 工作区分组（S3 桶，逐组）
    ├── 置顶区  pinned = true —— 与全局分区是同一批行的组内呈现
    │     ├── 已固化：按 order 排列
    │     └── 未固化：按 pinned_at DESC
    └── 普通区   pinned = false
        ├── 已固化：按 order 排列
        └── 未固化：按最近使用倒序（updated_at DESC）
```

- **置顶标记**：每会话一个布尔状态 + 置顶时间戳 + 可选颜色标记（三列数据，SDR-016/017），独立于排序（US1.1/US1.2/US1.4）。
- **固化（snapshot）**：全局置顶区与每个工作区（其置顶区与普通区各自）持有一份有序 id 清单；未固化的分组按动态规则排（US2.2）。
- **新条目插入**：新会话、新恢复会话（S1）、取消置顶的会话、新出现的工作区一律插入所属工作区普通区顶部——已固化清单则前插到清单头（SDR-002）。
- **归档压过置顶**：默认列表排除归档会话在读取层执行（持久化域 US6.1 的执行位置），置顶标记只对可见会话生效（US1.1 第三条）。
- **移动端差异**：移动端切换面板维持"工作区组内内联列表"的平铺形态，不渲染全局分区；其组内顺序与桌面组内相同（ADR-012 记录该差异与理由）。

### 2.2 工作区的分层视图

- 已固化：按 order 清单排列；未固化：按最近使用倒序；新工作区（首次注册）插入顶部。
- 分组折叠状态是纯界面状态，不持久化到域数据（US3.2）。

## 3. 数据契约

### 3.1 会话元数据（数据库行，ADR-006 单表示）

| 数据 | 位置 | 说明 |
|---|---|---|
| 置顶标记 | `sessions` 行的 `pinned`（布尔）、`pinned_at`（时间戳）、`pin_color`（可选语义色名）三列 | 唯一事实源（SDR-016/017）；expand-only 加列 |
| 会话排序真相 | 每个工作区桶根下一份顺序文档（`order.json`）：`{ pinned: [id…], normal: [id…] }` | 两清单各自可缺（未固化）；缺失 id 按 §2.1 动态规则排 |
| 工作区排序真相 | 数据根下一份 `workspace-order.json`：`{ ordered: [wd_id…] }` | 独立于 `workspaces.json`（后者是身份文件，不承载排序——见 ADR-001） |

- 顺序文档经 AtomicDocument 原子写（持久化域 §8 原语）；条目校验：清单内 id 必须属于本工作区桶（跨桶 id 拒绝，US2.3）。
- 容忍：清单中出现已删除的 id 时静默忽略（读取时过滤）；文档损坏按"未固化"处理。
- 置顶三列与顺序文档的分工：三列是逐会话的**事实**（是否置顶、何时、何色），顺序文档只承载**用户固化过的组内顺序**——置顶事实不再有任何第二表示（旧设计"元数据文档字段 + 索引缓存"的双表示随 ADR-006 消亡）。

### 3.2 索引缓存（S4）

- `sessions` 表的 `pinned`/`pinned_at`/`pin_color` 三列是置顶数据的**唯一事实源**（SDR-016——从旧设计的"对账回填缓存"升格，回填机制随 ADR-006 对账消解而不存在）；`workspaces` 表的 `sort_order` 列改为承载固化序号（清单位置）——从顺序文档读取。
- 列表查询按 §2.1 的分层顺序组装：行提供每会话的 pinned/pinned_at/pin_color/归属/时间，顺序文档提供固化清单，合成最终序。

### 3.3 wire 契约（mirri-proto 登记）

| 方法 | 参数 | 返回 | 语义 |
|---|---|---|---|
| `session.pin` | `sessionId`、`color?: PinColor` | `null`（noResult，与 `session.archive` 同形） | 置顶；重复置顶幂等（`pinned_at` 不因重复置顶刷新）；`color` 同时设置颜色标记（缺省 = 中性色，US1.4） |
| `session.unpin` | `sessionId` | `null` | 取消置顶（颜色一并清除，SDR-017）；会话插入普通区顶部 |
| `session.reorder` | `sessionId?`、`orderedIds: [...]`、`section: "pinned" \| "normal"` | `null` | 固化指定分组的整组顺序（客户端发送拖动后的完整清单，SDR-001 的全量快照协议） |
| `workspace.reorder` | `orderedIds: [...]` | `null` | 固化工作区顺序 |
| `session.list`（扩展） | 现有参数不变 | 行新增 `pinned: boolean`、`pinnedAt?: timestamp`、`pinColor?: PinColor`；**返回顺序即呈现顺序**（§2.1） | US4.3、US1.4 |
| `workspace.list`（扩展） | 现有参数不变 | 返回顺序即呈现顺序 | US3.1 |

- `PinColor` 枚举：`red | orange | yellow | green | blue | purple | gray`（SDR-017——有限预设色板，具体色值由各端主题定义；非法值整请求拒绝）。
- `section` 缺省 `normal`；`orderedIds` 含不属于该工作区桶的 id → 整个请求拒绝（不部分生效）。
- 全量快照协议使协议无合并冲突面（最后写者胜），与"拖动即固化"的用户语义一一对应。
- 置顶写点走元数据存储端口的**字段级增量更新**（pin 只写 `pinned+pinned_at+pin_color`、unpin 清空三列——ADR-006 裁决 4 的强制形态，写点已列入其实施计划的收窄清单）。

### 3.4 会话生命周期对排序的钩子

| 事件 | 排序效果 |
|---|---|
| 创建 / 恢复（S1） | 插入普通区顶部（固化清单则前插清单头） |
| 归档（S2） | 从任何固化清单中移除该 id（归档不可见，US1.1 第三条） |
| 恢复归档 | 视同新条目插入普通区顶部 |
| 删除 | 从固化清单移除 id；清理顺序文档中的残留 |
| 取消置顶 | 从置顶清单移除，插入其所属工作区普通区顶部（US1.2） |

## 4. 界面接线（网页首个消费方）

- 置顶区渲染：会话行新增置顶标记与置顶/取消置顶动作；列表数据源顺序即引擎返回顺序（零客户端排序）。
- 全局置顶分区（ADR-012）：网页侧栏在"工作区"分区之上渲染一个跨工作区的置顶分区——数据源是逐会话置顶事实（三列）的**客户端聚合**，不新增服务端列表方法；分区内顺序按 `pinned_at` DESC（未固化时）派生，该派生只读位置字段（id / pinned / pinned_at），不掺入运行状态等卷动数据（SDR-002 投影纪律）。行组件复用会话行，事件出口不变；行的所属工作区以该行的悬停提示交代（SDR-020 决策 5）。
- 组内置顶可见（ADR-013）：置顶行**同时**渲染在其所属工作区分组内，位于该组头部（同一置顶时刻比较器）。分组的行集合是全集（不按置顶过滤），分页与"加载更多/展开"计数按全集计算；置顶行排在组头，因此"只看第一页"的裁剪天然不会裁掉它。全局分区那份带所属工作区提示，组内那份不需要（紧挨着自己的工作区标题）。
- 行内的 Pin 控件（ADR-014）：会话行最左一个固定 24px 的槽，槽内一个圆点控件承担置顶状态、切换与颜色板入口——点击置顶（默认红）/ 取消置顶，右键与键盘上下文键打开颜色板。未置顶时槽内除圆点外不接收指针事件（点击穿透到行 = 打开会话）。工作区组头与"加载更多"按同一槽宽留白，标题对齐关系不变。
- 列表重排动效（ADR-015）：置顶/取消置顶时两个列表都以 FLIP 补间——存留行滑到新位置、新行淡入、离场行先脱流再淡出。动效不改变任何顺序语义；系统开启"减少动态效果"时补间取消，行仍落到正确位置。
- 颜色板的展开必须由**意图**触发：右键 / 键盘上下文键立即打开；悬停则要求指针在圆点上**停住**（移动会重置计时），指针扫过侧栏不会弹出浮层。浮层浮在列表之上，因此指针离开后须尽快收起。
- 移动端切换面板不渲染该全局分区：其平铺列表按同一比较器排序，置顶行天然位于组内前部（ADR-012）。
- 拖拽：采用原生 HTML5 拖放实现（现状无任何拖拽库依赖——见 context §1.1；不为此引入新依赖，ADR-004）。
- 拖放提交：松手即调用 `session.reorder` / `workspace.reorder`（乐观更新 + 失败回滚刷新）；拖入置顶区 = `session.pin` + 置顶区固化一步完成（US2.3 第三条）。
- 折叠状态保持为界面本地状态（US3.2）。

## 5. 跨引擎一致性

- TS 旧核心已冻结退役（SDR-002，见 ts-v1-engine-retirement 域）——旧设计"pinned 字段进 TS 元数据并集"的条款随之失效；Rust 核心是唯一实现，置顶三列（SDR-016）与顺序文档均为 Rust 单实现面。
- 多 Rust 实例共享 home 的置顶并发：pin/unpin 的字段级端口更新（只写三列）保证与其他元数据写点（改名、归档等）互不抹除（ADR-006 裁决 4 的机制性保障）。

## 6. 会话复制机制（E5 fork）

### 6.1 复制管道的五个阶段

fork 的执行单元是"截至分叉点的会话现场"，管道顺序固定：

1. **锚点解析**：不指定分叉点 = 取最近一个已收尾的回合终点；指定则校验该锚点存在且已收尾（进行中/不存在 → 明确报错，不静默降级到末尾）。
2. **成员级历史截取**：对源会话的**每个成员**（SDR-011），读取其会话日志并截取到锚点所属回合的收尾记录为止（含该回合的全部记录）；截断边界落在回合边界上（回合原子性）。截取出的记录流 + 头部元数据记录 + `forked` 边界记录构成新会话该成员的日志初始内容。压缩摘要记录按其落位顺序保留在截断边界之内——模型可见历史由折叠器从记录流自然重建，无需另行快照。
3. **元数据铸造**：新会话身份（引擎铸造，外部指定的 id 一律拒绝）、血缘（forkedFrom）、默认命名「Fork of 原会话标题」（SDR-012，源标题不可得时退化）、自定义元数据合并（剔除目标/进度类键）。
4. **运行中资产重置**：定时任务不带（SDR-007）；目标恢复为未启动；挂起交互不转移——全部在复制管道内完成，不依赖新会话首次启动时的清理。
5. **原子落位**：复制全部成功后才可见（列表、事件）；任何阶段失败 → 清理已写的目标目录与内存态，源会话零修改（失败回滚）。

### 6.2 分叉点参数（US5.4）

- 语义参数为"回合标识"：消费方从对话呈现层获得每轮已收尾回合的标识，随分叉请求传入；引擎以"该回合收尾记录"为截断锚点。
- 不提供按消息粒度的锚点——回合是权限/用量/审批的最小一致单元（SDR-006 裁决）。
- 跨引擎契约随 E5 契约登记批次进 wire 注册表（ROADMAP 开放项 7）。
- **消费端接线**（US5.4 界面条款）：网页端入口挂在对话呈现的回合边界上（呈现层的回合对象即锚点候选，仅已收尾者渲染入口——进行中回合无入口，可用性诚实）；终端端为命令 + 可搜索选择器（每项含该轮用户输入预览，交互模式与撤销选择器同构）；确认后入口防重触发。锚点候选由呈现层从既有回合数据派生，引擎不感知界面形态。

### 6.3 分叉的缓存计费边界（US5.5 / ADR-011）

- 模型请求配线携带一个"对话归属标识"（服务方各异：有的作为前缀路由键、有的作为归属元数据——形状由画像与提示词域（agent-profile）的请求配线定义）。
- **规则**：该标识 = **会话所属分叉链的根会话标识**。根会话（非分叉产生的会话）的根就是它自己，因此在创建时即持有自己的标识；分叉出的会话不持有新标识，而是沿用源的链根——嵌套分叉沿袭最初那个根（SDR-018 裁决）。
- 每个会话的每一次请求都携带自己的链根标识——链根标识必须被根会话自己真正使用过，否则分叉继承的是一段无人写过的对话，首次请求必然全量未命中。
- 分叉会话的首次请求前缀与源会话在分叉点后的下一请求前缀一致（§6.1 第 2 步的截取保证），归属又落在源会话用过的同一段对话上——两者合起来使分叉首请求在正常情形下即享已读优惠。命中与否最终由服务方的前缀匹配判定，引擎不承诺命中本身。
- 多分叉共享同一归属的代价（各分叉后续演进在服务方侧互相挤占）被接受为分叉的成本结构（ADR-011 的权衡）。
- 引擎侧不引入任何服务方特定的缓存预写/管理逻辑：命中是服务方行为，引擎的义务止于**请求前缀的确定性**（分叉截取管道的输出逐字节稳定）与**归属标识在会话存活期间的稳定**。

### 6.4 createChild 的复用关系

`session.createChild` 走同一条 fork 管道（§6.1 全阶段），仅元数据铸造阶段额外写入父会话标识与子会话类别标记（SDR-005：溯源不等于所有权）。

## 7. 对话撤销机制（Epic U）

### 7.1 落盘义务（ADR-006）

撤销改变模型可见历史，而会话日志（S5，持久化域）是对话历史的唯一真相——**每一次生产路径的撤销都必须作为一条撤销 wire 记录写入会话日志**，与内存变更同批提交。撤销 wire 记录在重放折叠器（reducer fold）中的解释语义是**按消息条数截断**（记录的 `count` = 从尾部移除的消息条数）：任何撤销写入方（含 Rust 内核的 live 撤销，即 U1 实现批次的接口义务）写入的 `count` 必须采用该口径——撤销量（轮数，粒度按开放项裁决）→消息条数的换算发生在写入侧，折叠器的解释语义不因写入方而变。US-U2（撤销经收起/重开保持）即由"记录 + 折叠"闭环保证。

### 7.2 与压缩域的联动

- **编号区间括号校正（压缩域 ADR-007）**：wire 记录形态的撤销产生条目编号消耗间隙，压缩落位记录的区间括号据此校正重放编号。该校正存在压缩域文档化的残差：撤销切点落入头部精华区或保留尾区之内时该区段欠校正；任意切点保真需逐撤销记录——该延后项载于压缩域 context §1.2 与折叠器侧文档注释（后者援引 ADR-007 的校正），并非 ADR-007 正文承诺，本域亦不承诺。详见压缩域架构 ADR-007 与其 context §1.2。
- **边界即停（C3）**：撤销锚点回溯在压缩落位摘要处停止，不穿越压缩考古（SDR-009 承接的压缩域裁决）。

### 7.3 护栏与可用性

- 撤销仅在会话空闲时接受：回复进行中、压缩进行中一律拒绝并如实反馈（拒绝与放行以同一忙碌判定为准，对称定义）。
- 请求超过可撤销深度时拒绝，并携带当前可撤销轮数与原因（到压缩边界 / 无可撤销内容）——用户可感知信号与真实可撤销范围一致。
- 撤销锚点谓词与"真实用户输入"口径一致（用户消息、用户触发的命令），用于识别回退落点；回退单元为**整轮**（US-U1 基线，回合 S7 原子性）——一个回合及其后的全部内容构成一个回退单元。更细的撤销粒度（输入级）是否提供属 ROADMAP 开放项 9，裁决前不实现。

### 7.4 契约

撤销沿用已登记的 `session.undo`（`sessionId` / `agentId?` / `count?`，缺省 1）——RPC 契约面无新增方法；撤销的持久化载体是既有的 `context.undo` wire 记录族（非新记录类型），落盘义务与 count 口径见 §7.1 / ADR-006。

## 8. 会话运行状态机制（US4.4 / SDR-013）

### 8.1 状态口径：四元组与主对话回合判定

会话运行状态是一个**四元组**（与参照引擎 TS v2 的 work facts 同口径）：`busy`（任一成员回合在途或后台工作存活——聚合忙碌）、`mainTurnActive`（主对话成员的回合未收尾——列表"运行中"标记与停止按钮的判定输入）、`pendingInteraction`（none / approval / question——挂起交互类型）、`lastTurnReason`（completed / cancelled / failed——最近回合结局）。**侧边栏"运行中"标记的口径 = `mainTurnActive`**：后台任务与子代理回合点亮 `busy` 但不点亮标记——刷新前后口径一致是 US4.4 的验收前提。

### 8.2 读面重建：进程内权威，不猜进程外的状态

刷新/换端后的状态由服务端给出，数据源是**进程内的在途回合注册表**（引擎内存中"该会话哪个成员的哪个回合正在跑"的登记）——同进程刷新/换端直接命中，含主对话回合判定（回合归属成员 = 主对话成员即 `mainTurnActive=true`）。**注册表未覆盖的会话一律按"未运行"呈现**——不做跨进程/重启场景的日志探测兜底：每个服务进程只如实报告自己承载的回合；未配对的回合开始记录会存活于会话日志，但"该记录是否还活着"只有其承载进程知道，其他进程（含重启后的同进程）无从判定，任何推断都会在进程死亡后变成假阳性（违背 US4.4 第四条）。索引行（静态行）的四元组一律为中性值（未运行/无挂起）。

**已知边界（被接受的近似）**：多进程共用同一数据根的部署形态下，另一个进程承载的运行中会话在当前进程的列表中显示为未运行——与参照引擎（TS v2）行为一致（每个服务进程只报告自己）；会话历史本身跨进程完整可见，仅运行态标记的可见性限于承载进程。

### 8.3 事件面：会话级状态通知

状态四元组的每次真实迁移（聚合器自带去重——状态未变的重复输入不产生事件）广播一条**会话级通知事件**（`event.session.work_changed`，负载即四元组，snake_case 与参照引擎 wire 一致），全局扇出到每个连接（不要求订阅该会话——列表行的状态更新不依赖逐会话订阅；协议总览的全局扇出例外条款见协议 §2.3）。事件为 **durable**：落会话事件日志、携带 seq、可被 cursor 重放（与参照引擎一致——刷新丢连接期间的迁移靠重放补齐，而非靠重拉列表）。回合结束的迁移必须排在对应 `turn.ended` 事件之后（消费方依赖"回合结束在前、状态熄灭在后"的顺序关闭运行中呈现）。

### 8.4 契约

| 面 | 扩展 |
|---|---|
| `session.list` 行 | 新增 `mainTurnActive` / `busy`（已有，语义校正为四元组口径）/ `pendingInteraction` / `lastTurnReason`（视图字段 camelCase，与既有 SessionView 一致） |
| `session.snapshot` 会话视图 | 同上四元组（快照是刷新/重连的重建种子，US4.4 第一条的主通道） |
| `event.session.work_changed` | 新登记事件：durable、全局扇出、负载 `{sessionId, busy, main_turn_active, pending_interaction, last_turn_reason}`（snake_case，与参照引擎 wire 拼写一致） |

跨引擎一致性：契约登记后 TS 侧（存活期内）按既有实现直接对齐（v2 的列表行与事件即目标形态，无需变更）。

## 9. 决策记录（ADR）

### ADR-001 排序真相存于磁盘顺序文档，索引只做缓存

- **背景与动机**：手动排序是用户数据而非派生数据——S4 会话索引被整体删除时任何用户数据不得丢失（持久化域 US7.1），因此固化顺序不能只存在于索引中；持久化域 ADR-002 曾预留 `workspaces.sort_order` 索引列，本设计将其定位收窄为"缓存"。
- **决策**：固化顺序真相 = 桶内 `order.json` + 数据根 `workspace-order.json`（§3.1）；索引列由文档回填，对账以文档为准。
- **否决的替代**：顺序只存索引（违反索引可丢弃原则）；顺序存进 `workspaces.json`（跨引擎共享的身份文件，每次拖拽全量重写且 TS 写回可能丢未知字段）；每会话存序号（跨会话的全局顺序拆进逐会话文件，固化一次要写 N 个文件）。
- **影响面**：§3.1、§3.2；持久化域 ADR-002 的列定位收窄（该域架构文档由本 ADR 引用而不改写）。

### ADR-002 置顶标记存于会话元数据文档

- **背景与动机**：置顶是逐会话的持久事实，须随会话目录整体拷贝/备份而不丢。
- **决策**：`state.json` 新增 `pinned` 布尔字段（跨引擎并集扩展，默认 false）；索引 `pinned` 列为缓存。
- **否决的替代**：只存索引（同 ADR-001 的否决理由）；存进顺序文档（置顶是会话属性而非列表属性，会话级文件更内聚）。
- **影响面**：§3.1、§3.2、§3.4。

### ADR-003 固化采用全量快照协议

- **背景与动机**："拖动即固化整组"（SDR-001）需要与用户心智一一对应的协议形态。
- **决策**：`session.reorder` / `workspace.reorder` 接收拖动后的完整 id 清单（§3.3）；最后写者胜，无合并冲突面。
- **否决的替代**：增量移动协议（`move(id, before, after)`——需处理并发移动的相对语义，复杂度不成比例）。
- **影响面**：§3.3。

### ADR-004 网页拖拽用原生实现，不引入拖拽库

- **背景与动机**：侧边栏拖拽是垂直列表内的简单重排；当前网页依赖树中没有任何拖拽库（context §1.1）。
- **决策**：HTML5 原生拖放（draggable + dropzone），必要时局部 pointer 事件补齐；不新增依赖。
- **否决的替代**：引入通用拖拽库（为单一列表重排场景引入整树依赖，不成比例）。
- **影响面**：§4。

### ADR-005 呈现顺序由引擎统一给出

- **背景与动机**：顺序是数据（US4.1），若各端自行拼装排序则"一份顺序"退化为"每端一套拼装逻辑"。
- **决策**：`session.list` / `workspace.list` 的返回顺序即呈现顺序（§2.1 分层序）；无拖拽能力的终端界面零成本获得正确顺序（US4.3）。
- **否决的替代**：引擎返回无序集合 + 各端按 pinned/order 字段自行排（逻辑重复，行为漂移面大）。
- **影响面**：§2、§3.3；网页接线（§4）零客户端排序。

### ADR-006 撤销必须落盘，count 语义与折叠器的按消息截断一致

- **背景与动机**：撤销直接改变模型可见历史，而会话日志（S5）是历史的唯一真相——若 live 撤销只改内存不写日志，收起重开后重放会回到撤销前的内容：用户看到"撤销了"、重开后"撤销消失"（US-U2 要消除的信号失真；现状差异见 context §1.6）。折叠器对撤销记录的解释语义是"从尾部截断 `count` 条消息"，与撤销侧的轮/锚点计数不是同一个数——写入方与折叠器口径不一致时，重放截断位置错位。
- **决策**：撤销落盘为 U1 实现批次的**接口义务**：live 撤销在内存变更的同批写一条 `context.undo` wire 记录，记录的 `count` 采用与折叠器按消息条数截断一致的口径（= 被移除的尾部消息条数）；撤销量（轮数，粒度按开放项裁决）→消息条数的换算由写入方完成，折叠器的解释语义保持不因写入方而变（§7.1）。
- **否决的替代**：(a) 撤销不落盘——重开复活被撤内容，违反 US-U2 与信号真实性（即要消除的现状缺口）；(b) 记录锚点数、折叠器按锚点重算——改变折叠语义会牵动既有 TS 写入日志的重放（两代写入方共享同一折叠器，语义单侧变更造成跨引擎重放不一致）；(c) 撤销时快照整个历史——代价重，且与"日志唯一真相"原则冲突。
- **影响面**：US-U2；§7.1、§7.4；压缩域 ADR-007 的编号区间括号校正（仅对 wire 记录形态的撤销可校正）；U1 实现批次的接口验收。

### ADR-007 分叉的归属标识随新会话身份，引擎义务止于前缀确定性

> **已被取代（2026-11-08，ADR-011）**：「归属标识 = 会话自身 id、分叉不沿袭」由 ADR-011 取代（改为沿袭分叉链根）。§6.3 已同步至最终状态；以下保留原文作为历史记录。

- **编号与日期**：ADR-007 · 2026-10-09（同日修订，随 SDR-010 修订）
- **背景与动机**：服务方对已读前缀的计费优惠依赖请求前缀的字节一致性（引擎的截取管道已保证，§6.1）与归属标识。首个方案曾裁决分叉沿袭根会话身份以保证首请求命中；修订时权衡：前缀稳定已是命中主因子，身份继承的边际收益不抵多分叉共享同一缓存归属的竞争（各分叉的后续演进互相挤占），复杂度不成比例。
- **决策**：归属标识 = 会话自身 id（分叉出的新会话用新身份——与参照引擎现状一致，无对齐变更）；分叉首请求的命中不做保证（可能的未命中是分叉的成本结构），其后请求按新身份稳定积累。引擎对服务方缓存不负任何管理职责——义务止于**分叉后请求前缀的确定性**（截取管道的输出逐字节稳定）。
- **否决的替代**：(a) 分叉沿袭根会话身份（同日修订否决的原方案）——单分叉首命中更确定，但多分叉共享归属互相竞争，且把计费连续性耦合进会话身份体系；(b) 引擎侧预写缓存/预热 API——服务方特定逻辑，超出引擎边界（两版一致否决）。
- **影响面**：§6.3；US5.5；参照引擎（TS v2/v1）现有行为即目标行为，无对齐变更；glossary G6（形态同步改写）。

### ADR-008 复制管道以"按记录截取重写"取代"目录整拷"

- **编号与日期**：ADR-008 · 2026-10-09
- **背景与动机**：分叉点参数（US5.4）与成员级全量复制（SDR-011）共同要求"截至锚点的选择性复制"——现行的目录复制路线（现状证据见 context §1.4）无法表达截断，也无法在拷贝中重置运行中资产；它只能在拷完后清理，留下"半成品窗口"与死数据。
- **决策**：复制管道 = 按成员读取源日志 → 截取到锚点 → 加 `forked` 边界记录 → 重写为目标日志（§6.1 第 2 步）；会话级共享文件（附件等）走共享引用不复制（SDR-007 共享条款，持久化域 ADR-007 底座）。
- **否决的替代**：(a) 目录整拷 + 事后截断——两步非原子，中途失败留下撕裂状态，且无法表达"哪些文件属于锚点之后"；(b) 引用计数共享日志段——读取侧需理解分段，折叠器复杂度上升，收益（省盘）与分叉频度不成比例。
- **影响面**：§6.1；TS v2 对齐批次的重构方向（现状证据 context §1.4）；与持久化域 ADR-007（附件共享存储）的实现耦合。

### ADR-009 运行状态双侧同补：列表读面 + 状态事件，重建只认进程内权威，不落持久化标记

- **编号与日期**：ADR-009 · 2026-10-13
- **背景与动机**：刷新后列表的"运行中"标记需要服务端重建，而重建有读面（列表/快照带状态字段）与事件面（状态迁移通知）两侧——只补一侧会留下"首屏恢复但后续无感"或"实时有感但刷新即失"的半吊子状态。运行态天然是进程内易变状态（进程死亡即死），任何持久化标记都会在死亡后变成谎言；同理，任何跨进程的运行态推断（如会话日志的未收尾回合探测）都无从判定"承载该回合的进程是否还活着"。
- **决策**：读面 + 事件面同批补齐（§8.2/§8.3）；状态重建只认**进程内在途回合注册表**，未覆盖即"未运行"——不做日志探测兜底（与参照引擎行为一致：每个服务进程只报告自己承载的回合）；**不做**运行状态的独立持久化（无索引列、无标记文件）——进程重启后按"未运行"呈现。多进程共用数据根的部署下，他进程承载的运行中会话在当前进程显示未运行（已知边界，历史完整可见，仅运行态标记限于承载进程）。
- **否决的替代**：(a) 只补读面——状态变化无通知，列表行退化为轮询模型（SDR-013 否决项 a 的架构视角）；(b) 状态持久化到索引——死亡后脏标记 + 失效清理义务（SDR-013 否决项 c）；(c) 事件用 volatile——丢连接期间的迁移无法靠 cursor 重放补齐，重连后必须强制全量刷新列表，而 durable 事件让重放路径天然覆盖（参照引擎同为 durable）；(d) 会话日志未收尾回合探测——重启后未配对的开始记录仍在日志里，探测会把死亡进程的残留回合报成"运行中"（US4.4 第四条的假阳性），且无进程存活判定可用；"自然消散"在日志不可变的模型下不成立。
- **影响面**：§8；US4.4；SDR-013；协议事件目录（`event.session.work_changed` 登记 + §2.3 全局扇出例外条款，rust-core-design 01 的协议修订）。

### ADR-010 置顶数据落座数据库行三列，补置顶时间戳与颜色标记（SDR-016/017）

- **编号与日期**：ADR-010 · 2026-11-03
- **背景与动机**：本域基线的置顶载体（元数据文档布尔字段 + 索引缓存列 + 对账回填）建立在"磁盘是唯一事实源"的持久化域原则之上；会话一致性域 ADR-006（2026-11-03 已裁决）将该原则整体翻转为"数据库行是会话元数据唯一事实源"——元数据文档退役、对账消解，旧载体三去其二。同时本域补齐基线缺失的置顶时间戳（未固化置顶区的排序依据）与新增颜色标记能力（用户需求，US1.4）。
- **决策**：置顶数据为 `sessions` 行三列——`pinned`（布尔）、`pinned_at`（时间戳）、`pin_color`（可选语义色名，有限预设色板 `red|orange|yellow|green|blue|purple|gray`，色值由各端主题定义）。列变更走 expand-only 纪律；`session.pin`/`unpin` 走元数据存储端口的字段级增量更新（pin 写三列、unpin 清三列）；未固化置顶区组内顺序 = `pinned_at` 倒序。顺序文档（order.json）继续承载用户固化过的组内顺序，与三列分工：三列是逐会话事实，顺序文档是用户固化意图。颜色是置顶的修饰而非独立标记（取消置顶一并清除）。
- **否决的替代**：(a) 保留 order.json 为置顶事实源、行只存缓存——ADR-006 终态下重引双表示与对账回填，正是被推翻的结构；(b) `pinned_at` 用 `updated_at` 近似——违反 SDR-004/014"维护性更新不算使用"口径，语义二义；(c) 颜色为独立标记（未置顶可染色）——膨胀为第二套列表组织维度，违背 YAGNI；(d) 自由取色（存 hex）——契约无法枚举校验、主题适配无统一保障。
- **影响面**：§2.1、§3.1、§3.2、§3.3；US1.1–1.4、US4.3；会话一致性域 ADR-006 实施计划（三列进 expand-only 迁移、置顶写点补入字段级收窄清单）；glossary G1（置顶颜色标记条目随同批登记）。

### ADR-011 分叉的归属标识沿袭分叉链根，且链根必须被自己真正使用过（SDR-018）

- **编号与日期**：ADR-011 · 2026-11-08（取代 ADR-007）
- **背景与动机**：分叉会话要在首次请求时兑现已读优惠，需要两个条件同时成立——请求前缀逐字稳定（截取管道已保证），以及请求上的归属标识与源会话用过的那一段对话**完全一致**。ADR-007 裁决"新会话用新标识、首请求命中不做保证"，把代价当作可接受的成本结构；实际代价与对话长度成正比：前缀越长，首请求要重新读取的内容越多，用户感知为分叉后第一句话的等待时间异常。归属标识是引擎唯一可控的输入，因此问题收敛为"标识指向谁"。
- **决策**：
  1. 归属标识 = **会话所属分叉链的根会话标识**。根会话在创建时即持有以其自身为值的标识；分叉出的会话不铸造新标识，而是解析并沿袭源的链根（源本身是分叉时取源的根，否则取源自身），与 `forkedFrom` 血缘相互独立——血缘说"从哪来"，归属说"算作哪段对话"，两者不合并建模。
  2. 每一次模型请求都携带该标识；未持有标识的会话（历史会话对象早于该字段）省略该字段，请求退回服务方默认归属。
  3. 承载方式：标识随会话元数据（非数据库行的列——行只承载标题/标签/归档等展示与生命周期事实，归属属血缘类事实，与 `forkedFrom` 同类），由发送与引导两条请求路径注入会话的回合流，再随每次步进请求下发到服务方。
  4. 会话重新载入时若元数据不携带标识，以其自身标识补齐——归属不得因进程重启而丢失，否则重启后的请求会退回默认归属，分叉继承再次落空。
- **否决的替代**：
  (a) 沿用 ADR-007（新会话新标识）——归属必然指向一段无人写过的对话，长对话下首请求即全量重读，与"分叉是低成本试错"的产品定位冲突。
  (b) 只有分叉结果携带链根、根会话不携带——标识所指的对话从未被写入，继承形同虚设（这正是"管道建了一半"的形态），不可接受。
  (c) 把归属并入 `forkedFrom` 单一字段——血缘是溯源的展示事实（可能被改写或清空），归属是计费输入（必须稳定且可解析到链根），一字段两语义会把两类变更耦合。
  (d) 引擎侧预热/预写服务方缓存——服务方特定逻辑，超出引擎边界。
- **影响面**：§6.3；US5.5；SDR-018；glossary G6（形态与定义同步改写）；ADR-007 标记为已被取代。

### ADR-012 置顶区提到侧栏顶部并跨工作区聚合，置顶行不在工作区分组内重复（SDR-020）

> **部分已被取代（2026-11-21，ADR-013）**：本条决策 3「置顶行从其工作区分组中移出、分组的分页按未置顶子集计算」由 ADR-013 取代——组内恢复渲染置顶行，分页按全集计算。其余决策（1 全局分区渲染顺序、2 共享置顶时刻比较器、4 所属工作区悬停提示、5 移动端不渲染全局分区）继续有效。以下保留原文作为历史记录。

- **编号与日期**：ADR-012 · 2026-11-15（取代 ADR-010/§2.1 中"置顶区位于各工作区分组顶部"的呈现归属；三列存储契约与 `pinned_at` DESC 规则不变）
- **背景与动机**：置顶是用户对"这是重点"的判断，判断本身不按工作区切分。把置顶区放在每个工作区分组内部，等于把一个判断拆成 N 份（N = 工作区数），每份通常只有一两条——重点清单因此失去"一眼看全"的价值，工作区越多衰减越快。呈现层需要一次归属调整，而数据层不需要任何变化（置顶事实本来就是逐会话的）。
- **决策**：
  1. 侧栏渲染顺序：全局置顶分区 → 工作区列表。全局分区的数据源是逐会话置顶事实的客户端聚合，**不新增服务端列表方法、不改列表返回顺序契约**（ADR-005 的"呈现顺序由引擎统一给出"仍约束工作区分组内部的顺序）。
  2. 全局分区的顺序派生与工作区排序共享同一置顶时刻比较器（`pinned_at` DESC）；该派生只读位置字段，不读运行状态/用量等卷动数据（SDR-002 投影纪律）。
  3. 置顶行从其工作区分组中移出，由该组的呈现层过滤（分组的数据仍完整——同一份分组数据同时服务移动端切换面板）；分组的分页与"加载更多/展开"计数按**未置顶子集**计算，否则会出现"计数说有更多、列表却已到底"的假信号。
  4. 每行的所属工作区以悬停提示给出（行内其它布局不变）——这是全局分区跨工作区后补偿"行失去了分组标题"的最小信息增量。该提示挂在行的标题上（标题是行内稳定、始终可见的目标），不挂在悬停时会让位给操作按钮的时间位置（那里鼠标一进就不可指向，提示永不出现）。
  5. 移动端切换面板不渲染全局分区，维持组内内联列表；其排序比较器保留置顶优先分支（因此该分支在移动端仍然生效）。两端的差异是**有意的**：移动端是单列平铺、以组为单位浏览，内联置顶让"组内最重要的"与"组内其它的"在同一视线内；桌面端跨组合并才解决"重点看全"。
- **否决的替代**：
  (a) 服务端新增"置顶会话列表"方法并在引擎侧排好序——数据本就是逐会话事实，跨工作区聚合是纯呈现选择；新增方法会把一个界面布局的决定固化进 wire 契约，且与"列表顺序由引擎给"的既有方法产生两份排序真相。
  (b) 置顶行在全局分区与工作区分组各渲染一份——同屏重复让"哪份是本体"、"点了哪个高亮"变得含糊，且两份需同步激活态。
  (c) 桌面端也保留组内置顶、仅在顶部加一个"重点"浮层——两份呈现并存即 (b) 的变体。
  (d) 移动端同步改为全局分区——单列平铺下，组内上下文（哪个项目的会话）比跨组合并更重要，全局分区会让用户在切面板时丢失组结构；移动端已有组内排序兜底。
- **影响面**：§2.1、§4；US1.1/US1.2/US1.3；SDR-020；glossary G1（呈现位置表述）；SDR-002 投影纪律（新增一个只读位置字段的排序派生点）。

### ADR-013 工作区分组恢复渲染置顶行，分页按全集计算（SDR-021）

- **编号与日期**：ADR-013 · 2026-11-21（取代 ADR-012 决策 3 及 §2.1「组内不重复」表述；ADR-012 决策 1/2/4/5 不变）
- **背景与动机**：ADR-012 让置顶会话只出现在顶部全局分区，代价是按项目浏览的路径断了——用户记得会话属于某个项目，去该项目分组里找，置顶后那一条就消失了。全局分区的顺序按置顶时刻排列，不携带项目结构，用户只能先认出"这条属于哪个项目"再判断是不是自己要找的。呈现层需要同时满足两个诉求，而它们并不互斥：数据的完整性从未变过（分组本来就有完整数据），冲突只在"分组呈现时是否过滤置顶行"这一处。
- **决策**：
  1. **分组呈现全集**：工作区分组的行集合 = 该组的全部会话（含置顶），不做置顶过滤。分组内顺序沿用既有比较器（置顶优先，置顶内 `pinned_at` DESC，其余按最近使用倒序），因此置顶行天然落在组头。
  2. **分页按全集计算**：「只显示第一页」的裁剪、`hasMore` 与"展开全部/收起"计数都以全集为基准。置顶行在组头，裁剪天然不会隐藏它——这条约束靠顺序保证，不靠额外的"置顶行豁免"分支。
  3. **两处渲染同一行数据**：全局分区与组内消费同一投影（同一 id、同一 `pinned`/`pinColor`），组件与事件出口复用，不引入第二份状态。因此改色、取消置顶、选中高亮在两处自动同步（都来自同一个响应式数据源）。
  4. **归属提示仍只在全局分区**：组内那份紧邻工作区标题，不重复交代归属；全局分区那份按 ADR-012 决策 4 给出所属工作区名称。
  5. **移动端不受影响**：切换面板本就不渲染全局分区、只用组内内联列表，其形态与本条决策 1 一致。
- **否决的替代**：
  (a) 维持 ADR-012 决策 3（被取代的方案）——按项目浏览时置顶会话不可见，本次改判动机。
  (b) 为本条新增"置顶行豁免分页"的特殊分支——置顶行已在组头，顺序已保证可见；额外分支只会让分页语义分裂成两套，后续改动易漏。
  (c) 组内那份渲染为只读指针行（置灰/不可交互）——用户看到一条不能正常用的会话行，与"排的顺序说了算"的整理者诉求相悖，且要维护两套行状态。
  (d) 取消全局分区、只保留组内——回到 ADR-012 之前的多工作区切碎问题。
- **影响面**：§2.1 分层视图与 §4 界面接线；ADR-012 决策 3 标记为被取代；SDR-021；US1.1 验收；glossary G1 呈现位置表述。

### ADR-014 会话行的 Pin 控件：左置固定槽 + 彩色圆点，悬停改色 / 点击取消置顶（SDR-021）

- **编号与日期**：ADR-014 · 2026-11-21（细化了 US1.1/US1.4 的呈现形态；SDR-016/017 的三列存储契约不变）
- **背景与动机**：置顶动作此前分散在两个入口——标题旁的状态图标（开颜色板）与行尾悬停区的另一个图标（置顶/取消置顶），两个锚点、两种图形，用户与读屏都必须先分辨"哪个是状态、哪个是动作"。同时，未置顶行常显一个图钉图标，让整列看起来像一排按钮；而"颜色"唯一的持续表达是行左缘 3px 竖条，存在感弱且与行的缩进规则抢位置。呈现层需要一个**单一锚点、单一控件**：状态、切换、改色都在同一处。
- **决策**：
  1. **左置固定 Pin 槽**：会话行最左固定一个 24px 的槽，树的缩进从槽右侧起算，槽本身不被推移；工作区组头、空态与"加载更多"控件同宽留白，保证会话标题仍对齐工作区名。
  2. **标记是彩色圆点，不是图标**：置顶用一个实心圆点表达，颜色即 `pinColor`；未置顶是同尺寸的空心圆点，仅在行悬停 / 聚焦时显形。两态共用一个形状与锚点，切换只变填充与显隐。
  3. **单一控件承载三种操作**：点击 = 置顶（默认红）/ 取消置顶；悬停已置顶的圆点 = 展开颜色板；右键 / 键盘上下文键 = 同一颜色板。颜色编辑因此不需要额外点击，也不需要第二个图标。
  4. **空白槽不响应**：未置顶时槽内除圆点外的区域不接收指针事件，点击穿透到行（打开会话）——不可能误触置顶。
  5. **置顶必带颜色**：置顶落下时若用户未选色，写入默认红。无色置顶在圆点形态下没有可见痕迹，因此"无色置顶"不是可达状态（SDR-017 的 `color` 可选性仍保留在契约层，仅为兼容既有数据）。
  6. **取消置顶不经颜色板**：圆点的点击是取消置顶，颜色板里不含"取消置顶"项——两个动作各有唯一入口。
- **否决的替代**：
  (a) 保留双入口（状态图标 + 动作图标）——两个锚点两个图形，用户与读屏都要先分辨角色，正是本条要消除的问题。
  (b) 用图标（图钉 / 星标 / 锁）而非圆点——图标需要额外的方向或形状区分态，而颜色本身就是态；圆点让"颜色 = 分类、填充 = 状态"两件事同形表达。
  (c) 圆点点击开颜色板、改色后再单独取消置顶——取消置顶会多一步，且"点一下状态标记"的直觉落空。
  (d) 悬停即开颜色板改为点击开——改色多一次点击，而悬停既有的 320ms 停留判定已能过滤误开。
- **影响面**：§4 界面接线；US1.1/US1.4 验收（默认红、悬停改色、点击取消置顶、圆点形态）；SDR-021 的呈现表述；`session.pin` 的默认色收敛到一处（网页端各入口共用同一默认值）。

### ADR-015 侧的 Pin 重排动效与颜色板开启纪律（SDR-021）

- **编号与日期**：ADR-015 · 2026-11-21（补充 ADR-014 的动效与浮层开启时机；不改任何排序或存储语义）
- **背景与动机**：置顶/取消置顶会让行在两个列表之间迁移，纯 DOM 重排是瞬移——用户看到的是一次跳跃，跟丢了自己刚操作的那一行。另外，颜色板的"悬停即开"在指针只是路过侧栏时也会弹出浮层，并盖住下方的行与"加载更多"，把一次普通移动变成一次意外的遮挡。
- **决策**：
  1. **两个列表都用 FLIP 补间**：全局置顶分区与工作区分组各用一个可动的列表容器；存留行在 `transform` 上滑到新位置，新行从上方微升淡入，离场行立即脱流（绝对定位、不接指针）再淡出，使其余行马上开始合拢。
  2. **动效预算跟侧栏一致**：位移用 `--duration-base`、透明度用 `--duration-fast`，缓动沿用 `--ease-out`——重排读作"一次即时位移"，不是一段动画。
  3. **动效不承载语义**：顺序、置顶状态、颜色全部由数据决定；动效关闭或跳过时，列表的最终形态完全一致。
  4. **减少动态效果即降级**：系统偏好 `prefers-reduced-motion: reduce` 时取消补间与入场位移，行直接落位。
  5. **颜色板只由意图触发**：右键与键盘上下文键立即打开；悬停需指针在圆点上停住（移动重置计时），因此扫过侧栏不会弹层。浮层浮在列表之上，指针离开后须尽快收起（宽限期以"能挪进浮层"为下限，不做长驻）。
- **否决的替代**：
  (a) 不做动效、只做高亮闪烁提示行已移动——瞬移仍然发生，用户依旧会丢失行的去向。
  (b) 用绝对定位 + 逐行计算 top 的手写动画——等于重写一遍 FLIP，且要自己管容器高度与离场行，复杂度换不到更好的效果。
  (c) 悬停即开颜色板（ADR-014 的原形态）——指针扫过就弹浮层并遮挡列表，实测会把"移向下一行"变成"关掉浮层再走"。
  (d) 颜色板改成只能点击打开——多一次点击，且与"点圆点 = 取消置顶"的动作冲突。
- **影响面**：§4 界面接线；ADR-014 的开启时机（悬停改为"停住才开"，其"点击=切换、右键/键盘开板"不变）；US1.4 的改色验收（悬停停留即可改色仍然成立）。
