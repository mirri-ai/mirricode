## A. TS 现状机制（Rust 对齐基线）

### A.1 蜂群模式状态机

- **状态模型**：触发源三值（manual / task / tool）加空（未开启），**不折叠为布尔**——自动退出判定依赖触发源：task 与 tool 在回合结束时自动退出，manual 不退出。
- **状态变更以会话持久化操作承载**：进入/退出各为一个持久化操作，携带触发源；操作回放即恢复状态。恢复不依赖显式恢复调用、不依赖进程内存。服务接口保留一个恢复入口（仅派发操作、不注入指引、不发布事件）供宿主恢复路径使用；TS v2 靠操作回放恢复，该入口在 v2 无调用方（v1 会话恢复路径使用）。
- **事件投影**：进入/退出操作各派生一条会话状态更新事件（含蜂群模式字段）；该事件为**易失事件**（不落操作日志），消费端重连靠状态快照回读补齐。
- **指引生命周期**：进入时向主代理上下文注入蜂群工作法指引（触发源为 tool 时**不注入**——批量派发工具自身的参数语义已足够）；退出时若进入指引仍位于上下文末尾，则以 live-only 上下文裁剪事件**弹出收回**，否则追加一条退出指引；实时与回放两个视角行为一致（回放不重现"当时不存在"的指引）。
- **幂等**：已处于蜂群模式时再次进入直接返回，不重复派发操作、不重复注入。

### A.2 触发路径（三条）

| 触发源 | 路径 | 自动退出 |
|---|---|---|
| manual | 宿主请求携带蜂群标志（会话请求的模式字段）→ 引擎进入 | 否 |
| task | SDK 组合调用：进入（task）后立即提交任务（"单任务蜂群"） | 回合结束退出 |
| tool | 批量派发工具执行时自动进入 | 回合结束退出 |

### A.3 蜂群批次独占否决

- 工具执行前做**批次级检查**：批次内批量派发调用数为 0，或恰为 1 且批次仅含它——放行；否则**整批否决**（以工具审批拒绝形态返回），"多个批量派发同批"与"批量派发混其它工具"两类场景各有固定提示文案模板（前者按是否混批追加提示）。
- **动机（抽象）**：批量派发是一次编排决策；混批破坏该决策的原子性与失败归因，也让聚合结果不可读。单一派发不受此限制（可混批）。

### A.4 消费端接线

- **网页端**：模式菜单（计划/目标/蜂群/协作四并列开关）→ 双路生效：随每次请求提交模式字段 + 独立的模式切换调用（两后端调用形态不同：v2 走会话 profile 更新，Rust 走模式进入/退出 RPC）；偏好按会话本地持久化（含"无会话暂存、首会话转移"与"会话删除清理"）；状态经快照回读 + 易失事件投影双向维护；手动权限下开启蜂群先弹确认。
- **终端**：斜杠命令（仅空闲回合可用）——裸命令切换、on/off 显式、带任务描述即"进入（task）+ 提交"；手动权限下三选项确认（切换自动 / 切换免确认 / 保持手动），取消还原命令文本；模式变化在状态栏徽标与转录标记（进入/退出/单任务结束）两处呈现。
- **桌面端**：薄壳加载网页界面，自身不实现协作面。
- 成员级进度/卡片呈现机制：引用子代理派发域与对话渲染域（不在本域）。

### A.5 事件与接口面

- **事件**：子代理生命周期五事件（spawned/started/suspended/completed/failed，字段含父工具标识、蜂群序号、后台标志、型号解析结果）+ 会话状态更新事件中的蜂群字段。**不存在** swarm.* / collaboration.* 事件类型。
- **接口**：蜂群控制在 TS 侧无独立 RPC——经会话请求的模式字段（REST）与进程内服务调用（SDK）生效；批量任务的查询/停止/读输出走任务服务契约。`swarm.enter/exit/get` 的 RPC 形态仅存在于 Rust 引擎的方法映射（现状核对见 context §7-C 勘误台账与 §1 就地勘误标注）。
- **后端自动检测**：网页按服务端自报的后端类型选择通道（TS daemon 双通道或 Rust 单通道 JSON-RPC）。

### A.6 权限面

- 蜂群模式**不改变权限语义**：成员继承派发者的权限模式与用户工具面；批量派发工具自身在默认策略中**自动放行**（可被用户规则覆盖）；无蜂群/子代理专属的独立权限策略（策略链细节引用子代理派发域与工具调用域）。

## B. 团队模型架构骨架（设计提案，超出 TS 现状）

> 以下支撑需求 E1–E7，全部为提案；落地前受需求 §11 Q1–Q5 裁决约束。可参照的既有资产：Rust 侧协作 crate 的协议骨架（现状为纯台账——合成 agent id、内存态、不驱动真实执行；其协议形状可回收，处置裁决见 rust-core-design N2，本域只引用不重复）。

### B.1 团队＝会话树上的协作层 [提案]

- 团队建模为特殊会话树：成员会话挂团队之下，**复用子代理设施**（生命周期注册、父子元数据、事件面、持久化）而非另建第二套 agent 机制；lead 即团队会话的主代理（对齐 SDR-002）。对应 Q3 倾向 a；b 的能力（跨会话长生命周期）由团队持久化承接。

### B.2 协作协议骨架 [提案]

- **消息**：结构化消息枚举（任务分派/任务结果/提问/回答/冲突升级/介入/状态更新）+ 未知类型前向兼容兜底（未知类型不崩、可扩展）。
- **角色**：职责与产出契约以角色行为提示词正文承载（SDR-001）；协作层只引用角色域定义，不为其发明字段。
- **规则**：流转模式（串行/并行/分层）、介入策略、冲突仲裁策略（人裁/lead 裁/多数决）、轮数上限——团队定义的显式组成部分。

### B.3 协作工具面与模式门控 [提案（Rust 侧已按 SDR-003 落地）]

- 协作工具组（团队启动/消息/状态/介入/升级/终止等）**注册但默认对 LLM 隐藏**；宿主经显式的进入/退出协作模式调用整组暴露/收回；模式为会话级、不持久化——重启后回到隐藏态，需再次显式开启。TS 侧现状无对应实现（TS 消费端的协作开关在 v2 后端下无引擎效果，见 context §6）。

### B.4 观测与持久化 [提案]

- 团队/任务/消息三类事件进事件流（durable、可按游标重放），风格对齐既有子代理事件；团队状态与消息历史随会话树持久化（对齐 B.1），恢复语义复用会话恢复机制。

## ADR-001 架构文档分区：现状机制与提案骨架（2026-09-12）

1. **背景与动机**：协作域同时存在"TS 已支持的蜂群模式"与"未落地的团队模型设计"，混排会使 Rust 团队无法区分"须对齐的现状"与"待裁决的设计"，也不符合设计/参考分离的文档治理（现状代码事实归 context）。
2. **决策**：A 部分记录现状机制（Rust 对齐基线的技术形状）；B 部分以 [提案] 标注团队模型架构骨架，受需求 §11 Q1–Q5 约束，裁决前不作为实现依据；file:line 级现状证据一律指向 context。
3. **被否决的备选方案**：a) 只写现状——丢失团队模型设计资产；b) 只写愿景——对齐基线不可用；c) 逐节混排加现状标注——阅读时无法整体区分两类断言，幻觉风险高。
4. **影响范围**：本文档全部；需求文档 §12/§13 与 SDR-004；context §5–§8。

### ADR-002 mirri-collaboration 冻结为实验 Draft；协作开关按后端能力诚实呈现（2026-09-12）

1. **背景与动机**：mirri-collaboration crate 现状为纯台账——合成 agent id、内存态、不驱动任何真实 agent 执行（现状证据见 context §2）；协作域团队模型需求（E1–E7 共 19 个 US）尚待产品评审，本文 B 部分的架构骨架受 Q1–Q5 裁决约束、未定案。评审与裁决完成前补完多 agent 调度属无锚点盲动。同时网页端协作开关在 v2 后端下无任何引擎效果（context §6），构成「存在但无效」的可用性诚实缺陷（违反治理 R5）。
2. **决策**：a) mirri-collaboration **冻结为实验 Draft**——保留协议骨架（8 种消息/角色定义/规则枚举，可作未来回收资产）与 SDR-003 已落地的模式门控（注册但默认隐藏 + 显式进入/退出协作模式）；**不在当前落地程序内补完**多 agent 协作调度，待协作域 19 个 US 产品评审通过后**另立项**实施（届时再裁决协议骨架的回收与重构）。b) 网页协作开关**按后端能力诚实呈现**：连接 v2 后端（无引擎效果）时隐藏/禁用该开关；连接 Rust 后端时保留开关，且确保 SDR-003 的「进入协作模式即整组暴露协作工具」语义真实成立。
3. **被否决的备选方案**：a) 本程序内补完协作调度——产品评审未做、团队模型裁决（Q1–Q5）未定，实现方向无依据；b) 删除 crate——丢弃可回收的协议骨架资产，且模式门控已在其上落地；c) 开关维持现状（v2 下纯客户端 UI 状态）——呈现无效果的功能即「存在但无效」缺陷，违背诚实交付原则。
4. **影响范围**：rust-core-design N2（「collaboration 补完或冻结」二选一——本 ADR 为协作域侧答案：冻结，待评审后另立项）；需求 SDR-003（TS 侧缺口登记维持）、SDR-004；ROADMAP O4/O5；本程序 B10 批次（web 诚实化落地）。
