## 0. 总述

近期三个交付批次（设置页任务面板、创建表单、会话内工具面）落地后，用户对成品做了系统性反馈，点名批评了多个产品决策；随后产品侧做了两轮复审（复审又补充发现若干缺口，如任务不可编辑、空状态无引导），最终用户对每一项改善逐条确认——包括复审补充项与最后一轮确认的审批卡要求。本文是这批裁决的正式落地。

这批改善的整体定位，是**纠正此前产品自造概念的路线**：

- **Scheduled Task（定时任务）**回归「用户委托的例行工作」的简单心智——每次触发新建一个会话去执行，用户在设置页创建、查看、管理它；
- **会话内定时器**回归「Agent 的延时回调」的最小形态——Agent 在会话里说「多久之后提醒我做什么」，一次性、到点即收；
- 两者是完全不同的领域概念，各自独立，**产品面不再保留任何为定时任务自造的概念体系**（自造的权限档位、无人值守姿态、提议-审批包装等全部拆除）。

每一项改善都写明「为什么」——凡有用户原话的，如实引用。

## 1. A 组：Scheduled Task 设置页翻新

> 按用户旅程重排呈现顺序：先立概念（A7），再进入入口与表单（A1→A5、A8、A11、A6），再到列表与管理（A12、A9、A10、A13、A14）。编号保留裁决时的原编号。

### A7 · 概念彻底分离：定时任务与会话内定时器是两个东西

**背景/现状**：当前产品把「用户委托的例行工作」和「Agent 在会话里自计时」混在同一个「定时任务」概念下呈现——设置页的任务面板挂在会话视角下（只看活跃会话的任务）、产品文案里充斥技术词汇「cron」、会话页面还保留了创建会话级定时任务的入口。用户无法分清「我排定的例行工作」和「Agent 自己设的闹钟」是两个不同的东西。

**改善内容**：

- Scheduled Task 由设置页**独立页签**承载，首屏即任务列表与新建入口，不依附任何会话视角；任务列表按工作区分组呈现所有工作区的任务（呈现口径由 A14 修订——不随当前会话/工作区过滤显示范围）；
- 会话内定时器**不设管理页**——它只在所属会话的详情里**只读展示**，因为它是 Agent 的工具行为，不是用户委托的对象；
- 产品文案中「cron」字样全部降级替换为「周期规则」；确实要写技术表达式的**高级场景保留输入能力**，旁边给出示例，但它不是主路径；
- **从产品面删除会话创建路径**——会话内定时器的创建是 Agent 的工具行为，用户不需要也不应该有手动入口。

**目的**：两个概念各自回到本位。用户委托的例行工作是「我的资产」，该有管理页；Agent 的延时提醒是「会话内的行为」，只该被看见、不该被管理。混排让两边都解释不清。

**验收标准**：

- 假如我打开设置页、当页面呈现，那么我能看到一个独立的定时任务页签，点进去首屏就是任务列表（全工作区聚合口径见 A14）和「新建定时任务」入口，全程不出现会话选择或会话筛选。
- 假如一个会话内存在 Agent 设置的定时器、当我在该会话的详情中查看，那么我能看到它的只读展示，且没有任何删除或编辑入口。
- 假如我走完整个创建流程、当所有文案呈现，那么主路径上不出现「cron」字样，一律是「周期规则」；只有在选择高级（表达式）输入时才出现技术表达，且旁边有示例。
- 假如我在会话页面寻找「创建会话级定时任务」的入口、当页面呈现，那么该入口不存在。

### A1 · 创建入口解禁

**背景/现状**：当前必须先在会话页面选中某个会话，「新建定时任务」按钮才可点。但定时任务是工作区资产、不属于任何会话——入口被会话选择绑架，与概念不符（见 A7）。

**改善内容**：设置页的定时任务页随时可点「新建定时任务」，不依赖会话页面的任何选择状态；任务归属的工作区在表单里选。

用户原话：「不管用户在会话页面有没有选择某个会话或者 workspace，都应该能按新建定时任务按钮，在这个页面中选择一个 workspace」。

**目的**：创建入口与任务的真实归属（工作区）对齐，用户不被无关的会话状态卡住。

**验收标准**：

- 假如我没有在任何页面选中过会话或工作区、当我在设置页的定时任务页点击「新建定时任务」，那么创建表单正常打开，不被禁用、不报错、不要求我先去做别的操作。

### A2 · 工作区选项数据源修复

**背景/现状**：创建表单的工作区下拉选项来自「已有定时任务的工作区」。用户建第一个任务之前，下拉是空的——功能等于不可用，属于「存在但残缺」的缺陷。

**改善内容**：下拉选项来自工作区列表，与「新建会话」时的工作区选择同源；默认可预选当前工作区。

**目的**：第一次创建就能顺利完成；用户在哪里能开会话，就在哪里能排任务。

**验收标准**：

- 假如整个产品里还没有任何定时任务、当我打开创建表单，那么工作区下拉列出我的全部工作区，且当前工作区已预选。
- 假如我在表单中切换工作区、当下拉展开，那么选项集合与我在新建会话时看到的工作区一致。

### A3 · 删除「工作目录」输入项

**背景/现状**：创建表单里有一个「工作目录」文本框，让用户手工填写任务运行时的工作目录。这与「任务属于某个工作区」的归属模型冲突：工作区已经决定了目录，再让用户自由填一个目录，既多余又可能填出界外路径。

**改善内容**：表单不再提供「工作目录」项，任务按所选工作区的默认目录运行。

补充裁决：引擎侧（也就是产品背后真正执行任务的那一层程序）对越界工作目录拒绝执行的既有防线**保留**——它防的是绕过产品面直连调用的场景，属于引擎的安全行为，不构成产品概念，本文不展开。

**目的**：表单少一个绝大多数用户不该碰的技术项；任务「在哪里跑」由工作区这一个选择完整回答。

**验收标准**：

- 假如我打开创建表单、当表单呈现，那么不存在「工作目录」输入项；任务建成后实际在所选工作区的默认目录中运行。
- 假如有请求绕过产品面提交一个越界的工作目录、当引擎执行时，那么该任务被拒绝执行（防线是引擎行为，产品面不呈现该概念）。

### A4 · 权限模式原样复用会话的三档

**背景/现状**：当前创建表单为定时任务自造了一套权限体系——「运行姿态三档映射」加一个会话里没有的第四档「只读观察」，还引入了「无人值守」概念。用户为定时任务多学一套只有这里用的权限词汇，且映射关系让「选的名字」和「实际执行的规则」之间存在翻译层。

**改善内容**：表单只提供会话已有的三个权限模式——逐条确认、自动常规、自动通过（yolo）——与新建会话**完全同款、同名、同文案**，不新增任何档位、不引入任何新概念。默认选中档与新建会话的默认一致（用户在哪里看到的三档，缺省也一致）。

用户原话：「我们不需要为这个 scheduled task 重新设计任何会话内的权限控制模式。只提供当前我们已经支持的会话内的权限控制模式即可」「全凭用户自主」。

**目的**：用户已经会用会话的权限模式，定时任务这边零学习成本；同时把「定时任务跑起来是什么权限」的责任完全交还用户自己的选择，产品不做额外的姿态包装。

**验收标准**：

- 假如我在创建表单中查看权限模式、当选择器呈现，那么我看到的选项与新建会话时完全相同（逐条确认 / 自动常规 / 自动通过），名称与说明文案一字不差，没有第四档、没有「无人值守」字样。
- 假如我打开创建表单、当选择器呈现，那么默认选中的档位与新建会话时的默认档一致。
- 假如我以某个权限模式创建任务、当任一次运行发生，那么该次运行按所选模式的规则执法——选了什么就是什么。

### A5 · 三时刻改为「理论推演」

**背景/现状**：当前表单的「上次运行」行查询运行事实，没有记录就显示「尚未运行」。但用户配置日程时想回答的问题是「这个规则到底会在什么时刻触发」，不是「这个还不存在的任务过去跑没跑」——对着一个尚未创建的任务显示「尚未运行」，信息量为零。

**改善内容**：上次/下次/下下次三个时刻**全部是「基于当前频率设置的理论推演」**——假设该日程已经存在，最近的理论触发点是什么、接下来的两次是什么。它帮助用户在提交前认知周期规则的效果。

用户必须知道这是预测、不是事实（用户原话：「从来都不是让你去写事实，而是预测结果，而且用户也得知道这是预测结果」）。

真实的运行事实（真正跑过的上次运行）只在**运行记录/历史**里呈现，两处各归其位：表单与列表常驻位管「预测」，运行记录管「事实」。

呈现细节见 B1（时间轴合并）与 B2（时区标注）。

**目的**：把「三时刻」从「查历史」改造成「验证我的规则」——用户看到理论上的过去、下次、下下次，就能确认自己写的频率是否正确；预测的标签保证用户不会被误导成「已经跑过」。

**验收标准**：

- 假如我在表单中选定一个周期规则（如每天 09:00）、当三时刻呈现，那么我看到的是三个理论推演时刻（最近的理论过去时刻、下次、下下次），而不是「尚未运行」。
- 假如我选定的是一次性规则（只会触发一次的未来任务）、当三时刻呈现，那么没有理论过去时刻，过去位呈现「—」，不虚构一个「已过去」的时点。
- 假如三时刻呈现、当我查看，那么界面明确标注这是「预测 · 基于当前日程推算」，不会让我误以为是运行事实。
- 假如我修改频率设置、当修改完成，那么三时刻立即按新规则重新推演刷新。
- 假如我想知道任务真正跑过的历史、当我打开运行记录，那么我在那里看到真实的运行事实——预测不进历史、事实不进预测，两处不混。

### A8 · 选「自定义」即弹设置窗

**背景/现状**：当前在频率档位里选择「自定义」后，还要再点击一个随后才动态渲染出来的按钮，自定义设置窗才会打开。用户的意图在选择「自定义」那一刻已经明确，多按一次按钮是纯粹的交互摩擦。

用户原话：「按 custom 的时候，用户的意图已经明确了，你还需要用户再按一个你动态渲染出来的按钮，这是一个产品经理该容忍的事情吗？」

**改善内容**：选择「自定义」的瞬间，自定义设置窗直接打开，不再有中间按钮。

**目的**：砍掉一个零价值步骤；选择即表达意图，产品不该让用户确认自己刚刚确认过的东西。

**验收标准**：

- 假如我在频率档位中选择「自定义」、当选择发生，那么自定义设置窗立即自动打开，中间不出现、也不需要任何额外的确认按钮。

### A11 · 表单呈现形态：页面内视图切换

**背景/现状**：创建表单的承载形态此前未裁决，存在抽屉、弹窗、页面切换等多种可能，不同形态各带一套交互惯例。

**改善内容**：采用**设置页内容区内的视图切换**——点击「新建定时任务」后，设置页的内容区切换为表单视图；完成或取消后切回列表视图。与设置页既有页面的模式对齐。

**目的**：不引入新形态；用户在设置页里的导航心智保持一致（进去一层、回来一层），也没有抽屉/弹窗带来的层叠与遮挡。

**验收标准**：

- 假如我点击「新建定时任务」、当操作发生，那么设置页内容区切换为创建表单视图，不出现弹窗或抽屉。
- 假如我完成创建或点击取消、当操作发生，那么内容区切回任务列表视图，新建的任务（若创建成功）已在列表中。

### A6 · 表单打开时收起会话视角

**背景/现状**：当前打开创建表单时，页面上还残留「全部会话 / 当前会话 / 搜索」的筛选条——那是会话列表的视角控件，与正在创建工作区级定时任务的用户毫无关系。

用户原话：「为什么新建定时任务，上面还显示着这些内容？」

**改善内容**：定时任务页不出现会话视角控件；表单视图自然也没有。

**目的**：页面上的每个控件都应与当前任务相关；残留的会话筛选暗示「定时任务属于会话」，与 A7 的概念分离直接矛盾。

**验收标准**：

- 假如我进入定时任务页或打开创建表单、当页面呈现，那么不出现「全部会话 / 当前会话 / 搜索」等任何会话视角的筛选控件。

### A12 · 任务行信息降噪

**背景/现状**：当前任务列表的一行里堆叠了三种权限/存活相关的徽章——无人值守标识、运行姿态、触发条件的双口径标注。用户扫一眼列表，真正需要决策的信息被徽章淹没。

**改善内容**：任务行信息删到只剩用户决策必要的内容（任务是什么、什么频率跑、下次何时跑、是否启用等），权限姿态等明细在详情中按需查看。

**目的**：列表是扫描与决策的界面，不是参数陈列柜；行内信息密度降下来，用户才能快速找到要管的任务。

**验收标准**：

- 假如我查看任务列表、当列表呈现，那么每一行只呈现用户决策必要的信息，不堆叠权限/存活类的多重徽章；行内至少包含任务名、频率、下次运行（预测）、启用状态四项，其余信息项在视觉稿阶段定稿。
- 假如我需要某个任务的权限等明细、当我打开它的详情，那么明细在那里完整可查。

### A9 · 任务编辑与暂停/恢复

**背景/现状**：当前任务只能删除后重建。改一个标题、调一个时间也要走「删了重排」，而重建后的任务与原任务的历史运行记录归属断裂——用户再也查不到「这个例程过去跑过什么」。

**改善内容**：支持**编辑**已有任务（标题、指示、周期规则、执行环境）与**暂停/恢复**；编辑与暂停不改变任务身份，运行历史归属连续。

「执行环境」的可编辑范围：**包括权限模式改档**（如从逐条确认改为自动常规）——权限模式只是任务的一项配置，改档不换任务身份；**工作区归属不可编辑**——把任务挪去另一个工作区等于换了一个任务，历史归属会失真，要「换地方」应删除后新建。

**目的**：例行工作天然需要随时间调整；「删了重排即失忆」逼迫用户在「保持历史」和「改配置」之间二选一，两者都该有。

**验收标准**：

- 假如我编辑某任务的周期规则并保存、当保存完成，那么该任务按新规则继续调度，运行历史保持归属连续——过去的记录仍属于这个任务。
- 假如我暂停某任务、当暂停生效，那么该任务到点不再触发；恢复后按周期规则继续，暂停期间错过的执行不伪装成跑过（历史如实）。
- 假如我编辑任务标题或指示、当保存完成，那么后续运行按新内容执行。
- 假如我编辑任务的执行环境、当保存完成，那么权限模式等环境配置按新值生效，后续运行按新配置执法。
- 假如我尝试修改任务的工作区归属、当编辑表单呈现，那么工作区不可修改（不提供改归属的操作）。

### A10 · 空状态引导

**背景/现状**：用户建第一个定时任务之前，看到的是一个空列表，没有任何说明这个功能是干什么的。

**改善内容**：空状态呈现一句话价值说明——「让助手定时自动执行，如每日 PR 审查」——加引导按钮直达创建表单。

**目的**：第一次到达这个页面的用户在三秒内明白「这里能帮我做什么」并被引导迈出第一步；空列表本身不传递任何价值信息。

**验收标准**：

- 假如所有工作区都还没有任何定时任务、当我进入定时任务页，那么我看到一句话价值说明（含示例，如每日 PR 审查）与一个引导创建的按钮，点击即进入创建表单（空态的触发条件为「所有工作区都没有任务」——A14 聚合口径修订）。

### A13 · 审批待办落点【本节及 §4 依赖表中引用本节的行已被 SDR-126 取代】 （**2026-11-04 SDR-126 取代**：审批现场只有发起创建的会话里的审批卡，任务页不再有「待确认」区。）

**背景/现状**：Agent 发起的定时任务创建请求需要用户审批，但审批待办此前没有明确的归属位置，通知与决策现场混在一起。

**改善内容**：审批待办在**任务页的「待确认」区**呈现——含全参数可读卡片（卡片要求见 C3）；通知只做「有待确认」的提醒，不做决策现场。

弹窗审批与「待确认」区是**同一个审批流的两个呈现现场**，不是两个决策：用户在场时，即时弹出审批窗（C2）；用户未及时响应时，该待办沉淀到任务页的「待确认」区等待处理。时限口径沿用既有审批域裁决——审批不因超时自动失效，引擎不设过期，不发明新的时限。任一时刻一个待办只在一处呈现（弹出中，或已沉淀待确认区，不同时双挂）；无论在哪一处处理（批准或拒绝），待办即从所有现场消失，不存在「弹窗批了、待确认区还挂着」或反向的双账。

**目的**：Agent 发起的创建请求只有一条审批流——在场即时弹窗、离场沉淀待确认区，处理即消失；用户从通知被提醒、到看清参数、做出决定，全程面对的是同一个待办，不产生第二个决策现场。

**验收标准**：

- 假如 Agent 发起了一个定时任务创建请求、当请求到达且我正在使用产品，那么审批窗即时弹出，我可以在那里批准或拒绝（C2）。
- 假如该请求待审批、当我未及时响应弹窗，那么该待办以全参数可读卡片沉淀在任务页的「待确认」区，我在那里仍可批准或拒绝。
- 假如一个待办已被处理（无论在弹窗还是待确认区）、当处理完成，那么它在弹窗与待确认区两处一并消失，不存在残留。
- 假如请求待审批、当通知到达，那么通知只提醒「有待确认」，点开即引导至任务页的待确认区，通知本身不承载决策操作。

### A14 · 任务列表为全工作区聚合视图

**背景/现状**：任务列表只显示「当前会话所在工作区」的任务。用户在表单里选了另一个工作区创建（A2 允许、也是被推荐的用法），创建成功后列表却只看当前工作区——任务实际已建成，但在这个页面「消失」了，用户无从判断创建成功还是失败。管理页把显示范围交给了聊天会话的位置，与「任务是我的资产，这里是我的管理面」的心智（A7）不符。

用户原话（2026-11-03）：「只有我 active session 是对应 workspace 的时候才显示。真实奇葩的傻设计。」

**改善内容**：定时任务页一次显示**所有工作区**的任务，按工作区分组呈现（每组带工作区名标识，当前活动工作区排最前）；不存在「切换了会话/工作区才能看到某些任务」的隐藏状态。当前没有任何任务的工作区不出现分组（不制造空分组噪音）。

**目的**：管理面所见即全部——创建到任何工作区的任务都立刻可见；任务页不再有「看不见的另一半」。

**验收标准**：

- 假如我在页面停在活动工作区 A 的状态下、在表单中选工作区 B 创建任务、当创建成功，那么任务列表立即显示工作区 B 的分组、其中包含我刚创建的任务（工作区 A 的分组若同时存在则并列显示，A 不因创建动作被隐藏）。
- 假如我拥有多个工作区且各自有任务、当我进入定时任务页，那么一个列表内同时看到所有工作区分组，每组有可辨识的工作区名标识，活动工作区排在最前。
- 假如某工作区当前没有任何任务（无论从未创建过、还是已全部删除）、当列表呈现，那么该工作区不出现分组。
- 假如所有工作区都没有任务、当我进入定时任务页，那么呈现空状态引导（A10），文案如实表达「所有工作区都还没有定时任务」的口径。
- 假如创建失败（网络/服务异常）、当失败发生，那么用户收到明确的错误反馈，表单停留在原位不丢失已填内容（区分于成功场景——成功必有可见结果，失败必有可见反馈，两者都不静默）。

## 2. B 组：预测呈现细节

### B1 · 日程预览时间轴

**背景/现状**：三时刻以三行独立文本呈现，过去与未来混排且无视觉区分；「上次」的语义（理论过去）在纯文字下容易被误读为运行事实（A5 的用户知情要求落不到实处）。

**改善内容**：三个时刻合并为**一条时间轴**呈现——理论的过去时刻 → 下次 → 下下次；过去部分用可区分的样式并标注「理论值」；界面明示「预测 · 基于当前日程推算」。

**目的**：时间轴让「这是一个周期规则在时间上的样子」一眼可见；过去段的特殊样式 + 标注，让「这是推演、不是事实」成为视觉层面的常识，而不是一行容易被忽略的小字。

**验收标准**：

- 假如我在表单或常驻位查看三时刻、当呈现，那么三时刻以一条时间轴呈现（过去 → 下次 → 下下次），过去部分样式可区分且带「理论值」标注，整体带「预测 · 基于当前日程推算」的明示。
- 假如频率为高频档（如每小时）、当时间轴呈现，那么「过去时刻」可省略或弱化呈现（「一小时前」的过去点对决策没有信息量），下次与下下次保持完整。
- 假如我修改周期规则、当修改完成，那么时间轴即时按新规则刷新。

### B2 · 时区标注

**背景/现状**：预测时刻若不带时区，桌面与服务器时区不一致时，用户看到的时刻与实际触发时区对不上，造成误导。

**改善内容**：所有预测时刻带时区标注；无论桌面与服务器时区是否一致，呈现的时刻与其标注的时区严格对应。

**目的**：用户对「几点触发」的判断只依赖一个信息——时刻旁边的时区；不存在需要用户脑内换算或猜测服务器时区的场景。

**验收标准**：

- 假如我查看任何预测时刻、当呈现，那么每个时刻旁都带明确的时区标注。
- 假如桌面时区与服务器时区不一致、当我查看预测时刻，那么呈现的时刻与所标时区严格对应，不被服务器时区干扰。

## 3. C 组：工具面重构

> 工具面指「Agent 在会话内可用的能力」。本组是对此前会话工具面的**缩编裁决**：把三个工具与相关防繁殖机制的「用户侧复杂度」整体取代，防线简化为一次性语义本身。
> 缩编后的工具面里，**Agent 不具备编辑或删除既有定时任务的能力**（C2 只能新建、新建必审批）——修改或停用一个任务，只有用户在任务页亲自操作（A9）这一条路径，防止模型在会话内顺着 C4 的引导尝试「帮你改一下任务」。

### C1 · 会话内三件套下线，代之以单一「SetTimer」

**背景/现状**：当前会话内给 Agent 提供了三个工具——**`CronCreate`（创建定时任务）、`CronList`（列出定时任务）、`CronDelete`（删除定时任务）**。这套设计有三个问题：反复触发风险（Agent 可能重复创建同类任务）、表达式易写错导致意外频率（写错一处，任务以错误的频率反复执行）、还需要模型记得事后清理（忘了删，任务一直挂着）。

**改善内容**：会话内只提供**一个**工具「SetTimer」（命名定死，用户已裁决认可，不再留备选、不在架构阶段重开命名讨论）：

- 参数只有两个——「多久之后」（时长）与「到点说什么」；**不可**选择具体时刻、日期或频率；
- **永远只触发一次**——到点触发后自动回收，模型无需、也无法清理；
- 不提供列表、删除工具。

**目的**：把会话内定时器收敛为「延时回调」的最小形态——低心智负担（一个工具、两个参数）、覆盖绝大多数真实需求（如「10 分钟后查一下 CI 结果」）、安全（一次性语义本身杜绝意外反复触发与忘删遗留，不再需要额外的防护机制）。

**验收标准**：

- 假如 Agent 在会话内需要延时提醒、当它调用该工具，那么它只能表达「多久之后 + 到点说什么」，无法设定具体时刻、日期或循环频率。
- 假如一个定时器到点触发、当触发完成后，那么它自动失效，不再触发第二次，也不需要任何清理动作。
- 假如我在会话内盘点 Agent 可用的定时类工具、当工具呈现，那么只有一个 SetTimer——**CronCreate、CronList、CronDelete 三个工具不复存在**。
- 假如 Agent 设置「10 分钟后提醒」、当到点，那么会话收到一次注入的提醒（即系统在到点时自动把这句话送进会话、就像用户发了一条消息那样），内容为 Agent 预先写的「到点说什么」。

### C2 · 「提议」包装下线，代之以「CreateScheduledTask」高危直建

**背景/现状**：当前 Agent 为用户创建工作区定时任务的路径是一套「提议」包装：模型起草提案、系统把提案作为中间产物保存一段时间（72 小时有效）、用户再批准。从用户的角度，创建一个定时任务被拆成两段、中间多出一个「提议」的中间状态，体感莫名其妙。

用户原话：「从用户的角度，这个设计莫名其妙，很烦人。」

**改善内容**：提供「CreateScheduledTask」工具，语义是**真实创建**：

- **任何权限模式**（逐条确认 / 自动常规 / 自动通过）下一律触发系统**既有的高危操作审批**（与其它高危工具同等待遇）——批准即建、拒绝即无；
- 不产生「提议」中间概念，没有中间产物、没有有效期。

**目的**：去掉自造的「提议-审批」概念，回归用户已经理解的「高危操作弹审批」心智——一个动作、一次审批、当场生效或当场作废，没有中间态。

**验收标准**：

- 假如 Agent 在任意权限模式（逐条确认 / 自动常规 / 自动通过）下调用该工具发起创建、当请求到达，那么用户收到与其它高危操作同款的高危审批，全程不出现「提议」「提案」等中间概念与中间状态。
- 假如我批准了该审批、当批准完成，那么定时任务立即创建成功并出现在任务页。
- 假如我拒绝了该审批、当拒绝完成，那么什么都不创建，也没有任何残留的待处理项。

### C3 · 审批卡全参数可读 （**2026-11-04 SDR-126 落实**：一次审批、批准即创建；卡片参数口径不变，呈现现场收敛为聊天审批卡。）

**背景/现状**：高危审批的呈现若只给一个笼统的「Agent 想创建定时任务」，用户无法判断该不该批——看不懂将创建什么，审批就变成无依据的点击。

用户原话：「我得能看出具体创建的所有参数细节，最好能很容易看懂会有什么样的任务以什么样的时间/频率创建出来。」

**改善内容**：审批卡片上**完整展示将创建任务的全部参数**，并用人类语言组织成一句话可读的形式，例如：「每天 09:03（GMT+9）· 在工作区 X · 用模型 Y · 执行：回顾过去 24 小时的提交……」——一眼看懂什么任务、以什么频率、在哪里、用什么被执行。

**目的**：审批的前提是知情；参数不全的审批等于让用户掷硬币。全参数 + 人话组织，把「批不批」变成一个有依据的决定。

**验收标准**：

- 假如 Agent 发起的创建请求进入审批、当审批卡呈现，那么卡片上完整展示该任务的全部参数（周期规则含时区、工作区、模型、指示内容等），并以人类可读的句式组织，不需要任何技术知识就能读懂。
- 假如我读完审批卡、当我做决定，那么我能准确说出「将创建一个什么任务、以什么频率、在哪里跑」——批的是我理解的东西。

### C4 · 模型引导重写

**背景/现状**：当前给模型的工具引导（工具描述）把「会话内定时」与「工作区定时任务」混用同一套 cron 词汇，模型分不清两个场景该用哪个能力，容易在会话内用错工具或用错概念。

**改善内容**：模型工具引导按两概念分界彻底重写——SetTimer 的引导 = 会话内延时提醒（一次性、时长参数）；CreateScheduledTask 的引导 = 工作区例行任务、需用户审批。消除 cron/timer 混用的表述。

**目的**：模型选对工具是全链路的第一环；引导里概念混浊，下游的产品面再清晰也会被上游的误用打穿。

**验收标准**：

- 假如模型阅读 SetTimer 的工具引导、当它需要「会话内延时提醒」时，那么它选择 SetTimer 且只表达时长与到点内容。
- 假如模型阅读 CreateScheduledTask 的工具引导、当它需要「替用户排定例行工作」时，那么它选择 CreateScheduledTask，并知道该操作将触发用户审批。
- 假如任一工具引导呈现、当我通读，那么不存在两个概念混用的表述——每个引导只描述自己那一侧的场景。

**底部**：一行紧凑的内联工具栏，收着工作区 / 权限模式 / 模型 / 思考档四个次要配置——**不带任何字段名称（label），四个选择组件直接并肩排成一行**，紧凑呈现（用户原话：「这些塞进1行，紧凑些，不要label，直接给出选择组件」）；次要配置压到最小空间，不逐项成块。各选择组件当前选中的值本身说明了它是什么（如工作区下拉显示工作区名、权限下拉显示档位名），不需要重复的字段说明文字。

### 列表页基准（自动化首页）

用户另指定了任务列表页（自动化首页）的参考图。以产品语言记录，约束 A12（行内信息）与 A10（空态）的呈现：

**卡片结构**（每张卡片三层信息，从上到下）：

1. **任务标题**——粗体，卡片的主标识；
2. **指示内容**——灰色常规字，最多两到三行、末尾省略截断（完整内容在详情）；
3. **底部元信息行**——两个并列元素：频率与下次运行的合并标注（如「每个工作日 09:00 · 下次 12 小时后」，用可区分的颜色表示进行中/正常），以及运行次数标注（如「已运行 24 次」，灰色统计信息）。

**交互与操作**：

- **卡片上没有任何操作按钮**（无编辑/删除/暂停/开关）——点击卡片进入详情页，编辑、暂停/恢复、运行历史都在详情页完成（详情页形态见下）；

- 筛选 Tab 行 + 右上角的创建按钮（主操作）构成列表页工具栏。

**详情页形态**（承接卡片点击）：顶部为任务标题与状态，Tab 切换「设置 / 历史」——设置 Tab 即任务的全字段（编辑表单，复用创建表单的布局与组件、预填既有值）；历史 Tab 为运行记录（真实运行事实的呈现处，与 A5 的「事实归运行记录」呼应）。

**简洁手法**：

- 卡片上砍掉操作按钮与状态徽章——列表只做浏览，操作进详情；
- 无头像/图标装饰，纯文字驱动；

## 7. 决策记录（SDR）

- **SDR-125（2026-11-04，用户裁决）· 定时运行就是一次普通回合**：用户裁决——定时任务的一次运行，等同于「新建一个会话并发出第一条消息」，不再有独立的「无人值守」运行形态。本决策含三条：
  1. **运行即普通回合**：运行使用任务创建时所选的权限模式（逐条确认 / 自动常规 / 自动通过），之后的审批与手动发消息的会话完全一致；逐条确认的运行遇到需要审批的操作时，停在该运行的会话里等用户处理，不会被系统自动拒绝。
  2. **来源标记**：该会话与其首条消息要能被识别为「由某个定时任务触发」，仅用于展示与追溯，不改变任何权限行为。
  3. **启动记录**：每次运行如实记录——谁触发的（定时 / 立即运行 / 排队接续）、原定触发时间、实际开始时间（二者之差即启动延迟）、是否真的有产出、是否在等待审批。「成功」只在回合正常结束且有助手产出时记；否则记失败并写明原因。
  影响范围：本域 A4（权限三档为运行时唯一执法依据）、B 组（运行记录的启动记录字段）、阶段一「无人值守」系列裁决（SDR-002/003 等任务级声明——已废，glossary CS2 已打退役标记）。
  被否决备选：a）逐条确认遇到审批自动拒绝（即现行无人值守语义）——会让用户所选模式静默降级；b）把等待审批当作运行失败——用户回来点批准后任务本可继续。

- **SDR-126（2026-11-04，用户裁决）· Agent 创建定时任务 = 一次普通审批**：用户裁决——Agent 调用「创建定时任务」工具时，沿用引擎默认的工具审批，不再有为它单独设计的审批体验。含三条：
  1. **一次审批，批准即创建**：用户只会被问一次；批准后任务立即创建并回告 Agent「已创建」；拒绝则什么都不发生。不再出现第二次确认，也不再有「待确认」中间状态。
  2. **审批卡讲人话**：审批卡完整展示将创建的任务——多久跑一次（含时区）、在哪个工作区、用什么权限模式与模型、任务标题、执行的完整指令、是否只跑一次或有次数上限——用户读完就能说出「批的是什么」。
  3. **任何权限模式下都必须经用户确认**（保持 C2 原有强约束）：自动常规、自动通过模式下也不自动放行。
  本决策取代 C2/C3/A13 中「创建请求落到任务页『待确认』区、跨会话沉淀」的部分：设置页不再有「待确认」区，审批现场只有发起它的那个会话里的审批卡。被否决备选：a）保留两次审批（第一次确认调用、第二次确认任务）——同一件事问两遍；b）保留设置页待确认区作为只读入口——审批现场与数据来源仍会分裂，复杂度高且不是用户要的。
