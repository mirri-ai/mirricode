## 0. 领域边界

**产品定位（SDR-009）**：本文服务的是**给 Agent 准备的需求**——agent 在工作中需要「过一会儿回来做某事」的自计时能力：创建 PR 后等 CI 出结果、周期性巡查自己看护的东西、未来的指挥官-工人协作中定期 check 工人动态。这些需求的**自然归属是 session scope**：agent 的工作以会话为单位，它的定时器跟着会话走是正确设计，不是缺陷（SDR-010）。用户的「例行工作委托」需求（每天早上跑一遍体检报告、不依赖我开会话）是另一类需求，由阶段二承载。

**本域覆盖**：定时任务的**调度体系**——任务从哪来（用户直接创建 / 模型代建）、任务怎么活着（存活规则、过期规则）、到点怎么跑（统一调度、忙闲语义、审批姿态）、跑得有没有边界（次数上限）、以及调度总开关的真实性。会话级任务的创建与管理面交互细节沿用后台任务域既有裁决（E11/E12），本域不重定义。

**不在本域**（引用相邻域，不重复定义）：

| 相邻域 | 边界划分 |
|---|---|
| subagent（后台任务与子代理） | 任务**管理面与呈现**（E9/E10 面板、E12 呈现、fork 口径、上限族 N12）与 cron 表达式语义（SDR-005/006/B6-01：时区/jitter/coalesce/stale 投递形态/run-now 不动日程）归彼域；本域管调度体系层——任务的来源标注、存活规则改造、调度归属、审批姿态、开关真实性。拆域理由见 SDR-001。 |
| approval（权限与审批） | 审批策略链本身（什么工具需要问、问谁）归彼域；本域定义「定时触发的回合以什么姿态进入审批链」（无人值守声明如何被消费），不新增策略规则。 |
| turn-scheduling（回合调度） | 回合准入契约（忙则并入、闲则自起）归彼域；定时注入是既有的异步唤醒源之一（L1），本域不改变准入语义，只补齐手动触发对忙闲检查的遵守。 |

## 1. 角色与场景总览

本文的**需求动机是 agent 的自计时场景**（SDR-009/010）——agent 在会话工作中需要三类定时能力：

- **单次延时回访**：Agent 创建 PR 后 CI 要跑几分钟到十几分钟——循环 sleep-poll 是浪费算力和本地资源的笨办法；agent 应能设一个单次定时器（如 10 分钟后注入「确认 PR #xxx 的 CI 结果，有问题分析并修复」），把等待交给调度体系。
- **周期巡查**：agent 看护的长期工作（等 CI、盯发布流程）需要按计划周期性回来查看，而不是每次都靠用户提醒。
- **未来协作预留**：自主协作模式下，指挥官（commander）用周期任务定期 check 其他 Worker Agent 的动态，防止工人跑偏——这是同一能力的协作形态。

这些需求的自然载体是**会话**：agent 的工作发生在会话里，它的计时器跟着会话走（会话开着即有效、关闭后诚实补发）是正确归属，不是缺陷（SDR-010）。

- **A0 · 看护中的 Agent**（动机主体）：正在干活、需要定时回访能力的模型侧消费者。
- **P1 · 看护工作流用户**：接受 agent 建议设定的看护任务（如「挂了叫我」），期望任务在会话存活期间可靠、无人值守地跑、跑偏有硬边界。
- **P2 · 直接排定者**：想自己创建、自己看清每个任务的执行历史与状态的用户。
- **P3 · 成本敏感用户**：担心循环任务失控烧钱——要求次数上限可见、可设、可依赖。
- **P4 · 运维/脚本用户**：用环境变量关停定时子系统的运维场景。

**功能闭环**（每个环节都是验收点，任何一环缺失即闭环未合拢）：

```
创建（用户直建 / 模型代建，带来源与姿态声明）
  → 存活（活跃任务不过期，停摆任务有界过期）
  → 调度（统一调度器驱动，会话忙则等待，闲时注入）
  → 执行（有人值守走审批；无人值守预先拒绝需问询操作）
  → 收尾（次数到达 / TTL 到期 / 用户删除，状态如实）
  → 总控（开关真实生效，文档不撒谎）
```

## 2. Epic A：任务的来源与创建面

作为 P2 用户，我直接创建定时任务，不必须通过模型；作为审批链的消费者，任务的创建来源是明确标注的。

**创建路径审批总览（评审轮 4 落档）**：下表是**全域（两阶段）审批语义的单一入口**——回答「谁在什么场景下建任务、要不要人批」只看这一张表，细则见各行「依据条目」所引条目。

| 创建者与场景 | 任务归属 | 需要审批吗 | 附加约束 | 依据条目 |
|---|---|---|---|---|
| 用户从管理面直建任何任务 | 任意 | 否——用户自己的决定 | — | 阶段二 D.0c |
| 模型建会话级一次性任务（如 10 分钟后查 CI） | 会话 | 否（一次性视同 1 次 ≤ 门槛 3） | — | A.2a |
| 模型建会话级循环任务，声明次数 ≤ 3 | 会话 | 否 | — | A.2a |
| 模型建会话级循环任务，次数 > 3 或未声明上限 | 会话 | 有人时问询<br>・自动执行姿态拒<br>・无人一律拒 | 拒绝回传含改道指引 | A.2a/A.2b |
| 模型在定时触发回合内建循环任务（任何预算/归属） | 任意 | 不允许——一律拒绝 | 不问权限姿态（机械判定） | A.6 |
| 模型在定时触发回合内建一次性会话任务 | 会话 | 否 | 会话内血统链累计上限 12 封顶 | A.6a/A.6b |
| 模型发起工作区任务提议 | 工作区 | 是——必须真人批准 | 任何权限模式无例外 | 阶段二 D.0/SDR-105 |

- **A.1 用户直建**：**假如**我在管理面发起创建、**当**填写计划、提示词、是否循环（及循环任务的最大触发次数）、是否无人值守并提交，**那么**任务立即建立，列表即时可见；创建后其来源固定标注为「用户」，不因后续编辑改变。
- **A.2 模型代建（既有路径保持）**：模型经既有工具创建的任务来源标注为「模型」；创建语义、拒绝条件族（上限、超长、非法表达式）沿用后台任务域既有裁决，本域不放松。
- **A.2a 模型代建的审批门槛（SDR-006）**：**假如**模型创建的是一个预算不超过代建门槛（声明触发次数 ≤ 3，或一次性任务——一次性视同已声明 1 次）、**当**创建提交，**那么**直接放行（不打扰用户，一次提醒与短看护是代建的正当主场）。**假如**声明预算超过门槛或未声明预算（无上限循环）、**当**创建提交，**那么**按当时权限姿态分流：有人应答的姿态（手动确认、免点击放行）呈现审批问询——用户可批可拒；自动执行姿态**拒绝**并回传可行动的失败回执（告知门槛值、该姿态下更高预算不可达成、以及改道路径：建符合门槛的任务并告知用户、或请用户从管理面直建）；无人在场一律**拒绝**（无人审批的放行等于绕过审批面）。门槛值为固定基准（3 次），不提供配置项。
- **A.2b 拒绝是回执不是惩罚**：超门槛被拒的回执文案与回执形态沿用无人值守的改道语义（D.5）——模型在同回合改道（建合规任务、告知用户）是常态预期；拒绝不触发额外告警。
- **A.3 来源如实展示**：任务列表的每一项呈现来源（用户 / 模型）；来源是消费端姿态（审批链、展示）的判定输入之一，不是装饰性标签。
- **A.4 循环默认改判（SDR-003）**：模型经工具创建任务时，未声明是否循环的，默认**一次性**（不循环）——缺省解析到便宜错误侧：漏标循环的任务不会无限跑下去。恢复读取旧记录时无此字段的，同样按一次性处理。用户直建面的默认值与文案随本裁决同步。
- **A.5 次数上限可选**：循环任务创建时可设定最大触发次数（正整数，可选）；一次性任务无此参数（天然一次，代建审批门槛视同已声明 1 次）。达到上限后任务按 F.1 收尾。
- **A.6 血统防线：cron 注入回合内拒绝创建**循环**定时任务（SDR-007；SDR-106 收窄）**：**假如**一次定时任务的触发回合内、模型调用创建定时任务的操作、**当**该操作提交，**那么**创建**循环任务**（无论归属、无论预算）一律**拒绝**（机械判定：回合来源为定时注入即拒，不做意图推断）并回传失败回执——说明定时回合不可创建循环任务、已有任务可经删除操作清理；创建**一次性会话任务**（不循环、声明触发次数不超过代建门槛——一次性视同 1 次）**允许**（SDR-106 自计时豁免，见 A.6a——另受 A.6b 血统链累计上限封顶）。理由：单任务的次数上限只约束一个任务的**生命周期**，不约束**血统**——有上限的循环任务在触发回合内仍可以再建新任务，形成繁殖放大；「回合来源为定时注入」是可以机械判定的事实，是所有防繁殖护栏中最可靠的一条。
- **A.6a 执行会话内自计时豁免（SDR-106）**：**假如**一个定时任务的触发回合（或其派生子代理的回合）内、模型想创建一个**单次**的回访定时器（如工作区任务的执行会话里建完 PR，想 10 分钟后确认 CI 结果）、**当**该创建请求是**会话归属、一次性（recurring=false）、预算不超代建门槛（一次性视同 1 次 ≤ 3）**、且本会话内 cron 血统创建的一次性任务累计未超血统链累计上限（A.6b），**那么**放行创建；**任何循环任务**（含低预算循环）仍被拒绝。理由：CI 回访类自计时是本域的核心动机场景（§1），工作区任务的执行会话内同样需要；但一次性任务**并非结构上安全**——可串行链（A 触发后自删前建 B，B 再建 C，每次都是新预算 1，活跃数恒为 1，「每会话 ≤ 50 活跃上限」对恒为 1 的活跃数无效），构成分钟级无休止无人值守循环的可达路径，故须由 A.6b 累计上限封顶。
- **A.6b 血统链累计上限（SDR-106）**：**假如**本会话内经 cron 血统回合（含其派生子代理回合）创建的一次性任务已达累计上限（常量，初值 12——足够 CI 回访等正当场景，远低于可构成滥用循环的量级；具体数值实施可调）、**当**血统回合内再发起一次性任务创建，**那么**拒绝并回传失败回执（说明累计已达上限、指引改道：请用户接管）。机械判定：血统回合发起的创建计数是可数的（创建时回合来源可查）。被否决备选：a) 收回豁免、血统防线全灭（牺牲 CI 回访核心场景）；b) 对豁免任务设最短延时下限（延时不在判定条件内——不可判定的输入进不了机械检查，且易被规避）。

## 3. Epic B：存活规则（stale 改造）

作为 P1 用户，正常运行的长期任务不会周期性死亡；停摆的任务有界可期。

- **B.1 活跃不过期**：**假如**一个循环任务持续正常触发（调度器在跑、注入在发生），**当**它度过了自创建起第 7 天、第 70 天、第 700 天，**那么**它**不会**因「创建太久了」而过期——存活上限从**最近一次成功触发**起算。
- **B.2 停摆有界**：**假如**一个循环任务超过存活上限（自最近一次触发起）未再触发（计划停摆、注入持续失败或调度不可达），**当**它下一次被调度检查到，**那么**执行一次带「过期」标记的最终触发（沿用既有 stale 终信号形态与信封，模型可决定是否续命重建），随后任务收尾移除。
- **B.3 一次性任务不变**：一次性任务仍按其一次触发规则自删，存活上限不适用于它（沿用既有裁决）。**未触发即会话终结的清理（评审轮 3）**：**假如**一个一次性任务在其会话被删除前从未触发、**当**其所属会话被删除，**那么**该任务随会话级联清除（沿用既有级联裁决——不产生「等待一个永不打开的会话」的悬置任务）；会话仅关闭未删除时任务保留、重开补发（C.2/C.4 口径），不为一次性任务另设「会话永不重开」的独立清理计时（会话生命周期即其边界）。
- **B.4 过期信号语义保持**：最终触发的信封中「过期」标记语义、呈现与模型续命路径沿用既有约定（后台任务域裁决），本域只改判定基准（从「创建时间」到「最近触发时间」），不改信号形态。

## 4. Epic C：调度体系与忙闲一致性

作为用户，任务调度由一个统一的东西驱动，手动与自动触发遵守同一忙闲纪律。

**Session scope 归属（SDR-010）**：会话级任务的注入发生在其所属存活会话内——这是 agent 计时需求的**设计归属**而非缺口。本 Epic 的 #180 相关条目（C.2/C.4/E.5）修复的不是「任务要脱离会话」（那是阶段二的用户需求），而是**诚实性**：不活跃时任务不触发这一事实要**可见**（不能静默失约）、错过要**可追溯**（补发可期）、文档承诺要与真实触发条件**一致**。

- **C.1 统一调度器**：全部定时任务的到点检查由**服务级调度器**统一驱动——一个驱动循环覆盖服务内全部任务归属面（会话级任务仍只在存活会话内注入，调度检查上提但注入目标不变）。服务运行即有调度；不因某会话关闭而丢失对其他任务的调度。其需求表述定位为：**让已打开的活会话的任务在应用存活期间可靠触发**（driver 时钟上提的服务级化），不为进程外存活承诺背书（那是阶段二以后的独立裁决）。
- **C.2 会话级任务的存在面**：会话级任务的注入仍发生在其所属存活会话内（阶段一不变更归属模型）；会话未打开时任务不注入、**但不静默失约**——该事实在任务列表可见（E.5），重开后按既有补发规则继续。文档对「关闭界面 / 退出进程」两种场景的承诺按此口径如实修订（见 D-M4）。
- **C.2a 迟到投递携带迟到标记（评审轮 3）**：**假如**一个单次任务在错过 N 个调度周期后才补发（会话忙碌、服务重启等原因）、**当**它最终注入，**那么**注入信封携带**迟到标记**（错过时长）——模型可自行判断任务是否仍然相关（如「10 分钟后查 CI」迟到 2 小时后注入，模型可判断 CI 早已出结果、直接查即可）；**不静默作废**（保留 agent 的判断权，作废是把判断权从模型收走的过度设计）。迟到阈值 N 与标记口径实施时与既有补发（coalesce）规则对表。
- **C.3 手动触发守纪律（SDR-004）**：**假如**一个会话正处于忙碌（回合进行中）、**当**我在管理面对其任务执行「立即运行一次」，**那么**该次触发与自然触发一样被挂起等待空闲注入（run-now 不动日程的既有裁决不变），**不会**与运行中的回合并发闯入。空闲会话中手动触发立即注入（既有行为）。
- **C.4 挂起不永久丢失（会话关闭场景）**：**假如**会话关闭时有挂起未注入的触发、**当**该会话被重新打开，**那么**挂起的触发按既有补发（合并）规则投递——「关掉就永久丢失」不再是设计选择；**当**该会话被永久删除，**那么**其挂起触发随任务一并清除（级联既有裁决不变）。
- **C.5 调度可观测**：调度器的每次检查与每次任务的触发（自然 / 手动）产生既有事件（`cron.fired`），事件携带完整的任务元数据（来源、计数、过期标记、合并次数），消费端无需反查即可呈现。

## 5. Epic D：无人值守执行姿态（核心裁决，SDR-002）

作为 P1 用户，我的看护任务在没人盯着的时候**要么预先改道、要么干脆完成**，绝不挂死到超时。

- **D.1 声明式无人值守**：任务创建时（用户直建或模型代建）声明该任务是否无人值守运行。核心原则：**不猜「人在不在」**——系统不在触发时刻探测用户是否在场（探测不可靠且语义含糊），只依据创建时的显式声明。
- **D.2 无人值守下的问询处理**：**假如**一个无人值守任务的触发回合中，模型调用了需要用户问询（审批）的操作、**当**问询到达审批链，**那么**该操作**立即**被拒绝并回传工具失败（拒绝理由明确告知模型「本任务无人值守，问询类操作不可用，请改用不需要问询的方式完成或放弃该步骤」），模型在**同一个回合内**自行改道——不挂起、不等待、不占回合直到超时。
- **D.3 有人值守保持现状**：未声明无人值守的任务，触发回合的问询走既有审批面（用户在场应答）；声明不影响会话内其他回合（用户手打的、其他任务注入的）。
- **D.4 声明的可见与可改**：任务的无人值守声明在任务列表中可见；**假如**用户后来想改、**当**他编辑该声明，**那么**下一次触发即按新姿态执行（任务级声明，非全局开关——一个会话内可并存两种姿态的任务）。
- **D.5 拒绝是回执不是惩罚**：无人值守下的拒绝回执**不**导致任务被删、不触发额外告警风暴；模型在同回合改道是常态预期。回执文案让模型能理解约束并继续工作。
- **D.6 审批模式的选择性（阶段一收窄）**：阶段一的无人值守姿态只定义「问询一律拒」这一档；更细的姿态（如「按策略白名单放行」）留待阶段二随权限模式选择一起裁决（见阶段二文档 Epic D），本阶段不预设。

## 6. Epic E：管理面与总开关

作为 P2/P4 用户，我直接管理任务，并且总开关是真实的。

- **E.1 用户创建入口**：管理面（web 设置的定时任务面板）提供创建入口——计划、提示词、循环与次数上限、无人值守声明；创建结果与模型代建的任务在同一列表统一管理。
- **E.2 列表信息补全**：任务列表在既有列（计划、下次触发、是否循环等）之上补充：来源（用户 / 模型）、已触发次数（及设定了上限时的「n / 上限」）、无人值守声明。
- **E.3 触发计数如实**：**假如**一个设定了最大触发次数 5 的任务已触发 5 次、**当**第 5 次注入完成，**那么**任务收尾（收尾形态见 F.1），列表中它以「已完成（次数到达）」终态呈现，不再出现在活跃任务中；计数从创建起算，补发的合并触发按既有合并计为一次。
- **E.4 总开关真实（D-M6）**：**假如**我设置 `MIRRICODE_DISABLE_CRON=1`、**当**服务以此环境启动，**那么**定时子系统整体停摆：模型创建工具拒绝新任务（报「定时任务已禁用」）、既有任务不再触发、调度器不进入检查循环；列表读取仍可用（如实显示任务与「已禁用」状态）。解除后服务重启即恢复。该开关当前名不副实的现状证据见 context §4（幽灵开关小节），本条把用户文档的既有承诺兑现为真实行为（裁决过程见 D-M6 与 ADR-006）。
- **E.5 跨会话可见性：从一个地方看到全部任务（SDR-008）**：**假如**我打开管理面的任务列表、**当**列表呈现，**那么**我看到的不是「当前打开会话的任务」，而是**全部定时任务的聚合视图**——不依赖我恰好打开某个特定会话；每项呈现其真实投递条件：计划（下次触发）、归属（所属会话，未打开的如实标注「未打开——打开该会话后触发/补发」）、来源、计数、姿态。理由（#180 诚实性核心）：「有没有人提醒我」的答案不应取决于我开着哪个会话；任务藏在未打开的会话里、列表空空如也，用户会误判任务从未创建——这是对信任伤害最大的失败形态。聚合视图按会话归组展示（投递条件的真实口径沿用 C.2：会话级任务的注入仍依赖其会话存活），不改归属模型——可见性是全局的，投递是会话级的，两者如实分开呈现。

## 7. Epic F：任务收尾与状态如实

- **F.1 收尾形态统一**：任务的收尾原因有且只有四种——**一次性完成**（一次触发后自删，既有）、**次数到达**（max_fires 耗尽，新）、**存活到期**（TTL 耗尽，B.2 终触发后删）、**用户/模型删除**（既有）。每种收尾在事件与列表呈现中如实标注，不互相冒充。
- **F.2 收尾信号给模型**：因次数到达或存活到期收尾的**最后一次触发**，信封中携带对应标记（计数到达 / 过期），模型可告知用户任务已按设定完成——沿用既有 stale 终信号的信封形态，新增计满标记。
- **F.3 终态可查**：收尾的任务从活跃列表消失，但其收尾事实（原因、时间）在任务事件的观测流中可查（阶段二的运行历史承载完整查询面，见阶段二文档）。

## 8. 契约级裁决（阶段一）

- **D-M1 调度归属上提、注入归属不变**：到点检查上提到服务级调度器（唯一驱动循环）；会话级任务的注入仍只在所属存活会话发生。被否决备选：a) 保持每会话独立驱动并另加全局巡检（两套时钟、竞态与补发语义割裂）；b) 阶段一就把注入也上提（无会话运行时形态，属阶段二）。
- **D-M2 声明式无人值守（SDR-002）**：无人值守是**任务创建时的显式声明**，触发时刻不做任何「人在不在」探测。被否决备选：a) 触发时刻探测用户活跃（超时不可靠、误判代价双向：有人被判无人 → 拒绝误伤；无人被判有人 → 挂死依旧）；b) 按会话是否打开界面推断（桌面/web/无头多形态下语义含糊）；c) 无人值守一律预放行（安全倒退，问询类操作无人审批时放行等于绕过审批面）。
- **D-M3 无人值守 = 问询一律拒（SDR-002）**：该姿态下问询类操作**立即拒绝并回传工具失败**，模型同回合改道；不引入白名单放行档（阶段二再裁决）。被否决备选：a) 挂起等超时（现状——挂死 300s，资源浪费且无产出）；b) 按操作类型选择性放行（阶段一无裁决依据，先立最保守档）。
- **D-M4 生命周期承诺如实化**：用户文档对定时任务的承诺按真实能力修订——「关闭界面」= 任务保留、重开补发（既有）；「退出进程」= 任务随进程停止、重启后经会话恢复继续（既有，但调度器上提后表述统一为服务级）；不再用含糊的「closing the UI is fine」覆盖两种场景。被否决备选：阶段一承诺进程外存活（那是新存储与守护形态，属阶段二以后的独立裁决）。
- **D-M5 存活上限改判基准（SDR-005 前置）**：循环任务的过期基准从「创建时间」改为「最近一次成功触发时间」（fire-refresh 口径）。被否决备选：a) 每 TTL 需模型续命（看护类任务的正常态不该要求续命仪式）；b) 一次性大 TTL（治标——停摆任务过期不可期的问题依旧）。
- **D-M6 总开关：兑现而非删除（ADR-006）**：`MIRRICODE_DISABLE_CRON` 名不副实的现状证据见 context §4.1——裁决为**实现该开关**（创建拒绝 + 调度停摆 + 列表如实），而非删除文档承诺。被否决备选：删除文档（否——运维关停是真实场景，且文档已公开承诺，删承诺是能力倒退的信号；实现成本经 ADR-006 评估为一批内可完成）。
- **D-M7 触发计数为投递口径**：fire count 按**成功注入**计（补发合并计一次，run-now 不计数——run-now 不动日程的既有裁决推论）。被否决备选：按日程时刻计数（调度不可达期间计数照走，max_fires 语义失真）。
- **D-M8 模型代建审批门槛（SDR-006）**：门槛按**声明触发次数**判定——≤3 或一次性（视同 1 次）直接放行；超门槛或未声明上限按姿态分流（有人问询、自动执行拒绝回传改道指引、无人在场拒绝）。门槛为常量基准（N=3），不提供用户配置。被否决备选：a) N 可配置（配置项会诱导「调大即解决」，安全门槛失效）；b) 门槛只看是否循环不看次数（误伤一次性提醒，且不设界）。#179 的四个开放问题同步裁决：会话级累计上限初版**不做强制门**（按姿态分流的门槛已覆盖最危险路径：无上限与高预算必然问询或被拒；累计上限属「更紧」方向，待实施反馈再议；血统链上的累计风险已由 SDR-106 血统链累计上限专项兜底）；模型自述创建理由**可选**（只作展示与审计，永不放宽门槛——自报不可作为安全依据）；一次性视同声明 1 次（最常见的「十分钟后提醒我」不该被打断）。
- **D-M9 cron 注入回合内拒绝创建**循环**定时任务（SDR-007；SDR-106 收窄）**：回合来源为定时注入时，创建**循环任务**一律拒绝（机械判定，不做意图推断、不问权限姿态）；**一次性会话任务且预算不超代建门槛**放行（A.6a 自计时豁免），但会话内 cron 血统创建的一次性任务受**血统链累计上限**封顶（A.6b，常量初值 12、实施可调）——超限拒绝。被否决备选：改为审批问询（cron 回合常无人值守，问询即挂死——违背 Epic D 原则；且机械拒绝比意图推断可靠）；SDR-106 层面的被否决备选见该记录（全灭 / 完全豁免 / 延时下限）。

## 10. SDR 记录（阶段一）

- **SDR-001（2026-10-30）**：建域——cron 子系统从后台任务域拆出。背景：定时任务的调度体系（来源、存活规则、调度归属、审批姿态、总开关）与后台任务管理面是两层关注点；#177/#179/#180/#181 四个 issue 的裁决全部落在调度体系层，继续堆在 subagent 域会使该域承载两套异质语义。既有裁决（表达式、时区、jitter、coalesce、run-now、fork 口径、上限族）**沿用不重定义**，归属仍在原裁决处，本域引用。决策：新建 cron-scheduling 域，两阶段（cron-attended → cron-workspace-scope）；域内术语见 glossary CS 节。被否决备选：a) 继续在 subagent 域内扩展（两套语义混杂，评审半径过大）；b) 把调度体系拆到 turn-scheduling 域（那是回合准入，不是任务调度）。影响范围：本套件全部文档。
- **SDR-002（2026-10-30）**：无人值守语义 = 创建时显式声明 + 问询一律拒 + 回传改道。背景：现状下 cron 注入回合与交互回合同路，无人值守时任何需审批的工具挂死到回合超时（300s 量级）；探测「人在不在」不可靠（有人被误判为无人 → 拒绝误伤；反之挂死依旧），语义上只能显式声明。决策：任务级无人值守声明（D.1）；该姿态下问询立即拒绝、回传工具失败含改道指引，模型同回合改道（D.2/D.3/D.5）；阶段一只有这一档姿态（D.6 阶段二扩展）。机制（回合来源经权限链 plumb-through、问询拒绝语义泛化）见架构 ADR-001/ADR-002。被否决备选：a) 触发时刻探测在场（不可靠）；b) 按界面形态推断（多端语义含糊）；c) 无人值守放行（安全倒退）。影响范围：Epic D 全部、V5/V6、架构 §4、approval 域联动（不新增策略，消费新姿态）。
- **SDR-003（2026-10-30）**：模型创建的循环缺省改判为一次性。背景：创建入口对「是否循环」的缺省解析，工具层与恢复读取层不一致（一层缺省循环、一层缺省一次性，详见 context §1）；缺省应解析到便宜错误侧——漏标一次性，用户损失的只是一次提醒（可重发）；漏标循环，用户损失的是无限次执行与费用。决策：工具层默认一次性（#178 用户裁决，2026-10-29）；恢复层保持缺省一次性（两层一致）；用户文档同步。行为变更，changeset 待定（默认 minor，待用户复核）。被否决备选：保持循环缺省（烧钱侧解析，不对称论证不成立）。影响范围：A.4、V7、架构工具契约节、用户文档 tools.md。
- **SDR-004（2026-10-30）**：cron.trigger 补忙闲纪律。背景：手动触发直接走注入路径，无 busy gate——忙碌会话中被手动触发会与运行中回合并发投递，与自然触发的 held-until-idle 语义相悖（#177 发现）。决策：手动触发与自然触发共用同一忙闲检查（C.3）；run-now 不动日程的既有裁决（SDR-B6-01 D-2）不变——挂起等待不等于游标推进。被否决备选：手动触发保持直插（「看看能不能跑」的语义不值得破坏回合单飞不变量）。影响范围：C.3、V3、架构 §3。
- **SDR-005（2026-10-30）**：存活上限改为 fire-refresh 口径。背景：stale 7 天从 created_at 起算不随触发重置——长期看护任务每 7 天死一次，是 #181 的核心产品问题之一；模型虽有续命路径（终触发后重建），但正常运行的活跃任务不该需要续命仪式。决策：基准改为最近一次成功触发时间（D-M5）；停摆任务仍有过期出口（B.2 终触发形态沿用）。被否决备选：a) 模型显式续命（仪式负担）；b) 单次大 TTL（停摆不可期问题依旧）。影响范围：Epic B、V2、架构 §5。
- **SDR-006（2026-10-30）**：模型代建按声明触发次数设审批门槛（#179 核心主张）。**范围限定（2026-10-31 用户裁决补充）：本门槛仅适用于会话级任务（agent 自计时）；工作区归属任务的工具入口不走此门槛，改走提议-审批（阶段二 SDR-105）。**背景：模型代建的循环任务无成本上限也无审批门槛——跑偏的模型可代建无限跑的任务，在自动执行姿态下创建更是无人过问；「这个任务会跑多少次」在创建时刻是可声明的，理应成为门槛的判定输入。决策（A.2a/A.2b、D-M8）：门槛 N=3——声明触发次数 ≤N 或一次性任务（视同 1 次）直接放行；超预算或未声明上限：有人值守问询、自动执行拒绝并回传改道指引、无人在场一律拒绝；N 为常量不配置。#179 四个开放问题同批裁决：会话级累计上限初版不做强制门、创建理由可选仅作展示、一次性视同 1 次、N 不可配。被否决备选：a) 门槛不区分声明预算一刀切问询（误伤一次性提醒的正当主场）；b) 门槛交给模型自律（软约束，跑偏模型正是不可依赖方）；c) session 级累计强制门初版落地（更紧但初版复杂度不成比例；血统链上的累计已由 SDR-106 累计上限覆盖，非血统累计待数据）。影响范围：A.2a/A.2b、V7a、架构 §2/§4。
- **SDR-007（2026-10-30；2026-10-31 被 SDR-106 收窄）**：cron 注入回合内拒绝创建**循环**定时任务（#179 §4）。背景：单任务次数上限只约束生命周期不约束血统——一个有上限的任务在触发回合内仍可再建新任务，繁殖放大不受限；「回合来源为定时注入」是机械可判定的事实（无需推断谁授权、意图为何），是最可靠的防繁殖护栏。决策（A.6、D-M9）：cron 注入回合内创建**循环任务**一律拒绝并回传失败说明，不问权限姿态；原「一律拒绝（无例外）」口径被 SDR-106 收窄为「循环任务拒绝、一次性会话任务（预算不超代建门槛）放行」。被否决备选：a) 改为审批问询（cron 回合常无人值守，问询即挂死，违背 SDR-002 原则）；b) 允许但计入门槛（血统繁殖经多次小额任务照样放大，门槛管不住血统）。影响范围：A.6/A.6a、V7b、架构 §4.4。
- **SDR-008（2026-10-30）**：任务列表跨会话聚合可见（#180 验收第一条）。背景：列表只看活跃会话时，任务藏在未打开的会话里，用户核对「提醒到底建没建」得到的是空列表——可见性缺口与投递缺口（C.2/D-M4）是两个问题，前者修复成本极低且是信任问题的第一现场。决策（E.5）：管理面任务列表聚合呈现全部任务（分属各会话的归组展示），每项呈现真实投递条件；**只改可见性，不改投递**——会话级任务的注入仍依赖会话存活（阶段一归属模型不变，SDR-010 确认该归属为正确设计），未打开会话的任务如实标注状态而非隐藏。被否决备选：a) 列表维持活跃会话视角（#180 明确判为缺陷：答案依赖打开哪个会话）；b) 借可见性改造顺带把投递也上提到进程级（那是阶段二 scope 的裁决，混在一起评审半径失控）。影响范围：E.5、V8a、架构 §6。
- **SDR-009（2026-10-31，用户裁决）**：两类需求定性分离——阶段一（#179/#180）是「给 Agent 准备的需求」（agent 自计时能力），阶段二（#181）是「用户的产品化需求」（用户委托的例行工作），两者是不同角度的不同需求，不是同一问题的递进层。背景：v1 建域时把阶段一定位成阶段二的地基（「阶段二依赖阶段一」），理由之一是共享机制；但产品层面两者的动机主体不同——agent 的定时需求（单次延时回访、周期巡查、协作 check）天然发生在会话工作流内，用户的例行委托需求天然要求脱离任何会话。决策：a) 阶段一需求动机全部改写为 agent 场景（§0/§1）；b) 两阶段共享**技术基建**（权限接线、统一调度器、存活规则、数据模型扩展）但**产品定位独立陈述**；c) 阶段二文档不再以「依赖并扩展本文」定位，改为「复用基建、独立定位」。被否决备选：a) 维持「地基-上层」叙事（把 agent 计时矮化成 workspace 任务的前置件，需求动机失真，验收主体错位）；b) 两类需求合并成单一阶段（agent 计时与用户委托的验收主体、权限模型、生命周期承诺完全不同，合并评审半径失控）。影响范围：本文档头部与 §0/§1、阶段二文档头部与 §0/§1、ROADMAP 依赖关系节、glossary CS 节域定位描述。
- **SDR-010（2026-10-31，用户裁决）**：session scope 是 agent 计时需求的正确归属；#180 的修复范围聚焦为诚实性。背景：v1 曾把「任务绑定会话、应用/会话不活跃即不触发」当作需要「解放」的缺陷（为 workspace 任务铺路的叙事）；用户裁决——agent 的定时需求（单次延时触发、周期巡查）保留在 session scope 内是合理设计，不是缺陷。具体动机场景：Agent 创建 PR 后 CI 要跑几分钟到十几分钟，循环 sleep-poll 浪费算力与本地资源，agent 应设单次定时器（如 10 分钟后注入「确认 PR #xxx 的 CI 结果，有问题分析并修复」）；未来的自主协作模式中，指挥官用周期任务定期 check 其他 Worker Agent 动态、防跑偏。决策：a) #180 相关条目的修复范围校准为**诚实性**——应用/会话不活跃时任务不触发这一事实要可见（现状静默失约）、错过要可追溯（coalesce 补发）、文档承诺要与真实触发条件一致（C.2/C.4/D-M4/E.5 表述同步）；b) 统一调度器的需求表述改为「让已打开的活会话的任务在应用存活期间可靠触发」（C.1），不为「任务脱离会话」背书；c) 会话归属模型在本文档范围内**不再是待修缺陷**，任务脱离会话的需求归阶段二（用户委托场景）。被否决备选：a) 把 agent 计时也上提到 workspace 归属（agent 的回访对象就在会话里——CI 结果回注入对话、协作 check 面向会话中的 worker，上提反而割裂语境）；b) 维持 v1 的「解放任务」叙事（需求动机与真实用户裁决不符）。影响范围：§0/§1/§4（C.1/C.2）、E.5 理由句、阶段二文档定位节、ROADMAP 依赖关系节。
- **SDR-106（2026-10-31，评审轮 3 用户裁决；同日复核修订）**：血统防线收窄——执行会话内自计时的受控豁免（收窄 SDR-007）。背景：评审发现场景冲突——工作区任务（阶段二）的执行会话中，agent 建完 PR 想设 10 分钟 CI 回访定时器，被血统防线（SDR-007「cron 注入回合内一律拒绝」）拦下；但该场景正是本域阶段一的核心动机场景（SDR-009/010：CI 回访自计时），工作区任务的运行中同样需要。分析：血统繁殖的**主引擎**是**循环任务**——循环任务在触发回合内再建循环任务，链条才能自续；一次性任务**并非结构上安全**——可串行链（A 触发后自删前建 B，B 再建 C，每次都是新预算 1，活跃数恒为 1，「每会话 ≤ 50 活跃上限」对恒为 1 的活跃数无效），构成分钟级无休止无人值守循环的可达路径，须另设封顶。决策（A.6a/A.6b、D-M9 修订）：cron 注入回合（含其派生子代理回合——传播规则见架构 ADR-001 补充）内，允许创建**会话归属、一次性（recurring=false）、预算不超代建门槛（一次性视同 1 次 ≤3）**的任务，但会话内 cron 血统创建的一次性任务受**血统链累计上限**封顶（常量，初值 12——足够 CI 回访等正当场景，远低于可构成滥用循环的量级；具体数值实施可调），超限即拒绝（机械判定：血统回合发起的创建计数是可数的）；**任何循环任务**（无论归属、无论预算）仍一律拒绝——防线从「拒绝一切创建」收窄为「拒绝循环创建」，防繁殖语义由循环拒绝 + 累计上限双门共同承载。被否决备选：a) 血统防线全灭不动（牺牲 CI 回访这一核心动机场景——工作区任务的执行会话反而失去自计时能力，倒挂）；b) 对执行会话完全豁免（打开繁殖口子——执行会话内的循环任务创建正是「任务生任务」最顺手的通道）；c) 对豁免任务设最短延时下限（延时不在判定条件内——不可判定的输入进不了机械检查，且长延时的串行链照样构成无休止循环，易规避）。影响范围：A.6/A.6a/A.6b、D-M9、V7b、阶段二 D.0d、glossary CS6 同名异义警示段、架构 §4.4/ADR-011 联动标注。

## 11. 未来增强提案（非本批能力）

- **P-CS1 计划内活跃心跳检测**：TTL 判定之外，区分「计划停摆」与「调度健康但注入持续失败」两种停摆形态，前者静默过期、后者告警——待观测数据支持再裁决。
- **P-CS2 任务级权限白名单档**：无人值守的第二档姿态——按任务声明白名单放行特定操作（阶段二 Epic D 承接，此处预登记）。
- **P-CS3 调度精度可配**：调度器 tick 的可配置化（现固定值）；无诉求不动。
