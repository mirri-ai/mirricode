# 定时任务（cron-scheduling）架构文档

> 本文档描述定时任务域的实现机制、接口形状与数据流；动机保持抽象（不含代码事实），现状依据见 [cron-scheduling-context.md](cron-scheduling-context.md)（下称「context 文档」）。需求见 [cron-scheduling-requirements.md](cron-scheduling-requirements.md)（下称「阶段一需求」，裁决编号 D-M* 沿用其 §8）与 [cron-workspace-scope-requirements.md](cron-workspace-scope-requirements.md)（下称「阶段二需求」，其 D-M* 编号独立）。
> 运行目标为 Rust core + web；TS core 退役线不承载本域。
> 修订（2026-11-03）：存储介质裁决 ADR-020（SQLite 单表）取代 ADR-007（工作区级 JSON 单文件）；任务页聚合呈现口径修订（cron-improvement A14——列表不随活动工作区过滤）。

## 0. 架构总览

```
├─ 消费层 ─────────────────────────────────────────────────────────┐
│ web 定时任务面板（阶段一：cron.add RPC 用户直建 + 列表信息补全；    │
│   阶段二：工作区任务列 / 运行记录 / 权限姿态选择）                  │
│ 模型工具（CronCreate/List/Delete——沿用，来源自动标 agent；              │
│   ScheduledTaskPropose（原名 CronPropose）——阶段二提议工具，   │
│   工作区草案专用入口，§9.3）                                        │
├─ 服务层（embedded server 内）──────────────────────────────────────┤
│ CronScheduler（服务级统一调度循环——ADR-003）                        │
│   ├─ 到点检查（复用核心库 check_due 语义，含 coalesce/TTL 新口径） │
│   ├─ 会话级 fire → 经既有所属会话的注入路径（忙则 held）           │
│   └─ 工作区 fire → RunSpawner（阶段二，§8）                        │
│ CronService（任务 CRUD：RPC 与工具两个入口的同一语义层）           │
│ 无人值守姿态消费者（权限链入口——ADR-001/002）                      │
├─ 核心库（mirri-core）─────────────────────────────────────────────┤
│ CronManager（数据模型扩展：origin / max_fires / fire_count /        │
│   unattended / TTL 基准 / scope——§1）                              │
├─ 存储层 ──────────────────────────────────────────────────────────┤
│ 会话级任务：随会话 wire 事件流（既有，不动）                        │
│ 工作区任务：定时任务专用 SQLite 单库存储（阶段二，§7——ADR-020）   │
└──────────────────────────────────────────────────────────────────┘
```

**分层动机**（抽象问题）：任务的「到点」判断与「到点后怎么跑」是两层——前者只需要一个时钟和一个任务表，后者才涉及会话形态（交互会话或一次性运行）。现状把两者都绑在「每个会话自带一个驱动循环」上，导致服务整体没有调度面、某会话关闭即局部失明。上提后的统一调度器只负责到点与路由，执行形态由任务的归属决定。

## 1. 数据模型扩展（mirri-core CronTask）

阶段一新增字段（全部可缺省——旧记录无字段按缺省解释，无需迁移）：

```text
CronTask {
  ...(既有字段不动)
  origin: TaskOrigin,          // user | agent；缺省 agent（历史记录全是模型代建）
  unattended: bool,            // 无人值守声明（SDR-002）；缺省 false【2026-11-04 ADR-021 废弃：运行即普通回合（SDR-125），该任务级声明与翻译已退役；下文为历史形态】
  max_fires: Option<u32>,      // 循环任务可选次数上限（需求 A.5；阶段一 D-M8 门槛的判定输入；一次性任务无此参数、门槛视同 1）
  fire_count: u32,             // 成功投递计数（D-M7：注入成功 +1；补发合并计一；run-now 不计）
  scope: TaskScope,            // 阶段二前置字段：Session(id) | Workspace(id)；缺省按 session_id 归位
}
```

- **TTL 基准改造（SDR-005 / 阶段一 D-M5）**：过期判定从 `now - created_at >= TTL` 改为 `now - last_fired_or_created >= TTL`——每次成功投递推进基准（fire-refresh）。停摆出口保持「终触发搭载投递」的既有形态。
- **计数推进点**：与游标推进同址（同锁内），保证 max_fires 判定与投递原子；到达上限的 fire 计划携带「计满」标记（信封新增键，复用 stale 的终信号呈现位）。
- **缺省解释**：`origin` 缺省 agent、`unattended` 缺省 false、`max_fires` 缺省无上限——旧记录语义零变化；A.4（SDR-003）的 recurring 工具层默认改 false 不经此模型（工具参数层裁决，恢复层现状缺省见 context §1）。

## 2. 服务层：CronService（统一 CRUD 语义）

RPC 与模型工具两个创建入口收敛到同一服务方法（新增字段的构造、校验、事件发布单点）：

```text
create(scope, cron, prompt, recurring, opts { timezone, max_fires, unattended, origin }) -> Task
  // origin 由入口决定：RPC=user、工具=agent；校验族沿用既有（上限/8KiB/350 天/5 年）
remove(scope, task_id)
trigger(scope, task_id)        // run-now；ADR-004 补忙闲纪律
list(scope) -> Vec<TaskView>   // 视图补 origin/fire_count(±max)/unattended
set_unattended(scope, task_id, bool)   // D.4 声明修改【2026-11-04 ADR-021 废弃，同上】
```

- **scope 是入口属性不是工具参数（评审轮 3 硬判定）**：**工具入口（模型可达面）只允许 session scope——`scope` 不作为模型可传参数出现**（工具 schema 无该字段；工具创建的任务归属发起回合所在会话）。workspace scope 只能经两条路径进入：a) 用户经 RPC 直建（用户直建面）；b) 模型经提议通道起草、用户批准（§9.3）。判定收益：模型对「建在哪一层」**没有选择权**——「在当前会话建定时器」是工具面唯一的动作；「想变成工作区任务」= 走提议（never-auto-approve），模型无法通过谎报 scope 把任务送达更宽的归属面。`create` 的 `scope` 参数是服务层内部签名（由入口分流注入），不是模型面参数。
- **cron.add RPC（阶段一 A.1）**：`sessionId` 为可选参数——省略时归属发起会话不可行则报错（阶段一只有会话级）；wire 契约与 `cron.delete`/`cron.trigger` 同注册族。
- **校验拒绝文案**：禁用态（E.4）拒绝创建的理由 =「定时任务已禁用（MIRRICODE_DISABLE_CRON）」。

## 3. 统一调度器（CronScheduler，ADR-003）

```text
CronScheduler {
  tick: 固定间隔（现状值见 context §2），
  loop {
    for scope in 已注册的任务面（存活会话集 ∪ 工作区任务表） {
      due = check_due(scope 任务表, now)        // 核心库既有语义 + 新 TTL/计数
      for fire in due {
        match fire.scope {
          Session(id) => 经该会话的注入路径投递（busy 则 held——既有 B2 语义）
          Workspace(id) => RunSpawner::spawn(fire)   // 阶段二 §8
        }
      }
    }
  }
}
```

- **与既有 per-session driver 的关系**：调度检查上提后，per-session 驱动循环退役，其注入路径（canonical 代理、held-until-idle、resume 补发）**原样保留**为调度器的会话级投递通道——上提的是「时钟」，不是「执行」。现状注入依赖的会话侧句柄（turn 流、在飞注册表、游标写穿索引）由调度器在 tick 时经会话注册表重解析持有（与会话关闭竞态时 fire 按「会话不在场」处理——held，等重开补发）。
- **会话关闭的 held 修复（C.4）**：held fires 从「随驱动任务消亡」改为「随任务表存活」——挂起状态记录在任务侧（游标已推进、待注入），会话重开时按补发规则投递；会话删除时级联清除。孤儿治理循环（现状结构见 context §6）不在本域改造范围。
- **手动触发的忙闲纪律（SDR-004）**：`trigger` 复用与自然触发相同的注入前检查——busy 则进入同一 held 通道（不绕过）；run-now 不动日程的既有裁决不变（挂起 ≠ 游标推进）。

## 4. 无人值守姿态的权限链接线（ADR-001 / ADR-002）

### 4.1 回合来源的 plumb-through（ADR-001）

`PermissionPolicyContext` 增加 `turn_origin: TurnOriginContext`（枚举：`Interactive` / `Cron { unattended: bool, task_id }` / 其他后台源的现状语义）；由回合发起处在构造上下文时注入——cron 注入路径带 `Cron` 变体，交互回合带 `Interactive`。这是**加法管道**：既有策略不读此字段则行为零变化。

**传播规则（评审轮 3，ADR-001 补充）**：`turn_origin` 随子代理派生（spawn / swarm）传播——子代理回合**继承发起回合**的 origin：cron 回合内派生的子代理，其回合仍是 `Cron` 血统；交互回合派生的仍是 `Interactive`。实现位置：子代理回合构造 `PermissionPolicyContext` 时继承发起者的 `turn_origin`，不按派生源重置。防线含义：血统防线（§4.4）不因委派失效——「先 spawn 一个子代理、让子代理建任务」不构成绕过。

### 4.2 问询拒绝的泛化（ADR-002）

【2026-11-04 ADR-021 废弃本段机制——`unattended` 字段删除、判据改读 `workspace`（生产恒等）；下文为历史裁决记录】`Ask` 结果的 headless 翻译层增加一支：`turn_origin` 为 `Cron { unattended: true }` 时，`Ask → 工具失败回执`（拒绝文案 = SDR-002 D.5 的改道指引），**在策略链翻译处统一实现**（与既有 `deny_when_unattended` 同址的机制层）：

```text
Ask {
  deny_when_unattended: true,   // 既有字段（私有网络 fetch 策略）→ 该姿态下同样走拒绝
} 在 turn_origin == Cron{unattended:true} 时 → Blocked(改道指引文案)
其他 Ask 在同姿态下 → Blocked(同上)          // SDR-002 / 阶段一 D-M3：一律拒
Interactive 回合 → 既有行为完全不变
```

- **回执形态**：模型收到的工具失败（不是回合失败）——回合继续，模型在同回合改道；这是「问询通道不存在」的诚实语义，不是惩罚。
- **范围收敛**：本机制只挂在 cron 注入的回合上；goal 续航、任务通知等其他后台注入源的姿态不在本批（无裁决，不猜测）。

### 4.3 模型代建的审批门槛（SDR-006 / 阶段一 D-M8）

门槛判定发生在 CronService 的创建路径上（工具入口，origin=agent 时），坐在策略链**之前**的机械检查 + 一支策略链消费：

```text
create(origin=agent, 预算 = max_fires 或 (recurring=false → 1)) {
  预算 ≤ 3（常量 AGENT_CRON_FIRE_GATE = 3，不配置）→ 放行
  预算 > 3 或未声明上限 →
    有人应答姿态（manual/yolo）→ Ask（审批面呈现：计划、预算、理由[可选]）
    auto 姿态                  → Blocked（回执含三要素：门槛值 N、该姿态下更高预算
                                 不可达成不可重试、改道路径[建合规任务并告知用户/
                                 请用户从管理面直建]）
    无人在场（含 cron/无人值守姿态）→ Blocked（同上改道语义）
}
```

- **门槛位置**：与内网抓取问询门同构——置于模式放行策略之前，任何权限模式都不能绕过；「预算是多少」在创建时刻是机械事实（声明值或一次性=1），无意图推断。
- **会话级累计上限**：初版不做通用强制门（阶段一 D-M8 裁决）——更紧的通用累计门待实施反馈（数据先行，开放项登记于 ROADMAP O-5）；血统链上的累计风险已由**血统链累计上限**（SDR-106，§4.4——cron 血统创建的一次性任务按会话累计计数，超限拒绝）专项兜底。
- **自述理由**：创建参数含可选 `reason`，只入记录与展示，**永不参与门槛判定**（自报不可作为安全依据）。

### 4.4 血统防线（SDR-007 / 阶段一 D-M9；SDR-106 收窄）

创建路径的最前段机械检查：`turn_origin` 为 `Cron` 变体（任何 cron 注入的回合，不区分值守姿态；经 §4.1 传播规则含其派生子代理的回合）时，创建**循环**定时任务**一律拒绝**——不问权限模式、不做审批、无例外档；一次性会话任务（预算不超 §4.3 门槛）按收窄口径放行。回执说明「定时回合内不可创建循环任务」并指引清理路径（删除既有任务）。该检查与 §4.1 的 plumb-through 共用同一输入：门槛管单任务生命周期，血统防线管繁殖。

**收窄（SDR-106，评审轮 3 用户裁决）**：防线的拒绝对象收窄为**循环任务**——cron 注入回合内允许创建**会话归属、一次性（recurring=false）、声明触发次数不超过代建门槛（一次性视同 1 次 ≤ 3，即不引入预算问题）**的自计时任务；任何循环任务（无论归属、无论预算）仍在该回合内一律拒绝。理由：血统繁殖的**主引擎**是循环任务；「执行会话内自计时」（工作区任务的运行中建单次回访定时器，如 CI 回访）是 agent 自计时的核心动机场景（SDR-009/010），工作区任务的执行会话内同样需要。**但一次性任务并非结构上安全**：可串行链（A 触发后自删前建 B，B 再建 C，每次都是新预算 1，活跃数恒为 1——「每会话 ≤ 50 活跃上限」对恒为 1 的活跃数无效），构成分钟级无休止无人值守循环的可达路径。故豁免受**血统链累计上限**封顶：会话内经 cron 血统回合（含其派生子代理回合）创建的一次性任务按会话累计计数，达到常量上限（初值 12，实施可调）即拒绝并回传改道指引——机械判定：血统回合发起的创建计数是可数的。经循环拒绝 + 累计上限双门，CI 回访类自计时不受阻，无休止血统链有硬边界。

## 5. TTL 与计数的演进语义（核心库）

- **fire-refresh**：`last_fired` 既是 coalesce 游标基准（既有）又是 TTL 基准（新）——两个语义共用一个字段，投递成功时同锁推进，无第二真值源。
- **计满收尾**：fire 计划产生时判 `fire_count + 1 == max_fires` → 该 fire 携带「计满」标记 + 投递后移除任务（与一次性任务的首触发自删同一代码路径，参数化收尾原因）。
- **收尾原因枚举**（F.1）：一次性 / 计满 / TTL 到期 / 删除——收尾事件携带枚举，消费端如实呈现。

## 6. 消费面

- **web 定时任务面板**：阶段一补创建表单（计划/提示词/循环/次数上限/无人值守）与列表列（来源、计数 n/上限、姿态）；**列表查询改为跨会话聚合**（E.5/SDR-008：按会话归组呈现全部任务，未打开会话的任务如实标注投递状态，不再只看活跃会话）；`cron.add` 经既有 RPC 面。阶段二扩展见 §9。**列表呈现口径（2026-11-03 修订，cron-improvement A14）**：任务页为全工作区聚合视图——一次呈现所有工作区的任务、按工作区分组，不随「当前会话/活动工作区」过滤显示范围（存储侧跨工作区查询由 ADR-020 的单表形态直接支撑）。
- **模型工具**：CronCreate 工具参数增加可选 `unattended`【2026-11-04 ADR-021 废弃该参数】（模型可代用户声明——但用户直建与模型代建同受 A.4 默认改判）；**无 `scope` 参数**（M2 硬判定——工具面只建会话归属任务，工作区归属只能经提议通道或用户直建，见 §2/ADR-014）；CronList 输出补新字段。阶段二新增 **CronPropose**（提议工具，定名——命名实施可调，职责不变）：模型发起工作区任务草案的唯一工具面入口，创建语义天然是工作区草案、不与 CronCreate 混用（§9.3/ADR-014）。工具描述的 jitter/30s tick/idle-only/7 天存活语义文案对齐属独立快修批次（#177），本域不重复承载。

## 7. 阶段二 · 存储与归属上提（阶段二 D-M1；存储介质由 ADR-020 取代 ADR-007）

```text
TaskScope = Session(session_id) | Workspace(workspace_id)
工作区任务存储：定时的独立 SQLite 数据库（引擎数据根；与会话索引同约定不同文件）内的 scheduled_tasks 表
  —— workspace 为表内普通字段（非按工作区分文件/分目录），跨工作区查询 = 同表一次查询
  每任务一记录：任务字段（§1）+ 运行记录数组（§8 的 RunRecord）+ 提案记录
会话级任务：存储不动（会话 wire 事件流），调度器经会话注册表读取
```

迁移面：既有 JSON 工作区存储（ADR-007 形态，现状盘点见 context 文档）按启动时一次性导入迁移至 SQLite 表，导入完成后旧文件保留为只读存档、不再读写（迁移细则属实施批次计划，本文只锁目标形态）。journal 归属：工作区任务的 ops 不入会话事件流（发独立事件，事件总线按 workspace 维度广播）。

**术语**：「引擎数据根」指引擎主目录（用户级、跨工作区共享的那一层——工作区注册表与会话索引所在处），区别于「会话数据根」（按工作区分桶的那一层）。定时任务数据库落在引擎数据根：任务是用户资产、跨工作区查询，不随任何单一工作区的桶走。

## 8. 阶段二 · RunSpawner（SDR-101 的机制）

```text
RunSpawner::spawn(fire) {
  1. 并发姿态检查（阶段二 D-M3）：上次运行在跑？默认 skip（RunRecord 记「跳过」）；排队档则入单槽队列
  2. session.create(workspace_id=fire.workspace, 形态=无人值守执行)
     —— 不 spawn 会话级驱动/事件中继；懒物化：无首条用户消息语义的例外路径（§8.1）
  3. 注入提示词（cron 信封 + 权限姿态 turn_origin=Cron{unattended:<按任务档位映射>}）【2026-11-04 ADR-021：Cron 变体不再携带 unattended 字段，下文为历史形态】
  4. 等待回合终局 → RunRecord 落 {状态, 起止, 时长, 用量归因=task:fire.task}
  5. 会话资源释放；有产出时经「显式打开」路径落盘进索引（B.2）
}
```

### 8.1 懒物化的执行会话例外

执行会话的首条内容是 cron 注入（非用户消息）——默认仍**不进索引**（与「首条用户消息才落盘」一致）；「显式打开」（运行记录点击）触发落盘，落盘后走既有会话回放。即：索引准入 = 用户显式动作（打开）或运行产出留存声明，定时运行本身不触发。

### 8.2 未打开执行会话的清理（阶段二 D-M5 b 层）

未落盘的执行会话驻留暂存层（内存/会话暂存区），需要一个不依赖用户动作的出口：运行结束后保留 7 天（服务侧计时，重启不重置），期间未被显式打开即**丢弃**；RunRecord 保留轻量摘要（状态/起止/时长/用量），用户仍可从运行记录得知「发生过什么」、只是过程不可回看。7 天内被打开的按 §8.1 落盘，此后转正式会话、由既有会话留存策略接管（与 a 层单一交接点）。实现挂靠孤儿治理循环的 sweep 结构（服务级、无会话依赖——现状结构见 context §6），扫描条件 = 会话形态为无人值守执行 && 未落盘 && 运行结束时间距今超 7 天。

### 9.2 时区的显式呈现（阶段二 D.5）

### 9.3 创建审批：提议-审批通道（阶段二 SDR-105 / D-M8） **（2026-11-04 ADR-022 取代本节：单次工具审批、批准即创建；下文为历史裁决记录）**

经提议专用入口（工具面新增**提议工具 CronPropose**，命名实施可调、职责不变）发起的创建请求**不进入 CronService 的直接创建路径**，而是：**工具面形状（ADR-014 口径）**：新增专用提议工具 CronPropose，其创建语义天然是**工作区草案**，不与 `CronCreate` 混用——`CronCreate` 工具面永远只建 session scope（§2 M2 硬判定），模型想涉入工作区任务只有「提议」这一个动作，没有可谎报的 scope 参数。

```text
工具创建请求（工作区归属）
  → CronService 不建任务，产出「提议」记录（草案 = 计划/提示词/循环/预算/建议姿态）
  → 经既有反向问询审批通道（reverse RPC 审批面）呈给用户
      ├─ 用户批准 → CronService.create（origin=agent[经审批]）——唯一创建路径
      └─ 用户拒绝/撤回 → 草案作废；工具回执（改道指引：改草案重提 / 请用户直建）
  审批策略位：never-auto-approve
      —— 策略链翻译层对该问询标 never-auto-approve，
         任何权限模式（manual/auto/yolo）都不得自动应答；
         无人值守/无人在场语义下与 deny_when_unattended 同走拒绝（不可能有人批准）
```

**检查顺序（评审轮 3，B1 硬化）**：never-auto-approve 的检查必须**置于既有 headless auto-approve 翻译分支之前**——headless 链路中「有人应答时自动批准普通 Ask」的既有翻译分支不得消费该问询；never-auto-approve 策略位在任何翻译路径下**永不落 Approved**。覆盖「交互会话 + 客户端断连」格子：yolo/auto 模式下有人在场但客户端掉线时，既有 headless 分支会自动批准普通 Ask——提议审批若走同分支会被静默吞掉变成「已批准」，本裁决要求它在分支之前被截住、按无人应答处理（等待或拒绝，不自动批准）。

**四模式 × 三在场态推演表**（验证 never-auto-approve 无死角；「提议结局」= 模型发出的工作区任务创建请求的最终去向）：

| 权限模式 \ 在场态 | 有人在（客户端连接） | 无人（无审批面） | 交互中客户端断连 |
|---|---|---|---|
| manual | 问询呈面，等用户批/拒（既有审批面语义） | deny_when_unattended 同路拒绝 | 断连等待（既有审批域断连韧性语义，不自动批准） |
| auto | never-auto-approve 截住 auto 放行 → 问询仍呈面等用户 | 拒绝（同上） | **B1 覆盖点**：headless auto-approve 分支被前置检查截住，不落 Approved，按断连等待/拒绝处理 |
| yolo（无人值守） | never-auto-approve 截住 yolo 放行 → 问询仍呈面等用户 | 拒绝（同上） | 同 auto 行——任何翻译路径不落 Approved |
| 只读观察（阶段二档位） | 问询呈面等用户 | 拒绝 | 同上 |

推演结论：四模式 × 三在场态共十二格中，提议的结局只有三种——**呈面等用户 / 断连等待 / 拒绝**，不存在任何「自动批准」格子；「yolo/auto + 有人在但掉线」这一格由检查顺序硬化（B1）封死。

- **与 §4.2 泛化机制的关系**：§4.2 的 `Cron { unattended: true }` Ask 翻译是「**运行时**问询的无人值守拒绝」（触发回合里模型问事 → 拒）；本节的 never-auto-approve 是「**创建时**审批的永不自动通过」（建任务的提议 → 必须真人批）——后者是更强的语义：deny_when_unattended 只排除无人场景，never-auto-approve 连有人场景的自动放行（yolo/auto）也排除。两者同住策略链翻译层，共用 §4.1 的 turn_origin 输入，是同一泛化机制的两个策略位。
- **与阶段一 §4.3 门槛的关系**：门槛（AGENT_CRON_FIRE_GATE）只作用于**会话级**任务（agent 自计时的小额放行）；工作区归属的请求绕过门槛判定、直接进提议通道——两类请求在 CronService 入口按 scope 分流，互不消费对方的规则（scope 分流依据见 §2 的「scope 是入口属性不是工具参数」）。
- **回执形态**：原回合的同步工具结果只承载「提议已呈审」（回合不挂死——与 SDR-002 的诚实语义同族）；批准/拒绝的**结果回执**按 §9.4 异步送达（批准 = 任务已创建（id）回执，拒绝 = 含改道指引的失败回执）。
- **血统防线前置**：§4.4 的 turn_origin 前段检查仍在提议通道之前（cron 注入回合内的创建请求连提议都不生成，直接拒绝——经 §4.1 传播规则，cron 回合派生的子代理发起的请求同样被拒；**含 CronPropose 的一次性工作区提议，阶段二 D.0d 批 4 计划评审补裁——cron 回合内不产生任何工作区提议**）。

**实施裁决（2026-10-31 批 4 计划评审）——审批通道归属，澄清 ADR-013 而非推翻**：批 4 计划曾提出新建 `cron.proposal.decide` 独立审批 RPC，评审识别这与 ADR-013「否决新建独立审批面、复用既有 reverse-RPC 问询审批通道」矛盾。裁决：**维持 ADR-013 原裁决**——提议审批走既有 `approval.ask` / `approval.decide` 通道（CronPropose 的 Ask 携带 never-auto-approve 策略位，fire-and-forget 呈审 + 待决列表注册，用户经 `approval.decide` 决策）；`cron.proposals.list` 保留为**纯查询面**（只读，不是审批面——与 ADR-013「不新建审批面」无冲突）。**回退条款**：若实施中发现既有 approval gate 无法承载提议语义（如提议无工具执行体、审批面无法呈现非工具类问询），则该实施障碍构成 ADR-013 **被否决备选 b**（新建独立审批面）的触发条件——届时须回炉重新裁决，不得在实施中就地另造审批路径。

### 9.4 提议的异步回执闭环（评审轮 3，M5） **（2026-11-04 ADR-022 取代本节：批准与创建在同一次工具执行内，无异步回执；下文为历史裁决记录）**

提议是**异步决策**，批准/拒绝的回执不经原回合同步返回，而是走「下一次该 agent 活跃时的系统通知注入」：

```text
用户批准 → 通知通道注入：「任务已创建（任务 id、计划摘要）」→ CronService.create 已发生，模型收到的是确认回执
用户拒绝 → 通知通道注入：「提议被拒绝（原因/用户留言，如有）」+ 改道指引（调整草案重新提议 / 请用户直建）
用户改草案后提交 → 语义 = 拒绝原提议 + 修改意见回传，模型重新提议（显式决策）
```

- **通道复用不新建**：回执复用既有 notification 注入通道形态（agent 下一次活跃时收到系统通知），不造第二套「模型侧回执投递」机制；原回合的同步工具结果只承载「提议已呈审」（不挂起等待审批——与 SDR-002 挂死问题同构的规避）。
- **改草案 = 拒绝 + 重提**（显式决策）：否决「用户直接编辑草案」形态——编辑态下「批准的是谁的内容」权限语义复杂（用户署名的模型草案？混合内容？），且弱化审计链（无法分辨原始提议与用户改后版本）；拒绝 + 修改意见回传 + 模型重新提议，每一步的署名与责任都清晰。
- **提议 TTL**：无响应悬置 **72 小时**后作废（通知模型「提议已作废（无响应）」）——与审批域断连等待机制的量级对齐；具体数值标注为**实施可调**（本域不锁常量，实施时与审批域既有等待参数对表后定）。
- **草案提示词按不可信内容呈现**：审批面呈现草案（含提示词全文）时按**不可信内容**标注与呈现（模型起草的提示词可能是注入载体——用户批准前，其内容不代表用户意图，呈现层不因其「来自自家 agent」而降低防注入姿态）。

## 11. ADR 记录

- **ADR-001（2026-10-30）**：回合来源经权限上下文 plumb-through，加法管道。背景：权限策略链看不到「这一轮是谁发起的」，任何按回合姿态的裁决（无人值守、未来的源级策略）都没有输入。决策：`PermissionPolicyContext` 增加 `turn_origin` 字段，回合发起处注入；既有策略不读则零变化。**（2026-10-31 评审轮 3 补充，M1）turn_origin 随子代理派生传播**：子代理/swarm 回合继承发起回合的 origin（cron 回合里派生的子代理仍是 Cron 血统），不按派生源重置为交互——防线不因委派失效（否则「spawn 一个子代理去建任务」即绕过血统防线）。传播在子代理回合构造上下文处实现（§4.1 传播规则段）。被否决备选：a) 为 cron 回合单独造一条审批旁路（第二套审批语义，漂移起点）；b) 在策略里反查任务表（策略层不该有数据依赖）；c) 子代理回合按派生源重置为 Interactive（防线可被委派绕过——传播的缺失即绕过路径）。影响范围：§4.1、子代理回合发起处、permission 模块。
- **ADR-002（2026-10-30）**：无人值守的问询拒绝在**策略链翻译层**统一实现。背景：拒绝语义必须是「所有 Ask 的统一去向」而非逐策略打补丁（否则新策略漏拒）；既有 `deny_when_unattended` 字段（私有网络 fetch）已是同层先例。决策：翻译层按 `turn_origin` 分支——`Cron{unattended:true}` 下全部 Ask → 工具失败回执（含改道指引）；复用并覆盖 `deny_when_unattended` 的既有语义（该字段在该姿态下同走拒绝，无行为冲突）。被否决备选：a) 逐策略加 `deny_when_unattended: true`（枚举式防御，新增策略必漏）；b) 在模型注入提示词里「嘱咐」模型别用问询工具（软约束，不可靠）。影响范围：§4.2、permission 翻译层、策略族。
- **ADR-003（2026-10-30）**：统一调度器采用「上提时钟、保留注入通道」的改造路径。背景：直接删 per-session 驱动重造会牵动全部会话侧句柄（turn 流、在飞注册表、游标写穿）；而问题只在「时钟归属」。决策：调度检查上提到服务级循环（孤儿治理循环的结构同款：interval 驱动、无会话依赖——现状结构见 context §6）；会话级注入路径原样保留为调度器的投递通道，tick 时经会话注册表重解析句柄。被否决备选：a) 一次性重写驱动（风险与收益不成比例）；b) 保持 per-session + 全局巡检兜底（两套时钟竞态）。影响范围：§3。
- **ADR-004（2026-10-30）**：手动触发的忙闲纪律复用自然触发通道。背景：run-now 直插注入与「回合单飞」不变量冲突（busy 会话中并发投递）。决策：trigger 进入与自然触发相同的注入前检查与 held 通道；「不动日程」（SDR-B6-01 D-2）语义不变。被否决备选：trigger 保持直插并文档化其例外（回合单飞不变量不应有例外）。影响范围：§3、routes cron.trigger。
- **ADR-005（2026-10-30）**：TTL 基准复用 last_fired 字段。背景：TTL 需要一个「最近活跃」真值；last_fired 已是 coalesce 游标基准且同锁推进——再造第二时间戳必然出现两真值漂移。决策：`last_fired`（缺省回退 created_at）同时作为 TTL 基准。被否决备选：独立 last_activity 字段（双真值；两处推进点的原子性成本）。影响范围：§5。
- **ADR-006（2026-10-30）**：`MIRRICODE_DISABLE_CRON` 兑现为三层实现而非删除文档。背景：该开关名不副实——文档多处宣传而代码未实现（完整证据链见 context §4.1），R4 信号真实性违背；删除承诺是能力倒退信号，且运维关停是真实场景。决策：a) 创建拒绝（工具与 RPC 均拒绝，理由明确）；b) 调度器启动时读环境变量、禁用态不进检查循环；c) 列表读取可用并显示禁用状态。实现评估为单批可完成（一个启动检查 + 两处拒绝 + 状态位）。被否决备选：删除文档承诺（否——见 D-M6）；实现为运行时热切换（无场景诉求，重启生效足够）。影响范围：§2、§3、§6、用户文档。

- **ADR-020（2026-11-03，用户裁决）**：工作区任务存储介质 = 单一 SQLite 数据库内的 scheduled_tasks 表，workspace 为表内字段。取代 ADR-007 的单文件 JSON 形态。背景：两个独立信号指向同一结论——a) 按工作区分文件/分目录的形态使「跨工作区聚合」退化为逐文件遍历与内存拼接，聚合视图（cron-improvement A14）与全局可见性（阶段二 Epic E）每次呈现都要全量收集多个分散文件，且从未建过任务的工作区天然缺席于任何清单，聚合口径难以保持诚实；b) ADR-007 否决 SQLite 时的前提「依赖不成比例」已不成立——引擎内已有同库约定的 SQLite 消费方（会话索引），依赖已存在且被验证。用户裁决（2026-11-03）：「直接在 SQLite 设计一个新的 table，存储这些任务数据。workspace 可以是其中一个字段。」决策：引擎数据根下定时的独立 SQLite 数据库（见 §7 术语定义；独立数据库文件，不与会话索引共库——两者是同约定而非同文件：同样的 rusqlite bundled 依赖、同样的 busy 超时与单写者约定）承载 scheduled_tasks 表；workspace_id 为普通列（任务归属靠字段值，不靠文件位置）；跨工作区查询、按工作区过滤均为同表单查询；运行记录与提案记录随任务行内嵌（沿用 ADR-007「单任务运行量小、随任务删而删」的内嵌判断，不另立 runs 表）；会话级任务存储不动（仍为会话 wire 事件流，不迁移）；锁约定从「文件锁」自然替换为 SQLite 自身的写串行与 busy 超时；既有 JSON 数据按启动时一次性导入迁移，旧文件转只读存档。被否决备选：a) 维持每工作区一个 JSON 文件（跨工作区聚合的收集复杂度正是被推翻对象；「依赖不成比例」前提已失效）；b) 每工作区一个 SQLite 库（同 a 的分裂形态，只是换了介质）；c) 运行记录独立成表 + 外键 Join（单任务运行量小、随任务删而删，Join 成本无回报——沿用 ADR-007 对该形态的否决理由）。影响范围：§7、§6（聚合视图的查询支撑）、ADR-007（被取代）；表结构细节（列清单、索引、迁移脚本）属实施批次计划，本文只锁介质与归属模型。**（2026-11-03 实施修订：CronPersistence 契约缝）**存储契约经 mirri-core 内定义的 CronPersistence trait 缝消费、由嵌入式层（mirri-embedded）的适配器实现——因 zero-IO 门禁将 rusqlite 锁出 mirri-core 的依赖树，核心域不得直接依赖承载 crate（mirri-cron-index）；mirri-core 的 Cargo.toml 仅以 dev-dependency 携带 cron-index（真实 SQLite 路径的测试覆盖留在核心测试内，门禁的 cargo-tree 遍历只覆盖正式依赖）；承载 crate 保持其纯存储、不依赖核心的姿态（mirri-session-index 先例）。

- **ADR-022（2026-11-04，用户裁决）· CreateScheduledTask 收敛为单次工具审批**（对应 cron-improvement SDR-126）：删除 `ScheduledTaskCreationSink::register_creation` 这条「工具执行后再注册第二张 gate 条目」的旁路——工具的创建动作回到 `execute` 本身：审批链里 `CreateScheduledTaskNeverAutoApprovePolicy` 仍在链首对该工具无条件 `Ask{never_auto_approve:true}`（这是唯一一次审批，也保证任何权限模式都弹），用户批准后 `execute` 经新的宿主接口 `ScheduledTaskCreator::create(draft)` 调 `WorkspaceCronManager::add`，把「已创建（任务 id、计划摘要）」作为工具结果同步返回；拒绝即工具调用被拦截，`execute` 不运行，零副作用，拒绝理由随工具被拒的标准回执回到模型。随之删除：`scheduled_task_pending` 内存映射与 `draftId`、`approval.decide` 里的创建分支（`decide_scheduled_task_creation`）、G4 的 steer 通知注入、`cron.pendingApprovals` RPC 与设置页待确认区。审批卡的内容由该工具 `ExecutionPlan.display` 提供：`ToolInputDisplay` 新增结构化变体 `ScheduledTaskCreate { cron, timezone?, workspace_id, permission_mode?, model?, effort?, title?, prompt, recurring, max_fires?, reason? }`，聊天审批卡按它渲染人话详情（工作区名由前端用 workspace_id 映射，核心工具拿不到注册表）。这样重启后不存在「批了但任务没建」的窗口（批准与创建在同一次工具执行里）。被否决备选：保留旁路并把第一次审批改成自动放行——旁路的内存映射与重启丢失问题仍在。影响范围：§9.3、§9.4、ADR-013（其「提议-审批通道」描述整体被本条取代）。
