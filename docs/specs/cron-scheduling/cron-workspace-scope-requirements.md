## 0. 领域边界（阶段二增量）

**产品定位（SDR-009/105）**：本阶段服务**用户委托的例行工作**——「每天早上替我巡检一遍、有异常叫我」这类用户不想手把手定义的工作流：到点自己跑、不依赖用户开着任何会话、跑完留痕、成本看得见。**工作区定时任务（每次运行新会话）是用户拥有的产品面**；Agent 在这个面上是**起草者**——用户不想手把手定义复杂工作流，Agent 可以代为起草/提议，用户核对其是否符合意图后**审批**；Agent 没有直接创建权（见 Epic D 提议-审批模型）。

**本阶段覆盖**：定时任务脱离单一会话——归属工作区（workspace）、独立于会话存活、每次运行产生新的执行会话、运行历史可查、执行时的权限姿态显式可选可见、以及此类任务的**创建审批**模型（Agent 提议 → 用户审批）。

**不在本阶段**（沿用阶段一与相邻域边界）：会话级任务的既有语义（阶段一 Epic C.2 保持，且其 session scope 归属经阶段一 SDR-010 确认为正确设计）、表达式/时区/jitter/coalesce/上限族（后台任务域）、回合准入（回合调度域）、审批策略本身（approval 域）。

**术语表**（阶段二增量；跨域登记见 glossary CS 节）：

| 规范名 | 形态/示例 | 含义 | 禁止的叫法 |
|---|---|---|---|
| 工作区任务 | 归属字段为工作区而非会话的任务 | 到点后**新建一次执行会话**跑完提示词，跑完即归档；任务本体长期存活于工作区 | ~~全局任务~~（归属是工作区不是全局）、~~跨会话任务~~（暗示注入既有会话，语义相反） |

## 1. 角色与场景总览

- **P1 · 委托例行工作的用户**（本阶段动机主体）：「每天早上替我巡检一遍、有异常叫我」——用户不想手把手定义复杂工作流，要么自己直建，要么接受 Agent 起草的提议后审批放行。
- **P2 · 直接排定者**：我在工作区层面排定任务，会话开不开、开哪个都无所谓。
- **P3 · 成本敏感用户**：每次运行用了多少钱、这个月跑了多少次，要看得见（#181 验收标准）。
- **P5 · 审慎用户**：任务的创建审批是我的（Agent 提议必须经我批）；任务的运行时权限姿态是我显式选的、界面上看得见（#181 验收标准）。

**功能闭环**：

```
创建（用户直建；或 Agent 提议 → 用户审批后才创建——两个入口，一个归属：工作区）
  → 存活（独立存储，不随会话生灭）
  → 调度（阶段一统一调度器驱动工作区任务）
  → 执行（每次运行新建执行会话，按任务声明的运行时权限姿态）
  → 留痕（运行记录：状态/时长/用量）
  → 收尾（次数/TTL/删除，阶段一收尾形态沿用）
```

## 2. Epic A：工作区归属与独立存活

作为 P2 用户，我的任务不属于任何一个会话。

- **A.1 工作区任务**：任务可归属**工作区**创建；归属工作区后不再与会话绑定，会话的创建、关闭、恢复、删除均不影响其存活。
- **A.2 独立存储**：工作区任务的记录存于工作区级存储（脱离任何会话的事件流）；服务重启后任务与游标完整恢复（补发规则沿用阶段一 C.4 口径）。
- **A.3 会话级任务不受影响**：既有会话级任务的语义、管理面与呈现保持（阶段一 C.2）；两类任务在同一管理面共存，归属列如实区分。
- **A.4 工作区删除的级联**：**假如**工作区被删除、**当**删除完成，**那么**其工作区任务一并清除（不产生孤儿）；正在执行的运行被终止并如实记录——in-flight 的 RunRecord 终止时**记录终止原因**（「工作区已删除」），不静默消失、不误计为运行失败。

## 3. Epic B：执行形态——每次运行新会话

作为 P1 用户，每次巡检是一次干净的新会话，不带历史包袱。

- **B.1 每次运行新建会话**：工作区任务每次触发**新建一个执行会话**（在任务所属工作区内），提示词作为首条消息注入；会话按无人值守形态运行（不驻留会话级驱动与事件中继——那是给交互会话用的）。
- **B.2 懒物化不进索引**：执行会话在仅有定时运行内容时**不进入会话列表索引**；**假如**一次运行产出了值得回去看的内容（模型主动留存产物、用户想打开查看）、**当**该会话被显式打开，**那么**它按既有懒物化规则落盘可见。运行记录始终可从任务面进入查看（不依赖会话索引）。
- **B.3 一次性完成**：**假如**一次运行结束（回合完成/失败/被拒收尾），**当**收尾发生，**那么**执行会话资源释放（不留常驻循环），运行记录落一条终态；未打开过的执行会话（仍在暂存层）按 D-M5 的清理路径处理。
- **B.4 运行的并发纪律**：**假如**上一次运行尚未结束、**当**下一次触发到点，**那么**按用户选择的并发姿态处理（见 D-M3 裁决）。

## 4. Epic C：管理面与运行记录

作为 P2/P3 用户，我看得到每次运行及其成本。

- **C.1 任务面扩展**：管理面在同一列表呈现工作区任务与会话任务（归属列区分）；工作区任务的管理操作（删除、立即运行、编辑声明）与阶段一面语义一致。
- **C.2 运行记录**：每个工作区任务携带运行记录列表——每次运行的状态（进行中/成功/失败/被拒）、起止时间、时长、模型用量（费用与 token，口径复用既有用量可见域的归因体系）。
- **C.3 用量归因**：运行产生的用量归属到该任务（可按任务聚合查看「这个任务本月花了多少」），复用既有用量归因的来源标注，不另立统计体系。
- **C.4 运行详情入口**：**假如**用户想查看某次运行的过程、**当**点击运行记录，**那么**进入该次执行会话的只读回放（B.2 的显式打开路径）；无产出的失败运行如实呈现失败原因。

## 5. Epic D：创建审批与运行时权限姿态（两个独立决策点，SDR-105）

作为 P5 用户，「这个任务允不允许建」（创建审批）与「这个任务用什么权限跑」（运行时姿态）是两个独立决策点，都要显式、可见。

### 5.1 创建审批：提议-审批模型（Agent 无直接创建权）

- **D.0 提议-审批（never-auto-approve）**：**假如**模型经工具请求创建工作区任务、**当**该请求提交，**那么**系统**不创建任务**，而是生成一份**提议**（计划、提示词、循环与预算、建议的运行时姿态等完整草案）呈给用户审批；**无论当前会话处于何种权限模式（手动确认、免点击放行、自动执行、无人值守/yolo）**，审批都**不能被自动通过**——没有任何模式可以绕过用户审批，**包括「用户在场但客户端临时断连」的窗口**（该窗口下既有的自动应答机制不得消费提议审批，检查顺序见架构 §9.3）；与阶段一 SDR-006 的代建门槛是两种逻辑：阶段一会话级任务适用「小额放行」（≤3 次的短看护是代建正当主场）；工作区任务每次运行都是全新无人值守会话，**成本不可见且不可折叠**——一次审批涵盖的是无限期的未来运行，不存在「小额」可放行的语义。**模型发起提议的入口形状**：模型走**专用的提议入口**（架构定名 ScheduledTaskPropose（原 CronPropose））发起工作区草案——它与创建会话定时器的入口是**两个工具**：后者（CronCreate）没有任务归属的参数可传，归属由入口天然决定（模型无谎报归属的面，见架构 ADR-014）；这不是流程偏好而是防绕过设计。
- **D.0a 审批内容完整（字段清单显式化，批 4 计划评审）**：提议呈现给用户的面包含判断「是否符合我的意图」所需的全部信息，提议记录含以下字段：**计划**（schedule，含时区）、**提示词全文**（prompt，一字不改）、**循环声明**（recurring 与否）、**预算声明**（max_fires 或无上限的显式呈现）、**建议的运行时姿态**（三档之一，见 D-M2）、**预估成本口径**（有历史数据时按「一次运行约 N 元」的历史均值，无数据不显示——口径见 D-M4）——用户 check 意图，而非补填参数。
- **D.0b 拒绝与撤回**：用户拒绝提议 → 草案作废，无任务创建，模型收到明确回执（可改道：调整草案重新提议，或请用户从管理面直建）；提议在审批前可被用户随时撤回。拒绝不是惩罚，回执让模型能继续工作。
- **D.0c 用户直建不受影响**：用户从管理面直接创建工作区任务**无需任何审批**（用户自己的产品面，自己的动作就是授权）；Agent 提议被批准后创建的任务，来源如实标注为「模型（经审批）」。
- **D.0d 血统防线沿用（收窄口径，阶段一 SDR-106；批 4 计划评审补裁）**：定时注入回合内的创建请求（含工作区归属）一律拒绝**循环任务**——提议不是例外通道；**一次性会话任务**（预算不超阶段一代建门槛）按阶段一 A.6a 自计时豁免放行（执行会话内的 CI 回访回执场景），受阶段一 A.6b 血统链累计上限封顶。**一次性工作区提议亦拒（批 4 计划评审裁决）**：血统回合内经 ScheduledTaskPropose（原 CronPropose）发起的**一次性（one-shot）工作区任务提议**同样拒绝——工作区任务每次运行都是全新无人值守会话，血统回合内提议工作区任务即使一次性也属「cron 回合派生新的无人值守执行」；且提议需经审批（若批准即由 cron 血统间接触发工作区运行）。裁决理由为**机械简单性**：保持「cron 回合内不产生任何工作区提议」与 CronCreate 血统防线同口径，不做「循环拒、一次性放」的二次分叉（那需要区分提案入口与豁免条件的组合判定，防线复杂度翻倍）；用户想要一次性工作区任务，让交互会话发起。被否决方向：对一次性工作区提议放行（结构性可论证 one-shot 不构成血统链，但「回合内零工作区提议」的机械不变量比逐案豁免更可靠——与阶段一 SDR-106 否决「完全豁免」同族理由）。
- **D.0e 异步回执闭环（评审轮 3）**：批准/拒绝的回执以「**下一次该 agent 活跃时的系统通知注入**」送达（复用既有通知通道形态，不新造机制）——**批准即任务创建成功**，模型收到「任务已创建（任务 id、计划摘要）」回执；**拒绝**（含作废）回传拒绝理由与改道指引。**用户改草案 = 拒绝 + 修改意见回传 + 模型重新提议**（显式决策，否决「用户直接编辑草案」——编辑态的权限语义复杂且弱化审计）。**提议 TTL**：无响应悬置 **72 小时**后作废（与审批域断连等待机制量级对齐；具体数值为实施可调参数）。审批面呈现的**草案提示词按不可信内容呈现**（模型起草的提示词可能是注入载体——批准前不代表用户意图）。

### 5.2 运行时权限姿态（三档保留，D-M2）

- **D.1 创建时选择**：任务（用户直建或提议审批通过）创建时**显式选择**运行时权限姿态（「问询一律拒」为默认；可选档位见 D-M2 裁决），选择结果记录在任务上并在列表呈现。
- **D.2 运行中如实**：执行会话按任务声明的姿态运行；**假如**姿态是「问询一律拒」、**当**运行中模型调用需问询操作，**那么**阶段一 D.2 语义生效（立即拒、回传改道）；**假如**姿态是更宽的档位、**当**运行中触发其边界，**那么**按该档位定义处理并**在运行记录中留下痕迹**（哪次运行、哪个操作、因何被拒/放行）。
- **D.3 修改生效**：**假如**用户修改任务的权限姿态、**当**下一次运行，**那么**按新姿态执行（运行中的一次不受中途修改影响）。
- **D.4 成本可见性（#181 开放问题裁决）**：见 D-M4——预估与实耗两级呈现。
- **D.5 时区显式展示（#181 验收标准）**：任务的时区在创建面显式选择（缺省 = 用户本地时区，但作为可见的显式值呈现，不静默继承），并在任务列表与运行记录中如实展示；下次触发的呈现换算到该时区——「09:00」就是该时区的 09:00，不因查看者所在环境的时区而歧义。

## 6. Epic E：全局可见性与统一入口

作为用户，我不用打开任何特定会话就能看到全部任务及其真实投递条件（含 agent 在各会话里设的自计时任务——可见性是全两类的）。

- **E.1 聚合任务视图（阶段一 SDR-008 的工作区扩展）**：**假如**服务内有分属多个会话与多个工作区的定时任务、**当**我打开任务管理面，**那么**全部任务聚合可见（会话级按会话归组、工作区级按工作区归组），每项呈现：标题/提示词摘要、计划（下次触发及**时区**）、归属、来源、触发计数（含上限）、权限姿态、并发姿态。
- **E.2 投递条件如实**：会话级任务标注「依赖所属会话存活」（未打开会话的任务如实标注，阶段一 C.2 口径）；工作区任务标注「服务运行即触发」。两种口径在列表中共存且可分辨——用户从一处即能回答「这个任务到底什么条件下才会跑」。
- **E.3 失察可期**：被跳过的运行（并发姿态默认跳过）、被禁用的子系统（总开关）在任务面上如实标注，不静默。

## 7. 契约级裁决（阶段二）

- **D-M1 上提工作区管理器**：任务管理器从会话归属上提到工作区归属（数据模型 `session_id` → `scope`：会话或工作区）；存储脱离会话事件流（工作区任务入工作区级存储；会话级任务存储暂不迁移、语义不变——避免一次性大迁移，迁移另立裁决）。被否决备选：a) 工作区任务继续存「专用代理会话」的事件流（伪造归属，现状耦合原样保留，清单见 context §5）；b) 全量迁移会话级任务到新存储（收益不成比例，风险大）。
- **D-M2 权限姿态档位（#181 裁决；批 4 计划评审补 ADR-015 联动）**：工作区任务的姿态档位 = 阶段一的「问询一律拒」（默认）+ 复用既有权限模式中的「自动执行」档（auto：全部放行不问询，既有语义）+「只读」观察档（拒绝全部写操作——判定输入 = 工具能力类别声明，只读/非只读二分，见架构 ADR-015；问询也拒）。三档覆盖看护（拒）、信任全自动（auto）、审慎观察（只读）三类诉求；不引入每任务规则编辑器（既有权限规则体系可后续挂接）。被否决备选：a) 只有一档（无人值守拒）——信任全自动场景无解，用户会绕道；b) 任意规则组合（复杂度爆炸，无验证过的诉求）。
- **D-M3 并发姿态（#181 开方问题裁决）**：默认**跳过**——上一次运行未结束时，新触发跳过（记录「跳过：上次运行中」），不排队不叠加；可选**排队**（最多积压 1 次，超出的合并）。被否决备选：a) 并行多跑（同一任务的并发运行互相踩工作区，产物冲突无解）；b) 无限排队（停摆后堆积爆发，违背看护语义）。默认跳过的理由：看护类任务「上次还没跑完」通常意味着工作区正忙，再跑一次大概率重复劳动。
- **D-M4 成本可见性（#181 开放问题裁决）**：两级——**事后**（C.2/C.3 的按任务聚合实耗）为第一优先；**事前预估**（创建时按「一次运行约 N 元」的历史均值提示）为第二优先、有历史数据后才呈现（无数据不显示假预估）。被否决备选：只做事前预估（无历史数据时是瞎猜，误导）。
- **D-M5 留存裁决（#181 开放问题）**：两层。a) 执行会话**本体**留存跟随既有会话留存策略（session-retention 域），本域不另立定时清理；已落盘的运行会话随既有策略清理。b) **未打开的执行会话**（仍在暂存层未落盘的）：运行结束后保留 7 天，期间未被用户从运行记录打开即**丢弃**（运行记录仍保留摘要，可查发生过什么）；7 天内被打开的按既有落盘协议转正式会话、此后走 a) 层。7 天的量级依据：一次夜间看护运行，用户没在数天内回头看，基本不会再回头看；而「永不清理」会让每小时任务在暂存层无限堆积。被否决备选：a) 未打开会话永久保留在暂存层（无界堆积，正是 #181 开放问题 1 指出的失控形态）；b) 运行结束立即丢弃（产出窗口过窄，用户当晚想看已不可得）；c) 到期归档到不可见区（暂存层之外再造第二层存储，成本不成比例）。运行记录（轻量摘要）跟随任务存活，任务删除时一并清除。
- **D-M6 通知裁决（#181 开放问题；评审轮 3 补产出物摘要）**：运行终态（成功/失败/被拒）按既有任务通知体系投递（后台任务域 E10 语义），不新建通知通道；降噪（连续失败不重复打扰）复用既有分级与降噪提案路径（P-022）。**产出内容摘要随通知携带**：终态通知附带本次运行**产出内容的摘要**（如「巡检完成：3 项异常，详见运行记录」）——用户点开摘要即可判断是否需要进会话看全文，这是新闻收集类任务（「每天早上汇总给我」）的最低可用闭环，不必为看一句话结论打开一次运行。**实施裁决（2026-10-31 批 4 计划评审）——摘要降级**：初版摘要取**运行最后一条 assistant 消息截断**（零额外 LLM 调用），不按通知模板另行生成；「模型按通知模板生成摘要」的形态留后续批次，届时另行裁决。V20 验收口径相应为「截断摘要」。**完整投递渠道**（产出内容发送到外部即时通讯、邮件等）超出本域边界，登记为开放项 **O-7**。被否决备选：a) 每任务独立的通知规则编辑器（通知体系已有域，双轨）；b) 通知只投终态信号不带内容（用户为看一句结论被迫每次打开运行记录——新闻收集场景闭环断裂）；c) 本域新建外部投递通道（超域，且外部渠道各有自身的鉴权与频控语义）。
- **D-M7 模型创建工作区任务（已被 D-M8 取代，保留历史裁决）**：~~允许模型经工具直接创建工作区归属的任务，复用阶段一 SDR-006 的代建门槛（≤3 次放行 / 超预算问询）。~~ **被 SDR-105/D-M8 推翻**（用户裁决 2026-10-31）：「小额放行」逻辑对工作区任务不成立——每次运行都是全新无人值守会话，成本不可见且不可折叠，任何权限模式下的自动放行都等于让无限期未来运行绕过用户；改为提议-审批模型（D-M8），运行时姿态三档（D-M2）保留但与创建审批区分为两个独立决策点。原文被否决备选中「一刀切禁止模型创建」的方向被部分吸收——禁止的**直接创建**成立，但以「提议」形态保留 Agent 的起草价值。
- **D-M8 提议-审批模型（SDR-105，用户裁决 2026-10-31）**：Agent 对工作区任务**没有直接创建权**——经工具的创建请求一律转为**提议**（完整草案），经**用户审批**后才创建任务；审批是 never-auto-approve 语义：**任何权限模式（manual/auto/yolo/无人值守）都不能自动通过**，等价于阶段一「无人在场一律拒绝」语义的强化版（从「无人时拒」升级为「任何模式都等人」）。机制上复用既有反向问询审批通道呈现提议（详见架构 ADR-013）。与阶段一 SDR-006 代建门槛的关系：门槛管**会话级任务**（agent 自计时，小额放行成立）；审批管**工作区任务**（用户产品面，每次运行成本不可见，无小额语义）——两者不同物、不互相替代。血统防线（阶段一 SDR-007，SDR-106 收窄为循环任务）对工作区任务同样生效（D.0d）。被否决备选：a) 沿用 D-M7 的门槛复用（见 D-M7 取代原因）；b) 完全禁止模型涉入工作区任务（用户不想手把手定义工作流，Agent 起草是真实价值——一刀切禁止把委托逼回纯手工）；c) 按权限模式放行（yolo/auto 下自动通过——用户裁决明确：任何模式不可绕过）。

  **为什么小额放行逻辑止步于会话级**（两类成本形态对照）：

  | 维度 | 会话级任务（agent 自计时） | 工作区任务 |
  |---|---|---|
  | 预算可声明性 | 创建时即可声明总次数；一次性视同 1 次 | 每次运行都是全新的无人值守会话，不存在可声明的「单笔小额」 |
  | 审批可折叠性 | ≤3 次免审放行；成本可见、可折叠成一次小额决定 | 一次批准涵盖**无限期的未来运行**，成本在批准时刻不可见、不可折叠 |
  | 活跃数封顶 | 会话内血统链累计上限（初值 12）封顶 | 无「小额」语义可用；唯一入口是提议-审批（never-auto-approve） |

  结论：两类任务的成本**形态不同**（单笔可声明的短期看护 vs 无限期的新会话运行），放行逻辑不共用——小额豁免只对前者成立。

## 9. SDR 记录（阶段二）

- **SDR-101（2026-10-30）**：工作区任务 = 每次运行新建执行会话（不是注入既有会话）。背景：#181 的核心形态裁决——「注入某个常驻会话」要求一个永不关闭的宿主会话（幽灵会话），与懒物化、会话生命周期、fork 口径全面冲突；「每次运行新建」与无 UI 起跑已验证可行（print 模式先例，证据见 context §5 前置件）。决策：B.1/B.2 形态——执行会话不驻留驱动、不进索引（有产出才显式落盘）。被否决备选：a) 常驻宿主会话（现状会话耦合之外再造一个不可关闭的会话，所有会话语义被它绑架）；b) 无会话直接跑引擎回合（绕过会话基建——权限、事件、用量归因全部重造）。影响范围：Epic B、V11-V13、架构 §8。
- **SDR-102（2026-10-30）**：#181 四个开放问题的产品裁决落档——并发默认跳过（D-M3）、通知复用既有任务通知体系（D-M6）、留存跟随既有会话留存策略（D-M5）、成本先实耗后预估（D-M4）。背景：四问在 issue 中开放，本文按「最小新机制优先」逐项裁决；均记录被否决备选于对应 D-M 条目。影响范围：D-M3/4/5/6、V14/V18/V20、C.2/C.3。
- **SDR-103（2026-10-30）**：权限姿态三档显式选择。背景：#181 验收标准要求「permission mode 显式选择并可见」；只有阶段一的「问询一律拒」一档无法覆盖信任全自动场景。决策：三档（拒问询默认 / auto 复用 / 只读观察），选择记录于任务、运行留痕（D-M2/D.1-D.3）。**（2026-10-31 范围澄清，SDR-105）：本裁决的适用范围是「运行时权限姿态」——任务运行中用什么权限执行；「创建审批」（Agent 提议的任务能否建）是独立决策点，由 SDR-105 的提议-审批模型裁决，本裁决原文若被读作涵盖创建放行（如 D-M7 曾引用本条门槛逻辑），以 SDR-105 为准。**被否决备选见 D-M2。影响范围：Epic D（§5.2 部分）、V15-V17、架构 §9。
- **SDR-104（2026-10-30）**：阶段二三裁决落档——a) 全局可见性 Epic E（聚合视图是 #180 验收第一条；阶段一 SDR-008 先行覆盖会话级聚合，本阶段扩展到工作区任务与双口径投递条件标注）；b) 未打开执行会话的清理路径（D-M5 b 层：暂存 7 天未打开即丢弃，运行记录保摘要）；c) 模型可代建工作区任务（**D-M7 该项已被 SDR-105 取代**——工具入口的裁决改为提议-审批；a/b 两项不受影响）。背景：三者均为评审识别的缺口——可见性缺口与投递缺口是两个问题（前者零成本修复且是信任第一现场）；悬空会话不清理正是 #181 开放问题 1 指出的无界堆积形态；工具入口不裁决则模型涉入工作区任务处于无规则地带。被否决备选分别见 SDR-008、D-M5、SDR-105。影响范围：Epic E、B.3、V16a/V16b/V21-V23、架构 §6/§8/§9.3。
- **SDR-105（2026-10-31，用户裁决）**：工作区任务的创建权限模型 = 提议-审批，Agent 无直接创建权，never-auto-approve。背景：用户裁决工作区定时任务（每次运行 new session 的工作流）是**用户拥有的产品面**——用户不想手把手定义复杂工作流，Agent 可以代为起草/提议，用户 check 是否符合意图后审批；但 Agent 没有直接创建权，**无论何种权限模式（manual/auto/yolo/无人值守）都必须经用户审批，没有任何模式可以绕过**。这与阶段一 SDR-006 的「小额放行」门槛（≤3 次放行）是两种逻辑：工作区任务每次运行都是全新无人值守会话，**成本不可见且不可折叠**——一次审批涵盖无限期未来运行，不存在可放行的「小额」。决策（D.0/D.0a-D.0e、D-M8）：工具创建请求一律转为提议（完整草案呈审）；审批不可被任何模式自动通过（等价于 deny_when_unattended 的强化版：never-auto-approve）；拒绝作废草案并回传改道指引；用户直建无需审批；血统防线沿用（D.0d，收窄口径见阶段一 SDR-106）；**运行时权限姿态三档（SDR-103）保留**，但明确区分为两个独立决策点（创建审批管「能不能建」、运行时姿态管「怎么跑」）。**（评审轮 3 补充裁决，并入本 SDR）**：a) never-auto-approve 检查置于既有 headless auto-approve 翻译分支之前——「yolo/auto + 有人在但客户端断连」时提议不被自动批准（架构 §9.3 检查顺序硬化 + 四模式 × 三在场态推演表）；b) 批准/拒绝回执经既有通知通道在下一次 agent 活跃时注入，批准 = 任务已创建（id）回执（D.0e）；用户改草案 = 拒绝 + 修改意见回传 + 重新提议（否决直接编辑草案）；提议 72 小时无响应作废（实施可调）；草案提示词按不可信内容呈现（防注入载体）；c) 工具入口无 scope 参数——模型可达面只有会话归属创建，workspace 归属只能经提议或用户直建进入（架构 ADR-014，模型无法谎报归属绕过审批）。被否决备选见 D-M8（门槛复用 / 一刀切禁止 / 按模式放行）及 D.0e/D-M6（直接编辑草案 / 通知不带摘要 / 新建外部投递通道）。影响范围：Epic D 全部（§5.1 新增 D.0d 收窄/D.0e、§5.2 保留）、D-M7（被取代）、D-M8（新增）、V16a/V16b/V16c/V20a、架构 §9.3/§9.4/ADR-013/ADR-014、glossary CS7/CS8。

## 10. 未来增强提案（阶段二非本批）

- **P-CS4 任务级规则挂接**：把既有权限规则体系（会话级批准记忆等）按任务维度挂接为第四档之后的细化能力。
- **P-CS5 工作区任务日历视图**：任务的下次触发、历史运行在日历面上呈现；无排期诉求不做。
- **P-CS6 进程外调度（守护形态）**：服务不跑时也触发（OS 级定时唤醒或独立守护）——超出「服务内调度」边界，待产品判断。
