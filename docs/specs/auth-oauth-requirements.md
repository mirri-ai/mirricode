# 认证（auth-oauth）需求文档

> 本文档记录 TS 引擎已支持的用户身份认证能力基线，作为 Rust Core 的对齐基线（parity floor）——**是 Rust 应当匹配的底线，不是限制 Rust 只能做到这些**。超出 TS 现状的设计改进以「未来增强提案」章节单独披露，永不反向对齐削弱。
> 验收标准统一采用 Given-When-Then 格式。技术机制见 [auth-oauth-architecture.md](auth-oauth-architecture.md)；现状盘点（代码事实、差异矩阵）见 [auth-oauth-context.md](auth-oauth-context.md)，本文不重复。

## 0. 领域边界

**本域覆盖**：用户身份认证的端到端闭环——登录发起（CLI / TUI / web / desktop / ACP 宿主各入口）→ 设备码授权流 → 访问令牌的获取、安全存储、刷新与过期处理 → 多认证方式（OAuth 与 API key）及其互斥 → 认证状态在各界面的呈现 → 失败路径（拒绝、超时、网络错误、令牌被吊销）→ 登出与清理。

**不在本域**（引用相邻域，不重复定义）：

| 相邻域 | 边界划分 |
|---|---|
| approval（审批授权） | 工具执行过程中的权限审批交互属 approval 域；本域只管"用户是谁"（认证），不管"允许做什么"（授权审批）。 |
| mcp（MCP 服务器认证） | 远程 MCP 服务器自身的 OAuth 授权流（需授权状态、授权工具、连接恢复）属 mcp 域（见 `mcp-requirements.md` Epic E6）。本域仅提供"平台账户登录"，两者协议与生命周期互不相干。 |
| model-settings（配置与模型） | 登录成功后写入的模型目录、默认模型选择、curated 模型、provider 管理页属 model-settings 域；本域定义"登录触发装配 / 登出触发清理"的契约与触发时机，模型清单内容与选择策略由 model-settings 域裁决。 |
| 服务访问鉴权 | 本地守护进程自身的访问凭证（bearer token / 密码、40101 豁免流程）是**服务访问控制**，不是用户身份认证；属服务运行域。本域文档仅在架构层声明这一边界以防混淆。 |
| non-functional（遥测） | 登录/登出/刷新的遥测事件命名与上报归遥测面；本域只定义"哪些认证事件必须可观测"。 |
| 反馈提交通道 | 反馈提交/上传复用本域的托管凭证供给（工具箱附带能力，见 architecture §7）；反馈的 UI 与提交流程不在本域。 |

**术语表**（域内规范名，跨域术语的注册清单见 ROADMAP）：

| 规范名 | 形态/示例 | 含义 | 禁止的叫法 |
|---|---|---|---|
| 托管账户登录 | `managed:mirri-code` | 平台 OAuth 账户（Mirri Code）登录，token 由客户端保管 | ~~Mirri OAuth 登录~~、~~kimi 登录~~（用户可见文案允许品牌名，规格内部统一用规范名） |
| 设备码 | RFC 8628 `user_code`，如 `ABCD-1234` | 用户在另一设备上输入以完成授权的一次性代码 | ~~验证码~~（易与 2FA 混淆；用户可见英文原文 "Verification code" 指它） |
| 授权页地址 | `verification_uri_complete` | 已内嵌设备码的授权链接，打开即免手动输入 | ~~回调地址~~（本域无浏览器回调流） |
| 凭证槽 | `oauth/mirri-code`、`oauth/mirri-code-env-<指纹>` | 一份登录凭证在本地凭证库中的存储位置；不同环境（授权主机 + 服务地址组合）各占一个槽 | ~~账户~~（一个账户可在多环境各有一槽）、~~profile~~（与 agent-profile 域撞名） |
| 失效墓碑 | 空 access_token 的凭证记录 | 凭证文件仍在但服务端已拒绝——「曾登录过、现在需重登」，区别于「从未登录」 | ~~删除的 token~~（文件并未删除） |

## 1. 角色与场景总览

- **P1 · 新用户**：首次启动，无任何凭证与模型配置，需要引导完成第一次登录。
- **P2 · CLI/TUI 用户**：在终端中通过命令或斜杠命令登录、登出、切换认证方式。
- **P3 · web/desktop 用户**：通过浏览器页面（desktop 为其外壳）完成登录，由守护进程驱动授权流。
- **P4 · ACP 宿主（如编辑器插件）**：宿主自己不实现登录界面，复用 CLI 的终端登录入口。
- **P5 · API key 用户**：不走平台账户，直接使用平台 API key 认证。
- **P6 · 多环境/自托管用户**：通过环境变量切换服务地址/授权主机，需要在多个环境各自持有凭证且互不污染。

**功能闭环**（每个环节都是验收点，任何一环缺失即闭环未合拢）：

```
发起登录（P1-P4 各入口）
  → 设备码授权流（出码 → 用户在浏览器授权 → 客户端轮询）
  → 令牌获取与安全存储（凭证槽）
  → 登录后配置装配（托管 provider + 模型目录写入，引用 model-settings）
  → 会话期令牌消费（懒刷新、过期处理、401 引导重登）
  → 认证状态呈现（欢迎页 / 登录页门禁 / 会话内提示）
  → 失败路径（拒绝 / 超时 / 网络错误 / 令牌吊销）
  → 登出 / 切换（凭证删除 + 配置清理 + 会话收敛）
```

## 2. Epic A：登录发起与入口

### US-A1 · CLI 子命令登录

作为 P2 用户，我在终端运行 `mirri login` 时，产品以非交互的设备码流完成登录，无需我进入交互界面。

- **A1.1 发起**
  - Given 我在终端运行 `mirri login`（无参数），When 命令开始执行，Then 产品立即启动设备码授权流，并在拿到授权页地址后**先打印手动回退信息、再尝试打开浏览器**——即使浏览器打开失败（无头环境、无桌面），我也能从屏幕上拿到完整链接与设备码。
  - **A1.2 用户可见输出**（stderr，逐行）
    - `Opening browser for Mirri device login: <授权页地址>`
    - `If the browser did not open, paste the URL above and enter code: <设备码>`
    - `Code expires in <秒数>s.`（仅当服务端返回了有效期）
    - `Waiting for authorization to complete...`
  - **A1.3 成功**：Given 我在浏览器完成授权，When 流程结束，Then 我看到 `Logged in to <provider 名>.` 且进程以退出码 0 结束。
  - **A1.4 Ctrl-C 取消**：Given 授权仍在等待，When 我按 Ctrl-C，Then 流程中断、我看到 `Login cancelled.`、进程以退出码 1 结束，且**不留下半成品凭证或半装配配置**。
  - **A1.5 其他失败**：Given 流程失败（网络错误、服务端拒绝等），When 错误发生，Then 我看到 `Login failed: <具体原因>`、进程以退出码 1 结束。

### US-A2 · TUI 斜杠命令登录

作为 P2 用户，我在 TUI 中通过斜杠命令完成登录，全程不离开交互界面。

- **A2.1 命令入口**：内置斜杠命令名为 `/login`（别名 `login-with-kimi`，描述 "Select a platform and authenticate"）；Given 我输入该命令，When 执行，Then 弹出**平台选择器**，选项为「Mirri Code (OAuth)」与各开放平台（API key 方式，见 US-G 组）。按 Esc 取消选择器则整个登录中止，无副作用。
- **A2.2 设备码展示**：Given 我选择了 OAuth 平台，When 服务端发放设备码，Then 界面在对话流中插入一个圆角边框卡片：标题 `Sign in to Mirri Code`、提示行 `Visit the URL below in your browser to authorize:`、授权页地址（高亮）、`Verification code:  <设备码>`（强调色）、辅助提示 `Press Ctrl-C to cancel`；同时**自动尝试打开浏览器**（失败不影响展示）。
- **A2.3 等待反馈**：卡片下方出现旋转等待指示（`Waiting for authorization…`），授权期间用户可以继续等待或取消。
- **A2.4 成功收尾**：Given 授权完成，When 流程结束，Then 等待指示以 `✓ Logged in.` 收尾；随后自动刷新模型配置——刷新失败时明确提示 `Authentication successful, but failed to refresh config: <原因>`（登录本身已成功，不误导为登录失败）。
- **A2.5 重复登录**：Given 我此前已登录且令牌仍有效，When 我再次执行 `/login` 并选择 OAuth，Then 产品不重复走设备码流，直接刷新令牌并提示 `Already logged in. Model configuration refreshed.`。
- **A2.6 取消**：Given 授权仍在等待，When 我按 Ctrl-C（取消优先于其它在途操作处理），Then 指示以 `✗ Login cancelled.` 收尾，无其它副作用。
- **A2.7 失败**：When 登录失败，Then 指示以 `✗ Login failed.` 收尾并显示 `Error: Login failed: <原因>`；失败以日志记录（注：遥测 `login` 事件仅覆盖成功路径，见 K.3）。

### US-A3 · web 登录对话框

作为 P3 用户，我在浏览器中通过登录对话框完成登录，由本地守护进程驱动授权流。

- **A3.1 入口**：登录入口有三处——未登录时的整页登录门（"Sign in" 按钮）、设置面板 Account 标签、斜杠命令 `/login`（描述 "Sign in to Mirri in the browser"）。
- **A3.2 授权流状态机**：对话框状态依次为 `starting → device-code →（成功|过期|错误）`：
  - `starting`：显示 `Starting authorization flow…`；
  - `device-code`：显示 `Click the button below to authorize in a new browser tab.` 与主按钮 **Authorize in browser**（在新标签页打开授权页地址，不占用当前页）；或回退分隔线 `or` + `On another device? Open <裸地址> and enter the device code:`（设备码等宽字体大间距展示，附 **Copy** 复制按钮，复制后变 `Copied`、约 2 秒后还原）；下方显示 `Waiting for authorization, signs in automatically…` 与 mm:ss 倒计时。
  - **A3.3 无二维码**：设备码为纯文本展示；TS 现状不提供二维码（见「未来增强提案」）。
- **A3.4 成功**：Given 服务端确认授权，When 轮询到完成态，Then 对话框显示 `Authorized` / `Loading, will close automatically…`，约 1.2 秒后自动关闭并触发全局会话重载。
- **A3.5 过期/取消**：显示 `Authorization code expired` / `Please restart the authorization flow`，提供 **Retry** 与 **Close**；重试重新发起完整流程。
- **A3.5b 拒绝（TS 现状行为）**：用户在授权页选择拒绝后，REST 快照状态为 `denied`，但 web 对话框的轮询消费面不识别该状态——表现为**继续轮询**，直至流被服务端回收、连续轮询落空后落入「守护进程失联」错误态（拒绝最终以误导性信号收场；改进建议见提案 P-9，CLI/TUI 面无此问题——其登录由库同步驱动，拒绝直接表现为 `Login failed`）。
- **A3.6 守护进程失联**：Given 轮询连续 3 次失败，Then 对话框进入失联态：`Lost connection to the daemon` / `Authorization polling failed repeatedly. Check the mirri-code process and try again.`——**不得**把失联误报为登录失败或未登录。
- **A3.7 能力缺失**：Given 守护进程版本过旧不支持登录端点，Then 显示 `The current daemon does not support login yet` / `Please upgrade mirri-code and try again`。
- **A3.8 关闭即取消**：Given 对话框在授权等待中被我关闭，Then 以尽力而为方式通知守护进程取消在途授权流（守护进程侧有独立超时兜底，见 US-E 组）。

### US-A4 · ACP 宿主终端登录

作为 P4 用户（编辑器插件等 ACP 宿主），我的宿主不需要自带登录界面，可复用 CLI 的终端登录。

- **A4.1 一等终端认证**：宿主通过 ACP 协议发现 `terminal-auth` 方法（名称 `Login with Mirri account`、描述 `Open the device-code login flow in a terminal.`），按协议在代理启动参数后附加 `--login` 即可在终端执行设备码登录。
- **A4.2 旧版宿主回退**：对未支持一等方法的宿主，服务在协议元数据中同时广播传统的 `terminal-auth` 描述（命令 + `login` 参数 + 环境变量透传），保证旧宿主也能拉起同一登录入口。
- **A4.3 数据根一致**：宿主为登录子进程透传的数据根环境变量与代理进程一致，子进程登录写入的凭证被代理进程直接读取——宿主无需了解凭证格式。

### US-A5 · REST 接口登录（服务端消费方）

作为服务端（守护进程 / 桌面端背后）的 API 消费方，我通过 REST 驱动授权流。

- **A5.1 发起**：`POST /oauth/login`（可选 provider 参数，缺省为托管账户）同步返回：流标识、授权页地址、设备码、有效期（秒）、轮询间隔、过期时刻、状态 `pending`；服务端未返回有效期时按 15 分钟兜底上报。
- **A5.2 已登录快速路径**：Given 该 provider 已持有有效令牌，When 发起登录，Then **不发放设备码**，直接返回 `{status: 'authenticated'}`——消费方无感知地拿到「已登录」结论。
- **A5.3 单在途流**：Given 某 provider 已有一个等待中的授权流，When 再次发起登录，Then 旧流先被取消（状态 `cancelled`）再发放新流；同一 provider 任意时刻至多一个在途流。
- **A5.4 轮询**：`GET /oauth/login` 返回当前流快照（状态、授权页地址、设备码、过期时刻、错误信息、完成时刻）；无流或已被回收时返回 `null`。
- **A5.5 取消**：`DELETE /oauth/login` 取消在途流；对流已终结时幂等返回当前状态而不报错。
- **A5.6 终态保留**：进入终态（authenticated / denied / expired / cancelled）的流在内存中保留约 5 分钟供消费方最后一次轮询落点，之后回收；等待中的流无此保留，由上游授权流自身的总超时兜底。
- **A5.7 配置变更失效**：Given 某 provider 的配置在授权等待期间被增加/修改/删除，When 变更事件到达，Then 该 provider 的在途流被取消——轮询消费方看到 `cancelled` 终态及理由 `Provider configuration changed during login.`。

## 3. Epic B：设备码授权流协议（RFC 8628）

作为任何入口的用户，我看到的授权流行为一致，遵循设备码授权标准。

- **B.1 出码**：客户端向授权主机申请设备码，响应必须含设备码、用户码、含码授权页地址——任一缺失即视为授权流失败（不展示残缺信息）。
- **B.2 轮询节奏**：按服务端给定的间隔（缺省 5 秒）轮询令牌端点；服务端要求降速（`slow_down`）时**永久**增加 5 秒并继续。
- **B.3 等待中**：`authorization_pending` 继续轮询，对用户表现为持续等待。
- **B.4 用户拒绝**：`access_denied` → 流失败，向用户呈现「授权被拒绝」及服务端给出的描述。
- **B.5 服务端码过期**：`expired_token` → **自动重新申请设备码**并继续（在本地总预算内），用户仅需在新一轮授权页完成操作；重新出码时回调消费方更新展示的码与地址（现状注记：web 对话框只在发起时渲染一次、轮询不刷新展示——换码后用户持已作废的码直至超时；TUI 换码时会插入新的设备码卡片但前一张卡片的等待指示不收尾、持续旋转；改进并入提案 P-9；CLI 子命令面重复打印完整四行、无此问题）。
- **B.6 本地总预算**：整个登录流程有 15 分钟本地墙钟预算——即使服务端不报过期，超时后流以「超时」失败，用户看到明确超时提示；服务端返回的设备码有效期被原样呈现（未返回时 REST 面按 15 分钟兜底上报）。对外展示的有效期承诺不晚于本地预算属超出 TS 现状的增强，见提案 P-10。
- **B.7 响应完整性**：令牌端点返回必须同时含访问令牌、刷新令牌、有效期三要素，任一缺失或非法（非正数、空串）即失败——**不落盘残缺令牌**。
- **B.8 客户端身份标识**：每次授权请求携带设备身份头（平台、版本、设备名、设备型号、系统版本、设备 ID），授权主机可据此识别客户端家族；设备 ID 在本机首用时生成并持久化（见 US-D 组）。
- **B.9 错误信息透传**：服务端错误响应中的用户可读信息被提取并呈现（按约定字段优先级取第一条非空信息：直述字段 → 错误串 → 嵌套错误对象 → 错误数组），不显示「未知错误」占位。

## 4. Epic C：令牌存储与安全

作为关注安全的用户，我的登录凭证被安全存储，且不会被环境误用。

- **C.1 存储位置与权限**：令牌以 JSON 文件存放在用户数据目录的 `credentials/` 子目录；目录权限 0700、文件 0600（含写入后二次收紧），非 Windows 平台尽力而为。
- **C.2 原子写**：写令牌先写临时文件、强制刷盘、再原子改名——**任何时刻磁盘上不存在半个令牌文件**；失败时清理临时文件。
- **C.3 损坏容错**：读取时文件缺失、JSON 损坏、结构不符一律视为「无令牌」，不抛错、不崩溃。
- **C.4 路径安全**：凭证名经过净化，携带路径分隔符、`..`、隐藏文件前缀的名称被拒绝——凭证名不能逃逸凭证目录。
- **C.5 凭证槽隔离**：每个「授权主机 + 服务地址」组合映射到独立凭证槽；默认组合占用规范槽，非默认组合按指纹派生专属槽——**多环境切换不会串用凭证**（A 环境登录的令牌不会被 B 环境的请求拿去用）。
- **C.6 环境覆盖**：服务地址与授权主机可被环境变量覆盖（含新旧两组变量名，见 context 差异矩阵）；登录、运行时消费、配置装配从同一槽位推导，写入与读取永远一致。
- **C.7 配置引用一致性**：运行时若环境变量指定的槽与配置中记录的槽不一致，以环境变量推导为准——防止换环境后读到旧槽凭证。

## 5. Epic D：设备身份

作为用户，我的设备在授权与托管服务面前有稳定、诚实的身份。

- **D.1 设备 ID**：首次使用时生成随机标识并持久化于用户数据目录（0600，尽力而为）；此后所有请求复用同一 ID。持久化失败不阻塞使用（退化为内存 ID）。
- **D.2 身份头诚实性**：设备名（主机名）、型号、系统版本等取真实系统值；非 ASCII 字符被清洗，取不到时用 `unknown` 占位，**不伪造**；产品名与版本为必填非空，缺失即报配置错误而非发送空值。
- **D.3 各宿主自报平台**：CLI / SDK / web 各宿主显式声明自己的平台标识，授权主机据此区分客户端类型；不得静默继承其它宿主的平台值（现状注记：v1/v2 两代协议库的平台标识值存在漂移——同一 CLI 宿主经 v1 门面与 v2 引擎会向授权主机报两个值，见 context §12.3）。
- **D.4 自定义请求头**：用户可通过环境变量以 `Name: Value` 逐行格式为出站请求附加自定义头，作为**最低优先级**层——身份头、provider 自定义头、认证头都会覆盖它；无冒号的行被忽略。

## 6. Epic E：令牌刷新、过期与多进程安全

作为长时间使用的用户，我的登录自动保持有效，且并发使用不会互相破坏。

- **E.1 懒刷新**：令牌在**被使用时**检查剩余寿命，剩余低于阈值（有效期的一半、下限 5 分钟）才刷新；不做后台轮询——空闲时零网络开销。
- **E.2 单进程并发合并**：同进程多个并发请求同时需要刷新时，只发起一次刷新，所有请求共享结果；「强制刷新」请求不会搭已过时的非强制刷新结果便车。
- **E.3 跨进程互斥**：多个进程（如多个 CLI 实例）同时需要刷新同一凭证槽时，通过凭证槽级文件锁串行化；拿锁后重读凭证，若他进程已刷新则直接复用，不浪费一次刷新。
- **E.4 刷新重试**：限流（429）与 5xx 错误以指数退避重试（默认 3 次内）；网络层失败（DNS、拒连、超时）同样可重试。
- **E.5 不可恢复拒绝**：刷新被拒（401/403/授权失效）时判定凭证失效：
  - 若是**他进程并发刷新导致的竞态**（磁盘上已出现新令牌），自动恢复使用新令牌；
  - 否则写入**失效墓碑**（凭证记录保留、内容清空），使后续任何进程看到「曾登录、需重登」而非「从未登录」。
- **E.6 失效后的用户引导**：令牌缺失/被拒/无刷新令牌时，错误信息明确引导重新登录（"Run /login to authenticate." / "re-login required"），并被映射为协议级「需要登录」错误码供各界面消费（TUI 显示 `OAuth login expired. Send /login to login.`，会话中断但界面仍可用）。
- **E.7 登录期自动降级**：已持有令牌的用户执行登录时先尝试静默刷新；刷新被拒则**自动转入设备码流**，无需用户先手动登出。
- **E.8 刷新可观测**：每次刷新结果（成功 / 失败+原因分类）可被宿主观察并上报遥测。
- **E.9 锁的逃生门**：文件锁在不支持的平台自动禁用、可被环境变量显式关闭；锁配置了却拿不到时**快速失败**（不无锁刷新），避免旋转刷新令牌竞态。

## 7. Epic F：认证状态呈现与就绪门

作为用户，我在每个界面都能如实知道当前的登录/就绪状态。

- **F.1 综合就绪快照（REST）**：`GET /auth` 返回 `{ready, providers_count, default_model, managed_provider}`——`ready` 为「至少一个 provider + 有默认模型 +（若存在托管 provider）其凭证未被判失效」；`managed_provider.status` 的契约枚举含四种取值（`authenticated / expired / revoked / unauthenticated`），就绪计算将 `revoked` 视为未就绪（现实现只产生 `authenticated / unauthenticated`，`expired / revoked` 为契约保留位，见 context 差异矩阵）。
- **F.2 web 登录门禁**：Given 初始化完成后就绪快照为未就绪，When 用户访问任何页面，Then 整页登录引导（`Welcome to Mirri Code` / `Connect your Mirri Code account before starting or continuing conversations.` / **Sign in** 按钮）接管，且浏览器地址被替换为 `/login`（不污染原地址历史）；登录成功后回到原地址。
- **F.3 首载容错**：就绪探测的瞬时失败（网络抖动）按可重试处理（周期约 2 秒重试；首次失败静默、自第二次起在启动页显示连接原因），**不得**把瞬时失败读作「未登录」把已登录用户弹去登录页。
- **F.4 TUI 欢迎页**：未配置模型时欢迎页以警示色显示 `Run /login or /provider to get started.` 及 `not set, run /login or /provider`。
- **F.5 TUI 常驻提示**：无模型时发送 skill/plugin 命令提示 `LLM not set, send "/login" to login`；无活动会话时提示 `No active session. Send /login to login.`。
- **F.6 web 设置面板**：Account 标签显示登录状态（登录则显示 provider 名）、当前默认模型与登出按钮；移动端设置页提供登录/登出一行。sidebar 提供退出登录/未登录/登录入口（`Sign out` / `Not signed in` / `Sign in`）。
- **F.7 会话内失败提示**：模型调用认证失败时，会话错误面以 provider 级警示呈现（`Model authentication failed`）；需要登录的错误码单独呈现为过期重登提示（F/E.6）。
- **F.8 认证就绪门（引擎级）**：发起会话/请求前引擎校验「有 provider、模型可解析到 provider、该 provider 有可用凭证（API key 或缓存 OAuth 令牌）」；三类失败分别报「完成登录或配置 provider」「模型未解析到 provider」「provider 无凭证」，错误均为公开、不可重试、附用户行动建议（如 `Run /login to authenticate with the OAuth provider.`）。
- **F.9 互斥强制**：同一 provider（或模型）同时配置 API key 与 OAuth 引用时，请求装配**直接报冲突错误**，不静默择一——两种认证方式互斥，可见即强制。

## 8. Epic G：API key 认证方式

作为 P5 用户，我可以不经平台账户，直接用平台 API key 完成认证。

- **G.1 入口**：`/login` 平台选择器中除「Mirri Code (OAuth)」外，列出各开放平台（名称含 API key 标识与控制台域名）。
- **G.2 密钥输入**：选择平台后弹出 API key 输入框（标题 `Enter API key for <平台名>`、副标题显示 base_url 与 `saved to ~/.mirri-code/config.toml`）；输入以圆点掩码显示，回车提交、Esc/Ctrl-C/Ctrl-D 取消，空值提示 `API key cannot be empty.`，页脚 `Enter to submit · Esc to cancel`。
- **G.3 即时验证**：提交后用该 key 实时拉取平台模型列表验证有效性；失败提示 `Failed to verify API key: <原因>`；**401 时追加引导** `Hint: If your API key was obtained from Mirri Code, please select "Mirri Code" instead.`（帮用错渠道的用户走到正确路径）。
- **G.4 模型选择**：验证通过后从平台模型清单（按平台前缀过滤）选择默认模型与思考档位；过滤后清单为空时提示 `No models available for this platform.`；完成提示 `Setup complete: <平台名> · <模型>`。
- **G.5 配置落盘**：API key 明文保存在用户配置文件的对应 provider 条目中（区别于 OAuth 凭证文件），并装配该 provider 的模型目录（细节归 model-settings 域）。
- **G.6 API key 与 OAuth 平等消费**：请求装配时 API key（模型级 → provider 级 → 环境变量推导的 provider 级）与 OAuth 凭证走同一凭据解析链，互斥规则见 F.9。

## 9. Epic H：登出与清理

作为用户，登出后不留任何可被误用的残留。

- **H.1 CLI/TUI 登出选择**：`/logout`（别名 `/disconnect`）枚举可登出对象：托管 OAuth（有凭证或配置残留时，描述 `OAuth login`）+ 各 API key provider（描述为其 base_url）；无可登出对象时提示 `Nothing to logout.`；选择器默认聚焦当前使用中的 provider。
- **H.2 登出效果（OAuth）**：删除凭证槽中的令牌文件 + 从用户配置移除托管 provider、其模型别名、搜索/抓取服务引用；若默认模型指向被移除的别名则清空默认模型，且此时（v2）同时清空思考配置；若默认 provider 指向托管 provider 则清空之（v1 链路）。v1 CLI 链路的登出清单不含思考配置。
- **H.3 会话收敛**：登出的若是当前活跃 provider，则刷新运行时配置并结束当前会话（会话关闭理由 `logged out`）；登出其它 provider 仅刷新配置。
- **H.4 完成反馈**：`Logged out from <名>.`；被登出 provider 名为产品名，API key provider 显示其 id。
- **H.5 REST 登出**：`POST /oauth/logout` 执行同语义清理，并在登出过程中取消该 provider 的在途授权流（对消费方表现为返回前流已取消）；返回 `{logged_out: true, provider}`。
- **H.6 web 登出**：设置面板/侧边栏登出按钮 → 调用 REST 登出 → 重新探测就绪并重载会话；失败以操作失败路径提示。
- **H.7 取消在途流**：登出时若有等待中的授权流，先取消再清理——登出后的状态探测永远看到干净的未登录态。

## 10. Epic I：登录后配置装配（触发契约）

作为用户，登录成功即开箱可用，登出即干净收敛——配置装配的触发与完整性归本域，装配内容归 model-settings 域。

- **I.1 装配触发**：设备码流成功（或已登录快速路径确认）后，自动用新令牌拉取托管平台模型目录并写入用户配置：托管 provider（OAuth 引用）、模型别名、搜索/抓取服务引用、默认模型与思考默认值。
- **I.2 装配重试链**：装配请求被拒（401/402/403）时：已登录场景先强制刷新令牌重试一次，再被拒则**降级走设备码流重新登录**后装配——两级回退后仍失败才把错误交给用户。
- **I.3 重复登录保选择**：已登录用户重复登录时，若当前默认模型仍可用（含默认模型属于**非托管**第三方 provider 的情形）则**保留用户选择**，只刷新目录；无有效选择时取服务端首推模型。
- **I.4 目录自动刷新**：已登录快速路径登录成功后，尽力而为刷新服务端模型目录（失败不阻断登录成功结论，仅记录）。
- **I.5 装配一致性**：配置中记录的凭证槽引用与实际存储槽位由同一推导规则得出（见 C.5-C.7），登录写入的槽永远等于运行时读取的槽。
- **I.6 会话衔接**：TUI 登录成功后刷新配置并按默认模型激活/新建会话；web 登录成功后全局重载。

## 11. Epic J：账户信息与用量查询（引擎级）

作为登录用户，我的账户资料与用量可被查询（TS 现状为引擎/REST 能力；web UI 未消费，见 context 差异）。

- **J.1 账户资料**：`GET /oauth/userinfo` 返回托管账户资料：昵称、状态、区域、等级、头像、邮箱、手机号（脱敏形态）、注册/最近登录时间等；缺省字段独立降级，仅账户标识缺失视为畸形。
- **J.2 用量**：`GET /oauth/usage` 返回用量摘要（周期限额行 + 多档限额数组 + 加量钱包余额/月消费上限），字段拼写宽松兼容；重置时间格式化为人类可读（`resets in 2h 15m`）。
- **J.3 查询鉴权**：两项查询自动复用托管凭证并按需刷新；401/404 给出引导性错误（检查登录 / 该端点在当前套餐不可用）；请求超时 8 秒。
- **J.4 失败不抛出**：查询失败返回结构化错误（含状态码与信息）而非异常，消费方自行决定展示。

## 12. Epic K：非功能需求

- **K.1 超时预算**：单次 OAuth HTTP 请求 30 秒；用量/资料查询 8 秒；设备码流本地总预算 15 分钟；授权流请求超时被折叠为可读错误（真实原因：DNS/拒连/TLS/超时——不显示裸 `fetch failed`）。
- **K.2 并发安全**：多进程共享凭证下，刷新串行化、竞态恢复、墓碑传播（E.3-E.5）；登录流单在途（A5.3）。
- **K.3 可观测性**：登录成功（含方式 OAuth/api_key、是否重复登录）、登出、令牌刷新（结果+原因）、首启设备 ID 生成均为遥测事件；登录失败走日志不进遥测；授权流状态转换有日志。
- **K.4 密钥不出现在明文日志**：错误信息与日志不回显令牌内容。
- **K.5 平台覆盖**：凭证锁在 Windows 自动降级、其余机制跨平台一致。
- **K.6 国际化**：web 登录/账户文案提供中英双语；CLI/TUI 文案为英文（现状基线）。

## 13. 未来增强提案（超出 TS 现状，非已支持能力）

> 以下为设计改进建议，供 Rust Core 参考；TS 现状不包含这些能力，不得作为现状被引用。

- **P-1 系统钥匙串存储**：配置结构已预留 `storage: 'file' | 'keyring'` 的凭证槽声明，但现状只有文件实现——Rust 可落地真正的系统钥匙串（macOS Keychain / Windows Credential Manager / libsecret）后端，声明即可生效。
- **P-2 浏览器回调授权码流**：本地 CLI 场景可补充「环回地址回调 + PKCE」授权码流作为设备码之外的选项（自动跳转免手动输码），设备码保留为无浏览器环境回退；与 MCP 域的授权流共用基础设施。
- **P-3 二维码设备码**：web/desktop 登录对话框对设备码附加二维码（手机扫码授权），纯文本保留为回退。
- **P-4 令牌寿命预警**：会话空闲期后台预刷新（现懒刷新在首请求处引入一次刷新延迟），或在 UI 呈现「登录即将过期」提示。
- **P-5 userinfo/usage 的 UI 消费**：引擎端点已提供账户资料与用量（Epic J），web UI 尚未消费——建议 Rust 统一在设置面板/侧边栏呈现头像、昵称、等级、用量条与重置倒计时。
- **P-6 多账户切换**：凭证槽已按环境隔离，可进一步支持同环境多账户并存与一键切换（现状同槽新登录覆盖旧登录）。
- **P-7 登录命令名统一**：~~现状多处文案指 `/login` 而实际命令为 `/login-with-kimi`（见 context 缺口）；建议 Rust 收敛为 `/login` 并为旧名保留别名，或统一全部文案。~~ **已关闭（2026-10-12，SDR-003，后由 SDR-004 取代）**：命令曾收敛为 `/login`（别名 `login-with-kimi`）；同日 SDR-004 将全部 TS 登录入口退役，`/login` 不再存在，文案统一指向 `/provider`。
- **P-8 服务访问凭证命名一致**：~~ServerAuthDialog 文案与实现注释对密码环境变量名表述不一（`MIRRICODE_CODE_PASSWORD` vs `MIRRICODE_PASSWORD`）~~ **已关闭（2026-10-09，SDR-002）**：不落地密码环境变量，弹窗文案已改为仅指引启动打印的随机凭证（防回归测试钉住「文案不含环境变量名」）。
- **P-9 web 拒绝态呈现**：用户在授权页拒绝后，web 对话框不识别 `denied` 状态（轮询消费面契约只认 pending/authenticated/expired/cancelled），持续轮询直至流回收后误报「守护进程失联」；此外服务端换码后对话框也不刷新已展示的设备码（只在发起时渲染一次）。建议 Rust 在 web 面渲染明确拒绝态（`Authorization was denied` + Retry）并随轮询同步最新设备码；TUI 换码时应收尾旧的等待指示再插入新卡片。
- **P-10 展示有效期钳制**：对外展示的设备码有效期承诺不晚于本地 15 分钟预算——TS 现状原样呈现服务端返回值、不钳制超预算值；建议 Rust 以本地预算为展示上限（回退：服务端值更小时取服务端值）。

## 14. SDR 记录

- **SDR-004（2026-10-12）**：managed login 全线退役。背景：`managed:mirri-code` 托管账号登录已在 Rust 核心与 web（提交 `50e05aa5`，2026-10-12）移除，TS 侧的登录入口（TUI `/login`、`/logout`、CLI `mirri login`、ACP terminal-auth 与鉴权门）成为孤岛——既无后端可登录，也与「无托管登录」的产品事实冲突。决策：本批移除全部 TS 登录入口——TUI 内置命令 `/login`（含别名 `login-with-kimi`）与 `/logout`、CLI `mirri login` 子命令与 ACP `--login`、acp-adapter 的 `terminal-auth` 广告与连接鉴权门全部删除；`/login` 相关用户可见文案与文档引导统一改为 `/provider`；`OAUTH_LOGIN_REQUIRED_STARTUP_NOTICE` 删除，`auth.login_required` 会话错误不再有专门的登录提示分支、按普通错误渲染，启动期登录门（`enterLoginRequiredStartupState`）同步移除。被否决备选：保留入口但提示已下线（否——入口即承诺，空转入口徒增维护与误导）；将 `/login` 重定向为 `/provider` 别名（否——命令已不存在，直接移除最诚实且无兼容负担）。影响范围：A1.1、A2.1、A2.2、A4、F.5、H、P-7（取代 SDR-003 的 `/login` 文案收敛决策，登录命令不再存在）、O-2、用户文档与 ACP 协议面（`authMethods` 恒为空）。
- **SDR-003（2026-10-12）**：P-7 落地——登录命令收敛为 `/login`。背景：命令名带有已迁移的品牌词，与品牌清理目标不符；且多数用户可见文案已指向 `/login`，而实际命令为长名——用户按文案输入会落到普通消息分支（现状证据见 context §12.1）。决策：内置斜杠命令收敛为 `/login`，旧名 `login-with-kimi` 保留为别名；TUI 常驻提示与错误消息统一指向 `/login`。被否决备选：把全部文案统一改为 `/login-with-kimi`（否——保留品牌残迹，且改动面大于单点改名）；不保留旧名别名（否——破坏既有用户习惯与已发布内容的兼容性，保留别名成本低）。影响范围：A2.1、A3.1、E.6、F.5、G.1、P-7、开放项 O-2 及用户文档。（注：`/login` 命令本身随后由 SDR-004 于同日退役。）
- **SDR-002（2026-10-09）**：关闭提案 P-8。背景：web ServerAuthDialog 弹窗文案指引设置 `MIRRICODE_CODE_PASSWORD` 环境变量，但 v2 引擎实际读取的是 `MIRRICODE_PASSWORD`、v3 Rust 核心无任何密码环境变量——提示对两个引擎都不可用。决策：不引入密码环境变量能力（保持「随机凭证 + 启动打印 + 凭证文件」这一种凭证机制）；弹窗文案改为仅指引启动打印的凭证。被否决备选：让 v3 也支持 `MIRRICODE_PASSWORD` 对齐 v2（否——为一个文案笔误反向加功能，且固定密码弱于随机凭证）。影响范围：P-8、开放项 O-3。
- **SDR-001（2026-09-12）**：本域基线建立。背景：Rust Core 迁移需要认证域的 TS 现状完整基线（此前无域内文档）。决策：以 v2 引擎 + v2-oauth 为主、v1 链路（CLI/TUI 实际消费）标记 v1-source 全量收录；桌面端作为 web 外壳只继承 web 行为。被否决备选：只记录 v2（否——CLI/TUI 主要 UX 仍在 v1 链路，会丢失消费面）；把服务访问鉴权并入本域（否——不同关注点，仅作边界声明）。影响范围：全部条目。
