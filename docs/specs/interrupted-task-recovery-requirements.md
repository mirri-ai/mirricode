# 中断任务恢复（interrupted-task-recovery）需求文档

> 状态：v1（SDR-001 建域，用户四点裁决已并入基线）· 2026-10-28 ·
> 本文是中断任务恢复域需求侧的唯一事实源（内部规格文档，不进文档站构建，中文单语）。
> 产品愿景：**重启不是失忆**——应用再打开的那一刻，用户一眼知道上次有哪些任务没做完，并且能以一次点击、不带负担地把它们接回去；没有被中断的任务时，用户获得的则是「一切已了结」的安心静默。
> 配套文档：技术机制见 [interrupted-task-recovery-architecture.md](interrupted-task-recovery-architecture.md)（下称「架构文档」）；现状盘点见 [interrupted-task-recovery-context.md](interrupted-task-recovery-context.md)（下称「context 文档」），本文不重复。
> 验收标准统一采用「假如-当-那么」三段式。
> 范围边界：本域覆盖**应用退出后重新打开时的中断感知与恢复交互**——退出方式判定、中断清单、恢复通知、会话树中断徽标、就地续跑发起；回合生命周期与准入调度本身归回合调度域；会话的存储与重放归会话持久化域；后台进程任务的死活裁决归孤儿清扫既有机制。

## 0. 领域边界

**本域覆盖**：用户从「应用退出再打开」到「把被中断的任务接回去」之间的全部产品语义——

1. **中断判定**：退出方式（优雅/异常）的记录与识别、被中断任务清单的确定；
2. **知情呈现**：重启后的恢复通知、会话树的中断徽标；
3. **恢复操作**：单个续跑、批量续跑、忽略、以及恢复后的收尾（徽标清除、通知消散）。

**不在本域**（引用相邻域，不重复定义）：

| 相邻域 | 边界划分 |
|---|---|
| turn-scheduling（回合调度） | 回合的准入、排队、结局语义（含四值结局词汇）是回合调度域的；本域只**新增**「运行中断」这一结局成因的判定与回填（词汇裁决经该域 SDR-006），并经用户消息类准入发起续跑，不发明新调度路径 |
| session-persistence（会话持久化） | wire 日志、快照、重放机制归持久化域；本域只消费「未收尾回合」这一既有磁盘事实，不改变存储格式 |
| session-management（会话管理） | 会话列表的组织交互（置顶/排序/归档）归会话管理域；本域的中断徽标是列表行上的**状态标记**，排序与分组规则沿用会话管理域既有裁决 |
| conversation-rendering（对话渲染） | 会话打开后的对话流呈现（含恢复卡片的容器规范）归对话渲染域；本域定义恢复卡片的语义（何时出现、按钮含义、点击后果） |
| background-tasks / orphan-sweep（后台任务） | 后台进程任务的死活裁决与报告归既有孤儿清扫机制；本域的中断清单只覆盖**回合**，不重复裁决后台任务 |
| goal（目标） | 目标异常结束后的收敛（Paused）归目标域；本域徽标不改变目标状态机 |

## 1. 角色与场景总览

- **R1 · 日常用户**：关掉应用去吃饭/下班，回来重开，希望知道刚才跑着的任务怎么样了，能顺手接回去。
- **R2 · 多任务用户**：同时在多个工作区跑多个任务，崩溃后不想到处翻哪个断在半路。
- **R3 · 谨慎用户**：退出就是因为任务跑歪了，不想被自动重跑，需要便宜的忽略路径。
- **R4 · 观察型用户**：重启后什么都没被中断——他要的是「一切已了结」的静默，而不是任何打扰。

**功能闭环**（每个环节都是验收点，任何一环缺失即闭环未合拢）：

```
判定（退出方式记录 + 退出瞬间在跑清单）
  → 识别（重启时确认哪些任务被中断，含异常退出的磁盘反推）
  → 呈现（恢复通知 + 会话树中断徽标，双通道）
  → 决策（逐个续跑 / 批量续跑 / 单个忽略 / 全部忽略；误关通知后从会话树补）
  → 续跑（带中断前上下文重新发起回合，独立进度，不重复已完成的工作）
  → 收尾（徽标清除、状态复位、保留期到期自动消散）
```

## 2. Epic A：中断判定（退出记录机制）

作为用户，我不需要理解服务怎么退出，但系统必须准确知道——这决定了我看到的是如实的告知还是沉默。

- **A.1 启动记录**：服务每次启动时留下「本次启动」的持久标记（启动时间 + 服务实例标识）；标记的写入必须不可被半路截断成不可读（原子落盘）。
- **A.2 优雅退出记录**：服务经任意优雅关闭通道（用户退出应用、标准关闭信号）收尾时，写「优雅退出」记录，**内容必须包含退出瞬间仍在跑的全部会话清单**（会话标识 + 中断时间），同样是原子落盘。
- **A.3 异常退出的判定**：下次启动时读取上次记录——有启动记录、无优雅退出记录，即判定上次为异常退出（不预设成因：崩溃/强杀/断电不作区分）。
- **A.4 异常退出的清单反推**：判定异常退出后，系统从会话的持久事实（有用户发起的回合、无收尾记录的会话）反推出「退出瞬间在跑」的清单；反推只考察最近一个生命周期的痕迹，**不翻旧账**（上一个生命周期之前遗留的未收尾回合不再视作中断）。
- **A.5 多实例互斥**：多个服务实例并存时（如主桌面版与轻量版），退出记录按实例区分；判定前必须先确认对方实例**确实已不在运行**（存活实例的记录不参与判定、不被清除）——A 实例的退出不冒充 B 实例的退出，也不让 B 实例的正常运行掩盖 A 实例的异常死亡，更不能把 B 实例还在跑的任务误判成 A 实例的中断。
- **A.6 只认最近一个生命周期**：每次启动完成中断识别后，消费并清除旧记录——旧的中断状态不跨生命周期累积；同一任务再次真正在跑后遇到新的退出，其中断状态刷新时间、不重复计数（仅靠旧中断状态维持、未再次在跑的会话不刷新）。

## 3. Epic B：识别与状态

- **B.1 中断状态判定**：被中断的任务 = A.2 优雅退出记录里的在跑清单（优雅路径），或 A.4 反推出的清单（异常路径）；**用户主动取消的、已正常收尾的、已归档的会话一律不算**。
- **B.2 状态呈现口径**：会话的「运行中断」状态在会话树可见，且**跨重启存活**（重启即失忆是本域要消灭的问题，现状证据见 context §2）；状态出现与消退的时机见 Epic D/E。
- **B.3 保留期**：中断状态保留 **72 小时**（从中断时刻起算）；到期自动消退，会话回到普通状态；已消退的中断不再出现在任何恢复入口里。
- **B.4 排除口径**：处于「等待用户决策」的挂起回合（代理在等回答/审批）**不计入中断清单**——判定口径只针对「正在执行」的回合。此类等待在服务退出后的实际存活状态由会话恢复（S1）机制决定，不是本域的判定前提；若恢复后等待已失效，用户经普通打开会话即可看到当时的提问上下文并自行处理。

## 4. Epic C：恢复通知（第一呈现通道）

作为 R1/R2 用户，重新打开应用时，一条通知告诉我哪些任务断了，我可以就地决定每个的去留。

- **C.1 出现时机与形态**：会话列表就绪后，以一条**非模态通知卡片**出现在界面上（不弹窗、不阻断、可关闭）；无被中断任务时**完全不出现**（R4 的静默是验收点）。
- **C.2 内容逐任务呈现**：每个被中断的任务一行，必须可见：**工作区名 + 会话标题 + 中断时间**；多个任务就是多行，每行携带独立的操作组。
- **C.3 单任务操作**：每行提供「继续」（发起该任务的续跑，见 Epic E）与「忽略」（该行收起、徽标清除、会话回普通状态）两个操作；点击行内会话信息可跳转打开该会话。
- **C.4 批量操作**：通知卡片底部提供「全部继续」与「全部忽略」；「全部继续」逐个发起续跑、**按钮上带将启动的任务数量**（如「全部继续（3）」），让用户在点击前知道规模。
- **C.5 批量并发上限**：一次「全部继续」最多同时续跑 **3 个**任务，其余排队依序启动；每个任务的进度各自独立反馈，不合并成一个进度。
- **C.6 关闭即收起，不等于忽略**：手动关闭通知卡片只是收掉本次呈现——徽标仍在会话树（Epic D），用户可从那里恢复；本次前端运行期间不再重新弹出。
- **C.7 如实措辞**：优雅退出且当时有任务在跑 → 「上次退出时有 N 个任务仍在进行中」；异常退出 → 「上次应用异常退出，N 个任务被中断」（异常退出按定义不区分崩溃/强杀/断电，统一中性措辞，不预设「崩溃」）。
- **C.8 跨重启重现**：未被处理（既未续跑也未忽略）的中断，在前端每次新启动时重新呈现恢复通知，直到被续跑、被忽略或保留期到期；仅被手动关闭的通知在同一次前端运行期间不再弹出。

## 5. Epic D：会话树中断徽标（第二呈现通道 / 兜底）

作为 R2/R3 用户，即便我关掉了通知，会话树里的徽标仍持续告诉我哪些会话被中断，并支持就地恢复。

- **D.1 徽标呈现**：被中断的会话在会话树行上显示「运行中断」徽标（与既有的用户取消/失败、停滞两类状态徽标同一视觉家族）；徽标点亮的条件以 B.1 判定为准，**跨重启依然点亮**（用户核心诉求：退出应用再打开后要能看出来）。
- **D.2 就地恢复**：徽标行支持就地「继续」操作（悬停快捷入口与徽标小菜单：继续 / 忽略 / 打开会话，两种交互形态语义一致，实施择一或并用）——单项操作的语义与 C.3 完全一致；这是通知被误关后的兜底通道。
- **D.3 工作区聚合提示**：工作区分组标题旁显示中断计数（如「workspace-A（2 个运行中断）」），多工作区多任务时不需逐行扫描。
- **D.4 归档压制**：已归档会话不显示中断徽标、不进恢复清单（归档是比中断更强的用户声明）。

## 6. Epic E：续跑（从中断处继续）

作为 R1 用户，我点「继续」后不需要重新描述任务——系统带着中断前的上下文把它做完。

- **E.1 发起语义**：「继续」= 在该会话中**重新发起一个回合**，续跑请求携带中断恢复语境（让模型知道「这个任务在 X 时刻因服务退出而中断，请从中断处继续」），不带任何用户需要补写的说明；续跑请求走既有用户消息类准入，遵守单活动回合排队规则。
- **E.2 不重复已完成的工作**：续跑以已持久化的执行事实（已发生的工具调用与结果）为上下文，已完成的部分不重做；续跑前把未收尾的旧回合以「运行中断」定局收口，不留悬空。
- **E.3 后台任务的结果消费**：被中断的回合若当时在等待某个后台任务的结果，续跑时优先提示「该后台命令可能已执行完成，请先检查结果」而非盲目重发（后台任务的死活裁决沿用既有孤儿清扫机制，本域不重复裁决）。
- **E.4 续跑中又中断**：续跑后的回合再次遇到服务退出，按本域完整流程重新判定与呈现（同一任务刷新中断时间，不重复计数）。
- **E.5 忽略的可逆性**：「忽略」不清除会话本身（历史上下文完整保留），用户之后仍可打开该会话手动发消息继续——忽略的只是「被推荐恢复」的身份，不是数据。
- **E.6 收尾**：发起续跑即视为用户已决策——中断状态随即清除、徽标消失（不论续跑回合此后以完成/失败/再次取消收尾）；徽标跟踪的是「未被用户决策的中断」，不是「任务是否成功」。

## 7. Epic F：非功能需求

- **F.1 判定准确性**：退出记录机制不可把「正常收尾的会话」报告为中断，也不可把「退出瞬间在跑的会话」漏报；异常退出反推的误差面（退出前极短窗口内刚收尾/刚发起的回合）以记录时间戳为准，宁可少报不误报。
- **F.2 静默的完整性**：没有中断时，恢复通道全线零呈现——无通知、无徽标、无任何「检查中」的中间态暴露给用户。
- **F.3 低开销**：退出记录的写入只在启动与退出两个时点各一次（数据量小、瞬时完成）；异常反推只在确认异常退出后执行一次，不拖慢正常启动；不做周期性心跳写盘。
- **F.4 原子性与容错**：退出记录损坏或缺失时按「无法判定」处理（不弹错误、不误报中断），并留有可检索的日志；机制不因记录文件损坏而阻断服务启动。
- **F.5 界面一致**：web 与桌面（外壳行为一致）共享同一套判定与呈现语义；轻量桌面版复用同一引擎机制，不另建判定。

## 8. 契约级裁决

- **D-M1 退出记录是退出方式判定的唯一依据**：启动留标记、优雅退出补记录、异常退出缺记录——「有没有优雅退出记录」就是判定本身，不引入周期性心跳、不依赖进程表推断。被否决备选：a) 周期性心跳快照（否——SDR-002：与用户「只靠启动/退出两个事件」的裁决不一致，且引入持续写盘；保留 5 秒误差窗口的收益配不上代价）；b) 进程表/系统日志推断（否——跨平台不可靠，且无法覆盖断电）。
- **D-M2 优雅路径直读、异常路径反推**：优雅退出记录自带在跑清单（退出时顺手写下），异常退出才走磁盘反推（未收尾回合判定）；正常退出零额外扫描。被否决备选：全部路径都反推（否——优雅退出时信息就在手上，弃用是浪费；反推结果与记录冲突时以退出记录为准）。
- **D-M3 「运行中断」是新增成因，不复用既有结局词汇**：服务退出导致的回合定局为新的成因值（interrupted），与「已取消」（用户发起）、「已停滞」（系统看门狗）词汇分立；跨域规范名与 zh 界面词统一为「运行中断」（glossary IT1），域内旧称「服务中断」废弃。被否决备选：复用「已取消」（否——turn-scheduling SDR-003 原则二已确立「终止必带可见原因」的词汇纪律，混用让用户无法区分「我停的」和「它断的」）。
- **D-M4 恢复交互是通知内嵌按钮 + 会话树就地操作的双通道**：不建独立恢复页面；每任务独立按钮组 + 批量按钮 + 通知误关后会话树兜底。被否决备选：独立恢复面板页（否——SDR-001 用户裁决「太重」；且多一个页面就多一个要维护的入口）。
- **D-M5 批量续跑必须显式知情**：「全部继续」按钮带数量、并发上限 3、各自独立进度；不静默批量。被否决备选：静默恢复全部（否——违背知情原则，R3 用户的退出动机可能就是任务跑歪）。
- **D-M6 等待用户决策不算中断**：挂起在提问/审批上的回合不属于被中断清单（B.4）。被否决备选：一律计入（否——判定口径只针对「退出瞬间正在执行」的回合；等待类挂起是否计入不影响数据安全——上下文已持久化，将其混入恢复清单是对「正在跑」语义的扩大化）。

## 9. 验收标准（汇总）

| # | 验收项（假如-当-那么） |
|---|---|
| V1 | 假如服务优雅退出、当退出时 2 个会话在跑，那么下次启动的退出记录含这 2 个会话，恢复通知列出它们（C.7 优雅措辞） |
| V2 | 假如服务被强杀/崩溃，当下次启动，那么判定为异常退出并反推出中断清单，通知以异常措辞列出；反推不包含上一个生命周期之前的旧未收尾回合（A.3/A.4） |
| V3 | 假如优雅退出且无任务在跑，当下次启动，那么不出现任何通知与徽标（C.1/F.2） |
| V4 | 假如上次退出瞬间某回合已被用户主动取消，当下次启动做中断识别，那么它不出现在中断清单（B.1） |
| V5 | 假如某会话中断后 72 小时内未被处理，当保留期到期，那么徽标与恢复入口自动消散；中断状态只保留最近一个生命周期、不累积（B.3/A.6） |
| V6 | 假如恢复通知展示 3 个任务，当通知渲染完成，那么每行可见工作区名 + 会话标题 + 中断时间，且各有「继续/忽略」；「全部继续（3）」点击后最多 3 个并发、各任务独立进度（C.2-C.5） |
| V7 | 假如用户关闭了通知但未做任何选择，当会话树渲染，那么徽标仍点亮且可就地「继续/忽略」，语义与通知内一致（C.6/D.2） |
| V8 | 假如用户在会话树对某中断会话点「继续」，当操作完成，那么该会话被打开、发起携带中断恢复语境的续跑回合，旧回合以「运行中断」定局收口，徽标随即清除（D.2/E.1/E.2/E.6） |
| V9 | 假如被中断的回合当时在等待后台任务结果，当用户点「继续」，那么续跑前先提示检查该后台结果，不盲目重发（E.3） |
| V10 | 假如主桌面版与轻量版同时运行、主桌面版异常死亡，当轻量版做启动检查，那么轻量版凭存活探测跳过仍在运行实例的记录，不掩盖、不误判主桌面版的异常（A.5） |
| V11 | 假如退出记录文件损坏或缺失，当下次启动读取，那么按「无法判定」处理——不误报中断、不弹错误、服务正常启动，日志可查（F.4） |
| V12 | 假如某会话挂着「等待用户决策」的回合时服务退出，当下次启动做中断识别，那么它不进中断清单；用户重新打开该会话时可见当时的提问上下文（B.4/D-M6） |
| V13 | 假如续跑后的回合再次因服务退出中断，当下次启动，那么按完整流程重新判定与呈现，同一任务刷新时间、不重复计数（E.4） |
| V14 | 假如已归档会话曾处于中断状态，当会话树渲染恢复清单，那么它不显示徽标、不进恢复清单（D.4） |
| V15 | 假如用户在通知卡片对某行点「忽略」或点「全部忽略」，当操作完成，那么该行收起、徽标清除、会话回普通状态；会话本体与历史完整保留，之后仍可手动打开继续（C.3/C.4/E.5） |
| V16 | 假如多个工作区各有被中断的会话，当会话树渲染，那么各工作区分组标题显示中断计数（D.3） |
| V17 | 假如中断未被处理且前端重启，当前端新一次启动完成，那么恢复通知重新呈现（保留期内；仅手动关闭在同一次前端运行期间不再弹出）（C.8） |

## 10. SDR 记录

- **SDR-001（2026-10-28）**：建域，并并入用户四点裁决。背景：应用退出再打开后，所有会话显示如常、被中断的任务不可见（现状证据见 context §2/§6）；首轮提案（启动横幅 + 独立恢复面板 + 会话内卡片三层）经用户裁决修订：保留期 7 天改 **72 小**时；「上一生命周期内未收尾」口径收紧为「退出瞬间仍在运行」并要求基于退出事件精准记录；删除独立恢复面板，改为**通知卡片内嵌逐任务按钮 + 批量按钮**（3 个任务 3 套按钮）；会话树作为第二通道支持就地恢复。决策：建本域承载判定/呈现/恢复全语义（Epic A-F），采纳 D-M1 至 D-M6；zh 界面词定为「运行中断」（「已中断」已被用户取消/失败徽标占用，见 context §2.2）。被否决备选：a) 自动恢复全部中断任务（否——违背知情原则，退出动机可能是止损）；b) 仅会话列表小红点、无主动通知（否——冷启动进空白草稿页，发现率趋零）；c) 独立恢复面板页（否——用户裁决太重）。影响范围：全部条目。
- **SDR-002（2026-10-28）**：退出判定采用「启动标记 + 优雅退出记录 + 异常磁盘反推」，不做周期性心跳。背景：force kill 场景曾有三案（心跳快照 / 纯磁盘反推 / 混合），用户裁决方向：以「启动留记录、正常退出留记录、异常退出无记录」为判定骨架（哨兵思路）。决策：正常退出记录自带在跑清单（退出时直写），异常退出经磁盘反推补齐清单；砍掉心跳（D-M1/D-M2）。被否决备选：a) 心跳快照（否——持续写盘、与哨兵骨架冗余）；b) 纯磁盘反推不记录退出方式（否——无法区分「退出时在跑」与「更早的未收尾」，且丢失优雅/异常的措辞区分）。影响范围：A.2-A.4、C.7、F.3、D-M1/D-M2。
