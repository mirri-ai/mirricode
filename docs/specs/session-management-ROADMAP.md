## U1 开放项详析（2026-09-10，待裁决）

> 治理规矩：任何待裁决项，先写清背景、痛点、选项与各优缺点，再交用户裁决；不允许裸问。

### 一、撤销语义统一方向

**背景**：三引擎撤销"数什么、停在哪、记什么"不一（context §1.6）：v1 = TUI 入口 + 锚点计数 + wire 记录（**count = 锚点数**）+ 边界停止；v2 = 锚点计数 + wire 记录（**undo op + 截点尺寸 ops 双写**）+ 压缩边界即停 + 检查点深度上限 + 忙碌护栏；rust = 锚点回退（计数锚点、移除锚点及其后全部，同样遇压缩摘要停止），但**不落盘、无护栏**。折叠器侧：rust fold 把 `context.undo` 的 count 解释为**消息条数**——与 v1 记录的锚点数口径分裂，跨引擎重放同一日志截断位置不一致。

**痛点**：跨端/跨引擎同一会话的撤销行为与保真性不可预期（rust 撤销后重开复活被撤内容）；实现批次没有单一目标语义无法开工；count 口径不收敛则写入方与折叠器无法对账。

**选项**：

| | A. 收敛到 v2 形态 | B. 收敛到 rust 形态（+落盘化） | C. 分层统一（推荐） |
|---|---|---|---|
| 做法 | 锚点计数 + 落盘 + 护栏 + 边界即停全量对齐 v2；rust 补齐落盘、护栏、检查点深度等价物 | 以 rust 锚点回退为准补落盘；v1/v2 冻结现状随引擎退役 | 用户可感知语义统一（撤 N 轮、整轮原子、边界即停、落盘保真、诚实反馈、忙碌拒绝）；引擎内部机制（检查点、参与者对账）各自保留；count 口径按 ADR-006 统一为消息条数 |
| 优点 | 语义最完整（v2 是三家中可感知行为最诚实的） | rust-first，改动集中在新内核 | 与 SDR-003「契约同定、rust 先行」方针一致；不为过渡引擎引入机制债 |
| 缺点 | 检查点深度限制依赖 v2 特有机制，rust 无对应物，等价物需另设计 | v2 已有的护栏/反馈在过渡期回退 | 引擎内部行为仍有差异面，需在 context 持续盘点 |
| 成本 | 高（rust 需补齐 v2 全部机制） | 中 | 低（契约只约束可感知行为与记录语义） |

### 二、撤销粒度与深度上限

**背景**：三引擎现状的计数单位都是"真实用户输入"锚点（用户消息、用户触发的 skill/plugin 命令），一个锚点连带其后全部内容作为一个回退单元；单回合多锚点（steer、hook 上下文注入等）场景下"锚点"与"回合"（S7）不重合。需求基线已定为回合级（US-U1 整轮原子）。深度上限：v2 受检查点深度限制，v1/rust 无固定上限（受压缩边界约束）。

**痛点**：验收语言（"撤销最近 N 轮"）与实现锚点口径在单回合多输入时错位；深度上限不统一导致跨端可撤销范围不一致。

**选项**：

| | A. 严格回合级 | B. 维持锚点级 | C. 锚点级内部 + 回合级呈现 |
|---|---|---|---|
| 做法 | S7 回合为最小撤销单元，回合内多锚点不可部分撤销 | 每条真实用户输入一个锚点，现状口径 | 内部按锚点，界面按"撤回到哪一条输入"选择（v1 TUI 选择器已是此形态），产品语言呈现为轮 |
| 优点 | 用户心智最简单，与回合原子性（S7、US5.1 fork）同口径 | 表达力最强、三引擎零改动 | 兼顾细粒度回退与可预期呈现 |
| 缺点 | steer/顺带修正类输入失去细粒度回退 | 单回合多输入时"撤 1"实际撤多少不可预期，UI 需补偿 | 验收口径要双轨 |
| 成本 | 中（锚点→回合聚合） | 零 | 低 |

深度上限选项：压缩边界内不限（现状）/ 固定上限（防误操作）/ 检查点深度（v2 特有）。建议与粒度一并裁决。

### 三、redo 是否随批承诺

**背景**：撤销的补操作（把刚撤销的内容放回）。三引擎现状均无 redo；撤销后内容从当前历史移除，但 append-only 日志原文仍在。

**痛点**：用户撤销后后悔时无低代价路径，可能因怕误撤销而不敢用撤销；redo 与压缩、编号（H4 编号不回收）交互复杂——被撤销条目的编号已被消耗，重做是"重新追加"还是"原位复活"直接影响编号语义与压缩域 ADR-007 的区间括号校正。

**选项**：

| | A. 不随批承诺 | B. 随批承诺（US-U4） | C. 不做 redo、记录形态预留（推荐） |
|---|---|---|---|
| 做法 | 本 Epic 范围外，redo 另立需求 | 撤销+重做成对交付 | 本批不做 redo；撤销落盘时记录形态为将来 redo 预留可恢复定位（原文在 append-only 日志中天然保留） |
| 优点 | 批次最小，撤销语义先定型 | 功能完整，撤销可用性最好 | 成本低，不预支未裁决的语义 |
| 缺点 | 后悔路径缺失 | 批次膨胀；且依赖开放项一/二定型（redo 粒度=undo 粒度），编号复活语义需与压缩域联动再裁决 | 预留是否够用要到 redo 立项时才能验证 |
| 成本 | 零 | 高 | 低 |

### 四、撤销切点落入已压缩段时的行为

**背景**：撤销的可撤销范围当前止于最近一次压缩落位（C3：撤销遇摘要即停，不穿越压缩考古）。边缘形态：请求的切点需要穿越压缩段（撤到压缩落位之前更早的轮次）。压缩域 ADR-007 已文档化相关约束：编号不回收（H4）；wire 记录形态的 undo 产生编号消耗间隙、经 apply 记录区间括号校正——该校正对切点落入头部精华区/保留尾区之内时欠校正（残差与"任意切点保真需逐撤销记录"的延后项均载于 compaction-context §1.2 与 reducer 文档注释，而非 ADR-007 正文）。

**痛点**：用户对"为什么撤不到更早"只有一条"到压缩边界"的解释；若支持跨压缩段撤销，现有区间括号校正不够，且与 C3"不穿越压缩考古"的裁决直接冲突。

**选项**：

| | A. 维持边界即停（推荐） | B. 跨段撤销（撤销到压缩前 + 重放重建） | C. 边界即停 + 分叉/读回替代路径 |
|---|---|---|---|
| 做法 | 维持现状语义（C3 一致），边界反馈诚实 | 撤到压缩前目标点，重算保留尾与落位 | 跨段回退诉求由「按轮次终点分叉（US5.4）+ 读回（H1）」组合承接 |
| 优点 | 最简单，与压缩域已裁决边界条款零冲突 | 能力最强 | 已有立项覆盖该需求，零新增 |
| 缺点 | 压缩频繁的长会话中可撤销窗口短，用户感知"撤销经常失灵" | 需改 C3 裁决；编号/区间校正需逐撤销记录（载于 compaction-context §1.2 与 reducer 文档注释的延后项），成本高 | 路径是"另开分支"不是"原地回退"，用户心智不同 |
| 成本 | 零 | 高 | 零（本域） |

建议 A + C：边界即停为终态语义，跨段回退诉求导向分叉/读回组合。
