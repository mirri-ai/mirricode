## 0. 角色定义（Personas）

| 角色 | 场景 | 核心诉求 |
|---|---|---|
| **会话发起人**（开新会话干活的用户） | 启动会话、委派任务 | 主 agent 开局就合适；干着干着发现不对，能换 |
| **主 agent 使用者**（想换主 agent 的用户，同配置面文档定义） | 为不同类型任务或工作模式选主 agent | 不同任务用不同的「开号」主 agent，而不是全局只有一套默认 |
| **主 agent**（选择并派发子 agent 的执行者） | 决定派谁干活 | 选人依据可信（每个角色是什么、能干什么一目了然）；不该派的派不出去 |
| **用量观察者** | 弄清成本花在哪 | 每个角色花了多少可查 |
| **lead agent**（协作域 persona，随协作 spec E1） | 组建团队、分派任务 | 引用的角色按职责就位；角色变化时团队不静默降级 |

## 1. 消费时刻全景（领域地图）

> 术语口径：本文「角色 / 主 agent / 子 agent / 可派发子角色」为 `glossary.md`「A. 角色域」条目的域内视图，规范定义以术语表为准。

角色配置在运行时被读取的时刻，穷举如下——这是本文的分析骨架，也是 §7 最小声明集的推导依据。各时刻的现状与差距对照见 context 文档 §1.4；定义侧与消费侧的完整闭环（示意图与接线表）见配置面文档「功能闭环」节：

| # | 消费时刻 | 消费者 |
|---|---|---|
| M1 | 会话启动 · 主 agent 装配 | 引擎 |
| M2 | 运行中 · 主 agent 切换 | 用户 / 引擎 |
| M3 | 子 agent 派发 · 选择 | 主 agent（LLM 决策） |
| M4 | 子 agent 派发 · 装配 | 引擎 |
| M5 | 能力路由 · 缺口建议 | 引擎 |
| M6 | 团队组建 · 角色就位 | lead agent / 引擎 |
| M7 | 观测 · 用量归因 | 用户 / 引擎 |

## 2. Epic U1：主 agent 装配与切换

> 动机：主 agent 全局只有一套——定制只能「全局替换默认提示词」（用户级 SYSTEM.md、项目级 agent.md、同名覆盖），替换影响所有会话，无法为「代码审查会话用严谨审查人格、日常开发用高效执行人格」这类诉求提供并存的多套主 agent（现状证据见 context §2）。页面呈现要求见配置面文档 US-B5。

### US-U1.1 声明角色用途（P0）

作为主 agent 使用者，我想让每个角色都能声明自己的用途——作为主 agent、作为子 agent、或两者皆可，以便主 agent 选择器与子 agent 派发列表各自干净。

- Given 角色用途为主 agent 或两者皆可，When 打开主 agent 选择器，Then 该角色出现；用途为仅子 agent 的角色不出现
- Given 角色用途为子 agent 或两者皆可，When 主 agent 派发子任务，Then 该角色可被派发；用途为仅主 agent 的角色不被作为普通子角色推荐
- Given 角色未声明用途，Then 视为仅子 agent（存量角色行为不变）
- Given 角色被禁用，When 新建会话打开主 agent 选择器，Then 该角色不出现（启停状态与派发列表同源，US-U2.1）
- Given 会话已以某角色为主 agent 运行中，When 该角色随后被禁用或删除，Then 本会话主 agent 继续按其被装配时的定义工作，不受影响（快照语义，US-U2.4）
- 用途标记在配置页可编辑，列表按用途筛选，具备主 agent 资格的角色带醒目标识（配置面文档 US-A1/US-B6）

### US-U1.2 新建会话时选择主 agent（P0，本 Epic 核心）

作为会话发起人，我想新建会话时选择一个专门的主 agent，以便不同类型的任务用不同人格、工具面、模型的主 agent。

- Given 已定义多个可选主 agent，When 新建会话并选择其一，Then 该会话的主 agent 完整采用所选角色：系统提示词、工具面、默认模型、可派发子角色全部生效
- Given 未选择，Then 回退内置缺省角色（向后兼容）
- Given 所选角色的工具面缺失会话必需能力（如权限审批交互），When 选择生效，Then 显式警告说明缺什么、影响什么，不得静默残缺
- Given 新建会话时显式指定一个已禁用或已删除的角色，When 创建会话，Then 报错并指名角色与其不可用原因（与 US-U2.5 同语义）
- Given 用户以旧版本客户端在启用该能力的服务端上新建会话，Then 回退内置缺省角色，不报错
- 入口暴露面首批为「终端参数 + 页面」两端，程序接口后置为第二批（SDR-005）；交付下限即此两端可用

### US-U1.3 工作模式预设默认主 agent（P1）

作为主 agent 使用者，我想为不同工作模式绑定各自的默认主 agent，以便不必每次手动选择。

- Given 用户为某工作模式（如 Plan 模式）配置了默认主 agent，When 以该模式新建会话，Then 主 agent 自动使用该角色
- Given 模式未配置，Then 回退全局默认
- Given 用户清除某模式的绑定，Then 该模式回到全局默认，选择器与配置页即时反映
- Given 为该模式绑定的默认主 agent 已被删除或禁用，When 以该模式新建会话，Then 回退全局默认，并给出一次性可见提示（指名失效的绑定与角色），不阻塞会话创建（SDR-004）

### US-U1.4 运行中切换主 agent（P2）

作为会话发起人，我想把进行中的会话切到另一个主 agent 并保留已有上下文，以便任务性质变化时不必重开会话。

- Given 会话进行中，When 切换到另一角色，Then 原地替换：提示词与工具面即刻换新，历史消息保持不变，切换事件在会话历史中可见（SDR-006）
- Given 切换后的角色与前角色工具面不同，Then 用户在切换前得到工具面差异的明确提示

## 3. Epic U2：子 agent 派发语义

> 派发是最高频的消费时刻。本组定义派发的选择依据、委托边界、模型解析与生效边界语义。

### US-U2.1 派发决策依据：描述即选择器（P0）

作为主 agent，我想在决定派发时看到每个可选角色的名称与描述，以便选对角色。

- Given 主 agent 请求可用角色列表，When 列表返回，Then 每项含名称、描述、使用时机——描述面向「选谁」这个决策撰写
- Given 角色被禁用，When 列表返回，Then 不出现该角色（派发列表与配置页启停状态同源）

### US-U2.2 派发边界（P0）

作为会话发起人，我想限定某个角色能派发哪些子角色，以便派发关系可控。

- Given 角色声明了可派发子角色白名单，When 其派发，Then 只能从白名单中选择；白名单外的显式指定被拒绝并说明可用集合
- Given 角色未声明白名单，Then 可派发全部启用角色（缺省语义）

### US-U2.3 模型解析链（P0）

作为主 agent，派发时我想模型按明确顺序解析，以便成本与能力可预期。

- Given 派发请求显式指定模型，When 装配，Then 用指定模型
- Given 未显式指定且角色声明了默认模型，Then 用角色默认
- Given 两者皆无，Then 用调用方当前模型

### US-U2.4 定义变更的生效边界（P0）

作为会话发起人，我想知道角色被编辑后对进行中的工作意味着什么，以便改配置不引发隐性行为漂移。

- Given 角色被编辑，When 已在运行的派发继续执行，Then 沿用其被装配时的定义（快照语义），不受编辑影响
- Given 角色被编辑，When 新的派发发生，Then 使用新定义
- Given 定义切换发生，Then 会话历史可见「该派发起用的新定义版本」，便于事后归因
- Given 主 agent 所在会话进行中，When 该角色被编辑，Then 本会话主 agent 沿用其被装配时的定义，编辑只影响之后的新会话（或经 US-U1.4 切换后生效新定义）
- 如对该语义有异议（如要求运行中热更新），在评审时提出——本文默认快照语义

### US-U2.5 角色不可用的处理（P1）

作为主 agent，当被引用的角色不可用时，我想得到明确反馈，以便换人或求助而不是盲试。

- Given 白名单引用的角色被禁用或删除，When 派发列表返回，Then 该角色不出现且不产生错误噪音
- Given 显式指定一个不可用的角色，When 派发，Then 报错并指名角色与其不可用原因（禁用 / 已删除 / 不存在——从未创建或名称错误）

## 4. Epic U3：能力路由

### US-U3.1 能力缺口建议（P1）

作为会话发起人，当主 agent 的模型缺某项能力（如看图）而任务需要时，我想被建议派发具备该能力的角色，以便任务不被模型能力卡死。

- Given 主 agent 模型缺少任务所需能力，When 能力路由触发，Then 建议派发具备该能力的角色（含角色名与描述）

### US-U3.2 无可用角色的降级（P1）

作为会话发起人，当没有任何启用角色具备所需能力时，我想得到明确告知，以便补充角色或换模型，而不是静默失败。

- Given 无任何启用角色具备所需能力，When 能力路由触发，Then 明确告知能力缺口与「当前无可用角色」，并指出补充途径（配置页创建/启用）

## 5. Epic U4：团队消费（对齐协作 spec E1）

> 协作域约束（协作 spec N6）：角色即 agent profile（协作域不为其发明字段，职责等以提示词正文承载，SDR-009），协作域单向依赖角色域。本组定义团队场景下对角色的消费语义；团队机制本体（任务板、消息、交接）归协作 spec。

### US-U4.1 角色就位（P0×协作域）

作为 lead agent，团队组建时我想每个成员按其角色定义就位，以便成员行为符合职责声明。

- Given 团队定义含角色集，When 组建，Then 每个成员按其角色装配：职责进系统提示、工具面与默认模型按角色定义生效
- Given 团队定义引用的角色不存在，When 组建，Then 报错并指名（与协作 spec US1.3 模板校验同语义）

### US-U4.2 职责与产出契约的判定（P0×协作域，对齐协作 spec US1.1）

作为 lead agent，判定成员任务完成时，我想以角色的产出契约为依据，以便完成标准客观。

- Given 角色的行为提示词声明了产出契约，When 判定任务完成，Then 判定包含契约要求的产出检查（SDR-009）
- Given 角色的行为提示词未声明产出契约，Then 完成判定退回任务描述本身（向后兼容）

### US-U4.3 团队引用一致性（P1×协作域）

作为 lead agent，当团队引用的角色中途变化（被禁用、删除、职责被改）时，我想得到明确反馈，以便团队不静默降级。

- Given 运行中团队引用的角色被禁用或删除，When 该角色下次被消费（新任务分派/认领），Then 报错或团队视图标注「角色不可用」，不静默以无定义状态运行
- Given 角色的职责被编辑，When 团队继续运行，Then 已就位成员沿用快照语义（US-U2.4），团队视图标注定义版本变化

## 6. Epic U5：观测与归因（P1）

### US-U5.1 按角色归因用量（P1）

作为用量观察者，我想按角色（而非只按会话）查看用量与成本，以便判断每个角色值不值。

- Given 会话含多次派发，When 在会话视图中查看用量，Then token 与成本可按角色聚合，子 agent 用量归因到其角色，聚合结果在会话视图内呈现（SDR-004）
- Given 团队运行（协作 spec E1），Then 团队维度聚合可下钻到角色（对齐协作 spec N2）
- 呈现面边界：本 US 定义会话视图内的按角色归因；跨会话聚合（设置页维度）为 P2 未来项，本文不定义

## 7. 角色的最小声明集（本文对定义面的要求）

> 本节从消费时刻倒推角色**必须**声明什么——是 §1 全景的直接推论，也是配置面文档字段设计的边界。其中使用时机与工具面两项已裁决（见文末 SDR-001），其余随评审裁决。

### 7.1 推导

每个消费时刻读取的声明项求并集：

| 消费时刻 | 读取项 |
|---|---|
| M1/M2 主 agent 装配与切换 | 行为提示词、工具面、默认模型、可派发子角色 |
| M3 派发选择（LLM） | 名称、描述 |
| M4 派发装配 | 行为提示词、工具面、默认模型 |
| M5 能力路由 | 工具面 |
| M6 团队组建（协作域） | 行为提示词正文（含职责与产出契约的声明） |
| M7 观测归因 | 名称 |

### 7.2 结论：最小核心五项

**名称、描述（含使用时机）、行为提示词、工具面、默认模型**。前四项必选，默认模型可选。业界同类的子 agent 声明规范采用同构的最小集（名称/描述/工具/模型/系统提示），与上述推导互相印证。

两项**可选**扩展：用途标记（主 agent / 子 agent / 两者皆可，缺省仅子 agent，US-U1.1）；可派发子角色（派发边界，US-U2.2）。

协作域的两项声明（职责、产出契约）并入行为提示词正文承载，不设独立字段（SDR-009）。

### 7.3 简化裁决（未决项）

已裁决的简化（使用时机并入描述；能力标签与工具白名单合并为单一「工具面」概念）见文末 SDR-001。未决项：

| # | 提案 | 理由 | 裁决 |
|---|---|---|---|
| 1 | 继承（extends）不进用户面，以「从现有角色开始」的模板复制取代 | 运行时提示词已自包含；任何角色可作模板，创建即整体复制、此后两者独立——比「理解继承链」简单 | 已裁决（SDR-007） |
| 2 | 模板变量、内置角色差异编辑机制不作为用户概念暴露 | 服务于内置角色维护的机制，自定义角色用不到 | 随架构文档 |
| 3 | 启用、覆盖等状态类开关不算「定义项」 | 是生命周期状态，不是角色声明 | 无争议，直接采纳 |

### 7.4 声明集与消费时刻的覆盖校验

最小核心 + 可选扩展覆盖 M1–M7 全部消费时刻——M6 的职责与产出契约由行为提示词正文承载（SDR-009），无需独立字段。无任何消费时刻需要核心五项与可选两项之外的独立声明——这是「字段面最小」主张的验证方式。

## 8. 非功能需求（NFR）

| # | 需求 | 指标/约束 |
|---|---|---|
| NU1 | 快照一致性 | 同一次装配（主 agent 或派发，装配完成到运行结束）内角色定义不漂移；编辑只影响下一次消费 |
| NU2 | 生效延迟 | 定义变更对新的消费在下一轮生效（与配置面 N2 同义，本域定义边界） |
| NU3 | 权限一致 | 派发与切换不豁免权限——所有派发与切换行为过权限面（对齐协作 spec N3） |
| NU4 | 单向依赖 | 消费域不发明定义域字段；新消费时刻需要新声明项时，先扩定义域（走配置面文档变更流程） |
| NU5 | 消费可观测 | 每次装配、切换、定义版本变化在会话历史可见（支撑事后归因） |

| QU7 | 内置缺省角色的地位 | 已裁决：接受放宽——保留不可删/不可禁保护，定位改为「未选择时的兜底」；覆盖限制于 2026-09-10 解除（SDR-011：同名文件即覆盖、内容可编辑，页面附兜底警告）；配置面锁定语义见配置面文档 SDR-012（其 N3） |

## 附录：需求决策记录（SDR）

### SDR-001 字段面简化：使用时机并入描述、单一「工具面」概念（2026-09-08）

1. **背景与动机**：角色字段面存在两处认知税——「使用时机」与「描述」表达同一件事（这个角色是什么、何时用）；「能力标签」与「工具白名单」两个概念最终都收敛到激活工具集，面向用户构成重复概念。
2. **决策**：使用时机并入描述（读取兼容存量声明，不再单独产出字段）；面向用户合并为单一「工具面」概念——可直接选具体工具，也可按能力包选择（能力标签降为工具面的「按能力选择」视图，能力到工具的映射留作引擎内部机制）。模态路由按默认模型的模型属性走、不经能力标签，故不受合并影响。schema 层两字段是否物理合并留架构文档裁决（工具名与能力标签的值域冲突需评估）。
3. **被否决的备选方案**：保留两套独立用户概念——认知税维持，与「字段面最小」方向冲突。
4. **影响范围**：§7.2 最小声明集、§7.3；配置面文档 US-A2/US-A4 的字段编辑表述与裁决点 Q9；QU4、QU5 关闭。

### SDR-002 角色用途采用三值标记（2026-09-08）

1. **背景与动机**：主 agent 资格需要认定方式，避免「专为子任务设计的小角色」混入主 agent 选择器，同时保留任何角色作为主 agent 的可能。
2. **决策**：每个角色可声明用途三值之一——主 agent / 子 agent / 两者皆可，未声明视为仅子 agent（存量角色行为不变）。主 agent 选择器只列出「主 agent / 两者皆可」；子 agent 派发列表只含「子 agent / 两者皆可」。配置页列表按用途筛选，具备主 agent 资格的角色带醒目徽章。
3. **被否决的备选方案**：a) 布尔标记（能否当主 agent）——无法表达「仅主 agent」用途，两个列表的隔离只能单向；b) 约定任意角色可选——选择器噪音大，两种用途不区分。
4. **影响范围**：US-U1.1、§7.2（用途标记入可选扩展）；配置面文档 US-A1（徽章与筛选）、US-B6（用途编辑，随配置面 SDR-004 移入）；QU2 关闭。

### SDR-003 主 agent 装配的快照语义与启停交互（2026-09-08）

1. **背景与动机**：快照语义原仅对「派发」显式（US-U2.4、NU1），主 agent 本人靠类推成立、未显式记录；启停状态对主 agent 选择器与运行中会话的影响同样未定义。
2. **决策**：主 agent 沿用其被装配时的定义，编辑只影响之后的新会话（或经 US-U1.4 切换后生效新定义）；禁用或删除角色不影响已以其为主 agent 的运行中会话（快照），但禁用角色不再出现在新会话的主 agent 选择器（与派发列表同源，US-U2.1）；新建会话显式指定不可用角色时报错指名（与 US-U2.5 同语义）。
3. **被否决的备选方案**：a) 运行中热更新（编辑即刻生效）——与会话行为可预期性冲突；b) 禁用即中断运行中会话——惩罚已开始的合法工作，无收益。
4. **影响范围**：US-U1.1、US-U1.2、US-U2.4、NU1；配置面文档接线表「启停」行。

### SDR-004 运行时引用悬空的回退与用量归因呈现面（2026-09-08）

1. **背景与动机**：工作模式绑定引用的角色被删除/禁用后行为未定义；「按角色归因用量」未定义呈现面，验收主体缺失。
2. **决策**：悬空的模式绑定回退全局默认并给一次性可见提示（指名失效绑定与角色），不阻塞会话创建；派发的不可用原因枚举补「不存在（从未创建或名称错误）」；用量归因呈现面定为会话视图内按角色聚合（token 与成本、子 agent 归因到角色），跨会话聚合（设置页维度）为 P2 未来项。
3. **被否决的备选方案**：a) 悬空绑定报错阻塞会话创建——惩罚用户且无补救指引；b) 静默回退——违反「不静默降级」域原则。
4. **影响范围**：US-U1.3、US-U2.5、US-U5.1。

### SDR-005 主 agent 选择入口首批范围（2026-09-08）

1. **背景与动机**：入口暴露面（终端参数、程序接口、页面）是否一次做全未决，阻塞 U1.2 排期。
2. **决策**：首批交付「终端参数 + 页面」两端；程序接口后置为第二批，待前两端的真实使用反馈再定形。
3. **被否决的备选方案**：三处一次做全——首批交付变慢，接口使用者目前极少，提前做的部分大概率按反馈返工。
4. **影响范围**：US-U1.2、§9；QU1 关闭。

### SDR-006 运行中切换主 agent 语义为原地替换（2026-09-08）

1. **背景与动机**：切换语义（派生保留上下文 vs 原地替换）未决，U1.4 无法排期。
2. **决策**：原地替换——切换后提示词与工具面即刻换新，历史消息保持不变，切换事件记入会话历史可见，切换前给出工具面差异提示。
3. **被否决的备选方案**：派生新主 agent（历史完整可追溯）——实现复杂度高，且切换的即时性诉求高于「切换前人格思路轨迹」的留档价值。
4. **影响范围**：US-U1.4、§9；QU3 关闭。

### SDR-007 继承退出用户面，以「从现有角色开始」取代（2026-09-08）

1. **背景与动机**：继承链要求用户理解「改了模板，继承者会不会变」，认知负担大；运行时提示词已自包含，继承对消费侧无必要。
2. **决策**：目标态角色定义不含继承语义；任何现有角色（含内置）可作为创建新角色的模板——创建即整体复制，此后两者完全独立（模板是复制一次，继承是持续联动，两者为不同概念）。复用入口唯一化为页面「从现有角色开始」（现状页面已具备，由配置面文档 US-A3 正式化，配置面 SDR-005）。rust 侧现有继承机制在双引擎统一时不予保留，遗留字段仅作兼容显示。
3. **被否决的备选方案**：a) 继承降级为文件层便利（原初步倾向）——「持续联动」概念仍在，认知税未消除；b) 继续作为页面一等概念——与字段面最小方向冲突。
4. **影响范围**：§7.2、§7.3、US-U2.2（仅术语，语义不变）；配置面文档 US-A3；QU6 关闭。

### SDR-008 内置缺省角色放宽为兜底（2026-09-08）

1. **背景与动机**：支持按会话选择主 agent（U1.2）后，内置缺省角色「唯一不可替换」的地位与新能力冲突。
2. **决策**：接受放宽——保留「不可删、不可禁、不可覆盖」的数据面强制约束（系统兜底必须始终存在），定位改为「未选择专用主 agent 时的兜底」；页面明确标注兜底身份（配置面文档 US-A1、N3，配置面 SDR-006）。
3. **被否决的备选方案**：a) 不放宽——按会话选主 agent 的核心需求不成立；b) 放宽同时解除锁定——系统失去兜底，误删后新会话无法装配。
4. **影响范围**：US-U1.2、§10；配置面文档 US-A1、N3；QU7 关闭。

### SDR-009 协作域声明（职责、产出契约）并入提示词正文（2026-09-08）

1. **背景与动机**：协作 spec US1.1 原设想职责与产出契约两个独立字段，但两者的最终消费者均为 LLM（lead 选人、完成判定），自由正文对其无理解损失；独立字段与正文提示词语义重叠，且需数据模型、传输契约、页面表单、rust 对齐一条完整扩展链路。
2. **决策**：职责与产出契约作为行为提示词正文的一部分自由撰写，不设独立字段；团队组建（M6）与完成判定（US-U4.2）从正文读取。页面按职责筛选「团队就绪」的结构化能力放弃（配置面文档 US-D2 改按「被团队模板引用」筛选）；协作 spec US1.1 同批修订（其 SDR-001）。
3. **被否决的备选方案**：a) 独立字段（协作 spec 原方案）——字段面膨胀、与正文双轨；b) 约定标题的结构化正文——隐式契约脆弱（标题改动即识别失败），且仍需双引擎实现标题解析。
4. **影响范围**：§7.1（M6）、§7.2、§7.4、US-U4.2、§5 Epic U4 引言；配置面文档 US-D1/US-D2；协作 spec US1.1、N6（其 SDR-001）。配置面 Q2 关闭。

### SDR-010 团队 lead 与主 agent 为同一机制（2026-09-08）

1. **背景与动机**：团队功能将引入 lead 角色，若另建一套「队长」机制，用户需学两套概念且行为易漂移（选择、切换、快照、权限各一套规则）。
2. **决策**：lead 即「团队会话的主 agent」——同一机制的两面：复用主 agent 的全部机制（装配与切换、快照语义、权限面、按角色归因），不建第二套；团队场景的特殊需求（任务板分派等）作为主 agent 机制之上的协作能力，不另起炉灶。
3. **被否决的备选方案**：两套独立机制——灵活但概念税与行为漂移风险高，与「字段面/概念面最小」方向冲突。
4. **影响范围**：§5 Epic U4；协作 spec US1.2、E7（其 SDR-002）；配置面 Q3 关闭。

### SDR-011 缺省主 agent 的覆盖限制解除（2026-09-10，修订 SDR-008）

1. **背景与动机**：SDR-008 保留缺省主 agent 的「不可删、不可禁、不可覆盖」三重保护。用户裁决（2026-09-10）：存在同名文件本身就是覆盖意图的表达，无需额外声明；主 agent 的提示词等自定义需求真实存在，整体禁止覆盖过度保护。两引擎现状亦不一致（TS 要求文件内显式覆盖标记、rust 同名即覆盖）。
2. **决策**：缺省主 agent 的保护收缩为「不可删、不可禁」——内容可被同名文件覆盖（提示词、模型、工具面等均可自定义），文件内声明的禁用对该角色不生效（兜底必须始终存在）；页面可编辑并附带兜底身份的警告提示。同时裁决：该语义对全部内置角色统一（同名即覆盖、无声明，TS 引擎放弃显式覆盖标记）。锁定语义的页面呈现见配置面文档 SDR-012（其 N3、US-A6）。
3. **被否决的备选方案**：a) 维持不可覆盖——自定义需求落空，与「文件即意图」冲突；b) 仅写侧自动补声明——手写文件两引擎仍分歧；c) rust 对齐 TS 显式声明要求——被用户明确否决。
4. **影响范围**：§10（QU7 重述）；配置面文档 US-A5/US-A6/N3（其 SDR-012）；架构文档 ADR-006；R4 批次落地。
