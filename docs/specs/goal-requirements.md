# 自治目标模式（goal）— 需求文档（User Stories）

> 状态：v1 基线 · 2026-09-13 · 待用户评审 ·
> 本文是目标域需求侧的唯一事实源（内部规格文档，不进文档站构建，中文单语）。
> 本文件记录 TS 引擎已支持的能力作为 Rust 对齐基线——是 Rust 要匹配的地板，不是天花板。
> 配套文档：技术形状见 [goal-architecture.md](goal-architecture.md)；现状盘点见 [goal-context.md](goal-context.md)。
> 术语规范：目标（O1）、续航提示（O2）的唯一定义见 [glossary.md](glossary.md)。
> 范围边界：本域管**目标的产品语义**——创建、四态生命周期、预算、续航、提醒、终态产物、消费端。回合准入/合并/挂起的**机制**见 [turn-scheduling-requirements.md](turn-scheduling-requirements.md)；后台任务与通知的业务语义见 [subagent-requirements.md](subagent-requirements.md)。等待挂起的产品语义由本域 E5 承接（承接自后台任务域 SDR-011，关闭其 O11）。

## 0. 角色定义

| 角色 | 场景 | 核心诉求 |
|---|---|---|
| **用户**（发起/观察/干预者） | 定目标、看进度、暂停/恢复/取消、排队下一个 | 我说清目标和验收标准，它自己干到有结论；我要能随时停、随时看花了多少 |
| **执行者**（干活的模型） | 自治工作、自审、报终态 | 我知道目标与验收标准是什么、还剩多少预算、什么时候该自审；我的判断有明确的出口（完成/阻塞/继续） |
| **配置者**（设预算的人） | 用回合/token/时间约束成本 | 三种单位都能限，超了就停而不是失控烧钱 |
| **集成方**（订阅目标事件的程序方） | 基于目标状态做自动化 | 状态变化有事件、有终局原因、可回放 |

## 1. Epic E1：创建与校验

### US1.1 明确意图才建（P0）

作为用户，只有我明确要求自治工作时才建立目标——问候、普通提问、无验证条件的模糊请求不建。

验收：
- Given 目标创建入口的说明面，Then 明确指引：仅当用户明确要求自治或触发目标引导时调用；模糊请求先要验收标准，不自行建立
- Given 请求无验证条件的模糊自治意图，When 创建前，Then 先向用户索要验收标准而不是自行编造
- Given 已索要验收标准，When 用户坚持不给而要求照建，Then 尊重用户意愿照建（逃生口，不僵持）

### US1.2 目标内容校验（P0）

作为用户，目标描述受基本约束，保证可用性。

验收：
- Given 目标描述为空或超长（约 4000 字符），When 创建，Then 拒绝并说明
- Given 验收标准超长，When 创建，Then 截断保留而非报错（标准是辅助信息，不是门禁）
- Given 目标描述，Then 指引保持简洁；超长内容以文件路径引用

### US1.3 单目标与替换（P0）

作为用户，同一会话同一时刻只有一个目标；换目标要么显式替换。

验收：
- Given 已有目标（任何状态）且未选替换，When 再建，Then 拒绝并说明已有目标在
- Given 选择替换，When 创建，Then 旧目标被清除、新目标生效
- Given 我还想排队多个目标，When 操作，Then 通过消费端的待办目标队列（见 E7）逐个接力，而非引擎内并存多目标

### US1.4 启动审批（P1）

作为用户，在需要确认的权限模式下启动目标要先经我确认（目标一旦启动将自主消耗预算）。

验收：
- Given 手动确认或全部放行模式，When 启动目标，Then 弹出确认（可在确认时切换权限模式；目标启动属于即便全部放行也要确认的事项）
- Given 自动模式，When 启动目标，Then 不弹确认

## 2. Epic E2：生命周期（四态）

### US2.1 状态全集（P0）

目标有四个状态：进行中、已暂停、已阻塞、已完成。

验收：
- Given 目标存在，When 查询，Then 状态 ∈ {进行中， 已暂停, 已阻塞, 已完成}，附目标内容、验收标准、进度与预算（见 E3）
- Given 无目标，When 查询，Then 明确返回无目标

### US2.2 暂停的来源族（P0）

作为用户，目标的暂停必须可说明、可恢复。

验收：
- Given 我主动暂停，When 暂停，Then 状态为已暂停并附原因（用户暂停）；若回合流式中执行暂停，Then 当前回合被中断（暂停即时生效，不等回合自然结束）
- Given 回合被中断，When 结算，Then 目标自动暂停并附原因（中断后暂停）
- Given 供应商故障（限流/连接/鉴权/安全策略）导致回合失败，When 结算，Then 目标自动暂停并附对应原因
- Given 续航启动本身失败，Then 目标暂停并附原因
- Given 会话重启后恢复，When 恢复，Then 进行中的目标降级为已暂停（附"恢复后暂停"原因），不自动续跑
- Given 已暂停/已阻塞的目标，When 恢复，Then 转回进行中并继续续航

### US2.3 阻塞（P1）

作为执行者，判定真实僵局（外部条件、需用户输入、持续技术失败、目标不可能/不安全/自相矛盾）时我报"已阻塞"并说明解法；对持续性僵局不轻易报——连续多个自治回合复现同一阻塞才报。

验收：
- Given 目标不可能/不安全/自相矛盾，When 当回合判定，Then 可立即报阻塞并说明
- Given 其他阻塞（外部条件/需输入/持续失败），When 连续约 3 个自治回合复现同一阻塞，Then 报阻塞并说明"需要什么输入或改变才能解"
- Given 连续复现的计数口径，Then 自治回合自目标起始起计，恢复后重新计数
- Given 报阻塞，Then 阻塞原因由执行者在随后的消息里自己写（状态是机器信号，解释是模型的话）
- Given 已阻塞目标，When 用户恢复，Then 转回进行中

### US2.4 完成是瞬态（P1）

作为用户，目标完成即出总结、随即清位。

验收：
- Given 执行者报完成，Then 状态短暂为已完成 → 总结产出后目标清除（不常驻占用）
- Given 完成总结，Then 由执行者在同一回合内写出（面向用户：目标已完成、做了什么、跑了什么验证）
- Given 完成判定，Then 必须对照验收标准逐条核验——弱证据不算完成；预算将尽不是完成理由

### US2.5 过期目标调用的拒绝（P2）

作为用户，目标状态在回合中途变化后，基于旧状态的终态申报不被采纳。

验收：
- Given 回合进行中目标已被更换或清除，When 执行者以旧目标为对象调用目标工具，Then 该调用被拒绝并说明"目标已变化"（不作用到新目标上，拒绝对模型可见）

## 3. Epic E3：预算

### US3.1 三种单位（P0）

作为配置者，我能用回合数、token 数、时间限制目标的成本。

验收：
- Given 设置预算，Then 三种单位任选（时间支持毫秒到小时的换算；时间合理区间约 1 秒–24 小时，区间外拒绝）
- Given 复合限制，Then 指引换算成单一单位后再设
- Given 我未设预算，Then 目标不因预算停止（按判定结束）
- Given 指引，Then 不允许执行者自行发明限制——只有用户给了明确限制才设

### US3.2 记账口径（P0）

- Given 回合计数，Then 每个续航回合计 1
- Given token 记账，Then 记输出 token（输入与缓存不计入目标预算）
- Given 时间记账，Then 按实际经过时间累计，进程重启/停机期间也计入（不因停机而豁免）

### US3.3 耗尽行为（P0）

作为配置者，预算是硬闸门。

验收：
- Given 任一预算耗尽，When 记账点检查，Then 目标转为已阻塞并附"预算已达"原因（可恢复继续）
- Given 耗尽发生在回合中段（还有步数余量），Then 给一个宽限回合：注入"立即停止、别再调工具"的提醒，后续工具调用被拒绝
- Given 已超限的预算被设置，When 设置时，Then 立即停止当前回合并说明

### US3.4 剩余量查询（P1）

- Given 目标存在，When 查询，Then 返回三种预算的剩余量与是否已达

## 4. Epic E4：续航循环

> 目标模式的核心：回合结束即续航，直到终态。挂起语义（E5）是对它的受控暂停。

### US4.1 回合结束即续航（P0）

作为用户，目标进行中时回合正常结束就自动开下一个回合继续工作。

验收：
- Given 目标进行中，When 回合以"已完成"结束，Then 自动注入续航提示开启新回合（提示要求：选一个有边界的有用切片继续做；多数续航回合不应报终态；简单/已答/不可能的目标当回合即报终态）
- Given 回合因步数上限终止，When 结束，Then 视为非异常——注入"接续上次进度"的续航提示继续
- Given 回合被中断/失败/被钩子阻断，When 结算，Then 目标按 E2.2 处置（暂停/阻塞），不续航
- Given 续航提示入队，Then 有防重入保护（同一目标同时至多一个待启动续航）

### US4.2 终态后的同回合收尾（P1）

作为用户，报终态时总结/阻塞说明出现在同一个回合里，不需要再等一个回合。

验收：
- Given 执行者报完成/阻塞，When 工具返回，Then 同一回合同步追加一个空续步，让执行者读终态提示后在**本回合内**写出面向用户的总结或阻塞说明
- Given 该追加受单回合步数余量约束（余量不足则不追加）

### US4.3 状态提醒注入（P0）

作为执行者，每个新回合我都记得自己在目标模式里、进度与预算如何。

验收：
- Given 目标进行中，When 新回合开始，Then 注入进行中提醒：目标内容（标注为数据非指令）、验收标准、进度（续航回合数/token/耗时）、预算与剩余；近预算（约 75%）时附"收敛"指导
- Given 未设任何预算，When 提醒注入，Then 不包含预算引导（不得在无预算存在时宣称"在预算内"——现状缺口见 context §1.4 与 goal-ROADMAP O6）
- Given 目标已阻塞/已暂停，When 新回合，Then 注入对应提醒：说明当前未自治、用户可用什么命令恢复
- Given 会话被复制（fork），Then 新会话不携带目标（fork 时清除并补发清除提醒）

## 5. Epic E5：等待挂起（承接后台任务域 SDR-011）

> 目标模式下"回合结束即续航"的结构缺陷：等待后台结果时不存在空闲，退化为轮询确认的空耗。本 Epic 承接其产品语义（与 [subagent-requirements.md](subagent-requirements.md) E13/US13.3 同一裁决；机制侧见 [turn-scheduling-architecture.md](turn-scheduling-architecture.md) 挂起接口）。

### US5.1 续航提示携带任务清单（P0）

作为执行者，续航回合里我知道有哪些后台工作还在跑、结果会自己来。

验收：
- Given 目标进行中且存在未定局的后台任务，When 续航提示注入，Then 携带任务清单（数量/类型/描述，注入时刻快照）与"完成会自动送达、勿轮询查询"指引
- Given 无进行中后台任务，Then 续航提示不携带清单

### US5.2 空转即挂起（P0）

作为用户，目标确实只剩等待时循环停下来等，不空转。

验收：
- Given 目标进行中、存在未定局后台任务，且续航回合结束时执行者未执行任何实际工作（无工具调用），When 判定，Then 视为等待信号：暂停发放续航提示（挂起），等待期不再产生模型调用
- Given 挂起期间任一后台任务定局，When 通知到达，Then 开启新回合消化结果（目标上下文随常驻提醒在场；一次唤醒一个回合）
- Given 挂起持续无任何事件（通知被抑制/任务卡死），When 超过兜底时限，Then 强制续航一次
- Given 挂起期间用户插话，When 消息到达，Then 照常开回合（用户优先于挂起）
- Given 目标处于挂起，Then 挂起期不计回合数预算（消耗时间不消耗回合）

## 6. Epic E6：消费端（终端 / 网页 / 无界面）

### US6.1 终端命令族（P0）

作为用户，我用命令管理目标。

验收：
- Given `/goal` 命令族，Then 支持：查状态（状态面板：状态/目标/验收标准/进度/停止条件）、暂停、恢复（恢复即发送恢复指令）、取消、替换式新建、排队下一个、管理队列
- Given 需确认权限模式下启动/替换目标，Then 先弹确认
- Given 状态面板，Then 停止条件行如实展示（如"20 回合后停（已 7/20）"/ token / 时间；无上限则说明"直到判定完成"）

### US6.2 状态与终局呈现（P1）

作为用户，我看得到目标的状态变化与终局。

验收：
- Given 暂停/恢复/阻塞发生，Then 对话流出现一行状态标记（可展开原因）
- Given 目标完成，Then 出现确定性完成卡片（结论原因、回合数、耗时、token）
- Given 目标工具调用，Then 以简洁头部呈现（"已建立目标"/"已报目标完成"等）

### US6.3 待办目标队列（P1）

作为用户，我能排队多个目标，当前目标结束后自动接力。

验收：
- Given 排队了下一个目标，When 当前目标终局，Then 自动接力启动下一个
- Given 排队时当前无活动目标且空闲，When 排队，Then 直接立即启动该目标而非入队（排队的语义是"接在后面"，无"后面"时就是现在）
- Given 队列管理入口，Then 支持编辑/排序/删除
- Given 队列存储，Then 为消费端本地资产（不在引擎内）——引擎内同一时刻仍只有一个目标

### US6.4 网页端对等（P1）

- Given 网页会话有目标，Then 目标条呈现：状态徽章（进行/阻塞/暂停）、目标内容、token 预算进度条；支持暂停/恢复/取消

### US6.5 无界面模式（P1）

作为脚本/管道调用方，无界面运行目标有确定的行为与退出码。

验收：
- Given 无界面模式带目标启动，Then 持续跑到终态，结束时输出目标总结（结构化或文本）
- Given 终态，Then 退出码：完成=0、阻塞=3、暂停=6
- Given 目标的暂停/恢复等管理子命令，Then 无界面模式不支持（回落普通输入）

## 7. 非功能需求（NFR）

| # | 需求 | 指标/约束 |
|---|---|---|
| N1 | 单目标 | 引擎内同一会话同一时刻至多一个目标；多目标靠消费端队列接力 |
| N2 | 状态可回放 | 目标状态变化经对话记录持久化，重启后可重建（进行中降级为已暂停） |
| N3 | 预算硬闸门 | 三种单位任一耗尽即阻塞；宽限回合内工具被拒 |
| N4 | 续航防重入 | 同一目标同时至多一个待启动续航 |
| N5 | 终态瞬态 | 完成为瞬态（总结后即清），不常驻 |
| N6 | 等待零空转 | 挂起期间模型调用开销为零（承接 subagent 域 N16） |
| N7 | 单向依赖 | 本域依赖回合调度域（续航/挂起机制），被遥测消费；与任务服务零直接耦合 |

## 10. 未来增强提案（超出 TS 现状，明确标注为提案）

- **P1 阻塞复现的运行时计数**：为"连续 N 个续航回合复现同一阻塞"提供运行时计数与校验（现状纯提示词，见 context §1；Rust 核心可直接超出）。
- **P2 目标队列引擎化**：待办目标队列目前在终端客户端本地文件，引擎内无多目标概念——队列入引擎可跨端一致（现状依据见 context §1.7）。

## 附录：需求决策记录（SDR）

> 后续需求变更以 SDR 追加于本节，历史只追加不重写。

### SDR-001 建域与等待挂起承接（2026-09-13）

1. **背景与动机**：目标模式是用户可见的核心产品能力（四工具/续航/预算/四态），但无规格落点——后台任务域 SDR-011 裁决的"等待挂起"其目标侧机制悬空（该域 O11）；goal 的续航语义被迫寄生在相邻域文档里。
2. **决策**：建立本域（自治目标模式），与回合调度域同期建域（用户裁决 2026-09-13：机制/产品分离）。等待挂起的产品语义由本域 E5 正式承接（关闭后台任务域 O11）；续航作为回合调度域的消费方语义落位本域 E4。
3. **被否决的备选方案**：a) 并入会话管理域——目标的产品语义（预算/续航/四态）与"会话管理"主题不符，且该域将巨型化；b) 挂起语义留在后台任务域——挂起是目标循环的行为，不是任务的行为（任务只是唤醒源）。
4. **影响范围**：本文件全套；[subagent-ROADMAP.md](subagent-ROADMAP.md) O11 关闭；glossary O1/O2 注册；turn-scheduling 域（消费方关系确立）。

### SDR-002 停止与暂停真正停止目标机器（2026-09-14）

1. **背景与动机**：目标进行中用户点"停止"或"暂停"时，引擎里仍有活动继续跑——为投递后台任务通知、执行用户定时任务而自动注入的回合无法被中止；暂停只翻转了状态、没有冻结正在进行的活动；模型还能把用户暂停的目标直接改写成"已完成"，用户的暂停被覆盖。共识：用户的暂停是机器信号，模型无权推翻；用户叫停就是要机器真正停下，而不是等它自己跑完。
2. **决策**：
   - a) **暂停即冻结整个目标机器**：用户的暂停取消所有正在跑的回合（含引擎为投递通知/定时任务注入的回合，这些回合按"已取消"结算）；暂停期间后台任务完成的通知不再开启新回合（投递挂起、不丢弃）；模型不得把暂停中的目标改写成已完成或已阻塞；用户恢复后，目标转回进行中，挂起的通知投递恢复（补投），续航照常继续。取消目标同样取消所有正在跑的回合。
   - b) **恢复只解冻、不取消任何东西**：恢复动作本身不取消回合、不改变暂停前的其他行为。
   - c) **用户定时任务不随暂停冻结（范围边界）**：目标暂停只冻结"目标驱动的活动"——续航与任务通知投递；用户自行安排的定时任务（cron）是独立于目标机器的机制，其注入的回合照常执行。暂停不等于让引擎整体静音。
   - d) **已接受的时序窗口**：一个恰好抢在暂停生效前通过检查的投递节拍，仍可能启动一个通知回合——与"停止"的既有窗口同一语义，接受为边界（不追求逐回合原子性）。
3. **被否决的备选方案**：a) 暂停只翻转状态、不打断正在跑的回合——用户感知"暂停了但还在动"，违背"叫停即停"；b) 暂停期间任务完成通知直接丢弃——恢复后信息丢失；挂起补投（E5 既有语义）更符合"暂停非终局"；c) 暂停连用户定时任务一起冻结——定时任务与目标状态无关，冻结会造成用户预期之外的引擎整体静音。
4. **影响范围**：E2 生命周期（US2.2 暂停的来源族：用户暂停的即时性；US2.4 完成瞬态的 guard 侧）、E4 续航循环（通知唤醒与暂停的交互）、E5 等待挂起（US5.2：挂起期间任务定局不再唤醒——投递门为 E5 目标侧补强）、E6 消费端（web 停止/暂停按钮的引擎侧契约：暂停后无新回合、恢复后通知补投）；机制侧见 [goal-architecture.md](goal-architecture.md) ADR-003；现状证据见 [goal-context.md](goal-context.md) §3.1。

### SDR-003 跨回合续航与异常终局的目标状态诚实性（2026-10-18）

1. **背景与动机**：Rust 引擎的"goal 循环"只在单个 turn 内推进——turn 一旦结束（无论正常还是异常），没有任何机制开启下一个 turn，目标停在"进行中"却无人推进；turn 被看门狗误杀或 LLM 失败死亡后，目标状态悬空"进行中"，UI 永远显示一个不会动的进行中（session-b05098aa 事故形态）。用户对目标模式的预期是"不达目的不停"，且状态呈现必须诚实。
2. **决策**：
   - a) **跨回合自动续航**：turn 正常结束且目标进行中、预算未耗尽时，引擎自动开启续航 turn（system trigger `goal_continuation` origin，续航提示词与 TS v2 语义对齐），直到目标完成/被阻塞/被暂停或预算耗尽。
   - b) **异常终局的诚实结算**：turn 以停滞/中断/失败/钩子否决收场时，进行中的目标立刻结算——失败/停滞/中断转"已暂停"（带类型化 reason，如"因回合停滞而暂停"），钩子否决转"已阻塞"；不再悬空"进行中"。
   - c) **双护栏（Rust 独有加固）**：连续 3 个无工具调用且无目标状态变化的续航 turn，或单次激活累计 20 个续航 turn，目标转"已暂停"（护栏 reason）；用户发起的 turn 重置计数。
   - d) **范围边界**：只驱动 main agent 的目标；后台任务在飞时续航挂起、由通知 turn 唤醒；用户 turn 中插不清零护栏。
3. **被否决的备选方案**：a) turn 异常后保持"进行中"等通知/cron 唤醒重启——状态与实际活动脱节（O14 窗口期问题），且唤醒源不存在时永久空转；b) 异常终局直接置"已阻塞"——失败/停滞多为暂态（网络、看门狗误杀），"已暂停"留给用户判断是否恢复，语义更准；c) 仅靠提示词自律防续航风暴（TS 现状）——Rust 无 turn 级工具调用追踪，硬护栏成本安全更有保证。
4. **影响范围**：E4 续航循环（跨 turn 化）、E2 生命周期（异常终局来源族）；机制侧见 [goal-architecture.md](goal-architecture.md) ADR-004；O12/O14 关闭（见 [goal-ROADMAP.md](goal-ROADMAP.md)）。
