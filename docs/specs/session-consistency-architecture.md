## 1. 目标与设计原则

本设计描述**终态**：Rust 核心中多个服务入口共享同一份个人数据目录时的会话一致性架构。策略选型为**乐观并发控制为主、回合级围栏为辅**（ADR-001），不引入租约、锁文件、进程发现等悲观协调机制。

设计原则（对应需求编号）：

1. **文件即事实源即信号**：会话的操作日志是只增不改的追加文件，其"长度 + 修改时刻"天然构成单调版本号；一切同步与冲突判定都锚定它，不发明第二套版本机制（US C1.x、C2.x）。
2. **拦截只挂在提交动作上**：浏览路径永远只刷新不拦截；拦截点必须发生在用户消息落盘**之前**，保证被拦截时零回滚、零半成品（US C2.1）。
3. **增量为王**：任何同步路径只处理自上次同步点以来的新增内容；禁止任何路径退化为全量重放（US C4.1）。
4. **开销与体量解耦**：版本探测是常量时间的元数据读取；跟随开销只与新增内容量成正比（US C4.1、C4.2）。
5. **元数据单表示**：会话元数据的唯一权威表示是数据库行（ADR-006）；跨进程元数据并发由存储端口的字段级增量更新机制性保护（不同字段不互相抹掉），不存在第二份需要维护一致的元数据表示。
6. **存在性收敛降格为后台回收**：清单维护的批量动作不进启动关键路径；行删除是事务性的，正文目录的清理残留由低频后台归档回收（墓碑判定，见 ADR-006 决策 c）。

## 2. 域模型

### 2.1 核心概念

- **会话版本（session version）**：`(字节数, 修改时刻)` 二元组，取自对操作日志文件的一次元数据读取。字节数是主信号（追加文件只增不减），修改时刻为辅助信号。版本读取是微秒级操作，可高频执行。
- **本地已知版本（known version）**：一个入口进程内持有的"我已同步到哪个版本"，由两个来源更新——自己落盘写入后的已知版本前进；检测并吸收另一入口写入后的版本前进。
- **版本偏差（version divergence）**：磁盘当前版本 ≠ 本地已知版本。出现偏差时**不区分成因**（另一入口在写、或其崩溃前的最后写入），一律按"先刷新、再让用户重新确认"处理（US C2.1 的中性文案要求）。

### 2.2 冲突判定的时序模型

```
读侧（浏览路径）                     写侧（提交路径）
──────────────                     ──────────────
打开/恢复会话 → 检查版本             用户提交 → ①检查版本
  偏差 → 增量吸收                     偏差 → 拦截+提醒+消息回填（落盘前）
  无偏差 → 直接用                     一致 → ②落盘用户消息
前台周期检查 → 偏差则增量吸收                ↓
  （驱动实时跟随与活动徽标）           ③回合首条记录落盘前再验一次
列表/详情查询 → 顺带比对                 回合进行中 → 每个工具调用前检查
                                        偏差 → 中止本回合+留中止记录+通知
```

- **①提交前检查 + ③回合首记录前复验**共同构成提交围栏：即使检查与落盘之间存在微小窗口，③把"带偏差落盘"的概率压到 ①③ 之间的毫秒级间隙。
- 回合进行中的检查把中止延迟上限约束为一个工具调用的执行间隙。

### 2.4 回合与吸收的互斥契约（ADR-005）

三条不变量，缺一即出现"自己中止自己"或"漏段"：

1. **自身写入在写入点同步推进本地已知版本**。本入口每次落盘追加操作日志成功后，立即以刚写出的字节长度推进本地已知版本。增量吸收器因此**只处理外来写入**——自己的回合产生的追加永远不会被当成另一入口的偏差（回合监视器不会自中止、活动徽标不因自身活动误亮、吸收器不会重复折叠自己的记录）。
2. **版本锚的前进不得先于字节消费**。已知版本的推进只发生在两种时刻：自己刚写出的内容（天然已消费）；完成一次增量吸收之后（锚取于本次实际读到的末条完整记录边界，含对未写完整尾部的容忍）。禁止任何"先按元数据推进版本、后读内容"的路径——那会把跳过的字节永久漏段。
3. **回合运行期间，跟随调度器只上报、不吸收**。本入口回合运行中探测到偏差时，不并发执行增量吸收（避免与回合循环竞态修改同一内存态），而是立即触发回合监视器的既有中止路径；吸收延迟至回合结束或中止完成后进行。若本入口无回合在跑，跟随调度器探测到偏差直接吸收。会话内对内存态的并发访问以会话级互斥（回合循环与吸收器共享）串行化。

吸收的目标态是**引擎的会话内存态本身**（与恢复时刻的重放同一份状态），而非界面投影——由此检查点快照、界面投影、索引行都从同一份吸收后的内存态派生，不产生三态分叉。

### 2.3 范围边界

- 本设计的协调对象是"共享同一份个人数据目录的服务进程"（web 服务入口、desktop 服务入口，同一可执行文件的多个实例）。
- 终端旧引擎与 TypeScript 旧核心不在本设计范围内（见需求文档范围边界）；它们与本设计机制无交互——它们按既有方式读写磁盘，本设计读侧的增量吸收与字段级合并对它们的写入同样成立（视为"另一写入者"）。
- 会话 id 由各入口独立铸造（通用唯一标识），两个入口同时新建会话不会产生同名目录冲突；新建时的目录惰性物化对并发创建容忍（重复创建同一目录不报错）。
- 会话的检查点快照（snapshot.json）与操作日志并发写入为良性：快照采用原子替换写出，且重放以操作日志锚定进度、快照只作加速——旧快照最多导致恢复时多回放一段（慢路径），不产生错误状态。快照与吸收的内存态一致性由 §2.4 的互斥契约保障。
- 附件内容先于引用它的日志记录落盘（写序不变量），因此版本锚只锚定操作日志是安全的——版本前进到引用某附件的记录时，附件内容必然已在磁盘上。

## 3. 架构组件

### 3.1 版本探测器（version probe）

- **职责**：给定会话存储单元，返回其当前版本；比对本地已知版本，报告偏差。
- **依赖**：文件系统元数据读取（无内容读取）。
- **契约要点**：元数据读取失败按"无法判定"处理，不抛错阻断上层——读路径降级为直接使用内存态（宁可用旧的，不因探测失败卡死浏览）。

### 3.2 增量吸收器（incremental absorber）

- **职责**：给定同步偏移点，读取操作日志新增字节，重放进内存态，推进本地已知版本。
- **依赖**：追加日志读取（含对"最后一段未写完整"的既有容忍——停在上一完整记录，下次继续）。
- **契约要点**：
  - 以字节偏移为锚，绝不重读偏移之前的任何内容（US C4.1）。
  - 吸收是**写前动作**：吸收完成后才允许基于新状态继续（提交路径的拦截判定发生在吸收之前，见 §2.2 的顺序）。
  - 对一个已打开的运行中会话持续吸收外部新增记录，是本设计新增的运行模式（区别于仅在恢复时刻的单次重放）。

### 3.3 提交围栏（commit fence）

- **职责**：在用户消息落盘前做最终版本裁决；在回合首条记录落盘前复验。
- **契约要点**：
  - 拦截返回结构化错误（错误码 + 提示文案键），客户端据此提示并把消息回填输入框；**围栏通过后到落盘之间不再有任何用户可见动作**。
  - 拦截对 RPC 层是普通失败响应，不引入新通道。

### 3.4 回合监视器（turn guard）

- **职责**：回合执行期间，在每个工具调用执行前做版本检查；发现偏差则请求中止回合。
- **契约要点**：检查在工具调用调度点执行，微秒级，不改变工具调度语义；中止遵循既有回合中止路径（停后续工具、写中止记录、通知用户），不新造终止机制；**探测失败时按偏差处理**（无法判定 = 宁停勿脏，中止并提示重试）。

### 3.5 元数据存储端口（metadata store port，ADR-006）

- **职责**：核心层定义的元数据 + 存在性存储端口（async：get / upsert / delete / list-ids / batch），生产实现为数据库，测试实现为内存——核心层保持存储无关，正文（对话日志）不经端口直连文件。
- **契约要点**：
  - **字段级增量更新为强制不变量**：每个写点只声明并写入自己修改的字段（partial update），跨进程并发写不同字段互不抹除（US C3.1 的机制性保障，取代原三路合并协议——ADR-006）。
  - 行即会话存在性的唯一判据；物化守卫（是否已开始对话）以对话日志存在性（未压缩或压缩形态之一）为准。

### 3.6 存在性回收器（existence reaper，ADR-006）

- **职责**：低频后台回收"行已删除、正文目录残留"的磁盘垃圾；判定依据为删除事务内留下的墓碑（会话 id + 删除时刻，与行删除同事务落库）——只回收墓碑命中且无行的目录，无墓碑的无主目录不属其管辖（ADR-006 裁决 3：由用户自行处置）。
- **契约要点**：不挡任何读路径、不进启动关键路径；回收失败留待下轮，不阻塞、不报错升级。

### 3.7 前台跟随调度器（foreground follow scheduler）

- **职责**：为处于前台的已打开会话安排周期性版本探测（秒级间隔）；偏差则触发增量吸收并把新内容经本入口的事件通道推给界面；会话离开前台即停止。
- **契约要点**：调度挂在会话的前台状态上；探测失败静默重试（下个周期），不报错。

## 4. 数据流

### 4.1 双开浏览（A 跑回合、B 旁观）

1. A 的回合持续追加操作日志 → A 的已知版本持续前进。
2. B 的前台跟随调度器周期探测 → 发现偏差 → 增量吸收新字节 → 经 B 的事件通道推 UI。
3. B 的用户看到 A 的回合逐段出现；徽标基于"版本持续前进"点亮与熄灭。
4. B 把会话切后台 → 调度停止；切回 → 从暂停偏移补齐。

### 4.2 B 提交被拦截（A 有未同步写入）

1. B 提交 → 围栏检查发现偏差 → 拒绝执行（磁盘零写入）→ 返回结构化错误。
2. 客户端提示 + 消息回填输入框；用户看到刷新后的会话。
3. 用户再次发送 → 若 A 无新写入则正常执行；若仍有 → 再次拦截（对称）。

### 4.3 B 回合被中止（B 跑到一半、A 开始写）

1. B 的回合进行中，某工具调用前检查发现偏差。
2. 中止回合：停后续工具、写中止记录、通知用户；已完成部分完整保留。
3. B 的内存态随后吸收 A 的写入，历史对两边完整可见。

### 4.4 元数据并发写（ADR-006 后的终态）

1. A 改标题、B 归档，几乎同时。
2. 双方经存储端口各写各的字段（A 只写 title 列、B 只写 archived 列）。
3. 两个字段都生效——并发互抹在机制上不存在（字段级增量更新是端口写方法的强制形态，US C3.1）。

## 5. 错误处理

| 故障点 | 行为 |
|---|---|
| 版本探测失败（元数据读不到） | 读路径：降级用内存态，不阻断浏览；写路径围栏：按无法判定处理，拒绝提交并提示重试（宁拦勿写）；回合监视器：按偏差处理，中止回合（宁停勿脏） |
| 增量吸收遇到未写完整的最后一段 | 停在上一完整记录，下次探测再补；不报错不丢段 |
| 吸收时发现日志被截断（罕见：文件比已知偏移短） | 视为不可恢复的外部变更，重新完整恢复该会话（降级为慢路径） |
| 库启动自检失败（ADR-006） | 不静默降级——走恢复流程：先试备份回滚，备份不可用走半重建（正文目录全量重建行，标题取首条用户消息、时间戳取文件修改时刻；归档态仅对压缩形状可推断，未压缩的归档回未归档态——人工标注按最坏丢失计） |
| 存在性回收器遇目录回收失败（ADR-006） | 留待下轮，不阻塞不报错升级；墓碑仍在，不误收无墓碑的无主目录 |

## 6. 测试策略

集成测试以"同一数据目录下两个服务器实例"为标准夹具，覆盖需求验收逐条对应的场景：双开跟随、提交拦截与消息回填、回合中止、元数据并发写（字段级增量更新的互不抹除）、存在性判定与墓碑回收。另设三类专项：**围栏间隙并发注入**（在提交检查与回合首记录落盘的间隙注入另一入口的写入，验证残余窗口行为符合设计）；**自身写入回归**（自身回合的追加不触发自中止、不误亮活动徽标、不重复折叠）；**双实例长稳**（同目录双实例持续交替写入 soak，验证无漏段、无行回退）。单元测试覆盖：版本比较、增量吸收边界（未写完整尾部、偏移锚定）、字段级增量更新的并发矩阵（不同字段并发、同字段先后）、迁移幂等重入、库自检失败的恢复流程。性能测试：大体量会话的跟随开销与新增内容量（而非历史体量）成正比的断言。US C2.3 的提示文案断言（不含进程名、文件名、机制名等内部词汇）。

## 7. 决策记录

### ADR-001：乐观并发控制 + 回合级围栏（否决：会话级租约）

- **背景与动机**：多入口共享同一数据目录，需同时解决可见性与防双跑。悲观租约（锁文件 + 心跳 + 接管语义）与乐观检测（版本比对 + 刷新）两条路线可选。
- **决策**：乐观为主、回合级围栏为辅。版本号取自追加日志的"长度 + 修改时刻"，免费且单调；检测点挂读侧各同步时机与写侧提交/工具调用前；不引入租约与进程发现。
- **否决项与理由**：会话级租约被否决——需定义锁协议、崩溃恢复、接管语义，实现与体验成本最高，且"强制接管"概念与追加式历史的无主语义冲突；纯乐观（只刷新不拦截）被否决——无法关闭"检查后写入中"的竞态窗口，两代理同时操作用户工作目录的副作用事后不可恢复；文件系统事件监听被否决——亚秒级收益不抵监听器生命周期与跨平台差异的复杂度，周期探测已满足秒级跟随。
- **影响范围**：全部需求条目；§3 全部组件。

### ADR-002：拦截语义为"拦截 + 提醒 + 消息回填"，且围栏必须在消息落盘之前

- **背景与动机**：拦截若发生在消息落盘后，将出现"消息已进历史但回合未执行"的半状态，回滚复杂度全数回归。
- **决策**：提交围栏在用户消息落盘前裁决；拦截时磁盘零写入、客户端本地保留消息并回填输入框。
- **否决项与理由**：落盘后检测+回滚被否决——需要事务性撤销，与追加式日志的不可变语义冲突。
- **影响范围**：US C2.1；§3.3。

### ADR-003：元数据字段级合并而非整份覆盖

- **背景与动机**：元数据文档的原子重写在并发下是"最后写者整份覆盖"，两边改不同字段会互相抹掉。
- **决策**：写前检测磁盘版本非己所写则先读入、按字段最新者胜合并、再原子写出。
- **否决项与理由**：整目录锁被否决——为 KB 级小文档引入跨进程锁不成比例；不处理被否决——"桌面改的名字被网页抹掉"是用户可感知的数据丢失。
- **影响范围**：US C3.1；§3.5。

### ADR-003-R1：字段级合并的判定机制定为三路合并（原"时间戳较新者胜"不可实现）

> **已被 ADR-006 取代（2026-11-03）**：元数据文档退役后，本 ADR 的三路合并协议随之退役；字段级并发保护由存储端口的字段级增量更新（强制不变量）机制性保障。正文保留作历史记录，实施语义以 ADR-006 为准。

- **背景与动机**：元数据文档的磁盘形态只有文档级时间戳，无字段级时间戳——原基线的"每个字段取时间戳较新者"缺少判定依据；后写者只知道自己第二，无法凭时间戳知道对方改了哪些字段。
- **决策**：判定机制改为**三路合并**——进程保留自己上次写出的快照作为共同祖先，与磁盘当前版本逐字段比对：磁盘变化而己方未变取磁盘值；己方变化而磁盘未变取己方值；双方都变取己方值（后写者胜）。不要求元数据文档做任何形态演进。
- **否决项与理由**：字段级时间戳（或版本向量）被否决——判定更强但要求跨引擎兼容验证（旧引擎写入的文档无这些字段），为一项并发合并引入形态迁移成本不成比例；两路覆盖（己方全胜）被否决——会复现"整份覆盖"被否决的同一问题。
- **影响范围**：US C3.1；§3.5；§6 测试策略（三路合并优先级）。

### ADR-004：索引对账跨进程序列化（锁文件 + 过期接管模式），单行写不串行化

> **已被 ADR-006 取代（2026-11-03）**：索引升格为唯一事实源后对账机制整体消解，本 ADR 的锁与单行写数据源约束随之退役；其实施批注的两类读面消费方（启动读面不等待、恢复按需收敛）失去载体。正文保留作历史记录，实施语义以 ADR-006 为准。

- **背景与动机**：两个进程各自执行的"读盘-比对-重写"对账可互相覆盖、互相删行；但单行写已受数据库自身并发配置保护。另发现：单行 write-through 若以未对账的进程内存快照为数据源，会把另一入口已合并落盘的字段值冲回旧值。
- **决策**：对账与批量维护包跨进程互斥（锁文件 + 过期接管，与工作区注册表同一模式）；单行写维持现状，但**其数据源必须为磁盘最新元数据文档（或经合并写入器同步的内存态）**。
- **否决项与理由**：全量写路径都加锁被否决——热路径上引入跨进程等待，违背"缓存故障不升级"；单写者实例被否决——与"多入口独立共存"的现有部署形态冲突。
- **影响范围**：US C3.2、US C1.1；§3.6。

> **ADR-004 实施批注（2026-11-03，非功能性域 ADR-003 同批）**：本 ADR 的对账收敛语义新增两类消费方——①启动读面（会话列表等）在索引未收敛时**不等待对账完成**（行暂缺由本 ADR 的幂等收敛语义兜底，下次读取补齐）；②会话恢复/按 id 读取在索引未命中时**按需触发一次对账收敛**再判 not-found（避免启动期未收敛的会话打不开）。引擎装配段声明的「首个 dispatch 前对账必须结算、并发 session.list 必须看到已对账的行」内联时序随之放宽，由非功能性域 ADR-003 的按路由结算门承接（该放宽属其「裁决反转记录」）。对账本身的锁与写语义（本 ADR）不变。

### ADR-005：回合与吸收的互斥契约（自身写入同步推进版本锚）

- **背景与动机**：若自身回合的追加不推进本地已知版本，回合监视器会把本入口自己的写入当成偏差而自中止、活动徽标因自身活动误亮、吸收器重复折叠自己的记录；若版本锚先于字节消费推进，被跳过的字节永久漏段；若回合运行期间并发执行吸收，与回合循环竞态修改同一内存态。
- **决策**：三条不变量（详见 §2.4）：自身写入在写入点同步推进已知版本；版本锚推进不先于字节消费；回合运行期间跟随调度器只上报不吸收，吸收延迟至回合结束/中止后，吸收目标态为引擎会话内存态本身。
- **否决项与理由**："探测即吸收、与回合循环靠细粒度锁共存"被否决——为省一次中止引入回合循环与吸收器的复杂双向互斥，正确性论证成本高于直接延迟吸收；"吸收目标为界面投影态"被否决——与检查点、索引形成三态分叉。
- **影响范围**：US C1.2、C1.3、C2.2；§3.2、§3.4、§3.7。

### ADR-006：SQLite 升格为会话元数据唯一事实源，state.json 退役（2026-11-03）

- **编号与日期**：ADR-006 · 2026-11-03 · 以下决策 d)/e) 以「待裁决点」全部落定为生效前提。**裁决完成（2026-11-03）**：五项待裁决点均已由用户逐项裁决（各待裁决点内嵌裁决记录），本 ADR 进入已裁决待实施状态。
- **背景与动机**：会话元数据当前存在**两个表示**——磁盘上的元数据文档（每会话一份）与索引数据库行（读模型）。两个表示之间靠启动对账维持镜像一致。该结构有三类内生成本：
  1. **镜像一致性的永久维护成本**：对账每次全量执行（逐会话目录比对、逐行查库写库），成本随历史会话总量单调增长；写穿透是尽力而为的（失败仅告警），漂移随时可能发生，对账是兜底收敛器——只要双表示存在，这套机制就无法拆除。
  2. **崩溃窗口的结构性缺口**：元数据双写的两步（磁盘文档→索引行）之间无事务，中途崩溃留下永久性漂移，只能靠对账事后收敛。
  3. **半残会话态**：物化写序是"元数据先、对话日志后"，两步之间崩溃产生"有元数据无正文"的会话；恢复语义将其降级为空会话——不崩溃，但从一致性视角是失败态，且索引层无从区分"完整会话"与"空壳"。
  现状证据与实测数据（索引漂移构成、对账成本量级、孤儿行来源分布）见 [session-consistency-context.md](session-consistency-context.md) §5。
  动机抽象：**元数据的唯一权威表示应当只有一个；任何第二表示都是需要永久维护的缓存**。
- **决策（已裁决终态，2026-11-03）**：
  a) **升格**：索引数据库升格为会话元数据（标题、标签、时间戳、归档/压缩戳、最近输入等）与**会话存在性**的唯一事实源；磁盘元数据文档退役。
  b) **写序反转**：会话物化改为"**先写数据库行、后建对话日志**"。行即会话的户口，日志即正文；"行在、正文无"从崩溃残留态变为合法的"刚创建尚未对话"态（与懒物化语义自然对齐；物化守卫从元数据文件存在性改为对话日志存在性——日志存在性指未压缩或压缩形态之一存在，见影响范围·保留域联动）。写序反转同时把"未对话会话不写行"的守卫语义改写为"创建即写行、按最近输入为空过滤"——非过滤列表面对空壳行可见；设计上不加物化标志位（理由：过滤列表面是默认视图，非过滤面可见空壳属可接受行为，为它加列与维护不值当）。
  c) **双写消失，对账消解**：元数据单表示后，内容级对账（mtime 比对、整份重读）整体不再需要；保留的不是对账，而是**存在性收敛的降格形态**——行删除是事务性的，但会话正文目录的清理是文件操作，"行删目录在"的残留降格为**不影响列表正确性的磁盘垃圾**，由低频后台归档回收（不挡任何读路径、不进启动关键路径）。**回收判别用墓碑**：删除事务内记录墓碑（会话 id + 删除时刻，与行删除同事务落库），回收器只回收"墓碑命中且无行"的目录；**无墓碑的无主目录**（用户拷入、备份碎片）按裁决 3 由用户自行处置，不属回收器管辖——两类残留由此可判别，回收器永不触碰用户放入的目录。
  d) **并发语义迁移**：跨进程元数据冲突从"三路合并 + 原子重写"（ADR-003-R1）迁移为存储端口的**字段级增量更新（强制不变量**，见待裁决点 4 裁决）——每个写点只写自己改的字段，并发互抹在机制上消灭；提交围栏与回合中止（ADR-001/002）机制不变，其版本锚继续锚定对话日志文件（本 ADR 只动元数据表示，不动并发协调框架）。
  e) **迁移路径（一次性切换，无双写过渡期**，见待裁决点 5 裁决）：升级后首次启动自动完成——检测旧格式 → 迁移前备份 → 种子收敛补齐行（种子为现有对账 pass 的最后一次执行）→ 库内盖格式版本章；`state.json` 同批停止读写（旧文件不删不碰）；切换幂等可重入，中断自愈。回滚通道为迁移前备份 + 旧二进制，无运行时开关。
- **存在性判定迁移**（写序反转的配套约束）：以元数据文档存在性为会话存在/归属判定的全部消费点需统一迁移为查数据库行（或按其语义改为日志存在性），含：对账枚举、工作区归属探测的兜底层、无库降级的磁盘扫描枚举、列表合并的数据源、旧布局迁移命令的判定谓词、归档/恢复的物化检查、**导出/诊断包的标题与活动时间提取、fork 管线的元数据继承基底、中断恢复扫描的归档过滤谓词**。各消费点的过渡期行为（行在文档无的窗口态下如何应答）属实施计划的逐点清单，但**迁移义务与统一判据由本 ADR 裁定**。`snapshot.json` 为正文加速件（检查点），不在元数据退役范围。
- **待裁决点**（已全部裁决，2026-11-03，用户；每项内嵌裁决记录）：
  1. **无库降级形态**：引擎存在无个人数据目录的运行形态（ACP 内嵌引擎的工作区局部持久化、测试）。候选：工作区局部形态也用数据库（库放工作区目录内）/ ACP 注入 home 统一存储 / 不再支持无库形态。
     > **裁决（2026-11-03，用户）**：选 ACP 注入 home——ACP 的会话归属用户而非工作区（用户的使用流是"从 ACP 干活、不顺手回 desktop 继续"，两面对同一仓库应看到同一批会话）；列表可见性**保持**钉死于当前工作区（防编辑器宿主越权浏览其他工作区会话，与存储归属是两个正交裁决）；工作区局部持久化路径退役，存量会话经迁移工具迁入 home；无库形态退出产品面（测试夹具用临时 home + 临时库），"回退磁盘扫描"降级路径随之消亡。注：ACP 既有装配本就优先探测复用运行中的桌面 server（远程共享同一引擎），内嵌引擎的隔离是无桌面时的残留行为，本裁决将其抹平。
  2. **数据库损坏的恢复路径与 schema 演进纪律**：爆炸半径从"坏一个文件丢一个会话的元数据"变为"坏库丢全部元数据"；且现状 schema 迁移链的安全性建立在"索引是可整库丢弃的缓存"上，升格后**迁移失败即事实源损坏**，旧二进制遇新 schema 的行为也需定义。
     > **裁决（2026-11-03，用户）**：采纳三级恢复金字塔 + 演进纪律——①**启动自检**：每次启动于连接打开序列内跑全量结构自检（成本为与存量无关的常量，实测见 context §5；库增大后的退路是抽样版或降频，近期不需要）；自检失败**不静默降级**，走恢复流程。②**备份纪律**：滚动双备份，写时机挂**每次 schema 迁移前 + 优雅关机时**（均为非启动路径，正常启动零成本）。③**半重建兜底**：库损坏且备份不可用时，扫描会话目录从对话日志重建行（标题取首条用户消息、时间戳取文件修改时刻）——归档态仅对压缩形状可推断（压缩必先归档），未压缩的归档会话重建后回到未归档态，与标签同列"最坏丢失的人工标注"；重建器经存储端口全字段一次写回，与字段级更新不变量不冲突（重建是唯一合法的全字段写点）。该重建器即现对账 pass 的降格复用，从"启动例行"转为"应急通道"。**schema 演进**：迁移前必备份，DDL 由事务保证原子；采用**只扩展不收缩（expand-only）纪律**——日常演进仅做增量变更（加列带默认值、加表），SQLite 特性使旧二进制（N-1）对新 schema **无感知继续读写**（显式列名的读写不触碰新列、保留其已有值），升级即兼容；**破坏性变更（改列语义/删列/改主键）预留 major 格式标记，仅此时旧二进制拒绝写入并提示升级**（不做静默只读——只读模式会掩盖事实源已不健康）。expand-only 的固有代价显式接受：加列后旧二进制重写该行会把新列落回默认值——新列要么是从既有行数据可推导的派生字段，要么接受该重置。**不采纳**：云同步路径检测告警（跨平台产品为一个低概率场景维护各平台同步路径检测，用力过猛；备份纪律已是对该类故障的兜底，重复防护）。
  3. **单会话可携带性**：现状"拷走一个会话目录 = 拷走完整会话"（外部排查、手动备份、迁移）。元数据入库后该语义退役。
     > **裁决（2026-11-03，用户）**：接受退化，且**不建任何补偿机制**（含常态半重建兜底）——"单会话拷贝/分享"经需求推敲为伪命题：对话日志携带原机器路径与环境信息，裸分享本身是隐私泄漏（分享的正路是让模型产出综合报告，对话内已有此能力）；单会话备份/跨机迁移无真实普遍需求（备份是全量行为，整库备份已在待裁决点 2 覆盖）。常态不提供"无主目录自动补行"的扫描机制——正常路径数据库是权威，无主目录不是需要处理的状态；磁盘上多出的孤立目录不进任何列表、由用户自行处置。从对话日志重建行的逻辑仅存在于损坏恢复路径（待裁决点 2 第三级），不作为常态机制。
  4. **核心层依赖反转**：会话核心层现状不依赖数据库（依赖方向是外围索引层依赖核心层）；升格后核心层变为数据库承载（或引入存储端口抽象）。这是工作量主体，需裁决抽象层次。
     > **裁决（2026-11-03，用户）**：选存储端口（收窄版）——核心层定义元数据存储端口（async，仅覆盖元数据 + 存在性：get/upsert/delete/list-ids/batch），实现两个：数据库（生产）与内存（测试夹具）；对话正文（wire.jsonl）继续直连文件，不为正文做端口；与既有文件系统注入模式同构，不引入新范式。**字段级更新为强制不变量**：端口写方法按字段增量（partial update）设计，核心层每次只写自己改的字段——并发互抹（A 改标题、B 归档互相覆盖）在机制上消灭，偿还三路合并（ADR-003-R1）退役后的并发保护债；代价是全部写点从"整份序列化"改为"声明字段增量"，属本决策点主体工程量。
  5. **过渡期纪律**：双写期的兼容读优先级、回滚开关（按启动整体切换还是按会话粒度）、旧版本二进制与新版共存同一数据目录时的数据与 schema 双向互认策略。若本 ADR 裁决被推翻或实施周期过长，干净关机章（epoch）方案是独立的近期止血退路，其启用判据在本项一并定义。
     > **裁决（2026-11-03，用户）**：选**一次性自动迁移 + 版本地板锁**，不留双写过渡期——①升级后首次启动自动完成全部迁移（检测旧格式 → 迁移前备份 → 种子收敛补齐行 → 库内盖格式版本章），迁移幂等可重入；②`state.json` 同批停止读写，目录内旧文件不删不碰（视作历史遗迹，由用户自行处置）；③格式版本超过旧二进制认知地板时，旧二进制**启动即礼貌拒绝**（"数据已升级到新格式，请升级应用"）——这是待裁决点 2 预留的破坏性变更（major 标记）机制的首次启用，锁即最强形式的升级建议。共存窗口由此消失：不兼容旧版本，而是旧版本遇新数据主动退出。残余边界与实施约束：升级时仍在运行的旧实例锁不到（地板锁只拦新启动）——**窗口内旧实例的元数据写入（改名、归档等）在新格式下丢失，且其旧式整行回写会把新实例刚做的字段级更新冲回旧值**；这是一次性切换的显式代价，缓解手段为：**迁移序列必须以独占方式持有库（发现活跃连接/锁即提示"请先退出其他入口"后再执行）**——这同时给"重启全部入口"提供了检测机制。窗口闭合指锁的可观测恢复，**不含窗口内旧实例写入的找回**。"自愈"仅指：旧实例退出后不复存在、下一启动即被地板锁拦住。**回滚通道**：无运行时开关——出严重问题回退靠迁移前备份（数据）+ 旧二进制（代码），方向 1 的固有代价。**epoch 退路启用判据**：本 ADR 实施未完成期间若需启动性能止血，epoch 方案（被否决备选 1）可独立先行，与本 ADR 无依赖冲突；一旦本 ADR 落地其对账消解即取代 epoch 的全部收益。**发布策略**：本裁决为**机制奠基**而非立即发布——不为此单独发 minor；该一次性迁移与地板锁能力随本 ADR 的实施批次自然交付，同时为未来任何再次的破坏性升级（格式/存储变更）提供同款通道。
- **被否决的备选方案**：
  1. **维持现状 + 干净关机章（epoch）方案**——优雅关机时收尾收敛后盖章、运行期写穿透失败置脏标记、下次启动凭章跳过对账。否决理由：把启动成本从"存量的函数"改为"关机是否干净的函数"，性能问题得解，但双表示与对账机制本身永久保留——维护两套一致性的复杂度持续存在，且章机制本身是一套需要维护正确性的新状态机。**注**：作为独立于本 ADR 的近期止血方案保留可行性（启用判据见待裁决点 5）。
  2. **元数据文档保留 + 索引行增加完整性信号**——对账时把"对话日志是否存在"记进索引行，让列表层区分"完整会话"与"元数据孤儿"。否决理由：只让半残态可辨识，不消除双表示与对账本体，治标不治本。
  3. **对话正文也入库（全量单库）**——否决理由：对话日志是每回合追加的流式大对象（单会话可达数十 MB），入库使恢复扫描、自动压缩、外部排查工具链全部重写；迁移本身即一次全量对账；"绝对单库"的美学收益不抵工程与风险成本。
