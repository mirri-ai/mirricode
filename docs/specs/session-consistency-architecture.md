# 会话一致性 — 架构设计（面向 Rust 核心）

## 1. 目标与设计原则

本设计描述**终态**：Rust 核心中多个服务入口共享同一份个人数据目录时的会话一致性架构。策略选型为**乐观并发控制为主、回合级围栏为辅**（ADR-001），不引入租约、锁文件、进程发现等悲观协调机制。

设计原则（对应需求编号）：

1. **文件即事实源即信号**：会话的操作日志是只增不改的追加文件，其"长度 + 修改时刻"天然构成单调版本号；一切同步与冲突判定都锚定它，不发明第二套版本机制（US C1.x、C2.x）。
2. **拦截只挂在提交动作上**：浏览路径永远只刷新不拦截；拦截点必须发生在用户消息落盘**之前**，保证被拦截时零回滚、零半成品（US C2.1）。
3. **增量为王**：任何同步路径只处理自上次同步点以来的新增内容；禁止任何路径退化为全量重放（US C4.1）。
4. **开销与体量解耦**：版本探测是常量时间的元数据读取；跟随开销只与新增内容量成正比（US C4.1、C4.2）。
5. **元数据字段级合并**：元数据文档的并发写按字段级"最新者胜"合并，不做整份覆盖（US C3.1）。
6. **清单维护跨进程序列化**：索引对账与批量维护包进跨进程互斥（锁文件 + 过期接管模式的跨进程互斥），SQLite 自身的并发配置保持现状（US C3.2）。

## 2. 域模型

### 2.1 核心概念

- **会话版本（session version）**：`(字节数, 修改时刻)` 二元组，取自对操作日志文件的一次元数据读取。字节数是主信号（追加文件只增不减），修改时刻为辅助信号。版本读取是微秒级操作，可高频执行。
- **本地已知版本（known version）**：一个入口进程内持有的"我已同步到哪个版本"，由两个来源更新——自己落盘写入后的已知版本前进；检测并吸收另一入口写入后的版本前进。
- **版本偏差（version divergence）**：磁盘当前版本 ≠ 本地已知版本。出现偏差时**不区分成因**（另一入口在写、或其崩溃前的最后写入），一律按"先刷新、再让用户重新确认"处理（US C2.1 的中性文案要求）。

### 2.2 冲突判定的时序模型

```
读侧（浏览路径）                     写侧（提交路径）
──────────────                     ──────────────
打开/恢复会话 → 检查版本             用户提交 → ①检查版本
  偏差 → 增量吸收                     偏差 → 拦截+提醒+消息回填（落盘前）
  无偏差 → 直接用                     一致 → ②落盘用户消息
前台周期检查 → 偏差则增量吸收                ↓
  （驱动实时跟随与活动徽标）           ③回合首条记录落盘前再验一次
列表/详情查询 → 顺带比对                 回合进行中 → 每个工具调用前检查
                                        偏差 → 中止本回合+留中止记录+通知
```

- **①提交前检查 + ③回合首记录前复验**共同构成提交围栏：即使检查与落盘之间存在微小窗口，③把"带偏差落盘"的概率压到 ①③ 之间的毫秒级间隙。
- 回合进行中的检查把中止延迟上限约束为一个工具调用的执行间隙。

### 2.4 回合与吸收的互斥契约（ADR-005）

三条不变量，缺一即出现"自己中止自己"或"漏段"：

1. **自身写入在写入点同步推进本地已知版本**。本入口每次落盘追加操作日志成功后，立即以刚写出的字节长度推进本地已知版本。增量吸收器因此**只处理外来写入**——自己的回合产生的追加永远不会被当成另一入口的偏差（回合监视器不会自中止、活动徽标不因自身活动误亮、吸收器不会重复折叠自己的记录）。
2. **版本锚的前进不得先于字节消费**。已知版本的推进只发生在两种时刻：自己刚写出的内容（天然已消费）；完成一次增量吸收之后（锚取于本次实际读到的末条完整记录边界，含对未写完整尾部的容忍）。禁止任何"先按元数据推进版本、后读内容"的路径——那会把跳过的字节永久漏段。
3. **回合运行期间，跟随调度器只上报、不吸收**。本入口回合运行中探测到偏差时，不并发执行增量吸收（避免与回合循环竞态修改同一内存态），而是立即触发回合监视器的既有中止路径；吸收延迟至回合结束或中止完成后进行。若本入口无回合在跑，跟随调度器探测到偏差直接吸收。会话内对内存态的并发访问以会话级互斥（回合循环与吸收器共享）串行化。

吸收的目标态是**引擎的会话内存态本身**（与恢复时刻的重放同一份状态），而非界面投影——由此检查点快照、界面投影、索引行都从同一份吸收后的内存态派生，不产生三态分叉。

### 2.3 范围边界

- 本设计的协调对象是"共享同一份个人数据目录的服务进程"（web 服务入口、desktop 服务入口，同一可执行文件的多个实例）。
- 终端旧引擎与 TypeScript 旧核心不在本设计范围内（见需求文档范围边界）；它们与本设计机制无交互——它们按既有方式读写磁盘，本设计读侧的增量吸收与字段级合并对它们的写入同样成立（视为"另一写入者"）。
- 会话 id 由各入口独立铸造（通用唯一标识），两个入口同时新建会话不会产生同名目录冲突；新建时的目录惰性物化对并发创建容忍（重复创建同一目录不报错）。
- 会话的检查点快照（snapshot.json）与操作日志并发写入为良性：快照采用原子替换写出，且重放以操作日志锚定进度、快照只作加速——旧快照最多导致恢复时多回放一段（慢路径），不产生错误状态。快照与吸收的内存态一致性由 §2.4 的互斥契约保障。
- 附件内容先于引用它的日志记录落盘（写序不变量），因此版本锚只锚定操作日志是安全的——版本前进到引用某附件的记录时，附件内容必然已在磁盘上。

## 3. 架构组件

### 3.1 版本探测器（version probe）

- **职责**：给定会话存储单元，返回其当前版本；比对本地已知版本，报告偏差。
- **依赖**：文件系统元数据读取（无内容读取）。
- **契约要点**：元数据读取失败按"无法判定"处理，不抛错阻断上层——读路径降级为直接使用内存态（宁可用旧的，不因探测失败卡死浏览）。

### 3.2 增量吸收器（incremental absorber）

- **职责**：给定同步偏移点，读取操作日志新增字节，重放进内存态，推进本地已知版本。
- **依赖**：追加日志读取（含对"最后一段未写完整"的既有容忍——停在上一完整记录，下次继续）。
- **契约要点**：
  - 以字节偏移为锚，绝不重读偏移之前的任何内容（US C4.1）。
  - 吸收是**写前动作**：吸收完成后才允许基于新状态继续（提交路径的拦截判定发生在吸收之前，见 §2.2 的顺序）。
  - 对一个已打开的运行中会话持续吸收外部新增记录，是本设计新增的运行模式（区别于仅在恢复时刻的单次重放）。

### 3.3 提交围栏（commit fence）

- **职责**：在用户消息落盘前做最终版本裁决；在回合首条记录落盘前复验。
- **契约要点**：
  - 拦截返回结构化错误（错误码 + 提示文案键），客户端据此提示并把消息回填输入框；**围栏通过后到落盘之间不再有任何用户可见动作**。
  - 拦截对 RPC 层是普通失败响应，不引入新通道。

### 3.4 回合监视器（turn guard）

- **职责**：回合执行期间，在每个工具调用执行前做版本检查；发现偏差则请求中止回合。
- **契约要点**：检查在工具调用调度点执行，微秒级，不改变工具调度语义；中止遵循既有回合中止路径（停后续工具、写中止记录、通知用户），不新造终止机制；**探测失败时按偏差处理**（无法判定 = 宁停勿脏，中止并提示重试）。

### 3.5 元数据合并写入器（metadata merge writer）

- **职责**：元数据文档落盘前，若磁盘版本 ≠ 自己上次写出的版本，先做**三路合并**再原子写出：以本进程保留的"自己上次写出的快照"为共同祖先，与磁盘上的当前版本做字段级比对——磁盘相对祖先有变化而己方未变的字段，取磁盘值；己方变化而磁盘未变的字段，取己方值；双方都变的字段，取己方值（后写者胜）。
- **契约要点**：
  - 合并只需"自己上次写出的快照"与"磁盘当前版本"两份输入，**不依赖元数据文档携带字段级时间戳**——判定依据是共同祖先的三路合并，跨引擎（对方是旧引擎写入的文档）天然成立。
  - 合并只发生在检测到并发时；单侧修改路径与现状完全一致。写出仍走既有原子写原语（临时文件 → fsync → 原子重命名），合并逻辑叠加在其上，不产生第二条写路径。
  - 合并后更新"自己上次写出的快照"为新写出值。

### 3.6 索引维护串行器（index maintenance serializer）

- **职责**：将对账与批量索引维护动作用跨进程互斥串行化（锁文件 + 过期接管语义的跨进程互斥，与工作区注册表同款模式）；单条行的日常写仍走 SQLite 既有并发配置（WAL + 忙等超时）。
- **契约要点**：
  - 串行化只包**对账/批量维护**这类"读盘-比对-重写"的复合动作，不包单行写；锁等待设上限，超时降级为本轮跳过（下轮再对账），不阻塞用户操作（延续"缓存故障不升级"原则）。
  - **单行 write-through 的数据源约束**：任何索引行的回写，其数据源必须是磁盘上最新的元数据文档（或已经过合并写入器同步的内存态）——**禁止直接使用未经对账的进程内存快照回写行**，防止陈旧元数据把另一入口已合并落盘的字段值冲回旧值（US C1.1 与 C3.2 的交叉保障）。

### 3.7 前台跟随调度器（foreground follow scheduler）

- **职责**：为处于前台的已打开会话安排周期性版本探测（秒级间隔）；偏差则触发增量吸收并把新内容经本入口的事件通道推给界面；会话离开前台即停止。
- **契约要点**：调度挂在会话的前台状态上；探测失败静默重试（下个周期），不报错。

## 4. 数据流

### 4.1 双开浏览（A 跑回合、B 旁观）

1. A 的回合持续追加操作日志 → A 的已知版本持续前进。
2. B 的前台跟随调度器周期探测 → 发现偏差 → 增量吸收新字节 → 经 B 的事件通道推 UI。
3. B 的用户看到 A 的回合逐段出现；徽标基于"版本持续前进"点亮与熄灭。
4. B 把会话切后台 → 调度停止；切回 → 从暂停偏移补齐。

### 4.2 B 提交被拦截（A 有未同步写入）

1. B 提交 → 围栏检查发现偏差 → 拒绝执行（磁盘零写入）→ 返回结构化错误。
2. 客户端提示 + 消息回填输入框；用户看到刷新后的会话。
3. 用户再次发送 → 若 A 无新写入则正常执行；若仍有 → 再次拦截（对称）。

### 4.3 B 回合被中止（B 跑到一半、A 开始写）

1. B 的回合进行中，某工具调用前检查发现偏差。
2. 中止回合：停后续工具、写中止记录、通知用户；已完成部分完整保留。
3. B 的内存态随后吸收 A 的写入，历史对两边完整可见。

### 4.4 元数据并发合并

1. A 改标题、B 归档，几乎同时。
2. 后落盘者检测到磁盘版本非己所写 → 读入合并 → 标题与归档同时生效。
3. 若同字段先后修改 → 三路合并中后写入者胜（详见 ADR-003-R1）。

## 5. 错误处理

| 故障点 | 行为 |
|---|---|
| 版本探测失败（元数据读不到） | 读路径：降级用内存态，不阻断浏览；写路径围栏：按无法判定处理，拒绝提交并提示重试（宁拦勿写）；回合监视器：按偏差处理，中止回合（宁停勿脏） |
| 增量吸收遇到未写完整的最后一段 | 停在上一完整记录，下次探测再补；不报错不丢段 |
| 吸收时发现日志被截断（罕见：文件比已知偏移短） | 视为不可恢复的外部变更，重新完整恢复该会话（降级为慢路径） |
| 索引维护锁等待超时 | 本轮跳过对账，下轮重试；不阻塞用户操作 |
| 合并写入时对方版本损坏 | 回退为整份覆盖自己的（延续"单点损坏不扩散"原则），并留告警 |

## 6. 测试策略

集成测试以"同一数据目录下两个服务器实例"为标准夹具，覆盖需求验收逐条对应的场景：双开跟随、提交拦截与消息回填、回合中止、元数据合并、索引互不删行。另设三类专项：**围栏间隙并发注入**（在提交检查与回合首记录落盘的间隙注入另一入口的写入，验证残余窗口行为符合设计）；**自身写入回归**（自身回合的追加不触发自中止、不误亮活动徽标、不重复折叠）；**双实例长稳**（同目录双实例持续交替写入 soak，验证无漏段、无行回退）。单元测试覆盖：版本比较、增量吸收边界（未写完整尾部、偏移锚定）、三路合并优先级、锁超时降级。性能测试：大体量会话的跟随开销与新增内容量（而非历史体量）成正比的断言。US C2.3 的提示文案断言（不含进程名、文件名、机制名等内部词汇）。

## 7. 决策记录

### ADR-001：乐观并发控制 + 回合级围栏（否决：会话级租约）

- **背景与动机**：多入口共享同一数据目录，需同时解决可见性与防双跑。悲观租约（锁文件 + 心跳 + 接管语义）与乐观检测（版本比对 + 刷新）两条路线可选。
- **决策**：乐观为主、回合级围栏为辅。版本号取自追加日志的"长度 + 修改时刻"，免费且单调；检测点挂读侧各同步时机与写侧提交/工具调用前；不引入租约与进程发现。
- **否决项与理由**：会话级租约被否决——需定义锁协议、崩溃恢复、接管语义，实现与体验成本最高，且"强制接管"概念与追加式历史的无主语义冲突；纯乐观（只刷新不拦截）被否决——无法关闭"检查后写入中"的竞态窗口，两代理同时操作用户工作目录的副作用事后不可恢复；文件系统事件监听被否决——亚秒级收益不抵监听器生命周期与跨平台差异的复杂度，周期探测已满足秒级跟随。
- **影响范围**：全部需求条目；§3 全部组件。

### ADR-002：拦截语义为"拦截 + 提醒 + 消息回填"，且围栏必须在消息落盘之前

- **背景与动机**：拦截若发生在消息落盘后，将出现"消息已进历史但回合未执行"的半状态，回滚复杂度全数回归。
- **决策**：提交围栏在用户消息落盘前裁决；拦截时磁盘零写入、客户端本地保留消息并回填输入框。
- **否决项与理由**：落盘后检测+回滚被否决——需要事务性撤销，与追加式日志的不可变语义冲突。
- **影响范围**：US C2.1；§3.3。

### ADR-003：元数据字段级合并而非整份覆盖

- **背景与动机**：元数据文档的原子重写在并发下是"最后写者整份覆盖"，两边改不同字段会互相抹掉。
- **决策**：写前检测磁盘版本非己所写则先读入、按字段最新者胜合并、再原子写出。
- **否决项与理由**：整目录锁被否决——为 KB 级小文档引入跨进程锁不成比例；不处理被否决——"桌面改的名字被网页抹掉"是用户可感知的数据丢失。
- **影响范围**：US C3.1；§3.5。

### ADR-003-R1：字段级合并的判定机制定为三路合并（原"时间戳较新者胜"不可实现）

- **背景与动机**：元数据文档的磁盘形态只有文档级时间戳，无字段级时间戳——原基线的"每个字段取时间戳较新者"缺少判定依据；后写者只知道自己第二，无法凭时间戳知道对方改了哪些字段。
- **决策**：判定机制改为**三路合并**——进程保留自己上次写出的快照作为共同祖先，与磁盘当前版本逐字段比对：磁盘变化而己方未变取磁盘值；己方变化而磁盘未变取己方值；双方都变取己方值（后写者胜）。不要求元数据文档做任何形态演进。
- **否决项与理由**：字段级时间戳（或版本向量）被否决——判定更强但要求跨引擎兼容验证（旧引擎写入的文档无这些字段），为一项并发合并引入形态迁移成本不成比例；两路覆盖（己方全胜）被否决——会复现"整份覆盖"被否决的同一问题。
- **影响范围**：US C3.1；§3.5；§6 测试策略（三路合并优先级）。

### ADR-004：索引对账跨进程序列化（锁文件 + 过期接管模式），单行写不串行化

- **背景与动机**：两个进程各自执行的"读盘-比对-重写"对账可互相覆盖、互相删行；但单行写已受数据库自身并发配置保护。另发现：单行 write-through 若以未对账的进程内存快照为数据源，会把另一入口已合并落盘的字段值冲回旧值。
- **决策**：对账与批量维护包跨进程互斥（锁文件 + 过期接管，与工作区注册表同一模式）；单行写维持现状，但**其数据源必须为磁盘最新元数据文档（或经合并写入器同步的内存态）**。
- **否决项与理由**：全量写路径都加锁被否决——热路径上引入跨进程等待，违背"缓存故障不升级"；单写者实例被否决——与"多入口独立共存"的现有部署形态冲突。
- **影响范围**：US C3.2、US C1.1；§3.6。

### ADR-005：回合与吸收的互斥契约（自身写入同步推进版本锚）

- **背景与动机**：若自身回合的追加不推进本地已知版本，回合监视器会把本入口自己的写入当成偏差而自中止、活动徽标因自身活动误亮、吸收器重复折叠自己的记录；若版本锚先于字节消费推进，被跳过的字节永久漏段；若回合运行期间并发执行吸收，与回合循环竞态修改同一内存态。
- **决策**：三条不变量（详见 §2.4）：自身写入在写入点同步推进已知版本；版本锚推进不先于字节消费；回合运行期间跟随调度器只上报不吸收，吸收延迟至回合结束/中止后，吸收目标态为引擎会话内存态本身。
- **否决项与理由**："探测即吸收、与回合循环靠细粒度锁共存"被否决——为省一次中止引入回合循环与吸收器的复杂双向互斥，正确性论证成本高于直接延迟吸收；"吸收目标为界面投影态"被否决——与检查点、索引形成三态分叉。
- **影响范围**：US C1.2、C1.3、C2.2；§3.2、§3.4、§3.7。
