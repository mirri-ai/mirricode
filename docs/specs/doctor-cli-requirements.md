# Doctor CLI（Rust 内核版）需求定义

> **文档类型：设计/Spec 类**（按 `docs/specs/AGENTS.md` 治理约定）——只写终态，不写执行状态。 ·
> 现状证据：[doctor-cli-context.md](doctor-cli-context.md) · 技术设计：[doctor-cli-architecture.md](doctor-cli-architecture.md) ·
> 需求变更以 SDR 追加记录，历史不重写。

## 0. 背景与动机（抽象问题陈述）

Mirri Code 处于 TypeScript 内核向 Rust 内核迁移的过渡期。两套内核对同一份配置文件（`config.toml`）的接受口径**不完全一致**：TS 侧校验较严（不认识的键名直接判错），Rust 侧较宽（多套键名拼写都接受，不认识的键静默忽略）。现有"配置体检"命令只按 TS 口径出报告，导致"配置文件明明能在 Rust 内核下正常工作，体检却亮红"的误报；反过来，Rust 内核静默忽略的拼写错误（比如把某个键名打错了），现有体检也发现不了。

用户在迁移期需要的是：**"我的配置文件拿到 Rust 内核上跑，到底行不行、哪里有问题"**——一个以 Rust 内核真实解析行为为口径的、开箱即用的配置体检命令。技术形态（命令名、子命令、校验器分层）见 [doctor-cli-architecture.md](doctor-cli-architecture.md)。

## 术语表

| 术语 | 定义 |
|---|---|
| Rust doctor | Rust `mirri` 二进制上的配置体检命令（本文档定义的对象） |
| TS doctor | 现有 TS CLI 的 `mirri doctor` 命令（迁移完成后整体退役） |
| 检查项（check） | 一次对单个配置文件的独立检查，产出 通过/跳过/报错 三态之一 |
| 硬错误（error） | 会导致引擎加载配置时失败或行为偏离用户意图的问题，体检必须非零退出 |
| 软警告（warning） | 不阻断启动但值得用户知道的问题（悬空引用、已下线的键等），不影响退出码 |

## 1. 用户故事与验收标准

### US-1 主命令：体检默认位置的配置文件

**故事**：作为迁移期用户，我运行 `mirri doctor`，得到一份对 `config.toml` 的体检报告，让我在把配置交给 Rust 内核前确认它没问题。

**验收标准**：

1. **US-1.1** 默认体检对象是 `<MIRRICODE_HOME>/config.toml`（`MIRRICODE_HOME` 环境变量优先，缺省 `~/.mirri-code`，与现有所有 mirri 子命令同一寻址规则）。
2. **US-1.2** 文件不存在时**不算错误**：报告为"跳过"并说明"内置默认配置将生效"，退出码 0。
3. **US-1.3** 文件存在但 TOML 语法不合法：报告为报错，错误信息包含**出错的行号或足够定位的上下文**，退出码 1。
4. **US-1.4** 文件语法合法但内容不合法（类型错误、互斥键冲突等引擎会拒绝的写法）：逐项列出问题位置（哪一段、哪一条、什么问题），退出码 1。
5. **US-1.5** 体检过程**绝不修改**任何文件——只读。
6. **US-1.6** 体检**不发起任何网络请求、不读取环境变量做覆盖展开**：校验的是"文件本身"。（理由：与"写回磁盘安全"的加载口径一致——体检结果应与"这份文件拿给一个干净环境里的引擎"的行为一致，而不是被本机恰好设置的环境变量改写。）
7. **US-1.7** 全部检查通过：输出简短的成功汇总，退出码 0。

### US-2 指定文件体检

**故事**：作为用户，我在改配置前会先在副本上试——`mirri doctor config /path/to/candidate.toml` 应能体检任意指定文件。

**验收标准**：

1. **US-2.1** 显式指定的路径不存在：报错（区别于 US-1.2 的默认路径跳过），退出码 1。
2. **US-2.2** 相对路径按当前目录解析。
3. **US-2.3** 体检通过与否的判定标准与 US-1 完全一致（同一套检查，只是文件来源不同）。

### US-3 未知键检测（对齐 TS doctor 的核心价值）

**故事**：作为用户，我把 `notification_conditon` 拼错了。Rust 内核会静默忽略它，我永远发现不了——直到某天行为不对。Rust doctor 应该告诉我。

**验收标准**：

1. **US-3.1** 配置文件里出现** Rust 内核完全不认识的顶层键或节**（即任何引擎层都不会消费的键）：报错并指明键名与所在段，退出码 1。
2. **US-3.2** 检测依据是 Rust 内核维护的已知键清单（单一事实源，与配置写回逻辑共用，不得手抄第二份）。
3. **US-3.3** 已知键清单内的**条目级未知键**（如 `[providers.foo]` 里拼错的字段）：同样报错指明（依赖条目级键清单）。
4. **US-3.4** 两套等价键名拼写（如 hooks 的 `matcher`/`pattern`、`timeout`/`timeout_ms`、`failClosed`/`fail_closed`，providers/models 各字段的 camelCase 别名）都视为合法——**Rust 内核实际接受什么，doctor 就接受什么**，不多不少。

### US-4 软警告（advisory）

**故事**：作为用户，我的 `default_model` 指向了一个我没配置的模型别名。这不会让启动失败，但意味着我的默认模型根本没生效。Rust doctor 应该提醒我。

**验收标准**：

1. **US-4.1** 引擎已有的软诊断（悬空的 provider/model 引用、遗留 `[model]` 段、已弃用键）全部纳入报告，显示为"警告"，**不影响退出码**。
2. **US-4.2** 警告逐条给出人可读的解释与修复建议。
3. **US-4.3** 警告来自引擎的单一诊断事实源（与 RPC 诊断面共用同一实现，不得复制第二份规则）。

### US-5 输出与退出码契约

**验收标准**：

1. **US-5.1** 退出码只有两种：0（无硬错误）与 1（至少一个硬错误）；警告不改变退出码。
2. **US-5.2** 成功与失败报告都包含每个被检文件的**一行状态行**（状态 + 文件标签 + 路径），硬错误与警告各自逐行缩进列出。
3. **US-5.3** 成功汇总写标准输出；失败报告写标准错误（便于脚本管道使用）。
4. **US-5.4** 报告文本为英文（与现有 Rust CLI 子命令的输出语言一致）。

### US-6 实验开关未知项检测

**故事**：作为用户，我配置里留着 `[experimental]` 里一个早已删除的实验开关名。它静默无效。Rust doctor 应该告诉我"这个开关已不存在"。

**验收标准**：

1. **US-6.1** `[experimental]` 段中的键若不匹配 Rust 内核注册的任何实验开关名（引擎注册表为事实源），报**警告**（不是硬错误——未知开关不破坏启动，且预留宿主自定义 flag 的可能）。
2. **US-6.2** 警告指明开关名与"它不在此引擎中生效"的语义。

## 2. 非目标（明确不做）

1. **不做 tui.toml 校验**——那是 TS TUI 客户端的私有文件，Rust 二进制不读它；迁移期由 TS doctor 覆盖，TS doctor 退役时 tui.toml 随 TUI 一同处理（另行裁决）。
2. **不做配置迁移/自动修复**——doctor 只诊断不治病；修复走 `mirri migrate` 或用户手工。
3. **不改 TS doctor 的任何行为**——两者迁移期并存，TS doctor 随 TS 内核整体退役。
4. **不做 JSON 输出模式**——当前没有机器消费方；有需求时以 SDR 追加。
5. **不校验 secrets/权限治理**（如 API key 格式）——不在配置体检职责内。

## 3. 需求边界与约束

1. Rust doctor 的判定口径**以 Rust 内核真实加载路径为事实源**：凡 `ServerConfig` 加载路径会拒绝的，是硬错误；会静默忽略但不在已知键清单里的，是硬错误（US-3）；会接受但语义可疑的，是警告（US-4）。
2. 体检命令自身必须零副作用：不写文件、不建目录、不联网、不读环境变量覆盖（仅 `MIRRICODE_HOME`/`HOME` 用于定位默认文件）。
3. 检查逻辑必须**可在不启动引擎/服务器的前提下运行**（进程内直接调用，秒回）。

## 4. 需求评审记录

按 `docs/specs/AGENTS.md` R1–R9 自查：

- **R1 终端消费者**：命令行用户在修改配置前后、排障时直接消费报告 ✅
- **R2 可见性 ≠ 强制**：本需求不涉及安全拦截面；体检的"强制点"即退出码 + CI 可集成性，已对称定义（警告不改退出码）✅
- **R3 具体性**：每个 US 的验收标准映射到具体行为（退出码、报告行、文件来源）✅
- **R4 信号真实性**：报告的每个状态都对应引擎真实加载行为（口径锚定在加载路径），无"显示有效实际无效"的信号 ✅
- **R5 可用性诚实**：不做半成品入口；不做的（tui.toml、JSON 输出）列入非目标而非占位 ✅
- **R6 先分析后裁决**：现状证据（双内核 schema 漂移实测、serde 行为、既有诊断面）在 [doctor-cli-context.md](doctor-cli-context.md) ✅

- **R8 语言分层**：本文为产品语言；技术形态全部指向 architecture 文档 ✅
