# server-e2e 场景测试域 — 技术架构

> **文档类型**：架构（Architecture）。需求见 [server-e2e-requirements.md](server-e2e-requirements.md)；现状见 [server-e2e-context.md](server-e2e-context.md)。

## 总体形态

```
┌────────────────────────── 测试进程（Node/tsx）──────────────────────────┐
│  scenario runner（用户的手）                                             │
│   ├─ REST 客户端（HTTP）──────┐                                         │
│   ├─ 事件客户端（JSON-RPC WS）┼────► 真实 mirri 进程（被测产品）          │
│   └─ 文件系统断言（落盘产物） │        │                                  │
│                              │        └─ HTTP ──► fake provider（模型替身│
│  fake provider（可编程剧本）◄─┼──────────────────── 剧本编排：本轮回什么、 │
└──────────────────────────────┘                      发起什么工具调用      │
```

三个角色：

1. **被测产品**：真实 `mirri` 进程（rust 二进制），以命令行参数和隔离的数据目录启动，可被 kill/重启（旅程阶段⑤）
2. **模型替身**（fake provider）：宿主侧 HTTP 服务，说 OpenAI 兼容协议（SSE 流式），测试按剧本预排它的响应（`nextToolCall` / `nextText` / 流式多段）
3. **用户的手**（scenario runner）：`packages/server-e2e` 的客户端——REST 走 HTTP、事件走 JSON-RPC WebSocket、断言落在文件系统与 REST/事件内容上

## 关键决策

### ADR-001：事件客户端迁移到统一 JSON-RPC 端点（`/api/v1/rpc`）（2026-10-28）

- **决策**：重写 `packages/server-e2e` 的 WS 层（`ws.ts`/`client.ts` 的事件订阅部分），改说统一 JSON-RPC 2.0 协议——web 生产客户端在用的同一端点。REST 方法（会话 CRUD、提交消息等）保持走 HTTP。
- **备选与否决**：①改造旧 `/api/v1/ws` 端点补齐客户端需要的 ack 语义——否决，该端点是已裁决的 legacy 面，为其添功能违背既有架构裁决；②REST 轮询代替事件流——否决，R5/R8/R10 的"实时性/流式"验收本质需要推送语义。
- **订阅与回放语义**（R10/R12 的架构依据）：统一端点的订阅自带游标（`{seq, epoch}`）——第二个连接中途接入时带游标订阅即可回放缓冲区间事件，保证不丢不重；epoch 失配触发重新同步而非错误。R10（页面刷新接续）与 R12（两处一致）的验收都建立在这一机制上。
- **约束**：迁移后旧协议帧类型（`subscribe`+`ack` 方言）在 server-e2e 中删除，不保留双协议。

### ADR-002：进程编排器（per-scenario lifecycle）（2026-10-28）

- **决策**：新增场景编排层：每个用例声明所需的产品进程形态（全新环境 / 带配置 / 需重启），由编排器负责 spawn、健康等待、kill、重启、清理。进程一律带隔离的数据目录（`MIRRICODE_HOME` 指向临时目录），测试之间零共享。
- **备选与否决**：各用例手写 spawn 逻辑——否决，进程生死是阶段①⑤的核心动作，散落重复且不可靠；引用 web e2e 的 spawn 辅助为依赖——否决，跨包依赖测试内部函数会把 web 的测试实现细节变成隐性契约。
- **一次性命令支持**：编排器除 `serve` 进程生命周期外，还负责执行一次性 CLI 子命令（旅程阶段⑥的 `mirri migrate`：编排器以同一数据目录运行该子命令并等待退出码）。

### ADR-003：剧本编排（模型替身的接口）（2026-10-28）

- **决策**：替身的剧本接口沿用 e2e-harness 的既有原语（`nextText`/`nextToolCall`/`nextRawSSE`），场景内按"轮次"预排。多轮工具循环（R7 的 写→跑→汇报）由场景逐轮排布。替身需支持**宿主外可达**（绑定所有网卡），供容器内进程与独立进程访问。
- **备选与否决**：为旅程场景新造"轮次感知"的更高层剧本 DSL——否决（YAGNI），既有原语足以表达所有旅程分支，抽象等真用例出现再加。
- **理由**：复用既有基础设施（web e2e 已用同一替身），零新概念。

### ADR-004：用例结构 —— 每旅程阶段一个文件（2026-10-28）

- **决策**：用例文件按旅程阶段组织（`scenarios/journey-01-first-launch.ts` …），每个文件一个独立进程编排上下文；文件内多个断言块共享同一次旅程推进。
- **备选与否决**：按接口域分文件（sessions/ws/config…）——否决，那是旧场景的组织方式，正是本次重做要抛弃的。

### ADR-005：docker 作为可选执行环境承载同一批场景（2026-10-28）

- **决策**：本域的场景默认在宿主本机跑（spawn 本机 rust 二进制）；docker 执行流程作为同一批场景的容器化载体存在（干净环境 + 容器→宿主替身的真实跨网段 HTTP），手动触发。
- **备选与否决**：docker 流程进 CI——否决，容器内全量 rust 编译耗时数分钟，远超 CI 预算，且旅程测试的核心价值（真实进程）本机已满足；删除 docker 流程——否决，"干净环境冷启动"与"真实跨网段 LLM HTTP"两个观察面只有容器能提供。

## 旧版会话夹具（R11 的数据来源）

`mirri migrate` 的输入是旧引擎存储布局的目录树。旅程阶段⑥的用例自带最小旧格式夹具（`state.json` + `agents/main/wire.jsonl`，按旧引擎的目录约定放置在隔离数据目录的 legacy 根下），迁移后由产品进程验证可列出、可打开、内容完整。夹具是测试数据，随场景文件一同维护。

## 与既有测试的边界

| 测试层 | 归属 |
|---|---|
| 引擎单元/集成（mirri-core 内部逻辑） | rust 单测 |
| 接口契约（路由、envelope、握手、订阅、回放） | rust 进程内黑盒（tests/ 目录） |
| **用户旅程连续性（进程生死、跨进程持久化、端到端兑现）** | **本域** |
| 浏览器 UI 行为（组件、渲染） | web 组件测试 + web rust e2e |
