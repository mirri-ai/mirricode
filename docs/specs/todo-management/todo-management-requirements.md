# 任务清单域（todo）— 需求文档（User Stories）

> 状态：v1 · 2026-10-22 · 待用户评审 ·
> 本文是任务清单域需求侧的唯一事实源（内部规格文档，不进文档站构建，中文单语）。
> 本文件记录**终态需求**：清单是会话级、可持久、可恢复、可回退的进度追踪状态——两个引擎凡未达到此终态的能力都在对齐范围内。
> 配套文档：技术形状见 [todo-management-architecture.md](todo-management-architecture.md)；现状缺口盘点（G1–G7，含代码锚点）见 [todo-management-context.md](todo-management-context.md)，本文不重复。
> 术语规范：任务清单（T7）、清单写入（T8）、写入提醒（T9）、过期提醒（T10）的唯一定义见 [glossary.md](../glossary.md)。
> 范围边界：本域管**清单的产品语义**——共享、持久、恢复、提醒、压缩保留。工具的模型可见契约（描述/参数/输出文案）归 tool-calling 域（builtin-tools §4.4），本域只在涉及行为时引用；清单面板的呈现细节归 conversation-rendering 域。

## 0. 角色定义

| 角色 | 场景 | 核心诉求 |
|---|---|---|
| **用户**（观察者） | 长任务中看进度、跨天续作、回退错误轮次 | 清单是真实进度的可信镜像：重启不丢、回退跟着对、压缩后模型还认 |
| **执行者**（干活的模型，含子代理） | 多步任务中维护与更新清单 | 全会话只维护一份清单，人人可见可写；忘了更新有人提醒 |
| **消费端**（终端/网页/重放器的开发者） | 从会话记录重建清单展示 | 任何时刻都能从持久记录推导出当前清单，无需活进程 |

## 1. Epic E1：清单的会话级共享

（现状对照见 context.md §1.1 / §2.1。）

### US1.1 一份清单全会话共享（P0）

作为执行者，整个会话只维护一份清单——主代理与任何子代理读写的是同一份。

验收：
- Given 子代理更新清单，When 主代理随后查询，Then 读到子代理写入的版本
- Given 多个代理并发读写，Then 清单始终是一个完整一致的版本，不出现交错拼接

### US1.2 清单生命周期等于会话（P0）

作为用户，清单的存续范围是整个会话，不随单轮对话结束或子代理退出而消失。

验收：
- Given 清单非空，When 回合结束 / 子代理完成退出，Then 清单保持
- Given 用户开启新会话，Then 清单从空开始，不携带旧会话内容

## 2. Epic E2：清单的持久与恢复（Rust 缺口 G1/G2/G4）

### US2.1 每次写入留痕（P0）

作为消费端，清单的每一次变更都落在会话的持久记录里——不留痕的变更等于没发生。

验收：
- Given 模型提交一次清单写入，When 会话记录落盘，Then 记录里能找到这条变更及完整新清单
- Given 会话记录被重放（恢复 / 回放器 / 冷快照读取），Then 按序重放所有写入后得到的清单 = 写入发生时的清单
- Given 记录中存在一条形状损坏的清单写入，Then 重放跳过该条并继续，不因单条坏记录整体失败

### US2.2 重启恢复清单（P0）

作为用户，重启应用或恢复历史会话后，清单原样回来。

验收：
- Given 清单有 3 项、其中 1 项 in_progress，When 重启进程并恢复该会话，Then 恢复完成时清单仍是那 3 项与各自状态
- Given 清单最后一次操作是清空，When 恢复，Then 清单为空（空也是有效状态，与"从未写过"可区分时须可区分）
- Given 恢复后的会话，When 消费端请求会话状态，Then 拿到的清单与恢复前一致

### US2.3 回退（undo）后清单跟着回（P1）

作为用户，撤销最近几轮对话后，清单回到那几轮之前的状态——清单是对话的伴生状态，不是独立轨道。

验收：
- Given 清单非空，When 撤销最近几轮对话（覆盖那次修改），Then 清单恢复为修改前的 A
- Given 撤销后消费端界面，Then 清单展示同步更新为回退后的版本，无需手动刷新
- Given 对话明细已被压缩折叠（无法再回到更早），When 撤销，Then 清单保持压缩时刻的状态（回退不到压缩之前）

### US2.4 恢复的幂等与归属（P1）

作为用户，恢复操作不产生额外副作用。

验收：
- Given 同一会话恢复两次，Then 第二次恢复后清单与第一次一致，不重复叠加
- Given 子代理曾在清单上写入，When 恢复，Then 写入按原顺序折叠进清单（清单归会话，不归单个代理）

## 3. Epic E3：清单与长上下文（Rust 缺口 G3/G7）

### US3.1 压缩后清单保留在摘要里（P1）

作为执行者，上下文被压缩、明细对话被折叠成摘要后，我仍然知道清单上有什么、每项什么状态——进度不随压缩蒸发。

验收：
- Given 清单非空，When 自动或手动压缩完成，Then 压缩摘要包含当前清单（含每项标题与状态）
- Given 清单为空或已被清空，When 压缩，Then 摘要不包含空清单段落（不制造噪音）
- Given 压缩后的下一轮，When 模型查询清单，Then 查询结果与摘要中保留的一致

### US3.2 压缩后网页面板不空（P1）

作为用户，压缩发生后网页端的清单面板仍显示清单——网页面板从对话记录推导清单，压缩不得让推导结果变空。

验收：
- Given 清单非空，When 压缩完成（清单写入的对话明细被折叠掉），Then 网页面板仍显示清单（面板不再只依赖被折叠掉的对话明细来推导清单）

## 4. Epic E4：过期提醒（Rust 缺口 G5/G6）

### US4.1 主代理也会被提醒（P0）

作为用户，主代理长任务中忘记更新清单时，引擎提醒它——不是只有子代理记得纪律。

验收：
- Given 主代理连续 10 个回合未更新清单（无带清单参数的写入），When 下一次回合开始，Then 模型收到一条过期提醒（含当前清单渲染），提醒它更新或清理清单
- Given 距上次提醒不足 10 个回合，Then 不重复提醒（同一代理提醒去重）
- Given 只有查询调用（不带清单参数），Then 查询不重置"距上次写入"的计数

### US4.2 提醒只在工具可用时有意义（P0）

作为配置者，禁用了清单工具的代理不应被提醒去用它。

验收：
- Given 当前代理不可用清单工具（角色模板或策略排除了它），Then 模型不会收到过期提醒
- Given 工具中途被禁用，When 下次计数达标，Then 模型同样不会收到过期提醒

### US4.3 提醒的可复制基线（P1）

作为维护者，提醒的触发阈值与文案在两个引擎间一致——同一会话在两引擎上不应产生不同的提醒节奏。

验收：
- Given 相同的对话历史与清单状态，Then 两引擎就是否送达过期提醒得出相同结论（阈值：距上次写入 ≥10 回合且距上次提醒 ≥10 回合）
- 提醒文案与清单渲染格式与 tool-calling 域契约（builtin-tools §4.4 输出契约、write-reminder 原文）一致，本域不另行定义

## 5. Epic E5：消费端水合（与 G1/G2 同源，验收面在消费端）

### US5.1 终端恢复后面板不空（P0）

作为用户，恢复会话后终端的清单面板显示恢复前的清单，而非清空。

验收：
- Given 恢复前清单非空，When 终端完成会话恢复渲染，Then 面板显示清单（顺序、状态一致）
- Given 恢复前清单为空或全为完成态，Then 面板按既有呈现规则隐藏（正常行为，非缺陷）

### US5.2 网页冷快照包含清单（P0）

作为用户，网页端打开一个不在线的会话（冷快照），清单仍在。

验收：
- Given 会话持久记录含清单写入，When 网页端读取冷快照，Then 快照中的清单 = 最后一次写入的结果
- Given 记录无任何清单写入，Then 快照清单为空

## 6. 非功能需求

- **写入开销**：清单写入的留痕为单条记录追加，不产生会话记录的全量重写；清单本身无数量上限（对齐 tool-calling 域裁决）
- **恢复开销**：恢复会话不因清单引入额外的全量扫描或明显等待
- **共享安全**：多代理并发读写清单在同一会话内不产生交错或撕裂版本

## SDR 决策记录

### SDR-001 清单定位为会话级持久状态，而非进程内临时变量（2026-10-22）

- **背景与动机**：两个引擎对"清单是什么"存在根本分歧——TS 把清单当作有持久记录、可恢复、可回退的会话级状态；Rust 把它当作进程内的共享内存变量。分歧的后果集中在恢复与长上下文链路：重启即丢、压缩即忘。用户对清单的预期是"进度的可信镜像"（见角色定义），该预期与实现方式无关，应作为需求定死。
- **决策**：清单的每次写入必须在会话持久记录上留痕（US2.1），恢复、回退、冷快照均从记录推导当前清单（US2.2/2.3/5.2），压缩摘要保留清单（US3.1）。
- **被否决的替代方案**：
  - **清单单独落文件（会话目录内独立 json）**：看似简单，实际引入第二份需要与对话记录保持一致的状态源——回退、子代理写入排序、损坏容忍都要自己重做一遍，且破坏"从会话记录推导一切"的消费端模型。
  - **维持现状（内存变量）+ 恢复时不恢复**：等于宣称清单是易失装饰品，与"任务进度追踪"的产品定位矛盾；每次重启后模型重新编造清单比不显示更糟。
- **影响范围**：E2、E3、E5 全部；architecture 侧决定记录载体（见 architecture ADR-1）。

### SDR-002 过期提醒必须覆盖主代理且受工具可用性门控（2026-10-22）

- **背景与动机**：提醒机制的意义在于"执行者忘了纪律时有人兜底"。现状 Rust 只在子代理路径送达过期提醒，主代理——恰恰是清单最主要的使用者——反而收不到提醒；同时提醒不检查工具是否可用，被禁用清单工具的代理也会被催促去用一个不存在的工具，形成无效应答。
- **决策**：主代理与子代理同等地接受过期提醒（US4.1）；过期提醒以清单工具在当前代理可用为前提（US4.2）。
- **被否决的替代方案**：
  - **只在主代理挂、子代理不挂**：子代理可写共享清单，忘更新同样造成进度失真；共享语义下提醒不应挑人。
  - **提醒无条件送达**：等于向被禁用工具的代理发送无法执行的指令，模型要么困惑要么虚构调用——可见信号必须与真实能力对称。
- **影响范围**：E4；提醒阈值与文案沿用 tool-calling 域既有契约，本域不新设。
