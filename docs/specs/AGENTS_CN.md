# docs/specs/ 文档治理约定

> 目的：设计与执行分离——规格文档只在**设计变更**时修改，不因**执行推进**而修改。

> 本文件为中文版；英文版见 [`AGENTS.md`](./AGENTS.md)，两者如有分歧以中文版为准。

## 文档类型

`docs/specs/` 下允许四类文档：

| 类型 | 内容 | 允许修改的触发 |
|---|---|---|
| **设计/规格**（`*-requirements.md`、`*-architecture.md`、`rust-core-design/0*.md`，及经登记的域内设计子类——当前 `tool-calling-builtin-tools.md`（逐工具接口规格）、`skills-builtin-skills.md`（逐内置技能需求规格）与 `file-reference-uiux.md`（文件引用能力的域内交互契约）） | **仅终态**：目标描述、契约、需求、架构裁决、Trade-offs、风险 | 只有设计本身变了（新增/修订裁决、需求变更，以 SDR/ADR 形式追加，见下文） |
| **参考**（`*-context.md`） | 现状与现状痛点的盘点（代码事实、两侧差异矩阵、侦察产出、差距速览） | 随侦察/现状变化更新；每份带快照日期 |
| **计划**（`*/plans/*.md`、`{domain}-ROADMAP.md`，域目录内的目录级 `ROADMAP.md` 等价；`proposals.md`——跨域未裁决提案的唯一登记处） | 迁移计划、阶段切分、开放项汇总、执行状态 | 随执行推进随时更新 |
| **共享术语**（`glossary.md`） | 横跨多个域的术语的唯一规范定义（规范名、形态与示例、出现位置、禁止的叫法、同名异义警示） | 随引入/修订该跨域术语的域 spec 变更**同批**更新（见下文「跨域术语」） |

## 设计文档的四条禁入

设计/规格文档中**不得出现**：

1. **执行状态元素**：已实现 / 未启动 / 进行中 / 已交付 / 待实施 / ✅ 等状态词；会漂移的基线数字（测试总数）；阶段进度标注
2. **现状盘点**：代码事实引用（文件:行号级别的"现在是什么"）、两侧实现差异矩阵、现状差距速览——这些属于 `*-context.md`
3. **迁移性表述**："对齐现状 / 已修订 / 替代原路线" 等过程叙述
4. **技术实现细节**：接口方法名与签名、实现机制、系统结构描述——这些属于 `*-architecture.md`

**需求文档的产品语言要求**：`*-requirements.md` 必须使用**非技术人员能读懂的产品语言**——描述用户想要什么、验收什么，不描述系统怎么实现。技术名词出现时须转译为产品语义（例如"乐观锁"表述为"并发编辑冲突检测"，"幂等对账"表述为"只补差异、无变化时零成本"）；接口的技术形状（方法名、参数、返回结构、机制）归 `*-architecture.md`，需求文档以一句话指向。判断法：把文档拿给产品经理，不需要工程师在场解释就能读懂并指出错漏，才算合格。

**动机 vs 现状的边界**：设计文档可以（也应该）保留**动机**——但必须是**抽象的问题陈述**（"同进程多 workspace 下，用户级 server 会被重复拉起 M 份子进程"），不携带代码事实（文件路径、行号、方法清单、数字）。判断法：动机陈述的是问题（会随终态达成而消失），现状盘点陈述的是事实（会随代码演进而漂移）。详细的现状依据在对应 `*-context.md`，设计文档以一句话指向。

## 参考文档（`*-context.md`）的规范

- 每域一份，与该域设计文档并列（`mcp-architecture.md` ⇄ `mcp-context.md`；`rust-core-design/` 域内统一一份 `context.md`）
- 头部带快照日期；内容按域分节
- 它不描述目标、不含裁决——那些在设计文档里
- 设计文档与其 context 的关系是单向引用（设计 → context），context 不裁决、不规划

## 状态的唯一去处

| 状态种类 | 唯一维护点 |
|---|---|
| 各域开放项与执行状态 | 该域的 ROADMAP：顶层域用 `{domain}-ROADMAP.md`（如 `mcp-ROADMAP.md`）；域目录内用目录级 `ROADMAP.md`（如 `rust-core-design/ROADMAP.md`，两者等价） |
| 各批次执行的 ledger | `.superpowers/sdd/<program>/progress.md`（gitignored） |
| 域的现状盘点 | `*-context.md`（带快照日期） |
| 代码现实（测试数、注册表行数） | 代码与 CI 本身 |

ROADMAP 与计划文件只做状态/进度管理，不得承载需求或设计内容；反过来，需求/设计文档不得承载任何进度信息。

## 跨域术语

有的术语比单个域大——"model" 同时出现在 config.toml、引擎、wire 契约、web/TUI、agent 工具里。这类术语在 `glossary.md` 中获得**唯一**规范定义：

1. **收录条件**（满足其一即应收录）：术语出现在两个及以上域的 spec 中；或出现在**共享面**（config.toml 键值、wire 契约字段、CLI / web / TUI 用户可见文案）。
2. **单一事实源**：域 spec 可保留该术语的域内视图（可裁剪、可补域内语境），但不得重新定义；两者冲突时以 `glossary.md` 为准。
3. **同批变更**：引入或修订跨域术语的 spec 变更，必须同批更新 `glossary.md`——不允许"先改 spec、术语表以后再说"。
4. **域内私有术语**留在所属域的 spec 里，不倒入 glossary（什么都收的术语表会漂移成过期垃圾场）。
5. **边界：仅限术语**。glossary 条目只含规范名、形态与示例、定义、出现面、禁止的叫法、同名异义警示；**不含代码、实现机制、裁决**——代码事实与域内语境归该域 spec / context，机制与约束归架构文档。glossary 里出现代码块、方法名、文件路径即为缺陷。

## 需求/设计变更记录（SDR / ADR）

需求或设计发生变更时，变更必须**写回对应的需求/设计文档本身**，以决策记录的形式追加，不允许只记录在 ROADMAP、计划文件、commit message 或对话里：

- **需求变更** → 追加到对应的 `*-requirements.md`，以 **SDR**（Specification Decision Record，需求决策记录）记录
- **设计变更** → 追加到对应的 `*-architecture.md` / 设计文档，以 **ADR**（Architecture Decision Record，架构决策记录）记录

每条 SDR/ADR 至少包含：

1. **编号与日期**（如 `SDR-001`、`ADR-003`）
2. **背景与动机**：抽象的问题陈述，不带代码事实（现状依据指向 `*-context.md`）
3. **决策**：变更后的终态要求
4. **被否决的备选方案**及取舍理由
5. **影响范围**：波及哪些需求/设计条目

历史记录**追加而不要改写**：被后续决策替代的条目标注 superseded 并指向新记录，正文条目同步更新为终态。

## 需求定义的评审检查清单

撰写或评审任何需求文档（`*-requirements.md`）时逐条自检，任一判定问题答"否/不确定"即为缺陷，修完再提交（规则来源：2026-09-08 MCP 设置页需求评审确立的检查观点）：

| # | 规则 | 判定问题 |
|---|---|---|
| R1 终点消费方 | 变更类需求必须写到真实消费方为止——执行中的任务、调用管线、界面；验收主体是消费方，不是中间层（连接、配置面） | 这条变更写完之后，**谁**在**什么时刻**感知到？"可用面/连接已更新"这类中间层表述不合格 |
| R2 可见性 ≠ 强制 | 安全/权限类需求必须定义硬强制点（调用校验环节、先于连接建立/复用），拦截与放行**对称**定义 | 绕过清单直接调用会被拦吗？强制点在管线哪个环节？解除后的放行也定义了吗？ |
| R3 具体性 | UI/交互类需求的验收必须逐项映射到具体行为 | 能画出"什么变了 → 界面怎么变"的对照表吗？更新原则（谁触发/以谁为准/无变化零动作）写了吗？"实时刷新""即时更新"单独出现即不合格 |
| R4 信号真实性 | 每个用户可感知的信号（按钮、日志、提示）必须与真实效果一致 | 它声称发生的事真的发生了吗？单目标操作产生了全局性/误导性信号吗？ |
| R5 可用性诚实 | 交付面上不允许"存在但无效"的功能 | 每个 UI 入口背后的后端能力完整吗？要么完整可用，要么这个入口不存在——"点了就报错"的占位控件是缺陷不是降级 |
| R6 先分析后裁决 | 面向"删掉/简化"的提案必须先给客观分析 | 五问答全了吗——现状机制是什么？哪些环节会出异常？有哪些外部参与者？自动机制覆盖到哪？需不需要手动逃生门？答不全不得提案删减 |
| R7 先例穷尽 | 向用户提问决策前，先查尽既有事实 | 既有实现的行为查了吗？既有规格文档读了吗？问题是否携带事实依据，而不是把"没查"外包给用户的选项？ |
| R8 语言分层 | 需求文档与决策提问按受众分语言；技术细节归架构文档 | 产品经理不需要工程师在场能读懂吗？决策问题里有未转译的技术词吗？ |
| R9 显式记录 | 需求必须显式记录为可验收的一等条目 | 藏在其它条目措辞里的隐含语义不算记录——散落的间接表述要收敛为显式条目 |

R1–R3 合起来是完备性检查：一条变更类需求的触达面要覆盖**运行时任务（R1）→ 调用强制（R2）→ 界面呈现（R3）**三个消费方，且双向（出现/移除、启用/禁用）对称定义。

**验收句式**：验收标准与 Given-When-Then 型条件一律用中文语序书写——「**假如**…、**当**…，**那么**…」——禁止在中文句子里内嵌 `Given/When/Then` 英文标记（中英混排难读；2026-10-28 确立，provider-credential 评审）。英文词 "Given-When-Then" 仅允许在指名该格式本身时出现。

## 修改设计文档时的检查

提交设计文档变更前自问：

1. 这段话六个月后还成立吗？（不成立 → 状态或现状元素，移走或删除）
2. 这是"要达到什么"还是"现在是什么"？（现在是什么 → 移 `*-context.md`）
3. 如果是动机：能否去掉文件路径/行号/数字，只留问题本身？（能 → 抽象后保留）
4. 这次改动是需求/设计变更吗？（是 → 在本文档追加对应的 SDR/ADR，而不是只写进 ROADMAP 或 commit message）
5. 文档中每个标识符类术语是否唯一可归位？（否 → 提交前修正表述或补消歧说明。检验标准：两个读者是否可能把同一个词映射到两个不同的值——例如把"别名 id"读成完整 `provider/model` 字符串、或读成斜杠右侧的原始模型名；或把显示名误当成可传入参数的合法值。若有此风险，须在术语表中给出规范名 + 具体形态示例，正文禁用自造同义词，并显式标注同形异义冲突——尤其是 wire 字段、RPC 参数、config 键复用同一个词的情况。若该术语横跨多个域，其规范定义的唯一去处是 `glossary.md`，同批注册/核对）
