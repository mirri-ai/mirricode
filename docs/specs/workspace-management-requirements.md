# 工作区管理 — 需求文档

> 状态：v1 基线 · 2026-09-11 · 记录 TS v2 引擎现网工作区能力作为 Rust Core 对齐基线（基线是 Rust 要达到的底线，不是上限）；本域产品语义裁决 SDR-001~007 已定（见 §决策记录）· 待用户评审 ·
> 本文是工作区管理域需求侧的唯一事实源（内部规格文档，不进文档站构建，中文单语）。
> 配套文档：技术形状见 [workspace-management-architecture.md](workspace-management-architecture.md)；现状盘点见 [workspace-management-context.md](workspace-management-context.md)；执行状态见 [workspace-management-ROADMAP.md](workspace-management-ROADMAP.md) 与 [rust-core-design/ROADMAP.md](rust-core-design/ROADMAP.md) 1.8。
> 术语规范：工作区（W1）、工作区注册表（W3）、工作区信任（W4）、别名集（W5）、工作区桶（S3）、会话索引（S4）的唯一定义见 [glossary.md](glossary.md)。
> **范围边界**：本域覆盖工作区的**生命周期**（注册/列出/重命名/移除/信任）、**身份与跨引擎共享**、**多工作区并发模型**、**会话与工作区的归属**、**工作区范围的配置加载门**。不覆盖：工作区/会话的**排序与置顶**（见会话管理域 E2/E3）、会话**持久化机制**（见会话持久化域）、MCP **三池架构**（见 MCP 域，本域只定义信任门对项目层配置的开关语义）、文件沙箱与执行环境（见执行环境域）。
> **标记约定**：〔TS 基线〕= TS v2 现网已支持；〔设计增强〕= 超出 TS 现网的设计（不因 TS 没有而削弱）；〔提案〕= 尚不存在任何实现的建议。

## 0. 角色定义

| 角色 | 场景 | 核心诉求 |
|---|---|---|
| **多项目开发者** | 同时在几个项目里干活 | 一个界面管全部项目，切换零成本，各项目互不串扰 |
| **整理者** | 收拾侧边栏的用户 | 添加/重命名/移除工作区要直觉、可预期、误操作可恢复 |
| **跨引擎用户** | 网页 + 终端混用、新旧引擎过渡期 | 两边认同一套工作区，谁注册的都互见，删除不被复活 |
| **安全敏感用户** | 经常打开来源不明的仓库 | 陌生项目的配置（尤其是能起进程的配置）默认不生效 |

## 1. Epic E1：工作区注册与身份〔TS 基线〕

> 一个项目目录成为工作区的方式：显式添加，或创建会话时隐式注册。身份一旦确立跨引擎不变。

### US1.1 显式添加工作区（P0）

作为整理者，我想通过文件夹选择器把一个项目目录添加为工作区，以便它的会话在我这里集中呈现。

验收：
- Given 添加对话框打开，When 我浏览目录树（逐级进入、返回上级、面包屑跳转），Then 只显示目录（文件不可选），点选即定位
- Given 对话框的输入框，When 我输入绝对路径（含 `~` 展开、Windows 盘符/UNC 形态），Then 实时给出校验状态（有效 / 路径不存在且父目录下有近似候选 / 上级目录不存在）
- Given 对话框打开，When 确定起始目录，Then 从当前工作区根（或会话工作目录）开始浏览，无则从系统主目录开始
- Given 路径不存在时按回车，When 父目录有近似候选，Then 选中首个候选；连按两次 Esc，Then 先清空输入框、再关闭对话框
- Given 对话框的输入框，When 我输入当前目录下的子目录名片段，Then 触发有界模糊搜索并列出候选（无全局失控扫描）
- Given 我点选/输入的路径不存在或不是目录，When 提交，Then 添加被拒绝，错误在对话框内联显示（不是全局报错弹窗）
- Given 目录浏览服务不可用，When 对话框仍可用，Then 我可以退化为直接输入绝对路径完成添加（可用性诚实：降级路径存在且可用）
- Given 添加成功，When 对话框关闭，Then 新工作区出现在列表中，主界面进入该工作区的新会话草稿（发第一条消息才真正建会话）
- Given 待发送的输入因无工作区被暂存，When 添加成功，Then 暂存内容自动发送到新工作区

### US1.2 隐式注册（P0）

作为多项目开发者，我想直接指定一个目录发消息而不用先"添加工作区"，以便没有仪式感地开始干活。

验收：
- Given 一个未注册的目录，When 我在该目录下创建会话，Then 该目录被自动注册为工作区（会话归属它，列表中出现）
- Given 创建会话时显式指定了工作区，When 目录与该工作区不符，Then 请求被拒绝（不允许"注册的是 A、会话却落在 B"的错位）

### US1.3 重复添加幂等（P0）

作为整理者，我想重复添加同一目录时什么都不坏，以便手滑无害。

验收：
- Given 工作区已存在，When 我再次添加同一路径，Then 不产生第二条记录；其"最近使用"时间被刷新（触摸语义），名称与既有设置保留
- Given 添加时提供了自定义名称，When 该路径已注册，Then 名称不覆盖（已有名称优先）

### US1.4 身份跨引擎共享（P0）

作为跨引擎用户，我想新旧引擎认同一套工作区身份，以便过渡期两边列表一致、会话不串档。

验收：
- Given 新引擎注册了工作区，When 旧引擎查看列表，Then 该工作区可见（同一份磁盘名单）
- Given 一边删除了工作区，When 另一边刷新，Then 不复活（删除标记跨引擎生效）
- Given 同一目录在两边先后注册，Then 身份相同（编号由路径确定性派生，不因注册方不同而分叉）

### US1.5 别名集折叠（P0）

作为跨引擎用户，我想历史上因路径拼写差异被拆成多条的同一项目被当作一个工作区，以便列表不出现重复。

验收：
- Given 一个工作区历史上存在多个编号拼写（大小写 / 斜杠方向 / 尾斜杠差异），When 我按工作区过滤会话列表，Then 全部拼写桶的会话一起返回（视为一个工作区）
- Given 同上，When 我查看该工作区的会话计数，Then 计数折叠全部拼写桶
- Given 同上，When 我手动刷新该工作区，Then 每个拼写桶都被重新收敛

### US1.6 会话列表按工作区过滤（P0）

作为多项目开发者，我想按工作区拉取会话列表，以便侧边栏分组与分页加载。

验收：
- Given 指定工作区的会话列表请求，When 返回，Then 只含该工作区（含其别名集）的会话，按更新时间倒序，支持游标分页（向前/向后）
- Given 会话从未发过消息（空会话），When 界面默认视图，Then 空会话被排除（契约层为显式排除参数，网页端恒携带）

## 2. Epic E2：展示与信息〔TS 基线〕

### US2.1 工作区信息展示（P0）

作为浏览用户，我想每个工作区分组显示足够辨识的信息，以便不用猜哪个是哪个。

验收（按界面分别核验）：
- Given 桌面侧边栏分组标题，When 渲染，Then 显示文件夹图标与名称（默认为目录名）；**不显示**会话数、分支、路径（桌面标题保持极简——会话数经分组"加载更多 N"计数可见）
- Given 移动端切换面板，Then 每分组副行显示 git 分支（无分支时显示 `~/…` 短路径形态）
- Given 移动端顶栏，Then 显示工作区/会话路径与运行状态行（运行中标记、分支、会话数）
- Given 工作区从会话目录派生（从未显式注册），When 显示，Then 名称取目录名，同样成组（派生工作区与注册工作区同等展示）
- Given 会话很多，When 分组内分页，Then 有"加载更多/显示全部"入口与加载中状态

### US2.2 重命名（P0）

作为整理者，我想给工作区改显示名，以便按我的叫法找项目。

验收：
- Given 重命名入口（菜单或右键），When 进入内联编辑，Then 原名预填、自动聚焦
- Given 编辑中，When 按 Enter，Then 提交；按 Esc 或失焦，Then 取消不提交（输入法组词期间的 Enter 不误提交）
- Given 提交了空白名，Then 静默不生效（不报错不落库）
- Given 服务端重命名失败且该工作区是派生的，When 回退，Then 本地名称覆盖生效（下次加载仍用我的名字）
- Given 重命名只改显示名，Then 路径、身份、会话归属一律不动

### US2.3 折叠与空状态（P2）

验收：
- Given 分组标题点击，When 展开/折叠，Then 桌面端状态本地记忆（刷新保持）；移动端切换面板的折叠每次打开重置（不记忆）；折叠不影响排序、不锁拖动（排序归会话管理域）
- Given 分区标题的全收/全展开关，When 点击，Then 一键收起/展开全部分组
- Given 没有任何工作区，When 查看侧边栏，Then 显示"无工作区"空态；居中撰写区的添加入口可达
- Given 已有工作区的桌面端，Then 侧边栏的独立"添加工作区"按钮当前被隐藏（入口评估中）——桌面添加入口存在于新会话撰写区的选择器内（见 US2.5），零工作时空态另有居中添加按钮
- Given 工作区没有会话，When 打开它，Then 显示该工作区下的居中撰写草稿

### US2.5 新会话的工作区选择器（P0）

作为多项目开发者，我想在开始一段新对话时选择它落在哪个工作区，以便不必先去侧边栏操作。

验收：
- Given 新会话的居中撰写区，When 工作区数 ≥ 1，Then 显示当前工作区名与下拉入口；下拉列出可见工作区（名称 + 短路径，超量折叠进"更多"展开）
- Given 我在下拉中选择另一工作区，When 未开始输入，Then 新对话的目标工作区切换（当前已是该工作区则不动作）
- Given 下拉底部，Then 提供"添加工作区"入口（与添加对话框同一流程）
- Given 已移除（隐藏）的工作区，Then 不出现在选择器

### US2.4 移动端（P1）

验收：
- Given 移动端切换面板，Then 可用动作：切换工作区、新建会话、新建工作区、复制路径、移除（确认框）；不可用（桌面专属）：手动刷新、拖拽排序、内联重命名（以系统输入框替代）
- Given 移动端顶栏，Then 显示工作区/会话路径与运行状态行（运行中标记、分支、会话数）

## 3. Epic E3：移除工作区

> TS 现网的移除是"列表层面消失、数据全部保留"；本域裁决在此基础上增强为三选一。

### US3.1 从列表移除（P0）〔TS 基线〕

作为整理者，我想把不想要的工作区从列表移除，以便列表只留活跃项目。

验收：
- Given 移除入口（菜单/右键/移动端），When 触发，Then 出现确认框；确认后分组从列表消失
- Given 移除完成，Then 本浏览器记忆该隐藏（该工作区不再因历史会话被重新派生显示），且服务端名单同步移除（尽力而为，失败不阻塞界面移除）
- Given 移除的是当前活跃工作区，When 界面回落，Then 切到剩余列表的第一个工作区（无剩余则清空到空态）
- Given 移除后其他设备/引擎同步，When 收到工作区删除事件，Then 本地同样隐藏——事件消费端已就绪，但**现网 v2 后端不发射该事件**（仅旧引擎发射），即多客户端移除同步在 v2 后端下实际不生效（Rust 补齐发射面已裁决随 plans/08 W2 落地，2026-09-11）
- Given 我重新添加同一路径，When 成功，Then 工作区回归且历史会话可见（移除不删数据）

### US3.2 删除时按意图三选一〔设计增强 · SDR-001〕（P0）

作为整理者，我想在删除时明确选择力度，以便清理磁盘时敢删、误删时能救。

验收：
- Given 删除入口触发，When 确认框出现，Then 提供三个动作：**物理删除**（该工作区全部会话数据从磁盘清除，不可恢复）/ **仅从列表移除**（数据保留，同 US3.1）/ **取消**
- Given 确认框文案，Then 明示三种后果的差异；物理删除为**主推项**（用户已确认删除意图时鼓励彻底清理，缓解存量会话占满磁盘）
- Given 物理删除执行，When 完成，Then 该工作区的会话目录与会话索引条目被清除，跨引擎删除标记生效（其他引擎不复活）
- Given 物理删除执行时该工作区有进行中的会话，Then 先干净收尾再删除（不留半截状态）

## 4. Epic E4：工作区信任

> TS 现网：后端具备信任机制（默认不信任、信任仅控制项目层 MCP 配置加载），**网页端没有任何信任入口**——用户不可达（可用性诚实缺口）。本域裁决补齐入口并扩大门控范围。

### US4.1 项目配置的门控语义（P0）〔TS 基线〕

作为安全敏感用户，我想新注册工作区里的项目级配置默认不生效，以便打开陌生仓库不等于自动执行别人写的进程定义。

验收：
- Given 新注册的工作区，When 未信任时，Then 其项目层 MCP 配置（团队共享层 + 本机项目层）**不加载、不连接**；用户全局层与插件层不受影响
- Given 我信任该工作区，When 信任生效，Then 项目层配置加载；信任状态持久（重开保持）
- Given 我撤销信任，When 撤销生效，Then 项目层连接即刻断开、配置不再加载（无需重启；门控对称：开与关双向定义）
- Given 信任变化发生在另一个进程，When 本进程查看，Then 需重启才感知（现网信任变化的生效边界是同进程热重载——跨客户端即时同步见 §10 提案）

### US4.2 信任入口可达〔设计增强 · SDR-002〕（P0）

验收：
- Given 我在网页端注册/使用一个未信任的工作区，Then 存在明确的"信任此工作区"操作入口（TS 现网无任何网页入口，此为补齐）
- Given 我在界面选择一个未信任的新工作区（新会话选择器或侧边栏切换），When 选中，Then 出现信任确认——两个动作："信任此工作区" / "暂不"〔设计增强 · SDR-007：选中即用、用前确认，不在注册动作上打断〕
- Given 选择"暂不"，Then 工作区正常可用，但项目层配置不生效且界面如实呈现（US4.1）
- Given 未信任的工作区，Then 界面诚实呈现其项目配置未生效的状态（不存在"以为生效其实没生效"的暗坑）

### US4.3 信任门控范围扩大〔设计增强 · SDR-002〕（P1）

验收：
- Given 未信任的工作区，When 会话运行，Then 其项目说明文件（AGENTS.md 项目段）**不注入**对话背景〔超出 TS 现网——TS 只门控 MCP 配置，此为 rust 侧加固〕
- Given 信任后，Then 项目说明注入恢复

## 5. Epic E5：多工作区并发模型〔TS 基线〕

> 一个服务进程同时承载全部注册工作区——TS v2 形态，Rust 对齐。

### US5.1 多项目同进程（P0）

验收：
- Given 一个进程，When 注册了 N 个工作区，Then 全部同时可用（会话、配置、切换即时）
- Given 任一工作区的会话操作（发消息/订阅/审批/恢复），When 在非默认工作区上执行，Then 与默认工作区行为完全一致（无"二等公民"）

### US5.2 注册数量不拖慢启动（P0）

验收：
- Given 注册了很多工作区，When 进程启动，Then 只完整加载默认工作区（最近使用的），其余首次触达才加载——启动耗时与注册数量无关

### US5.3 嵌入式宿主钉扎（P1）〔设计增强 · SDR-006〕

验收：
- Given 编辑器插件/桌面内嵌这类为单一项目启动的宿主，When 共享名单里有其他工作区，Then 它仍只以协商目录为默认工作区；其余不加载、不进默认可见列表（不因共享名单而串项目）——TS 现网的嵌入式宿主运行在旧引擎栈上，无 v2 钉扎实现，此为 Rust 侧目标语义

## 6. Epic E6：跨引擎并存〔TS 基线 + SDR-005〕

### US6.1 并发写防护（P0）

作为跨引擎用户，我想两边同时改名单不互相覆盖，以便注册不丢。

验收：
- Given 新引擎与旧引擎同时修改名单，When 各自保存，Then 任何一边读时已见的注册不因另一边写入而丢失；删除不被复活（技术保证手段见架构文档 §3 并发边界）
- Given 旧引擎（无锁整写形态）与新引擎几乎同时写，When 旧引擎后写，Then 极小概率覆盖新引擎刚写入的条目——此残余窗口**已声明**（补救：重新添加即恢复，数据无损；旧引擎退役后自然消失）

## 7. Epic E7：手动刷新（P1）〔TS 基线〕

### US7.1 重扫磁盘

验收：
- Given 我怀疑外部写入（别的工具/旧引擎）改了会话目录，When 点刷新，Then 服务端重扫该工作区（含全部别名桶）的磁盘会话并入索引，界面重新拉取（列表与会话数刷新）
- Given 刷新进行中，Then 该工作区的刷新按钮进入加载态且防重复点击；失败则提示，旧数据不动
- Given 移动端，Then 无刷新入口（桌面专属）

## 8. 非功能需求

| # | 需求 |
|---|---|
| N1 | 列表/计数读取走会话索引读模型，不逐会话解析磁盘文件（响应时间不随会话总数线性恶化） |
| N2 | 注册表读写原子（写坏不丢全量：写入失败不得损坏既有名单） |
| N3 | 工作区数量级：至少百级注册无功能退化（惰性加载保证） |
| N4 | 会话索引可丢弃重建（重建后工作区身份、计数不变） |

## 9. 决策记录（SDR）

### SDR-001 删除工作区为三选一（物理删除 / 仅移除 / 取消），确认场景鼓励清理
- **编号与日期**：SDR-001 · 2026-09-11（用户裁决）
- **背景与动机**：TS 现网移除一律保留磁盘数据；存量会话占满磁盘是真实风险，用户确定删除的场景应能真正清理（产品性能受益）。
- **决策**：删除确认框三动作——物理删除（不可恢复，清除会话目录与索引条目）/ 仅移除（TS 基线语义，数据保留）/ 取消；物理删除为主推项。
- **否决的替代**：一律物理删除（误删不可逆）；一律保留（无视磁盘风险）；有进行中会话则拒绝删除（把清理成本转嫁用户）。
- **影响面**：US3.2；契约需携带模式参数（技术形状见架构文档）。

### SDR-002 信任门补齐入口并扩大范围（默认不信任维持 TS）
- **编号与日期**：SDR-002 · 2026-09-11（用户裁决 D6）
- **背景与动机**：TS 后端信任机制完备但网页无入口（用户不可达，可用性诚实缺口）；且 TS 只门控 MCP 配置，项目说明注入未门控（陌生仓库的说明文字直接进入对话背景）。
- **决策**：默认不信任（TS 一致）；补齐网页信任入口；门控范围扩大到项目说明注入（超出 TS 的加固）。
- **影响面**：US4.2、US4.3。

### SDR-003 别名集折叠纳入首期（不缓办）
- **编号与日期**：SDR-003 · 2026-09-11（用户裁决 D3，否决"后续再补"分期建议）
- **影响面**：US1.5；与会话持久化域开放项 #6 对齐（同一事项）。

### SDR-007 信任入口形态：选中未信任新工作区时确认
- **编号与日期**：SDR-007 · 2026-09-11（用户裁决，细化 SDR-002 的入口落点）
- **背景与动机**：注册动作发生在添加对话框，此时用户尚未使用该工作区，注册即弹信任确认会打断"添加"主流程，且用户对陌生仓库尚无使用意图与判断依据；选择动作意味着"我要用它了"，是信任决策的自然时机。
- **决策**：信任确认的触发点是**用户在界面选择一个未信任的新工作区**（新会话选择器或侧边栏切换）时；两动作——"信任此工作区" / "暂不"；暂不则工作区正常可用，项目层配置不生效且界面诚实呈现（US4.1）。
- **影响面**：US4.2；rust 落地见 plans/08 W8。

> 技术形态裁决（管理结构、路由结构、写并发机制等）见 [rust-core-design/08-multi-workspace.md](rust-core-design/08-multi-workspace.md) ADR D1-D8，需求侧不重复。
