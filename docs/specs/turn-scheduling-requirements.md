# 回合调度与循环控制 — 需求文档（User Stories）

> 状态：v1 基线 · 2026-09-13 · 待用户评审 ·
> 本文是回合调度域需求侧的唯一事实源（内部规格文档，不进文档站构建，中文单语）。
> 本文件记录 TS 引擎已支持的能力作为 Rust 对齐基线——是 Rust 要匹配的地板，不是天花板。
> 配套文档：技术形状见 [turn-scheduling-architecture.md](turn-scheduling-architecture.md)；现状盘点见 [turn-scheduling-context.md](turn-scheduling-context.md)。
> 术语规范：回合（S7）、异步唤醒源（L1）、准入策略（L2）、回合结局（L3）的唯一定义见 [glossary.md](glossary.md)；本文件只使用规范叫法。
> 范围边界：本域管**引擎如何驱动回合**——回合生命周期、准入调度、插话合并、异步唤醒源的统一接入契约。目标（goal）的产品语义见 [goal-requirements.md](goal-requirements.md)；任务/定时的业务语义见 [subagent-requirements.md](subagent-requirements.md)；回合内容的界面呈现归对话渲染域。

## 0. 角色定义

| 角色 | 场景 | 核心诉求 |
|---|---|---|
| **执行者**（在回合里干活的模型） | 在回合中工作、被插话、被合并注入 | 我在干活时来的新消息能并入我正在做的请求，不丢失、不打断 |
| **用户**（发起与干预的人） | 发消息、插话、取消 | 我随时能插话且插话立刻被消化；我取消能真停 |
| **异步源集成方**（任务通知/定时触发/目标续航/未来的异步能力） | 把"晚到的消息"送进对话 | 我不需要懂调度内部，接入时有一个统一插座：忙则并入、闲则自起 |
| **配置者** | 调整步数上限等 | 默认合理、可配、生效可预期 |

## 1. Epic E1：回合生命周期与唯一活动回合

> 解决"回合是什么、同时能有几个、怎么收尾"。回合是引擎的最小调度单位——一切消息最终都要变成某个回合里的工作。

### US1.1 单活动回合（P0）

作为用户/集成方，同一代理同一时刻只有一个回合在跑，新回合请求排队等待。

验收：
- Given 某代理已有运行中的回合，When 新回合请求到达，Then 新回合进入排队（先来先跑），不出现两个回合并发执行
- Given 运行中的回合结束，When 队列非空，Then 按排队顺序启动下一个回合
- Given 排队中的回合在启动前被取消，Then 它不启动、以"已取消"定局

### US1.2 回合结局如实（P0）

作为用户/集成方，回合的结局必须与真实情况一致。

验收：
- Given 回合正常完成（工作队列耗尽），Then 结局为"已完成"
- Given 回合因错误终止，Then 结局为"失败"并携带错误信息
- Given 回合被用户取消，Then 结局为"已取消"
- Given 回合被系统判定无进展而终止（如僵死保护），Then 结局为"已停滞"（系统判定无进展且回合协作收场的情形；不协作的硬丢弃按引擎故障记"失败"）且携带归因（见 US5.4）
- Given 回合因单回合步数上限终止，Then 结局为"失败"且原因明确标为"步数上限"（可被目标续航等消费方识别为非异常）

### US1.3 结束事件的有序性（P0）

作为集成方（订阅回合结束事件的程序方），回合结束时所有关注方先于下一回合启动处理完毕。

验收：
- Given 回合结束，When 结束事件发布，Then 全部订阅方（目标续航、生命周期钩子、活动视图等）处理完毕后，下一个排队回合才启动

### US1.4 模型空手而归的回合如实（P0）

作为用户，当模型一步工作结束却什么都没产出（没有回答、没有思考、也没有调用任何工具）时，我不能接受界面告诉我"本轮已完成"。

验收：
- Given 模型的回应完全为空（无正文、无思考、无工具调用）且回合并非因取消、中止或内容过滤收场，When 引擎判定回合结局，Then 该回合不得记为"已完成"——无论模型以哪种停止形态收场（正常结束、未知原因、输出截断、暂停，凡对用户呈现为"已完成"的形态均属本条范畴）
- Given 上述空回应出现且仍在既有重试额度内，When 引擎处理该步，Then 自动重试该步，重试成功后对话正常继续，用户无需干预
- Given 重试额度耗尽后回应仍为空，Then 回合以"失败"定局，并在对话中留下一条可见标记，明确告知"模型返回了空回应"、可重新发起
- Given 回合因用户取消或系统中止而未产出任何内容，Then 按取消/中止的既有结局收尾，不触发本条的自动重试
- Given 判定条件本身，Then 只依据该步的结构化产出（正文/思考/工具调用三者是否全空），不引入"任务是否完成"之类引擎无法观测的语义

## 2. Epic E2：准入策略

> 解决"一个新来的请求怎么进入回合"。准入是本域的核心词汇：四类准入覆盖了引擎里所有"消息变工作"的路径，任何异步源都不得发明第五类。

### US2.1 立即开新回合（P0）

作为用户/集成方，需要独占一个新回合的请求（用户消息、重试、目标续航提示）立即开新回合。

验收：
- Given 标记为"立即开新回合"的请求到达，Then 无论是否有活动回合，都创建新回合进入排队

### US2.2 忙则折入、闲则自起（P0）

作为异步源集成方，我把晚到的消息交给引擎时不需要判断当前忙闲。

验收：
- Given 有运行中的回合，When 此类请求到达，Then 并入该回合的下一次模型请求（不额外开回合、不额外消耗一次调用）
- Given 无运行中的回合，When 此类请求到达，Then 自行开启新回合消化该消息
- Given 多条此类消息在忙时先后到达，Then 全部并入、内容不丢失

### US2.3 等待下一回合（P1）

作为集成方，某些请求只应在"已有回合"的语境里出现；没有活动回合时暂存，等下一个回合创建时一并带入。

验收：
- Given 无活动回合，When 此类请求到达，Then 暂存；下一个回合创建时被收编
- Given 有活动回合，When 此类请求到达，Then 并入该回合

### US2.4 仅活动回合（P1）

作为集成方，某些请求只对运行中的回合有意义。

验收：
- Given 无活动回合，When 此类请求到达，Then 报错（不静默丢失、不自行开回合）

### US2.5 同批合并（P0）

作为引擎使用者，多条可合并的请求折进同一次模型调用。

验收：
- Given 一个回合的队列里有一条主请求与若干可合并请求，When 取下一批工作，Then 它们合并为一次模型请求，各自内容全部在场

## 3. Epic E3：插话（steer）

> 解决"用户在回合运行中说话怎么办"。插话是用户优先权的直接体现。

### US3.1 运行中插话并入下一步（P0）

作为用户，我在回合运行中发的消息会在下一步被消化，与当时的工作合并在同一次模型请求里。

验收：
- Given 回合运行中，When 用户插话，Then 该消息并入当前回合的下一次模型请求（不排队到回合结束、不另开回合）
- Given 多条插话先后到达，Then 依次全部并入

### US3.2 跨回合存活（P1）

作为用户，我回合结束前发出的插话不会因回合结束而丢失（以回合正常完成为前提）。

验收：
- Given 回合正常完成（工作队列耗尽），Then 队列内插话已在同批请求中消化（与 US3.1 同律，不因回合边界额外损耗）
- Given 回合异常终止（步数上限/失败/取消/钩子停止）时尚有未消化的插话，Then 该插话随回合一并终止，不静默带入后续回合
- Given 本条承诺与真实行为的一致性，Then 以 [turn-scheduling-context.md](turn-scheduling-context.md) §1.6 的现状缺口标注为准——承诺与实现不一致即为缺陷（见 ROADMAP O6）

### US3.3 可撤销（P2）

作为集成方，已入队的请求可以在被消化前撤销。

验收：
- Given 请求已入队但未被消化，When 撤销，Then 该请求不再出现；若撤销的是整个排队回合的发起请求，则该回合一并取消

## 4. Epic E4：统一异步唤醒源契约

> 解决"任何'非阻塞发起 + 消息通知'的能力如何接入对话"。这是本域对外的核心承诺：**单一插座**——任务通知、定时触发、目标续航、以及未来的异步能力（异步工具调用、外部事件等）都走同一准入路径、同一来源标识规范，不各自发明调度。

### US4.1 单一插座（P0）

作为异步源集成方，接入对话不需要理解调度内部。

验收：
- Given 任何异步源产生"要送达模型的消息"，When 接入，Then 通过统一入口走既有准入类别（见 E2），不新增调度路径
- Given 新的异步能力（如外部事件）加入引擎，When 接入，Then 遵守同一契约（准入类别、来源标识、合并规则），而不是旁路自造

### US4.2 来源可辨识（P0）

作为执行者（模型），我能分辨每条注入消息来自哪里、是什么性质。

验收：
- Given 任一注入消息，When 查看，Then 携带结构化来源标识（用户/任务/定时/目标/注入/重试/压缩摘要等），同一来源家族有统一格式

### US4.3 不打断进行中回合（P0）

作为用户，异步通知不会粗暴打断我正在进行的回合。

验收：
- Given 回合运行中异步通知到达，When 投递，Then 折入该回合下一步（与插话同律），不开新回合、不中断当前工作

### US4.4 挂起联动（P0，与目标域协同）

作为用户，自治目标挂起等待后台结果时，任务通知就是唤醒源。

验收：
- Given 自治目标处于等待挂起（见 [goal-requirements.md](goal-requirements.md) E5），When 任一异步唤醒源送达消息，Then 该消息经"闲则自起"开启新回合，唤醒即消化
- Given 目标处于挂起，When 观察，Then 不产生任何新的续航提示（该类回合驱动源暂停发放）
- Given 挂起期间唤醒消息到达，When 投递，Then 经既有准入自行开启新回合消化（一次唤醒一个回合，不双开）

### US4.5 静默期（排他窗口）（P1）

作为集成方，撤销等排他操作期间新请求被扣住而不是被拒绝或错投。

验收：
- Given 排他窗口（如对话撤销）进行中，When 新请求到达，Then 被扣住；窗口结束后按原顺序放行

## 5. Epic E5：取消与中断

### US5.1 取消活动回合即时生效（P0）

作为用户，我取消运行中的回合会立即、真实地生效。

验收：
- Given 回合运行中，When 取消，Then 执行停止（不再产生新的模型调用与工具执行），结局为"已取消"并携带取消原因（用户取消/中止）

### US5.2 排队回合可取消（P1）

作为用户/集成方，排队中的回合可在启动前取消。

验收：
- Given 回合在排队中，When 取消，Then 不启动、以"已取消"定局，其携带的未消化请求一并终止

### US5.3 阻塞等待的取消即时生效（P0）

作为用户，我取消一个正在等待任务结果的回合时，等待立即让路、回合干净收场。

验收：
- Given 回合正在阻塞等待某任务结果，When 回合被取消，Then 等待即刻中断、回合以"已取消"定局——不出现"已取消却继续等待数分钟"的僵尸期
- Given 等待被取消中断，Then 该任务已产出的结果不丢失，恢复会话后仍可继续消费

### US5.4 系统性终止必带可见原因（P0）

作为用户，任何不是由我发起的回合终止，我都能在界面上看到一句话原因。

验收：
- Given 回合因引擎判定无进展而被系统终止且回合协作收场，Then 结局为"已停滞"（与用户发起的"已取消"是两个词；不协作被硬丢弃的回合按引擎故障记"失败"），界面上悬停可见一句话归因（如"引擎在等待任务时长时间无进展，已自动停止"）
- Given 任一系统性终止发生，Then 服务端日志同期留有可检索的告警记录——不允许"静默终止、零日志"

### US5.5 健康等待不得被判为僵死（P1）

作为用户，代理等待一个仍在正常推进的对象（任务、子代理、工具或用户决策）时，回合不会被误判终止。

验收：
- Given 回合阻塞等待某对象、且该对象仍在正常推进（引擎向对象侧查询到的活体事实为"推进中"），Then 引擎不得将回合判为僵死
- Given 等待对象真正失去推进（真僵死——对象侧查询报"停滞"），Then 兜底终止仍生效——资源保护不因本条削弱
- Given 回合在等一个引擎未识别的等待对象（未登记等待类别），Then 该回合在兜底窗口（不得短于历史静默窗口）后才被终止——漏接线的代价是延迟兜底，不是一个静默窗口内的误杀

### US5.6 等待用户决策的时长是无限的（P0）

作为用户，代理向我提问或请求批准时，我会在我方便的时候回应——无论多久，等待都不会中断；我的回应到达时代理一定还在等我。

覆盖范围：所有"引擎向用户发出的提问与批准请求"——代理的结构化提问、工具执行的权限审批（含计划确认、目标启动确认、敏感访问确认等一切以"请求用户批准"为语义的审批，它们都经同一条审批登记路径）、以及其他以"请求用户决策"为语义的等待；也覆盖 IDE 集成模式（ACP）下同样的等待。

验收：
- Given 代理向我提问/请求批准且我尚未回应，Then 回合无限期等待——无论过了多久，不因"引擎长时间没动静"被系统终止（等待用户是合法暂停，不是引擎僵死）
- Given 我最终回应（回答/批准/拒绝/关闭问询），Then 等待即刻结束、回合以我的回应继续——我的回应永远落在"还活着的等待"上，不落在已死的回合上
- Given 我主动取消，Then 等待结束、回合按"已取消"收场——用户取消是唯一合法的中断
- Given 客户端连接断开，Then 等待随连接失败而结束（断开连接不是超时惩罚；重连后可重新发起）
- Given 引擎真正僵死（无未决的用户请求、对象侧查询持续报"推进"已不可能但等待仍未返回——含等待状态机自身降级失守），Then 兜底终止仍生效——资源保护不因本条削弱

边界说明（何时不适用）：本条保护的是"引擎侧的等待"；若用户界面本身设有可配置的展示层超时（未来需求），那是界面自己的行为，与本条的引擎侧无限等待独立。IDE 集成模式下非用户决策类的请求（如读取文件、执行终端命令）不在本条覆盖内，维持各自的既有超时。

## 6. Epic E6：步数上限

### US6.1 单回合步数上限（P1）

作为配置者，我能限制单个回合的最大步数。

验收：
- Given 未配置，Then 不设限（回合按工作队列自然结束）
- Given 配置了上限，When 回合步数达到上限，Then 回合以"失败"定局且原因明确标为"步数上限"，错误提示指向对应配置项

## 7. 非功能需求（NFR）

| # | 需求 | 指标/约束 |
|---|---|---|
| N1 | 单活动回合 | 同一代理同一时刻至多一个运行中回合；其余排队（先来先跑） |
| N2 | 结束有序 | 回合结束事件的全部消费方处理完毕后，下一回合才启动 |
| N3 | 合并不丢内容 | 可合并请求折入同一次模型调用，任何一条的内容都不丢失 |
| N4 | 准入封闭 | 新异步源必须复用既有准入类别与合并规则，不发明旁路调度 |
| N5 | 可撤销性 | 已入队未消化的请求可撤销，撤销不留残余 |

### SDR-001 建域：统一异步唤醒源契约收编（2026-09-13）

1. **背景与动机**：回合驱动与准入调度是引擎最承重的机制，但此前无专项事实源——任务通知的准入规则写在后台任务域、定时的忙时挂起写在定时任务条目、目标续航无落点。任何新异步能力接入都要重新理解这套机制（Goal 模式等待轮询问题的根因分析因此付出高成本）。
2. **决策**：建立本域（回合调度与循环控制），把"准入类别、合并规则、插话语义、异步唤醒源统一契约、挂起的机制侧"收编为唯一事实源；相邻域文档保留本地视图并指向本域。用户裁决（2026-09-13）：与目标域同期建域（机制/产品分离）。
3. **被否决的备选方案**：a) 并入会话管理域——该域将变巨型，且统一契约的落点不够中立；b) 并入后台任务域——调度机制不属于"后台任务"，goal 挂起、用户消息都在此域之外。
4. **影响范围**：本文件全套；[goal-requirements.md](goal-requirements.md)（续航作为本域消费方）；后台任务域 ADR-003/005/008 的机制侧从此以本域为准；glossary L1/L2。

### SDR-002 模型空手而归的回合不得静默记为完成（2026-10-09）

1. **背景与动机**：真实会话中出现过"模型一步消耗了输出额度却未产出任何可见内容，回合被记为已完成"的情况——用户看到工作停在半途且没有任何解释，无从区分是模型自行停止还是系统吞掉了输出。US1.2 的"结局如实"未覆盖这种退化形态：空回应被错误归入了"正常完成"。
2. **决策**：新增 US1.4——完全为空的回应对用户不可接受，必须先在既有重试额度内自动重试；耗尽后以"失败"定局并在对话中留下可见标记。覆盖范围是**所有会以"已完成"呈现给用户的停止形态**（正常结束、未知原因、输出截断、暂停——四者在对外结局上同渲染为"已完成"），而非仅正常结束一种；取消、中止与内容过滤（自有非"已完成"结局）不受影响。判定必须是纯结构性的（无正文且无思考且无工具调用），不引入"任务是否完成"的语义判断——引擎在步级没有任务状态可观测，只能依据结构信号。
3. **被否决的备选方案**：a) 只提示不重试——偶发空回应无法自愈，每次都要用户手动重发；b) 判定加入"任务未完成"条件——该条件在引擎层不可实现，只能靠结构信号；c) 空回应照旧记完成、仅补一条提示——违背 US1.2 的结局如实原则。
4. **影响范围**：US1.2（结局如实的补充细化）；技术形状见 [turn-scheduling-architecture.md](turn-scheduling-architecture.md) ADR-002。

### SDR-003 回合终止的用户体验四原则（2026-10-15）

1. **背景与动机**：一天内两个真实会话同因"Stopped"终止（证据快照见 [turn-scheduling-context.md](turn-scheduling-context.md) §3.2）：代理按工具指引等待后台任务结果时，引擎的僵死看门狗把"健康的阻塞等待"误判为引擎停滞并静默取消回合——无日志、无归因、取消后回合仍僵尸存活 5 分钟，任务结果返回时回合已死。复盘定性为四个产品断层：停止无因（UI 只显示 Stopped）、等待被惩罚（阻塞等结果被当故障）、取消不生效（看门狗取消后仍等了 5 分钟才落地）、成果变孤儿（任务结果无人消费）。与 SDR-002 同族——都是"系统性终止对用户不可解释"的缺陷。
2. **决策**：确立四原则并落为用户故事——
   - **原则一（等待是合法语义）**：代理"阻塞等待一个有界、可取消的任务"是合理行为，引擎必须安全支持它，不得依赖提示词劝阻。落为 US5.3（等待的取消即时生效）+ US5.5（健康等待不得判僵死）。
   - **原则二（终止必带原因）**：每一次非用户发起的终止都必须用户可见、日志可查。落为 US5.4（系统性终止必带可见原因），要求对外结局词汇区分"已取消"（用户）与"已停滞"（系统看门狗）——今天一个 cancelled 盖三种含义（用户取消/看门狗/系统中止）。
   - **原则三（资源保护与业务语义分离）**：僵死看门狗的正当职责是防止僵死回合永久钉死资源（资源保护），但它不得有能力终止一个正在健康等待 IO 的回合（业务语义）；判据从"静默时长"升级为"静默时长 × 无任何活动信号"。
   - **原则四（事故后恢复顺滑）**：回合死了，已产出的任务结果不该失踪；恢复会话时应主动提示未消费的任务结果（跨域提案 P-028，落点后台任务/会话管理域）。
3. **被否决的备选方案**：a) 强化工具指引措辞让模型别等待——治标不治本，模型等待是真实业务需求，两天内两次无视指引即为证；b) 看门狗静默时长从 300s 调大——阈值永远存在误杀带，不解决判据缺陷；c) 取消看门狗——真僵死（等待对象已死）失去兜底，资源保护倒退。
4. **影响范围**：US5.3/US5.4/US5.5 新增；glossary「回合结局」条目（cancelled/stalled 词汇拆分，跨域术语同批登记）；跨域提案 P-028（恢复时未消费任务结果提示）；技术形状见 [turn-scheduling-architecture.md](turn-scheduling-architecture.md) ADR-004。

### SDR-004 等待用户决策的时长是无限的（2026-10-16）

1. **背景与动机**：与 SDR-003 原则一同族的缺陷，但等待对象不同：代理向用户提问或请求权限批准时，回合在"等待人"上静默——人没有回应的分钟里引擎没有任何活动信号。看门狗把"等待用户决策"与"引擎僵死"混为一谈：审批等待在静默阈值后被判停滞、回合被杀（且被错误归因为"用户取消"）；IDE 集成模式更直接——权限请求在固定的短超时后无人回应即拒绝执行（证据快照见 [turn-scheduling-context.md](turn-scheduling-context.md) §3.3）。用户视角的语义很简单：我在思考、我在忙，回应之前代理就该等着；等待被超时打断、回应落在死回合上，是体验断层（与 SDR-003"等待被惩罚"同族——那次等待对象是任务，这次是用户本人）。SDR-003 已把"等待合法"确立为原则一，但仅覆盖任务类等待；本条把它补全到用户决策类等待。
2. **决策**：确立不变式——引擎侧等待用户决策的时长是无限的；唯一能结束等待的是用户的回应（回答/批准/拒绝/关闭问询）或用户主动取消；客户端断连按连接失败收场（连接语义，不是超时裁决）。判据侧：看门狗静默到期时先查会话是否有未决的用户请求——有未决请求即重置计时（等待用户是合法暂停，不是引擎僵死），无未决请求且无活动信号才判僵死（资源保护不削弱）。落为 US5.6。覆盖范围与 US5.6 一致（结构化提问、权限审批等所有用户决策等待；含 IDE 集成模式的用户决策请求；其非用户决策类的请求——如读取文件、执行终端命令——不适用，维持既有超时）。
3. **被否决的备选方案**：a) 在每个等待点复制保活心跳（工具层已对提问工具这样做过）——逐点打点治标不治本，新增等待点要靠自觉，看门狗语义本身没修；b) 看门狗静默阈值调大——与 SDR-003 否决 c 同理，阈值永远存在误杀带，且用户思考可以远超任何阈值；c) 移除看门狗对用户等待的裁决——等同于本决策，但表述为"删能力"而非"修判据"，会丢掉"真僵死仍兜底"的边界。
4. **影响范围**：US5.6 新增；§4.5 看门狗判据（ADR-005 的正文形态）；ACP 集成模式的用户决策请求超时（架构侧 ADR-005）；glossary 无新跨域术语（「回合结局」条目已覆盖）。

### SDR-005 健康等待判据的措辞与覆盖面随拉模式架构修订（2026-10-18）

1. **背景与动机**：架构侧僵死看门狗三代重构（ADR-006：推模型活动信号改拉模式 owner 查询）裁决通过。需求文本的两处滞后：US5.5 的"活动信号"是推模型词汇（用户不需要知道信号由谁推送），且覆盖面只点名"任务"（设计实态覆盖全部等待类别）；US5.6 的"真正僵死"未覆盖等待状态机降级失守的极端形态（查询通道持续故障 + 门上无未决登记——引擎并未僵死，但状态机已无法证明任何一方的活体，兜底仍可终止）。
2. **决策**：US5.5 措辞等价改写——"仍有活动信号"→"引擎向对象侧查询到的活体事实为'推进中'"，验收行为不变（推进中不误判、真停滞兜底仍生效），覆盖面从"任务"显式扩展到全部等待对象，并新增第三验收（未登记等待的延迟兜底语义——漏接线代价从"一个静默窗口内误杀"变为"兜底窗口后终止"）；US5.6 兜底验收的"真正僵死"扩展为含等待状态机降级失守形态。均为措辞对齐，无行为变更。
3. **被否决的备选方案**：维持原措辞不动——需求文本与设计实态脱节，验收语言无法映射新架构的判定事实源。
4. **影响范围**：US5.5/US5.6；架构侧 ADR-006（同批裁决）。
