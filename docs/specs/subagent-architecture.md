## 1. 目标与设计原则

本设计描述**终态**：Rust 核心中子代理派发域的完整架构（TS 引擎现行行为为本设计的参照基线，其终态行为与本设计同构；双引擎并存期的行为一致性保证见 §7）。

设计原则：

1. **信号真实性至上**：一切对外信号（工具结果、任务状态、事件、界面标记）必须与真实执行结局一致——"停止/中断/超时"三类语义必须真生效（需求 N3）。
2. **事件闭合**：每个"已启动"必有且仅有一个终态事件；续作路径同律（需求 N4）。
3. **续作可信**：续作指引存在处，续作能力必存在；同一子代理不允许并发双执行流（需求 N7、US4.2）。
4. **调度自愈**：批量派发遇限流自动降速重试，不静默吞失败（需求 N6）。
5. **预算闸门**：时长上限是确定性闸门，处置结果可说明、可续作（需求 E5）。
6. **单向依赖**：本域依赖角色域与任务域，被协作域依赖（需求 N8）。

## 2. 域模型

### 2.1 核心概念

- **子代理身份（Subagent Identity）**：一次派发产生的、跨执行流存在的实体——由"角色装配 + 专属对话记忆"构成，是续作与用量归因的锚点。身份存活于其主会话生命周期内，跨重启保留。
- **执行流（Run）**：子代理身份上的一次执行（一次指令 → 一个终态）。同一身份同一时刻至多一个活跃执行流。
- **派发工具（Dispatch Tools）**：单一派发（`Agent`）与批量派发（`AgentSwarm`），见 [glossary.md](glossary.md) A7。
- **后台任务（Background Task）**：脱离工具调用、由任务管理面（查询/停止/通知）管控的执行流，见 A5。
- **任务（Task）**：任务管理面的一等工作单元——执行流的观测代理，承载状态、输出、终态仲裁结果与通知。
- **子代理会话记录（Subagent Session Record）**：子代理身份在其**独立记录流**中的完整对话与事件记录——是续作记忆、回放查询与用量归因的记录依据；与主会话记录分离，两者经派发镜像与引用关联（见 §3.2.1、glossary A8）。

### 2.2 执行流状态机

```
idle(待命/可续作)
  → running(运行中)
      → suspended(挂起：等待用户审批/作答，或限流退避)
          → running
      → completed(已完成) / failed(失败) / cancelled(已中断) / timed_out(已超时) / stopped(已停止)
  → queued(排队重试，限流语境，仅批量)
      → running
```

- 终态五元（completed / failed / cancelled / timed_out / stopped）互斥，**终态一旦写入，不再被任何后续事件改写**（停止不被完成覆盖——需求 US5.4）。
- `stopped`（用户/管理面主动停止）与 `cancelled`（父级中断传播）语义分离：前者是人的决定，后者是链式取消的结果；对外呈现上两者都不得伪装为 `completed`（需求 US2.2）。
- 批量语境追加 `not_started`（未启动即中止）的可辨识标记（需求 US6.4）。
- `suspended`（挂起，ADR-011）：成员暂停推进但**进展、上下文与身份保留**，等待用户（审批/作答）或限流退避后**同身份续跑**；挂起是运行中的子状态，不是终态——终态唯一性不受影响。等待用户期间时长预算停表（§5.1），挂起成员让渡批量并发槽（§3.4）。

### 2.3 取消模型（取消令牌分层）

取消沿三层令牌传播，任何一层触发都真实终止执行流：

```
父级令牌(会话/派发者作用域) → 派发作用域令牌(单次工具调用/批量) → 执行流令牌(子代理 turn)
```

- 前台派发：派发作用域令牌 = 工具调用取消信号；执行流令牌为其子令牌。
- 后台派发：派发作用域令牌 = 任务管理面的停止动作；`TaskStop`/会话收敛经此令牌真实中止执行流（需求 US3.3、US5.4）。
- 取消语义到 LLM 调用链的传播由内核既有机制承担（流式调用可中断）。
- **取消不是"尽力而为"**：执行流令牌触发后，执行流以 `cancelled/stopped` 定局，且不产生新的工具调用（需求 US5.3）。

### 2.4 终态仲裁规则

多个终止来源并发时（完成 vs 取消 vs 超时 vs 停止），**先定局者胜**，且写入动作幂等（终态唯一）。仲裁点为执行流驱动器（见 §3.3），任务管理面只接收仲裁结果，不自行覆盖（需求 US3.3、N7）。

## 3. 组件结构（rust 落位）

按 `rust-core-design` 分层：内核层（mirri-core，零 IO、trait-only）、接线层（mirri-server / mirri-embedded）。

```
mirri-core（内核，零 IO）
 ├─ subagent/
 │   ├─ mod          ：域模型、请求/结果类型、状态机、终态五元
 │   ├─ host         ：SessionSubagentHost（身份注册表 + spawn/resume/retry）
 │   ├─ run          ：执行流驱动器（RunDriver：turn 编排 + 取消 + 时长闸门 + 仲裁）
 │   └─ task_bridge  ：SubagentTask（执行流 → 任务管理面桥接）
 ├─ tools/
 │   ├─ agent_tool.rs      ：单一派发工具（描述面 + 校验 + 前台/后台分流）
 │   ├─ agent_swarm_tool.rs：批量派发工具（模板展开 + 校验）
 │   └─ task_list/output/stop：任务管理面工具（经任务服务）
 ├─ scheduling/
 │   └─ swarm_scheduler.rs：批量调度器（斜坡/并发上界/限流自愈/排队重试）
 ├─ task.rs                ：任务管理面（状态机、输出、上限、通知、持久化）
 └─ session/events.rs      ：状态事件面（闭合性保证在 host/run）
mirri-server（接线）
 └─ 任务服务接线：时长上限配置、通知投递、停止的真实中止联动、会话收敛
```

### 3.1 派发层（工具）

- **单一派发**：参数契约与校验（子角色默认值、可派发名单、模型别名校验、续作互斥）在工具层完成；校验失败作为可纠错的工具错误返回（含合法选项清单），不静默降级（需求 US1.1/US1.2）。
- **批量派发**：模板展开（条目占位符）、条目数界（≥2，上限缺省 3、`maxSwarmItems`/env 可配、`0` 不限——SDR-012）、重复展开检测、续作名单优先于条目；派发前置校验失败即整批拒绝（需求 US6.1/US6.5）。
- **描述面**：可用子角色清单（名称、用途、适用时机、默认型号、型号能力）与可用型号清单（curated 门控：无用途说明不展示）——由角色域与模型域数据装配（需求 US1.3）。
- **后台可用性**：后台派发前置条件（任务管理面工具可用）在派发层校验，不满足即拒绝并说明（需求 US3.1）。

### 3.2 生命周期层（身份注册表 + 续作）

`SessionSubagentHost` 持有会话级**子代理身份注册表**（取代按运行丢弃的跟踪表）：身份条目 = 子代理标识、装配信息（角色/型号）、对话记忆归属、活跃执行流标记、最近终态。

- `spawn`：身份创建（幂等于每次新派发）。
- `resume`（续作）：校验三前置——身份存在、**属于当前派发者**（所有权，元数据标签 + 注册表归属双检）、**无活跃执行流**（US4.1/US4.2）；通过则复用其对话记忆开启新执行流（对话保留，跨重启亦然——身份注册表随会话持久化）。
- 续作不更换角色，沿用已记录型号（需求 US4.6）。

### 3.2.1 会话记录与恢复

**记录载体（独立流，不混流）**：每个子代理身份拥有**一条独立记录流**，承载其自派发起的完整对话与事件（消息、工具调用与结果、步骤事件）；与主会话记录分离存储，互不污染。设计依据：子代理记录与主会话记录生命周期不同（可独立截断/归档/导出），混流使主会话日志膨胀、按身份回放与恢复困难（现状证据：context G21）。

- **派发面镜像**：子代理 run 的对外可见事件（含父子关联、用量）在派发者的记录中以镜像/摘要形式保留——主会话回放视图仍能呈现"谁派出、何时、结果如何"，但完整对话只存在于子代理自身记录流（需求 US7.2/US7.3）。
- **身份元数据**：装配信息、归属标签（派发者、工具调用）、最近终态随会话元数据持久化（agents 表形态），与记录流分离。
- **恢复重建**：会话重启 → 从会话元数据还原身份注册表（身份、归属、装配）→ 从各身份独立记录流重放重建对话记忆与用量 → 可续作（需求 US4.5/US8.3）。重启前未定局的后台任务按既有调谐规则落 lost（§3.5）。恢复时序遵从持久化域 ADR-006 的懒重放裁决：**会话就绪不等待子代理记录流**——注册表先行、主 agent 记录流重放为就绪门槛、子代理记录流在续作/查看时按需重建（重建记忆完整，非降级）；技术形状见持久化域 ADR-017。
- **查询与回放**：按身份浏览/回放其记录流（含中间事件与工具调用）；用量按身份累计并回写派发面归因（需求 US7.3）。
- **设施落位**：记录流复用内核持久化设施（日志文件按身份分片），与主会话记录同持久化根、不同流；契约与恢复流程登记 mirri-proto 注册表（§7）。
- **执行流与对话记忆的关系**：对话记忆属于身份、跨执行流累积；每次执行流从当前记忆续接，最终文本提取与用量归因按本次执行流结算。

### 3.3 执行层（RunDriver）

- 每次执行流 = 子代理身份（AgentScope）+ 独立 TurnFlow 实例（**不跨执行流复用 TurnFlow**——执行流状态互不污染，续作只复用记忆）。
- RunDriver 职责：
  - turn 编排（角色系统提示、装配工具面、LLM 工厂）；
  - 取消联动（执行流令牌 → turn 中止）；
  - **时长闸门**（§5.1）：超时即按处置策略终止并定局 `timed_out`；
  - **终态仲裁**（§2.4）：向任务管理面与事件面推送唯一终态；
  - 生命周期钩子配对（开始/结束，含执行流被丢弃时的 Drop 兜底——需求 US7.4）；
  - 子代理继承（权限模式、用户挂载工具、角色提示词前缀、思考档位——需求 US8.1 与裁决点 Q2）。

### 3.4 调度层（批量）

`swarm_scheduler`（每批量一个实例）：

- **起步斜坡**：首批少量立即启动（对齐现行量级约 5），其后按固定节奏逐个启动；运行中成员数不超过并发上界（缺省内置，环境变量可覆盖——需求 US6.2）。
- **限流自愈状态机**（需求 US6.3/N6）：成员限流失败 → 打上"排队重试"状态并发布排队事件 → 指数退避（基数与倍率内置）→ 容量收缩（逐步下探，下限 1）→ 恢复期逐步回升 → 对**同一身份**发起重试执行流（保留已有对话与已完成工作，不从头重跑）；重试超限如实判失败。
- **通用成员挂起（ADR-011）**：限流自愈的「同身份挂起 → 重试」机制泛化为通用挂起原语——挂起原因结构化（等待用户审批 / 等待用户作答 / 限流退避）；等待用户的成员同样经挂起-恢复通道回流（审批/作答决议即刻触发调度），并在挂起期间**让渡并发槽**（排队成员顶上，容量计算排除挂起成员）；恢复时重新竞争槽位。挂起与恢复经状态事件面发布结构化原因（§3.6）。
- **批量中止**：批量信号中止 → 未启动成员与已启动成员分别以可辨识状态定局（需求 US6.4）。
- **爬坡与事件节奏**：成员"已创建"事件随调度渐进发布（与真实启动节奏一致，不提前放量——观测真实性）。

### 3.5 任务管理面

- 状态机：running / completed / failed / stopped / timed_out / lost（重启调谐），终态不可覆盖；`killed` 是"用户主动停止"的内部历史别名，对外统一呈现 `stopped`（需求 US2.2/US5.4）。
- **停止 = 真实中止**：`TaskStop`/让我确认/会话收敛 → 经任务条目持有的取消令牌中止执行流 → 执行流以 `stopped` 定局并回写终态（需求 US5.4）。
- 容量上限：后台任务并发数受配置上界约束，超限拒绝新后台派发（需求 US3.2）。
- 输出：按创建会话隔离读取、超限截断保留尾部并带截断标记（对齐现行行为）。
- 通知：任务定局（含 lost）自动产生通知（需求 US3.4）。
- 持久化与重启：任务状态、子代理身份与对话记忆随会话持久化——记录载体为各身份独立记录流（§3.2.1）；重启后 running 任务调谐为 lost 并通知，可续作（需求 US8.3）。

### 3.6 观测层

- 状态事件面：`spawned / started / suspended(挂起，结构化原因：等待用户审批/作答或限流退避) / queued(限流排队) / completed / failed / cancelled / timed_out / stopped / aborted(批量中止)`——**闭合性由 host 与 RunDriver 保证**（每个 started 必有终态，含未启动即中止；续作路径同律——需求 US7.1）；挂起/恢复配对同律（挂起必有解除——恢复或终态），`suspended` 事件的 reason 为结构化原因（分类 + 审批请求/工具调用标识）而非自由字符串（ADR-011）。
- 子代理 turn 的中间事件（步骤、工具调用、实时输出）经 live relay 以独立 turn 标识流入会话事件面（界面展开能力，需求 US2.4/US7.2）。
- 生命周期回调：派发者侧开始/结束回调逐次配对，续作与异常退出同律（需求 US7.4；即内核的生命周期钩子机制，跨文档用语映射）。
- 用量归因：执行流用量结算到子代理身份，批量按成员分别归因（需求 US7.3）。

## 4. 批量结果契约

批量结果的对外形状（XML 面，供派发者消费）：

- 汇总段：完成/失败/中断/超时/停止**分列**（中断不并入失败——需求 US6.4，现状证据见 [subagent-context.md](subagent-context.md) G5；成员按终态归入对应列，汇总可自洽求和）；
- 成员段：成员内容、子代理标识、终态（completed/failed/cancelled/timed_out/stopped）、未启动标记（state=not_started——同上 G5）；
- 续作指引：存在任一非完成成员时给出，且指引指向续作能力（同上 G14，实现见 §3.2）；
- 单发语义：仅当全员失败才整体判失败（需求 US6.5）。

## 5. 关键机制详设

### 5.1 时长闸门

- 配置源：`[subagent] timeout_ms`（内置默认约 2 小时），环境变量优先且不落盘；对每次派发生效（存量不受影响，或按裁决点 Q1 处置）。
- 触发机制：RunDriver 内每执行流一个 deadline；到达即按处置策略定局 `timed_out`：
  - 前台：按裁决点 Q1——缺省 a（停止并如实报告）；若选 b，则执行流转入后台任务继续（relabel 为后台任务，派发者先拿回控制权），需要时以续作/查询接管；
  - 批量成员：仅该成员定局，其余不受影响（需求 US5.2）。
- 超时结果携带：时长说明 + 处置结果 + 续作指引（需求 US5.2）。
- **等待豁免（ADR-011）**：时长闸门只计引擎自身推进的时长；成员处于等待用户（审批/作答）挂起态时预算停表，决议后从剩余额度续跑。限流退避**不豁免**——退避是成员交付周期的一部分，预算闸门的确定性语义不变。

### 5.2 续作契约实现

- 三前置校验（§3.2）在 host 层同步完成，冲突即时报错（可纠错信息）。
- 并发双跑防护：身份条目的活跃执行流标记在 spawn/resume 创建执行流时原子占用、定局时释放；占用失败即拒绝（US4.2，现状证据见 context G13）。
- 完成后续作：身份条目与对话记忆在终态后保留，续作不因终态而失效（现状证据见 context G14）。
- 驳回与工具结果的续作指引一致性：指引生成与 host 校验使用同一身份注册表（指引存在 ⇔ 续作可行——US2.3）。
- **上下文复用**：续作执行流的首请求上下文 = 身份既有全部对话（续接而非重建），复用部分按既有上下文缓存计费、不产生重建完整上下文的输入成本（缓存是否命中以用量数据如实反映，非承诺不变量）；"重新派发"是独立新身份（记忆、用量归因互不污染）——需求 US4.3/US4.7。
- **未竟动作重做**：续作指令携带"重做中断点未竟动作（其结果未入记忆者）"的提示，已入记忆的完整动作不重复执行——需求 US4.4；此为**提示级衔接**（子代理依记忆自主判断，非强制不变量），提示文案由工具结果承载，重做的判定以记忆为凭。

### 5.3 取消与终态仲裁实现

- 执行流驱动器的终态写入为一个原子动作（含：取消令牌已触发判定、LLM 流中断、任务终态、事件、钩子配对收尾）。
- 任务管理面的 `stop` 只发起取消，终态由执行流回写；管理面不自行覆盖终态（现状证据见 context G3/G16）。
- 前台取消的结果呈现：`cancelled` 终态 + 原因文案，绝不呈现 `completed`（现状证据见 context G15）。

### 5.4 限流自愈状态机参数

| 参数 | 缺省 | 说明 |
|---|---|---|
| 首批并发 | 5 | 斜坡起点（对齐现行量级） |
| 斜坡间隔 | 700ms | 首批后逐个启动节奏 |
| 重试基数 | 3s | 指数退避起点 |

### 5.5 未来与层级边界

- 嵌套派发边界待裁决点 Q2；单层裁决下，子代理装配面不含派发工具，行为与文档一致（不静默失效、不崩溃——需求 US8.2）。
- 与协作域交接：协作域的团队模型若复用于代理机制，其身份注册表与续作契约为本域对外的稳定接口面（见 collaboration-requirements US7.1 裁决）。

## 6. 非功能设计

- **并发上界**：全局运行中执行流数受会话级上限约束（约 10，可配），批量另受调度层并发上界；超限按派发来源分别处置（后台拒绝 / 批量排队）（需求 N1）。
- **成本可观测**：用量按执行流结算、按身份累计；批量按成员聚合（需求 N2/NFR）。
- **零 IO 内核**：上述全部逻辑位于 mirri-core，文件/时钟/进程经 trait 注入，可测试性对齐 rust-core-design 分层要求。
- **事件体积**：swarm 成员事件的渐进发布与成员编号，避免大批量一次性事件洪峰（需求 US6.2 观测节奏）。

## 7. 与相邻设计的关系

- **引擎分层**：内核组件全部落位 mirri-core；配置装配、通知投递、会话收敛等接线在 mirri-server/mirri-embedded。
- **协议层**：事件契约（spawned/started/queued/completed/failed/cancelled/timed_out/stopped/aborted，与 §3.6 一致）与任务通知契约登记 mirri-proto 注册表，作为唯一事实源；双引擎并存期以对拍保证一致。
- **角色域**：子角色装配、可派发名单、型号选择规则来自角色域；本域不为其发明字段（需求 N8）。
- **协作域**：本域是其上游机制；协作域裁决（US7.1）前，本域保持边界稳定（裁决点 Q2 与其联动）。

### ADR-001 续作契约补充：上下文复用与未竟动作重做（2026-09-09）

1. **背景与动机**：续作契约原设计只保证"对话保留"，未定义续作执行流的上下文组织方式与中断点衔接机制；需求侧增补（SDR-001）后需设计侧承接。
2. **决策**：续作执行流首请求上下文 = 身份既有全部对话（续接而非重建），复用部分按既有上下文缓存计费、命中如实反映；未竟动作重做为提示级衔接（续作指令携带重做提示，判定以记忆为凭）；"重新派发"为独立新身份（记忆与归因互不污染）；终态枚举统一六元，`killed` 降为内部历史别名、对外呈现 `stopped`。
3. **被否决的备选方案**：a) 续作时重建上下文——违背连续性与成本目标；b) 重做做成强制不变量——与子代理对记忆的自主判断冲突。
4. **影响范围**：§2.2 状态机、§3.5 任务管理面、§3.6/§7 事件契约、§4 批量结果契约、§5.2 续作契约。

### ADR-002 子代理会话记录独立于主会话记录（2026-09-09）

1. **背景与动机**：会话记录的事实形态未定义——参照基线中每子代理有自己的记录流（own wire journal），而 Rust 侧子代理事件与主会话混写同一日志，恢复折叠同一日志（现状证据见 context G21）。混流导致：主会话日志膨胀且被子代理事件污染、无法按身份独立截断/归档/导出、续作记忆的重建绑定于整条会话日志、与参照基线记录语义不一致。
2. **决策**：每个子代理身份拥有**独立记录流**，承载其完整对话与事件；与主会话记录分离存储；主会话记录仅保留派发面镜像/摘要与引用；身份元数据随会话元数据持久化；恢复时按身份从独立记录流重放重建（§3.2.1）。
3. **被否决的备选方案**：a) 维持单一日志混流（现状）——污染与恢复耦合问题不可接受；b) 不做持久化、只靠进程内记忆——违背跨重启续作需求（US4.5/US8.3）。
4. **影响范围**：§2.1 域模型、§3.2 身份注册表、§3.5 任务管理面持久化、§7 协议层（记录流契约登记）、glossary A8。

### ADR-003 任务通知以对话消息投递（对话闭环机制）（2026-09-12）

1. **背景与动机**：后台任务定局后，若只发界面事件，派发者（模型）无法自主获知，只能轮询或阻塞等待——后台派发"立即拿回控制权"的价值链断裂。需要把定局送达模型本身，且与对话流（进行中的回合、压缩、撤销重做）自洽。
2. **决策**：终态通知是**投给派发者的合成用户消息**，经回合调度按"忙则折入当前回合、闲则自起新回合"投递；通知内容自足（任务号、类型、终态、原因、输出的获取方式；子代理失败附可行动恢复指引，含续作标识与任务号的防混淆警示）。投递具备：幂等（同一任务同一终态至多一次，投递状态随对话记录可回放）、可对账（对话撤销后按记录回滚投递状态，不重不漏）、恢复补录（重开后未投通知静默入上下文，不触发新回合）、压缩免疫（压缩后首个回合重注入"后台任务仍在跑 + 任务清单 + 勿重复派发"提醒）。用户主动停止的任务不再补发通知（停止操作的应答即唯一答案）。
3. **被否决的备选方案**：a) 仅发事件让界面消费——模型不可见，闭环断；b) 强制轮询接口——空耗且违背"不等待"承诺；c) 通知一律自起新回合——进行中回合会被打断，改为忙时折入。
4. **影响范围**：需求 E10、US3.4；§3.5 任务管理面、§3.6 观测层新增通知投递机制；协议层通知契约登记（含 `task.notified` 类事件）。

### ADR-004 任务持久化与恢复（状态即记录，游标不存绝对时刻）（2026-09-12）

1. **背景与动机**：后台任务跨进程重启需要恢复"有哪些任务、各自什么状态、输出在哪"。绝对时刻（下次触发/预计结束）随停机失效，存了反而是幽灵数据；任务状态既要全量可查（磁盘），又要能在对话回放中重建（wire 记录）。
2. **决策**：双层持久化——每任务一个原子状态文档 + 每任务一条追加式全量输出日志（存放于任务属主的记录目录下，路径作为只读凭据外发）；生命周期转换同时写入对话记录的可回放操作集（终态转换附有界的输出尾部快照，供冷转录折叠重建）。恢复三段式：对话记录回放建幽灵任务 → 磁盘加载合并（取新者）→ 调谐：非终态任务落"丢失"并回写。会话关闭时被终止的后台任务按"孤儿"落"丢失"（而非"被停止"），与重启调谐的投影一致。定时任务同律：只存触发游标（最后触发/创建时刻），恢复时重算下次触发，停机错过的触发按合并语义处理。
3. **被否决的备选方案**：a) 只存内存——违背跨重启；b) 持久化绝对下次触发时刻——停机后成为幽灵数据；c) 全部走对话记录——输出体量大，污染对话日志。
4. **影响范围**：需求 US8.3、US9.2、US10.3、US11.4；§3.5 任务管理面持久化机制；协议层 wire 操作契约。

### ADR-005 定时任务（cron）子系统（2026-09-12）

1. **背景与动机**：提醒/周期检查/看护类工作需要"到点自动让模型做事"，且不能与后台任务管理面重复发明状态机、持久化与投递。
2. **决策**：定时任务 = 计划表达式 + 提示词，归属于创建它的会话（不跨新会话传递；**会话复制（fork）一律不携带**——2026-09-12 由需求侧 SDR-006 裁决修订，原"整体克隆"表述作废，避免新旧会话双触发）。触发采用轮询检查 + 空闲投递：会话忙时触发挂起，空闲后以合成用户消息注入（信封携带任务标识、计划、循环性、合并计数、过期标记，提示词逐字包裹）。生命周期：一次性触发即自删；循环任务 7 天未刷新即过期，过期任务最后一次投递带标记后自删（防止陈旧任务无限堆积）。防扎堆：循环任务触发时刻向后确定性小幅偏移（≤ min(10% 周期, 15 分钟)），一次性任务仅在整点/半点类扎堆时刻提前 ≤90 秒；偏移由任务标识确定性导出（可复现、可测试）。创建侧硬校验：表达式 5 年内须有触发、每会话 ≤50 个、提示词 ≤8KiB、一次性任务首触发 ≤350 天。表达式语义：标准 5 字段、本地时区、纯数字语法（时区语义已由需求侧 SDR-005 裁决：默认本地时区 + 可选显式指定；秒级/别名不采纳——显式时区的架构承接随本程序 B5 批次以新 ADR 落档）。
3. **被否决的备选方案**：a) 操作系统级 cron/定时器外挂——与会话生命周期、恢复、会话资产携带语义（修订前为整体克隆）脱节；b) 每任务常驻线程/协程计时——任务量大时开销与恢复复杂；轮询 + 游标重算最简且可测试。
4. **影响范围**：需求 E11、N12/N13；任务管理面复用（ADR-004 持久化与恢复同律）；协议层 `cron.fired` 类事件契约。本 ADR 依赖裁决点 Q5（时区语义）的机制在表态前视为**对齐 TS 现状的缺省决策**——Q5 已由需求侧 SDR-005（2026-09-12）裁决关闭，缺省决策随之定案，显式时区字段的增量架构随 B5 批次以新 ADR 承接。

### ADR-006 停止的优雅终止与生命周期边界（2026-09-12）

1. **背景与动机**："停止=真实停止"（US5.4）若只有瞬时硬杀，正常收尾（缓冲落盘、子进程回收）会被撕裂；若只有软取消，失控任务收不回来。会话退出与无界面模式又引入第三种边界：任务的存续以会话为界还是独立存活。
2. **决策**：停止分两段——先发取消信号并给收尾宽限期（默认约 5 秒，可配），宽限内自然定局者以其结果为准；超期未定局则执行强制终止升级（进程类：先礼后兵直至强杀），仍未定局才由管理面落"已停止"。会话退出默认收敛全部后台任务（收敛前抑制终态通知，避免退出风暴），孤儿落"丢失"；可配置让独立存活的进程类工作跳过收敛（存活续跑，语义上归属其进程本身而非会话）。无界面模式（单次运行）三策略：完成即退 / 等待收敛（抑制通知 + 时长封顶）/ 接力驱动（默认：通知驱动新回合，受时长与回合数双封顶，防失控循环）；无界面模式未显式配置时后台工作不设时长上限（避免长任务被交互场景的默认上限误杀）。
3. **被否决的备选方案**：a) 纯硬杀——收尾撕裂、输出丢失；b) 纯软取消——失控任务收不回；c) 退出一律收敛——独立存活的进程类工作被误杀（keepAlive 例外由此而来）。
4. **影响范围**：需求 US9.3、US9.5、US5.4、N11/N14；§2.3 取消模型补充宽限层；§3.5 任务管理面。本 ADR 依赖裁决点 Q6（无界面默认策略）与 Q8（会话关闭默认）的机制在表态前视为**对齐 TS 现状的缺省决策**，表态后以新 ADR 修订。

### ADR-007 摘要提炼与批量续作名单映射（2026-09-12）

1. **背景与动机**：子代理的产出以"最后一条助手文本"为准入派发者结果；为空或过短时派发者拿到的是不可用的空结果。批量场景下续作成员各自处境不同，"统一续作指令"无法表达逐成员的差异交代。
2. **决策**：a) 摘要提炼：子代理回合结束后，若最终助手文本不满足其角色声明的摘要质量线（最小长度），自动以续问方式追加回合直至达标或达重试上限；回合因输出长度上限截断的，按失败定局并明示原因（不把半截文本当结果）。b) 批量续作名单：批量续作参数为"成员标识 → 逐成员续作指令"的映射（非名单），每成员可携带专属指令；续作成员先于新成员启动。
3. **被否决的备选方案**：a) 空摘要原样返回——派发者无法行动，违背结果可用性；b) 截断静默成功——掩盖执行不完整；c) 续作名单只带统一指令——逐成员差异无处表达。
4. **影响范围**：需求 US2.1（结果摘要可用性）、US6.1（续作名单语义扩展）、G29/G30 相关差距项；§4 批量结果契约。

### ADR-008 等待入口与目标挂起的技术形态（2026-09-13）

1. **背景与动机**：需求侧 SDR-011（A+B 组合裁决）需设计侧承接——阻塞等待入口的接口形态、目标挂起与通知唤醒的准入交互、以及两者的职责切分；现状证据（TS v2 无等待入口 / v1 与 Rust 的参数先例 / goal 续航与任务系统零交互）见 [subagent-context.md](subagent-context.md) §6.13。
2. **决策**：
   a) **阻塞等待入口**：任务输出查询工具增可选「等待」参数（形态对齐 v1/Rust 先例：缺省关闭；时长上限缺省约 30 秒、硬上限 1 小时；等待内部复用任务服务的既有等待原语，中断信号可打断）。到期未定局为**非错误**：返回部分输出快照 + 「仍在运行」标注 + 勿再等待的纠正指引。批量等待**不新增聚合参数**——由同一并行调用组内多次等待表达（各自定局各自返回，先完成先拿到结果）；被否决的聚合形态（单调用多任务、流式部分返回）徒扩工具面且与并行调用组语义重复。等待命中定局时抑制该任务的自动通知（复用既有抑制机制，等待的返回即应答）。普通查询的未就绪返回附一行动态劝阻提示（不依赖静态描述面）。
   b) **续航提示任务感知**：任务服务向目标续航提示的拼装方供给「进行中任务快照」（数量/类型/描述，注入时刻快照；仅存在进行中任务时携带）。
   c) **等待挂起与唤醒**：挂起 = 目标续航提示的**暂停发放**（不新增回合类型、不进目标持久状态机）；唤醒 = 任务通知经既有「闲则自起新回合」准入自然开启回合，目标上下文由既有的每回合常驻提醒在场——**零新增合并机制**（挂起期间无活动回合，通知的忙折入分支天然不触发）。等待信号判定：续航回合结束时无任何工具调用（纯文本收尾）且存在进行中后台任务；误判由看门狗兜底（挂起计时器到期注入一次续航提示，时长可配、缺省量级由目标域定）。用户消息照常开回合（优先于挂起）；重启后挂起态不恢复，按常态重建。
   d) **与无界面模式的同构**：本机制是 print 模式「接力驱动」策略在交互目标模式下的对应物——等待由引擎侧事件承担，模型调用开销归零（需求 N16）。
3. **被否决的备选方案**：a) 独立 Wait/Sleep 工具——与任务无绑定，鼓励空转；b) 唤醒时专门拼装「续航+通知」合并消息——既有常驻目标提醒已覆盖目标上下文，双消息徒增回合；c) 挂起入持久状态机——跨重启语义（挂起中的目标如何恢复）徒增复杂度，运行时挂起 + 通知/看门狗双兜底已闭合；d) 唤醒采用任务通知折入挂起前回合——挂起期间无活动回合，该分支不存在，无需设计。
4. **影响范围**：需求 E13（US13.1–13.3）、N16；任务输出查询工具的参数面与结果面（工具调用域逐工具规格同步）；任务服务的通知抑制接线；目标（goal）域的挂起态/看门狗/预算计费——**已由 goal 域 E5/ADR-001 正式承接（2026-09-13，goal 域四件套建立，本域 O11 关闭）**；glossary A12/A13。
### ADR-009 子代理审批通道接线（2026-09-14）

1. **背景与动机**：会话审计 session-30c0d8bb（docs/specs/reports/rust-v3-session-30c0d8bb-audit.md，P0-1）证实：Manual 模式下子代理的全部 `Write`/`Bash` 调用（含合法工作区内写入与只读命令）即时被拒——`approval required but no approval mechanism available`，`approval.ask` 从未到达客户端。根因：子代理 TurnFlow 的两个 turn 入口（spawn/resume face）逐项接线了 permission/hooks/task/goal/plan/todo/event/wire 服务，唯独漏接 `set_reverse_rpc_callback` 与 `set_interaction_kernel`（全库唯一生产接线点在 embedded 主代理 dispatch）。需求 US8.1（权限与能力一致，P0）要求"子代理沿用派发者的权限生效规则"，现状是该需求的实现缺陷。
2. **决策**：
   a) 子代理 TurnFlow 在 spawn 与 resume 两个 turn 入口统一补接 `set_reverse_rpc_callback` + `set_interaction_kernel`，取值继承父代理的 `AgentScopeConfig`（host 构造子代理 config 时既已继承 `reverse_rpc_callback`，补齐 `interaction_kernel` 的继承）；turn 入口处从子代理自身 config 读出并接线（与 permission_manager 的接线同模式）。
   b) 重启恢复（`restore_subagents`）重建子代理 config 时，两字段同样从主代理 config 继承，避免"重启后子代理审批通道丢失"的时序缺陷。
   c) 子代理审批请求**暂不携带 agent 身份**（`ApprovalSnapshot.agent_id` 现为 nil 占位，wire `agentId` 为可选字段）——客户端以会话为粒度渲染审批卡；作为已登记限制，后续若审批面需要来源区分再单独裁决。
   d) **审批拒绝的下游语义**（复审澄清）：审批被拒是**工具级反馈**而非执行流终局——工具调用以错误结果回传，模型继续本回合（可改用其他路径或明示受阻后结束）；执行流终态仍由回合停止原因决定（见 ADR-010）。本 ADR 不引入"被拒即 failed"的短路。
3. **被否决的备选方案**：a) 子代理一律 headless 自动放行——违反 US8.1"不能因派发而变松"，静默越权；b) 仅修 embedded 一面——mirri-server 部署无子代理面（authoritative-methods.tsv:54），embedded 即全部生产路径，host 层修复天然全覆盖；c) 把审批回调下沉进 PermissionManager——现有 seam 在 TurnFlowHooks 的 `authorize_tool_execution`，下沉需改权限域公共接口，改动面大且无新收益。
4. **影响范围**：§3（host 接线）；需求 US8.1；审批域（请求来源为子代理时的呈现，受 c) 限制约束）。
5. **修订记录**（2026-09-14，复审后补强 b）：resume/restore 路径的 base config 需与 create 路径同样装配 `interaction_kernel`（源：会话 artifacts 的 approval/question gate）——否则恢复后子代理的待审批在 `approval.listPending` / `approval.decide` / `interaction.*` 面不可见（reverse-RPC 主通道不受影响）。
6. **修订记录**（2026-09-14，验收期死锁修复 `bcfb3ed4`）：真实进程验收发现 serve 部署面的既有缺陷——wait 模式 `message.send` 的处理内联占用连接循环，`approval.ask` 无法送达客户端，turn 被引擎看门狗 300s 误杀（fire 模式不受影响）。修复：反向 RPC 状态移入 `Arc<Mutex<ReverseRpcState>>`，审批回调直接投递连接 outbox（独立 writer 任务刷写），引擎域方法 dispatch spawn 化。**并发语义变化**：wait 模式下同一连接的并发请求由串行变为并行——这是解锁审批通道的必要前提（连接循环是 socket 唯一读者，不能被长 turn 占用）；单连接内请求间不再有顺序保证，依赖顺序的客户端应自行串行化。已知后续项：并发上限（reviewer N2）、反向 RPC 超时统一（Q2）。
7. **修订记录**（2026-09-16，后续项 Q3 关闭）：断线后 pending 审批恢复语义已由 [ADR-011](#adr-011-成员挂起原语与等待用户状态2026-09-16) e 裁决并实现——审批 gate 为待决唯一事实源，通知面投递失败不结束请求，重连客户端经待决读面重建审批卡（实现 commit 79cbba34）。

### ADR-010 子代理任务终态携带回合停止原因（2026-09-14）

1. **背景与动机**：同审计 P2-2：子代理回合以 Filtered / Paused / Unknown / BlockedByHook 结束时，任务一律记 `completed, exit_code 0`（`SubagentCompletion` 不携带 `stop_reason`，host 构造时丢弃 `TurnEndResult.stop_reason`）——违反设计原则 1（信号真实性）与 §2.2 终态五元的外在呈现。
2. **决策**：`SubagentCompletion` 增加 `stop_reason` 字段，任务终态按其映射：`EndTurn → completed`；`Filtered → failed`（输出被内容过滤截断）；`Paused → failed`（回合被暂停后定局）；`BlockedByHook → failed`（被钩子阻断）；`Unknown → failed`（未知停止原因，fail-safe）。失败消息文案点名原因。**诚实边界**：模型在回合正常结束时于文本中口头报告"任务失败"的，无法可靠自动检测，仍记 `completed`——该限制在任务输出文本中可读，不伪装、不误标。
3. **被否决的备选方案**：a) 解析子代理最终文本判定成败——不可靠且语言敏感，误判比缺信号更糟；b) 为 Filtered/Paused 新增任务终态枚举值——TS 词表（running/completed/failed/killed）已覆盖，映射即可，扩枚举破坏跨引擎词表一致；c) 维持现状（completed）——把过滤/阻断的失败伪装成成功，违反终态仲裁的信号真实性。
4. **影响范围**：§2.2（终态呈现）、任务域状态面；`subagent_integration_tests` 的 settle 断言面。

### ADR-011 成员挂起原语与等待用户状态（2026-09-16）

1. **背景与动机**：批量成员在执行中存在"暂停推进、等待外部输入"的真实状态——等待用户审批/作答、限流退避。现状只有限流退避拥有可观测挂起与同身份恢复通道；等待用户期间成员对外恒呈"运行中"，且等待时间计入成员时长预算——用户决策越慢，成员越易被时长闸门判 `timed_out`，最终以"失败"面目呈现（呈现侧证据见 [agent-supervision-context.md](agent-supervision-context.md) §9）。另：审批请求的即时投递通道与连接生命周期耦合——通道断开时请求被按"用户已取消"收尾，用户从未实际表态（ADR-009 修订记录登记的后续项 Q3）。督导域 SDR-008/US5.4 需要"等待用户"成为结构化的成员状态事件。
2. **决策**：
   a) **通用挂起原语**：调度器既有的"限流挂起 → 同身份重试"机制（§3.4）泛化：挂起原因结构化为三分类——`approval`（等待用户审批）/ `question`（等待用户作答）/ `rate_limit`（限流退避）；同一身份、进展保留，原因解除后同身份续跑。
   b) **挂起状态事件化**：成员进入/退出挂起经 `subagent.suspended` / `subagent.started` 发布（§3.6）；`suspended` 的 reason 从自由字符串升级为结构化原因（分类 + 上下文：审批请求标识、工具调用标识），挂起/恢复配对遵循事件闭合。契约登记 mirri-proto 注册表；迁移窗内旧字符串 reason 以兼容形态并存。
   c) **时长预算的等待豁免**：等待用户（approval/question）期间预算停表，限流退避计入（§5.1）——用户响应速度不是成员的可控属性，而退避属于成员交付周期。
   d) **并发槽让渡**：挂起成员（含等待用户）让渡批量并发槽，恢复时重新竞争（§3.4）。
   e) **审批请求的连接无关性**（关闭 ADR-009 后续项 Q3）：会话审批 gate（interaction 内核）是待决请求的唯一事实源，反向 RPC 只是通知面——通知投递失败（连接断开/无订阅者）**不结束请求**，gate 条目保留，重连的客户端经待决读面重建审批卡并决策；是否过期由审批域既有语义决定（现状：无过期），不因通道断开而隐式取消。
   f) **终态词汇**：等待用户期间的批次取消按 `aborted` 定局（非 failed）；批量结果契约（§4）的 outcome 词汇与内部终态枚举一一对齐。
3. **被否决的备选方案**：a) 呈现层自行推导等待状态（前端关联待决审批与成员行）——治标：断线后审批仍消失、时长预算仍误杀；且推导逻辑与引擎状态机双轨，违背单一状态源。**但作为迁移期过渡被保留**（supervision 域 ADR-008 ④ 的显式待删实现，其 P4-4 删除）。b) 为等待用户新建独立事件/通道——限流挂起已有完整机制（同身份、退避、事件），新通道造成两套挂起语义。c) 提高时长上限缓解等待误杀——把"等用户"与"跑太久"混为一谈，误杀依旧，只是阈值变化。d) 通道断开后向新连接自动重发审批请求——重发只解通道半边；无 gate 为事实源的裁决，重发与决议会竞态。
4. **影响范围**：§2.2 状态机、§3.4 调度层、§3.6 事件面、§5.1 时长闸门；ADR-009 修订记录的 Q3 关闭；supervision 域 §4.6（消费侧契约）与其 SDR-008/US5.4；glossary A14；协作域未来"成员阶段汇报"（proposals P-027）以结构化原因为词表基础；P-025（用户级暂停/恢复）若裁决通过，复用本原语。

### ADR-012 后台进程的跨服务代际治理机制（2026-10-14；评审二轮修订）

1. **背景与动机**：进程形态后台任务的档案收敛与物理进程存活是两个独立事实——服务正常关闭走 SDR-007 的同步收敛，「退出保留」任务与崩溃路径都产生「档案未定局、进程无主」的孤儿态，且无人对账。孤儿判定的技术难点是进程号复用。现状事实与事故证据链见 [subagent-context.md](subagent-context.md) §7。

2. **决策**：
   a) **进程身份指纹（三元组）**：`pid + pgid + 进程启动时刻`（术语 A15；命令文本为旁证展示，不参与判定）。启动时刻是身份主判据：同一进程号在同一启动时刻上至多属于一个进程实例。**采集点 = 进程获取时**（两类路径的公共点：后台 spawn 与前台启动/前台转后台都拿到 child 后即取，而非只在后台 spawn 时——覆盖 US14.1 第三条的前台转后台路径）。指纹随任务档案持久化；旧记录无指纹字段时普查按「无法判定」降级（仅报告，不处置）。
   b) **启动时刻的跨平台来源**：macOS 经 libproc（`proc_pidinfo` 族，需在 mirri-os 补该绑定——现状 nix 依赖不覆盖）取进程创建时刻；Linux 取 `/proc/<pid>/stat` 启动时刻字段。两平台统一抽象为 mirri-os 的一个查询（存活与否 + 启动时刻 + 进程组内成员枚举）；**非 Unix 平台**指纹查询降级为「仅存活」，普查照跑但判定降级为「无法判定」档（仅报告）。平台范围本 ADR 只裁决 macOS/Linux，Windows 留待执行环境域既有差异条款。
   c) **普查与加载调谐的时序（评审二轮 Blocker 1 裁决）**：既有的「会话加载时把运行中任务调谐为 Stopped 并写回」机制会摧毁普查输入集。裁决为**普查先行**：携带指纹的进程类 Running 档案在会话加载时**不再无条件调谐**，改为延迟到普查判定（普查把档案收敛为「已丢失」/登记孤儿后，会话加载读到的已是终局或保留态）；无指纹的旧档案维持既有调谐不变。该裁决修订 ADR-004 恢复三段式中「非终态任务落丢失」的适用面（进程类带指纹任务改走普查判定）。普查器在服务启动路径上**异步**执行，不阻塞就绪；普查与会话懒加载对同一档案的写序由「加载尊重已落普查结论、未普查的带指纹档案暂不调谐」约束。
   d) **判定树三分支**：①pid 存在且启动时刻匹配 → 存活孤儿（登记报告，默认不动手）；②pid 不存在或启动时刻不匹配（复用）→ 档案收敛 Stopped（「已丢失」呈现，SDR-007 词表不扩容）并注明普查来源；③pid 不存在但 pgid 组内仍有存活成员（组长死亡态）→ 档案同样收敛，**同时**登记「组内残留」条目（组员枚举 + 命令旁证），进入普查报告与 US14.6 可见性——该分支不得静默。档案收敛与残留登记是两个动作，报告消费的是后者。
   e) **处置的进程组语义与安全边界**：终止 = 向指纹确认的进程组发终止信号（组号为任务启动时创建的独立组）。**落盘 pgid 跨越信任边界**（被污染档案可携带任意组号）：终止执行前重验——组内成员枚举须非空、且组长存活时指纹须匹配；组信号只发给重验通过的组。**组长死亡态**（指纹不可达）：默认仅报告；终止档位下对重验过的组发组信号，并在 ADR 安全边界记档：组长与全部后代死亡后组号可被系统复用，重验（存活成员存在性）缩小但不完全闭合该窗口——残余概率登记为已知限制。终止执行复用执行环境域的两层升级策略（终止信号 → 宽限 → 强杀），但**不复用现有 ChildProcess::kill 方法**（普查器无 child 句柄）——mirri-os 新增「按裸组号发组信号（含升级）」API，该 API 承载上述重验不变量。
   f) **总寿命上限的执行者（评审二轮 should-fix 裁决）**：总寿命闸门复用任务管理器层的超时执行点，但**执行者补一个服务级驱动**：会话内的超时仍由既有任务驱动循环武装；「退出保留」任务（会话已关、无驱动循环）与 mirri-server 部署（无 embedded 任务驱动）下，由服务级低频清扫循环驱动总寿命判定——该循环是普查器的常驻化形态（同一条档案读路径，只在启动时跑一次改为周期性跑），不清扫「退出保留」任务（SDR-013 d 默认豁免），只覆盖未豁免任务。双部署差异：embedded（`mirri web`）与 mirri-server 各自装配该循环，行为一致。
   g) **实例代际标识**：任务档案持久化时写入创建它的服务实例标识。**取 embedded 的 epoch**（任务档案的写者均为 embedded 引擎侧；mirri-server 复用 embedded 装配），不以 server HTTP 层的实例标识为准——档案的代际归属跟写者走，避免双标识歧义。
   h) **契约面**：US14.5 关闭告知与 US14.6 可见性需要承载字段（「上一代遗留」标注、判定结果、已存活时长）——按 E12 先例本域定契约并登记 mirri-proto；US14.5 的界面呈现归各端（TUI/web/desktop 的关闭确认），无界面回落为「直接按既定策略执行 + 日志与下次普查报告」（US14.5 第四条）；处置入口（US14.3）为 RPC 面，ACP 面本 Epic 不接入（如需另裁决）。

3. **被否决的备选方案**：a) 纯 pid 判定——复用误伤；b) 命令文本比对作判定——巧合进程不可区分；c) 普查内嵌会话加载路径同步执行——拖慢就绪且无必要；d) 为孤儿发明新终态——SDR-007 已裁决不扩词表；e) 服务退出时把「退出保留」任务一并杀掉——违背该配置的产品语义；f) 心跳间接判定存活——心跳断只说明「任务不健康」，不说明「进程身份」；g) 维持「加载即调谐」不变、普查改在调谐前抢跑——竞态窗口结构化存在（任意会话先打开即摧毁候选），改为「带指纹档案不调谐、普查独占收敛权」才是封闭解。
4. **影响范围**：requirements Epic E14（US14.1–14.6）与 SDR-013；任务持久化 schema（指纹三元组 + 实例代际号，向后兼容降级）；mirri-os（存活+启动时刻+组员枚举的跨平台查询抽象、按裸组号的组终止 API 含重验不变量）；TaskManager（加载调谐适用面修订——ADR-004 恢复三段式联动；总寿命闸门）；服务启动装配（异步普查器 + 常驻清扫循环）；执行环境域（升级策略复用，方法不复用）；mirri-proto（US14.5/14.6 承载字段登记）；glossary A15 同批登记。

### ADR-013 恢复时序措辞对齐持久化域懒重放裁决（2026-10-15）

- **背景与动机**：本域 §3.2.1 恢复重建条目此前未同步持久化域 ADR-006（2026-09-09）已裁决的恢复时序（注册表先行 → 主 agent 记录流重放为就绪门槛 → 子代理记录流懒重放），读法上可被误解为"恢复时全量重建各身份记忆"。实测大会话重开等待与内存尖峰的调查（`docs/specs/reports/rust-v3-session-cold-open-perf-20261015.md`）确认恢复实现确在就绪路径全量重建全部子代理上下文，属实现违背既定设计。
- **决策**：§3.2.1 恢复重建条目补充懒重放遵从句——会话就绪不等待子代理记录流，子代理上下文续作/查看时按需重建且记忆完整。语义无变更（ADR-002 记录流裁决与 ADR-006 恢复时序裁决均不变），技术形状与验收见持久化域 ADR-017 / SDR-005。
- **影响面**：§3.2.1；持久化域 ADR-006/ADR-017、SDR-005。
