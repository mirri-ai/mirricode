## 0. 领域边界

**本域覆盖**（技能的完整功能闭环）：

1. 技能资产的定义与格式（`SKILL.md` 及平铺 Markdown 的契约、参数占位符）；
2. 技能的发现与来源层级（用户级 / 项目级 / 额外目录 / 显式目录 / 插件托管 / 内置，含优先级与合并规则）；
3. 技能内容进入模型上下文的**消费闭环**：系统提示词中的技能列表注入、模型自动调用（Skill 工具）、用户显式调用（斜杠命令，含技能触发符唤起与消息内联引用，见 US3.4 / US3.6）、插件会话启动注入、嵌套技能加载——以及激活后的呈现、事件与遥测；
4. 插件系统本体：插件的安装 / 更新 / 移除 / 启停、marketplace 目录、manifest 契约、信任与安全模型，以及插件的全部贡献面（技能、会话启动技能、技能附加指令、斜杠命令、MCP 服务器**声明**、hooks 声明、插件托管角色目录、插件系统提示词段）——插件是技能与指令的主要分发宿主；
5. 技能相关配置项（额外技能目录、合并开关、启动时显式技能目录参数）。

**本域不覆盖**（引用相邻域，防重叠与缺口）：

- **画像与提示词模板本体**（角色定义、系统提示词渲染管线）归 agent-profile 域；技能列表**如何作为一份内容进入**系统提示词（注入时机、门控条件、注入格式）属本域，衔接点见 US5——两域以「技能目录产出的模型可见清单」为交接物。
- **工具调用的执行管线**（工具注册、调用、结果回传、审批流）归 tool-calling / approval 域；本域只定义 Skill 工具自身的契约（何时可用、参数、门控、注入方式），其作为一个工具的执行与审批走 tool-calling 域的通用机制（见其 US4.12）。
- **MCP 服务器的连接与工具注入**归 mcp 域；本域只覆盖插件对 MCP 服务器的**声明与启停管理**（manifest 字段、按服务器粒度的开关）。
- **子代理机制**归 background-tasks 域；技能对子代理可见性的影响仅经由角色的工具面（见 US5.5），本域不定义派发机制。
- **hooks 的执行机制**（事件触发、进程管理）超出本域；插件对 hooks 的**声明与启用门控**属本域（US6.9）。
- 插件托管的**角色目录**的解析与装配归 agent-profile 域；本域只定义插件作为该目录一个来源的事实（US6.10）。

## 0.1 Personas

| 角色 | 场景 | 核心诉求 |
|---|---|---|
| **技能作者**（写技能的人 / 团队） | 把方法论、流程、规范沉淀为文件 | 格式简单稳定；参数能传；坏文件不连累别人 |
| **技能使用者**（日常干活的人） | 让 agent 按既有方法论做事 | 我写的技能立刻能用；模型该用时自动用；我能随时手动调 |
| **插件作者** | 把技能打包分发给团队或社区 | 一个安装单元带技能+命令+服务；升级有提示 |
| **插件使用者**（装插件的人） | 从 marketplace 或 GitHub 装扩展 | 装得上、看得见信任级别、能关能删；第三方要确认 |
| **观测者** | 弄清技能/插件用没用 | 激活有记录、有事件、可统计 |

## 1. Epic S1：技能资产的定义与创建

> 动机：同一套方法论每次对话都靠粘贴提示词复用，既不可维护也不可分享。技能把它变成一个可发现、可参数化、可分发的文件资产。

### US1.1 技能文件格式（P0）

作为技能作者，我想用一个 Markdown 文件定义一个技能，以便不改任何代码就能扩展 agent 的能力。

- Given 技能以**目录形态**存在（技能目录下有一个名为 `SKILL.md` 的主文件），When 被发现，Then 该目录整体视为一个技能包，同目录的脚本、参考文件等辅助材料随包可用
- Given 技能以**平铺形态**存在（技能根目录顶层的一个 `.md` 文件），When 被发现，Then 技能名取文件名（去掉扩展名），正文即技能内容
- Given 同一目录下同时存在 `<名字>/SKILL.md` 与同名的 `<名字>.md`，When 被发现，Then 目录形态胜出，平铺同名文件被忽略（静默）
- Given 目录形态的 `SKILL.md`，When 解析，Then 它由「头部配置区（两行 `---` 之间的结构化元数据）+ Markdown 正文」组成，两者缺一不可
- Given 平铺形态的 `.md` 文件，When 解析，Then 头部配置区可省略，正文即技能内容

### US1.2 技能元数据字段（P0）

作为技能作者，我想在头部配置区声明技能的身份、用途与调用约束，以便系统决定何时以及谁能使用它。

- Given 目录形态技能，When 未显式提供 `name` 或 `description` 之一，Then 该技能解析失败（见 US9.1 的容错语义），不进入可用列表
- Given 平铺形态技能，When 未提供 `name`，Then 技能名取文件名；When 未提供 `description`，Then 取正文第一个非空行（超过 240 字符截断）；正文为空时用固定占位描述
- Given 头部声明 `type`，When 其值为 `prompt` / `inline`（两者同义，`prompt` 为缺省）之一，Then 技能既可被用户调用也可被模型自动调用；When 为 `flow`，Then 只能由用户显式调用（模型侧被硬拦截，见 US4.3）；When 为 `reference`，Then 技能受支持并注册（出现在技能清单查询中），但**既不可被用户激活也不可被模型调用**——它是被动加载的素材（如插件会话启动注入可加载它）；When 为上述四种之外的其他值，Then 该技能被跳过并记录跳过原因，不中断其他技能
- Given 头部声明 `whenToUse`（兼容连字符与下划线两种变体写法），When 技能进入模型可见列表，Then 该字段随列表呈现，帮助模型判断何时调用
- Given 头部声明 `disableModelInvocation: true`（兼容连字符与下划线两种变体写法），When 模型尝试经 Skill 工具调用，Then 被硬拦截并返回「只能由用户触发」的错误（见 US4.3）；用户斜杠调用不受影响
- Given 头部声明 `arguments`（字符串数组或空格分隔的字符串），When 用户或模型带参调用，Then 正文中同名占位符按声明顺序取值（见 US1.4）
- Given 头部声明子技能开关为真（三种写法：连字符、驼峰、嵌套在头部 `metadata` 子表内任一），When 扫描该技能目录，Then 其子目录里的技能被发现并注册为「父名.子名」的子技能；未声明时子目录技能不被发现
- Given 子技能，When 构建模型可见技能列表与用户斜杠命令，Then 子技能不单列（不在模型列表中；斜杠命令用裸名）
- Given 技能名大小写不同的两个技能，When 以任何途径（斜杠、模型调用）指名，Then 名称匹配不区分大小写
- Given 技能正文包含 mermaid / d2 图表代码块，When 解析，Then 图表内容被单独提取为技能定义的组成部分（供技能内部流程描述使用）

### US1.3 技能参数占位符（P0）

作为技能作者，我想在正文中声明参数占位符，以便一个技能适配不同输入复用。

- Given 调用技能时携带参数串，When 正文含 `$ARGUMENTS`，Then 该占位符展开为完整原始参数串（内容转义后注入）
- Given 参数串按空白分词（单引号或双引号包裹的连续内容算一个词），When 正文含 `$1`、`$2`… 或 `$ARGUMENTS[1]` 等位置占位符，Then 按分词结果零起始填充；越界占位符展开为空
- Given 头部声明了命名参数，When 正文含 `$<参数名>`，Then 按声明顺序对位填充
- Given 正文含技能目录占位符，Then 展开为该技能文件所在目录（供正文引用随包分发的脚本/参考资料）；Given 正文含会话标识占位符，Then 展开为当前会话标识
- Given 正文不含任何参数占位符，但调用携带了参数，When 渲染，Then 参数串以 `ARGUMENTS:` 行追加在正文末尾（参数不丢失）
- Given 所有参数值，When 注入模型上下文，Then 均经内容转义（防参数内容被解释为标记）

## 2. Epic S2：技能的发现与来源层级

> 动机：个人技能、团队技能、项目技能、官方技能要能共存且不打架；改配置不改代码。

### US2.1 多层来源（P0）

作为技能使用者，我想在不同层放置技能——个人的放家里、团队的放项目里、额外的指个目录，以便按作用域管理。

- Given 未做任何特殊配置，When 发现技能，Then 以下来源全部生效，同名冲突时按**项目 > 用户 > 额外 > 插件 > 内置**的优先级取高者（用户自己配置的额外目录技能胜过插件带来的同名技能）：
  - **用户级**（对所有项目生效）：品牌数据根下的 `skills/` 目录；跨工具共享的 `~/.agents/skills/` 目录
  - **项目级**（对单个项目生效）：项目根下 `.mirri-code/skills/`；项目根下 `.agents/skills/`（项目根 = 从工作目录向上找到第一个 git 仓库根）
  - **额外目录**：配置文件顶层声明的额外技能目录列表（支持绝对路径、`~` 开头、相对项目根解析）
  - **插件托管**：已启用插件声明的技能目录（见 US6）
  - **内置**：随产品分发的官方技能（优先级最低，可被任何用户层同名覆盖）
- Given 品牌目录组配置（`merge_all_available_skills`，缺省开启），When 开启，Then 品牌目录与通用目录全部参与发现；When 关闭，Then 每组只取第一个实际存在的目录（仅该目录参与发现）
- Given 启动进程时通过参数显式指定一个或多个技能目录，Then 这些目录**完全取代**默认的用户级与项目级发现（作为用户级来源生效）；未指定时默认发现不变
- Given 额外技能目录配置发生变化，Then 对应来源单独重扫，技能目录更新（见 US7）

### US2.2 扫描规则与容错（P0）

作为技能作者，我想保证一个坏技能文件不破坏整个技能系统，以便试错无风险。

- Given 扫描技能根目录，Then 向下递归时跳过 `node_modules` 与以点开头的子目录；顶层的技能文件命中不受此过滤影响（点开头的平铺文件与点开头目录里的 `SKILL.md` 仍会被注册——命名约定不作为隐藏机制）；目录递归深度上限为 8 层
- Given 技能根目录顶层的平铺 `.md`，Then 只在顶层识别（子目录里的散 `.md` 不算技能，除非按子技能规则下钻）
- Given 插件托管的技能根目录，Then 根目录自身的 `SKILL.md` 也算一个技能（单技能插件形态）
- Given 某个技能文件解析失败（缺字段、坏配置区、不支持的类型），When 扫描，Then 仅该技能被跳过：类型不支持记入「按策略跳过」清单（带原因），解析错误记入警告日志；扫描继续，其余技能正常注册
- Given 技能根目录在项目工作区之外（如用户级、额外目录），When agent 使用文件工具，Then 技能目录对文件读写工具可访问（技能随包分发的脚本与参考文件可被读取、执行引用）

### US2.3 内置技能（P1）

作为新用户，我想开箱即得一组常用工作流技能，以便不写任何文件就体验到技能能力。

> 逐技能需求规格（触发与门控、功能闭环、共享安全范式、依赖面、验收标准）见 [skills-builtin-skills.md](skills-builtin-skills.md)——本节只保留总纲。

- Given 全新安装，Then 以下内置技能可用且模型/用户按各自权限调用：配置 MCP 服务器、导入第三方 CLI 配置、修改产品配置、定制 TUI 主题、撰写目标、子技能工作流（含两个子技能）
- Given 部分内置技能声明了「禁用模型自动调用」，When 模型尝试调用它们，Then 被拦截（这些技能只响应显式调用）
- Given 用户在更高层放了同名技能，Then 内置版本被覆盖

## 3. Epic S3：用户显式调用技能

> 动机：方法论有些是「我要用的时候才用」——用户要一个确定性的入口，而不是等模型自己想到。

### US3.1 斜杠命令（P0）

作为技能使用者，我想用斜杠命令直接调用一个技能并可带参数，以便确定性触发而不依赖模型自觉。

- Given 技能已发现且属于用户可调用类型（`prompt` / `inline` / `flow`），When 用户在输入框输入 `/技能名` 或 `/skill:技能名`（两种写法等价解析），Then 触发该技能；消息内任意位置的内联引用触发见 US3.6（混合消息内只有内联引用块是结构化执行单元，首位手打斜杠命令在混合消息中按普通文本处理）
- Given 内置技能或子技能，When 生成斜杠命令，Then 使用裸名（不带 `skill:` 前缀）；其他来源技能使用 `skill:` 前缀——前缀差异只影响命令命名与解析语法，不影响触发语义；菜单呈现层不以该前缀渲染技能条目（改以统一技能图标为视觉前缀，见 US3.5）
- Given 斜杠命令自动补全菜单，Then 全部可操作选项**分组呈现**：命令组（内置命令 + 插件命令）在前为第一优先级，技能组（全部用户可调用技能，内置技能优先排序）在其下，两组带可区分的组标题；技能条目以统一技能图标为视觉前缀、技能裸名与描述呈现，无描述时显示中性占位文案（不渲染符号残留）
- Given 斜杠命令自动补全菜单处于过滤状态（用户输入了过滤词），Then 命令与技能一起参与匹配排序，命中结果仍按两组呈现（命令组在前）
- Given 会话被切换、重载或新建，Then 技能命令清单随之刷新（新目录里的技能立即可补全）；刷新失败时保留旧清单且不中断会话
- Given agent 正在输出回复（流式中）或正在整理上下文（压缩中），When 用户输入技能斜杠命令，Then 被拦截并提示先终止当前动作（Esc / Ctrl-C 或等待整理完成）
- Given 技能激活成功，Then 用户看到一张激活卡片：技能名 + 参数预览（超长截断），并在会话历史重开/回放时同样可见
- Given 用户斜杠激活了技能，When 用户执行撤销，Then 该激活与其后对话构成可撤销单元（激活是撤销锚点）
- Given 技能激活作为会话内首条用户输入，Then 该会话以「/技能名 + 参数」命名（会话获得可识别标题）

### US3.2 激活的排队语义（P0）

作为技能使用者，我想在回合运行中发起技能调用而不丢输入，以便连续指挥。

- Given 当前有回合正在运行，When 用户发起技能激活，Then 激活请求进入排队（不丢、不中断运行中回合），界面呈现「已排队」状态；前一回合结束后激活自动开始
- Given 技能渲染内容发生在排队出队时刻（而非入队时刻），Then 参数按出队时的会话上下文展开（会话标识占位符等取真实值）
- Given 排队中的激活，When 服务侧返回，Then 明确告知排队状态（排队中 / 已开始）
- Given 经程序接口同步等待激活启动，When 排队项最终未能启动回合（如被取消），Then 返回「回合运行中无法激活」的明确错误

### US3.3 多端入口（P0）

作为用户，我想在终端与网页用一致的方式调用技能，并让程序侧能查询技能清单。

- Given 网页端对话输入框输入 `/`，Then 弹出命令菜单并按 US3.1 的分组规则呈现（命令组在前、技能组在后），选中后命令留在输入框供追加参数
- Given 网页端对话输入框输入技能触发符（US3.4），Then 弹出纯技能候选；选中后依输入框状态回填：为空时回填规范斜杠命令供追加参数，已有内容时在光标处插入内联引用块（US3.6）
- Given 网页端当前无会话，When 用户以技能命令发出首条消息，Then 先创建会话再执行激活，激活消息照常呈现
- Given 网页端正在运行回合，When 技能激活被排队，Then 消息以「暂驻」状态呈现，激活实际开始后转为正常呈现
- Given 程序接口查询技能清单（REST 提供会话级与工作区级两个专属口径；RPC 以会话口径为主，工作区场景由客户端复用会话口径调度），Then **会话级**返回该会话可见的全部技能（含来源与类型标注）；**工作区级**（尚无会话时）返回「该工作区新建会话将看到的」清单——两口径对同一工作目录结果一致
- Given 程序接口（REST / RPC）对会话发起技能激活（技能名 + 可选参数），Then 校验通过后返回激活受理结果（含排队/运行状态）；未知会话、未知技能、不可激活类型分别返回可区分的错误（见 US9）
- Given 程序接口以带插件命名空间的技能名发起激活，Then 命名解析语义与模型调用一致（按插件命名空间解析）；解析后仍走用户激活的既有校验（类型门控等），激活呈现回显正式名

### US3.4 技能专用触发符（P0）

作为技能使用者，我想用一个专门的触发符唤起纯技能候选，以便装了很多技能时不必在混排的命令长列表里翻找技能。

- Given 光标位于输入串首位、或紧随空白字符之后，When 输入技能触发符且其后尚未输入空白，Then 弹出技能候选列表，仅含用户可调用技能（不含内置命令与插件命令），内置技能优先排序；已被用户停用的技能不出现在候选中
- Given 触发符为全角货币符（`¥` / `￥`），Then 与 `$` 等价触发——中文输入法下无需切换到英文态即可唤起技能候选
- Given 技能候选列表中的技能条目，Then 以统一技能图标（US3.5）为视觉前缀、以技能裸名与描述呈现（无描述时显示中性占位文案），不以 `skill:` 文本前缀形态呈现
- Given 用户从技能候选中选中一个技能，Then 依输入框状态回填：为空时回填为该技能的规范斜杠命令（按 US3.1 命名规则：内置技能裸名、其余 `skill:` 前缀）并追加一个空格、光标置于末尾，供继续输入参数；已有内容时在光标处插入内联引用块（US3.6）——**触发符只是唤起候选的输入辅助，不引入新的执行语法**
- Given 用户直接发送以 `$` 开头的文本且未从候选中选中条目，Then 按普通消息处理（不解析、不激活任何技能）
- Given 技能候选列表已弹出，When 用户继续输入字符，Then 按技能名对候选做过滤匹配（以技能裸名为匹配依据，不受 `skill:` 前缀干扰）

### US3.5 统一技能图标（P0）

作为用户，我想在所有界面看到同一个代表「技能」的图标，以便形成稳定认知——看到它就知道这是技能。

- Given 产品内任何代表「技能」这一概念的条目、区块标题或分组标识，Then 均使用统一的技能图标；同一图标在网页与终端以各自渲染能力呈现同形视觉标识，不得各端自选
- Given 统一技能图标必须覆盖的表面，Then 至少包括：输入框候选列表（斜杠菜单技能组与技能触发符候选）、设置与管理界面的技能相关区块与条目（技能设置页、插件详情中的技能目录、工具分组中的技能组）、技能激活呈现（激活卡片/消息与技能调用展示）
- Given 命令（内置命令与插件命令），Then 不使用技能图标——图标只标识技能，与命令的视觉标识不得混用
- Given 技能图标的字形，Then 以架构文档登记的单一资产为唯一来源（各端引用同一资产，不各自绘制）

### US3.6 消息内联多技能 / 多命令注入（P0）

作为技能使用者，我想在一条消息的任意位置引用一个或多个技能（或斜杠命令），与普通文本混排，发送后一次性全部生效，以便用一句话自然语言组织多个技能的工作，而不必拆成多条纯命令消息、也不必依赖模型自己想到去调 Skill 工具。

**内联引用块（用户可见形态）**

- Given 用户在输入框插入一个内联引用块，Then 输入中与发送后的消息里均以**内联芯片**呈现：技能芯片用统一技能图标（US3.5）+ 名称，命令芯片用命令视觉标识 + 名称，二者不混用；删除芯片以整体为单位（光标进入底层文本的处理见下文降级条目）
- Given 内联引用块的目标，Then 既可以是技能，也可以斜杠命令（内置命令与插件命令）
- Given 内联引用块的底层文本形态，Then 为消息文本自身携带的**行内链接**（技能指向其文件路径，命令指向其名字），输入框在光标处渲染为芯片（用户不手写链接语法）；底层形态的规范名见 glossary SK7，解析与注入的技术形状归 [skills-architecture.md](skills-architecture.md)
- Given 手动编辑底层文本（改写链接文字、删触发符、直接手写或粘贴同形态链接），Then 按「文本形态判定」处理——该文本只要满足解析形态即具备激活资格，菜单插入只是主产生路径（误触发面由触发符前缀 + 合法目标双重条件收窄，属可接受残余风险，见 SDR-005）

**触发与插入（输入中）**

- Given 光标位于输入串首位、或紧随空白字符之后，When 用户输入 `/` 或技能触发符（US3.4），Then 弹出候选菜单：`/` 唤起全部可操作选项（US3.1 分组），触发符唤起纯技能候选（US3.4）；从菜单选中条目后，在光标处插入内联引用块（芯片）并自动补一个尾随空格，光标落在空格之后，用户可继续输入普通文本或再次触发插入
- Given 输入框内已有芯片，Then 芯片之后的文本位置仍满足「紧随空白之后」的触发条件（芯片本身等价于一个词）；芯片之间的连续空格在发送时收敛为一个分隔空格（不影响指令语义，仅整洁）
- Given 光标不满足触发条件（位于词内或紧贴非空白字符），When 输入 `/` 或触发符，Then 不弹菜单（按普通字符处理）——防止用户在代码片段、URL、路径中间打 `/` 时被菜单打断
- Given 输入框为空时首位触发，When 选中技能条目，Then 与 US3.1/US3.4 的现状语义一致：回填规范斜杠命令（裸输入框、单技能、可追加参数）——首位触发的**命令回填规则不变**，内联化只作用于「消息已有其他内容」的场景
- Given 消息中已存在内联引用块，When 用户在首位继续输入以 `/` 开头的完整斜杠命令并直接发送，Then 该消息按混合消息处理（见下文「发送与执行」），首位命令不单独拦截为命令执行——混合消息内**只有内联引用块是结构化执行单元**，其余均为普通文本
- Given 用户从消息中主动移除全部内联引用块，Then 发送时按纯文本消息处理（不激活任何技能、不执行任何命令）

**发送与执行（多技能同一轮直达）**

- Given 一条混合消息（普通文本 + 一个或多个内联引用块），When 发送且当前无进行中回合，Then 该消息自起一个新回合，引擎解析全部内联引用块：
  - 技能块 → 解析、校验（含门控与停用，错误路径走 US9.1），技能全文经「技能已加载」包裹（US5.1）注入该回合上下文——**模型无需调用 Skill 工具**；
  - 命令块 → 按下文「命令块的执行」执行；
  - 消息正文（去除引用块后的普通文本）作为用户意图一并送达模型
- Given 发送时有回合正在运行，When 用户发送混合消息，Then 沿用普通用户消息的接纳语义（整条消息排队进下一回合，不并入运行中回合），引用块在消息实际进入回合时再解析（排队期间技能状态变化如实反映，不做提交时刻的快照）
- Given 同一条混合消息引用多个技能，Then 各技能按引用块在消息中的出现顺序依次注入，注入前以一句话声明用户在消息中激活了这些技能（与 US5.1 用户斜杠激活的声明语一致：用户主动激活，请遵循其指引）
- Given 一条混合消息内的全部技能激活构成**一个可撤销单元**（对该消息整体一次撤销回到发送前），其中的每条激活事实仍是独立记录（回放、遥测、激活卡片逐条呈现）——多激活的撤销粒度是消息整体，不是逐个激活回退
- Given 内联引用块指向的技能不存在、不可激活或已停用，Then 该块**不静默失败**：消息发送前输入框给出可定位的警示反馈（块内定位 + 原因方向），用户可选择移除后重发或带警示发送；带警示发送时该块降级为普通链接文本，**用户视图**呈现普通链接（可点击跳转），**模型上下文**保留该链接文本（无技能全文注入）并附一句失败原因说明（模型可据提示向用户解释，错误语义与 US9.1 一致）
- Given 同一条混合消息中同一技能被引用多次，Then 只注入一次（重复引用折叠为单次激活）；折叠以解析后的技能为准，同名不同层时以引用块携带的技能文件路径为解析权威（路径指向哪个副本就激活哪个副本），路径失效则按上一条的失败语义处理
- Given 混合消息激活的技能参与既有观测闭环，Then 激活事实、激活卡片（含触发方式标注，触发方式标注为用户斜杠族的新成员「用户消息内联」）、遥测与撤销锚点语义均与用户斜杠激活一致（US5.1 / US5.2 / US8.1 / US8.2）——排队语义不适用 US3.2（那是独立技能激活的排队，内联激活随消息本身的回合接纳走）

**命令块的执行**

- Given 混合消息中的命令块，When 消息被接纳进回合，Then 命令块不进入模型上下文，由提交端（客户端界面）在消息发送时刻**先行分发**到命令执行面——命令执行先于技能注入与正文送达（命令的执行语义、作用域与失败路径归其自身所属域，本域只定义「经内联引用块触发」这一入口与触发来源标注）
- Given 命令块与技能块混排，Then 两者互不阻塞：命令执行不等待技能注入，技能注入不等待命令结果——但**清理类命令**（清空历史、整理上下文一类）例外：清理类命令块与技能块混排时，发送前警示反馈明示两者互相冲突（清理会丢弃同消息的技能激活），用户须移除其一或改为分条发送
- Given 命令块指向的命令不存在或不可经内联触发，Then 与技能块同等的失败路径：发送前警示（可移除或带警示发送，带警示发送时降级为普通链接文本）

**历史与回放**

- Given 混合消息进入会话历史，Then 引擎接纳时的处理结果被持久化：正文以标记形态保存（激活成功的引用处替换为可读的技能名标记，技术形状见架构文档），并随附一份激活清单记录（US3.7）；会话恢复与回放时依据清单重建芯片呈现（不重复触发激活与遥测），与用户斜杠激活的回放语义一致（US5.2）
- Given 会话在其他客户端打开（如终端），When 该客户端不识别激活清单记录，Then 引用处按正文里的技能名标记呈现（纯文本可读、不可点击），不报错、不中断渲染；识别清单的客户端可按各自渲染能力重建芯片或高亮
- Given 混合消息为会话内首条用户输入，Then 会话命名仍取正文普通文本（无正文时取首个引用块的名称），与既有「首条输入命名」规则一致

**作用域**

- Given 本条需求，Then 以网页端为第一落点；终端端降级语义（上一条）与输入体验对齐属终端域后续裁决

## 4. Epic S4：模型自动调用（Skill 工具）

> 动机：让模型在「技能描述与当前任务匹配」时自己加载方法论，用户不必每次提醒。

### US4.1 技能列表注入（P0）

作为用户，我想让模型知道有哪些技能可用，以便它主动用而不是我提醒。

- Given 当前 agent 的工具面包含 Skill 工具，When 构建系统提示词，Then 注入当前可用技能清单：仅含可被模型调用的技能（排除禁用模型调用的、flow 型与素材型（reference）的、子技能），按来源分组（项目 / 用户 / 额外 / 内置），每条含名称、描述（超长截断）、可选的「何时使用」、技能文件路径
- Given 技能清单首行，Then 声明其取代会话历史中的任何更早技能清单（模型以最新一份为准，不混淆新旧清单）
- Given 系统提示词中技能段说明文字，Then 向模型说明：技能是可复用能力包；按需读取；同名时按「项目 > 用户 > 额外 > 内置」的更具体来源优先——供模型向用户解释技能来源与消歧
- Given 技能清单为空，When 构建系统提示词，Then 不注入技能段（不留空标题残留）
- Given 技能在会话进行中被新增/移除（目录变更、插件重载），Then 新回合的技能清单随之更新

### US4.2 Skill 工具契约（P0）

作为模型，我想通过一个具名的 Skill 工具按需加载技能全文，以便只在需要时占用上下文。

- Given 工具面包含 Skill 工具，When 模型判断技能清单中某技能与用户请求匹配，Then 必须调用该工具（而非自由发挥文本），工具描述中以此作为强制要求声明
- Given 模型调用 Skill 工具，When 参数为技能名（须与清单中拼写一致，不区分大小写）+ 可选参数串（命令行风格，按 US1.3 展开），Then 技能全文以一条用户角色的转向消息注入**当前回合**的上下文（模型当轮即可遵循，无需等下一回合）
- Given 模型调用的技能名带插件命名空间（`插件id:技能名` 形态——插件技能文档与从其他生态导入的技能常以此形态交叉引用），When 该插件确实提供了同名技能，Then 与裸名调用等效：正常加载注入；激活记录、事件与激活卡片呈现回显该技能的正式名（裸名，不带前缀）；工具调用的输入展示仍回显原始输入（与其他工具一致）
- Given 带命名空间的技能名解析失败（插件未提供该技能，或前缀不是任何已装插件），When Skill 工具执行，Then 返回与「清单中不存在」一致的错误结果（回显原始输入名）
- Given 限定名解析成功的技能属于禁模型调用、非模型可调用类型或被用户停用，When Skill 工具执行，Then 返回对应的门控/停用错误（而非「清单中不存在」），错误回显原始输入名——解析先于门控，门控语义与裸名调用完全一致
- Given 同一技能、相同参数的已加载块已存在于对话中，Then 工具描述指示模型不得重复调用（直接遵循已加载内容）；参数不同时则需重新调用（已加载块按旧参数展开，不反映新输入）
- Given Skill 工具调用成功，Then 模型收到「技能已内联加载，遵循其指引」的结果，用户侧看到结构化的技能调用展示（含技能名与参数）
- Given Skill 工具调用，When 审批规则按技能名匹配（支持通配），Then 与其他工具调用走同一审批通道（审批流本体归 approval 域）
- Given agent 的工具面不含 Skill 工具（如某些只读型子代理），Then 该 agent 既无 Skill 工具也无技能清单注入（见 US5.5）

### US4.3 调用门控（P0）

作为技能作者，我想控制谁能调用我的技能，以便流程型技能不被模型滥用。

- Given 调用的技能不存在于当前技能清单，When Skill 工具执行，Then 返回「清单中不存在」的错误结果（带技能名），不产生注入
- Given 技能声明禁用模型调用，When Skill 工具执行，Then 返回「只能由用户触发」的错误结果，不产生注入——拦截点在工具执行环节（硬强制，先于内容注入）
- Given 技能类型为 flow 或 reference，When Skill 工具执行，Then 返回「不可被模型调用」的错误结果（仅 inline/prompt 型可被模型调用）
- Given 放行对称性：技能未声明禁用且类型为 inline/prompt，Then 模型调用不受额外限制

### US4.4 嵌套深度防护（P1）

作为系统，我要防住技能互相引用导致的无限递归，以便一次失控不烧穿预算。

- Given 模型在已加载技能内容的指引下再调用另一个技能（嵌套技能），Then 允许，但嵌套深度上限为 3 层
- Given 嵌套链达到深度上限仍要继续，Then 拒绝继续加载并给出明确错误（拒绝再递归）
- Given 不同触发路径（用户斜杠 / 用户消息内联 / 模型工具 / 嵌套），When 技能激活被记录，Then 触发方式被如实标注（四态之一）

## 5. Epic S5：技能内容的注入形态与门控

> 动机：技能全文常驻系统提示词会撑爆上下文——注入必须是「清单常驻、全文按需」的两级结构，且注入点有明确门控。

### US5.1 激活注入的统一包裹（P0）

- Given 技能被任一路径激活（用户斜杠 / 用户消息内联 / 模型工具 / 嵌套），When 技能全文注入，Then 以统一的「技能已加载」包裹块呈现，属性如实标注：技能名、触发方式、来源层级、技能目录、参数（存在时）
- Given 用户斜杠激活，Then 注入前附带一句「用户激活了该技能，请遵循其指引」
- Given 模型工具 / 嵌套激活，Then 注入前附带一句「技能工具为本请求加载了指引，请遵循」
- Given 插件托管的技能，When 渲染技能内容，Then 若该插件声明了技能附加指令，则附加指令以独立的插件指令前缀块置于技能正文之前

### US5.2 会话内激活记录（P0）

- Given 技能激活发生，Then 会话记录中获得一条激活事实（技能名、触发方式、类型、路径、来源、参数），由此派生激活事件（供各端呈现）并在会话恢复/回放时重建激活卡片而不重复触发遥测
- Given 会话回放，When 遇到激活事实，Then 回放为激活卡片（历史一致性），不产生新的激活副作用

### US5.3 技能清单与工具面的联动门控（P0）

- Given agent 的工具面含 Skill 工具，Then 技能清单注入（US4.1）；Given 不含，Then 清单与注入段整体缺失——**可见性与可用性同门**：没有入口就没有清单，不存在「看得见列表却调不了」的状态
- Given 用户通过配置禁用 Skill 工具（全局工具启停配置），Then 所有会话不再有技能清单注入与自动调用（用户斜杠调用仍可用——斜杠不走工具面）

### US5.4 模型可见性的刷新一致性（P1）

- Given 技能目录在会话进行中变化（新增/删除/修改文件），Then 变化经短暂静默期（防止连续写文件期间反复扫描）后只重扫受影响的来源，新回合的技能清单与斜杠命令一致更新
- Given 会话恢复（进程重启后重开），Then 技能目录按当前磁盘状态重建，与该工作区新会话所见一致

### US5.5 子代理的技能可见性（P1）

- Given 派发的子代理所装配的角色工具面含 Skill 工具，Then 该子代理与主 agent 共享同一份会话技能目录（技能清单一致）
- Given 角色工具面不含 Skill 工具（如只读侦察型子代理），Then 该子代理不可见技能清单、不能调用 Skill 工具——技能对子代理的可见性完全由其角色工具面决定，无独立的子代理技能配置

## 6. Epic S6：插件系统（技能与能力的分发宿主）

> 动机：技能要跨团队、跨机器分发，还需要带 MCP 服务与命令——插件把它们打包成一个可安装、可信任、可升级的单元。

### US6.1 安装来源与流程（P0）

作为插件使用者，我想从本地目录、zip 包或 GitHub 仓库安装插件，以便一条命令获得整套能力。

- Given 一个本地插件目录路径，When 安装，Then 校验其 manifest 后，插件被复制到用户数据根下的托管目录，之后始终从托管副本运行（修改原目录不影响已装插件；升级 = 用同 id 重装，覆盖托管副本）
- Given 一个 zip 下载地址，When 安装，Then 下载（有超时上限）→ 解压 → 定位插件根（包一层目录时自动下钻）→ 校验 manifest → 落托管目录；下载/解压/校验任一失败则安装失败且不留半成品（回滚）
- Given 一个 GitHub 仓库地址，When 安装，Then 支持四种形态：裸仓库（最新 release，无 release 回退默认分支）、`/tree/<分支|标签|短 SHA>`、`/releases/tag/<标签>`、`/commit/<完整 SHA>`；网络请求只经 github.com 跳转与 codeload 下载，不触碰 API 配额；无法解析（仓库不存在等）时给出明确错误
- Given zip 内容，When 解压，Then 路径穿越攻击被阻止（所有解压目标必须落在目标目录内），文件权限位保留
- Given 安装成功，Then 安装记录被持久化（整体替换式写入——中途故障不产生半成品记录；记录损坏时给出明确的加载失败错误而非静默清空）；重装同 id 保留既有的启用状态、安装时间与用户偏好

### US6.2 marketplace 目录（P0）

作为插件使用者，我想浏览官方与第三方插件目录，以便发现并一键安装。

- Given 打开插件管理面板，Then 含四个标签页：**已安装**（管理现状）、**官方**（产品方维护的目录插件）、**第三方**（其他发布者的目录插件）、**自定义**（直接从 URL / 本地路径安装）；标签间用 Tab / Shift-Tab 切换
- Given 目录数据（一个 JSON 清单：插件条目 = id + 安装源，可选展示名、版本、描述、关键词、分级；安装源与展示名均接受别名键；条目可声明类型字段——当前类型及两个遗留别名均被接受），When 需要时，Then 自动加载（默认官方地址，可被环境变量或命令参数覆盖为自定义地址——支持 http/https、file://、本地路径）；默认地址加载失败时回退到随产品分发的本地目录
- Given 目录条目，Then 按分级归入对应标签页（官方 / 精选两级分级；未分级的进第三方页）
- Given 自定义目录源，When 浏览，Then 落在第三方标签页
- Given 目录 JSON 格式错误，Then 给出可定位的解析错误（哪个条目缺什么字段）
- Given 目录条目未声明版本，When 其源是 GitHub 且 URL 内含版本形状（release tag / tree 引用），Then 版本从 URL 推导；裸仓库 URL 则查询最新 release（避开 API 配额）作为最新版本

### US6.3 信任与确认（P0）

作为插件使用者，我想在安装非官方内容前被明确告知信任级别，以便知情决策。

- Given 每个已装/可装插件，Then 呈现信任徽章：官方地址来源（官方徽章）、精选地址来源（精选徽章）、其余一切（第三方徽章）
- Given 安装第三方插件（任何非官方地址，含自定义标签页安装），When 安装，Then 先弹确认提示且默认选项为「取消」——只有用户主动选择信任才继续安装
- Given 官方地址来源，Then 安装不弹确认（隐式信任）

### US6.4 更新管理（P1）

作为插件使用者，我想知道插件有没有新版本并一键升级。

- Given 已安装插件有更新的 marketplace 版本（按版本号比较，仅双方版本号格式均合法时判定，避免误报或误降级），Then 已安装页显示更新徽章
- Given 已安装页对有更新的插件按安装键，Then 执行更新（重装同 id 覆盖托管副本，保留用户偏好）
- Given GitHub 来源插件，When 检查更新，Then 对分支引用与裸仓库比较安装时记录的提交与来源当前指向，提示是否有新版；**固定到标签或提交的引用视为冻结**（不比较、不提示更新）；无版本信息时判定为「未知」，不误报「已是最新」
- Given 插件不自动更新——更新永远是用户显式动作

### US6.5 启停与移除（P0）

作为插件使用者，我想随时停用或移除一个插件，以便控制它对我环境的影响。

- Given 已装插件，When 停用，Then 其全部贡献面失效（技能、命令、MCP 服务器、hooks、会话启动注入、系统提示词段）；重新启用后恢复
- Given 已装插件，When 移除（需确认），Then 安装记录删除；磁盘上的托管副本保留（移除不删文件，重装可恢复）
- Given 插件声明的某个 MCP 服务器，When 单独停用/启用它（其他服务器不受影响），Then 生效于下次重载/新会话；已记录的每服务器偏好（含工具过滤）跨启停保留
- Given 插件变更（安装/启停/移除），Then **下一会话或用户手动重载后生效**——当前运行中的会话不变更（变更提示明确告知需要重载或新会话）
- Given 用户手动重载插件，Then 系统重新读取安装记录与全部 manifest，报告新增数 / 移除数 / 错误数

### US6.6 manifest 契约（P0）

作为插件作者，我想用一份 manifest 声明插件的全部贡献，以便一次配置全量生效。

- Given 插件根目录，Then manifest 按候选文件优先级查找（产品规范名 > 兼容旧名 > 生态兼容名），多处存在时取最高优先级并在**同族命名**（同一命名体系的根文件与目录形态）内提示被遮蔽者；跨命名体系并存时静默取高优先级；完全没有 manifest 则该插件进入错误态（诊断呈现，不影响其他插件）
- Given `name`（插件 id），Then 必填且须符合「小写字母数字开头，限小写字母/数字/连字符/下划线，至多 64 字符」；id 不区分大小写归一
- Given `skills`（一个或多个 `./` 相对路径），Then 每个路径经软链接追踪后必须落在插件根目录内（越界记错误级诊断——错误级诊断使**整个插件**进入错误态，见本条末句）；指向非目录记为警告（插件照常加载）；**未声明 skills 时，插件根目录自身的 `SKILL.md` 被视为单个技能根**（单技能插件）
- Given `sessionStart.skill`（技能名），Then 新会话或恢复会话启动时，将该插件技能加载进主 agent（见 US6.8）
- Given `skillInstructions`（文本），Then 该插件的任何技能被加载时（无论经会话启动、用户斜杠还是模型调用），附加指令随技能正文呈现
- Given `commands`（一个或多个 `./` 路径，指向目录或 `.md` 文件），Then 目录下全部 `.md` 递归注册为斜杠命令，命令名以插件 id 为命名空间（`/插件id:命令名`），命令文件头部可声明 `name`（覆盖按路径推导的名字）与 `description`，正文支持**完整参数串**占位与无占位符时的追加规则（与技能占位符族的这两条规则相同；技能的位置参数、命名参数与目录/会话占位符对命令不生效）
- Given `mcpServers`（按名声明，复用 MCP 配置契约），Then stdio 服务的命令与工作目录可使用插件根内的 `./` 相对路径（越界即拒绝）；运行时以 `plugin-<插件id>:<服务器名>` 形态的全名注册（无歧义）；MCP 声明的服务器默认启用、可逐个停用
- Given `hooks`（规则数组，字段与全局 hooks 一致），Then 仅在插件启用期间生效；hook 进程以插件根为工作目录运行并携带产品主目录与插件根两个环境变量
- Given 插件托管的**角色目录**（声明 `agents` 路径，或存在约定的 `agents/` 目录时自动采纳），Then 该目录作为角色来源层之一被装配（装配机制归 agent-profile 域）
- Given `systemPrompt`（内联文本或文件路径声明），Then 已启用插件的内容以「插件指令段」并入主 agent 系统提示词；该段被明确标注为**非特权指令通道**：不得凌驾系统指令或用户直接指令，冲突时系统指令胜出；体积超限记为警告诊断
- Given 展示元数据（`interface` 的显示名、简介、详情、开发者、主页等；`version`、`description`、`keywords`、`author`、`homepage`、`license`），Then 用于插件列表与详情页呈现
- Given manifest 声明了不支持的运行时字段，Then 记为提示级诊断（不执行、不报错）——manifest 校验以诊断呈现而非整体失败：错误诊断使插件进入错误态（贡献面不生效），警告/提示不影响加载

### US6.7 安全模型（P0）

作为插件使用者，我想安装与加载插件不执行任意代码，以便默认安全。

- Given 安装插件（任何来源），When 安装过程，Then 不执行插件内的任何命令或运行时（hooks 只在启用期间由匹配事件触发，MCP 服务器在重载/新会话后启动——安装动作本身零执行）
- Given manifest 中的路径类字段，Then 经软链接追踪后必须落在插件根目录内（防越界引用）
- Given 某插件 manifest 损坏或路径不安全，Then 该插件单独进入错误态并在详情页呈现诊断，不影响其他插件与其他会话

### US6.8 会话启动注入（P1）

作为插件作者，我想让技能在会话一启动就生效，以便初始化规则与术语映射始终在场。

- Given 已启用插件声明了会话启动技能，When 新建或恢复会话且主 agent 装配完成，Then 该技能全文以会话启动注入块进入主 agent 上下文（仅主 agent，子代理不注入）
- Given 同一会话，When 注入已发生，Then 不重复注入（每会话一次）
- Given 插件在会话中被重载，When 其会话启动技能集合变化，Then 追加一条新的注入块并声明「取代本会话内任何更早的同类注入」；全部移除时追加中性化声明（避免旧注入残留误导）——**失效必声明**，不留过期指令
- Given 声明的启动技能在插件技能目录中找不到，Then 记警告并跳过该插件（不阻断其他插件的注入）

### US6.9 插件 hooks 声明（P1）

- Given 已启用插件声明 hooks 规则，Then 规则与全局 hooks 同机制触发（事件、匹配器、命令、超时），差异仅在于：插件停用即停、工作目录为插件根、附加环境变量——hooks 执行机制本体超出本域（见边界声明）

### US6.10 插件技能的来源归属（P1）

- Given 插件托管的技能，When 进入技能清单，Then 归入「额外」来源层级（低于项目与用户层）；技能被激活时，其插件身份如实标注于激活记录与包裹块属性

## 7. Epic S7：技能目录的动态一致性

> 动机：用户改了技能文件或配置，期望下次对话就用新版——不一致会让人怀疑技能系统根本没生效。

### US7.1 变更传播（P0）

- Given 项目技能目录（含尚不存在的候选目录）内发生文件变化，Then 经短暂静默期后仅重扫项目来源，合并目录更新
- Given 额外技能目录配置变化，Then 仅重扫额外来源
- Given 合并开关（品牌目录合并策略）变化，Then 用户级与项目级两个来源重扫（该开关同时约束两级的品牌目录组行为）
- Given 插件重载，Then 仅重扫插件来源
- Given 任一来源重扫完成，Then 合并目录整体更新并通知订阅方（各会话的技能清单、斜杠命令随之刷新）——重扫是来源级的，永不全量重扫所有来源
- Given 同一工作区的多个会话，Then 共享一份工作区级合并扫描（每来源一次扫描，多会话复用），会话内可再叠加会话本地贡献

## 8. Epic S8：呈现与观测

### US8.1 激活呈现（P0）

- Given 技能激活（任一路径），Then 终端呈现激活卡片（含参数预览，超长截断）；网页呈现「已激活技能」消息（含参数行），并作为回合标题的一部分参与会话列表命名；headless（无界面的命令行一次性执行）模式不呈现激活卡片（事件照常产生）
- Given 模型调用 Skill 工具，Then 与其他工具调用同样呈现结构化展示（类别为技能调用，含技能名与参数）
- Given 会话历史回放，Then 激活卡片与当时一致重现（去重同一激活不重复渲染）

### US8.2 遥测（P1）

- Given 技能激活发生（仅真实激活，非回放），Then 记录一次技能调用遥测：技能名 + 触发方式（用户斜杠 / 用户消息内联 / 模型工具 / 嵌套）
- Given flow 型技能被激活，Then 额外记录一次流程调用遥测（技能名）
- Given 插件命令被激活，Then 同样记录一次插件命令激活事件（含插件与命令标识，供界面呈现与观测）；经内联命令块触发的，事件标注来源为「用户消息内联」
- Given 终端用户经斜杠命令触发技能，Then 本地记录输入命令事件（含技能名）
- Given 会话恢复/回放重放的激活，Then 不重复记录遥测

### US8.3 插件管理呈现（P0）

- Given 插件管理面板（已安装页），Then 每个插件行呈现：显示名、启用状态、更新徽章、id、技能数、MCP 服务器数、来源（本地 / zip / GitHub）、信任徽章、错误标记；版本在文本列表与详情页呈现；hooks 数、命令数与安装/更新时间在详情页呈现
- Given 插件详情页（含 `/插件 详情` 与 `/插件 <id>` 直达两种入口），Then 呈现 manifest 全量展示元数据、版本、技能目录列表、MCP 服务器清单（连接形态、命令、环境变量键名等）、hooks 数、命令数、安装时间与更新时间、诊断（含被遮蔽 manifest 提示）
- Given 已安装页的安装键，Then 行为随状态切换：有更新时装更新、无更新时看详情；官方/第三方页的安装键为安装或更新；自定义页为安装
- Given 斜杠命令 `/插件` 系（打开面板 / 列表 / 详情 / 安装 / 启停 / 移除（确认） / 重载（+N -M E 报告） / MCP 启停 / 浏览目录），Then 每个子命令的用法错误给出用法提示文案
- Given 插件命令（`/插件id:命令名`），Then 在斜杠自动补全中与内置命令、技能命令合并呈现

## 9. Epic S9：错误路径（全局）

> 每条错误路径必须可区分、可定位、不扩散。

### US9.1 技能侧（P0）

- Given 目录形态技能缺必填字段 / 配置区格式非法 → 该技能跳过 + 警告日志（系统其余部分照常）
- Given 技能类型不支持 → 记入按策略跳过清单（带类型与原因，供查询）
- Given 调用的技能不存在 → 用户侧错误「技能未找到」（带名字）；接口侧错误码与「名称为空」共用一类
- Given 技能不可被该途径激活（flow/reference 被模型调用；非用户可激活类型被用户调用）→ 返回「不可激活」错误（带名字与原因方向）
- Given 会话不存在 / 未激活 → 会话级错误（与技能无关，见 session 域），但技能接口须保留该错误透出
- Given 回合运行中用户斜杠激活排队（非错误）→ 状态返回排队
- Given 排队中的激活最终未能启动回合（如被取消）→ 同步等待方收到「回合运行中无法激活」错误（排队本身不报错，见 US3.2）

### US9.2 插件侧（P0）

- Given 安装失败（无 manifest / 下载失败 / 解压失败）→ 明确错误（含来源与原因），不留半成品（回滚到安装前状态）
- Given manifest 校验失败 → 插件进入错误态 + 诊断呈现（US6.6/US6.7），其他插件不受影响
- Given 安装记录文件损坏 → 明确的加载失败错误（不静默清空）
- Given 重载出现个别插件错误 → 重载结果中按插件列出错误，其余照常
- Given 未知插件 id 的操作（启停/移除/详情）→ 明确的未找到错误

## 11. 未来增强提案（超出参照现状）

> 以下均为〔提案〕——尚不存在参照实现的建议（对照见头部「基线性质说明」与 context 差异矩阵），实现与否由 Rust 侧独立裁决；**不得作为现状承诺引用**。各条的「现状」描述仅为提案动机的对照面，不构成需求。

1. **`/skills` 清单命令与技能浏览器**：参照现状无技能总览视图（终端仅斜杠补全、网页仅斜杠菜单）；建议提供清单命令（含来源层级、类型、模型可调性）与分页浏览，辅助发现与排障（如确认坏技能是否被跳过）。
2. **逐技能启停**：参照现状仅能通过改文件或 frontmatter 的 `disableModelInvocation`（只挡模型侧）控制；建议提供技能级（列表内 disable，覆盖用户与项目层）及会话级（临时禁用单个技能）两个粒度的开关，含对称放行语义。
3. **技能管理页（web）**：参照现状 web 端仅有合并开关；建议补齐技能浏览、启停与额外技能目录编辑的管理界面（对齐插件管理的完整度）。
4. **技能创建脚手架**：建议提供创建技能的引导命令（生成骨架 `SKILL.md` + 校验提示），降低作者上手成本。
5. **占位符与环境变量命名统一**：技能目录/会话标识占位符与插件环境变量在新旧两代引擎间存在两套前缀（品牌全名 vs 短名），文档与代码已有漂移；建议 Rust 侧收敛为一套并兼容旧写法。
6. **插件技能的来源标识**：参照现状把插件技能归入「额外」来源，用户无法从列表区分「我配置的目录」与「插件带来的」；建议在对外契约中显式携带插件身份。
7. **技能版本与更新提示**：技能无版本概念（插件有）；若技能从远端分发，建议复用插件更新徽章机制。
8. **技能目录只读沙箱选项**：参照现状技能目录对文件工具可写（供脚本落地）；建议提供「技能包只读」的会话/全局选项，防止会话内误改技能包。
9. **`allowed-tools` 声明**：导入的第三方技能文件中已出现该 frontmatter 概念（提示模型注意）；建议正式定义「技能声明其推荐工具面」，激活时按声明收紧或提示。
10. **技能清单附限定别名**：模型可见清单当前只列裸名（模型按清单拼写为主形态）；建议在插件技能条目上附「插件id:技能名」限定别名提示，让模型优先学会限定形态、减少对容错解析的依赖（SDR-002 备选 3 的落点）。

## 13. 决策记录（SDR）

### SDR-001 · 2026-09-12 · 基线首轮评审修订并入

- **背景与动机**：基线初稿经需求完整性评审（对照代码逐条核验）发现若干断言与参照实现不一致——若不修订，Rust 团队会据错误基线信任「TS 已支持」。
- **决策**：以下条目按代码事实修订为终态表述：
  1. US1.2 技能类型枚举补全 `reference` 语义（受支持注册、用户/模型双不可调、可作插件会话启动素材）；「类型之外」跳过边界改为四种受支持类型之外。
  2. US2.2 扫描过滤语义修正：`node_modules` 与点开头条目仅在**向下递归**时跳过，顶层文件命中不受过滤影响。
  3. US6.6 插件命令的占位符支持范围收窄为「完整参数串占位 + 无占位符追加」两条规则（技能占位符族其余成员不适用）。
  4. US6.4 更新检查：固定到标签/提交的引用视为冻结（不比较不提示）。
  5. US6.6 manifest 遮蔽诊断限定同族命名内生效；skills 指向非目录为警告级（越界仍为错误级）。
  6. US6.2 marketplace 条目契约补记（来源/展示名别名键、类型字段及遗留别名）。
  7. US2.1 优先级链补插件层位置（项目 > 用户 > 额外 > 插件 > 内置）；US7.1 合并开关变更触发用户级与项目级双源重扫。
  8. US3.3 技能清单程序接口补会话级/工作区级两口径（RPC 以会话口径为主）；US8.x 呈现字段按面板行/文本列表/详情页逐层修正并补 headless 与插件命令激活观测边界。
  9. R8 技术词转译为产品语义（整体替换式写入、软链接追踪、短暂静默期、内容转义、版本号格式合法性）。
- **被否决的备选方案**：保留初稿措辞并另附勘误表——否决，理由：基线文档的每个断言都会被直接当作 Rust 对齐依据，正文必须自洽为终态；勘误表式双轨易漂移。
- **影响范围**：US1.1、US1.2、US2.1、US2.2、US3.2、US3.3、US6.2、US6.4、US6.6、US7.1、US8.1–8.3、US9.1、§12。

### SDR-002 · 2026-10-09 · 插件限定名解析增补

- **背景与动机**：生态插件自带的技能文档（以及从其他生态导入的技能与计划文档）以「插件id:技能名」形态交叉引用技能；而调用链此前只认清单裸名——模型按文档指引调用即失败，被迫绕过技能系统自行从磁盘读取技能文件（有真实会话证据：限定名调用返回「清单中不存在」，随后模型直接读盘补救，方法论约束全部旁路）。
- **决策**：US4.2（Skill 工具）与 US3.3（程序接口激活）增加命名空间形态的解析语义：先按裸名解析（现状语义与来源覆盖优先级完全不变），未命中且名称含分隔符时按「插件id:技能名」解析插件技能；限定名指向该插件自己的技能副本（穿透同名遮蔽）。解析成功后激活记录、事件与呈现回显正式名，门控与停用语义不变（解析先于门控）；错误路径回显原始输入名。用户斜杠命令的命名形态不变（斜杠侧另有 `skill:` 前缀语义，不混用）。
- **被否决的备选方案**：
  1. 技能清单改用限定名为主名——否决：所有存量裸名调用、各端呈现与用户心智全部被破坏，而内置/用户/项目技能本无命名空间。
  2. 拒绝限定名、要求模型只按清单拼写——否决：技能正文与第三方文档不受本产品控制，模型遵循文档指引是常态路径，硬拒只会让本缺陷持续复现。
  3. 仅在清单渲染时附限定别名提示——保留为后续增强（可让模型优先学用限定名），但不解决存量文档中的引用，单独采用不闭环。
- **影响范围**：US3.3、US4.2；工具接口契约同步修订（tool-calling 域 Skill 工具节）；机制与已知边界见架构文档 ADR-001。

### SDR-003 · 2026-10-12 · 技能专用触发符与统一技能图标

- **背景与动机**：技能条目与命令混排在同一个斜杠菜单里，且靠 `skill:` 文本前缀做区分——装技能较多的用户在超长列表里翻找技能，可达性差；文本前缀只解决「看得出是技能」，不解决「快速到达技能」。同时技能在各界面（菜单、设置、管理页）没有统一的视觉标识，用户认知无法沉淀。
- **决策**：
  1. 新增技能专用触发符（US3.4）：输入 `$`（全角货币符 `¥` / `￥` 等价）唤起纯技能候选；选中后回填规范斜杠命令——触发符是唤起辅助，不引入新的执行语法，直接发送 `$` 开头文本仍是普通消息。
  2. 定义产品级统一技能图标（US3.5），用于输入候选、设置与管理界面技能条目、激活呈现；菜单中技能条目不再以 `skill:` 文本前缀渲染，改以图标为视觉前缀——`skill:` 前缀仍保留为命令命名与解析语法（US3.1 不变），图标只改变呈现层。
  3. 技能无描述时显示中性占位文案（不渲染符号残留）。
- **被否决的备选方案**：
  1. `$` 作为执行语法（发送 `$技能名 参数` 直接激活）——否决：普通消息以 `$` 开头常见（shell 片段、变量引用），执行歧义与误触发风险高，且与斜杠执行语义形成双轨。
  2. 保留 `skill:` 文本前缀、仅靠分组改善——否决：前缀只解决辨识不解决直达；且文本前缀参与条目名后干扰输入过滤的前缀匹配（用户的输入拼不出前缀就拿不到靠前的排位）。
  3. 各客户端/界面自选图标——否决：破坏统一认知，正是本决策要建立的东西。
- **影响范围**：新增 US3.4、US3.5；US3.1（菜单条目呈现与命名条目）、US3.3（网页菜单描述）修订；架构文档新增 ADR-002；glossary 登记 SK6（技能触发符）。

### SDR-004 · 2026-10-12 · 斜杠菜单的命令/技能分组

- **背景与动机**：`/` 是「全部可操作选项」的统一入口，但技能条目与命令平铺混排——多技能环境下菜单一次倾倒上百条条目，命令（数量少、频次高）的可达性被稀释；新用户打开菜单先面对技能长列表，形成压迫感。既要保留统一入口，又要让命令优先可达，需要一个明确的信息架构。
- **决策**：斜杠菜单维持展示全部可操作选项（命令与技能），但分组呈现（US3.1）：命令组（内置命令 + 插件命令）在前为第一优先级，技能组（用户可调用技能，内置技能优先）在其下，两组带可区分的组标题；过滤状态下命令与技能一起参与匹配，命中结果仍按两组呈现（命令组在前）；**不做折叠与数量上限**——技能洪峰由技能专用触发符（SDR-003）分流，`/` 菜单保持完整可浏览。
- **被否决的备选方案**：
  1. 技能区折叠 +「显示全部」入口——否决：与专用触发符双轨冗余；折叠态需多一次交互才能看全，且阈值是无依据的拍脑袋参数。
  2. `/` 只展示命令、技能全部走触发符——否决：破坏「`/` = 全部可操作入口」的统一心智，存量用户「`/技能名` 直输」的肌肉记忆断裂。
  3. 按使用频率智能排序——否决：不可预期性高，违背保守原则（本域既有裁决惯例）。
- **影响范围**：US3.1（菜单分组条目）、US3.3（网页菜单描述）；架构文档新增 ADR-003。

### SDR-005 · 2026-10-13 · 消息内联多技能 / 多命令注入

- **背景与动机**：现状下技能与命令的触发被限制为「整条消息即一条命令」——用户想让多个技能配合一条自然语言指令工作时，只能拆成多条纯命令消息逐条发送，或在消息里口头描述并指望模型自己调 Skill 工具。前者割裂表达（一句话的事要发几条消息、无法与普通文本混排），后者不可靠（模型可能不调、调错或漏调）。同时，触发符/斜杠只在输入框**首位**生效，用户在消息中间想插入技能时无处下手。
- **决策**：新增 US3.6「消息内联多技能 / 多命令注入」：
  1. **内联引用块**：用户可在消息任意位置引用多个技能或斜杠命令，底层为消息文本自身携带的行内链接（这条消息本身就以可显示的链接形式记录全部引用，不引入独立字段），输入框与消息呈现层渲染为统一技能图标 + 名称的内联芯片。
  2. **触发位置扩展**：技能触发符（US3.4）与 `/` 从「输入串首位」扩展到「首位或紧随空白之后」的光标位置（词内不触发，防误弹）；选中后依输入框状态回填——为空时维持现状（回填规范斜杠命令），已有内容时插入内联引用块。
  3. **激活判定按文本形态**：链接文字带触发符前缀且指向合法技能文件或命令名的行内链接即具备激活资格——菜单插入是主产生路径，手写/粘贴的等形态文本同样可激活（误触发面由「触发符前缀 + 合法目标」双重条件收窄，纯技术兜底）；普通 markdown 链接（无触发符前缀）永远不激活。
  4. **同轮直达执行**：混合消息发送后（忙时整条随普通消息排队进下一回合），引擎在消息进入回合时解析全部引用块——技能全文经「技能已加载」包裹按出现顺序注入（模型无需调用 Skill 工具），正文作为用户意图一并送达；重复引用折叠、失败块不静默失败（发送前警示、降级为普通链接文本且模型侧可见失败说明）。
  5. **直行命令也内联化（1-B）**：斜杠命令与技能同等支持内联注入；命令块由提交端在消息发送时刻先行分发到命令执行面（不进模型上下文），清理类命令与技能混排时发送前警示冲突；含内联命令块的混合消息不因「首位恰为斜杠命令」而被拦截为纯命令执行。
  6. **多激活一个撤销单元**：一条混合消息内的全部激活构成一个可撤销单元（整体一次撤销），每条激活事实仍独立记录与呈现。
  7. 观测闭环对齐既有用户斜杠激活（激活事实、卡片、遥测、撤销锚点），触发方式标注新增「用户消息内联」成员；历史与回放按底层行内链接持久化，其他客户端降级为普通链接文本。
- **已识别的体验风险与应对**（随本决策一并定案的应对设计）：
  1. **误触发菜单**：代码片段、URL、路径中打 `/` 被菜单打断 → 触发条件收紧为「光标在词首（首位或紧随空白）」，词内不触发。
  2. **误激活（粘贴链接文本）**：激活判定按文本形态（决策 3）意味着粘贴一段含等形态链接的文本会被激活——收窄条件为触发符前缀 + 合法目标双重命中，二者缺一即普通文本；接受该残余风险，换取判定规则可实现且可预期。
  3. **失效引用**：技能在插入后被删除/停用/文件移走 → 发送前警示反馈，用户可选移除或带警示发送（降级为普通链接文本，不静默吞掉）。
  4. **多技能注入撑爆上下文**：一条消息注入 N 个技能全文 → 与嵌套加载共用既有注入纪律与上下文成本约束（清单常驻、全文按需、同参去重），重复引用折叠为单次注入。
  5. **清理类命令与技能混排**：清空历史/整理上下文类命令会丢弃同消息的技能激活 → 发送前警示两者冲突，用户须移除其一或分条发送。
  6. **多端不一致**：其他客户端无法识别底层形态 → 降级为普通链接文本（可点击跳转技能文件），不报错不中断渲染；终端端输入体验对齐属后续裁决。
- **被否决的备选方案**：
  1. **1-A（仅技能内联化，命令维持首位单条）**——否决：命令与技能在输入层已统一为一个混合心智（`/` 菜单、触发符、分组呈现），让「技能可内联、命令只能在首位」会造成同一菜单选出的两种条目落点行为不同，用户无法建立稳定预期；且「把 /clear 混在句子里」本就是用户显式选择，无须产品层替用户挡。
  2. **2-B（前端解析为结构化字段传输）**——否决：需要改传输契约增加消息字段，历史消息的芯片呈现依赖结构化数据，脱离网页端即丢语义；行内链接让消息正文自身即唯一事实源，历史/回放/多端天然一致，网页端只需负责渲染。
  3. **多技能拆成多条排队激活**——否决：保持「一条消息一个激活」现状、引擎侧排队逐个执行——用户看到的是 N 张独立激活卡片与 N 次注入声明，与「一句话指挥多技能」的表达意图不符，且排队顺序与消息正文的关联丢失。
  4. **「仅菜单插入才激活」（以来源区分手写与插入）**——否决：纯文本载体上菜单插入与手写不可区分，需引入隐藏标记才能实现（破坏「正文即事实源」）；且用户粘贴自己历史消息中的合法引用无法激活，可用性反而下降。
- **影响范围**：新增 US3.6；US3.4（触发位置从首位扩展到词首、回填分状态）、US3.3（网页触发符回填描述）、US4.4/US5.1/US8.2（触发方式枚举扩四态）、§0 领域边界（消费闭环措辞）修订；glossary 新增 SK7（技能引用链接）、修订 SK6（触发位置）与 SK2（触发方式四态）；架构文档新增 ADR-004；US3.1 的首位斜杠语义在混合消息场景下由 US3.6 收敛（纯命令消息不变）。

### SDR-006 · 2026-10-17 · 激活后正文芯片重建（with_skills 记录字段）

- **背景与动机**：US3.6 落地后暴露一个呈现缝隙——混合消息被引擎接纳时，正文里的技能引用链接会被替换为裸技能名标记（防重复注入的解析幂等 + 模型侧可读性，见 ADR-004 决策 2），持久化与回放用的都是这份替换后正文。而客户端的芯片渲染只认「触发符前缀 + 完整链接」形态，于是激活成功的历史消息里引用退化为纯文本方括号名（`[writing-plans]`），与激活卡片能显示激活事实形成落差，用户看到「发送前是芯片、刷新后是文本」的不一致呈现。
- **决策**：为「激活结果记录」补充一个结构化旁路字段 **`with_skills`**（挂在被引擎改写的正文消息上）：引擎在替换正文时，把本条消息实际激活的技能清单写入该字段随消息持久化（每项含技能名、技能文件路径、触发方式——形状裁决见 ADR-006；技能名兼任渲染匹配键）；客户端回放渲染时依据 `with_skills` 把正文中的裸名标记重建为内联芯片。正文的**文本形态不变**（仍是替换后的标记形态，模型侧语义与缓存稳定性不动），芯片重建纯粹是呈现层的逆向映射。
- **与被否决的 2-B 的区别**（SDR-005 备选 2，须显式切割）：2-B 否决的是**提交方向**的结构化引用——用户消息靠字段携带引用进来，正文文本与结构化数据两份事实源，脱离支持端丢语义。本决策是**记录方向**的激活结果：行内链接仍是唯一激活事实源（激活判定、发送前校验、多端降级全部不变），`with_skills` 是引擎激活成功后的**产物记录**——有它则芯片精确重建，无它（旧会话、不支持端）则维持现状的文本降级，不存在「丢字段即丢事实」的依赖。
- **已识别的体验风险与应对**：
  1. **旧会话无字段**：升级前落库的历史消息没有 `with_skills` → 维持现状文本呈现（与今天一致，无回归）；新消息从此字段精确重建。
  2. **字段与正文标记不匹配**（改名、字段损坏）→ 匹配不到标记时该技能不重建芯片，按普通文本呈现，不报错不中断。
  3. **重复引用折叠**：同技能多次引用的折叠事实照实记录在字段里（去重后的激活清单），正文里所有同名标记均重建为指向同一技能的芯片。
  4. **字面文本碰撞**：用户在同一条消息里手打与标记形态相同的字面文本（如讨论标记形态本身、且该技能恰好被激活）——按匹配键相等会被误重建为芯片，属呈现层化妆品级误判，无法与真实标记区分；接受该残余风险（仅影响展示，不影响激活事实）。
- **被否决的备选方案**：
  1. **降级保留触发符**（正文标记保留 `$` 前缀，`[$name]` 形态）——两行改动即可让客户端现有的紧凑 token 解析命中，但把「给模型的文本」和「客户端渲染协议」耦合在同一形态上：模型侧文案的任何调整都会牵动渲染兼容，且不解决命令引用的同类降级。作为应急修复被评估后搁置，采用结构化正解。
  2. **渲染层启发式匹配**（拿激活卡片的名字猜正文标记）——不碰协议，但属于客户端私有的猜测逻辑，TUI 无法复用，且名字与标记本质上是两次独立来源，匹配错即错渲染。
- **影响范围**：新增 US3.7（下方）；US3.6「历史与回放」节补充呈现重建依据；架构文档新增 ADR-006；wire 契约（消息 schema 新增可选 `with_skills` 字段）、引擎（正文替换时写入字段）、web（气泡渲染依据字段重建芯片）、asyncapi 文档同步；TUI 侧可凭同一字段做终端能力的芯片/高亮呈现，属终端域后续裁决。

#### US3.7 激活后引用的芯片重建（P1）

作为技能使用者，我想让带技能引用的消息在会话历史的每次呈现中都稳定显示为内联芯片（与发送前一致），以便回看时仍然一眼识别我当时激活了哪些技能，而不是看到一堆裸方括号文本。

- Given 一条混合消息被引擎接纳且技能激活成功，Then 该消息进入会话历史时随附一份**激活清单**（本条消息实际激活了哪些技能；记录的形状与携带位置见架构文档 ADR-006）
- Given 客户端渲染携带激活清单的历史消息，Then 依据清单把正文中的对应技能名标记重建为内联芯片（技能芯片用统一技能图标 US3.5，可点击跳转技能），呈现与发送前一致
- Given 消息不带激活清单（升级前的旧会话、不支持该记录的来源），Then 维持现状：技能名标记按普通文本呈现，不报错、不中断渲染
- Given 清单与正文标记对不上（标记被手改、清单部分缺失），Then 对不上的标记按普通文本呈现，对得上的正常重建——逐标记独立降级
- Given 同一技能在一条消息中被引用多次（折叠为单次激活），Then 清单记一次，正文所有指向该技能的标记均重建为该技能的芯片
