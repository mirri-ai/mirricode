# 权限与审批（approval）— 需求规格

> 本文档记录当前 TS 引擎已支持的能力，作为 Rust Core 的对齐基线（parity floor）——是 Rust 需要追平的下限，**不是**限制 Rust 只能做到这些的水平线。Rust 侧的增强空间见文末「未来增强提案」与 [approval-ROADMAP.md](approval-ROADMAP.md)。
> 2026-09-12（B0 治理批次）：追加 SDR-003（会话级批准跨代理共享 + 审批过期诚实化），US5/US10 正文同步修订为终态。
> 2026-09-16：追加 SDR-004（权限模式以会话实时模式为唯一运行时决策源），US1.2 正文同步修订为终态。
> 2026-10-13：追加 SDR-005（问询关闭的终态语义——回合终止、归还输入权），US8 正文同步修订为终态。
> 2026-10-24：追加 SDR-006（问询通道的连接韧性——投递失败挂起等待重连，而非立即错误），US8/US10 正文同步修订为终态。

## 1. 范围与边界

**本域覆盖**（审批流的端到端用户闭环）：

1. **权限模式（permission mode）**：manual / auto / yolo 三档姿态的语义、切换入口（CLI 启动参数、配置默认值、TUI 命令与选择器、目标/蜂群启动确认、IDE 客户端模式切换）、模式切换的生效范围与对子代理的广播、模式相关的上下文提醒。
2. **审批判定**：单次工具调用「放行 / 拒绝 / 问询」的裁决顺序与各裁决面（模式姿态、用户规则、会话记忆、敏感路径、兜底问询）。
3. **审批呈现与用户决策**：审批请求何时弹出、展示什么内容、提供哪些选择（含反馈输入、计划变体选择、批量排队呈现），覆盖终端（TUI）、网页（web）、IDE 客户端（ACP）、嵌入式 SDK 四类消费端。
4. **决策结果回传执行**：批准 → 执行；拒绝/取消 → 以模型可读的工具结果回传（含拒绝原因与对子代理的行为指引）。
5. **记忆化与会话级策略**：「本次会话内记住这一批准」的规则记录、去重、会话恢复重建、排队请求的自动继承。
6. **用户权限规则（[permission] 配置）**：用户以配置文件声明 allow / deny / ask 规则（含工具名通配与参数匹配）后，审批行为随之变化的用户闭环。
7. **问询交互（AskUserQuestion 类）**：引擎向用户提问、用户作答、答案回传模型、用户关闭面板的用户闭环。
8. **错误 / 取消 / 超时路径**：无人应答、应答方异常、用户中止、回合结束、进程崩溃恢复等场景下审批与问询的终态。

**本域不覆盖**（引用相邻域，防重叠）：

| 相邻主题 | 归属 | 本域引用方式 |
|---|---|---|
| 工具的声明式启停（某工具是否在可用集合内） | tool-calling 域 | 本域只裁决「集合内的调用是否放行」 |
| 审批刻面的生成（调用如何归一为可匹配的规则串） | tool-calling 域 | 本域消费该刻面做规则匹配 |
| 工具执行原语（终端 / 文件 / 进程 / 沙箱） | execution-environment 域 | 批准后由执行域落地动作 |
| 计划模式的进入/退出语义、计划文本规范 | tool-calling 域（工具）+ 会话管理域 | 本域覆盖「计划提交后的审查审批 UX」 |
| 目标（goal）/ 蜂群（swarm）的业务语义 | 各自域 | 本域覆盖其「启动前的权限确认」交互 |
| 旁路问询（btw）的投递机制 | session-management 域 | 本域覆盖「btw 子代理禁用一切工具调用」的审批面 |
| 用户身份认证 / 登录 / OAuth | auth-oauth 域（含认证摘要服务——经甄别，认证摘要是登录状态与提示词就绪性，与审批无关） | 无重叠 |
| MCP 服务器的授权（mcp auth 工具） | mcp 域 | 本域只覆盖其审批刻面触发的审批 UX |
| 审批在会话转录中的历史呈现 | conversation-rendering 域 | 本域覆盖交互发生时的实时闭环 |

## 2. 用户画像

- **P1 终端用户（CLI / TUI）**：在终端里以交互或无头方式使用引擎；关心何时被打断、看到什么、怎么选。
- **P2 网页用户（web）**：通过网页客户端连接引擎；关心审批卡片、会话等待状态与多会话提醒。
- **P3 IDE 客户端用户（ACP）**：通过支持 Agent Client Protocol 的编辑器（如 Zed）使用；关心权限请求选项与模式下拉。
- **P4 嵌入式 SDK 开发者**：以 SDK 内嵌引擎；关心审批/问询回调接口的形状与缺省行为。

## 3. 用户故事与验收标准

### US1 权限模式三档姿态

**US1.1 模式语义**

- Given 引擎处于 **manual（手动）** 模式，When 模型发起一次工具调用，Then 只读与编排类内建工具（阅读、检索、列表类、任务面板类、网页搜索与抓取、子代理与蜂群派发、问询、技能调用、计划进出、目标管理、工具选择）自动放行；其余调用（写文件、改文件、跑命令、停止后台任务等）一律弹出审批。
- Given 引擎处于 **auto（自动）** 模式，When 模型发起任意工具调用，Then 除用户显式 deny 规则外全部自动放行——包括高危动作。
- Given 引擎处于 **auto** 模式，When 模型调用「向用户提问」工具，Then 该调用被拒绝，且模型收到明确指引：自行做出合理决定并继续，不要提问。
- Given 引擎处于 **yolo** 模式，When 模型发起一次工具调用，Then 自动放行；**但**以下三类仍会打断用户问询：用户显式 ask 规则命中的调用、涉及敏感文件的访问、涉及 git 控制路径（`.git` 目录）的访问。
- Given 引擎处于 **yolo** 模式，When 模型调用「向用户提问」工具，Then 允许提问（yolo 不禁用问询；auto 才禁用）。
- Given 引擎处于任一模式，When 旁路问询（btw）子代理发起任何工具调用，Then 一律拒绝（btw 子代理只能用文本作答）。
- Given 同一批工具调用中包含多个「蜂群派发」调用、或「蜂群派发」与其他调用混合，When 提交执行，Then 该批调用（含其中的蜂群派发与同批其他调用）被拒绝，模型收到说明（单独一个蜂群调用不受影响）。

**US1.2 模式切换入口与生效**

- Given 用户以命令行参数指定 auto / yolo 启动，When 会话建立，Then 会话以该模式开始，无需再手动切换。
- Given 用户在会话建立前已选定权限模式（如新会话输入框的模式选择），When 首条消息发出，Then 会话以所选模式开始——首个工具裁决即按该模式执行，不出现「界面显示所选模式、实际按默认姿态裁决」的认知错位（SDR-004）。
- Given 用户在配置文件中设定了默认权限模式，When 新主会话建立且未显式指定模式，Then 以配置的默认模式开始（未配置时为 manual）；该默认值只决定新会话的初始姿态与界面的初始显示，不参与任何进行中会话的裁决——运行时以会话实时模式为唯一决策源（SDR-004）。
- Given TUI 用户输入 `/auto` 或 `/yolo`（支持 on / off / 无参切换三种形态），When 命令执行，Then 模式切换成功并显示对应说明文案；已是目标状态时显示「已在目标状态」提示，不重复切换。
- Given TUI 用户输入 `/permission` 或经设置入口选择权限模式，When 在选择器中选定一档，Then 生效并提示当前模式；选择当前已处模式时提示「未变化」，零动作。
- Given 用户在 TUI 中设置的目标模式下启动目标（goal）或蜂群（swarm）任务，When 权限确认对话框选择了「切换到 Auto/YOLO 并启动」，Then 先切换模式再启动；若随后目标创建失败，Then 自动恢复到启动前的模式（不留下比用户原状态更宽松的会话）。
- Given 用户在会话进行中切换权限模式（无论经哪个入口：终端命令、网页选择器、IDE 客户端、SDK、目标/蜂群启动确认），When 切换生效，Then 同会话内所有代理的后续工具调用立即按新模式裁决——包括已存在的子代理与后续派生的子代理；子代理没有独立的权限模式，始终与会话实时模式一致（广播覆盖全部存活代理，SDR-004）。
- Given 界面上显示的模式与会话实际模式不一致（断线重连、多端并开、模式经其他入口变更），When 状态同步，Then 以会话实际模式为准刷新界面显示——界面是会话实时模式的镜像，不自行持有权威状态；模式设置未能落地时必须向用户显式暴露失败，不得静默吞掉（SDR-004）。
- Given 模式被重复设置为相同值，When 设置发生，Then 不产生多余的状态变更通知（幂等）。

**US1.3 模式的上下文提醒**

- Given 权限模式进入或离开 auto，When 下一次上下文注入发生，Then 模型收到对应的模式提醒（进入 auto：告知问询被禁用、应自行决策；离开 auto：恢复说明），使模型行为与当前姿态一致。
- Given 一条模式提醒已被历史压缩折叠，When 再次注入上下文，Then 提醒重新出现（模式提醒不因压缩而永久丢失）。

**US1.4 IDE 客户端模式档位**（ACP 面）

- Given IDE 客户端创建或恢复会话，When 引擎返回可用模式列表与当前模式，Then 呈现四档：Default（手动审批，工具正常执行）/ Plan（只读规划，不执行工具）/ Auto（自动放行安全与不安全操作）/ YOLO（全部自动放行）；默认档为 Default。
- Given IDE 客户端切换模式，When 选择 Plan，Then 同时进入计划模式并保持 manual 姿态；选择 Auto / YOLO 分别映射为对应权限姿态。

### US2 审批触发面（何时弹）

- Given 一次工具调用未被任何显式规则/放行面覆盖，When 执行前，Then 弹出审批（兜底问询，永不静默失败或静默执行）。
- Given 调用涉及敏感文件（凭据、密钥类文件）的读或写，When 处于 manual 或 yolo 模式，Then 弹出审批。
- Given 调用的目标路径包含 `.git` 路径组件、或落在 git 工作树的控制目录内，When 处于 manual 或 yolo 模式，Then 弹出审批。
- Given 用户以 ask 规则命中某调用，When 处于 manual 或 yolo 模式，Then 弹出审批（auto 模式下 ask 规则不生效，见 US1.1）。
- Given Write/Edit 调用的全部写入路径都在工作区（含附加目录）内、会话目录本身是一个 git 工作树、且运行在 posix 系统上，When 处于 manual 模式，Then 该写入直接放行，不弹审批。
- Given 会话内已有对该调用刻面的会话级批准记忆，When 再次发生同刻面调用，Then 直接放行。
- Given 用户以 deny 规则命中某调用，When 执行前（任何模式，含 auto/yolo），Then 直接拒绝，工具结果带用户规则原因。
- Given 一次调用同时命中多个裁决面，When 裁决，Then 按固定优先序取第一个命中面：旁路问询全禁 > auto 问询禁用 > 用户 deny > auto 全放行 > 会话记忆放行 > 用户 ask > 用户 allow > 敏感文件问询 > git 控制路径问询 > yolo 全放行 > 内建默认放行 > 工作树内写放行 > 兜底问询。

### US3 审批面板 UX（TUI）

**US3.1 呈现内容**

- Given 一次审批弹出，When 面板渲染，Then 顶部为工具对应的问句标题（命令类「Run this command?」、写文件「Write this file?」、改文件「Apply these edits?」、停止任务「Stop this task?」、计划审查「Ready to build with this plan?」、其余「Approve <工具名>?」）。
- Given 待批动作带有结构化展示（命令、diff、文件内容、文件操作、网址抓取、搜索、子代理/技能调用、任务停止、目标启动、计划审查、后台任务、待办列表），When 面板渲染，Then 按对应形态渲染成预览块（命令块显示工作目录与命令行；diff 块带路径头与上下文，最多显示 10 行、提示可展开预览；文件内容块语法高亮、最多 10 行、提示剩余行数与预览入口；其余为单行概要或简要文本）。
- Given 待批动作只带原始参数、无结构化展示，When 面板渲染，Then 引擎按参数特征（命令 / 新旧文本对 / 文件路径加内容 / URL / 搜索词 / 文件路径）尽力推导出预览块；推导不出时显示动作描述文本。
- Given 面板中的预览块与描述文本重复，When 渲染，Then 重复的简述块被去重。
- Given 预览块超过 5 个，When 渲染，Then 只显示前 5 个。
- Given 待批命令匹配高危模式（递归删除、sudo、管道进 shell、dd 写盘、mkfs、写裸设备、递归 777、fork 炸弹），When 命令块渲染，Then 显示醒目的「Dangerous: <类型>」警示。

**US3.2 选项与操作**

- Given 一次常规审批弹出，When 面板渲染，Then 提供四个选项：「Approve once（批准本次）」「Approve for this session（本会话内均批准）」「Reject（拒绝）」「Reject with feedback（拒绝并附反馈）」，按此顺序排列。
- Given 用户按 ↑/↓ 移动选择、回车确认，或直接按数字键 1-4，When 按下，Then 对应选项被选中执行。
- Given 用户选择了「Reject with feedback」，When 确认，Then 面板切换为行内反馈输入（回车提交；Esc 或 ↑/↓ 返回选项列表，不提交）。
- Given 用户在面板上按 Esc / Ctrl+C / Ctrl+D，When 按下，Then 视为拒绝（rejected）。
- Given 面板含 diff 或文件内容块，When 用户按 Ctrl+E，Then 打开全屏预览；按 Ctrl+O 切换工具输出视图。
- Given 面板渲染，When 显示底部，Then 呈现操作提示行（↑/↓ select · 数字 choose · ↵ confirm · 可预览时附 ctrl+e preview）。

**US3.3 排队与并发**

- Given 多个审批请求并发到达（如多个并行子代理各自请求审批），When 呈现，Then 一次只显示一个面板，其余按到达顺序排队，当前面板解决后自动推进。
- Given 用户对某请求选择了「本会话内均批准」，When 排队中存在动作描述相同的其他请求，Then 这些排队请求自动继承批准（不逐个弹面板）；继承的响应不携带首次交互的反馈与选项标签（它们只描述首次交互）。
- Given 用户切换会话或退出，When 尚有未决审批/问询，Then 全部以取消（cancelled）收尾，不悬挂。
- Given 审批面板与问询面板同时待显示，When 呈现，Then 两类面板互斥串行（先到先显示、解决后推进另一类），不会互相覆盖丢失；同类内部各自按到达顺序排队。

**US3.4 特化选项**

- Given 计划审查审批（见 US7.1）弹出，When 面板渲染，Then 选项为：各计划变体（模型给出 ≥2 个时逐个列出）或单一「Approve」，加上「Revise（修订，需反馈）」「Reject（拒绝）」。
- Given 目标启动审批（见 US7.2）弹出，When 面板渲染，Then 选项为：切换到 Auto 并启动 / 切换到 YOLO 并启动（或保持 YOLO 启动）/ 以手动模式启动 / 不启动（返回输入框且不丢失已输入命令），每项带解释文案；**当前已处于 YOLO 姿态时不提供「以手动模式启动」**（仅切换 Auto / 保持 YOLO / 不启动三项）。
- Given 蜂群启动确认（见 US7.3）弹出，When 面板渲染，Then 选项为：切换到 Auto 并启动 / 切换到 YOLO 并启动 / 以手动模式启动，各带解释文案；取消（Esc）返回输入框且命令不丢失。

### US4 决策语义与回传

- Given 用户选择「批准本次」，When 决策回传，Then 该调用放行执行，不产生任何记忆。
- Given 用户选择「本会话内均批准」，When 决策回传，Then 本次调用放行，且为该调用的审批刻面记录一条会话级放行记忆；后续同刻面调用自动放行，不再弹面板。
- Given 用户拒绝（可附反馈），When 决策回传，Then 调用不执行，模型收到错误形态的工具结果：「工具因用户拒绝审批而未运行」，附用户反馈原因。
- Given 决策以取消收尾（面板被关闭、会话切换、回合结束等），When 决策回传，Then 调用不执行，模型收到的工具结果明确表述「审批请求被取消」——与「用户拒绝」文案可区分。
- Given 审批请求来自子代理（worker）而非主代理，When 拒绝/取消结果回传，Then 结果附加行为指引：换一种方法，不要重试同一调用，不要尝试绕过限制（主代理不附加此指引）。
- Given 用户 deny 规则或策略直接拒绝某调用，When 结果回传，Then 工具结果为错误形态，带拒绝方指定的消息（用户规则带 reason）。
- Given 一次审批被请求或被解决，When 事件发生，Then 引擎发出对应事件（请求/已解决），供外部钩子与 UI 感知。

### US5 会话级批准记忆

- Given 用户作出一次「本会话内均批准」，When 记录时该刻面已有记忆，Then 不重复记录（去重）。
- Given 会话被持久化后恢复，When 重放历史，Then 会话级批准记忆按历史批准记录重建，恢复后同刻面调用继续自动放行。
- Given 历史会话记录产生于旧版本、未携带审批刻面信息，When 恢复时，Then 按当时的动作描述推导出工具刻面重建记忆；无法可靠推导的动作（如后台命令、计划模式内命令）不重建记忆（宁可多问一次，不放过未经批准的动作）。
- Given 会话级记忆为**会话内共享**（不按发起调用的代理隔离），When 子代理发起与已批准刻面相同的调用，Then 自动放行不再弹面板——同会话内任何代理（含子代理）共享批准记忆（见 SDR-003）。
- Given 会话结束，When 会话关闭，Then 会话级记忆随之消亡（不跨会话留存）。

### US6 用户权限规则（[permission] 配置）

- Given 用户在配置文件的 `[permission]` 节声明 deny / allow / ask 列表（如 `deny = ["Bash"]`），When 引擎加载，Then 规则生效于审批裁决（见 US2 优先序）。
- Given 用户以 `tool` + `match` 简写声明规则（如 `{ tool = "Bash", match = "git*" }`），When 加载，Then 归一为「工具名(参数模式)」形态的规则，参数匹配交由该工具的审批刻面判定。
- Given 用户直接声明完整规则（decision / scope / pattern / reason），When 加载，Then 同样生效；scope 支持 user（用户级，默认）、project（项目级）、turn-override（单回合覆盖）。
- Given 规则 pattern 非法（空串、缺右括号、空工具名），When 配置加载，Then 该配置被拒绝（校验失败），不会以静默方式忽略或误匹配。
- Given pattern 的工具名带通配（如 `B*` 或 `*`），When 匹配，Then 按通配语义匹配实际调用的工具名。
- Given 用户 deny 规则带 reason，When 调用被拒，Then 拒绝消息带该原因。
- Given 规则的 pattern 只写工具名，When 匹配，Then 不做参数级匹配（任何参数都命中）。
- 规则刻面（工具如何把自己的调用归一为可匹配串）的生成语义见 tool-calling 域；本域覆盖规则的用户面（声明、校验、生效于审批）。

### US7 特殊审批流

**US7.1 计划审查（ExitPlanMode）**

- Given 模型在计划模式下提交计划（调用退出计划工具且携带非空计划文本与计划审查展示），When 执行前且处于 **manual 或 yolo** 模式，Then 弹出计划审查审批；**auto 模式下计划提交直接放行、不弹审查**（与目标启动确认的 auto 跳过一致）。
- Given 计划审查审批携带 ≥2 个方案变体，When 面板渲染，Then 用户可逐个选择批准哪个变体。
- Given 用户批准（含选定变体），When 决策回传，Then 退出计划模式；工具结果包含「计划模式已解除、全部工具可用」、批准的计划全文；选定变体时附加「只执行所选方案，不得执行未选方案」的明确指令。
- Given 用户选择「Revise」并附反馈，When 决策回传，Then 保持计划模式，模型收到用户反馈原文。
- Given 用户拒绝且未选 Revise/未给反馈，When 决策回传，Then 保持计划模式，本回合终止，模型收到「计划被用户拒绝」；**「拒绝并退出计划模式」的出口随呈现端而异**：IDE 客户端与网页提供显式「Reject and Exit」选项（退出计划模式并终止回合），终端（TUI）只提供「Reject / Revise」，终端侧拒绝一律保持计划模式。
- Given 用户关闭审查面板（dismiss），When 决策回传，Then 保持计划模式，模型收到「审查被关闭，计划模式保持」。

**US7.2 目标启动（CreateGoal）**

- Given 模型在 manual 或 yolo 模式下请求创建目标（携带目标启动展示），When 执行前，Then 弹出目标启动审批；auto 模式下不弹（直接按 auto 姿态继续）。
- Given 用户在启动审批中选择了某个权限档位，When 批准，Then 会话切换到所选档位后目标启动（档位切换经模式面生效）。
- Given 用户选择「不启动」，When 决策回传，Then 目标不创建。

**US7.3 蜂群任务启动（/swarm）**

- Given TUI 用户以 **manual** 姿态发起蜂群任务，When 任务真正下发前，Then 弹出蜂群启动权限确认（选项：切换 Auto 并启动 / 切换 YOLO 并启动 / 以手动模式启动，各带解释文案）；已处于 YOLO/Auto 姿态时**不弹确认，直接下发**。
- Given 用户按 Esc 取消蜂群启动确认，When 确认，Then 任务不下发，已输入的命令文本回到输入框（不丢失）。

### US8 问询交互（AskUserQuestion 类）

- Given 模型调用问询工具，When 执行，Then 用户侧呈现问询面板：一批问题（每题含题面、可选标题/正文、选项列表、可多选、可附「其他」自由文本标签与说明）；用户作答后答案回传模型。终端问询面板支持 Ctrl+O 切换工具输出视图（与审批面板一致）。
- Given 用户在 IDE 客户端（ACP）使用，When 模型问询，Then 问询复用权限请求面呈现：每个选项一枚按钮（选项文本原样回传）、尾部一枚「Skip」（跳过即无作答）；**多问题批次降级为只问第一题**（其余问题被丢弃并留观测痕迹）；**多选题降级为单选**（接受单个答案）；**不提供「其他」自由文本作答入口**（仅预设选项与 Skip）；请求失败或返回未知选项时以「无作答」收尾——绝不替用户编造答案。
- Given 用户多选作答，When 答案回传，Then 模型收到以逗号连接的选项文本（与用户所见文案一致，不含内部标识）。
- Given 用户跳过某题，When 答案回传，Then 该题不出现在答案记录中。
- Given 用户直接关闭问询面板（Esc / 关闭按钮），When 交互结束，Then 当前**回合以「问询已关闭」收尾**：引擎向模型回传「用户关闭了问询且未说明原因」的明确结果，并**终止该回合**——模型不基于对用户意图的猜测继续行动，输入权归还用户；关闭后的回合结束路径与 US10 的回合收尾语义一致（不悬挂、可下轮继续）。
- Given 用户关闭问询时附带可选原因文本（提供关闭原因输入的接入面），When 交互结束，Then 原因随「问询已关闭」结果一并回传模型，同样终止回合——原因供模型下一轮理解用户意图，不改变终止语义。
- Given 用户关闭的是**后台问询**（不阻塞回合的提问），When 关闭发生，Then 问询任务以「已取消」定局、等待中的发起代理收到「用户已关闭问询」的通知；该代理**停止依赖该答案的后续决策**，可继续与该答案无关的工作——收到关闭通知后不得自行假设答案推进原决策点。
- Given 问询被关闭后的后续回合，When 模型考虑再次问询，Then 关闭语义为「暂不回答」而非「永久拒绝」——模型可以换更清晰的方式重新提问，但**不得原样重问**刚被关闭的问题（重复骚扰护栏，防止关闭→重问循环）。
- Given auto 模式下模型尝试问询被拒（见下条），Then 属于授权委托的显式通道，**不适用**本节关闭语义。
- Given 问询来自子代理，When 呈现，Then 问询面板归属于发起它的子代理（其事件与转录帧路由到该代理的面，而非误挂到主代理）。
- Given auto 模式，When 模型尝试问询，Then 被拒绝并收到「自行决策」指引（见 US1.1）。「自行决策」的授权有**专用显式通道**（auto 模式），用户无需用关闭动作表达「你决定」——关闭问询面板在 manual/yolo 下不构成对模型的委托授权（SDR-005）。
- Given 问询呈现通道在用户作答前断开（客户端掉线、网页刷新、客户端进程重启后重连），When 用户在重连后继续操作，Then 该问询仍然可以被作答（答案经问询应答通道回传）——引擎侧问询保持待决，投递尚未成功的问询在重连后重新送达用户眼前；问询不因连接断开而丢失或提前关闭（已送达待作答的问询在重连后的界面重现另见开放项）。
- Given 问询呈现通道在问询发起时已断开且在一段时间内未恢复，When 引擎等待，Then 问询**挂起等待重连**（通道断了，用户没理由错过问题）：等待期间引擎保持回合存活（不因长时间无响应而误判卡死，不向模型回传任何中间信号）；等待有明确上限（缺省 5 分钟，可配置），到期后以可区分的错误收尾并附指引「改用纯文本提问或稍后重试」，不允许永久悬挂。该上限到期收尾**不写入防重问护栏**——护栏只由用户主动关闭触发，通道故障不是用户意图，模型可原样重发问询。
- Given 连接断开期间引擎需要发起新问询，When 尝试投递，Then 新问询同样挂起等待重连（与已有问询一致），不因通道当时不可用而直接失败。
- Given 会话从未连接过任何交互承接方（无头模式、嵌入式未注册问询处理器），When 问询发生，Then 维持既有缺省语义立即收尾（均为「无作答」，见 US9.3/US9.4 与下条），不进入等待——等待的前提是「用户曾经在场」（有过连接），从未在场的会话不存在会回来的用户。
- Given 嵌入式 SDK 使用者未注册问询处理器，When 问询发生，Then 立即以「无作答」收尾，不悬挂。
- 问询工具自身的定义与参数契约见 tool-calling 域；本域覆盖「问—答—回传」的用户闭环。

### US9 多端呈现与接入

**US9.1 网页（web）**

- Given 会话中有待决审批，When 用户打开该会话，Then 审批以独立卡片呈现（含工具名、动作摘要与结构化预览），用户可批准 / 本会话内批准 / 拒绝 / 拒绝并附反馈；计划审查卡片提供变体选择、Revise（反馈框）与 Reject and Exit。
- Given 网页审批卡片可见且无输入焦点占用、无正在处理的决策，When 用户按数字键 1-4，Then 对应动作执行（与按钮一致）。
- Given 会话有待决审批，When 会话状态计算，Then 会话显示「等待审批」状态；侧栏对应会话有待关注计数（审批 + 问询合计），并可触发提醒（含声音）。
- Given 网页断线重连或刷新，When 恢复，Then 待决审批列表从引擎重新拉取，用户仍可作答（已答过的不会重复出现在待决中）。
- Given 网页侧审批请求含计划展示，When 卡片渲染，Then 计划全文显示在卡片顶部（不被截断为仅动作摘要）。

**US9.2 IDE 客户端（ACP）**

- Given 引擎向 ACP 客户端请求权限，When 请求呈现，Then 提供三个规范选项：「Approve once」为主操作、「Approve for this session」为次操作、「Reject」为终止操作（排序保证误触最难命中拒绝的反面——批准）。
- Given ACP 客户端传回的选项标识未知（含旧版客户端的旧标识），When 解析，Then 按兼容映射处理：旧版一次性批准/会话级批准标识继续被接受；完全未知的标识一律按拒绝处理（拒绝比批准安全）。
- Given ACP 权限请求携带工具调用上下文，When 客户端渲染，Then 审批与已渲染的工具卡片关联（diff / 文件预览作为卡片头条内容），并始终附带「请求批准以 <动作>」的人读摘要。
- Given ACP 客户端取消权限请求（未选任何项），When 解析，Then 决策为取消。

**US9.3 嵌入式 SDK**

- Given SDK 使用者为某会话注册了审批处理器，When 审批发生，Then 处理器被调用，其返回值即决策（approved / approved + session / rejected / cancelled，含可选反馈与所选标签）。
- Given SDK 使用者未注册审批处理器，When 审批发生，Then 决策为取消并附「未注册审批处理器」说明（不默认放行）。
- Given SDK 审批处理器抛出异常，When 异常发生，Then 决策为取消并附「处理器失败」说明，同时向使用者的错误事件流报告错误详情。
- Given SDK 使用者可为问询注册处理器，When 问询发生，Then 处理器返回答案；未注册时问询以「无作答」收尾。
- Given SDK 使用者调用会话的模式设置接口，When 指定 manual / auto / yolo，Then 会话权限模式切换（与 US1.2 一致）。

**US9.4 无头模式（headless / 单次提示）**

- Given 用户以无头方式运行单次提示（无交互界面），When 任何审批发生，Then 自动批准（不阻塞流水线）；When 问询发生，Then 以「无作答」收尾。

**US9.5 网页服务端审批接口（REST）**

- Given 网页客户端查询某会话的待决审批，When 会话存在，Then 返回待决列表（含创建时间等元数据）；会话不存在时返回会话不存在错误。
- Given 客户端对某待决审批提交决策，When 该审批仍待决，Then 决策生效并返回已解决确认；审批不存在时返回不存在错误。
- Given 客户端重复提交同一审批的决策（刚解决后短期内），When 再次提交，Then 返回「已解决」冲突信号（幂等保护，防止重复点击/重放造成二次副作用），而非假装成功或报未知错误。

### US10 错误、取消与超时路径

- Given 回合结束（无论正常/异常）时尚有未决审批或问询，When 回合收尾，Then 全部以取消收尾（原因：回合已结束），不悬挂到下一回合。
- Given 问询关闭触发的回合终止（US8 / SDR-005），When 回合收尾，Then 同一会话内的其余未决问询一并以「回合已结束」取消收尾；若存在其他未决审批，按其各自等待语义收尾（审批不因问询关闭而连带取消——两者独立等待，问询关闭只终止发起问询的那个回合）。
- Given 用户中止（中断）进行中的操作，When 存在未决审批，Then 审批等待随中止一并取消（用户取消语义原样传播，不误报为错误）。
- Given 审批应答端发生异常（处理器崩溃等），When 异常发生，Then 以错误事件通知（请求方感知），审批以 error 结果收尾；请求面若提供了错误自救延续则按其处理，否则异常上抛。
- Given 进程在审批等待中崩溃/被杀，When 会话随后恢复，Then 历史中未决的审批/问询折叠为已取消（不恢复悬挂的等待，不伪装成用户批准）。
- Given 引擎侧没有可用的审批承接方（无界面、无处理器、无服务端），When 审批被需要，Then 按接入面的缺省语义收尾（嵌入式 SDK：取消；无头：批准——见 US9.3/US9.4），两种缺省都必须有明确定义，不允许悬挂。
- Given 待决审批放置很久无人应答，When 时间流逝，Then 审批不会因超时自动失效（引擎不设过期）；界面**不派生展示用的到期时间**——引擎未提供真实到期信息时不渲染倒计时（见 SDR-003）。
- Given 问询因通道断开进入挂起等待（US8 / SDR-006），When 等待超过上限，Then 问询以明确的「通道不可用」错误收尾（可与「用户关闭」「回合结束」区分），模型收到「恢复连接后重试或改用纯文本」的指引，不悬挂到下一回合；When 回合在等待期间被中止，Then 沿本节既有的取消收尾语义处理（取消、非错误），不误报为通道故障。

### US11 非功能与可观测性

- Given 每次权限裁决发生，When 裁决完成，Then 产生一条决策遥测（含回合、调用、命中策略名、工具名、当前模式、决定与原因明细）。
- Given 每次审批往返完成，When 完成，Then 产生一条结果遥测（含决策结果、展示形态、耗时、是否写入会话缓存、是否带反馈）。
- Given 权限模式切换，When 切换发生，Then 产生切换遥测（yolo 开关、auto 开关分别记录）。
- Given 计划提交与审查解决，When 发生，Then 分别产生遥测（含是否有变体、最终结局与所选变体）。
- Given 用户配置了外部钩子（PermissionRequest / PermissionResult 事件），When 审批请求/解决发生，Then 钩子被触发并收到脱壳后的请求/结果数据；钩子失败不阻断审批主流程。
- Given 多审批并发排队，When 逐个解决，Then 每个请求保持独立决策，不互相串扰。
- Given 会话恢复重放历史，When 遇到审批类记录，Then 重放过程静默（不触发重复的 UI/审批往返），只重建派生状态。

## 4. 未来增强提案（超出 TS 现状，明确标注为提案）

以下为 recon 中识别的改进空间，**当前 TS 引擎不支持**，仅作为 Rust Core 的设计参考，不构成对现况的事实陈述：

1. **审批过期语义**：TS 的 v1 协议层曾有 60 秒过期的审批，v2 引擎侧审批不过期。提案：定义统一的显式过期策略（可配置），过期后自动转取消并通知模型重试路径。
2. **跨会话的「始终允许」**：当前会话级记忆只活一个会话，用户级规则只能手写配置文件。提案：审批面板直接提供「始终允许」选项，一键把会话级规则升级为用户级配置。
3. **规则与会话记忆的管理 UI**：提案：TUI / web 提供查看与增删当前生效规则、清除会话记忆的界面（现只能改配置文件或重开会话）。
4. **显式批量批准**：当前排队请求只按「同动作描述」自动继承会话级批准。提案：面板提供「批准全部排队请求」的显式批量操作。
5. **审批审计导出**：遥测已有逐次决策数据。提案：提供面向用户的审批历史审计视图/导出（谁在何时批准了什么）。
6. **敏感文件清单可配置**：当前敏感文件判定为内建清单。提案：允许用户增删敏感路径模式。

## 5. 需求决策记录

### SDR-001（2026-09-12）问询交互（question）的归属

- **背景与动机**：问询（AskUserQuestion 类）与审批同属「引擎阻塞等待人类输入」的交互，但问询工具的定义/参数契约在 tool-calling 域。若两域都写问询会产生重叠与漂移。
- **决策**：问询的**用户闭环**（何时呈现、如何作答、答案如何回传模型、关闭语义、无处理器缺省、ACP 面的降级行为）归本域（approval）；问询**工具的定义与参数契约**归 tool-calling 域；两者以交叉引用衔接。认证摘要（登录状态摘要，属提示词就绪性门）经甄别与审批展示无关，归 auth-oauth 域，本域不覆盖。
- **被否决的备选**：问询整体归 tool-calling（否决原因：问询的用户交互闭环与审批共享同一套阻塞-应答内核与排队机制，拆开会导致同一机制两处描述）；问询单独成域（否决原因：域粒度过细）。
- **影响范围**：US8、US9.3、US10。

### SDR-002（2026-09-12）权限规则的用户面归属

- **背景与动机**：工具权限的声明式规则（allow/deny/ask）既涉及配置声明又涉及审批裁决，与 tool-calling 域的「工具可用面」存在潜在重叠。
- **决策**：规则的**声明、校验、生效于审批裁决**的用户闭环归本域；调用如何归一为可匹配的**审批刻面**（规则串生成）归 tool-calling 域（该域已先行文档化刻面生成）。本域以 US6 + 引用衔接，不重复刻面语义。
- **被否决的备选**：规则整体归 tool-calling（否决原因：规则的用户价值在审批行为变化，脱离审批闭环描述规则会退化为配置面清单，违反 R1 终点消费方）。
- **影响范围**：US2、US6。

### SDR-003（2026-09-12）会话级批准跨代理共享与审批过期的诚实呈现

- **背景与动机**：会话级批准记忆此前按「发起调用的代理」维度隔离——同一会话内，主代理已批准过的动作，并行子代理再次发起时仍会逐个弹面板；用户对「本会话内均批准」的心智是「这个会话里这类事不用再问我」，代理维度隔离使该承诺在子代理场景失效（重复打扰）。审批到期方面：引擎不设过期，而消费端曾以派生值展示倒计时，向用户呈现了引擎并不保证的信息（信号真实性问题）。
- **决策**：a) 会话级批准记忆在**会话内跨代理共享**——一次「本会话内均批准」后，同会话内任何代理（含子代理）对同刻面的调用自动放行；记忆仍随会话恢复重建、会话结束即消亡（不跨会话——跨会话属用户级规则的职责，层级不混淆）。b) 审批过期**诚实化**：引擎不派生任何展示用的到期时间；界面在引擎未提供真实到期信息时**不渲染倒计时**（未来若引入显式过期语义再呈现倒计时）。
- **被否决的备选**：a) 维持代理维度隔离——同会话子代理场景重复打扰，违背「本会话内均批准」的用户语义；b) 派生展示用到期值——呈现引擎不保证的语义，违反信号真实性；c) 为展示需求引入引擎级强制过期——当前无过期即无悬挂（审批由回合结束/会话切换收尾），新增终态面不成比例。
- **影响范围**：US5（「代理维度互不串用」条目已同步修订为会话内共享）、US10（到期展示条目改为不渲染倒计时）；术语表 AP2（「按发起调用的代理维度隔离」表述同批修订为「会话内跨代理共享」）；本程序 B9 批次落地（「始终允许」升级用户级规则与规则管理 UI 一并交付）。

### SDR-004（2026-09-16）权限模式以「会话实时模式」为唯一运行时决策源

- **背景与动机**：权限模式是用户对「这个会话如何对待我」的核心承诺。界面上显示的模式与会话实际裁决姿态一旦不一致，两个方向的错位都破坏信任：显示自动、实际手动 → 每步都被打断（打扰，用户以为自动却要一直点确认）；显示手动、实际自动 → 未经预期的动作被放行（越权）。用户并不区分「我什么时候选的、模式存在哪里」——凡是界面当前显示的模式，就是用户认为自己所处的模式。若配置默认值、会话建立时序、子代理派生等任何环节引入与界面显示不一致的姿态，就产生认知错位。
- **决策**：
  a) **唯一决策源**：运行时裁决只读取「会话实时权限模式」（会话内权威状态）；界面上当前显示的模式是该状态的镜像，两者任何时刻必须一致。
  b) **种子职责**：配置的默认权限模式（default_permission_mode）只承担两个职责——新会话的初始姿态、界面的初始显示；不参与任何进行中会话的裁决，也不覆盖会话实时模式。
  c) **先落地后裁决**：用户在会话建立前选定的模式，必须在首条消息的首个工具裁决之前落地为该会话的实时模式（覆盖「先选模式、后建会话、再发首条消息」的时序，与命令行启动参数同构）。
  d) **全量实时生效**：会话进行中切换模式，实时广播到会话内全部代理——已存在子代理、后续派生子代理、蜂群成员；子代理不存在独立的权限模式（始终跟随会话实时模式，继承只是实现手段，不是用户可感知的语义）。
  e) **服务端权威**：界面显示与会话实际模式不一致时（断线重连、多端并开、其他入口变更），以会话实际模式为准刷新界面；模式设置未能落地时必须向用户显式暴露失败。
- **被否决的备选**：①每条消息携带模式——消息间可出现不同模式、与消息内容耦合产生双写竞争，且与本域既有设计（模式状态只经专用通道变更）冲突；②配置默认值直通运行时——进行中会话可被全局配置覆盖或忽略用户的中途切换，违背 b）；③子代理独立模式 + 显式继承——用户心智中不存在「每个子代理一个权限模式」，继承时序不应成为用户需要感知的产品语义（子代理永远跟随会话实时模式）。
- **影响范围**：US1.2（新增「会话建立前选择落地」「进行中切换全量生效」「界面镜像与服务端权威」三条验收，默认值条目补种子语义）；architecture §2.4 + ADR-004；术语表 AP1（同批补充「配置默认值非运行时状态」消歧）；v3 现状缺口见 context §8（web 首条消息路径丢模式、rust 不广播已存活子代理、default_permission_mode 无消费——修复项挂 ROADMAP）。

### SDR-005（2026-10-13）问询关闭的终态语义：终止回合、归还输入权，而非交模型裁量

- **背景与动机**：问询关闭（用户不回答、直接关掉面板）此前回传给模型的是一句不含行为指引的说明（「用户已放弃提问」），模型据此自行决定继续、假设默认值或重问。问题在于关闭是一个**意图不明**的动作——它可能意味着「稍后再说」「问得不对」「想自己打字」「误触」中的任何一种，而「别问了你自己定」这一种已有专用显式通道（auto 模式拒绝问询并附自行决策指引）。在用户选择了 manual/yolo（即「我要参与决策」）的会话里，把一个意图不明的拒绝交由模型猜测着继续执行，等于用猜测冒充共识——与权限域的根本原则（意图不清晰时不行动）相悖。跨端公平性：该语义须在 web 与桌面端一致成立，不因接入面不同而漂移。
- **决策**：关闭问询的终态语义定为——**终止当前回合、归还输入权**：a) 引擎向模型回传「用户关闭了问询且未说明原因」的结果并强制结束该回合（引擎侧保证，不依赖模型自觉）；b) 提供原因输入的接入面下，用户可附可选原因，随关闭结果一并回传（原因不改变终止语义）；c) 后台问询被关闭时任务以取消定局、通知发起代理停止依赖该答案的决策，但不打断其无关工作；d) 关闭语义是「暂不回答」而非「永久拒绝」——后续回合允许换方式重问，但禁止原样重问（防骚扰循环）；e) 「自行决策」委托只经 auto 模式显式表达，关闭动作永不构成委托。
- **被否决的备选**：a) 维持现状（回传空结果、无行为指引，模型自行裁量）——在协作模式（manual/yolo）下拿猜测冒充共识，属不负责任的产品特性；且模型可能立刻重问形成骚扰循环；b) 关闭后弹二级输入强制用户填原因——把轻量动作变成重交互，惩罚误触与「稍后再说」的多数场景，误触用户被迫解释自己没做的事；c) 按关闭延迟（弹出后多久关闭）推断意图置信度——启发式伪装成语义，脆弱且不可验收。
- **影响范围**：US8（关闭条目重写为终态、新增后台问询关闭与重问护栏条目、auto 条目补显式通道说明）、US10（回合收尾补问询关闭与其他未决交互的边界）；architecture ADR-007（回传形态与终止机制）；术语表 AP5（同批登记）；tool-calling 域 US4.9 关闭条目同步；context 增补现状快照（§9）；ROADMAP 挂实现项。

### SDR-006（2026-10-24）问询通道的连接韧性：投递失败挂起等待重连，而非立即错误

- **背景与动机**：问询依赖「引擎把问题送到用户眼前」的呈现通道。长回合场景（一次回合持续数十分钟，期间等待后台任务）下，客户端连接可能中途断开并重连（网页刷新、心跳超时踢除、客户端进程重启）。现状是通道一断，进行中回合内的问询投递立即以连接错误收尾、回传模型一句技术性错误——用户没有任何感知（界面上没有问题，也没有错误提示），只能指望模型自觉降级为纯文本提问。这违反两条域内原则：其一，通道故障是**基础设施事件**，不是用户的意图表达，把它混进「用户已作答/已拒绝/已关闭」的终态语义里，是对用户意图的伪造；其二，用户体验上「该问的问题没问出来」是静默失败——问题没送达、错误也不可见。会话本身具备重连韧性（已登记待决的问询在通道恢复后重新送达），通道断开期间的问询完全有条件等到重连再送达。
- **决策**：问询投递遇到通道断开时改为**挂起等待重连**：a) 已登记为待决的问询在通道断开期间保持待决，投递侧不把它收尾为错误；b) 等待期间引擎保持回合存活（既有存活心跳机制，不新增用户可见行为）；c) 等待有明确上限（缺省 5 分钟，服务配置可调），到期以可区分的「通道不可用」错误收尾并附「改用纯文本提问或稍后重试」指引——上限存在是因为无界等待会占住回合且用户无从知晓；到期收尾**不写入防重问护栏**（护栏只由用户主动关闭触发——通道故障不是用户意图，模型可原样重发问询）；d) 断开期间新发起的问询同规则处理；e) 重连后问题重新送达用户眼前（等待重连的问询经投递重试送达），用户可作答。
- **范围边界**：等待的前提是「用户曾经在场」——会话从未连接过交互承接方（无头、嵌入式未注册处理器）不适用本决策，维持各自既有缺省（立即收尾，无作答），不给无头场景引入 5 分钟空等。问询卡片在重连后的界面重现为独立开放项（不随本决策交付）；审批的同类投递路径（`approval.ask`）**不随本决策变更**——审批已有「投递失败保持待决」的挂起语义，仅缺少等待上限与送达重试，作为开放项另行裁决。后台问询在挂起等待期间被用户显式停止时，其待决登记随之撤销（不等待上限兜底）。
- **被否决的备选**：a) 维持现状（立即错误回传模型）——把基础设施故障伪装成问询失败，用户不可感知，行为完全依赖模型自觉，不可验收；b) 无限等待重连——工程上最「忠实」，但回合被无限占住且用户毫无感知，缺省不可接受；若个别部署确有此需求，可将上限配置为足够大的值（审批的「无上限挂起」与问询此处不同：审批断连后可从待决列表恢复、用户有感知面，问询在重连送达前用户无任何感知渠道，两者感知面不同，不强行对齐；审批的等待上限策略作为开放项另行评估）；c) 断开即终止回合——比立即错误更激进，用户一次网络抖动就丢掉整轮工作，不成比例。
- **影响范围**：US8（新增「断线重连期间问询可恢复」「挂起等待有上限」「断开期间新问询同规则」「从未连接的会话不适用」条目）、US10（新增「通道不可用终态」收尾条目）；architecture ADR-008（挂起机制与等待环）；context 增补现状快照；ROADMAP 挂实现项。
