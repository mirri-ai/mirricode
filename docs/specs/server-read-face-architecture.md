# 服务端读面架构方针 — ADR（源自 26GB 峰值事故）

> 状态：v1.0 · 2026-10-16 · 三条横切架构方针的决策记录。
> 证据链：`docs/specs/reports/26g-peak-analysis-20261016.md`（根因分析）、`docs/specs/reports/26g-peak-retrospective-20261016.md`（复盘）。
> 教程化的展开（含代码对照与自查清单）：[server-read-face-best-practices.md](server-read-face-best-practices.md)。
> 适用范围：`mirri-server`、`mirri-embedded` 的全部 RPC 响应面；`mirri-core` 的恢复热路径；`apps/mirri-web` 的数据获取层。新 RPC / 新读面的 review 以本文为依据。

## 0. 为什么需要这三条方针

2026-10 的三层内存事故（26GB → 7-16GB → 收敛）中，杀伤力最大的根因不是局部手误，而是**同一批架构缺失在多个模块独立发芽**：列表端点直接倾倒领域实体（发生 3 次）、客户端被迫用"全量列表 + find"凑单实体查询、恢复热路径的复制成本藏在纯函数接口背后。方针不登记，下个新模块会重新发明一次 `task.list`。本文件把三条从事故中确立的方针登记为正式 ADR。

## ADR-R1：读面是设计出来的投影，不是领域实体的顺手倾倒

- **背景与动机**：`task.list` 直接序列化完整 `AgentTask`（含单实体上限 1MB 的 `output`）、resume summary 内嵌每 agent 全量 history×2 份、`message.list` 假分页——三个模块各自把内部实体原样倒上协议，同一反模式独立发芽三次（事故编号 S5a / P2 / P1）。实体内部字段演进（output 上限提升）自动变成协议膨胀，无人把关；消费方各自在客户端再裁剪，裁剪逻辑三处漂移。
- **决策**：**领域实体不上线**。每个 RPC 的响应是一个为该消费场景显式定义的投影（DTO）：
  - 列表类响应 = 摘要（标识/状态/时间/截断文本）+ 截断标志（`*_truncated`）+ 真实度量（`*_bytes`/总数）；完整字段一律走单实体端点（见 ADR-R2）；
  - 详情类响应默认也是"够用投影"；全量形态必须显式请求（如 `includeFull: true`），且全量路径不进任何高频/循环调用面；
  - 投影定义与协议契约测试绑定（`mirri-proto/src/rpc/authoritative-methods.tsv` + b1/b7 套件），截断字段的形状变化过契约闸门。
- **否决项与理由**：客户端自适应裁剪被否决——三次事故已经证明它把成本留在服务端、把正确性留给人肉记忆；实体直接上线 + 文档警示被否决——警示无法执行，实体字段演进不可见地放大响应。
- **影响范围**：全部列表/读面 RPC 的响应契约；`session-consistency`、`session-management` 域的列表面复核；新 RPC review 检查项（速查表见 best-practices 文末）。

## ADR-R2：API 从消费场景出发设计，单实体查询是一等公民

- **背景与动机**：因后端无单任务查询端点，web 客户端 `getTask` 以"全量 `task.list` 再 `find`"凑合（S5b）。该形态在数据量小时完全正常，被每秒轮询循环调用后成为 24GiB/30min 的出站洪水。API 清单的真实来源是"内部有什么就暴露什么"（`SessionManager::tasks()` 存在 → 暴露 task.list），而非"消费方有哪几类信息需求"。
- **决策**：**新增 RPC 前先做消费面枚举**，最小问题集：
  1. 消费方（TUI / web / desktop / SDK 用户）需要哪几类信息？按场景列全；
  2. 每类场景的最小满足是什么——**单实体查询（`get(id)` 与 `getX(id, tail)`）必须在列表端点之前设计**，而非事后补；
  3. 状态变化的第一信源是事件流，轮询只做兜底且必须可参数化收窄（`activeOnly` 类过滤是列表端点的必备参数，不是可选项）。
- **否决项与理由**："按需再补端点"被否决——S5b 证明客户端不会等待：没有正道它就用全量列表拼一条邪道，且邪道在小数据下不可见；只暴露聚合列表被否决——与单实体一等公民矛盾，且已在事故中证伪。
- **影响范围**：RPC 注册表新增条目的 review 流程；`apps/mirri-web/src/api/` 的客户端 API 层（禁止 `list().find()` 形态）；轮询相关 composable 的四格表（问什么/频率/字节/停止条件）。

## ADR-R3：恢复热路径的接口把成本写在签名上

- **背景与动机**：`reduce_with_limits(state, op) -> state` 的纯函数式签名在类型上零成本暗示，clone 藏在函数体内；fold 逐条日志复制累积状态导致 O(N²)，7000 条日志恢复 18.5s（事故 R1，修复后 9.4ms）。接口"优雅"与测试全绿（150+）都无法暴露代价，炸点只对数据规模敏感。
- **决策**：**重放/恢复路径的公共接口以就地变体为主接口**（`&mut` 状态、借用切片、单遍派生），纯函数式签名只作为薄包装保留给真正需要不可变语义的调用方（迁移模式已在 `apply_with_limits` 落地，为本方针的参照实现）。核心热路径接口设计时的硬性自查：复制是否可见于签名（`&` vs `&mut` / 返回值拥有 vs 借用）、锁内是否含 await（两段式：await 段 + 借用段）、一次磁盘读是否派生全部缓存（含"空"结果，无条件写）。
- **否决项与理由**：保持纯函数式主接口 + 文档标注性能被否决——R1 事故证明标注不可执行；全面改写所有调用方被否决——薄包装迁移模式已给出零 breaking 的渐进路径，没有理由付更高成本。
- **影响范围**：`mirri-core` 的 reducer / restore / journal 读面接口风格；新核心接口的 review 标准；`agent-context-assembly` 与持久化域的读接口复核。
