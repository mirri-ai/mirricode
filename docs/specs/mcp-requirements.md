# MCP 域需求文档（User Stories）

> 状态：v1（基于 2026-09-04 架构讨论整理） ·
> 本文是 MCP 域需求侧的唯一事实源（内部规格文档，不进文档站构建，中文单语）。
> 产品愿景相关：配置管理、连接治理、热更新、OAuth。
> 配套文档：`mcp-architecture.md`（RFC，下称「架构文档」）· [mcp-context.md](mcp-context.md)（现状参考）。
> 验收标准统一采用 Given-When-Then 格式；优先级 P0 > P1 > P2，与架构文档 Rollout 阶段对应。

## 0. 角色定义（Personas）

| 角色 | 场景 | 核心诉求 |
|---|---|---|
| **单人开发者**（终端 TUI 为主，单工作区） | 终端里开一个会话干活 | MCP 别拖慢我启动；配置改了马上生效 |
| **多工作区用户**（desktop/web，同时开多个工作区） | 桌面端并行多个项目 | 别为每个工作区重复拉起同一批 MCP 进程 |
| **项目成员**（项目级配置的维护者） | 给仓库配置团队共享的 MCP | 项目配置跟着仓库走，不泄漏到别的工作区 |
| **管理界面用户**（配置页/设置面板） | 在没有打开任何工作区时管理 MCP | 无上下文也能增删改查、测试连接、开关工具 |

> 术语：**工作区**（workspace）= 一个打开的项目上下文；**用户全局层**（user）/ **项目根层**（project-root，git 团队共享文件）/ **项目本地层**（project）/ **插件**（plugin）= 四种配置来源层。

## 1. Epic E1：用户级 MCP 配置管理（无工作区 / 无会话上下文）

> 对应架构文档 4.1 / Rollout P1。解决"配置页面在没有工作区、没有会话的情况下，用户级 MCP 配置管理怎么呈现"。

### US1.1 查看用户级服务器列表（P0）

作为管理界面用户，我想在任何工作区打开之前查看我配置的全部 MCP 服务器，以便了解当前用户级的 MCP 资产。

验收：
- Given 用户级配置了 3 个服务器，When 在无工作区上下文请求配置列表，Then 返回 3 条记录，每条含名称、连接方式（本地进程/HTTP/SSE）、启用状态、工具开关配置、超时配置
- Given 用户级配置为空，When 请求列表，Then 返回空列表（不报错）

### US1.2 新增/修改/删除用户级服务器（P0）

作为管理界面用户，我想在无工作区上下文增删改用户级 MCP 服务器配置，以便不依赖任何工作区维护我的全局工具集。

验收：
- Given 无工作区上下文，When 提交一个本地进程类型的服务器配置（名称/命令/参数/环境变量），Then 完整写入用户级配置（要么成功、要么失败，绝不留下半份坏文件），且后续任意工作区都能使用它
- Given 用户级已存在同名服务器，When 提交新配置，Then 该条目被完整替换（整体替换语义，非字段拼合）
- Given 删除一个已启用的服务器，When 该服务器在某个工作区中已连接，Then 连接被断开且工具从可用面移除（活跃会话与调用拦截视角见 US4.4/US4.5）
- Given 两个界面同时编辑同一配置文件，When 后提交的一方不带正确的版本号，Then 提交被拒绝并提示冲突（并发编辑冲突检测）

### US1.3 连接测试（不落盘先试）（P1）

作为管理界面用户，我想在保存配置前测试一个 MCP 服务器能否连通，以便避免保存一堆坏配置。

验收：
- Given 一份未保存的本地进程类型服务器配置，When 发起连接测试，Then 系统临时启动一次真实连接进行验证（含清点工具数量），返回成功（含工具数量）或失败（含原因），且不留任何持久痕迹（临时进程退出、不写入任何配置）
- Given 已保存的服务器，When 发起测试，Then 按已存配置实测并返回同样格式的结果
- Given 服务器启动超过配置的启动时限，When 测试，Then 返回明确的超时失败而非挂起

### US1.4 用户级工具开关（P0）

作为管理界面用户，我想对某个用户级服务器下的单个工具启用/禁用，以便全局屏蔽危险或无用的工具、只保留需要的。

验收：
- Given 用户级服务器 `db` 提供 6 个工具，When 在用户级禁用其中 `db.query`，Then 所有工作区中该工具均不可见/不可调用，其余 5 个不受影响
- Given 用户级禁用了 `db.query`，When 某项目级配置把它显式设为启用，Then 该工作区内 `db.query` 可用（项目层覆盖用户层——见 US2.3）
- Given 工具开关配置修改后，When 该服务器已有活跃连接，Then 工具可用面**不重连即更新**（工具级变更不断连接——依赖 E4）

### US1.5 插件捆绑服务器的工具开关（P0）

作为管理界面用户，我想对插件捆绑提供的 MCP 服务器做工具级启用/禁用，以便屏蔽插件里危险或用不到的工具而不必卸载整个插件。

> 差距依据：既有能力只覆盖"整个 server"的启停（详见 [mcp-context.md](mcp-context.md) §5）；本 US 把粒度细化到"单个工具"。

验收：
- Given 插件 P 提供 server S（3 个工具），When 在 MCP 配置页禁用 S 的某个工具，Then 该工具全局不可见/不可调用、其余工具不受影响，且插件自身内容不发生任何改动（偏好保存在用户的个人设置里，与既有的服务器级启用开关同存储、同生命周期）
- Given 已对 S 设置工具过滤，When 插件 P 升级，Then 过滤按（插件, 服务器）继续生效（插件资产更新不冲掉用户偏好）
- Given 插件 P 卸载后重装，Then 工具过滤偏好重置（随安装记录移除清理，与启用开关行为一致）
- Given 对插件来源的 server 提交连接定义修改（命令/环境变量/连接方式），When 提交，Then 被拒绝——插件层连接定义只读（见架构文档裁决 A1）
- Given 插件 server 的总开关与工具过滤并存，When server 被禁用，Then 整个 server 不可用（工具过滤随 server 一起失效，重新启用后过滤继续生效）

### US1.6 配置值的环境变量引用（P1）

作为管理界面用户/项目成员，我想在配置的字符串值里引用环境变量（`${VAR}` / `${env:VAR}`），以便凭据留在环境里、配置文件可安全共享，且变量未定义时能得到指明变量的诊断。

> 差距依据：环境变量展开已双端实现，本 US 固化为契约并补两个缺口——**可诊断性**与**配置页呈现语义**（原文/解析分离，详见 [mcp-context.md](mcp-context.md) §5）。

验收：
- Given 任意配置层的字符串值含 `${MY_KEY}` 或 `${env:MY_KEY}`，When 引擎加载配置并建立连接，Then 该值按运行环境替换为真实值（两种写法等价）；替换只发生在字符串值里，条目名称等其它位置不动；替换结果不会被再次替换（防止把真实值里的引用语法又当成引用）
- Given `MY_KEY` 未定义，When 加载，Then 替换为空（兼容既有行为），且加载诊断指明是哪个变量未定义、位于哪份配置的哪个服务器，而不是只报一句格式校验失败
- Given 配置页请求配置列表，When 响应到达，Then 返回的配置为**原文**（`${VAR}` 引用保留），解析后的真实值不出现在任何**默认**响应中（显式预览请求除外——见 N9 / D-S3 修订，2026-09-08）
- Given 用户想在保存前验证解析结果，When 发起连接测试（US1.3），Then 按替换后的真实值实测；因未定义变量导致连接失败时，结果诊断含变量名
- Given 插件自带的服务器配置含 `${VAR}`，When 该服务器建立连接，Then 同样按运行环境替换（与配置文件语义一致；现状差距见 [mcp-context.md](mcp-context.md) §1）

### US1.7 查看服务器的工具清单（P0）

作为管理界面用户/项目成员，我想查看某个服务器提供的全部工具及其启用状态，以便决定开关哪些工具（US1.4/US2.3 的操作前提）。

验收：
- Given 服务器已连接，When 请求其工具清单，Then 返回全部工具（名称、说明、当前启用/禁用状态——按调用方上下文的作用域合并结果）
- Given 服务器未连接，When 请求，Then 返回明确的"未连接"语义而非空列表假象
- Given 服务器版本未变且已有缓存的清单，When 再次请求，Then 不向服务器重复清点（对齐 US3.4）

## 2. Epic E2：工作区级 MCP 配置管理

> 对应架构文档 4.1 裁决 A2 / Rollout P1。解决"配置功能不仅支持用户级，还要支持工作区级"。

### US2.1 分层配置视图（含来源标注）（P0）

作为项目成员，我想在工作区内看到 MCP 配置的合并结果以及每条来自哪一层，以便理解"这个服务器为什么在/为什么被改了"。

验收：
- Given 用户全局层有 server A、项目根层有 server B、项目本地层有 server C，When 在该工作区请求合并视图，Then 返回 A/B/C 三条，每条标注来源层（用户全局 / 项目根 / 项目本地）
- Given 用户全局层与项目本地层都配置了同名 server D（不同命令），When 请求合并视图，Then 只返回一条 D，来源标注项目本地（项目本地覆盖用户全局），用户全局层原值可通过分层视图单独查看
- Given 插件提供了 server E，When 请求合并视图，Then E 可见且来源标注插件（含插件内名与运行时名）；对 E 的连接定义写入被拒绝（插件资产只读），对 E 的工具过滤写入被接受（US1.5）

### US2.2 项目层增删改（P0）

作为项目成员，我想给当前工作区添加项目专属的 MCP 服务器（配置落在项目本地层），以便团队成员共享而全局其它项目不受影响。

验收：
- Given 在工作区内提交一个项目作用域的服务器配置，Then 写入项目本地层（不是项目根的团队共享文件），该服务器仅在本工作区可见
- Given 请求写入项目根层的团队共享文件，Then 被拒绝——项目根是 git 共享资产，接口面只读（视图可见、不可写）
- Given 项目本地层配置修改，When 团队成员拉取仓库后打开工作区，Then 新配置自动生效

### US2.3 工作区级工具开关（覆盖用户级）（P0）

作为项目成员，我想在项目层覆盖某个服务器的工具开关，以便项目内启用/禁用与我的个人全局偏好不同的工具组合。

验收：
- Given 用户全局层 server `db` 禁用 `db.query`（US1.4 场景），When 项目本地层把 `db.query` 显式设为启用，Then 仅本工作区内该工具可用
- Given 项目本地层禁用 `db.migrate`，When 其他工作区（无项目覆盖）请求工具列表，Then 那些工作区的 `db.migrate` 仍按用户全局层配置可用

### US2.4 配置分层独立读写（P1）

作为项目成员，我想分别读取用户全局层原文与工作区层（项目根 + 项目本地）合并结果，以便配置页面分区呈现"个人全局 / 项目"两栏。

验收：
- Given 请求用户全局作用域，Then 仅返回用户全局层原文条目
- Given 请求项目作用域，Then 返回项目根与项目本地合并后的条目（不含用户全局层）
- Given 在某个工作区内请求且不指定作用域，Then 返回全量合并视图 + 来源标注（同 US2.1）

## 3. Epic E3：连接与性能（连接爆炸治理）

> 对应架构文档 4.2 / Rollout P2、P4。解决"MCP 连接爆炸"与"会话启动等待 MCP 缓慢"。

### US3.1 用户级服务器进程内单连接（P0）

作为多工作区用户，我希望用户级 MCP 服务器在同一进程内只建立一次连接，以便 8 个工作区不会拉起 8 份相同的服务器进程。

验收：
- Given 桌面进程打开 8 个工作区且用户级配置了 5 个本地进程服务器，Then 系统中该批服务器的子进程总数为 5（而非 40），内存占用相应缩减
- Given 两个工作区同时调用用户级服务器的工具，Then 两次调用复用同一连接（无新增连接）
- Given 某服务器为有状态协议（HTTP 会话），Then 跨工作区复用同一会话连接（同一进程内）

### US3.2 打开工作区不等待用户级 MCP（P0）

作为单人开发者/多工作区用户，我希望工作区与会话的创建不被 MCP 连接阻塞，以便在终端或桌面端新建会话时立即就绪（现状见 [mcp-context.md](mcp-context.md) §2）。

验收：
- Given 用户级有 5 个 MCP 服务器（其中 1 个故意配置为慢启动 30s），When 创建会话 / 打开工作区，Then 创建操作在引擎常规耗时内完成，与该慢服务器无因果
- Given 慢服务器最终连接成功，When 其后调用它的工具，Then 正常工作
- Given 用户级服务器全部不可达，When 打开工作区并开始对话，Then 仅在真正调用 MCP 工具时收到相应错误，其余功能不受影响

### US3.3 工作区级服务器懒连接（P1）→ 已裁决不实施（SDR-008，2026-10-12）

作为项目成员，我希望项目层的服务器在首次被需要时才连接，以便打开了工作区但没用到项目 MCP 的会话不付连接成本。

## 4. Epic E4：配置热更新

> 对应架构文档 4.3 / Rollout P3。解决"旧版运行时开关退役后，配置驱动的即时性"。

### US4.1 启用即连 / 禁用即断（P0）

作为管理界面用户，我在配置页切换某服务器的启用开关后，希望连接状态立即跟随，以便界面上看到的就是真实的。

验收：
- Given server Z 已连接，When 把 Z 切换为禁用，Then Z 的连接在 1 秒内断开（本地进程退出/网络连接断开），工具从可用面移除，状态变化的通知到达
- Given server Z 已禁用，When 切换为启用，Then 触发连接并广播状态（连接中 → 已连接/失败）
- Given Z 在断开时有在途工具调用，Then 在途调用完成或以明确错误终止（不悬挂）——具体策略实现阶段裁决

### US4.2 配置变更触达连接（P0）

作为管理界面用户，当我修改服务器配置（命令/环境变量/连接方式/凭据）后，希望连接按新配置重建，以便"改了就生效"不需要重载或重启。

验收：
- Given server W 已连接，When 修改其连接方式或启动命令，Then 旧连接断开、按新配置重连、状态通知序列完整（已连接 → 连接中 → 已连接/失败）
- Given 仅修改工具开关，Then 连接保持，仅工具可用面更新（不重连）
- Given 仅修改超时配置，Then 连接保持，新超时对后续操作生效

### US4.3 状态变更事件（P1）

作为管理界面用户/桌面端，我希望订阅 MCP 服务器状态变化通知，以便配置页与状态指示器实时刷新而无需轮询。

验收：
- Given 订阅了 MCP 状态通知，When 任一服务器状态变化（连接中/已连接/失败/已禁用/需授权），Then 收到含服务器名、所属层（用户全局/工作区/插件）、新状态的通知
- Given 服务器状态未发生变化，Then 不产生状态变化通知（无噪音）

### US4.4 活跃会话的工具面即时同步（P0）

作为正在与 agent 对话的用户，我在修改 MCP 配置（新增/删除/启停服务器、开关单个工具）后，希望**正在执行任务的 agent 会话在下一步就反映变更**——新增的工具可调用、删除或关闭的工具不再出现且不可调用，以便不需要重开会话或重启。

验收：
- Given 某会话正在执行任务，When 新增/启用一个 server 且其连接成功，Then 该会话执行下一步时即可调用该 server 的工具
- Given 某会话正在执行任务，When 删除/禁用一个 server 或关闭其某个工具，Then 该会话执行下一步时该工具不再出现在工具清单、调用被明确拒绝
- Given 某会话在变更后新派发了子代理（其角色声明允许使用相关工具），When 该子代理装配，Then 它同样在下一步即可调用新增/启用的工具（消费主体覆盖会话内全部 agent，含子代理——架构 ADR-014；子代理工具面的授权范围由其角色声明统治，见子代理域 SDR-014）
- Given 上述任一变更生效，Then 从变更写入配置到活跃会话工具面更新的延迟同进程 ≤ 1 秒（对齐 N2）
- Given 同一变更涉及多个作用域（用户全局/项目），Then 只有该作用域可达的会话受影响（对齐 US2.3/US7.1）

### US4.5 调用时点的强制校验（防御纵深）（P0）

作为用户，当某个 server 或工具被禁用后，即使调用方（agent 的模型输出、历史重放、其它调用入口）仍试图调用它，也希望在工具调用的校验环节被硬性拦截，以便"禁用"是真实的安全边界而非仅是"界面上看不见"。

验收：
- Given 某工具已被禁用，When 任何入口发起对它的调用（含模型基于过期清单的输出、直接指定工具名的调用），Then 在调用校验环节被拦截，返回明确的"该工具已被禁用"错误，不触达 server
- Given 某个 server 已禁用/已删除，When 调用其任一工具，Then 同样在调用校验环节被拦截，不建立也不复用连接
- Given 禁用被解除（启用/恢复），When 后续调用，Then 放行——拦截与放行随有效配置即时翻转（延迟对齐 N2）
- Given 多层配置并存（如用户全局禁用、项目层启用），Then 校验按该调用所属作用域的有效配置判定（对齐 US2.3）
- Given 工具清单存在缓存或快照，Then 校验不依赖其新鲜度——以调用时点的有效配置为准

## 5. Epic E5：状态观测

> 对应架构文档 4.4 / Rollout P2、P4。状态视图的两级呈现：全局无上下文视图 + 工作区合并视图（接口形状见架构文档）。

### US5.1 全局状态视图（无上下文）（P1）

作为管理界面用户，我想在无工作区上下文查看用户级服务器的实时连接状态，以便配置页顶部直接显示"3 已连接 / 1 失败 / 1 需授权"。

验收：
- Given 用户级 5 个服务器（3 连接、1 失败、1 需授权），When 无上下文请求状态，Then 返回 5 条含状态/错误信息/工具数的记录
- Given 某服务器连接中，Then 状态如实反映"连接中"而非阻塞等待

### US5.2 工作区合并状态视图（P1）

作为多工作区用户，我想在工作区内看到合并后的服务器状态（用户全局 + 项目层，含被遮蔽关系），以便理解当前会话可用的全部 MCP。

验收：
- Given 用户全局层 A（连接）、项目本地层 B（按需连接、尚未连接）、项目本地层同名 A'（连接），When 请求工作区状态，Then 返回合并视图：A'（标注遮蔽了用户全局 A）与 B（标注"未连接"），被遮蔽的 A 不出现在默认视图，分层视图可查

### US5.3 手动重连（P1）

作为用户，我想对失败/需授权的服务器手动触发重连，以便网络恢复或授权完成后立即恢复而不必重启。

验收：
- Given server 失败，When 触发重连，Then 重走连接流程并广播结果；并发多次触发只执行一次（并发去重）
- Given 重连成功，Then 已缓存的工具清单作废重取、状态变化的通知到达

### US5.4 启动指标（P2）

作为用户/开发者，我想查看 MCP 启动指标（各服务器连接耗时、工具清点耗时），以便诊断启动慢的问题。

验收：
- Given 完成过一轮连接，When 请求启动指标，Then 返回每服务器的连接耗时与失败原因汇总

## 6. Epic E6：OAuth 授权流

> 对应架构文档 4.5 / Rollout P4。远程（HTTP/SSE）服务器的授权闭环。

### US6.1 需授权的引导与完成授权（P1）

作为用户，当某远程（HTTP）MCP 服务器因未授权（401）进入"需授权"状态时，我想获得授权引导并在完成浏览器授权后自动恢复连接，以便远程服务器的登录体验与其它工具一致。

验收：
- Given 远程 server V 返回未授权（401），Then 状态变为"需授权"并保留在状态视图中
- Given 用户对 V 发起授权，Then 返回授权链接；用户在浏览器完成授权后，授权结果被自动接收，V 自动重连为"已连接"，状态变化的通知到达
- Given 用户在授权页点了拒绝，Then V 保持"需授权"，错误信息可查，无残留半完成状态
- Given 本地进程类服务器（协议上不会出现未授权），Then 发起授权对其返回明确的不适用提示

### US6.2 令牌存储兼容（P2）

作为集成者，我希望 MCP 授权令牌的存储位置与格式与 TS 引擎既有存储兼容，以便引擎外的读取方（诊断工具/迁移脚本）不受影响。

验收：
- Given TS 引擎已写入的 MCP 授权令牌，When rust 引擎读取，Then 语义一致（存储布局不变）；反向亦然

## 7. Epic E7：隔离与安全

> 对应架构文档 4.2 / 5。项目层凭据与同名遮蔽。

### US7.1 项目层凭据不跨工作区泄漏（P0）

作为项目成员，我希望项目层服务器的配置（含环境变量/凭据）与连接只在所属工作区存在，以便仓库专属的内部服务器不会暴露给其它工作区。

验收：
- Given 工作区 P1 配置了带内部凭据的项目层服务器，When 在另一工作区 P2 请求任何配置/状态/工具视图，Then 该服务器及其凭据完全不可见
- Given 工作区 P1 配置了项目层服务器，When 在另一工作区 P2 的会话中直接调用该服务器的工具，Then 在调用校验环节被拒绝，不建立跨工作区连接（强制点语义对齐 US4.5）
- Given 工作区 P1 关闭，Then 其项目层连接断开、子进程退出

### US7.2 同名遮蔽语义可解释（P1）

作为项目成员，当用户全局层与项目层存在同名服务器时，我希望遮蔽规则明确且可见，以便不会误用错误配置的服务器。

验收：
- Given 用户全局层 A 与项目层 A' 并存，Then 工作区内一切调用走 A'；A 的存在与被遮蔽事实在分层视图中可见（US5.2）
- Given 项目层 A' 被删除，Then 下次视图合并后用户全局层 A 恢复可见可用（无需重启）

## 9. Out of Scope

## 11. SDR 记录

### SDR-001 解析值预览例外（2026-09-08）

1. **背景与动机**：MCP 设置页需要「显示真实值」预览，让配置作者核对占位符（`${VAR}`）引用是否写对——即看到环境变量展开后的真实值。原 N9 禁止解析值出现在任何响应中，该能力无法成立。
2. **决策**：N9 修订为终态——解析值仍不得进入任何**默认**响应、通知与日志；唯一例外为**显式预览请求**可返回解析值（不缓存、不进通知/日志）。决策来源：mcp-settings-page-requirements.md D-S3。
3. **被否决的备选**：① 完全移除预览、验证一律走连接测试诊断——丢失"一眼确认占位符写没写对"的价值；② 仅对非敏感键本地预览——逻辑分叉，且"哪些键敏感"无可靠边界。
4. **影响范围**：NFR N9、US1.6 验收第 3 条（正文条目已同步更新为终态）。

### SDR-002 活跃会话工具面即时同步显式化（2026-09-08）

1. **背景与动机**："任何 MCP 修改须及时触达正在执行任务的 agent 会话（可感知/可调用）"此前只散见于连接层面的验收（US1.2/US1.4/US4.2 的"工具可用面更新"），无一条以活跃会话为第一主体，存在"连接已变、执行中会话的工具面未变"仍合规的灰区。
2. **决策**：E4 新增 US4.4，以活跃会话为验收主体（下一步可感知/可调用，延迟对齐 N2）；N2 的延迟指标扩展覆盖"到会话工具面生效"。
3. **被否决的备选**：仅依赖既有"工具可用面更新"表述——验收主体是连接而非会话，无法证明触达执行中的任务。
4. **影响范围**：E4 新增 US4.4；NFR N2 扩展；设置页需求 PS2.3/PS3.1/PS3.3 补对应验收条目；架构文档 §4.3 补链路终点说明（对应 ADR-002）。

### SDR-003 调用时点强制校验显式化（2026-09-08）

1. **背景与动机**：评审追问"禁用/启用的 server 或工具应在工具调用的校验硬环节被及时阻拦/放开，有没有明确记录"——既有验收只写"不可见/不可调用"，未区分**清单可见性**与**调用时强制**，无法证明拦截发生在调用管线，也无法排除"仅从清单移除、直接调用仍被放行"的实现，且未定义判定依据（调用时点的有效配置 vs 可能过期的清单快照）。
2. **决策**：E4 新增 US4.5，把"调用校验环节"定义为独立强制点：拦截/放行以调用时点的有效配置为准、按调用所属作用域判定、不依赖清单快照新鲜度（防御纵深——清单注册与调用校验是两层独立防线）。
3. **被否决的备选**：① 仅依赖清单可见性（模型看不到就不会调）——清单可能过期，且存在绕过模型的直接调用入口；② 仅在连接层拦截——禁用的 server 本就不应建立/复用连接，但强制点必须前置于连接判定，否则直接调用路径先于连接检查即失败。
4. **影响范围**：E4 新增 US4.5；设置页需求 PS3.1/PS3.3 补对应验收条目；架构文档 §4.3 补调用时强制点说明（对应 ADR-003）。

### SDR-004 隔离需求的调用时强制显式化（2026-09-08）

1. **背景与动机**：按需求评审检查清单 R2（可见性 ≠ 强制）复查 US7.1——原文只定义"跨工作区视图不可见"，未定义另一工作区的会话**直接调用**项目层服务器工具时的拦截，存在"视图不可见但调用被放行"的合规灰区。
2. **决策**：US7.1 增补验收：跨工作区的直接调用在调用校验环节被拒绝、不建立跨工作区连接（强制点语义对齐 US4.5）。
3. **被否决的备选**：仅靠视图不可见——存在绕过视图的直接调用入口（与 SDR-003 同理）。
4. **影响范围**：US7.1。

### SDR-005 产品语言合规化（2026-09-08）

1. **背景与动机**：`docs/specs/AGENTS.md` 确立"需求文档必须使用非技术人员能读懂的产品语言"（评审检查清单 R8）后复查本文——约 25 处技术词未转译（接口方法名、字段名、"乐观锁"、五态英文枚举等），违反禁入第 4 条。
2. **决策**：全文合规化改写：技术词转译为产品语义（如"乐观锁"→"并发编辑冲突检测"、五态中文化、方法名改为能力描述并指向架构文档）；术语表加入 §0；验收语义不变。
3. **被否决的备选**：保留技术表述以方便实现者对照——需求文档的读者是产品与评审者，实现对照靠架构文档与指向，不为实现便利牺牲读者正确性。
4. **影响范围**：全文语言层面；无任何验收语义变更（US7.1 的新增验收独立记录于 SDR-004）。

### SDR-006 工具清单查看的域级显式化（2026-09-08）

1. **背景与动机**：按评审检查清单 R9/R1 复查——工具开关（US1.4/US2.3，P0）的操作前提"查看某服务器提供了哪些工具及当前开关状态"在域文档缺位，此前仅设置页需求 PS3.2 覆盖页面场景；域需求是跨端事实源，缺位意味着 TUI/desktop 等其它管理入口无依据、各自发明。
2. **决策**：E1 新增 US1.7（P0，任意管理入口可用，不限页面）；接口形状（`mcp.tools`）已由架构 ADR-001 定义，无架构新增。
3. **被否决的备选**：仅由设置页需求覆盖——页面文档只约束页面，域级能力缺位会分裂为多个入口各自定义。
4. **影响范围**：US1.7；设置页 PS3.2 为其页面形态（语义一致，无需修改）。

### SDR-007 阶段映射注记与验收措辞修正（2026-09-08）

1. **背景与动机**：规格评审发现两处文档级缺口——① US1.7（工具清单查看，P0）的后端查询入口按架构 ADR-004 落在 Rollout P2，而 §10 映射表把 E1 整体标为 P1，读者会据此预期 P1 交付即可闭环 US1.7，实际无法验收；E7 行把 US7.2（P1）并入整行 P0 未分级标注。② US4.3 验收第 2 条"未发生变化的重复查询不产生通知"主语混乱（"查询"与"事件"混写），可被误读为查询行为受事件机制约束。
2. **决策**：① §10 E1 行加例外注记（US1.7 后端落 P2）、E7 行内分级标注（US7.1 P0 / US7.2 P1）；② US4.3 验收第 2 条措辞修正为"服务器状态未发生变化时不产生状态变化通知"。两者均为文档层修正，无验收语义变更。
3. **被否决的备选**：把 US1.7 优先级降为 P1 以对齐阶段——需求优先级（用户价值维度）与架构阶段（交付顺序维度）是两个轴，映射表的职责是显式暴露错位而非抹平。
4. **影响范围**：§10 映射表、US4.3 验收第 2 条；无验收语义变更。

### SDR-008 懒连接与工具清单缓存裁决不实施（2026-10-12）

1. **背景与动机**：US3.3（工作区级懒连接）与 US3.4（工具清单缓存）立项时假定的两个前提经代码核验不成立——① 连接并不阻塞启动：现状为「服务启动后即在后台连接全部已启用服务器，不阻塞任何请求，用户创建会话/打开工作区零等待」（用户效果与 US3.2 一致），懒连接解决的"启动等待"痛点实际不存在；② 服务器连上后会发状态变化通知（`event.mcp.server.status`，含连接建立事件），消费者可实时感知，不需要额外的"连接中"过渡提示设计。
2. **决策**：两项均**裁决不实施**，US3.3/US3.4 标记为不实施并保留原文留痕。核心理由：服务器在会话进行中途才连上会导致**工具清单（LLM 请求前缀的组成部分）在会话中段突变**，破坏供应商提示缓存的前缀稳定性（与缓存命中率治理方向相悖——同类问题曾以实测证伪过「中段修剪」方案，教训一致）；而现状「启动后即后台全连、首轮对话前基本就绪」恰好保证了工具表稳定。工具清单缓存亦无必要：清单只在连接建立时清点一次，后续读取走内存态，不存在重复清点成本；连接保持期间清单即缓存。
3. **被否决的备选**：① 实现懒连接 + "连接中"过渡提示——收益（省下未用服务器的常驻连接）小于成本（工具表中段突变破坏缓存、UI 状态机复杂化、事件时序更难推理）；② 实现带 TTL 的清单缓存——现状连接期间清单天然驻留内存，TTL 失效机制解决的问题（server 静默更新）已有重连逃生门覆盖；③ 按 server 维度选择懒/急混合——复杂度陡增且把时序语义变成不可预测的组合。
4. **影响范围**：US3.3/US3.4 标注不实施；架构文档裁决 A3 相应修订（ADR-013）；ROADMAP P4 缺口行收口；reports 审计文档同步。

### SDR-008 补遗：无会话授权入口搁置与令牌布局不迁移（2026-10-12）

同日补充裁决（与 SDR-008 主体同批）：

1. **无会话授权入口（搁置）**：`mcp.auth.start/complete` 无会话场景的独立授权发起入口**搁置**。现状授权流程在会话内完整可用（合成工具引导），设置页主动发起属便利项非缺口。触发条件与 web 事件消费的 PDM 决策同构：真实需求出现（用户在无会话场景需要即时授权）再立项，届时引擎侧 wire 面（auth 域 `auth.startLogin` 族已有参照）与设置页 UI 为独立小批次。
2. **令牌布局跨引擎统一（不做）**：F-8 关闭为不实施。过渡期代价 = 换引擎入口需对 OAuth 类工具服务器重新授权一次，可接受；单独迁移等于为将被移除的 TS 引擎维护兼容层。随 TS 引擎退役自然消失。
3. **影响范围**：ROADMAP P4 缺口行与 F-8 行收口；MCP 域 P4 阶段至此无剩余实施项（OAuth 机制已落地，其余全部裁决关闭/搁置）。
