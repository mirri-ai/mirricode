# 执行环境域 — 需求文档

> 状态：v1 基线 · 2026-09-12 ·
> 本文是执行环境域需求侧的唯一事实源（内部规格文档，不进文档站构建，中文单语）。
> 产品愿景：**agent 在任何宿主机上"落地即能干活"——文件、命令、终端的开箱即用与可预期行为，跨平台一致、跨环境同构**；用户不需要理解底层差异就能信任执行结果。
> 基线说明：本域为**新建域**。本文描述执行环境域引擎应支持的**终态行为**，作为 **Rust 内核的对齐基线（parity baseline）**——这是 Rust 需要对齐的**底线**，不是 Rust 被限制的天花板；Rust 可以（且应当）做得更好，文中不设上限。TS 引擎当前实现现状（含实现归属与差距）与代码事实见 [execution-environment-context.md](execution-environment-context.md)，机制与数据流见 [execution-environment-architecture.md](execution-environment-architecture.md)。
> **范围边界**：本域覆盖 agent 执行的**底层环境层**——执行环境抽象（本地/远程同构面）、主机环境探测（OS/壳/路径风格/主目录）、文件系统访问原语（读写守卫、编码、监视）、进程创建与生命周期（spawn/等待/终止/进程树）、终端仿真（PTY、尺寸、输出回放）、执行沙箱面（路径约束与逃逸防护，即"工作区内"的判定机制）、搜索二进制（rg）的管理。**不覆盖**：工作区注册/信任/生命周期/跨引擎注册表（见工作区管理域）；工具调用的参数契约与结果回传模型、以及文件类工具的逐工具参数语义（见工具调用域及其内建工具规格）；Bash 工具的超时转后台与任务面板（见后台任务域）；会话与回合管理（见会话管理域）；审批流（见 approval 域）。
> **标记约定**：〔TS 基线〕= TS 引擎现网已支持；〔TS 基线·v1-only〕= 仅 v1 引擎路径支持、v2 无对应能力（仍被消费方使用时注明）；〔设计增强〕= 超出 TS 现网的设计（不因 TS 没有而削弱）；〔提案〕= 尚不存在任何实现的建议。

## 0. 角色定义（Personas）

| 角色 | 场景 | 核心诉求 |
|---|---|---|
| **跨平台用户**（macOS/Linux/Windows） | 在任意系统上启动 agent | 不装一堆前置依赖就能干活；找不到必要组件时得到**可执行的修复指引**，而不是一句晦涩报错 |
| **命令执行用户** | 让 agent 跑构建/测试/git | 命令的输出完整不丢失（哪怕进程已被杀）；失败原因可读；杀就杀干净，不留孤儿进程 |
| **终端用户**（web/TUI） | 在界面上开一个交互终端 | 打开即用；断线重连不丢历史输出；关掉就真关掉 |
| **宿主集成者**（把引擎嵌进自己产品的开发者） | 决定 agent 在**哪台机器**上执行 | 换一个执行环境（本地→远程→宿主桥接）时，agent 的全部文件/命令/终端行为**不变形** |
| **安全敏感用户** | 打开来源不明的仓库 | agent 的文件访问被约束在明确的目录集合内；符号链接等手段不能绕过约束 |

## Epic E1：执行环境抽象 — 同一双手，不同的机器〔TS 基线〕

> 解决"agent 与具体机器的解耦"。上层（工具、文件界面、终端）只面向一个统一的执行环境接口；环境实现可以是本机、远程机器或宿主桥接，上层无感知。

### US1.1 本地执行环境（P0）

作为命令执行用户，我想让 agent 默认在启动它的机器上干活，以便零配置开箱即用。

验收：
- Given 用户在任意目录启动引擎，When 会话创建，Then 文件读写、命令执行、终端创建默认发生在本机，工作目录为该会话所属工作区的根目录
- Given 多个工作区/会话在同一进程内并发活动，When 各自执行命令或解析相对路径，Then 各自的工作目录互不串扰（一个会话切目录不污染另一个会话）
- Given 引擎从一个未加载用户登录环境的上下文启动（如图标启动器），When 会话创建，Then 命令仍能找到用户登录后安装的工具（如包管理器安装的 CLI），不需要用户手动改配置

### US1.2 远程执行环境（P1）〔TS 基线·v1-only｜库层能力，无产品入口〕

作为宿主集成者，我想把 agent 的执行环境指向一台远程机器，以便 agent 在远程项目上干活而本地只做展示。

验收：
- Given 宿主提供远程机器的地址、账号与密钥/密码，When 执行环境被构造，Then 远程连接建立后，文件读写、目录列举、命令执行全部发生在**远程机器**上，上层无感知
- Given 远程执行环境配置了初始工作目录，When 该目录不存在或不是目录，Then 构造失败并给出明确错误，不会静默落到别处
- Given 远程命令携带环境变量，When 命令执行，Then 变量注入不受远程服务器对环境变量传递的白名单限制（在远端壳内联注入）
- Given 远程文件操作遇到的错误（不存在/权限拒绝/连接断开），When 错误返回上层，Then 按统一错误类型区分，可程序化分支处理
- Given 远程环境不再使用，When 显式关闭，Then 连接释放，后续操作明确失败而不是悬挂
- Given 远程环境的能力差异（如不支持大小写不敏感的通配匹配），When 请求落在不支持的能力上，Then 以明确错误暴露，而不是静默给错结果
- 〔设计增强〕远程环境的主机事实（OS/壳/路径风格）在基线中以明确错误暴露"远程探测未接线"，终态须补齐远程探测（或以显式契约声明不可用），不允许上层把"远程探测失败"误读为"本地事实"
- 〔TS 现状注记〕该能力在 TS 引擎中以库层形式存在（含 SSH/SFTP 传输），但**没有任何产品界面或宿主流程默认使用它**；基线记录其行为契约，Rust 是否提升为产品能力由 Rust 决定

### US1.3 宿主桥接执行环境（P1）〔TS 基线·v1-only〕

作为宿主集成者（如把 agent 嵌入编辑器的集成方），我想让宿主代理一部分文件访问，以便 agent 读写的是宿主眼中的真实状态（如编辑器里未保存的缓冲区）。

验收：
- Given 宿主声明了可代读写的文件能力，When agent 读/写这类文件，Then 请求经桥接转发给宿主，结果以宿主视角为准
- Given 宿主未声明文件能力，When agent 执行，Then 一切行为与纯本地执行完全一致（桥接对工具层不可见，不引入能力开关逻辑）
- Given 桥接之外的其余操作（命令执行、目录、路径解析），When 发生，Then 始终委派给本地环境执行
- 〔TS 现状注记〕桥接面为**文本读写**：字节级/二进制读仍走本地执行（宿主 RPC 仅承载文本），向宿主的字节写入按有损文本转发——宿主集成者不应预期"二进制也走宿主视角"

### US1.4 执行环境上下文绑定（P0）

作为宿主集成者，我想让"当前用哪个执行环境"作为执行上下文隐式传递，以便深层代码不必层层透传环境引用。

验收：
- Given 一段执行被绑定到某个执行环境，When 该执行树内的任何文件/命令调用发生，Then 使用被绑定的环境与它的工作目录
- Given 两段并发执行各自绑定不同环境/工作目录，When 交错运行，Then 互不污染（绑定按并发上下文隔离）
- Given 某段执行树没有绑定任何环境，When 它尝试执行文件/命令操作，Then 得到明确的"环境未初始化"错误与修复指引，而不是落到隐式的全局默认

## Epic E2：主机环境探测 — 落地即知身处的机器〔TS 基线〕

> 解决"agent 启动时对宿主机的一次性认知"。OS、CPU 架构、版本、命令壳路径、路径风格、用户主目录，探测一次、进程内缓存、会话可用。

### US2.1 操作系统事实（P0）

作为跨平台用户，我想让引擎准确知道自己运行在什么系统上，以便平台分支行为正确。

验收：
- Given 引擎在 macOS/Linux/Windows 上启动，When 环境探测完成，Then OS 类别、CPU 架构、系统版本三项事实可供所有上层使用
- Given 探测结果，When 引擎判断路径风格，Then macOS/Linux 按 POSIX 路径处理、Windows 按 Windows 路径处理（含盘符/UNC/正反斜杠差异）

### US2.2 命令壳发现（P0）

作为命令执行用户，我想让引擎自动找到可用的命令壳，以便 shell 命令在任何机器上可执行。

验收：
- Given macOS/Linux 主机，When 探测，Then 依次在常见位置找 bash；找到则用它，找不到则回退系统 sh（不失败）
- Given Windows 主机，When 探测，Then 定位 Git Bash（从 git 可执行文件布局推断、查询 git 安装信息、常见安装路径、用户主目录下的安装位置多路探测）
- Given Windows 主机找不到任何 bash，When 探测完成，Then 得到带**已检查路径清单与安装指引**（指向 Git for Windows 官网）的错误，以及"用户可设置环境变量指向自定义 bash"的逃生门；该错误在产品面上呈现为可操作的修复提示
- Given 用户设置了壳路径覆盖变量，When 探测，Then 覆盖变量优先于全部自动探测（且仅在路径真实存在时生效）
- Given 探测过程需要查询 git 安装信息，When 查询，Then 查询带超时（5 秒），超时或失败不影响其余探测路径
- 〔TS 现状注记〕壳路径覆盖变量在不同引擎路径上的变量名不一致（详见 context 差异矩阵），基线要求：**统一为一个规范变量名，两个引擎路径都识别**

### US2.3 登录壳路径补全（P0）

作为跨平台用户，我想让从图形界面/服务上下文启动的引擎也能找到我登录后才能用的命令，以便 agent 不会"看不见"我装的工具。

验收：
- Given 引擎从一个缺少用户登录 PATH 的上下文启动（$SHELL 可解析，或可从操作系统用户数据库解析出登录壳），When 环境初始化，Then 引擎执行一次用户登录壳（login shell）并把登录 PATH 中**当前缺失的条目**追加到命令查找路径，已有条目顺序与优先级不变
- Given 登录壳探测失败（壳不可解析、执行超时 5 秒、输出无 PATH），When 环境初始化完成，Then 现有 PATH 原样保留（静默降级，不报错、不阻塞启动）
- Given 登录 PATH 中包含相对路径或空条目，When 合并，Then 这些条目**不被引入**（避免把"当前目录查找"这种依赖 cwd 的行为扩大到任意工作区）
- Given Windows 主机，When 环境初始化，Then 该补全过程跳过（该问题仅存在于 POSIX 登录壳）
- Given 引擎进程存续期间多次初始化，When 补全，Then 只执行一次登录壳探测（结果缓存）

### US2.4 探测时机与可用性保证（P0）

作为宿主集成者，我想让主机事实在会话创建前就绪，以便会话内代码永远同步读取、无竞态。

验收：
- Given 引擎启动，When 组装流程执行，Then 环境探测（含壳发现与登录 PATH 补全）在**任何会话创建之前**完成等待
- Given 探测未完成时有代码读取主机事实，When 读取发生，Then 得到明确的"就绪前访问"编程错误（指引等待就绪信号），而不是读到半成品数据

## Epic E3：文件系统访问 — 读得准、写得稳、看得见变化〔TS 基线〕

> 解决"agent 的文件 I/O 原语"。产品界面（web 文件树）与文件类工具共同依赖这一层；逐工具的参数语义归工具调用域。

### US3.1 读文件（P0）

作为命令执行用户，我想让 agent 以可预期的方式读文件，以便大文件、二进制、非常规编码都不会让会话卡死或返回垃圾。

验收：
- Given 一个文本文件，When 读取，Then 默认按 UTF-8 解码；内容不是合法 UTF-8 时，调用方按需选择"报错 / 替换字符 / 丢弃坏字节"三种策略之一，且合法的替换字符（U+FFFD）在"丢弃"策略下**不被误删**
- Given 一个大文件，When 读取，Then 支持只读前 N 字节、按行分页读（从头、从指定行、取尾部 N 行）三种窗口，不需要整文件载入
- Given 一个文件被并发读取与写入，When 读取，Then 读取反映打开时刻的内容，不因并发写悬挂
- Given 路径不存在 / 是目录 / 权限不足，When 读取，Then 得到按错误类别区分的稳定错误（见 US3.6），不会以空内容或乱码冒充成功
- Given 文件内容疑似二进制，When 读取方需要判定，Then 提供二进制探测原语（头部采样：含 NUL 字节即判二进制；否则不可打印字符占比超阈值判二进制），供上层选择"明确拒绝 / 自动改以字节编码回传"等策略（逐工具策略归工具调用域）

### US3.2 写文件（P0）

作为命令执行用户，我想让 agent 的写文件可靠，以便重要数据不丢、并发创建不冲突。

验收：
- Given 写一个文本/字节内容，When 写入，Then 覆盖或追加模式可选，默认覆盖
- Given 写入目标父目录不存在，When 写入，Then 父目录自动逐级创建（写入工具语义；本层提供递归创建原语）
- Given 需要独占创建（仅在文件不存在时写入），When 使用独占创建原语，Then 已存在时返回明确的"未创建"信号（不抛错），且创建成功时**内容强制落盘**（防断电丢数据）
- Given 创建目录，When 目录已存在，Then "已存在但不是目录"与"已存在且是目录（幂等成功或按需报错）"两种情况被区分，文件占位冲突不冒充成功

### US3.3 目录与元数据（P0）

作为命令执行用户，我想让 agent 能列举目录与读取文件元数据，以便了解文件系统结构。

验收：
- Given 一个目录，When 列举，Then 返回条目名（含类型判定：文件/目录/符号链接），路径拼接在根路径（如 `/`、盘符根）下正确
- Given 需要文件元数据（大小、修改时间、类型），When 查询，Then 单查与批量查（批量中单项失败不影响其余项，失败项返回明确空值标记）都可用
- Given 需要路径的"真实位置"（穿透符号链接），When 解析，Then 返回全部链接分量解析后的规范路径；路径不存在时按"不存在"错误返回
- Given 通配模式（glob），When 在目录树上匹配，Then `*`/`?`/字符类/`**` 递归语义与业界惯例一致；目录树中存在指回祖先的符号链接时**不陷入循环**；文件系统不提供可靠目录标识（如部分 Windows 文件系统）时循环保护降级为不追踪（正常遍历不受影响）

### US3.4 文件监视（P1）

作为终端用户/命令执行用户，我想让界面实时反映文件变化，以便 agent 的改动和外部改动都看得见。

验收：
- Given 我订阅了工作区内某些路径的变更，When 这些路径下发生创建/修改/删除，Then 我收到按事件类别（created/modified/deleted）与对象类别（file/directory）分类的变更通知
- Given 同一路径短时间内连续变化，When 通知投递，Then 按防抖窗口（默认 200ms，可配置）合并，避免通知风暴
- Given 单个防抖窗口内变更过多（默认超过 500 条），When 投递，Then 该窗口降级为"截断"信号并附事件总数（明确告知客户端需要全量重新同步），而不是悄悄丢一半
- Given 一个连接订阅的路径数超过上限（默认 100），When 再订阅，Then 超限错误明确返回，不会拖垮其他连接〔TS 基线·v1-only：现行 v2 监视无路径数上限，上限作为终态要求保留——v2 无界订阅本身是待收敛的缺口〕
- Given 变更洪峰导致底层监视器报错，When 发生，Then 记录告警、服务继续运行（单个 watcher 失败不拖垮整个监视服务）
- Given 无人订阅任何路径，When 最后一个订阅取消，Then 底层监视器关闭（不空耗资源）；有人订阅时重新开启
- Given 订阅的路径受 gitignore 约束，When 投递，Then 默认被忽略文件（如 `.git/`）的变更不投递

### US3.5 远程文件语义一致性（P1）〔TS 基线·v1-only｜同 US1.2〕

作为宿主集成者，我想让远程执行环境的文件行为与本地尽量一致，以便上层无感知。

验收：
- Given 远程环境下的读/写/列举/建目录，When 执行，Then 语义与本地一致（含"已存在但不是目录"的冲突区分、递归创建的逐级冲突检测、并发创建竞态的收敛处理）
- Given 远程按行读取，When 执行，Then 尾部换行不产生多余空行（与本地一致的共同保证）
  - 〔TS 现状注记〕TS 本地实现的行**保留**行终止符、远程实现**剥离**行终止符（两侧不一致）；终态裁决：行终止符的保留/剥离语义统一为一个（由实现方以 SDR 裁决择一），不允许"同一接口在两个环境下行形状不同"
- Given 远程通配匹配，When 大小写不敏感模式被请求，Then 返回明确的"当前环境不支持"错误，而不是静默给错结果

### US3.6 错误契约（P0）

作为宿主集成者，我想让文件错误以稳定类别呈现，以便程序化分支处理与用户可读提示并存。

验收：
- Given 底层操作系统错误（不存在/是目录/不是目录/已存在/权限拒绝/目录非空/资源不可用），When 到达上层，Then 被翻译为稳定的域名化错误码（不暴露平台细节），每个错误码带用户可读标题与"是否可重试"标记（资源不可用与未知错误标记可重试）；无法识别的错误归入"未知"类
- Given 同一个错误被重复翻译，When 翻译，Then 幂等（已是域内错误的原样通过）

## Epic E4：进程执行 — 生得快、杀得净、读得全〔TS 基线〕

> 解决"agent 起命令的原语"。超时策略、后台化、任务面板归后台任务域/工具调用域；本域提供 spawn/等待/终止/流面。

### US4.1 进程创建（P0）

作为命令执行用户，我想让 agent 以受控方式起子进程，以便命令执行可管理。

验收：
- Given 一个命令与其参数列表，When 创建进程，Then 进程在新进程组中启动（POSIX），stdin/stdout/stderr 均为管道，窗口环境不弹窗（Windows 隐藏控制台）
- Given 命令不存在或不可执行，When 创建，Then 创建立即失败并返回含命令名与原因的错误，**不会**返回一个"看似启动但实际不存在"的进程句柄（避免向已死进程写输入）
- Given 需要指定工作目录与环境变量覆盖，When 创建，Then 未指定时继承宿主进程环境；指定时覆盖项叠加在宿主环境之上（不凭空丢弃宿主环境）
- Given 进程需要长期驻留（不随父进程退出），When 创建时选择脱离模式，Then 进程脱离终端会话组独立存活

### US4.2 进程生命周期（P0）

作为命令执行用户，我想让进程的结束状态明确、终止彻底，以便不留孤儿进程与僵尸句柄。

验收：
- Given 进程启动成功，When 等待其退出，Then 得到退出码；进程异常终止时得到明确的异常码（不与正常退出混淆）
- Given 我终止一个进程，When 终止发生在 POSIX，Then **整个进程组**收到信号（shell 拉起的后台孙子进程一起结束，不留孤儿）；默认信号为可优雅退出的终止信号
- Given 我终止一个进程，When 终止发生在 Windows，Then **整棵进程树被强制终止**（含全部后代），且不依赖目标进程自己转发信号
- Given 进程在我终止它之前已退出，When 终止调用，Then 视为成功（幂等），不报"无此进程"错误
- Given 终止时权限不足（无法对进程组发信号），When 终止调用，Then 回退为对直系子进程直接发信号（尽力而为），而不是直接失败
- Given 进程句柄不再需要，When 释放，Then stdin/stdout/stderr 流被销毁、底层资源归还；释放幂等

### US4.3 输出流完整性（P0）

作为命令执行用户，我想让命令输出在流式消费与事后读取两种模式下都完整，以便先看进展、后取全量。

验收：
- Given 进程持续输出，When 消费方读取慢于生产，Then 流施加背压（生产暂停），不无限吃内存
- Given 消费方在进程结束后才读取 stdout/stderr，When 读取，Then 已缓冲的输出仍可读（不是空的），缓冲上限适度（不无限累积）
- Given 需要把 stderr 合并进 stdout 的场景（统一输出流），When 创建进程时选择合并，Then 调用方拿到的 stderr 句柄与 stdout 指向同一流（消费方无需区分两个管道）
  - 〔TS 现状注记〕TS 的合并实现仅让两个句柄同流，子进程真实的 stderr 管道未被读取合并（内容不会按序出现在 stdout 上，且未读管道存在写满阻塞子进程的隐患）——"内容级合并"为超出 TS 现状的设计增强：合并模式下子进程 stderr 内容应按序并入输出流，且不留未读管道

### US4.4 远程进程语义（P1）〔TS 基线·v1-only｜同 US1.2〕

作为宿主集成者，我想让远程命令的终止语义可预期。

验收：
- Given 远程进程被终止，When 终止信号发出，Then 按远程会话协议的信号语义投递（信号名去前缀），远端进程可优雅退出
- Given 远程命令的工作目录与环境变量，When 命令构造，Then 工作目录以"切目录后执行"方式注入、环境变量以壳内联赋值注入（绕过服务器环境变量白名单），且变量名经合法性校验（杜绝注入）
- Given 远程进程不存在操作系统级 PID 可用性，When 上层读取 PID，Then 得到明确的"不可用"哨兵值（不假装有 PID）

## Epic E5：终端仿真 — 会说话的窗口〔TS 基线〕

> 解决"交互式终端"。PTY 创建、输出流、尺寸、断线回放、关闭。
> 〔TS 现状注记〕v2 的服务层与 PTY 层完备（创建/回放/退出），但输入、调整尺寸与附加订阅的**传输通道尚未接线**（详见 context §3.3-4 与提案 P5）——本 Epic 描述终态行为契约，其现网消费面以服务层 API 为准。

### US5.1 创建与使用（P0）

作为终端用户，我想在会话内开一个真终端，以便跑交互式程序（vim、watch、REPL）。

验收：
- Given 我请求创建终端，When 请求合法，Then 一个伪终端（PTY）在指定壳、指定工作目录、指定初始尺寸下启动，返回终端标识
- Given 创建时未指定工作目录，When 创建，Then 默认为该会话工作区的根目录；指定的工作目录必须落在工作区允许的目录集合内（逃逸被拒，返回明确错误）
- Given 创建时未指定壳/尺寸，When 创建，Then 使用宿主默认壳与默认尺寸（80×24）；壳解析先看环境变量 $SHELL，未设置/为空时按平台回退到**该平台上确实存在**的默认壳（POSIX 回退系统 sh；Windows 回退 PowerShell）
  - 〔TS 现状注记〕TS v2 的回退是无平台分支的"系统 sh"（Windows 上通常不存在，PTY 启动会失败）；v1 实现了 Windows 的 PowerShell 回退但空字符串 $SHELL 不触发回退（缺陷）。跨平台回退的正确性按终态要求，不与任一现状对齐
- Given 终端在运行，When 我向它写入输入，Then 输入即时送达远端程序（交互不卡）
- Given 终端在运行，When 我调整它的尺寸（列/行），Then PTY 尺寸即时更新（运行中的全屏程序收到尺寸变化）
- Given 我显式关闭终端，When 关闭，Then PTY 被杀死，终端状态置"已退出"（退出码为空，与自然退出可区分）

### US5.2 输出与回放（P0）

作为终端用户，我想断线重连后不丢历史输出，以便像没断过一样继续。

验收：
- Given 终端持续产生输出，When 输出发生，Then 每帧输出带单调递增序号投递给订阅方
- Given 我重新附加到已运行一段时间的终端（携带"上次看到第几帧"），When 附加完成，Then 缓冲中其后所有帧被回放，并告知回放了多少帧
- Given 终端已退出后我重新附加，When 附加，Then 退出帧在回放中**总能补发**（视为最后的帧），不会"重连了但不知道终端已死"
- Given 终端输出超过缓冲上限（默认 2000 帧），When 新输出产生，Then 最老的帧被丢弃（环形缓冲），回放只覆盖最近窗口
- Given 终端自然退出，When 退出发生，Then 状态置"已退出"、记录退出时间与退出码、向订阅方投递退出事件、清理订阅

### US5.3 终端不存在与生命周期兜底（P0）

作为终端用户，我想让对不存在终端的操作得到明确错误、引擎退出时终端被清理。

验收：
- Given 我操作一个不存在的终端标识，When 操作发生，Then 得到含该标识与所属会话的"不存在"错误
- Given 引擎进程整体关闭，When 关闭，Then 全部存活的 PTY 被杀死（单个杀失败不影响其余）
- 〔设计增强〕终端创建请求中的工作目录以"相对工作区"为唯一合法形态（绝对路径直接拒绝），防止界面层与沙箱面口径不一——本层对**服务层 API** 强制该约束，工具/集成层的绝对路径需求走工具调用域的路径守卫

## Epic E6：执行沙箱面 — 边界清楚、放宽显式〔TS 基线〕

> 解决"agent 能碰哪些路径"。本域提供的是**共享的允许目录集**（主工作区根 ∪ 附加目录集）与"是否在工作区内"的判定机制；文件类界面（文件树/读/列/监视）以此为约束**并做符号链接防逃逸**；agent 文件工具的守卫口径（词法判定、绝对越界的处理）由工具调用域的内建工具规格定义（见其 §0.5 路径守卫）——两侧共享同一允许目录集数据，约束严格度各自声明。

### US6.1 工作区路径约束（P0）

作为安全敏感用户，我想让 agent 的文件访问默认约束在工作区目录集合内，以便陌生仓库里的内容不会指到我的系统其他地方。

验收：
- Given 一个相对路径，When 文件类界面（文件树/读取/列举/建目录）解析它，Then 相对工作区根解析；解析后落在工作区外（含 `..` 穿越、绝对路径形态）时被拒绝，错误带被拒原因（空/绝对/穿越段/解析到界外）
- Given 工作区内某条路径是指向区外的符号链接（或路径中某段是），When 该路径被**文件类界面**解析，Then 符号链接逃逸被检测并拒绝（错误明示"经符号链接逃逸"）；指向**尚不存在**目标的路径（还没创建的文件）也能正确判定（解析最长存在前缀）
  - 〔TS 现状注记〕agent 文件工具（Read/Write/Edit/Glob/Grep）的守卫是**词法判定**（不解析符号链接），符号链接维度的防逃逸不覆盖工具路径——该口径差异由工具调用域 §0.5 声明；本条验收针对文件类界面（服务层）
- Given 两个约束根目录（主根 + 附加根）分别与目标比较，When 判定"是否在界内"，Then 任一根内的路径都合法；判定容错路径分隔符差异与盘符根拼接（`//entry` 这类畸形不出现）
- Given 一个目录集合被声明为执行允许目录集（附加目录），When 附加目录生效，Then 主工作区之外的这些目录内的文件访问被放行（对文件树、读、监视、终端一致生效；agent 文件工具经其守卫消费同一目录集）

### US6.2 附加目录集（P1）

作为多项目用户，我想临时或持久地把工作区外的目录纳入允许范围（如 monorepo 兄弟目录、脚手架模板目录），以便 agent 干活不被一刀切挡住。

验收：
- Given 我添加一个附加目录并选择持久化，When 添加完成，Then 该目录写入工作区本地配置文件，进程重启后仍生效；配置文件被外部编辑时变更自动生效（带短防抖）
- Given 我添加一个附加目录并选择仅本次，When 添加完成，Then 该目录对该工作区的**全部会话**立即可见（同一工作区内共享），进程退出后消失
- Given 附加目录集合变化，When 变化发生，Then 已存在的会话立即以新集合判定路径（无需重启会话），并有一个变更信号供界面刷新提示

### US6.3 沙箱的诚实边界（P0）

作为安全敏感用户，我想清楚地知道"约束到工作区"到底挡住了什么，以便我对安全性有正确预期。

验收：
- Given agent 的文件访问被约束在工作区，When 我用 Bash 等命令执行工具访问界外路径，Then 命令级访问不受此文件约束机制限制（该机制只约束文件类界面/工具的路径解析；命令可去任何用户权限可达之处）——引擎在文档与产品描述中不夸大为"沙箱"
- Given 操作系统级隔离能力（容器、受限执行、网络隔离），When 它被问及是否属于本基线，Then 答案是否定的——该诉求只存在于 §未来增强提案，不作为已支持能力呈现

## Epic E7：搜索二进制管理 — rg 的自给自足〔TS 基线〕

> 解决"内容搜索/文件名搜索对 ripgrep 的依赖"。

### US7.1 定位、下载与降级（P0）

作为跨平台用户，我想让搜索功能在装了 rg 的机器上飞快、没装 rg 的机器上也能用，以便搜索永不"彻底不可用"。

验收（按消费方分层，〔TS 现状注记〕标明现状归属）：
- Given 系统安装了 rg，When 任一搜索路径首次执行，Then 使用系统 rg（探测结果缓存，不重复探测）
- Given agent 搜索工具（Glob/Grep）所在路径没装 rg，When 首次搜索发生，Then 自动从官方渠道下载对应平台的 rg（固定版本、带完整性校验）安装到引擎自己的二进制目录，下次直接复用；下载的二进制校验失败时明确报告"渠道内容可能被篡改"而不是继续使用
- Given 工作区文件搜索路径（文件树内容搜索）没装 rg 且缓存也没有，When 搜索发生，Then 降级为纯引擎内实现（结果正确但更慢，降级被遥测记录）〔TS 现状注记：该路径无自动下载能力；agent 工具路径下载失败时报错并附安装/手动放置指引，无降级——两路径行为不一致，统一供给见提案 P3〕
- Given rg 进程执行（agent 工具路径），When 执行发生，Then 带超时（默认 20 秒）、超时先优雅后强制的两段终止（5 秒宽限）、输出体积上限（各 10MB，防巨量输出拖垮会话）；工作区搜索路径的超时（默认 30 秒）见 US7.2

### US7.2 会话内搜索的限额与中止（P1）

作为命令执行用户，我想让搜索结果有界、可中止，以便大仓库搜索不失控。

验收：
- Given 搜索请求数量上限（文件数/单文件命中数/总命中数），When 达到任一上限，Then 搜索停止并返回已得结果 + 截断标记（不悄悄截断）
- Given 搜索进行中发生超时（工作区文件搜索路径默认 30 秒），When 超时，Then 已有结果时返回部分结果 + 截断标记；完全无结果时报"搜索超时"错误
- Given 搜索进行中被取消，When 取消发生，Then rg 子进程被杀死、句柄释放

## Epic E8：非功能与可观测性〔TS 基线〕

### US8.1 探测与初始化的时间预算（P1）

- Given 引擎冷启动，When 主机环境探测（含 Windows 的 git 查询、登录壳探测）执行，Then 每个子探测都有独立超时（5 秒量级），单个探测失败不阻塞其余探测；整体探测在秒级完成
- Given 探测结果在进程内缓存，When 多会话/多工作区并发使用，Then 不重复探测（探测次数与并发度无关）

### US8.2 资源上限的显式化（P1）

- Given 本域的每类资源消耗（读窗口大小、监视路径数、变更窗口事件数、搜索命中数、子进程输出量），When 达到上限，Then 以明确信号（截断标记/超限错误/降级提示）呈现，绝不静默截断或无界消耗

### US8.3 可观测性（P2）

- Given 关键降级路径发生（rg 缺失降级、登录壳探测失败、watcher 错误），When 发生，Then 以遥测事件或告警记录；**用户可见的告警**（日志/toast）对同一原因去重（一次性），遥测事件不在此限〔TS 现状注记：TS v1 有一次性告警；v2 为每次遥测事件（rg 降级）或完全静默（登录壳探测失败），"告警去重"按终态要求〕

### US8.4 并发与隔离（P1）

- Given 同进程多工作区/多会话并发使用文件、进程、终端原语，When 并发执行，Then 相互隔离（工作目录、环境变量叠加、订阅集合互不串扰）；共享的单例资源（主机事实探测、rg 定位、监视器）被安全复用

## 9. 未来增强提案（超出 TS 现状，明确标注为提案）

> 以下内容**不是 TS 引擎已支持的能力**，是本域 recon 中识别出的改进方向，供 Rust Core 与产品侧评估。它们不参与幻觉检查、不作为对齐基线。

### P1 操作系统级沙箱〔提案〕

现状：执行沙箱面只有"路径约束"一层（E6），命令执行不受约束。提案：引入真正的 OS 级隔离（macOS Seatbelt/sandbox-exec、Linux namespace/seccomp 或容器、Windows AppContainer），按工作区信任等级分级授予能力（文件系统范围、网络开关、进程数上限）；未信任工作区默认进入受限档。

### P2 远程执行环境产品化〔提案〕

现状：SSH 远程执行环境仅存在于库层（US1.2），无产品入口。提案：把"会话跑在远程机器"提升为一等产品能力（工作区可指向远程，探测/文件/进程/终端全链路远程化），并与工作区信任模型联动（远程工作区默认不可信）。

### P3 搜索二进制统一管理〔提案〕

现状：rg 定位/下载存在两套实现（工具层带自动下载、工作区文件搜索层无下载能力），行为与文案不一致。提案：Rust 内核统一为单一二进制供给服务（定位→缓存→下载→校验→共享），所有消费方（工具、文件搜索、未来功能）同一来源。

### P4 环境探测实现合一〔提案〕

现状：主机环境探测存在两份同源分叉（库层与引擎层），已出现变量名与探测集合的行为漂移（详见 context 差异矩阵）。提案：Rust 内核收敛为单一探测模块，避免双实现漂移；壳路径覆盖变量收敛为单一规范名。

### P5 终端完整产品面〔提案〕

提案：Rust 内核交付完整的终端交互面（输入、调整尺寸、附加订阅一条通道打通），并考虑跨进程的终端持久化（重开引擎续看）。现状缺口（服务层完备而传输通道未接线）见 context §3.3-4。
