# 会话管理 — 需求文档

> 状态：v1.1 基线 · 2026-10-09 · 已裁决 Q1–Q3（见决策记录 SDR）· Epic U 撤销为提案（SDR-009；开放项见 ROADMAP）· E5 fork 扩展增补（SDR-010/011/012 + 忙碌护栏口径，均已裁决）· US4.4 运行状态可见（SDR-013，2026-10-13）· 「使用」清单收窄（SDR-014，2026-10-23，取代 SDR-004 回复产出子句）· 界面"会话不存在"识别以语义为准（SDR-015，2026-10-25）·
> 本文是会话管理域需求侧的唯一事实源（内部规格文档，不进文档站构建，中文单语）。
> 产品愿景：**侧边栏是用户亲手布置的书架**——重要的置顶、顺手的排好、新来的可见；顺序在哪个界面看都一样，且刷新重开不变形。
> 配套文档：技术形状与契约机制见 [session-management-architecture.md](session-management-architecture.md)；现状盘点见 [session-management-context.md](session-management-context.md)；执行状态见 [session-management-ROADMAP.md](session-management-ROADMAP.md)。
> 术语规范：置顶（G1）、撤销（G5）、会话恢复（S1）、归档会话（S2）、工作区桶（S3）、会话索引（S4）的唯一定义见 [glossary.md](glossary.md)。
> 范围边界：本域覆盖**用户对会话列表与工作区列表的组织交互**（置顶、拖拽排序）与**会话的生命周期交互**（复制、派生、顺带问，E5；对话撤销，Epic U）；数据的存储、持久化与兼容机制属会话持久化域（[session-persistence-requirements.md](session-persistence-requirements.md)）；搜索与归档的列表可见性裁决见本域 N3（非目标之外的一处例外裁决）。

## 0. 角色定义

| 角色 | 场景 | 核心诉求 |
|---|---|---|
| **整理者**（收拾侧边栏的用户） | 会话与工作区多了，拖一拖、钉一钉 | 我排的顺序说了算；排完就固定，不被自动行为搅乱 |
| **浏览用户**（每天打开列表找会话的人） | 凭记忆的位置找东西 | 顺序稳定可预期——上次在哪这次还在哪 |
| **多端用户**（网页、终端换着用的人） | 在一个界面排好，换另一个界面继续用 | 顺序跟着数据走，不跟着设备走 |

## 1. Epic E1：置顶（P0）

> 解决"重要的永远在最上面"。置顶是显式的用户声明，不是智能猜测。

### US1.1 置顶置顶（P0）

作为整理者，我想把一个会话置顶，让它出现在其所在工作区分组的最上方，以便常用的东西永远第一眼可见。

验收：
- Given 任意会话（进行中的或已收起的），When 我执行置顶，Then 操作成功，该会话立即出现在其工作区分组顶部的**置顶区**
- Given 已有其他置顶会话，When 再置顶一个，Then 新置顶的会话出现在置顶区内其他会话**之前**（最后置顶的在最上）
- Given 一个已归档的会话，When 我执行置顶，Then 操作成功并记录标记，但该会话**不出现在任何默认列表中**（归档压过置顶——收纳中的东西不上书架）
- Given 置顶完成，When 刷新页面或重开应用，Then 置顶状态保持

### US1.2 取消置顶（P0）

作为整理者，我想取消置顶让会话回到普通位置，以便置顶区只留真正重要的。

验收：
- Given 一个置顶的会话，When 我取消置顶，Then 该会话离开置顶区，回到普通区**顶部**
- Given 取消置顶后刷新或重开，Then 状态保持为未置顶

### US1.3 置顶区可排序（P0）

作为整理者，我想在置顶区内拖动调整先后，以便置顶的几个之间也有我的顺序。

验收：
- Given 置顶区内有多个会话，When 我拖动其中一个到新位置，Then 置顶区按我排好的顺序固化（整组固化，规则同 E2）
- Given 置顶区被拖动固化过，When 再置顶新会话，Then 新会话仍插入置顶区最上方（新置顶的声明优先于既有固化顺序）

## 2. Epic E2：会话排序（P0）

> 解决"我排的顺序说了算"。拖动是显式接管：拖完之后，看到的就是排好的。

### US2.1 拖动即固化（P0）

作为整理者，我想拖动一条会话后整个分组的顺序固定为我看到的顺序，以便顺序不再被自动行为改变。

验收：
- Given 我在某个分组（置顶区或普通区）内拖动任意一条会话，When 松手，Then **该分组的全部条目**按拖动后的顺序保存固化
- Given 分组已固化，When 界面刷新/重开应用/换设备查看，Then 顺序与固化时一致
- Given 分组已固化，When 既有会话发生改名/收起/恢复等变化，Then 其位置不变（变化不改顺序）
- **固化范围**：一次拖动只固化其所在分组（置顶区、普通区是两个独立分组；固化互不影响）

### US2.2 未固化时的默认顺序（P0）

作为浏览用户，我想在我从未拖动过的分组里看到按最近使用排列的顺序，以便不整理也有合理默认。

验收：
- Given 普通区从未被拖动固化，When 查看列表，Then 按最近使用时间倒序（最近活跃的最上；什么算"使用"见 SDR-014——恰两项：用户发送消息、用户主动打开会话；改名等维护性更新与回合内内容产出都不刷新活跃时间）
- Given 新建或新恢复一个会话，When 查看列表，Then 它出现在普通区**顶部**（置顶区之下、普通区内最上）
- Given 普通区已被固化，When 新建或新恢复一个会话，Then 它同样插入普通区**顶部**，其余固化顺序不动（新来的往下推一格，不乱序）

### US2.3 排序边界（P1）

作为整理者，我想知道排序只在所属工作区内生效，以便结构清晰不混乱。

验收：
- Given 我拖动一条会话，When 尝试放到其他工作区分组，Then 拖放被拒绝（会话不能跨工作区移动——至少本域不做）
- Given 我拖动一条会话，When 放到置顶区，Then 视同"置顶 + 排序"一步完成（拖入置顶区即置顶）

## 3. Epic E3：工作区排序（P0）

> 解决"分组本身的顺序"。工作区分组的先后同样由用户接管。

### US3.1 工作区拖动固化（P0）

作为整理者，我想拖动工作区分组调整先后，以便常用的项目在最上面。

验收：
- Given 我拖动一个工作区分组，When 松手，Then 全部工作区的顺序按我看到的顺序固化（整组固化，规则同 E2）
- Given 工作区顺序已固化，When 刷新/重开/换设备，Then 顺序保持
- Given 我从未拖动过工作区，When 查看列表，Then 按最近使用倒序；新出现的工作区（第一次有会话/第一次打开）插入顶部

### US3.2 工作区收起与排序无关（P2）

作为浏览用户，我想分组的折叠状态不影响也不干扰排序，以便收拾视图不搬家。

验收：
- Given 我折叠了某个工作区分组，When 查看排序，Then 排序不受影响；展开后位置不变
- Given 折叠状态，When 我拖动该分组，Then 拖动照常生效（折叠不是锁定）

## 4. Epic E4：契约与跨端（P0）

> 解决"一份顺序，处处一致"。顺序是数据，不是界面偏好。

### US4.1 顺序由服务端持有（P0）

作为多端用户，我想让置顶与排序保存在服务端数据中，以便换界面、换设备顺序不丢。

验收：
- Given 我在网页上完成置顶/排序，When 在终端界面查看同一份会话列表，Then 置顶与顺序一致（界面只是消费顺序，不各自存一份）
- Given 清空界面的本地缓存，When 重新登录查看，Then 置顶与顺序不变（不在界面本地持久化）

### US4.2 契约单一共享（P0）

作为双引擎用户（见会话持久化域 US5.3 的角色定义），我想让置顶与排序的通信契约在两代内核间共享一份定义，以便任一内核实现后另一内核可以跟进而无需改契约。

验收：
- Given 契约已登记，When 任一内核实现它，Then 另一内核按同一契约对接（不含私有关键字/私有分支）
- **实现次序（SDR-003 裁决）**：新一代内核先行实现并提供服务；旧内核的对齐进其自身排期，过渡期内旧内核服务的界面无此功能、也不得出现假入口（可用性诚实）

### US4.3 列表呈现顺序统一（P0）

作为任意用户，我想让会话列表的返回顺序就是呈现顺序（置顶在前、固化的按固化序、未固化的按最近使用），以便终端等无拖拽能力的界面也能直接呈现正确顺序。

验收：
- Given 任一界面请求会话列表，When 渲染，Then 按上述统一顺序直接呈现，不需要各端自行拼装排序
- Given 置顶/排序发生变化，When 下一次列表请求，Then 新顺序立即生效

### US4.4 列表与事件双侧的运行状态可见（P0，刷新/换端保真）

作为多端用户，我想在刷新页面或从另一个界面打开时，仍能一眼看出哪些会话正在运行（侧边栏的"运行中"标记如实恢复），以便不必逐个点开确认哪些任务还在跑。

验收：
- Given 某会话的一个回合正在进行，When 我刷新网页（引擎进程未动），Then 该会话的"运行中"标记在列表中恢复（标记的判定口径 = 主对话回合未收尾，后台任务与子代理回合不计入——与未刷新时同一口径，刷新前后不变形）
- Given 某会话的一个回合正在进行，When 我从终端侧查看同一会话列表，Then 运行状态同样可见（状态跟着数据走，不是某个界面客户端的私有内存）
- Given 我未打开某会话（只在列表里看到它），When 该会话在另一个界面/另一个客户端被启动或结束回合，Then 我这边的列表标记随之亮起/熄灭（列表行的状态变化有主动通知，不依赖我重新拉取）
- Given 引擎重启，When 我查看列表，Then 之前"运行中"的会话不再显示运行中（进程内运行态不跨重启复活），但其未收尾的对话如实保留在历史中（收起重开可见，状态不撒谎）
- Given 一个从未打开过的会话属于非默认工作区且正在运行，When 我查看全部会话列表，Then 其运行状态同样可见（状态的重建不挑工作区）
- Given 一个会话由另一进程承载（多进程共用同一数据的部署），When 我在当前进程查看列表，Then 该会话显示为未运行（运行态的可见性限于承载进程，与参照引擎一致；其对话历史完整可见）

## 5. Epic E5：会话的复制与派生（P0，防回退基线）

> 解决"已上线的复制能力必须有需求锚"。复制与派生是 Rust 内核过渡期最容易回退的功能面——本 Epic 以现行可用能力为基线显式立项（身份裁决见 SDR-005），并在此之上扩展**按轮次终点分叉**（US5.4）。

### US5.1 复制会话（fork）（P0）

作为回访用户，我想基于任一会话复制出一个新会话，新会话带着截至分叉点的完整对话继续、原会话原封不动，以便"换个方向试"而不毁掉已有对话。

核心原则（SDR-007）：**复制"已完成"的对话、共享"文件世界"、重置一切"运行中"的状态**——凡是没画上句号的东西，都不带过来。默认分叉点是最近一个已完整结束的回合。

验收：

**继承（复制成独立副本）：**
- Given 截至分叉点的对话，Then 每一轮**已完整结束**的对话（含用量）整体复制成独立副本：改新不影响旧、反之亦然；一个回合要么整体带过来、要么整体不带（回合原子性）
- Given 最近的模型选择与智能体配置，Then 保留并继续沿用（它们是配置不是运行态；方案/计划这类**随对话记录**落盘的状态，因「复制已完成对话」自然带过来——判断标准是载体，纯运行态不落记录的不带）
- Given 会话中已创建的目标（它是什么、进行到哪一步），Then 内容与进度带过来，但一律处于**未启动**状态——需在新会话里再次明确授权才会自动推进
- Given 新会话，Then 记录"从哪个会话分出"的血缘关系，用于界面溯源
- Given 分叉出的会话继续对话，Then 对方的记忆连续、请求前缀稳定（费用结构见 US5.5 / SDR-010）

**共享（不复制）：**
- Given 会话所属工作区的**工作目录**（用户项目文件，非存放会话数据的目录），Then 新旧会话在同一片文件沙箱里干活——分出去换个思路重做时，旧会话留下的文件都在
- Given 对话中引用过的附件等物理文件，Then 不另存副本——分叉会话直接引用同一份存储；被引用的旧附件保持可见、不因分叉而被清理（全体会话共享同一套文件存储，存储形状见持久化域 ADR-007：全局内容寻址、指纹引用、引用感知回收）

**明确不带（重置为干净状态）：**
- Given 分叉点之后或尚未收尾的内容（正在进行的对话回合、正在执行的工具操作、正在流式输出的回复），Then 一律不进入新会话；界面不提供"生成到一半"的分叉选项（硬约束）
- Given 父会话设置的定时提醒与计划任务，Then 任何一条都不带进新会话——新会话只认自己分叉之后新建的任务，不会突然响起旧会话的闹钟（SDR-007，取代先前"随包带走"的裁决）
- Given 挂起中的人工交互（等待审批的操作、等待回复的询问），Then 不转移——分叉后一切从干净的等待状态重新开始
- Given 父会话"哪些内容已上报完成"的进度记录，Then 不沿用——新会话先把继承的对话完整重新投递一遍再继续（宁可重复、不可漏报，保证分叉会话的记录独立完整）
- Given 会话身份与创建时间，Then 全新身份与全新创建时间（仅血缘关系一条记录保留）

**其他：**
- Given 分叉出的会话，Then 它是**完全独立的会话**：出现在列表中，置顶/排序/归档/删除全部规则同普通会话（SDR-005）
- Given 复制时未指定名称，Then 自动命名为「Fork of 原会话标题」（可随时改名；源会话标题为空或不可得时退化为「Fork of 源会话标识」）
- Given 分叉出的会话，Then 落在源会话所属工作区（继承归属，见 S3 工作区桶）
- Given 复制中途失败，Then 无半成品残留（回滚清理，源会话不受影响）

**分叉的界面入口与落点（现行行为基线）：**
- Given 任一界面，When 我要复制会话，Then 有不依赖特定输入方式的入口：终端提供分叉命令（`/fork`），网页在会话行菜单与对话头部菜单各提供"复制会话"动作
- Given 分叉执行成功，When 操作完成，Then 我被**带到分叉出的新会话**（终端切换到新会话并告知返回源会话的方式；网页新会话插入列表顶部并立即选中）——分叉的动机是"换个方向推进"，落点是新会话
- Given 分叉后的新会话，When 我想回到源会话，Then 有明确的路径可返回（终端提示了返回命令；网页侧边栏源会话仍在原位）
- Given 分叉出的会话，When 我在界面上查看其来源，Then 能看到"从哪个会话分出"的血缘呈现（溯源可见，具体呈现形态随界面能力而定——列表角标、详情字段或头部标识均可，最小义务是可发现）

### US5.2 子会话派生（createChild）（P0）

作为用户/派工程序，我想从某会话派生一个带父子溯源关系的子会话，以便程序化派生的工作有可追溯的归属。

验收：
- Given 从某会话派生子会话，Then 子会话是**独立会话**（独立性与复制语义同 US5.1 / SDR-005 / SDR-007）且记录父会话标识，默认命名「Child: 源会话名」
- Given 列表查询按父会话过滤（childOf），Then 能列出其子会话（Rust 侧当前未建模父子关系——见 context，属本 Epic 补齐项）
- Given 父会话被删除，Then 子会话**保留**且可继续使用（父子是溯源关系不是所有权，删除不级联）
- Given 指定的新会话标识非法（含路径分隔符等），Then 请求被拒绝（标识由引擎铸造，不接受外部指定非法值）

### US5.3 顺带问一句（btw）（P0）

作为用户，我想在会话里"顺带问一句"而不打断正在进行的回复，以便小问题立刻有答案、主对话不受干扰。

验收：
- Given 主对话任意时刻，When 我发起顺带问，Then 得到回答且**主对话不受干扰**（继续独立进行，顺带问答不混入主对话历史）
- Given 顺带问的回答，Then 只基于既有上下文以文本作答、不执行任何工具操作（工具被禁用且对回答如此声明）
- Given 同一会话内追问顺带问，Then 复用同一个顺带分支继续对话（追问记得之前的顺带问答）
- Given 会话收起后恢复，Then 顺带分支的记录随会话一同保存与恢复（按身份分片的记录流，见持久化域 ADR-006）
- Given 宿主主对话发生过压缩（上下文压缩域），When 顺带问作答，Then 其上下文继承宿主**当前**的模型可见内容（压缩后视图），不快照压缩前的旧上下文

### US5.4 按轮次终点分叉（turn-end fork）（P1）

作为回访用户，我想从会话里任意一轮对话收尾的点上分叉出新会话，以便事后想起"该在干净结论处分叉"时不用付出代价——无关的后续对话不会跟进来，每个分叉话题都在干净的上下文里继续确认。

验收：
- Given 会话中任意一轮已收尾的对话（我的一句发言与其回复完整完成），When 我从该轮终点执行分叉，Then 新会话创建成功，包含源会话从开始到该轮终点（含该轮）的完整对话历史与用量；该轮之后的对话与用量**不进入**新会话
- Given 分叉出的会话，When 我在其中继续对话，Then 对方看到的上下文只到分叉点为止——分叉点之后的源会话内容对它不存在
- Given 源会话，Then 其全部对话（含分叉点之后的）原样保留；对源会话与对分叉会话的任何操作互不影响
- Given 某轮回复尚未收尾（会话正在进行），Then 该轮不构成可用的分叉点（分叉点只存在于已收尾的轮次终点）
- Given 凡呈现会话对话内容的界面，When 浏览历史对话，Then 已收尾轮次的终点均提供"从此处分叉"入口
- Given 分叉出的会话，Then 独立性、继承/共享/不带清单与命名规则全部同 US5.1（SDR-005/SDR-007；失败无半成品残留）；费用结构同 US5.5（SDR-010）
- Given 某一界面所属内核尚不支持分叉点参数（新内核先行，规则同 US4.2），Then 该界面不出现分叉点假入口（可用性诚实）

**分叉点选择的界面形态（新需求，首次定义）：**
- Given 网页端浏览历史对话，When 我停留在某一轮已收尾的回合上（悬停或键盘聚焦该轮），Then 该轮终点出现"从此处分叉"的动作入口；进行中的回合**不出现**该入口（入口的存在性即回合收尾状态的诚实信号，不得出现点了报错的假入口）
- Given 终端界面，When 我执行分叉命令，Then 弹出可搜索的分叉点选择器：列出本会话全部已收尾的回合，每项含该轮用户发言的摘要预览；选中即以该轮终点为分叉点执行分叉
- Given 分叉点选择器（终端）或回合分叉入口（网页），When 我确认执行，Then 分叉立即开始，执行期间入口不可重复触发（防双击产生两个分叉）
- Given 分叉执行成功，Then 我被带到分叉出的新会话（同"分叉后的落点"条款，见 US5.1）；源会话列表位置与内容不变
- Given 分叉执行失败，Then 我停留原地（源会话/列表状态不变），并收到明确的失败提示（含可理解的失败原因）——不出现半成品会话条目、列表不闪动（注意：会话进行中不再是失败原因——末尾分叉在忙碌时也可用，见下一验收）
- Given 会话正在进行（最后一轮未收尾），When 我发起末尾分叉（不指定分叉点），Then 分叉成功——新会话的历史截止到最近一个**已收尾**的轮次终点，进行中的内容不带（分叉在会话"忙碌"时也可用——分叉是只读操作，复制的是已画上句号的部分）
- Given 会话正在进行（最后一轮未收尾），When 我以该进行中的轮次为分叉点，Then 请求被拒绝并告知该轮尚未收尾（尚无完整历史可复制的轮次不构成分叉点——与"分叉点只存在于已收尾轮次"同一条规则的错误反馈面）

### US5.5 分叉后继续对话的记忆连续与费用结构（P1）

作为分叉会话的用户，我想在分叉出的会话里继续对话时，对方"记得"分叉点之前的全部对话、费用结构合理，以便分叉换个方向试的代价是"新方向本身的成本"，而不是"把旧对话重读一遍"被系统性地、长期地重复计费。

验收：
- Given 我从源会话分叉出一个新会话（任意分叉点），When 我在新会话里发出第一句话，Then 对方的回答基于分叉点之前的完整对话记忆（内容上"记得"）——分叉不丢失任何分叉点之前的内容
- Given 分叉出的新会话，When 我在其中继续对话，Then 发给模型服务的请求内容是分叉点的稳定延续——分叉点之前的部分逐字不变，新对话只在其后追加；不因分叉操作本身引入任何内容漂移（这是服务方按"已读过"给予计费优惠的达成条件，也是本引擎侧的唯一保证）
- Given 分叉会话里已经继续了若干轮对话，When 我继续提问，Then 请求前缀持续稳定（本会话内的连续请求正常享受服务方的已读优惠——分叉会话作为独立会话，其缓存从首次请求开始自行积累，后续命中率不受"它是分叉出来的"影响）
- Given 分叉后的首次请求可能未被服务方按已读计费（服务方按自己的前缀匹配规则决定），Then 这被接受为分叉的成本结构——分叉不承诺首次请求的费用折扣；引擎不为此做任何服务方特定的缓存管理（承诺边界，SDR-010）

### US5.6 多成员会话的分叉范围（P2）

作为多成员会话（会话内除主对话成员外还有辅助成员）的用户，我想明确分叉时哪些成员跟着走，以便分叉结果的成员构成可预期。

验收：
- Given 我分叉一个多成员会话，Then 分叉出的新会话携带源会话截至分叉点的**全部成员及其各自的对话记录**——分叉复制的是"整个会话现场"，成员构成与源会话一致
- Given 分叉出的多成员会话，When 我在其中继续对话，Then 各成员的行为延续各自截至分叉点的记忆（改新不影响旧、反之亦然）
- Given 分叉只发生在会话级（一个动作分叉整个会话），Then 不提供"只带某一个成员分叉"的入口——单成员现场是另一种产品形态，如需要另行立项（本域不做）

## 6. Epic U：对话撤销（U1，P1·提案）

> 解决"说错了就从那一点重来"。撤销（G5）是用户对自己**会话内对话历史**的显式回退声明：走错方向的最近几轮整轮撤掉，会话从撤销点继续；被撤销的内容从会话的后续状态中消失，且这一消失经收起/重开保持。
> 与压缩（上下文压缩域 C1）的关系：压缩是系统对模型可见历史的整理，撤销是用户对对话历史的回退——撤销遇压缩摘要（C3）即停，不穿越压缩考古（压缩域已裁决的边界语义，本域承接）。
> 背景事实（依赖，非本域裁决）：三引擎均有撤销实现且行为有差异（含"撤销后收起重开会回到撤销前内容"的保真缺口），差异盘点见 [session-management-context.md](session-management-context.md)；撤销的落盘载体与重放机制见架构文档（ADR-006）。语义统一方向、撤销粒度与深度上限、redo、跨压缩段行为四个方向性开放项（ROADMAP 开放项 8–11）先行裁决，不随默认值静默定案。

### US-U1 撤销最近若干轮并从该点继续（P1）

作为会话用户，我想撤销最近若干轮对话并从撤销点继续，以便消除走错方向的部分，而不必另开会话或从头再来。

验收：
- Given 会话处于空闲（没有正在进行的回复），When 我请求撤销最近 N 轮，Then 最近 N 轮对话——每轮含我的发言与对方的完整回复——从会话中移除，会话回到第 N 轮开始前的状态
- Given 撤销完成后继续对话，When 我在撤销点发起下一轮，Then 对方以未被撤销内容结束时的记忆作答——被撤销的内容对它不复存在
- Given 一轮回复尚未收尾（会话正在进行），When 我请求撤销，Then 请求被拒绝并告知等待本轮收尾后再试（撤销以整轮为单位，不产生半轮状态）
- Given 压缩整理正在进行，When 我请求撤销，Then 请求被拒绝并告知稍后再试；压缩完成后同一请求可再执行
- Given 我请求撤销的轮数超过当前可撤销的轮数，When 我执行撤销，Then 请求被拒绝，并明确告知当前最多可撤销多少轮、不能更多的原因（信号真实性）
- Given 凡呈现会话对话的界面，When 我需要撤销，Then 至少有一条不依赖特定输入方式的操作路径：既可按轮数撤销，也可从对话历史中直观选择"撤销到哪一轮"
- Given 撤销成功，When 我查看会话的对话呈现，Then 被撤销的轮次不再出现在该会话的对话中

### US-U2 撤销后收起再打开，对话停留在撤销后的状态（P1）

作为会话用户，我想在撤销之后收起会话再重新打开，对话仍停留在撤销后的状态，以便撤销是真实生效的持久操作，而不是只改了眼前画面的临时效果。

验收：
- Given 我撤销了最近 N 轮后收起会话（或重启应用），When 重新打开该会话（S1 会话恢复），Then 对话呈现为撤销后的状态：被撤销的轮次不复现
- Given 撤销后继续了新的对话，再收起重新打开，Then 呈现的是"撤销后的历史 + 新对话"，被撤销的内容不复活
- Given 重新打开后在撤销点继续对话，When 对方作答，Then 其记忆基于撤销后的历史——不会引用被撤销的内容
- Given 撤销发生在一个界面，When 我换另一个界面打开同一会话，Then 呈现同样的撤销后状态（状态跟着数据走，不跟界面走）
- Given 撤销后收起重开，When 查看会话的后续行为，Then 与撤销后的实际状态一致——不出现"内容已撤销、但后续行为仍按撤销前推进"的错位

### US-U3 撤销与压缩整理相遇时的可感知行为（P1）

作为会话用户，我想清楚地知道撤销能撤到哪里、遇到压缩整理的边界时会发生什么，以便撤销的范围可预期、反馈诚实。

验收：
- Given 最近一次压缩整理（对话呈现中出现压缩分隔条）之后有 M 轮对话，When 我请求撤销 K 轮（K ≤ M），Then 撤销正常生效，被撤销的内容只涉及压缩之后的对话
- Given 压缩整理之后只有 M 轮（M < K），When 我请求撤销 K 轮，Then 请求被拒绝，并明确告知最多可撤销 M 轮、以及"更早的对话已被压缩整理"的原因（撤销不穿越压缩边界，与 C3 一致）
- Given 压缩整理之后没有任何可撤销的对话，When 我请求撤销，Then 请求被拒绝并明确告知"本轮压缩之后没有可撤销的内容"
- Given 撤销至压缩边界附近后继续对话，When 对方作答，Then 以压缩摘要与保留内容为正常基础作答（撤销不破坏压缩后的上下文结构）

## 7. 非目标（明确不做）

- **不做**跨工作区移动会话（US2.3 拒绝的即此类操作；若未来需要，另立需求）
- **不做**智能/自动排序（按使用频率猜测位置）——排序权只属于用户的显式操作
- **不做**多套个性布局（不同设备不同顺序）——顺序是数据不是偏好
- **不定义**归档会话的搜索可见性——该裁决属会话列表查询契约的扩展，待搜索域评审（见 ROADMAP 开放项；当前行为：搜索包含归档会话）
- **不做**引擎崩溃/强杀后的运行中会话自动恢复（重启后引擎不再主动续跑中断的回合——状态可见性（US4.4）保证"中断"被如实标注，续跑与否由用户决定）

## 8. 决策记录（SDR）

### SDR-001 拖动即固化整组

- **背景与动机**：拖动排序存在两种接管模型——整组固化（所见即所排）或仅固定被拖项（其余自动排）。后者导致"某条会话夹在两条之间但谁都没拖过它"的不可解释状态。
- **决策**：一次拖动固化其所在分组的全部条目顺序（US2.1）。
- **否决的替代**：仅固定被拖项（实现与心智复杂度高，"为什么它在那"无法向用户解释）。
- **影响面**：US2.1、US2.2、US1.3。

### SDR-002 新条目插入普通区顶部

- **背景与动机**：固化后新条目需要确定的插入位置；沉底会导致会话多时新会话不可见。
- **决策**：新建/新恢复会话、新出现工作区一律插入普通区（置顶区之下）顶部（US2.2、US3.1）。
- **否决的替代**：插入末尾（顺序最稳但新条目可能长期不可见）。
- **影响面**：US2.2、US3.1。

### SDR-003 契约同定、新内核先行

- **背景与动机**：两代内核并存期，同批双实现工期翻倍且旧内核即将退役（仓库方向为全面切换新内核）。
- **决策**：通信契约一次定义、跨引擎共享登记；新一代（Rust）内核首个实现；旧内核对齐进其排期（US4.2）。
- **否决的替代**：双引擎同批实现（一致性最好但工期不可接受，且服务退役方向使其收益有限）。
- **影响面**：US4.2；ROADMAP 批次安排。

### SDR-004 什么算"使用"（recency 的 bump 规则）

- **背景与动机**：未固化分组的默认顺序按"最近使用"排——若任何元数据更新都刷新活跃时间，用户会感知"改个名，会话跳到列表顶部"，顺序被维护性操作搅乱。Rust 现状是元数据更新无条件刷新活跃时间（见 context，属本 SDR 的待修差距）。
- **决策**：**对话轮次活动（用户消息、回复产出）与用户主动恢复（S1）= 使用**，刷新活跃时间；**改名、标签、归档/取消归档等维护性元数据更新 ≠ 使用**，不改变列表位置。收起不改变位置（收起不是使用）。取消置顶的插入规则不变（US1.2，显式交互优先）。「回复产出」子句已被 SDR-014 取代——使用清单现收窄为用户发送消息与用户主动打开两项。
- **否决的替代**：任何元数据变更都算使用（改名跳顶，顺序不可预期）；活跃时间与元数据更新时间共用一个字段（语义耦合，注定二义）。
- **影响面**：US2.2；引擎侧需将"排序用活跃时间"与"元数据更新时间"拆为两个语义（见 ROADMAP 开放项）。

### SDR-005 复制与派生的身份裁决

- **背景与动机**：复制（fork）、子会话派生（createChild）、顺带问（btw）三者的"是不是独立会话"决定列表/归档/删除对它们的处理规则；顺带问的形态尤其易混——它像会话但不是会话。
- **决策**：**fork 与 createChild 产生完全独立的会话**（列表/归档/删除/置顶全规则适用；createChild 额外携带父子**溯源**关系——溯源不等于所有权，父删除子保留）；**btw 不是独立会话**——它是会话内按身份分片的旁路分支（工具禁用的轻量实例），随宿主会话持久化与恢复，不进入会话列表。
- **否决的替代**：fork 产生"依附会话"（归档/删除语义全部要另立一套，复杂度不成比例）；btw 独立成会话（旁路小问答膨胀列表，且违背"不混入主对话"的产品直觉）。
- **影响面**：US5.1–5.3；持久化域 ADR-006（btw 分支的记录载体即按身份分片的记录流）。

### SDR-006 分叉点从"会话末尾"扩展到"任意已收尾轮次终点"

- **背景与动机**：复制只能在会话当前末尾分叉——而用户常常先随口追问了某个分叉话题，事后才想起应该在干净结论处分叉另开话题；此时代价是无关的后续对话被带进每个分叉，干净上下文被污染。轮次终点是天然的分叉锚点：回复已收尾、状态已落定，每个已收尾轮次都是一条"当时的那条岔路"。
- **决策**：分叉点可以是会话内任意已收尾轮次的终点（US5.4）；新会话 = 源会话截至分叉点的对话历史与用量 + 完全独立的会话身份（独立性同 SDR-005）；进行中的轮次不构成分叉点。~~会话级资产（定时任务、后台任务）以分叉执行时刻为准随包，不做分叉点的资产时点快照~~（**此资产条款已被 SDR-007 取代**——fork 一律不带运行中资产）。
- **否决的替代**：(a) 原地回退/截断会话——销毁已有历史，与"换个方向试而不毁掉已有对话"的域定位直接冲突；(b) 维持仅末尾分叉（现状）——正是本 SDR 要解决的痛点；(c) 资产按分叉点做时点快照——已被 SDR-007 整体取代（不带，无需快照）。
- **影响面**：US5.4；E5 其余条目不受影响；分叉点参数随 E5 契约登记批次进 wire 契约（见 ROADMAP 开放项）。

### SDR-007 fork 的资产继承语义：复制已完成、共享文件世界、重置运行中

- **背景与动机**：此前裁决（SDR-006 资产条款、持久化域 SDR-001 的复制条款）让 fork 把父会话的定时任务"随包带走"，产生双跑：源会话与分叉会话各持一份相同的定时任务，两边开着时同一条提醒各响一次、各烧各的成本；且"执行时刻快照"语义会把分叉点之后为旧方向创建的提醒带进新方向。产品直觉上，"复制"复制的是**已经画上句号的东西**，不应自动延续"运行中"的世界。
- **决策**（US5.1 全量验收的依据）：
  - **核心原则**：复制"已完成"的对话、共享"文件世界"、重置一切"运行中"的状态。
  - **明确不带**：分叉点之后/未收尾的内容（回合原子性——一个回合要么整体带过来、要么整体不带）；定时提醒与计划任务（新会话只认自己新建的）；目标的执行许可（内容与进度带过来，但一律未启动，需再次授权）；挂起中的人工交互（审批/询问）；父会话的上报确认进度（继承对话完整重新投递，宁可重复、不可漏报）。
  - **共享不复制**：会话所属工作区的工作目录（用户项目文件——非会话数据存储目录）；附件等物理文件（共享存储、按引用共享，被引用即不清理，不另存副本）。
  - **继续沿用**：模型选择、智能体配置（配置非运行态）；方案/计划等随对话记录落盘的状态（随「复制已完成对话」带过来，判断标准是载体）。
  - **命名**：自动命名为「Fork of 原会话标题」（此条由 SDR-012 裁决并取代先前「原标题 (2)」递增序号；源标题不可得时退化为源会话标识；同源多次分叉产生同名是已知且被接受的行为——用户需要区分时可自行改名）。
- **否决的替代**：(a) 双跑 + 文档写明（语义最简单，但重复提醒是真实的用户打扰，且分叉场景下旧方向的任务污染新方向）；(b) 复制后源会话的定时任务自动暂停（"搬家"心智少一份打扰，但源会话被悄悄改动、违背"复制不影响源会话"的承诺，且需引入"会话级提醒暂停"新概念）；(c) 维持随包带走（双跑 + 执行时刻污染，即本 SDR 要解决的现状）。
- **影响面**：US5.1（全量重写）、US5.2（复制语义同 US5.1）、US5.4；SDR-006 资产条款（取代）；持久化域 SDR-001 的复制条款（取代——删除级联不变）；附件共享条款的实现底座 = 持久化域 ADR-007（全局内容寻址存储）；现网参照引擎行为需变更对齐（见 context 的 fork 现状盘点）。

### SDR-008：顺带问的上下文继承取宿主当前模型视图

- **编号与日期**：SDR-008 · 2026-09-09
- **背景与动机**：顺带问分支"继承既有上下文作答"，但宿主主对话可能发生压缩（上下文压缩域）——"既有上下文"是指压缩前的旧上下文快照，还是压缩后的当前视图，此前无裁决。快照旧上下文会让顺带问基于已被压缩丢弃的细节作答，与宿主的实际状态脱节。
- **决策**：顺带问每次作答取宿主**当前**的模型可见内容（压缩后视图），不快照压缩前的旧上下文（US5.3 新增验收）。
- **否决的替代**：快照发起时刻的完整上下文（与宿主实际状态脱节；顺带问的记录流自身仍可独立压缩，两者不冲突）。
- **影响面**：US5.3；上下文压缩域范围边界（btw 分支各自独立触发与落位）。

### SDR-009：对话撤销（undo）立项为 Epic U——归属会话管理域、撤销落盘为语义底线

- **编号与日期**：SDR-009 · 2026-09-10
- **背景与动机**：撤销是三引擎均有实现的功能面，但用户可感知行为不一（差异盘点见 context）：存在撤销后收起会话、重新打开回到撤销前内容的保真缺口（撤销只在眼前生效，信号失真）；撤销遇压缩整理的边界反馈与忙碌拒绝等护栏也不齐全。此前撤销悬置为上下文压缩域的开放项，2026-09-10 用户裁决归属本域——撤销是用户对会话内对话历史的生命周期交互，不是压缩整理的一部分。
- **决策**：新增 Epic U（US-U1～U3，§6）：(1) 撤销最近若干轮并从该点继续——整轮原子、忙碌拒绝、超额诚实反馈；(2) 撤销经收起/重开与跨界面保持（撤销是持久操作，落盘与重放机制见架构 ADR-006）；(3) 撤销遇压缩摘要即停（承接压缩域 C3 边界语义），边界反馈诚实。语义统一方向、撤销粒度与深度上限、redo、跨压缩段行为四个方向性开放项（ROADMAP 开放项 8–11）先行裁决，不随默认值静默定案。
- **否决的替代**：(a) 不立项、维持各引擎现状——行为分叉且"撤销后重开复活被撤内容"构成信号失真（R4），不可交付；(b) 归属上下文压缩域——撤销是用户对会话历史的生命周期操作而非压缩整理的一部分（2026-09-10 用户裁决否定）；(c) 只文档化差异、不设统一语义——跨端体验不可预期，违背本域"顺序/状态跟着数据走"的原则。
- **影响面**：本域新增 §6 Epic U；架构文档新增撤销机制节 + ADR-006；context 新增 §1.6；glossary 新增 G5 撤销；压缩域边界条款（C1/C3、US4.4）不受影响；ROADMAP U1 批次与开放项 8–11。

### SDR-010：分叉的缓存计费策略——归属标识随新会话身份，引擎义务止于前缀确定性

- **编号与日期**：SDR-010 · 2026-10-09（同日修订，修订记录见文内；修订版经用户确认）
- **背景与动机**：分叉会话在内容上继承分叉点之前的完整对话，用户预期"换个方向继续"的费用不该包含"把旧对话重读一遍"。模型服务方对已读过的对话内容按折扣计费（前缀缓存），其命中依赖两个因素：请求内容的**字节级稳定**（分叉点之前的内容逐字相同）与"归属"标识的连续性。首个方案曾裁决分叉沿袭源会话的归属标识（分叉链共享）；修订时权衡多分叉场景后改判——多分叉共享一个身份时，各分叉的后续演进在服务方侧互相竞争同一缓存归属，而前缀稳定本身已是命中的主因子，身份继承的边际收益不抵多分叉场景的耦合。
- **决策**：分叉出的会话使用**自己的新会话身份**作为归属标识（与参照引擎现状一致，无需引擎侧变更）。分叉首请求的缓存命中不做保证——命中与否由服务方按前缀匹配自行决定（前缀稳定性已由复制管道保证：截取到分叉点的记录流使分叉会话的请求前缀与源会话在分叉点的请求前缀一致）；**可能的首次未命中被接受为分叉的成本结构**，其后的连续请求按新会话身份稳定积累缓存，后续命中率不受分叉影响。引擎侧的缓存义务只有一条：**分叉后请求前缀不得无理由漂移**（截取管道的确定性输出）。
- **否决的替代**：(a) 分叉沿袭源会话（分叉链共享根身份）——单分叉首请求的命中率更确定，但多分叉共享同一缓存归属互相竞争，且身份与计费连续性耦合进会话身份体系，复杂度不成比例（2026-10-09 同日修订否决的原方案）；(b) 引擎侧预写缓存/调用服务方预热 API——引入服务方特定逻辑，超出引擎边界（首版即否决，维持）。
- **修订记录**：首版裁决沿袭根会话身份（"分叉链共享"）；同日经多分叉场景权衡修订为本决策（随新会话身份）。US5.5 验收同步改写。
- **影响面**：US5.5（验收全量改写）；ADR-007（同步改写）；glossary G6（形态改写）；参照引擎（TS v2/v1）的现有行为即目标行为，无对齐变更；画像与提示词域（agent-profile）的请求配线现状即达标，无登记义务。

### SDR-011：多成员会话的会话级分叉——全量复制成员现场，不提供单成员分叉

- **编号与日期**：SDR-011 · 2026-10-09（用户裁决通过，选项 A——全量复制）
- **背景与动机**：分叉的复制单元此前未显式裁决：是复制"整个会话现场"（全部成员及各自记录），还是只复制"被分叉的那个成员"？两种直觉各有支持：分叉的入口在会话上，直觉是复制现场；而分叉的动机是"换个方向推进主对话"，主对话之外的其他成员是否跟行无明确预期。不裁决则两代引擎可能各选其一，跨端同一分叉操作产出不同结果。
- **决策**：分叉是**会话级**操作，复制截至分叉点的完整现场——**全部成员及其各自的对话记录**（US5.6）；不提供"只带某一个成员分叉"的入口（会话内旁路分支另有「顺带问」（G4）承载"轻量分叉"的诉求，形态与持久化均已裁决）。
- **否决的替代**：(a) 单成员分叉（只带主对话成员的历史）——实现最轻，但成员构成的静默收缩违反"复制已完成"的直觉（分叉出的会话比源会话"少了人"却无提示），且失去其他成员记录里的上下文；(b) 分叉时可选成员清单——表达力最强，但"选哪些人跟我走"的心智复杂度高，且现无任何用户场景需要部分成员的现场。
- **影响面**：US5.6；US5.1/US5.4（复制范围条款的显式化——"截至分叉点的对话"指全部成员的全部对话）；架构文档的复制边界节（ADR-008）。

### SDR-012：fork 的默认命名为「Fork of 原会话标题」，取代递增序号

- **编号与日期**：SDR-012 · 2026-10-09
- **背景与动机**：SDR-007 曾裁决分叉默认命名为「原标题 (2)」式递增序号——在列表里与手动改名的会话无法区分，血缘不可辨。Rust 内核现状用**源会话标识**（系统 id）命名——对用户是不可读的字符串，不可接受；需要统一为一个带来源信息的默认形态，保持简单（用户要区分时可自行改名，不做序号消歧）。
- **决策**：分叉未指定名称时自动命名为**「Fork of 原会话标题」**（2026-10-09 用户裁决）；源会话标题为空或不可得时退化为「Fork of 源会话标识」。用户显式传入的名称优先。同源多次分叉产生同名，不附加序号消歧——需要识别时用户自行改名。createChild 的「Child: 源会话名」形态不变（已是该形态）。本条**取代 SDR-007 的命名条款**。
- **否决的替代**：(a) 「原标题 (2)」递增序号（被取代的原裁决）——与手动改名混淆、血缘不可辨；(b) 沿用 Rust 现状的源会话标识命名——系统 id 对用户不可读；(c) 序号消歧（"Fork of 标题 (2)"）——复杂化默认命名，用户自行改名即可达到同样效果（2026-10-09 用户裁决否决）。
- **影响面**：US5.1（命名验收条款已同步改写）；US5.4/US5.2（同语义）；SDR-007 命名条款（取代）；Rust 内核对齐批次（`session_handlers.rs:1565` 的 `Fork of <源id>` 改为源标题——注意需取**源标题**而非源 id）；glossary G2（形态描述同步）。

### SDR-013：会话运行状态的双侧可见——列表读面与事件面同补、口径统一为主对话回合

- **编号与日期**：SDR-013 · 2026-10-13
- **背景与动机**：新一代内核上线后，网页刷新/换端打开时会话列表丢失"运行中"标记——进行中的会话与已收尾的会话在侧边栏无从区分（用户看不出哪些还在跑）。运行状态此前只存在于各界面客户端的内存（连接期间靠事件维持），刷新后依赖服务端重建，而重建链路的两侧在新内核均缺失：列表读面不带运行状态字段、状态变化无主动通知事件。参照引擎（TS v2）两侧均有实现，新内核未对齐——这是 parity 缺口而非新功能。
- **决策**：列表读面（列表行与会话快照）携带运行状态字段（主对话回合是否活跃、聚合忙碌、挂起交互类型、最近回合结局四元组，口径与参照引擎一致）；状态变化以会话级主动通知事件广播（全局扇出，任何连接不订阅该会话也能更新列表行）；刷新/重开后的状态重建由服务端从**进程内的权威运行态**（在途回合注册表）给出——注册表未覆盖的会话一律按"未运行"呈现，不做跨进程的状态推断（每个服务进程只如实报告自己承载的回合）；**不引入独立的运行状态持久化文件**——进程死亡即状态清零，重启后按"未运行"呈现（对话历史本身仍在，US4.4 第四条）。
- **否决的替代**：(a) 仅补列表读面不补事件——刷新后首屏恢复但后续状态变化（另一端启动/结束回合）感知不到，列表行需轮询刷新，parity 只补一半；(b) 界面客户端自行对全部会话拉快照推断——把状态权威从服务端挪到客户端，每会话一次快照请求成本高且口径分裂；(c) 运行状态落持久化标记（如索引列）——进程死亡后标记成为谎言（状态已死但标记说在跑），需要额外的失效清理，违背"状态不撒谎"；(d) 从会话日志的未收尾回合记录推断运行态——日志无法回答"承载该回合的进程还活着吗"，重启后残留的未配对记录会假阳性地报告"运行中"。
- **影响面**：US4.4；架构文档 §8 与 ADR-009；context §1.8；glossary G7；ROADMAP 新批次 W1。

### SDR-014：「使用」清单收窄——回合内内容产出不算使用

- **编号与日期**：SDR-014 · 2026-10-23
- **背景与动机**：多任务并行运行时，列表按"最近使用"排序的会话行随内容产出反复跳顶（用户"想点的那行跑了"）——SDR-004 曾将"回复产出"计入使用，该子句正是跳顶的口径来源。运行中的会话产出内容是系统的行为而非用户的交互，把它算作"使用"使用户对位置失去预期。
- **决策**：**「使用」清单收窄为恰两项——用户在会话中发送消息、用户主动打开（恢复）会话**。回合内内容产出（回复消息、工具结果、子代理输出、用量水位更新）一律不算使用，不刷新排序活跃时间；维护性更新不算使用的既有裁决（SDR-004）不变。本条**取代 SDR-004 决策中"对话轮次活动（用户消息、回复产出）"的口径**，收窄为"用户消息"；排序位置的变化来源完整清单：新会话插入顶部（SDR-002）、用户交互的 recency 提升（本条）、用户显式拖拽（SDR-001）。术语唯一定义见 glossary G8（使用）。
- **否决的替代**：(a) 维持"回复产出算使用"（SDR-004 原口径）——多任务并行时行反复跳顶，用户对位置无预期；(b) 运行中的会话冻结位置、跑完再跳——"跑完跳顶"仍是用户没预期的移动，且与"会话结束不是使用"自相矛盾；(c) 排序加滞回带（变化小于阈值不动）——治标，长任务跨越阈值仍跳。
- **影响面**：US2.2；SDR-004（"回复产出"子句被本条取代，SDR-004 不再是"使用"口径的最终裁决）；glossary G8（新增）；事件投递域 SDR-002（位置与状态解耦的需求侧引用本条）；引擎侧排序活跃时间与内容产出的解耦（rust 侧落地见该域 ROADMAP）。

### SDR-015：界面对"会话不存在"错误的识别以**语义**为准——识别引擎通用不存在码

- **编号与日期**：SDR-015 · 2026-10-25
- **背景与动机**：会话被收纳（归档）或删除后，引擎对其后续读面请求如实回答"不存在"。用户在归档动作刚完成时，界面对该会话仍在途的状态拉取请求会收到这个回答；此时正确的产品行为是**安静地移除并切换到下一个会话**（收纳完成后列表不再有它，界面不应为一个已收纳的会话报错）。但界面此前只认得一种传输形态下的"不存在"错误（旧守护进程 REST 的领域码），新一代内核的实时通道以另一种编号（引擎 JSON-RPC 通用"不存在"码）回答同一语义——同一件事因通道不同被误判为故障，弹出了"无法加载当前会话"的吓人提示。**同一语义，不因通道形态而分叉**是本裁决的原则。
- **决策**：界面对"会话不存在"的识别**按语义而非单一编码**：除旧守护进程 REST 形态的领域码外，同时识别新一代内核 JSON-RPC 通道的**通用"不存在"错误码**（引擎对所有"资源不存在"类回答共用的那个码）。识别成立的处理不变：安静移除该会话、切换到下一个会话、不弹任何警告——与「归档离开默认视野」（持久化域 US6.1）的用户感知闭环。识别**不成立**的其他错误照旧弹警告（吞错是把真实故障静默化的反模式）。本裁决是识别面的修补，**不改变引擎侧的任何回答语义**（引擎对已收纳会话回答"不存在"是正确行为，见持久化域"读取层默认排除"的执行位置）。
- **否决的替代**：(a) 引擎为"快照读取"专门增设一个新错误码（如"会话已归档"专用码）——让通道为迁就界面识别缺口而变形，语义拆分（归档不存在 vs 删除不存在 vs 从未存在）对用户处理路径毫无差别（都是安静移除），徒增契约面积；(b) 界面在归档动作里取消一切在途请求——治本但需要为并发取消机制立项，且无法覆盖"另一端归档/删除"的场景（本端根本不知道要取消）；识别面修补同时覆盖两端归档、真删除、未知深链三种触发源。
- **影响面**：持久化域 N6（归档语义的界面侧消费闭环，含其 US6.1 的一条验收增补）；网页端会话同步的快照拉取错误分类。
