## 0. 架构总览

非功能性的实现分散在四个层次：

| 层次 | 职责 | 代表组件（详见 context） |
|---|---|---|
| **进程宿主层** | 启动编排、模式路由、崩溃处理、退出收尾 | CLI 入口、命令路由、crash 安装器 |
| **引擎层（v2 为主，v1 为遗留路径）** | 并发调度、重试、超时、流式管道、日志、遥测 | turn 队列、工具调度器、步级重试、日志服务、遥测服务 |
| **共享基础设施层** | 遥测客户端/缓冲/传输（被 CLI 与 v2 服务端共用）、模型访问 | 遥测包（客户端/批量槽/异步传输）、模型协议层 |
| **呈现层** | 终端差分渲染、网页事件合并、桌面壳就绪 | 终端渲染内核、网页事件批处理器、桌面就绪探测 |

动机：所有横切关注点（性能、可观测性、稳定性）都必然跨层；把它们集中到少数几个明确接缝（遥测门面、日志门面、取消信号、重试注册表），其余代码只声明"发生了什么"，不关心"怎么记下来、怎么发出去"。

## 1. 启动管线

### 1.1 进程入口顺序

入口函数按固定顺序执行：设置进程名 → 安装崩溃处理器（在任何其他初始化之前，保证最早期崩溃也有留痕）→ 安装全局代理分发器（在任何网络客户端构造之前，保证代理环境变量全程生效）→ 安装原生模块重定向钩子（单文件可执行模式）→ 可选的原生资产自检（提前返回）→ 后台调度旧缓存清理（微任务，不阻塞）→ 解析命令行。

动机：崩溃处理器必须最先安装（否则安装前的崩溃丢失）；代理必须先于任何客户端（否则首请求绕过代理）。

### 1.2 模式路由与引擎路由

命令行路由出多个模式：交互界面（默认）、一次性执行（-p）、本地服务（web）、ACP（编辑器集成）、可视化、升级、导出等。引擎本身有三条后端路由（优先级：实验性 Rust 原生后端 > v2 默认（进程内）> 旧引擎回退开关），三条后端实现同一宿主接口，上层模式代码不感知差异。

动机：引擎可替换性（Rust 迁移期三条后端并存）要求把"选哪个引擎"压缩到组合根的一处决策，而不是散落在每个模式里。

### 1.3 交互界面的就绪分层

界面初始化按依赖排序：客户端偏好（主题）→ 引擎配置（计时）→ 界面骨架构建 → 遥测初始化 → 终端模式接管（保存原始终端设置）→ 兜底异常处理 → 界面启动（信号注册 → 主初始化：可用模型刷新、会话创建/恢复 → 挂载底部栏 → 欢迎页 → 首帧渲染）→ 后台任务启动（横幅、输入历史、模型列表后台刷新、自动补全辅助程序、会话列表、技能/插件命令刷新）→ 启动完成（记录启动性能事件：总时长/配置耗时/初始化耗时/外部服务器就绪耗时）。

关键机制：**外部依赖（MCP 服务器）就绪与界面可用解耦**——会话创建不等服务器连接完成，而是把"等待初始就绪"推迟到首个模型步开始前与每次外部工具执行前（快路径，默认启用；保守开关可恢复旧行为）。会话创建中技能目录的加载也是显式不等待的（fire-and-forget）。

动机：启动时间的最大变量是外部依赖；把等待点从"启动时"移到"首次需要时"，让首问的延迟取决于真正用到的那台服务器，而不是最慢的那台。

### 1.4 原生资产机制

单文件可执行（SEA）分发形态下，原生组件内嵌在可执行文件里：启动时按清单校验并解出到版本化的本地缓存目录（哈希寻址），加载器优先从缓存 require；模块钩子在常规解析失败时重定向到缓存副本，再失败透传原始解析。缓存清理保留当前版本与最新兄弟版本。外部搜索程序（rg）的取得是四级解析链（PATH → 内置 vendor 位 → 本地缓存 → 按固定校验和下载），下载有模块级互斥锁防重复；失败回退纯内置搜索实现并埋点记录。

动机：单文件分发不能预置所有平台的二进制，也不能要求用户预装工具——"按需解出 + 校验 + 优雅回退"三件事缺一不可。

### 1.5 更新预检

更新检查在命令解析前作为预检执行：读本地缓存决策，需要时后台静默安装（分离进程、不接管 stdio），可被环境变量整体禁用。动机：升级提醒不能以启动延迟为代价。

## 2. 并发模型

### 2.1 回合队列与步内工具并行

会话内回合是单消费者先进先出队列，一次只跑一个回合；回合内模型每次响应产生的工具调用批次交给**工具调度器**：每个工具声明自己的资源访问集合，两个调用访问集合相交则串行（保持声明的先后），不相交则立即并行；执行结果按完成顺序流式产出（先完成先呈现）。调度器不设全局数值上限——并行度完全由工具的资源声明推导。

动机：数值上限对每种工具组合都不对（8 个只读搜索并行无害，2 个同写一个文件就太多）；把"冲突"交给工具作者声明，调度器只做仲裁，是可组合性更好的抽象。

### 2.2 子代理批次的斜坡调度

子代理批量启动采用"突发-节流"斜坡：先放初始若干个（默认 5），其后固定间隔放行一个；任何时刻的硬并发上限可由环境变量设置（默认无上限）。收到服务方限流信号后进入限流模式：容量按已成功启动数收缩、被限流任务指数退避重排队、静默期后每周期容量 +1 恢复。

动机：批量的启动瞬间对服务方的压力最大；斜坡让"快"与"不触发限流"折中，限流后的收缩-恢复让批次自适应服务方的真实容量。

### 2.3 外部服务器并行连接

MCP 服务器的连接（启动、关闭、重连）全部并行发起，单个服务器的失败不影响其他服务器。连接就绪的整体等待被快路径推迟（见 1.3）；重连有 in-flight 去重（同一服务器的重复重连请求合并）。

### 2.4 服务端进程与推送背压

本地服务是单进程多会话模型：一个核心作用域承载全部会话的路由，多实例靠磁盘实例注册表（定期心跳）+ 端口顺延共存。事件推送（WebSocket）的出站侧有：有界帧缓冲（超限丢帧由重连快照补偿，一致性归渲染域）、16 毫秒合批、高水位暂停发送 + 回落后重试的背压。服务端不主动断开连接（无服务端心跳），活性由客户端心跳承担。

动机：单进程模型让多会话共享一个引擎生命周期与配置监听，部署最简；背压保护的是**慢客户端不拖垮服务端事件循环**，而非事件不丢（不丢由重连补偿语义保证）。

### 2.5 取消传播

取消是一条贯穿的信号链：用户动作（ESC/快捷键）→ 回合级取消 → 步级信号（回合信号与步信号取"任一触发"合成）→ 工具执行信号 → 外部服务调用请求选项。工具执行对取消有 2 秒宽限期，宽限后以取消结果强制收尾；被用户中断的工具结果会注入"用户手动中断、勿自动重试"的说明供模型阅读。取消类错误（AbortError）在崩溃处理器中被过滤，不计为崩溃。

动机：取消必须"沿途全部能听见"——漏一环就会出现"界面已恢复输入但后台还在烧钱"的体验。

## 3. 超时与重试

### 3.1 步级重试（模型请求的核心恢复机制）

重试不放在 HTTP 客户端，而放在回合循环的错误处理注册表：注册的错误处理器匹配"可重试"分类（限流、超时类、5xx 家族、可降级的请求过大等），按退避序列（0.5 秒起、指数翻倍、封顶 32 秒、25% 抖动、尊重服务方 retry-after）把该步重新入队到**队列头部**（保序）。每回合重试预算可配置（默认 10 次尝试）。不可重试错误直接使回合失败。

配套机制：①请求结构降级链——同一请求被拒后先降媒体质量、再剥离媒体，尽量保住请求；②鉴权刷新恰好重放一次；③模型流中断**没有**流级自动重连，恢复统一走步级重试（简化语义：一步的失败只有一个恢复路径）。

动机：把重试放在"步"这一层而不是网络层，让重试预算、退避策略、与队列的交互（重入头部）成为回合语义的一部分，网络层保持纯粹。

### 3.2 模型请求无请求级超时（显式取舍）

模型请求不设请求级强制超时，只有透传的取消信号。理由：长思考模型的合法响应时间跨度极大（数十秒到数十分钟），任何静态超时都会误杀；恢复语义由"用户可随时取消 + 步级自动重试"承担。此取舍在需求侧显式记录（US4.2），超时上限作为提案保留（§9 P6）。

### 3.3 全局超时清单

每个对外交互各自定义超时常量（外部服务器启动/工具调用、子代理、前台命令、外部钩子、rg 搜索、磁盘锁、SQLite 忙等待、遥测请求、网页层 REST/握手/心跳等），集中索引见需求文档 §5。所有定时器尽量 unref（不阻止进程自然退出）。

### 3.4 网页端网络层

REST 请求统一带 30 秒超时、不自动重试；连接层有握手超时、客户端心跳（超宽限即主动断开）、指数退避重连（封顶 30 秒、带抖动），重连后按快照补偿对齐。半开连接检测：窗口聚焦时若连接疑似失效则强制重连。

## 4. 流式管道与呈现性能

### 4.1 引擎侧流式

模型响应通过回调推入异步事件队列，消费端逐事件 `await` 处理——消费端天然形成反压点（上游回调被消费速度限流），但队列内部缓冲无界（已知取舍，见提案 P7）。

### 4.2 终端差分渲染

终端渲染内核保存上一帧逐行快照，每帧只重绘首尾变化区间；渲染请求合并（每帧调度一次）且有 16 毫秒最低帧间隔（约 60 帧上限）；输出用终端的同步更新序列包裹防撕裂。界面内容的有界性由转录滑动窗口保证：超出保留回合数（+迟滞余量）的整块销毁释放、回合内较早的步骤合并为摘要、最近 N 回合可展开。

### 4.3 网页端事件合并

高频事件（流式分片类）标记为可合并，经帧级批处理器调度：按动画帧批量应用、单批数量与体积有界、超大分片拆分、偏移连续可证时无损合并；低频事件直接透传。重型渲染（公式、图表）移入工作线程（构建配置为 ES 模块 worker 以支持按需分包）；超大内容（文本/代码超阈值、围栏过多）自动降级渲染方式（放弃高亮保纯文本）。

动机：流式事件速率（毫秒级）远高于渲染收益上限（帧级），合并层把两者解耦；降级与 worker 保证"渲染成本有上界"。

## 5. 日志体系

### 5.1 双套装配并存

日志栈按引擎路径分为两套装配（旧引擎路径与新引擎路径各一套，机制同构、配置前缀不同）：分层为全局日志（一份）+ 会话日志（每会话目录一份，引用计数管理）；写入路径为异步串行队列 + 批量追加 + 每批强制刷盘（fsync）；崩溃路径有同步保全逃生（直接同步追加）。轮转按大小触发、保留个数有上限。写失败向标准错误节流提示（默认 30 秒一次）。级别与轮转参数仅由环境变量控制（不进配置文件——保持引擎库的无配置可用性）。服务端（本地服务进程）另有独立的结构化访问日志（按请求结果码记录），与引擎日志栈不桥接。

动机：日志要在"进程被杀前尽力保全"（fsync + 同步逃生）与"不能拖垮主流程"（异步串行 + 有界缓冲丢最旧）之间取平衡；环境变量而非配置文件，是因为日志是诊断配置文件本身问题的最后一层。

### 5.2 日志与崩溃的衔接

崩溃处理器上报后调用同步冲刷；界面模式的紧急退出路径先同步保全诊断日志、再恢复终端状态、最后退出。

## 6. 遥测体系

### 6.1 三段式管道

遥测由三段组成：**客户端**（默认单例，事件先入内存队列——上限 1000 条溢出丢最旧；支持按上下文派生作用域客户端，会话级打点带会话标识；禁用态丢弃一切）→ **批量槽**（攒批冲刷：50 条阈值或 30 秒周期先到先发；关闭时清缓冲）→ **异步传输**（HTTP 上报：10 秒请求超时、1s/4s/16s 退避重试、仅瞬态错误重试；失败落盘暂存为受限权限文件，启动时扫描暂存目录、7 天过期清理、损坏文件清理）。

初始化时装配三段并启动系统指标采样（预热采样 + 周期采样，采集进程与机器资源画像）与暂存重发。禁用判定：环境变量优先于配置布尔开关。

### 6.2 v2 引擎侧遥测服务

v2 引擎有自己的遥测服务（应用作用域，appender 列表，默认空 appender）：**类型化事件注册表**是事件的单一登记处（事件名、owner、属性及说明），引擎代码通过带类型的封装打点；**云端 appender** 与共享遥测包的传输机制同构（同批量阈值/周期/退避/落盘）。本地服务进程把 v2 引擎遥测桥接到自己的上报通道（opt-in，配置开关 + 环境变量双重控制）。

动机：v2 的类型化注册表让"采集了什么"机器可查（每事件有定义与属性说明），为审计与披露（提案 P4）提供结构基础；appender 列表让云端上报只是其中一种去向，测试与本地收集可以是别的 appender。

### 6.3 事件语义边界

遥测事件只含事件名 + 基础类型属性（数值/字符串/布尔，非基础类型静默丢弃）+ 匿名身份（设备标识、会话标识）+ 环境上下文。事件族覆盖：交互（快捷键/命令/主题/模式切换）、回合（开始/结束/中断/时长）、工具（调用/耗时/错误类型/去重）、模型错误（含可重试性与状态码）、会话生命周期（创建耗时/恢复失败）、外部服务器连接、压缩、子代理、审批决策、崩溃、系统指标、性能埋点（流式首 token 延迟、各阶段耗时）等；全量清单（file:line）见 context §7。

### 6.4 崩溃上报

崩溃处理器监听两个进程级钩子：未捕获异常监视器（只观察不拦截，保留默认崩溃语义）与未处理拒绝（若自己是唯一监听者则重新抛出以保留默认崩溃；有拒绝去重集合防止双报）。上报"崩溃"事件（错误类型、发生阶段 startup/runtime/shutdown、来源）后同步冲刷；AbortError 过滤（取消不是崩溃）。

动机：崩溃遥测的最高原则是**不能改变崩溃本身的行为**——宁可丢一条事件也不能吞掉或重复一次进程退出。

## 7. 退出与清理

各模式的退出路径共享一个分层时限模型：遥测冲刷限时（3 秒，超时转同步落盘）→ 整体清理限时（一次性模式 8 秒）→ 输出排空限时（10 秒）→ 强杀兜底（2 秒）。信号差异化：交互模式把 Ctrl+C 当键盘输入（分级：取消 → 清空 → 双击退出）；SIGTERM 走优雅路径；SIGHUP 与"终端已死"错误走紧急路径（跳过交互式清理）。会话数据由引擎持续落盘（写时持久化），退出路径无需专门"保存会话"步骤——退出只需释放进程内资源。

动机：退出路径的敌人是"卡在清理上"（外部服务不响应、终端已死还写）；时限模型保证任何情况下进程最终会结束，紧急路径保证不往死终端写。

## 8. 架构决策记录（ADR）

### ADR-001：非功能域的技术侧组织——按"横切机制"而非"指标类型"组织

- **编号与日期**：ADR-001 · 2026-09-12
- **背景与动机**：非功能需求天然按"性能/可靠/可观测"这类指标类型分类，但实现却按"启动管线/取消传播/重试注册表/遥测管道"这类横切机制组织；文档若按指标类型切分，每个机制会被拆到多个章节。
- **决策**：本文按横切机制组织（启动管线/并发/超时重试/流式呈现/日志/遥测/退出），指标类型由需求文档的用户故事承载，两侧靠章节映射对齐；执行状态与 file:line 级现状事实不入本文（现状证据归 context），机制的契约性默认值（时限、上限、退避参数）允许在机制描述中出现，跨域唯一数值汇总索引在需求文档 §5。
- **被否决的备选方案**：按指标类型组织（性能一章、可观测一章）——否决：同一机制被切碎，读者无法从一份文档看到某机制的完整链路。
- **影响范围**：本文全部章节。

### ADR-002：遥测管道在 CLI 与 v2 服务端的两套装配、共享同一传输语义

- **编号与日期**：ADR-002 · 2026-09-12
- **背景与动机**：CLI 宿主与 v2 服务端进程模型不同（前者进程内一体、后者独立服务进程），但上报语义（批量/退避/落盘/过期/权限）必须一致，否则事件口径漂移。
- **决策**：共享遥测包（CLI 装配路径）与 v2 云端 appender（服务端装配路径）实现相同的批量阈值、退避序列、落盘与过期语义；v2 侧以类型化事件注册表收口事件定义。现状的两套禁用环境变量名差异记录为已知不一致（提案 P2 与 ROADMAP 开放项），不在架构上裁决。
- **被否决的备选方案**：单一路径（v2 服务端复用 CLI 的装配）——否决：服务端进程没有 CLI 的宿主生命周期（设备标识、命令行上下文），强行复用引入反向依赖。
- **影响范围**：§6。
