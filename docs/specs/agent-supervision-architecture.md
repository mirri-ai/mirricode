# 多 Agent 督导域 — 架构文档

> 状态：v1 基线 · 2026-09-14 · 待用户评审
> 本文是督导域技术侧的唯一事实源（内部规格文档，不进文档站构建，中文单语）。
> 配套文档：需求见 [agent-supervision-requirements.md](agent-supervision-requirements.md)；现状盘点见 [agent-supervision-context.md](agent-supervision-context.md)。
> 本文描述终态架构；与现状组件的映射与差距见 context。凡"需求侧输入"章节（§4），其实现归属引擎侧（rust-core-design / subagent / collaboration 域），本文只定义契约需求。

## 1. 目标与设计原则

督导域的架构由两个正交维度定义：

**呈现三层**（信息去哪看）：摘要层（对话区委托卡片）→ 聚焦层（右侧详情面板）→ 深挖层（面板内叙事展开）。

**能力三轴**（能做什么）：观测（实时 + 回看）、控制（停止 / 暂停 / 审批）、干预（定向指令）。

三轴 × 三层的完备性矩阵是本域的验收坐标系——任何一格不允许出现"呈现了入口但能力缺失"（假入口）或"能力存在但三层皆不可达"（暗能力）。

四条设计原则（对应需求侧根需求的工程化表述）：

1. **过程细节单表面**：委托执行过程的渲染只存在于详情面板一条管线；对话区与卡片展开态对过程数据零消费。
2. **基数参数化**：一切督导组件以"成员集合（1..N）"为输入，N=1 是省略聚合结构的特例，不是独立组件。
3. **事实信号**：全部进度信号直接映射底层事件（成员完成、阶段变更、调用发生），不存在推导/估算层。
4. **事件溯源消费**：呈现层只消费结构化事实（事件、快照、名册）；凡当前依赖文本解析获取结构的位置（见 context §4），其结构化是引擎侧契约需求（§4.1），不是呈现层的解析技巧。

## 2. 呈现分层模型

### 2.1 层定义与内容契约

| 层 | 位置 | 内容契约 | 禁入内容 |
|---|---|---|---|
| **L0 摘要层** | 对话区内委托卡片（默认收起，可展开） | 描述、状态、N/M 计数、阶段分布摘要、当前活动单行、详情入口、异常标记、等待用户标记（"需要你处理"档，ADR-008）；展开态追加：任务原文、型号、成员名单（名字 + 阶段） | 工具调用记录、流式输出、推理内容、成员执行细节 |
| **L1 聚焦层** | 右侧详情面板 | 成员选择区（N>1）+ 成员聚焦视图：身份、任务原文、实时输出、过程叙事（L2）、结果、用量、操作区（停止/暂停）、指令输入区（预留落位） | 对话区内容、多成员同时展开（选择器互斥） |
| **L2 深挖层** | L1 内部的展开形态 | 调用叙事的逐条展开、推理全文、超长输出展开 | —（L2 是本架构的最深处） |

层级跳转关系（唯一的三个入口方向）：

```
对话区委托卡片 ──详情入口──▶ L1 面板（选择区/直接成员视图）
任务坞成员行   ────────────▶ L1 面板
卡片展开态成员名 ───────────▶ L1 面板（预选该成员）
L1 内部一切展开 ◀────────── L2（就地展开，无第三表面）
```

### 2.2 与产品其它右侧详情的关系

L1 面板占用产品既有的共享右侧详情槽位（与文件预览、思考过程等互斥切换），不新增并行面板。这是"督导细节有唯一的家"在布局层的体现。

### 2.3 模式升格（协作模式）

协作会话中，任务坞升格为 agent 总览：成员卡墙 + 摘要级事件流。升格是同一组件家族的模式化扩展——成员卡 = L0 卡片 + 干预/控制入口；点成员卡进 L1 面板（与单委托同一视图）。非协作会话维持任务坞既有形态。升格不引入新表面，只扩展现有表面的信息密度上限。

## 3. 组件结构（web 落位）

终态组件树（语义名；与现状组件的映射见 context §3）：

```
DelegationCard（对话区内，L0）
  ├─ head：icon · 描述 · N/M · 微型分布 · 状态 · 耗时 · [Open] 
  ├─ expand：任务原文 · 型号 · 成员名单（名 + 阶段，点击→L1 预选）
  └─ props：成员集合、终态结果、聚合状态

SupervisionPanel（右侧共享槽位，L1）
  ├─ MemberSelector（N>1 时）：成员行（色点 · 名 · 型号 · 活动单行 · 阶段 · 异常标记）
  ├─ MemberFocus（成员聚焦视图）
  │   ├─ 身份区（类型 · 型号 · 稳定色）
  │   ├─ 任务原文（富文本）
  │   ├─ 叙事区（L2，虚拟滚动容器；复用主会话内容块组件族，ADR-009）
  │   │    └─ 有序内容块[]（推理 / 富文本 / 工具卡，按发生顺序穿插）
  │   ├─ 结果区 / 用量区
  │   └─ 操作区（停止 · 暂停[预留] · 指令输入[预留落位]）
  └─ props：成员集合 · 选中态

AgentOverview（协作模式，任务坞升格）
  ├─ MemberCard[]（= L0 卡 + 控制/干预入口）
  └─ EventFeed（摘要级最近事件，虚拟滚动）
```

组件边界规则：

- `MemberFocus` 是唯一的成员详情视图——单委托、蜂群成员、团队成员（协作模式）三处消费同一组件（ADR-007）。
- `DelegationCard` 不持有过程数据流，只持有聚合事实（计数/阶段/活动行/终态）——过程流是 L1 的输入。
- 叙事区内容块的展开状态是纯本地 UI 状态；选中态（哪个成员聚焦）属于面板路由状态，随面板关闭丢弃，刷新后回到默认（选择区或唯一成员）。

### 3.1 状态与数据流

```
引擎事件流（WS，按 agentId 路由）
  └▶ 会话事件投影层（主代理帧→转录；成员帧→督导数据）
       ├▶ 聚合事实（计数/阶段/活动行）──────▶ DelegationCard / AgentOverview
       └▶ 成员过程事件 ────────────────────▶ SupervisionPanel 叙事区
快照读面（刷新/重开：名册 + 成员过程 + 终态结果）
  └▶ 同上两路（与实时同构，见 ADR-006）
```

状态源规则（NFR N1 的落位）：聚合事实与成员过程各有唯一的投影层派生点；卡片、面板、总览、任务坞只做消费，不自持派生状态。`agentId`（主代理为 `main`，成员为引擎分配的稳定标识）是全链路的成员路由键。

## 4. 引擎侧契约需求（本域的需求侧输入）

> 本章定义督导呈现对引擎/协议侧的依赖契约。实现与语义裁决归属：子代理生命周期类 → subagent 域；团队协作类 → collaboration 域；协议注册 → rust-core-design 域的契约事实源链（mirri-proto 注册表 + klient schema）。

### 4.1 结构化成员过程事件

**需求**：成员过程以结构化事件流提供，事件模型至少含五分类（对齐 US2.5、US3.1；text 为成员输出文本）：

```
MemberEvent {
  agentId,            // 成员稳定标识（路由键）
  type:               // thought | text | tool_call | tool_result | status | error
  content,            // 类型相关负载（文本/调用名+参数/结果/原因）
  timestamp, ordinal  // 时序
}
```

**动机**：呈现层不得以文本前缀解析重建结构（N6）；结构化事件同时是总览事件流、面板叙事、调试回放的共同底座。与 collaboration 域未来增强提案（结构化回流、成员阶段汇报）是同一通道的督导侧消费定义。

**验收（对引擎侧）**：实时（WS）与回看（快照/journal 读面）提供同构的事件模型；未知事件类型前向兼容（不崩、可透传）。

### 4.2 快照成员名册与过程读面

**需求**：会话快照携带成员名册（身份、归属委托、阶段、终态、任务原文、型号），且成员过程可按名册经读面获取。刷新后督导界面的一切数据源由此恢复（US4.1）。

**关联差距**：conversation-rendering 域差距矩阵中"快照名册恒空"与"身份分片记录流"两项（编号见该域 context）由本条作为消费方需求加压；数据侧落点为每成员独立 journal（事件溯源已是引擎事实），本条只要求读面与名册。

### 4.3 审批请求的发起者身份

**需求**：审批请求事件携带发起成员的标识，呈现层据此在审批卡标注发起者（US5.3）；单代理会话该标识为 `main`，呈现层按现状省略。

### 4.4 控制与干预操作面

**需求**（语义裁决归 subagent 域，登记为跨域提案）：

- **暂停/恢复**：按成员的暂停信号与恢复信号，进展与上下文保留；
- **定向指令（in-flight steering）**：向指定运行中成员注入下一轮上下文的指令通道；与事后续作（既有能力）的关系、权限配合、生效时机由 subagent 域裁决。

**本域约束**：操作面落地前，呈现层不渲染相关入口（SDR-006）；落地后入口出现在 §3 的预留落位。

### 4.5 成员身份与稳定色

**需求**：引擎为成员提供会话内稳定的标识；呈现层据此派生批次内稳定色（哈希分配，冲突回避），跨卡片/选择区/总览一致（US2.4）。协作模式下身份的生命周期（跨轮次/跨天）随 collaboration 域 E6 持久化语义延长，本域消费不重定义。

### 4.6 成员挂起状态事件

**需求**：成员进入/退出"等待用户"（审批/作答）与限流退避挂起时，引擎发布挂起/恢复事件，事件携带结构化原因（分类：等待审批/等待作答/限流退避 + 上下文：审批请求标识、工具调用标识）；等待用户期间成员时长预算停表、并发槽让渡。语义裁决与实现归 subagent 域（其 ADR-011），本条为呈现侧消费契约。

**验收（对引擎侧）**：挂起/恢复配对闭合（挂起必有解除——恢复或终态）；事件实时与快照读面同构；等待审批与限流退避在事件面可区分（US5.4、US1.2）。

## 5. 关键机制

### 5.1 实时与回看的同构恢复

刷新/重开的督导数据恢复与实时走同一投影层：快照（名册 + 过程）先播种聚合事实与叙事区基线，实时事件按 `agentId` + 序号续接（序号对齐机制复用既有转录同步协议的偏移对齐原则）。详情入口的显隐判定统一为"有无可查数据"（而非"有无实时任务"）——这是 US1.3 与 US4.1 共享的单一判定函数。

### 5.2 事件四分类渲染规则

叙事区复用主会话转录的内容块渲染体系（ADR-009）：成员过程归一化为与主会话单轮内部同构的有序内容块流（推理 / 富文本 / 工具卡），由同一组件族渲染。四分类事件的映射：

| 类型 | 默认形态 | 展开形态 | 折叠阈值 |
|---|---|---|---|
| thought | 一行摘要标记 | 全文（时序穿插） | 长度折叠 |
| tool_call | 与主会话工具卡同构：图标 + 调用名 + 参数人读摘要 + 状态 + 结果输出区（头尾行 + 计数） | 参数全量、输出全量、差异交互入口（US2.6；媒体/文件入口待需求侧裁决） | 行数折叠（头 N 尾 M + 计数） |
| tool_result | 并入对应工具卡的输出区 | 输出全量 | 行数折叠（头 N 尾 M + 计数） |
| status / error | 单行；error 最醒目样式 | 错误原因详情 | — |

叙事区按 `ordinal` 线性排列，四类穿插遵循真实发生顺序（US3.1）；流式富文本按主会话呈现规则渲染（呈现规则，非新内容契约）。

### 5.3 虚拟滚动与跟随

叙事区为虚拟滚动容器；跟随底部的判定为"距底 < 阈值即跟随，用户上翻即停，回到底部恢复"。总览事件流同规则。卡片聚合事实与滚动状态解耦（滚动位置不构成派生状态的一部分）。

### 5.4 可访问性

异常呼吸动画、状态色变更遵循系统"减少动效"偏好，静态替代方案内建于组件（同一组件的两种模式，不是两套样式）；全部交互（展开/选择/入口/操作区）键盘可达，焦点可见。

## 6. 与相邻设计的关系

| 邻域 | 关系 |
|---|---|
| subagent 域 | 生命周期与停止/审批/续作语义的权威；本域是其 US7.2（界面呈现）、US12（面板）在 web 侧的分层化承接；暂停/定向指令为待裁决提案 |
| collaboration 域 | E5（团队观测）的界面形态由本域 S7 承接；P-1/P-2（结构化回流/阶段汇报）与 §4.1 为同一通道；E8 蜂群模式的界面呈现以本域 SDR-002 为上位约束 |
| conversation-rendering 域 | 转录渲染通用协议（快照六要素、同步模型）是本域 L0/刷新恢复的协议底座；其差距矩阵中的名册/记录流两项由本域 §4.2 加压 |
| rust-core-design 域 | §4 全部契约的协议落位（wire 注册、schema 校验、跨后端契约测试） |
| apps/vis | 深度观测（拓扑/泳道/跨 agent 回放）的唯一归属（SDR-005）；与 §4.1 事件模型共享数据源 |

## 7. 非功能设计

- **性能**（N3）：叙事区/事件流虚拟滚动；聚合事实由投影层增量派生（事件粒度 O(1) 更新），不在渲染路径重算全量；并发多成员时面板只渲染聚焦成员的叙事（选择器互斥兼作性能边界）。
- **一致性**（N1/N2）：单一状态源 + 唯一入口判定函数（§5.1）；假入口为验收级缺陷。
- **端点**（N5）：本域组件以 web 为主定义面；终端端对等呈现的组件结构由呈现层各自映射，语义以本文为准。

## 附录：架构决策记录（ADR）

### ADR-001 三层渐进披露为督导界面的唯一信息架构（2026-09-14）

1. **背景与动机**：过程细节的呈现位置需要唯一裁决，否则会再次出现"两套组件各自内嵌过程"的重复实现。对话区是用户的核心注意力资产；外部产品调研（context §6）的双心智分层（只看结果 vs 关心过程）与渐进披露趋势支持分层而非并列。
2. **决策**：摘要（对话区卡片）→ 聚焦（右侧共享槽位面板）→ 深挖（面板内展开）三层为唯一信息架构；过程细节只在 L1 及以下；右侧面板与既有详情共享槽位。
3. **被否决的备选方案**：a) 过程独立弹窗——丢位置锚点、碎片化；b) 卡片内嵌过程 + 面板并存——即被本域取代的现状。
4. **影响范围**：§2 全部；conversation-rendering 域右侧槽位约定。

### ADR-002 委托卡片为单一组件、基数参数化（2026-09-14）

1. **背景与动机**：SDR-001 的工程化。数量差异若体现在组件分叉上，不一致会重新累积。
2. **决策**：`DelegationCard` 以成员集合（1..N）为输入；N=1 省略计数/分布/选择结构；单成员蜂群无需特判降级。
3. **被否决的备选方案**：共享 head 子组件 + 两个壳组件——仍有两处行为定义。
4. **影响范围**：§3 组件树。

### ADR-003 成员视图单一组件、三处消费（2026-09-14）

1. **背景与动机**：单委托成员、蜂群成员、协作团队成员对"一个成员的工作档案"的呈现需求同构；分叉则三处漂移。
2. **决策**：`MemberFocus`（含叙事区、操作区、指令预留落位）为唯一成员详情视图，三处消费。
3. **被否决的备选方案**：按来源（Agent/Swarm/Team）定制视图变体——回到三套演化。
4. **影响范围**：§3；S7 总览成员卡的定义。

### ADR-004 进度信号的事实映射（2026-09-14）

1. **背景与动机**：SDR-003 的工程化——需要一条可判定的规则区分"事实信号"与"合成信号"。
2. **决策**：合法信号必须与底层事件存在一一映射（成员完成事件 ↔ 计数增量；阶段变更 ↔ 分布变化；调用事件 ↔ 活动行）；不存在映射的信号（百分比、ETA）不出现在任何组件。派生仅允许两种无损形态：计数（对完成事件的计数）、分布（对阶段事实的分组）。
3. **被否决的备选方案**：允许标注置信度的估算信号——置信度不可验证，等于合法化造假。
4. **影响范围**：§5.2；NFR N2。

### ADR-005 dock→总览升格：同一组件家族的模式化扩展（2026-09-14）

1. **背景与动机**：SDR-004 的工程化——升格若另建总览屏，则任务坞与总览成为并列功能。
2. **决策**：协作模式下任务坞升格为 `AgentOverview`（成员卡 = L0 卡 + 控制入口；事件流复用叙事区的事件模型）；非协作会话维持任务坞形态；不存在第三种表面。
3. **被否决的备选方案**：独立总览路由/浮窗——破坏单一表面原则。
4. **影响范围**：§2.3、§3。

### ADR-006 观测数据的同构双源消费（实时 + 快照读面）（2026-09-14）

1. **背景与动机**：刷新后督导致盲的根因是快照读面缺失（context §5）；恢复机制若为实时流单独设计一套，两套数据路径会分叉出第三种观感。
2. **决策**：实时与回看走同一投影层；快照播种基线 + 事件按 `agentId`+序号续接；详情入口显隐的判定函数唯一（"有无可查数据"）。引擎侧每成员 journal 的事实（事件溯源）是回看数据的权威源，本域消费其读面（§4.2），不自建持久化。
3. **被否决的备选方案**：回看仅呈现终态汇总（放弃过程）——违反 US4.1 的"结构一致"。
4. **影响范围**：§5.1；§4.2；conversation-rendering 域同步协议的复用约定。

### ADR-007 预留落位不渲染占位控件（2026-09-14）

1. **背景与动机**：SDR-006 的工程化——"结构预留"与"假入口"只有一线之隔，需要可判定边界。
2. **决策**：`MemberFocus` 操作区与指令输入区是结构性落位（布局与路由参与组件树），能力未就绪时不渲染任何可交互控件；落位的验收是"能力落地时零结构变更接入"。
3. **被否决的备选方案**：渲染禁用态控件暗示未来能力——构成 N2 禁止的无效信号。
4. **影响范围**：§3；US6.2 验收。

### ADR-008 成员等待用户状态的呈现与状态源收敛（2026-09-16）

1. **背景与动机**：SDR-008 的工程化。等待用户状态此前不存在于成员状态词汇与事件面，呈现层只能以"运行中/失败"消化一切中间态；同时成员数据存在多源（实时事件行、任务管理面行、待决审批行），折叠键不统一会造成同一成员的状态分叉（现状证据见 context §9）。
2. **决策**：① 成员状态词汇扩为 `queued / working / awaiting_user（结构化原因：approval | question）/ backoff / completed / failed / aborted`——`awaiting_user` 只由引擎挂起事件驱动（§4.6 契约），呈现层不做推导；② 委托卡片聚合状态四档：`running / attention（需要用户行动）/ ok / error`——attention 是事实信号（存在等待事件），不计入异常（ADR-004 事实映射原则的扩展：等待用户是事实，不是失败）；③ 状态折叠以 `agentId` 为唯一键，任务管理面行仅作终态对账，不构成第二状态源；④ 迁移期过渡（ROADMAP P4-1）：事件通道未就绪前，呈现层以"该成员存在待决审批（发起者标识）"推导 awaiting_user 显示，代码显式标注为待删过渡（P4-4 删除）；⑤ `aborted` 与 `failed` 分档渲染（对齐 subagent 域终态词汇）。
3. **被否决的备选方案**：a) 无过渡、直接等事件通道——纯呈现修复被引擎排期阻塞，用户继续承受误报失败；b) attention 计入异常聚合——把"等用户"渲染为"出问题"，归因错误（正是本 ADR 要消除的）；c) 为 attention 新建独立引擎事件——聚合态是呈现层对成员事实的分组（ADR-004 允许的分布派生），不是引擎事件。
4. **影响范围**：§2.1（L0 内容契约）、§4.6（新契约条目）、§5.2 渲染规则（状态分类）；DelegationCard 聚合、成员行/选择器/聚焦视图的状态渲染；glossary A14；subagent 域 ADR-011（引擎侧承接）。

### ADR-009 叙事区复用主会话内容块渲染体系（2026-10-18）

1. **背景与动机**：督导面板叙事区的可读性问题表现为"像日志转储"：任务原文与流式输出为纯文本、工具调用退化为单行文本、无富文本与结构化卡片，与主会话的呈现质量断层。根因有二：呈现层未复用主会话已建立的内容块渲染组件；数据层把成员过程压平成截断的拼接文本（工具名/参数/结果/成败状态在回看侧丢失，现状证据见 context §3）。若只修呈现不修数据，回看侧仍是降级文本；若两侧各建一套，违背单表面原则。
2. **决策**：① 叙事区（L2）渲染复用主会话转录的内容块体系——同一组件族渲染推理块、富文本、工具卡（含折叠、状态、结果输出区），面板不自带降级渲染路径；交互入口以需求侧已裁决者为限（US2.6 差异入口），媒体/文件入口待需求侧裁决后启用；② 成员过程在呈现侧归一化为单一连续叙事：与主会话单轮内部同构的有序内容块流（推理 / 富文本 / 工具卡），不引入多轮结构（无轮次分隔、无轮序号）；③ 数据侧：实时路在会话事件投影层把成员的工具事件维护为结构化步骤（名称、参数摘要、输出行、状态），不以文本前缀解析重建结构；回看路不设文本压平归一层，成员 journal 的结构化读面与实时路汇入同一归一化点（内容块流，对齐 ADR-006）；④ 任务原文与结果摘要亦按主会话富文本规则渲染，适用范围为 L0 卡片展开态与 L1 面板。富文本为呈现规则，不构成新的内容契约。
3. **被否决的备选方案**：a) 仅呈现层换组件、保留压平数据——回看侧工具成败/参数仍丢失，只是化妆；b) 引擎侧新增面板专用结构化事件协议——§4.1/§4.2 契约已定义所需结构（现状证据见 context §3），超出呈现修复所需的最小契约变更；c) 面板内嵌主会话转录组件——转录组件背负轮次聚合、审批路由等主会话职责，整体复用引入无关耦合。
4. **影响范围**：§3（MemberFocus 叙事区组件树）、§5.2（渲染规则）；conversation-rendering 域的内容块组件成为共享渲染面（本域为消费方，对侧域的承接确认为开放项）；US2.5/US3.1 的 web 侧承接形态。

**开放项**：a) live 路的流式文本统一后置于工具卡之后（数据通道为单字段累积），settle 后 journal 路恢复真实穿插顺序——live 期穿插需要投影层维护结构化文本段，待后续裁决；b) 面板内工具卡的差异入口已接线，但差异面板的数据源（成员 blocks）尚未接入，现以主转录查无即不占槽位为守卫——完整支持需差异数据源裁决。

### ADR-010 成员状态单一事实字段：终态-阶段原子化与快照对账闭环（2026-10-23）

1. **背景与动机**：成员行的状态呈现建立在两个字段上——任务终态与成员阶段——而展示面（状态点/完成标记 vs 摘要行/实时流）读取优先级相反、更新路径只各写其一（快照折合只条件写阶段、事件 reducer 的终态分支只写终态），字段分叉时同一行同时呈现"完成"与"进行中"两种信号。独立放大缺口：快照对账的保留规则刻意不收敛已从服务端清单消失的进行中行，事件丢失（断连/序列间隙）后该行成为永久幽灵。诊断结论：引擎正常路径的终态时序自洽（事件闭合性由 subagent 域 ADR/US7.1 保证），缺陷在 web 读侧的状态收敛模型，本 ADR 只修读侧（SDR-009 ③对引擎侧加固"另行评估"的界定）。现状证据（写端/读端清单与代码事实）见 [agent-supervision-context.md](agent-supervision-context.md) §10。
2. **决策**：
   - ① **终态-阶段原子更新不变量**：四条更新路径——reducer 的终态分支、REST 快照折合、快照名册合并、用户停止的本地乐观写——在写入任一终态字段变更时，必须同一更新内同步映射另一字段（完成→completed；取消→aborted；失败→failed）。写入不对称是缺陷，不是设计自由度。
   - ② **终态粘滞性**：中间态写入（挂起、排队、退避等及其伴随的"运行中"回写）不得复活已达终态的行——迟到/重放的中间态信号在终态行上为幂等 no-op。
   - ③ **统一派生点**：新增唯一的成员阶段派生函数作为全部展示面的取值入口——规则：终态字段为完成/失败/取消时直接映射对应阶段；否则取中间阶段字段；无则视为进行中（成员行已建立但尚无阶段信号时按排队档呈现）。状态点、完成标记、摘要行文字、实时流开关、成员选择器行全部经该函数取值。任务坞/总览行例外豁免：其语义本就是任务终态面，直读终态字段。既有"终态优先"派生函数收编为该唯一入口。
   - ④ **对账收敛规则（keep-live 收紧）**：快照折合保留服务端清单已消失的成员行时，增加终态收敛判定，优先级从高到低：(a) 所属委托批次已交回结果且结果行携带该成员的逐成员终态 → 以该终态为准（父调用定局意味着引擎已将该成员结局折入聚合结果，此为有界推断而非合成信号）；(b) 无从判定且父工具调用已定局 → 视为已完成；(c) 父调用未定局（服务端注销但回合未闭合的边缘时序）→ 视为已中止。仅"服务端清单仍含该成员"或"行已终态"的行原样保留。父调用定局信号的读取落点：任务折叠层经成员行的父工具调用标识联查转录中该调用的结果落定状态（跨 store join），实现在 P5-3 统一收口。对账由既有轮询驱动（活跃会话 + 页面可见时），幽灵修复因此是有界延迟的收敛，不是即时事件——该有界性并入 ⑤ 的暂态口径。
   - ⑤ **诊断时序**：本 ADR 不依赖引擎侧改动。引擎双终态通道（成员终态事件、后台任务终态事件）与"内容先于状态送达"的时序维持现状——读侧自愈后，事件丢失仅造成有界的短暂不一致（至下一次快照对账），不再是永久幽灵。
3. **被否决的备选方案**：a) 只统一读端优先级（读侧修一）——写入路径不对称依旧制造分叉，本 ADR 的前提是写入不变量，读端统一只是其展示面；b) 删除中间阶段字段、全部从终态推导——挂起/等待用户/退避等中间阶段是真实信号（ADR-008 §4.6 契约），不可丢弃；c) 引擎侧合并为单一原子终态事件——治丢事件之源，但属跨端 wire 契约变更（事件面四端同步：投影/SDK/ACP/协议），超出呈现修复所需最小变更，读侧自愈落地后按实际残余不一致频率再评估；d) keep-live 行直接删除——丢失用户可见的成员结果行，回看名册残缺。
4. **影响范围**：§2.1（成员行状态字段约定）、§5.2（渲染规则取值入口）；web 事件 reducer 终态分支、快照折合、快照名册合并、用户停止乐观写四处实现与测试；需求 SDR-009；subagent 域事件面（读侧修复后其双通道时序的残余影响为有界暂态，登记该域评估）。
