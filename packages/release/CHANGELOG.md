- [#194](https://github.com/mirri-ai/mirricode/pull/194) [`f09ae28`](https://github.com/mirri-ai/mirricode/commit/f09ae28a6cea5408bf8a3804dd4dc88da5030bb1) Thanks [@mirri-ai](https://github.com/mirri-ai)! - Honor `MIRRICODE_DISABLE_CRON=1`: the documented switch now actually disables the cron subsystem in three layers (spec ADR-006 / requirements E.4):

  - **Creation refused** — the model's `CronCreate` tool rejects new tasks with the reason `定时任务已禁用（MIRRICODE_DISABLE_CRON）`; existing tasks are left untouched (not pruned).
  - **Scheduling halted** — the cron driver never enters its check loop, so existing tasks stop firing and no `cron.fired` events are published. The manual run-now face (`cron.trigger`) stays available: it is a management operation, not scheduled delivery.
  - **Honest lists** — `cron.list` (and the `CronList` tool) keeps working and now always carries a top-level `disabled` field, `true` while the switch is on, so surfaces can show why nothing will fire.

  The switch is read once at server startup: setting or clearing it takes effect on the next restart (no runtime hot reload). Any other value than exactly `1` leaves scheduling enabled.

- [#194](https://github.com/mirri-ai/mirricode/pull/194) [`f09ae28`](https://github.com/mirri-ai/mirricode/commit/f09ae28a6cea5408bf8a3804dd4dc88da5030bb1) Thanks [@mirri-ai](https://github.com/mirri-ai)! - Unified cron scheduling: held-fire persistence, trigger idle gate, fire-refresh TTL (cron-scheduling stage 1 batch 2):

  - **Long-running tasks no longer die at 7 days** — a recurring task's staleness now counts from its most recent fire, not its creation (requirements B.1/B.2): an active task survives indefinitely; only a genuinely stalled one (no fire for the TTL) gets the flagged final delivery and removal.
  - **Closing a session no longer discards pending fires** — fires that come due while the session is busy are now held on the task side and persisted to the session log (`cron.held`), and a session that closes with held fires redelivers them when reopened; deleting the session (or its task) clears the held fire with it (C.4). At-least-once: a crash between the injection and its clear replays the fire once more, never loses it.
  - **One server-level scheduler drives every live session** — the per-session cron drivers are retired; a single loop walks all built workspaces' live sessions each tick, so one session closing never stops the others' scheduling (C.1 / V10).
  - **Manual "run now" respects busy sessions** — `cron.trigger` on a busy session holds the fire through the same held channel instead of barging into the running turn; it is delivered on the first idle tick. The schedule itself stays untouched (run-now never moves the cursor or counts) (C.3 / SDR-004).
  - **Late deliveries carry a lateness mark** — a fire injected more than 60s past its scheduled moment carries `lateByMs` in the `<cron-fire>` envelope and the turn origin, so the model can judge whether the task is still relevant (C.2a); on-time and run-now fires are unchanged.

- [#194](https://github.com/mirri-ai/mirricode/pull/194) [`f09ae28`](https://github.com/mirri-ai/mirricode/commit/f09ae28a6cea5408bf8a3804dd4dc88da5030bb1) Thanks [@mirri-ai](https://github.com/mirri-ai)! - Cron scheduling (stage 2, batch 4b): workspace tasks now actually run, and agents can propose them — subject to your approval. A fired workspace task spawns a fresh execution session per run (created in the "lazy" form: no files on disk, nothing in the session list) and runs its prompt as an unattended turn under the task's declared permission posture; when the run ends, its record carries the outcome, duration, and a truncated summary of the run's final message (the run's token usage is not yet collected — the usage field stays empty until the turn-usage plumbing lands), and opening the record from the task panel (`cron.run.open`) is what persists the session for read-only replay. Concurrent triggers respect the task's concurrency posture — the default skips with a recorded reason while the previous run is still in flight, and the "queue" posture parks the new trigger in a single backlogged slot that runs once after the current run finishes (further triggers merge into that one slot); neither consumes the task's fire budget. For creation, agents have a new `ScheduledTaskPropose` tool that drafts a full workspace-task proposal (schedule with timezone, prompt verbatim, recurring flag, budget, suggested permission posture) and submits it for your approval through the existing approval surface — an agent previously could not discover this tool at all (it was missing from the agent and coder profile tool whitelists, and the system prompt carried no guidance on when to use it; both are fixed, and the tool was renamed from CronPropose to ScheduledTaskPropose while unreleased, so there is no user-visible break) — and no permission mode can auto-approve it (the proposal is presented or rejected in every mode, including disconnected-client and headless windows), a pending proposal lapses after 72 hours, and approve/reject receipts reach the proposing agent as a system notification on its next turn. Approved proposals create the task with the honest "model (approved)" origin; rejected ones return your feedback with reroute guidance, and a proposal whose approved creation fails lands in an honestly-marked failed state instead of silently lingering as pending. New query RPCs list a workspace's proposals (`cron.proposals.list`) and a task's run records (`cron.runs.list`); deleting a workspace now also terminates its in-flight runs with a recorded cause, unopened execution sessions are dropped after 7 days while their run records keep the summary, and a server restart converges any run record left "running" by the previous process to a clearly-marked failure so the task keeps scheduling. The "read-only" suggested posture currently runs as the equivalent of the ask-deny posture (read-class tools run; write-class asks are denied) — a true read-only tool category ships later with the tool-capability infrastructure (ADR-015).
