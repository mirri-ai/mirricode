Cron scheduling (stage 2, batch 4b): workspace tasks now actually run, and agents can propose them — subject to your approval. A fired workspace task spawns a fresh execution session per run (created in the "lazy" form: no files on disk, nothing in the session list) and runs its prompt as an unattended turn under the task's declared permission posture; when the run ends, its record carries the outcome, duration, and a truncated summary of the run's final message (the run's token usage is not yet collected — the usage field stays empty until the turn-usage plumbing lands), and opening the record from the task panel (`cron.run.open`) is what persists the session for read-only replay. Concurrent triggers respect the task's concurrency posture — the default skips with a recorded reason while the previous run is still in flight, and the "queue" posture parks the new trigger in a single backlogged slot that runs once after the current run finishes (further triggers merge into that one slot); neither consumes the task's fire budget. For creation, agents have a new `ScheduledTaskPropose` tool that drafts a full workspace-task proposal (schedule with timezone, prompt verbatim, recurring flag, budget, suggested permission posture) and submits it for your approval through the existing approval surface — an agent previously could not discover this tool at all (it was missing from the agent and coder profile tool whitelists, and the system prompt carried no guidance on when to use it; both are fixed, and the tool was renamed from CronPropose to ScheduledTaskPropose while unreleased, so there is no user-visible break) — and no permission mode can auto-approve it (the proposal is presented or rejected in every mode, including disconnected-client and headless windows), a pending proposal lapses after 72 hours, and approve/reject receipts reach the proposing agent as a system notification on its next turn. Approved proposals create the task with the honest "model (approved)" origin; rejected ones return your feedback with reroute guidance, and a proposal whose approved creation fails lands in an honestly-marked failed state instead of silently lingering as pending. New query RPCs list a workspace's proposals (`cron.proposals.list`) and a task's run records (`cron.runs.list`); deleting a workspace now also terminates its in-flight runs with a recorded cause, unopened execution sessions are dropped after 7 days while their run records keep the summary, and a server restart converges any run record left "running" by the previous process to a clearly-marked failure so the task keeps scheduling. The "read-only" suggested posture currently runs as the equivalent of the ask-deny posture (read-class tools run; write-class asks are denied) — a true read-only tool category ships later with the tool-capability infrastructure (ADR-015).
