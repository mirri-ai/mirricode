Cron scheduling (stage 2, batch 4a): the workspace task foundation — tasks can now belong to a workspace instead of a session. Creating a task with the new `workspaceId` parameter on `cron.add` registers it on the workspace's own task table (origin "user", stored in a workspace-level `cron/tasks.json` store with atomic writes and the same cross-process lock the session index uses), and it survives every session of the workspace closing — the unified scheduler now drives both faces in one loop, so a workspace task fires on schedule with no session open at all. The aggregated task listing gains a workspaces section whose rows state the honest delivery condition ("runs while the service runs" vs the session tasks' "runs while its session is open"), plus the task's permission posture (ask-deny / auto / read-only) and concurrency posture (skip / queue). Workspace task deletion and manual run-now route through `cron.delete` / `cron.trigger` with the same `workspaceId` parameter, and deleting a workspace removes its task store with it. Scheduled and manual workspace runs are recorded as run entries with a skipped status in this batch — the actual execution sessions and the approval-based creation flow arrive in the next batch.
