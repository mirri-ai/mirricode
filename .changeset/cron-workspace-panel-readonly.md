Cron scheduling (stage 2, batch 5): the workspace-task panel arrives, and the "read-only" posture becomes real. The Cron Jobs settings panel now groups the aggregated view by workspace alongside sessions — workspace rows label their honest delivery condition ("fires while the service runs" vs the sessions' "depends on its session being alive"), and each shows its origin (including the new "model (approved)" label for tasks you approved from a proposal), its declared runtime permission posture, and its fire count. A new "proposals awaiting approval" section presents agent-drafted workspace-task drafts in full — schedule with timezone, the verbatim prompt (marked as AI-drafted content you should review before approving), recurring/budget declarations, and the suggested posture — with Approve/Deny actions riding the existing approval channel; a denial can carry feedback that is relayed back to the agent, and decided proposals keep an audit trail. Selecting a workspace task lists its run records: status, duration, the run's output summary, the permission operations that were refused during the run, and an "Open run" button that materializes that run's execution session for read-only replay. The creation form gains a workspace target with the three-level permission posture picker (deny-all-asks default / auto-execute / read-only observation), the concurrency picker (skip / queue), and the timezone as a visible explicit value pre-filled from your local zone; per-task cost stays honestly "—" until usage collection lands. Under the hood, the read-only posture is now enforced by a real tool-capability category: every built-in tool declares whether it only observes state, and a read-only-postured run refuses any tool that does not (write-class refusal ahead of every permission-mode approval — previously the posture degraded to ask-deny semantics), while refused asks and write-class rejections during a run are recorded into that run's record for the panel to show.
